# LogiFlow Academy — platform blueprint

**Purpose of this document.** It is a complete, self-contained specification of the platform in
this repository, written so that a second agent with no access to these files can rebuild an
equivalent one **for PHP** — same architecture, same learning engine, same honesty, different
subject language.

It is a *blueprint*, not a summary. Where an algorithm matters, the algorithm is here in full.
Where a number matters, the number is here. Where the current implementation has drifted or is
wrong, that is called out rather than copied forward.

Read sections 1–2 for what to build, 3–8 for exactly how it behaves, 9 for what changes when the
subject language is PHP, and 10 for the build order.

---

## 0. One-paragraph version

LogiFlow is **two systems sharing a repository**. The first is a production-shaped .NET
application (logistics/order fulfilment: Clean Architecture, CQRS, EF Core, SQL Server) written to
be *read* — every non-obvious decision commented in the file where it was made. The second is a
**tutorial platform** built around one real job advert: a static, framework-free, offline-capable
site of 48 chapters with a full learning engine (440 quiz questions, spaced repetition, a free
recall drill, a timed mock interview, an Italian language layer, a CV linter) plus a small
accounts API that carries a learner's progress between devices. The two are joined by a course of
28 markdown modules and by an integrity tool that turns every cross-reference between them into a
build failure. The whole thing exists to get one person hired as a .NET developer in
Emilia-Romagna.

A PHP version keeps **all of the machinery** and replaces **all of the subject matter**.

---

## 1. The thesis (do not port the code without porting this)

Six product decisions carry the entire design. A PHP rebuild that drops any of them becomes an
ordinary tutorial site.

1. **Built from one real job advert, and honest about coverage.** Every chapter declares either
   `req` (the line of the advert it answers) or `extra` (why it exists although the advert never
   mentions it). The home page renders those as two separate tables, so the claim "nothing in the
   advert is uncovered" is verifiable rather than asserted.

2. **Every concept explained twice.** A `kid` box (the version you would give a child) and a `pro`
   box (the version you would give an interviewer). A top-bar switch hides one or the other, which
   turns the page into a self-test: read the simple one, produce the professional one from memory.

3. **Progress is measured by retrieval, never by scrolling.** A chapter is worth 25% for reading
   and 75% for the test score. Reading 48 chapters and answering nothing caps you at 25%.

4. **Recognition and recall are different skills, and both are drilled separately.** Multiple
   choice measures recognition; interviews measure recall. So there is a viva page that hides the
   answer until you have committed one, and a simulator that adds a clock and removes the options.

5. **The site works with no server, no build step and no network.** Every page is a real `.html`
   file; the shared navigation is generated by a plain `<script>` so it works from `file://`. An
   account is purely a way to move progress between devices — nothing is behind it.

6. **The accounts service is written in the language being taught, and doubles as portfolio
   code.** Six commented files containing the entire list a junior advert asks about. This is why
   a PHP version must rewrite it in idiomatic PHP rather than keep the C#.

Two further principles run through the prose and should be kept:

- **Honesty over polish.** Deliberate imperfections are labelled as such. The README publishes a
  mutation-testing score that undercuts its own test count. Where a shortcut was taken for
  teaching reasons, the comment says so.
- **Cross-references are content, and content rots silently.** Hence section 8.

## 2. System topology

Five deliverables. Only the first two are strictly required for a v1.

```
site/                    THE PLATFORM.  Static HTML + vanilla JS. No build step. Works on file://
  chapters/*.html          47 chapter pages
  assets/*.js              the manifest, the content banks, and the learning engine
  assets/*.css             two stylesheets, light + dark, no CDN
  sw.js + manifest.webmanifest   offline, installable

<accounts service>       THE API.  Accounts + progress sync + leaderboard. Also serves site/.
                         One process, one URL. SQLite by default so it needs no setup.
                         In this repo: src/LogiFlow.Academy.Api (C#). In a PHP build: PHP.

course/                  THE DEPTH.  28 markdown modules + 50 deeper chapters + two collected
                         pages (GOLDEN-RULES.md, LAWS-OF-CSHARP.md). The site explains a topic
                         well enough to hold a conversation; the module makes you dangerous.

src/ tests/ labs/        THE REFERENCE SYSTEM.  A production-shaped application in the language
                         being taught, heavily commented, with graded exercises, runnable demos
                         and benchmarks beside it. The course points at it constantly.

tools/ + .github/        THE INTEGRITY GATE.  One command that checks every cross-reference in
                         the repository, and CI that fails on it.
```

**Dependency rule:** the site depends on nothing. The API depends on nothing but its own database.
The course depends on the reference system by file path. The gate depends on all of them.

## 3. The content layer

### 3.1 The chapter manifest — the single source of truth

`site/assets/chapters.js`. One array drives the sidebar, the home-page cards, the prev/next
pager, both coverage tables, the sidebar search index, and the service worker's precache list.
Nothing else enumerates chapters.

```js
const PARTS = [
  "Start here",
  "Part 1 — The platform and the language",
  "Part 2 — Data",
  "Part 3 — The web",
  "Part 4 — Fast at scale",
  "Part 5 — Building it properly",
  "Part 6 — Tools and shipping",
  "Part 7 — What the region actually runs",
  "Part 8 — The human requirements",
];

const CHAPTERS = [
  {
    n:     "07",                       // shown in the sidebar; "" for the home page
    id:    "07-async-and-errors",      // === filename in chapters/ without .html
    part:  PARTS[1],
    title: "Async, await and exceptions",
    blurb: "What await really does, why .Result deadlocks, and how to handle failure properly.",
    tags:  "async await task cancellation exception deadlock threadpool",  // extra search terms
    req:   "Ottima conoscenza del linguaggio C#",   // the advert line this answers
    // extra: "..."   ← set INSTEAD of req when the advert never mentions it
  },
  // ...
];

self.PARTS = PARTS;      // `self`, not `window` — sw.js importScripts() this file
self.CHAPTERS = CHAPTERS;
```

`self` rather than `window` is load-bearing: the service worker imports this file so the offline
precache list is generated from the manifest instead of being a second copy that goes stale.
There is no `window` in a worker.

**Adding a chapter:** add the entry, give it `req` or `extra`, copy any chapter file as a
template, set `<body data-chapter="…">` to the same `id`, match the number in `<title>` and in
the `.crumbs` line. Nothing else is touched.

**Renumbering** means renaming files and rewriting every `href`, `<title>`, `.crumbs` and prose
reference. Reading order matters more than stable ids in a tutorial, so do it — but with a
script, and re-run the integrity gate afterwards.

| Markup | Purpose |
|---|---|
| `.box.kid` | 🧒 the explanation you would give a child |
| `.box.pro` | 🎓 the answer you would give in an interview |
| `.box.trap` | ⚠ the mistake people actually make |
| `.box.note` | context, or a pointer into the deep course |
| `.tryit` | something to type, not read |
| `.rules` | the golden-rules card |
| `.qa` | one interview question with a sketched answer |
| `nav#toc` | auto-filled from the `<h2>`s |
| `div#pager` | auto-filled from the manifest |

**Every concept gets both a `kid` and a `pro` box.** This is not decoration — the Both/Simple/Pro
switch in the top bar depends on it, and it is what makes a chapter usable as a self-test.

Diagrams are **inline SVG** using the `d-*` classes in `style.css` so they follow the theme. No
image files, no diagram library.

### 3.3 The question bank

`site/assets/quizzes-1.js`, `-2.js`, `-3.js`. Split only so each file stays editable; all three
merge into one map keyed by chapter id.

```js
window.QUIZZES = Object.assign(window.QUIZZES || {}, {
  "07-async-and-errors": [
    { q:    "the stem — plain text; < and > must be escaped",
      code: "optional snippet rendered in a <pre> above the options",
      a:    ["option 0", "option 1", "option 2", "option 3"],   // 2–5 options
      c:    1,                                                  // or [0, 2] for select-all
      why:  "shown after answering — ALWAYS, including when the answer was right" },
  ],
});
```

Rules that are not negotiable:

- **Question ids are `<chapter-id>#<index>` and the index is the array position.** That id is the
  key a learner's spaced-repetition schedule is stored under. **Append only. Never reorder,
  never delete.** Reordering silently reassigns other people's review history to the wrong
  questions. The integrity gate has a lockfile (`tools/quiz-ids.lock`) specifically to catch it.
- **`why` is shown on correct answers too.** Feedback that only appears on failure teaches people
  to guess and check.
- **Every stem must stand alone two weeks later, out of context.** Each question doubles as a
  flashcard. "Which of these is true?" is a bad stem for that reason; name the subject.

Current volume: **440 questions across 48 chapters**, 8–17 per chapter.

### 3.4 The viva deck — a generated file

`site/assets/rules.js` is **generated** from `course/GOLDEN-RULES.md` by `tools/viva-deck.cs`.
Never hand-edited. Regenerate after editing a rules card, or the drill quietly teaches the old
wording.

```js
window.RULES = [
  {
    "id":     "t12-ienumerable-runs-here-iqueryable-runs-there",  // derived from the claim text
    "kind":   "explain",          // or "complete" for rules with no written justification
    "tier":   "twelve",           // "twelve" | "six" | "" — the interview-priority tiers
    "module": "",
    "part":   "The twelve that decide interviews",
    "claim":  "`IEnumerable` runs here; `IQueryable` runs there.",
    "why":    "Assigning one to the other silently moves the filtering from the database into your process.",
    "continues": false,
    "checkpoints": ["IEnumerable", "IQueryable"],   // code terms matched literally against the answer
    "refs":   ["03", "16"]                          // chapters that earn this rule
  },
];
```

`id` is derived from the claim text, so reordering rules costs nothing and **rewording one resets
that single card's schedule** — which is the correct behaviour, since it is now a different claim.

`checkpoints` are what makes self-marking survivable: the rule's own code terms are matched
literally against what the learner wrote and shown as hit or missed. It cannot tell whether they
were right, but "you never mentioned `rowversion`" is a fact, and facts are harder to mark
generously than feelings.

Current volume: **362 rules**.

### 3.5 The language layer, the glossary and the CV builder

Three smaller banks, all plain arrays in JS files:

- **`glossary.js`** — 133 entries, `{ en, it, cat, where, def }`. `cat` groups them; `where` is a
  chapter number. Two kinds of word, and they are different problems: *technical* terms that stay
  English even in Italian offices (the trap is the ones that **are** translated — `collaudo`,
  `avvio in produzione`, `presa in carico`), and *process/contract* terms that are entirely
  Italian, appear in adverts, and are where a technically strong candidate loses an interview.

- **`italiano.js`** — situational `PHRASES` (opening, buying time, admitting a gap, disagreeing
  politely, asking about the work, salary) plus `IT_CHAPTERS` keyed by chapter id, with one or two
  `say` lines and the terms that `keep` their English. Rendered by `italiano-panel.js` both as a
  per-chapter panel and as the whole phrasebook on `italiano.html`.
  **Coverage is deliberately partial** (31 of 48 chapters) and the panel simply does not appear
  where there is no entry — a half-written translation teaches a sentence you would not want to
  say.
  The English technical nouns stay English on purpose (*la query*, *il deploy*, *fare il merge*):
  that is how the language is actually used in this industry, and translating them marks somebody
  who learned it from a textbook.

- **`cv.js`** — a builder that produces an Italian CV and cover letter from stored fields, then
  **lints them against the CV chapter's own rules**: the GDPR consent line, CEFR language levels,
  bullets that describe a result rather than presence, at least one number, one page. Every
  warning traces to a specific paragraph. It is not an AI that writes your CV; it can only tell
  you when a bullet contains no facts.

### 3.6 The deep course

`course/` is markdown, read in an editor, not served by the site.

- **28 modules**, each `module-NN-slug/README.md`, in five parts, with a fixed five-part shape:
  1. **The idea** — what the concept is and what problem it solves.
  2. **In this codebase** — the exact files that use it.
  3. **Do it** — an exercise, a lab, or a deliberate breakage to observe.
  4. **Golden rules** — the card: the module compressed into a dozen sentences.
  5. **Interview questions** — what you will be asked, with the answer sketched.
- **50 deeper chapters** sitting beside the READMEs, one per topic, linked from a contents table
  at the top of each module. These are what the `Covered in:` comments in the source point at, so
  reading a class and reading its chapter are one gesture.
- **`GOLDEN-RULES.md`** — every module's card, in module order, plus two priority tiers at the
  top: *the twelve that decide interviews* and *the six that separate a senior candidate*. This
  file is the source the viva deck is generated from.
- **`LAWS-OF-CSHARP.md`** — the same knowledge reorganised **by concept** into twelve books, so
  that when something surprises you it is findable by *what kind of thing it was*. (Rename for
  PHP: `LAWS-OF-PHP.md`.)
- **`SOLUTIONS.md`** — worked answers to the labs, with the reasoning.

The site and the course are deliberately different depths: **read a chapter to understand a
topic, read the module to be dangerous with it.**

## 4. The learning engine

Everything in this section lives in `site/assets/store.js` behind one global, `window.LF`. No
other script touches `localStorage` directly, because a profile can live in three places
(memory, `localStorage`, a server) and only one file should know that.

### 4.1 Storage contract

- One `localStorage` key: `logiflow.profile.v1`.
- **Every access is wrapped in try/catch.** `localStorage` throws in private windows and some
  embedded viewers; a failure downgrades to memory-only rather than taking the page down.
- Writes are debounced 250 ms (dragging a sticky note fires a save per pixel), with a
  `beforeunload` flush so a tab closing mid-debounce loses nothing.
- Migrations are **forward-only**, in `migrate()`. Never rename a field without one — somebody has
  a month of study in the old shape.

### 4.2 The profile document — complete schema

This is the exact object stored locally *and* the exact JSON body sent to the API.

```jsonc
{
  "v": 1,
  "id": "guest",
  "name": "Guest",
  "email": "",
  "createdAt": "ISO-8601",
  "updatedAt": "ISO-8601",
  "xp": 0,

  // per chapter id
  "chapters": {
    "07-async-and-errors": {
      "read": true, "readAt": "ISO", "best": 0.85, "attempts": 3,
      "lastAt": "ISO", "seconds": 412, "perfect": false
    }
  },

  // spaced repetition, keyed "<chapter-id>#<index>"
  "cards": {
    "07-async-and-errors#3": {
      "ease": 2.5, "interval": 4, "reps": 2, "lapses": 1,
      "due": "2026-09-10", "last": "2026-09-06", "grade": 2
    }
  },

  // the same shape, keyed by rule id — a SEPARATE map, see note below
  "viva": { "t12-a-linq-query-is-a-recipe-not-a-result": { /* identical fields */ } },

  "notes": [{
    "id": "n…", "ch": "07-async-and-errors", "chTitle": "…", "text": "…",
    "color": "yellow", "x": 24, "y": 24, "pinned": false, "quote": "…",
    "createdAt": "ISO", "updatedAt": "ISO"
  }],

  "badges": { "first-test": "ISO-8601 when earned" },

  "attempts": [{ "ch": "07-…", "at": "ISO", "correct": 9, "total": 11, "s": 240 }],  // capped 400

  // per local calendar day
  "history": {
    "2026-09-06": { "xp": 85, "cards": 12, "answers": 20, "correct": 17,
                    "minutes": 0, "cardXp": 60, "viva": 4 }
  },

  "streak": { "count": 5, "best": 12, "lastDay": "2026-09-06" },
  "goals":  { "dailyXp": 60, "dailyCards": 20 },
  "remote": { "userId": "", "syncedAt": "", "dirty": false },

  // added on first mock exam
  "examBest": 0.84,
  "examCount": 3

```

**Why `viva` is a separate map from `cards`.** The review page counts `cards` against the size of
the question bank and says "N of 440 questions are in your schedule". Mixing 362 rules into that
map makes every one of those sentences a lie. The *scheduler* is shared; the *piles* are not.

**A study day is local, not UTC.** `today()` formats the local calendar day as `YYYY-MM-DD`, and
day arithmetic parses `<day>T12:00:00Z` to dodge DST edges entirely. A 23:00 session in Italy must
not count as tomorrow.

### 4.3 Course mastery — the one honest percentage

```
per chapter:   0.25  if read
             + 0.75 × min(1, best test score)

mastery %   =  ( Σ chapter points / chapterCount ) × 100     rounded to 1 decimal
```

A chapter counts as **passed** at `best >= 0.8`.

**This formula is implemented twice** — in `mastery()` in `store.js` and server-side, because the
leaderboard needs it there. Both copies carry a comment saying so, and a server test is what
catches them drifting apart. Three specific hazards:

1. **Rounding.** .NET's default is banker's rounding (6.25 → 6.2) while JavaScript's `Math.round`
   is half-up (6.3). The server uses `MidpointRounding.AwayFromZero` to match. Any reimplementation
   must pick half-up explicitly. In PHP, `round()` is already half-up — match it, do not
   "improve" it.
2. **The denominator.** The browser uses `window.CHAPTERS.length`. The server uses a config key.
   **These have already drifted in this repo once** — the site grew and the API config stayed on
   39, so the leaderboard reported a higher mastery than the dashboard until it was caught. A
   `doctor.cs` check now compares the browser count, the config key and the compiled-in fallback,
   and fails on any disagreement. See §11.
3. **Clamping.** The server clamps `best` to 0–1 and the result to 0–100, because the document is
   client-supplied and a hand-edited profile must not be able to show 4000%.

`partMastery(part)` does the same arithmetic over one sidebar group, for the section progress bars.

### 4.4 XP, levels, streaks

| Action | XP |
|---|---|
| Read a chapter (first time) | 10 |
| Pass a chapter test (first time at ≥ 80%) | 50 |
| Perfect score on a chapter test (first time) | 25 |
| Flashcard reviewed — right | 5 |
| Flashcard reviewed — wrong | 2 |
| Viva rule recited — right | 8 |
| Viva rule recited — wrong | 3 |
| A day added to the streak | 15 |
| Mock exam | 2 × correct answers |

**Daily flashcard XP cap: 240.** Card and viva XP share the cap, so the two decks cannot be farmed
in parallel. Reviewing 400 cards in one sitting is not four hundred cards' worth of learning, and
a number that only goes up teaches you to farm it.

Levels, named for the job:

| XP | Level |
|---|---|
| 0 | Curioso |
| 250 | Stagista |
| 700 | Junior Developer |
| 1 500 | Developer |
| 2 800 | Mid Developer |
| 4 600 | Senior Developer |
| 7 000 | Tech Lead |
| 10 000 | Architetto |

**Streak:** `touchStreak()` is called once per meaningful action. If the last study day was
yesterday the count increments; any larger gap resets it to 1; the same day is a no-op. `best` is
the maximum ever. The streak is "alive" if the gap to today is ≤ 1 day.

### 4.5 Spaced repetition — SM-2, lightly modernised

One implementation, shared by both decks. Grades are `0 = wrong`, `1 = right but hesitant`,
`2 = right and certain`.

```
MIN_EASE = 1.3,  MAX_EASE = 3.2,  MAX_INTERVAL = 180 days
new card: { ease: 2.5, interval: 0, reps: 0, lapses: 0, due: today, last: "", grade: -1 }

grade == 0:
    lapses += 1
    reps    = 0
    interval= 1
    ease    = max(1.3, ease - 0.2)      // small penalty: one bad day must not bury a known card

grade >= 1:
    reps += 1
    interval = reps == 1 ? 1
             : reps == 2 ? (grade == 2 ? 4 : 3)
             : round(interval * ease)

    if grade == 1:                       // hesitant
        ease     = max(1.3, ease - 0.15)
        interval = max(1, round(interval * 0.7))
    else:                                // certain
        ease     = min(3.2, ease + 0.1)

interval = min(interval, 180)
due      = today + max(1, interval)
last     = today
grade    = grade
```

**Due selection** (`due()` / `vivaDue()`): everything with `due <= today`, sorted **most overdue
first**, ties broken by **most lapses**, optionally limited.

**Why the schedule is global rather than per chapter:** a review session then naturally mixes
async with T-SQL with Docker. That is *interleaving* — harder, better retention, and exactly what
an interview does to you.

**The "I half-guessed" button is the only signal the scheduler cannot derive.** A right answer you
had to dig for is not the same as one you knew, and scheduling them identically is why so many
flashcard apps stop working after a month.

Derived statistics:
- `recall()` — % of scheduled cards that are "strong" (`reps >= 2 && interval >= 4`).
- `weakest(n)` — chapters ranked by total lapses, for the "what to fix" panel.
- `vivaStats(total)` — seen / total / due / strong / lapsed / clean.

### 4.6 Badges

21 badges, each `{ id, icon, name, hint, test(profile) -> bool }`. Checked after every XP award,
coalesced into one pass per tick; once earned, never revoked; the earn timestamp is stored.

`first-step` (read one chapter) · `first-test` (pass any test) · `perfect` (100% on one) ·
`perfect-five` (100% on five) · `streak-3` · `streak-7` · `streak-30` · `cards-100` · `cards-500` ·
`faced-errors` (every lapsed card back to a ≥ 4-day interval) · `half` (50% mastery) ·
`the-advert` (pass every chapter with a `req`) · `the-edge` (pass every chapter with an `extra`) ·
`complete` (99% mastery) · `exam-pass` (80% on a mock exam) · `exam-ace` (95%) ·
`note-taker` (ten notes) · `viva-first` · `viva-50` · `viva-twelve` (all twelve tier-one rules
graded 2) · `night-owl` (answer something between 00:00 and 05:00).

Note `viva-twelve` reads `window.RULES`, which is only loaded on the viva page — which is exactly
when it can become true. Every other page leaves it alone.

### 4.7 The five retrieval surfaces

One renderer (`quiz.js`, `window.LFQuiz.mount(host, opts)`) serves the first three, because they
are the same thing with different question sources.

| Surface | Page | Source | Options shown | Clock | Records |
|---|---|---|---|---|---|
| **Chapter test** | any chapter | that chapter's bank | yes | no | `recordTest()` → chapter best, XP, badges |
| **Review** | `review.html` | today's due cards, all chapters | yes | no | `LF.review()` per card |
| **Mock exam** | `exam.html` | random mixed | yes | yes | `examBest`, `examCount`, 2 XP/correct |
| **Viva** | `viva.html` | the 362 rules | **no** | no | `LF.vivaReview()` |
| **Simulator** | `simulate.html` | rules **and** bank, options stripped | yes, hard | transcript only |

**Quiz interaction is three clicks or fewer per question:** pick an option → feedback appears
immediately and always → say how it felt ("I was sure" / "I half-guessed"; a wrong answer needs no
button, it graded itself) → next.

Exam presets: 15 q / 10 min, 30 q / 22 min, 50 q / 40 min, plus untimed. Pass mark 80%.

**The viva** shows a rule's claim and hides everything else until an answer is committed — or
"I can't say it" is pressed, which grades 0 *before* revealing anything. Retrieval only
strengthens a memory when it is actually attempted; a button that shows the model answer while you
are still thinking converts the exercise back into reading. Then the written justification appears
beside the learner's own words, checkpoint terms are shown hit/missed, and they self-mark 0/1/2.
Two toggles change what the practice is: **speak instead of type**, and **rispondi in italiano**
(the technical terms stay English either way).

**The simulator** adds the three things nothing else reproduces: a clock (~90 seconds), no
stopping and no going back, and the non-technical parts — it opens with *"mi parli di lei"* and
closes with *"ha domande per noi?"*, the two questions asked in every interview and prepared for in
almost none. Rounds: Screening 10 min / 6 technical, Primo colloquio tecnico 20 min / 12, Giornata
intera 35 min / 20. Bank questions are asked **without their options**, which turns recognition
items into recall items at no content cost.

**It produces a transcript, not a score.** A self-marked percentage is a number about your
generosity; what you said, next to what the course says, with the time you took, is not.

## 5. The accounts service

### 5.1 What it is for, twice over

**For the learner:** the site saves everything in the browser, which is fine until you want it on
your phone too, or two people share one machine.

**For the portfolio:** it is deliberately small enough to read in one sitting and contains, in
about six files, the entire list a junior advert asks about — routing, dependency injection, an
ORM, JWT authentication, refresh-token rotation, password hashing, middleware order, CORS, rate
limiting and optimistic concurrency, every non-obvious decision commented with *why*.

It references nothing else in the repository and nothing references it. Two systems sharing a
repository and nothing else.

### 5.2 The endpoint contract

| Method | Route | Auth | Purpose |
|---|---|---|---|
| `POST` | `/api/auth/register` | — | Create an account, sign in, return the **one-time recovery code** |
| `POST` | `/api/auth/login` | — | Sign in with a **username** and password |
| `POST` | `/api/auth/refresh` | — | Exchange a refresh token for a new pair |
| `POST` | `/api/auth/logout` | — | Revoke one refresh token |
| `POST` | `/api/auth/forgot-password` | — | Username + recovery code → a single-use reset ticket |
| `POST` | `/api/auth/reset-password` | — | Spend the ticket, set the password, get a fresh code |
| `POST` | `/api/auth/recovery-code` | Bearer | Replace the recovery code with a new one |
| `GET`  | `/api/auth/me` | Bearer | The signed-in user |
| `GET`  | `/api/profile` | Bearer | The stored progress document (**204** when there is none yet) |
| `PUT`  | `/api/profile` | Bearer | Store it (**409** carrying the current document when the revision is stale) |
| `GET`  | `/api/leaderboard` | Bearer | Top fifty learners who have not opted out |
| `PUT`  | `/api/me/leaderboard?visible=` | Bearer | Show or hide yourself |
| `DELETE` | `/api/me` | Bearer | Delete the account, its progress and its sessions |
| `GET`  | `/api/health` | — | Liveness. **Deliberately does not touch the database** |

Payloads (camelCase JSON both ways):

```jsonc
// POST /api/auth/register   { username, displayName?, password }
// POST /api/auth/login      { username, password }
// POST /api/auth/refresh    { refreshToken }
// POST /api/auth/logout     { refreshToken }
// → AuthResponse
{ "accessToken": "eyJ…", "refreshToken": "…", "expiresInSeconds": 900,
  "user": { "id": "uuid", "username": "…", "displayName": "…" },
  "recoveryCode": "A1B2C-…"   // ONLY on register and a completed reset; null otherwise
}

// POST /api/auth/forgot-password  { username, recoveryCode }
// → { "resetToken": "…", "expiresInSeconds": 900 }
// POST /api/auth/reset-password   { resetToken, newPassword }  → AuthResponse (with a fresh code)
// POST /api/auth/recovery-code    → { "recoveryCode": "…" }

// GET  /api/profile → { "data": {…}, "updatedAt": "ISO", "revision": 7 }
// PUT  /api/profile   { "data": {…}, "updatedAt": "ISO", "baseRevision": 7 }
//      200 → same shape as GET     409 → same shape, carrying the CURRENT document
//      413 → document over 1 MiB   400 → data is not a JSON object

// GET  /api/leaderboard → [ { displayName, xp, masteryPercent, streakDays, chaptersPassed, isYou } ]
```

Errors are RFC 9457 Problem Details with a `traceId` extension. `401` for bad credentials, `409`
for a taken username, `423` for a locked account, `429` for rate limiting.

### 5.3 Data model — four tables

```
Users
  Id                    uuid v7 PK (time-ordered: does not fragment the index)
  Username              varchar(32)  UNIQUE, stored already normalised (trimmed, lower-cased)
  DisplayName           varchar(60)
  PasswordHash          varchar(128)
  PasswordSalt          varchar(64)
  PasswordIterations    int
  RecoveryCodeHash      varchar(64)
  RecoveryCodeIssuedAt  timestamptz
  CreatedAt             timestamptz
  LastSignInAt          timestamptz null
  FailedAttempts        int
  LockedUntil           timestamptz null
  ShowOnLeaderboard     bool  default true          -- opt-OUT, not opt-in

Profiles
  UserId          uuid PK / FK → Users  ON DELETE CASCADE
  Document        text            -- the whole progress JSON, no length limit
  Revision        int             -- optimistic concurrency, hand-written
  ClientUpdatedAt timestamptz     -- the client's own stamp, used by its merge
  UpdatedAt       timestamptz
  Xp              int             ┐
  MasteryPercent  double          │ denormalised FROM the document on every write,
  StreakDays      int             │ because the leaderboard orders by them
  ChaptersPassed  int             ┘
  INDEX (Xp DESC)

RefreshTokens
  Id uuid PK · UserId FK CASCADE · TokenHash varchar(64) UNIQUE INDEX
  ExpiresAt · CreatedAt · RevokedAt null · ReplacedByTokenHash varchar(64) null

PasswordResetTokens
  Id uuid PK · UserId FK CASCADE · TokenHash varchar(64) UNIQUE INDEX
  ExpiresAt · CreatedAt · UsedAt null
```

**Why the profile is a blob and not a schema.** Its shape is owned by the browser and changes
with every learning feature — a new badge, a new counter, a different card field. Modelling it
relationally means a migration per badge, for data that is never queried by its parts: the server
only ever reads and writes the whole thing. The four columns that *are* promoted exist because the
leaderboard queries them, and querying inside a JSON column across two database engines is exactly
the sort of cleverness that stops working when somebody switches engine. They are denormalised
copies written on save; the document remains the source of truth.

**The server re-derives those four figures from the document rather than trusting a client
summary.** The document is the learner's own data and there is no point policing it — but the
leaderboard is shared, and a number that appears next to other people's names should not be one
the browser simply asserted. It is still not a ranking of record (anyone can edit their local
profile and sync it), and the honest thing is to say so rather than build defences that do not
hold.

**Every read of the document is defensive.** It was produced by a browser that may be running an
older version of the site, so a missing or wrongly-typed property is expected input, not an error.
A malformed profile must never be able to fail a sync — it produces zeroes, not a 500.

### 5.4 The six decisions worth reading (keep all of them)

**1 · No email address, anywhere.** The login is a username. There is no `Email` column and no
mail transport, and those two facts are the same decision: an address this service can never send
to could never be verified, never be written to and never recover an account, so storing one would
be personal data collected for no purpose — precisely what GDPR's data-minimisation principle
exists to stop.

Which leaves the obvious question: **how do you reset a password with no email?** Not by asking
for the username and believing the answer — that is an account takeover with a form around it.
Every account is issued a **recovery code** at registration: 20 characters of Crockford base32
(alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, ~100 bits), grouped in fives with dashes, shown
exactly once, stored only as a SHA-256 hash. Presenting it mints the reset ticket an emailed link
would otherwise have carried. It is spent on use and replaced, and a learner who still has access
can swap it for a new one at any time. Normalisation is forgiving: case-insensitive, dashes and
spaces stripped, `I`/`L` → `1`, `O` → `0`.

What it honestly is **not** is proof that anyone can still reach you — an email loop also confirms
the mailbox works. A lost code here is a lost account, and the site says so in those words rather
than pretending there is a way round it.

**2 · Passwords: PBKDF2-SHA256, salted, cost stored per user.** 210 000 iterations, 16-byte salt,
32-byte output, minimum 10 characters. A plain fast hash is the trap — strong *and fast*, and fast
is the wrong property when an attacker has a GPU. The iteration count lives in the user row so it
can be raised later without invalidating existing accounts: an old hash still verifies against its
own count and is silently re-hashed on the next successful sign-in. Comparison is constant-time.

**3 · A wrong password and an unknown account are indistinguishable.** Same message, same status,
and on the unknown-account path the server **burns equivalent PBKDF2 work** so the timing does not
leak either. The login form must not be an account-enumeration oracle.

**4 · Refresh tokens: hashed at rest, rotated, and a replay kills the family.** 32 random bytes,
base64url. Only the SHA-256 is stored — a refresh token is a bearer credential, so a stolen dump
must not hand over working sessions. Every refresh issues a new token, marks the old one used and
records which token replaced it. If a used token turns up again, the server cannot tell a thief
from a client that lost a response, so it revokes **every** session for that user.

Note the asymmetry, and keep it: a **fast** hash here where the password needed a **slow** one.
The reason is entropy. This token is 256 random bits, so a fast hash costs an attacker nothing to
begin with. PBKDF2's slowness only ever buys anything against a low-entropy, human-chosen secret.
The recovery code follows the same rule.

**5 · Lockout and rate limiting are different defences and neither substitutes for the other.**
8 consecutive failures locks the account for 15 minutes (per-account: stops credential stuffing
against one login). 10 requests per minute per IP on `/api/auth/*` (per-IP: stops a spray across
many accounts). `/api/health` is deliberately outside the limiter.

**6 · Static files above routing.** This was a bug before it was a decision. Static-file middleware
stands aside once an endpoint has been matched, and the framework inserted its routing step at the
*top* of the pipeline — so the catch-all `404` route matched `/` first and the home page 404ed
while every other page worked. Serving static files **before** routing fixes it and is better
anyway: the tutorial is public, so a stylesheet should never pay for route matching, token
validation or a rate-limit permit. A test named *every public page and asset is served
anonymously* keeps it that way.

Pipeline order, which is behaviour, not taste:

```
exception handler → status-code pages → static files → routing → CORS
  → rate limiter (before auth: rejecting a flood should be cheap) → authentication → authorization
  → endpoints → catch-all 404 (anonymous)
```

**Two clocks are one clock.** A clock abstraction is injected rather than "now" being called in
six places. Token expiry, lockout windows and streaks are all time-dependent, and a test that has
to wait fifteen real minutes to prove a token expired is a test nobody runs.

### 5.5 Configuration and schema management

Everything has a working default; the service must run with **no configuration at all**.

| Key | Default | Notes |
|---|---|---|
| provider | `Sqlite` | or a server engine |
| connection string | a file under `App_Data/` | required for the server engine |
| JWT signing key | generated in Development | **required** elsewhere; startup fails without it |
| access token lifetime | 15 min | short, because a JWT cannot be revoked |
| refresh token lifetime | 30 days | stateful and revocable |
| chapter count | *(mastery denominator)* | **must equal the manifest length — see §11** |
| auth requests/minute | 10 | per IP |
| allowed origins | localhost ports + `null` | `null` is the origin a `file://` page sends |

**The signing key** is generated on first run in Development and kept in a git-ignored file so
restarting does not sign everybody out. **No key is committed** — anyone holding it can mint a
token for any user. Outside Development a missing key stops the process at startup rather than
producing a service that boots green and fails at the first sign-in. Validate configuration at
startup, not at first use.

**Schema:** create-if-missing on first launch, not migrations — a single instance, a small schema,
no upgrade history to preserve. That trade is right *here* and wrong almost everywhere else: the
same shortcut in a multi-instance deployment races on startup and forces the runtime account to
hold schema-altering permissions. If this ever grows a second instance, the fix is real migrations
run as a separate pipeline step. The current code also detects a database that predates a schema
change and fails with an instruction rather than a stack trace.

### 5.6 What the tests assert

83 tests against a real relational engine in memory (**not** a fake in-memory provider, which is
not a database and happily passes tests that fail against anything you would deploy). Beyond the
happy paths, port these assertions:

- a wrong password and an unknown account produce the **same** message
- a forged token signature is rejected
- a used refresh token cannot be replayed, and replaying one revokes the whole family
- a stale `baseRevision` gets a 409 **carrying the current document**
- one learner cannot read another's profile
- a malformed progress document produces zeroes rather than a 500
- a mastery percentage cannot be inflated past 100 by a hand-edited profile
- the rate limiter throttles repeated sign-ins **and** leaves `/api/health` alone
- every public page and asset is served anonymously, and every unknown path is a 404, not a 401

## 6. The sync protocol and the merge

Client side, in `account.js`. Session state lives in `localStorage` under five keys:
`logiflow.api.base`, `.token`, `.refresh`, `.user`, `.revision`.

**API base resolution:** if the page is served over http(s) the API is the same origin and no
configuration is needed. Opened from `file://` there is no origin to guess, so it stays empty
until somebody types one in. Changing it necessarily signs you out — the token in this browser was
minted by the old server — but leaves local progress untouched, which is what makes it a safe
thing to let anyone do.

**Transport:** every request carries `Authorization: Bearer`. A `401` triggers one refresh and one
retry, then gives up. A `204` body is drained rather than abandoned (an unread response shows up
in the network panel as an aborted request, which looks like a bug).

**The recovery code is deliberately never written to `localStorage`.** Somewhere a person will
actually keep it is the point, and a browser somebody can clear is not that.

**The cycle** is *pull → merge → push*, coalesced, triggered 4 seconds after any profile change
and on demand:

```
pull()  GET /api/profile              → { data, updatedAt, revision } | null (204)
merged = merge(local, remote.data)
if merged ≠ local     → LF.replace(merged)      (the local copy adopts the merge)
if merged ≠ remote    → PUT /api/profile { data: merged, updatedAt, baseRevision: remote.revision }
                        409 → the response carries the current document; merge again and retry
store the returned revision; stamp syncedAt in memory only
```

`syncedAt` is stamped **in memory, never persisted** — persisting it would go through `save()`,
which emits `change`, which schedules another sync four seconds later, which stamps it again. It
is stamped even when nothing was sent, because "last synced" that only moves when something
changed is a clock that stops whenever you are up to date.

### The merge — field by field

Two devices editing the same profile is the normal case, not the exception: you answer questions
on a laptop and review cards on a phone. Last-write-wins silently throws one of them away.
**The merge is deliberately conservative — nothing is ever removed by it**, because losing a month
of study to a sync bug is unrecoverable and having a stale note is not.

| Field | Rule |
|---|---|
| `xp`, `examBest`, `examCount` | maximum |
| `updatedAt` | newer |
| `createdAt` | earlier |
| `name` | from whichever side has the newer `updatedAt` |
| `chapters[id]` | `read` = OR · `readAt` = **earlier** · `best`/`attempts`/`seconds` = max · `lastAt` = newer · `perfect` = OR |
| `cards[id]`, `viva[id]` | the device that reviewed **most recently** (`last`) owns `ease`, `interval`, `due`, `grade`; `reps` and `lapses` take the **maximum** of the two, because both reviews really did happen |
| `notes` | union by `id`, newest `updatedAt` wins |
| `badges` | union; keep the **earlier** timestamp — once earned, earned |
| `history[day]` | per-field **maximum**, never a sum (the same session could otherwise be counted twice) |
| `streak` | `count`/`lastDay` from whichever has the later `lastDay`; `best` = max |
| `attempts` | concatenate, dedupe on `(ch, at)`, sort by time, keep the last 400 |

## 7. Offline and installability

`sw.js` plus `manifest.webmanifest`. The site installs as an app and works with the network
unplugged.

- **Precache everything on install**: a hard-coded shell list (every non-chapter page, both
  stylesheets, every script) **plus every chapter, generated from the manifest** via
  `importScripts("assets/chapters.js")`. Files are added individually with a caught rejection, so
  one typo in the shell list cannot make the site un-upgradeable; the failures are logged and the
  install completes.
- **`activate` deletes every cache whose name is not the current one**, then claims clients.
- **Fetch: cache-first with a background refresh** (stale-while-revalidate). The reasoning is
  specific: this is a course, not a feed. A chapter one version old is fine to read and a spinner
  is not. Network-first would be right where staleness is a correctness problem; it is not right
  for a tutorial.
- **It never touches `/api/`, non-GET requests, or another origin.** Sign-in, sync and the
  leaderboard need the network and must fail honestly without it — a cached 200 for "here is your
  profile" would be a lie with somebody's progress attached.

> **The cache name is the version. Bump it on every content change.** A new name rebuilds
> everything and deletes the old; there is no partial invalidation and you do not want one. Forget
> it and returning visitors keep last month's chapters with no error anywhere — the single most
> common service-worker bug.

Service workers only run over http(s), so opening from disk skips all of this silently. That is
correct, and the site checks `location.protocol` before registering so the console stays clean on
`file://`.

## 8. The integrity gate

Almost everything valuable here is a **cross-reference**, and a cross-reference is the one kind of
content that rots without a symptom. A broken build shouts. A pointer to a chapter renamed six
weeks ago says nothing at all, to anybody, ever — and the reader who follows it concludes the
repository is sloppy rather than that one line is.

One command (`tools/doctor.cs`, a standalone file-based app deliberately outside the product's
build graph so it can run on a machine with no database) runs **twelve checks**:

| Check | What it couples |
|---|---|
| `site/manifest` | manifest entries ⇄ chapter files — no orphans, no missing |
| `site/links` | every relative link in every page resolves |
| `site/quiz-bank` | every chapter has questions; no questions for a chapter that does not exist; every `c` index is inside its own `a` array |
| `site/quiz-ids` | question ids against `tools/quiz-ids.lock` — **catches a reordered or deleted question** |
| `viva/deck` | `rules.js` is in step with `GOLDEN-RULES.md` |
| `course/golden-rules` | each module's own card ⇄ the collected page |
| `docs/links` | every markdown link resolves |
| `course/sections` | code comments citing a course **section number** still point at that heading |
| `code/covered-in` | every `Covered in:` comment in the source points at a file that exists |
| `labs/demos` | every demo cited by name in the course is registered in the runner |
| `docs/counts` | **every count stated in prose** matches reality — registered sentences, then a scan of every number next to a counted noun |
| `site/chapter-count` | the mastery denominator in the API still equals the number of chapters the site ships |

Report an **Error** for something definitely wrong and a **Warning** for something probably wrong;
only Errors set the exit code, because a gate people learn to ignore is worse than no gate.

Four of these had already broken at least once when they were written; the counts check was broken
in twenty-three places the first time it ran.

CI runs six jobs that fail for six different reasons: cross-references, build + unit tests,
integration tests against a real database, **"the lab exercises must still fail"** (somebody
committing the answers over the exercises is a real failure mode), vulnerable packages, and a
weekly mutation-testing run.

### 9.2 Stack mapping for the accounts service

The service is portfolio code, so it must be idiomatic **and** readable end to end in one sitting.
Two viable shapes — pick deliberately and say why in the README:

- **Slim 4 + PDO** (recommended). Closest to the original's spirit: an explicit middleware
  pipeline you can read, ~6 files, no magic. Middleware order stays a visible decision, which is
  half of what the chapter on it teaches.
- **Laravel**. What the Italian market actually tests. Costs the "read it in one sitting" property
  and hides the pipeline behind conventions — but if the target adverts say Laravel, the portfolio
  argument may outweigh the pedagogical one. Symfony likewise.

| Concern | .NET here | PHP equivalent |
|---|---|---|
| Password hashing | PBKDF2-SHA256, 210k, cost in a column | **`password_hash($p, PASSWORD_ARGON2ID)`** + `password_verify` + `password_needs_rehash` |
| Timing-safe compare | `CryptographicOperations.FixedTimeEquals` | `hash_equals()` |
| Dummy work on unknown user | `BurnEquivalentWork()` | `password_verify($p, $KNOWN_DUMMY_HASH)` |
| CSPRNG | `RandomNumberGenerator.GetBytes` | `random_bytes()` / `random_int()` |
| Token hash | SHA-256 → base64 | `hash('sha256', $t, true)` → `base64_encode` |
| JWT HS256 | `JwtSecurityTokenHandler` | `firebase/php-jwt`, or ~40 hand-written lines (fits the ethos better and is teachable) |
| ORM | EF Core | **PDO + hand-written SQL** (readable, and teaches the SQL chapters), or Doctrine/Eloquent if the adverts demand it |
| Default database | SQLite file, created on first run | **SQLite via PDO**, same decision, same argument |
| Server database | SQL Server | **MySQL/MariaDB** (what the PHP market runs) — the T-SQL chapters become MySQL chapters |
| DI container | built-in | PHP-DI, or explicit construction in one bootstrap file |
| Clock injection | `TimeProvider` | a `ClockInterface` (PSR-20) with a `FrozenClock` for tests |
| Rate limiting | built-in limiter | a small table keyed by IP + minute, or APCu |
| Config | appsettings + env | `.env` + a typed config array, **validated at startup** |
| Schema creation | `EnsureCreated()` | a `schema.sql` applied when the table list is empty |
| Static hosting + fallback | static files above routing | the same order; on the PHP dev server, a router script that returns `false` for existing files |
| Tests | xUnit + in-memory SQLite | **PHPUnit + `sqlite::memory:` through the real PDO driver** |
| UUID v7 | `Guid.CreateVersion7()` | `ramsey/uuid` v7, or 16 hand-built bytes |

**One genuine improvement to make and to write up:** PHP's `password_hash` stores the algorithm
and its parameters *inside* the hash string, so the `PasswordSalt` and `PasswordIterations`
columns disappear and `password_needs_rehash()` replaces the hand-written upgrade check. That is
the same decision, better expressed — say so in the comment rather than silently dropping two
columns.

**Two things not to "improve":** the mastery rounding (keep half-up, matching JS) and the
`viva`/`cards` split.

### 9.3 A chapter map for the PHP market

The original is built from **one real advert**, and everything downstream depends on that. So
**step one of a PHP build is not writing chapters — it is collecting three to five real PHP job
adverts** from the target market and deriving the manifest from them. The map below is a
defensible starting point, not a substitute for that.

For Emilia-Romagna the PHP market differs from the .NET one in ways that must shape the content:
**e-commerce platforms (Magento, PrestaShop, WooCommerce) and WordPress are a huge share of Italian
PHP work**, MySQL/MariaDB replaces SQL Server, and Laravel/Symfony replace ASP.NET.

```
Start here
```

### 9.4 The reference system

The .NET half is a logistics/order-fulfilment domain: orders with a **state machine**
(`Draft → Submitted → Confirmed → Shipped → Delivered`, plus `Cancelled` — and *not* from
`Shipped`, because once it is on a lorry "cancel" is a returns process), strongly-typed ids, money
as a value object, `Result` instead of exceptions for expected failures, optimistic concurrency
with a row version, domain events dispatched inside the transaction, a transactional outbox, and
an email queue claimed atomically.

**Keep the domain.** Order fulfilment is a good teaching domain in any language: it has real
invariants, real concurrency (two people reserving the last unit), real money arithmetic and real
state. Rebuild it in PHP with the same shape and the same commented trade-offs, scaled to what PHP
idiom supports:

- value objects → `final readonly class Money` with `BCMath` or integer minor units (**never
  floats for money** — the same lesson, a better demonstration in PHP)
- strongly-typed ids → `final readonly class OrderId` wrapping a UUID
- `Result<T>` → a small `Result` class, or typed exceptions with a documented boundary
- the state machine → a backed enum with an allowed-transitions map
- optimistic concurrency → a `version` column and `WHERE version = ?` on update, 409 on zero rows
  affected
- domain events → dispatched inside the transaction, same as here
- the outbox → identical; it is a database pattern, not a language one
- architecture tests → **a real PHP option**: `deptrac` or `phpat` will fail the build if the
  domain layer references the ORM, which is exactly what the .NET architecture tests do

And keep the three companion projects: graded exercises that are **deliberately red** until the
learner makes them green, runnable demos that make invisible behaviour visible (a race condition,
an N+1, a memory leak), and benchmarks so every performance claim in the course is checkable.

### 9.5 The honesty layer

Port this, not just the features. It is most of what makes the repository trustworthy:

- Label deliberate imperfections **in place**, with the reasoning and the fix beside them.
- Publish a metric that undercuts your own headline metric (here: mutation score against test
  count — `infection/infection` is the direct PHP equivalent and should be wired in).
- Say plainly what a mechanism does *not* prove — the leaderboard is a nudge, not an audit; a lost
  recovery code is a lost account; a self-marked mock produces a transcript, not a score.

## 10. Build order

Nine phases. Each ends with something that works.

1. **Collect the adverts.** Three to five real PHP postings from the target market. Derive the
   manifest (`chapters.js`) from them; every entry gets a `req` or an `extra`. Nothing downstream
   is stable until this is.
2. **The shell.** Copy `style.css`, `learn.css`, `site.js`, `chapters.js`, `index.html` and one
   chapter. Sidebar, TOC, pager, search, theme and the Simple/Pro switch working from `file://`
   with a single chapter. This is a day, and it de-risks everything after it.
3. **The engine, unchanged.** `store.js`, `quiz.js`, `learn.js`, `notes.js`, `review.html`,
   `exam.html`, `dashboard.html`, `notes.html`. Write ~20 questions for the one chapter and verify
   the whole loop: answer → feedback → grade → schedule → XP → badge → mastery.
4. **Content, in bulk.** Write the chapters and their questions. This is the bulk of the work —
   47 chapters and ~430 questions. Append-only discipline on the bank from the first question.
5. **The deep course.** The modules, in the five-part shape, and `GOLDEN-RULES.md` as you go.
6. **The viva.** Write the deck generator (`GOLDEN-RULES.md` → `rules.js`, ids derived from the
   claim text), then `viva.html` and `simulate.html`.
7. **The accounts service.** The contract in §5.2, the schema in §5.3, every decision in §5.4, and
   the test list in §5.6. Point the site at it; verify the two-device merge with two browsers.
8. **Offline and install.** `sw.js`, `manifest.webmanifest`, and the discipline of bumping the
   cache name.
9. **The gate.** The twelve checks, the quiz-id lockfile, and CI. Do this **before** the content is
   finished, not after — its whole value is catching rot as it happens.

The Italian layer, the glossary and the CV builder can be slotted in any time after phase 4.

## 11. Known drift and bugs — do not reproduce these

The first two were live in this repository until 2026-09-06. They are described in the past tense
because they are fixed, and kept here because a PHP build will hit both.

1. **The mastery denominator drifted, and the leaderboard was silently the more generous of the
   two.** The browser divides by `window.CHAPTERS.length`; the API divided by a config key with a
   compiled-in fallback. The site grew to 47 chapters and the API stayed on 39, so for that whole
   period the same profile scored one percentage on the learner's own dashboard and a higher one
   on the leaderboard beside other people's names. Nothing failed and nobody was told — the only
   symptom was a number being wrong in the one place where there was no second number to compare
   it against.

   **This is the structural cost of implementing one formula twice**, which the design accepts
   knowingly for a good reason (the leaderboard must not trust a client-supplied summary). Accept
   the duplication, then make it impossible to forget: the fix here was a
   `site/chapter-count` check comparing all three numbers — the manifest, the config value and the
   compiled-in fallback — and failing the build on any disagreement. In a PHP build do the same
   from the start, or remove the second source of truth entirely by having the server count the
   chapters it already serves.

2. **The counts check guarded a list of sentences, so prose written afterwards drifted in
   silence.** `CheckProseCounts` began as a list of sentence patterns somebody had registered,
   each derived from the thing it counted. Precise, and it caught rewording — but the default was
   the wrong way round: prose was *unchecked until registered*. Six sentences across four files
   stated the pre-growth chapter and question counts for as long as they were wrong, with the
   check green, because none of them happened to be phrased like the ones in the list.

   **Build it inverted from the start.** Every number next to a counted noun is a claim; anything
   that is not gets excused by name. Three things make that practical, and all three are needed:

   - **A floor.** Ignore any number below a third of the true figure. English uses small cardinals
     as quantifiers constantly ("two questions decide…", "three rules, and everyone knows the
     first") and they are not counts. The third is principled, not tuned: this catches counts
     invalidated by *growth*, and a corpus does not shrink to a third of its size.
   - **Let specific patterns win.** A number an anchored pattern already matched is skipped — it
     may be checked against a different quantity, since one noun can serve several ("chapters"
     covers the site total, the advert-gap subset and the ones with a translation panel).
   - **Name every exclusion, and expire it.** File, phrase, reason. An exclusion that matches
     nothing is an error, or the exclusion list rots the same way the sentences did.

   Turning this on in the .NET version immediately found five more wrong counts the patterns had
   never looked at, across six files that had been reviewed by eye more than once.

   The general lesson is worth more than either fix: **a gate that only inspects what it was told
   about reports green for the same reason a missing gate does.** When you add one, ask what it
   would fail to see, and write that answer down where the next person will find it. Both checks
   here carry that paragraph in the code.

3. **`EnsureCreated`-style schema creation cannot alter an existing database.** The service already
   detects this and fails with an instruction rather than a stack trace. Keep that behaviour, and
   keep the export-your-profile advice in the message.

4. **The service worker cache name is manual.** Every content change needs a bump and nothing
   enforces it. Consider making it part of the integrity gate, or deriving it from a content hash.

5. **Self-marking is the weakest link in the viva and the simulator**, and it is mitigated rather
   than solved. Keep both mitigations (the learner's own words stay on screen; checkpoint terms
   are matched literally) and keep saying so in the prose.
