# LogiFlow Academy

A W3Schools-style tutorial site built around one real job advert: a **.NET developer**
position in Emilia-Romagna. Fifty-six chapters, in dependency order: twenty-three cover
every line of that posting, and thirty-three are not in it at all, because the wider Modena /
Bologna / Reggio Emilia / Milano market asks for them anyway. Three of those thirty-three (WinForms/WPF,
industrial/MES and Business Central) are separate regional job markets in their own right.

## Opening it

Double-click **`index.html`**. That is the whole procedure — no build step, no npm, no
server. Every page is a real `.html` file and the shared navigation is generated by a
plain `<script>`, specifically so that it works from `file://`.

If you prefer a server (or want to test on a phone on the same network):

```bash
python -m http.server 8777 --directory site
```

There is a `.claude/launch.json` entry named `academy` that does exactly this.

For **accounts** — several people, or the same person on a laptop and a phone — run the
service that comes with it instead. It serves this site *and* the API from one process:

```bash
dotnet run --project src/LogiFlow.Academy.Api
# http://localhost:5280
```

No database to install and no configuration. Sign in from the button in the top bar, or from
the pages behind it — `signin.html`, `register.html`, `reset.html` and `account.html`, the
last of which is the *area riservata*: the account, its sync state, the figures the
leaderboard sees, and every button that touches your own data. See
[`src/LogiFlow.Academy.Api/README.md`](../src/LogiFlow.Academy.Api/README.md).

**The login is a username, and there is no email address anywhere.** This service cannot send
mail, so registration hands you a one-time **recovery code** instead: it is shown once, stored
only as a hash, and it is the only way back in if you forget your password. `reset.html`
exchanges it for a single-use ticket and then a new password — the same two-step shape an
emailed reset link has, with the code standing in for the mailbox.

Nothing on the site is behind that door except the door itself. Every chapter, test, review
session, exam and note works signed out, saved in the browser — an account only carries
them to a second machine.

**`assets/chapters.js` drives everything.** The left sidebar, the home-page cards, the
prev/next pager and the coverage table are all generated from that one array. To add a
chapter:

1. Add an entry to `CHAPTERS` in `assets/chapters.js` (keep `id` equal to the filename
   without `.html`, and set `part` to one of the strings in `PARTS`).
2. Give it either a `req` (the line of the advert it answers) **or** an `extra` (why it is
   here even though the advert never mentions it). The home page renders two separate
   tables from those fields, so the "nothing in the advert is uncovered" claim stays true.
3. Copy any existing chapter file as a template, set `<body data-chapter="…">` to the same
   `id`, and match the number in `<title>` and in the `.crumbs` line.

Nothing else needs touching — the navigation, the pager and both coverage tables pick it up.

**Renumbering.** Chapter numbers are part of the filename, so inserting a chapter in the
middle means renaming files and rewriting every `href`, `<title>`, `.crumbs` line and prose
reference. Worth doing — reading order matters more than stable ids in a tutorial — but do
it with a script, not by hand, and re-run the integrity check below afterwards.

## Conventions inside a chapter

| Markup | Purpose |
| --- | --- |
| `<div class="box kid">` | 🧒 the explanation you would give a child |
| `<div class="box pro">` | 🎓 the answer you would give in an interview |
| `<div class="box trap">` | ⚠ the mistake people actually make |
| `<div class="box note">` | context, or a pointer into `course/` |
| `<div class="tryit">` | something to type, not read |
| `<div class="rules">` | the golden-rules card |
| `<div class="qa">` | one interview question with a sketched answer |
| `<button class="jargon">` | **generated.** A professional word, with its plain-English one-liner |
| `<nav id="toc">` | filled in automatically from the `<h2>`s |
| `<div id="pager">` | filled in automatically from the manifest |

Every concept gets **both** a `kid` box and a `pro` box. The Both / Simple / Pro switch in
the top bar hides one or the other, which makes the page usable as a self-test: switch to
Simple, read the child's version, and try to produce the professional one from memory.

Diagrams are **inline SVG** using the `d-*` classes in `style.css`, so they follow the
light/dark theme automatically. No image files, no diagram library.

## The learning layer

Reading a chapter and understanding a chapter feel identical while you are doing it. Six
features exist to tell them apart, and they are built on the two findings in learning
research that survive replication: **you remember what you were tested on**, and you
remember it longest when the tests are **spaced out**.

### One honest percentage

`dashboard.html`. A chapter is worth `1/56` of the course, and within a chapter:

```
25%   for having read it
75%   for the best score on its end-of-chapter test
```

Reading counts for something — you cannot answer a question you have never seen — but three
quarters of the credit is only available by being tested. A progress bar that fills up by
scrolling teaches you to scroll.

The same formula is implemented twice, in `mastery()` in `assets/store.js` and in
`ProfileSummary.From` in the API, because the leaderboard needs it server-side. Both carry a
comment saying so, and `ProfileSummaryTests` is what catches them drifting apart.

### Tests at the end of every chapter

536 questions in `assets/quizzes-*.js`, 8 to 17 per chapter, written to be probed the way an
interviewer probes. The explanation appears **whether you were right or wrong** — feedback
that only shows up on failure teaches people to guess and check.

Adding a question: append it to the end of that chapter's array. **Never reorder them.** The
id is `<chapter-id>#<index>` and it is the key somebody's review schedule is stored under.

```js
{ q: "…", code: "optional snippet", a: ["…","…","…"], c: 1, why: "…" }
{ q: "…", a: ["…","…","…","…"], c: [0, 2], why: "…" }   // select-all-that-apply
```

### Spaced repetition

`review.html`. Every question you answer anywhere on the site enters an SM-2 schedule.
Wrong, and it comes back tomorrow; right and certain, and the gap grows. The
*"I half-guessed"* button is the only signal the scheduler cannot work out for itself — a
right answer you had to dig for is not the same as one you knew.

Because the schedule is global rather than per chapter, a session naturally mixes async with
T-SQL with Docker. That is **interleaving**: harder, better, and exactly what an interview
does to you.

### Free recall — the viva

`viva.html`. Everything above is multiple choice, which measures **recognition**. An
interview measures **free recall**: "spiegami perché" arrives with no options underneath it,
and the two come apart badly — the options on a quiz page are half of what makes the answer
feel available. It is entirely possible to hold 90% mastery here and still not be able to
say why `IQueryable` is not `IEnumerable` out loud.

So this page shows a Golden rule and hides everything else until you have committed an
answer. Then the written justification appears next to yours, and you mark yourself 0/1/2 —
into the same SM-2 scheduler, in its own pile (`profile.viva`, so the review page's counts
stay about the question bank).

Self-marking is the weak point, and it is pushed back on twice: your own words stay on
screen beside the model answer, and the terms the rule itself uses — `rowversion`, 409,
`IQueryable` — are matched literally against what you wrote and shown as hit or missed. That
cannot tell whether you were *right*, but "you never mentioned `rowversion`" is a fact, and
facts are harder to mark generously than feelings.

Two toggles change what the practice is: **speak instead of type** (closer to the real
thing, nothing compared for you) and **rispondi in italiano** (the interview in Modena is in
Italian; the technical terms stay English either way).

The deck is **generated**, not hand-written:

```bash
dotnet run tools/viva-deck.cs          # course/GOLDEN-RULES.md -> site/assets/rules.js
dotnet run tools/viva-deck.cs --check  # parse and report, write nothing
```

Rerun it after editing a Golden rules card, or the drill quietly teaches the old wording.
Card ids are derived from the claim text, so reordering rules costs nothing and rewording
one resets that single card's schedule.

### The interview simulator

`simulate.html`. Everything above lets you stop. This does not: a clock, a mixed round drawn
from both the Golden rules and the question bank, and the next question arriving while you are
still annoyed about the last one.

Two things make it different from the viva rather than a longer version of it. The **bank
questions are asked without their options**, which turns 536 recognition items into recall
items at no content cost. And it opens with *"mi parli di lei"* and closes with *"ha domande
per noi?"* — the two questions asked in every interview and prepared for in almost none,
because they do not feel like knowledge.

It produces a **transcript, not a score**. A self-marked percentage is a number about your
generosity; what you said next to what the course says, with the time you took, is not. Grades
feed the same SM-2 schedules as everywhere else.

### In plain English

`assets/jargon.js` and `assets/jargon-marks.js`. No page of its own: it lives inside the
chapters.

A chapter can be perfectly correct and still unreadable, because one word in the sentence is a
word the reader has never been told the meaning of — and nobody stops mid-paragraph to look it
up. They keep reading with a hole in the sentence, and by the third hole the paragraph means
nothing. So the definition comes to the word: the **first** appearance of each known term in a
chapter is underlined, and clicking it shows one sentence beside it, without leaving the page.
Everything marked is then collected into a *Plain English* box before the pager, which doubles
as a revision list and carries the switch that turns the underlines off.

To add a term, add an entry to `JARGON` in `assets/jargon.js`. The house rules for writing one
are at the top of that file and the first two matter most: **one sentence**, and **no jargon
inside the definition** — if a word in the definition is itself in the list, rewrite it.

**Ordinary English words with a technical second meaning are deliberately absent** — *state*,
*index*, *claim*, *branch*, *commit*, *view*, *layer*. The marker cannot tell which sense a
sentence means, and a confident wrong definition is worse than none; where the technical sense
matters it is listed as an unambiguous phrase instead (*clustered index*, *code smell*,
*container image*). Acronyms match case-sensitively for the same reason: without that, `CI`
marks the Italian *ci*, `MES` marks *mes* and `REST` marks the English word *rest*.

This is a different problem from the glossary. That one is about a word you cannot *translate*;
this one is about a word you cannot *decode*.

### In italiano

`italiano.html`, plus a panel on 34 of the 56 chapters.

The glossary gives you the words. This gives you the **sentences** — because what goes wrong in
a colloquio is not vocabulary. It is knowing the answer, knowing the words, and still not being
able to assemble a sentence at speed, so you simplify the answer down to what your Italian can
carry and sound like you know less than you do.

The English technical nouns stay English (*la query*, *il deploy*, *fare il merge*), on purpose:
that is how the language is used in this industry, and translating them is the marker of
somebody who learned it from a textbook.

**Coverage is partial and the panel simply does not appear where there is no entry.** A
half-written translation teaches a sentence you would not want to say. To add one, put an entry
in `IT_CHAPTERS` in `assets/italiano.js` keyed by chapter id, with one or two `say` lines and
the terms that `keep` their English.

### CV e lettera

`cv.html`. Chapter 36 tells you what an Italian technical CV needs; this produces one in that
shape and then **checks it against the chapter's own rules** — the GDPR line, CEFR levels,
bullets that describe a result rather than presence, at least one number, one page.

Every warning traces to a paragraph in chapter 36. What no checker can tell you is whether the
bullets are *true*, and whether they are the right three.

### Offline

The site installs as an app and works with the network unplugged: `sw.js` precaches all 56
chapters and every asset on first visit, and serves them cache-first afterwards.

**It never caches `/api/`.** Sign-in, sync and the leaderboard need the network and fail
honestly without it — a cached 200 for "here is your profile" would be a lie with somebody's
progress attached.

> **Bump `CACHE` in `sw.js` when content changes.** The cache name *is* the version: a new name
> rebuilds everything and deletes the old, and there is no partial invalidation. Forget it and
> returning visitors keep last month's chapters with no error anywhere — the single most common
> service-worker bug.

Service workers only run over http(s), so opening `index.html` from disk skips all of it
silently. That is correct, and `site.js` checks the protocol before registering so the console
stays clean on `file://`.

### Sticky notes

Select any sentence in a chapter and press **📌 Note this**. The note is pinned beside that
paragraph and also appears on `notes.html`. Notes carry the quote *and* your own words,
because paraphrasing is what does the work; copying does almost nothing.

### XP, levels, streaks and badges

Tied to retrieval, not to page views: reading a chapter is 10 XP, passing its test is 50.
Flashcard XP is capped per day, because reviewing 400 cards in one sitting is not four
hundred cards' worth of learning. Levels are named for the job — Stagista, Junior Developer,
Developer, Mid, Senior, Tech Lead, Architetto.

### Where it is stored

In `localStorage`, under one key, in this browser. Nothing leaves the machine unless you sign
in from the top bar; the dashboard has export and import buttons, and a reset. Every
`localStorage` access is wrapped, so a private window degrades to memory-only instead of
taking the page down.

## Checking it after an edit

```bash
python - <<'PY'
import io, os, re
ids = re.findall(r'id:\s*"([^"]+)"', io.open('site/assets/chapters.js', encoding='utf-8').read())
files = sorted(f[:-5] for f in os.listdir('site/chapters') if f.endswith('.html'))
print('missing:', [i for i in ids if i not in files] or 'none')
print('orphans:', [f for f in files if f not in ids] or 'none')
for f in files:
    s = io.open('site/chapters/%s.html' % f, encoding='utf-8').read()
    n = f[:2]
    if 'data-chapter="%s"' % f not in s: print('data-chapter mismatch:', f)
    if '<title>%s ' % n not in s:        print('title number wrong:', f)
    if 'Chapter %s</p>' % n not in s:    print('crumb number wrong:', f)
    for href in re.findall(r'href="([^"#]+\.html)', s):
        if not href.startswith('http') and not os.path.exists(os.path.normpath(os.path.join('site/chapters', href))):
            print('dead link:', f, '->', href)
    for href in re.findall(r'href="(\.\./\.\./[^"#]+)"', s):
        if not os.path.exists(os.path.normpath(os.path.join('site/chapters', href))):
            print('dead repo link:', f, '->', href)
PY
```

## Checking the learning layer

The chapter check above still applies. Two more, for the question bank:

```bash
python - <<'PY'
import io, re, json
manifest = io.open('site/assets/chapters.js', encoding='utf-8').read()
ids = re.findall(r'id:\s*"([^"]+)"', manifest)

bank = ''.join(io.open('site/assets/quizzes-%d.js' % i, encoding='utf-8').read() for i in (1, 2, 3))
keyed = re.findall(r'^  "([^"]+)":\s*\[', bank, re.M)

print('chapters with no questions:', [i for i in ids if i not in keyed] or 'none')
print('questions for a chapter that does not exist:', [k for k in keyed if k not in ids] or 'none')
print('total chapters:', len(ids), ' with a bank:', len(keyed))

# Every `c` index must be inside its own `a` array.
for block in re.finditer(r'\{\s*q:(.*?)
    \}', bank, re.S):
    body = block.group(0)
    opts = len(re.findall(r'^\s*"', body, re.M))
    for m in re.finditer(r'c:\s*(\[[^\]]*\]|\d+)', body):
        vals = json.loads(m.group(1)) if m.group(1).startswith('[') else [int(m.group(1))]
        if any(v < 0 for v in vals):
            print('bad answer index in:', body[:70])
PY
```

## Publishing it

The site is Cloudflare Workers static assets, configured in
[`wrangler.jsonc`](../wrangler.jsonc) at the repository root, and served at
<https://csharp.testdemo.it> with <https://csharp-academy.krsiti-komini.workers.dev> as a
fallback.

```bash
npx wrangler deploy
```

**Merging to `main` used to publish nothing**, and that is worth stating plainly because it
caught this repository out: a merge is the moment everybody assumes a static site has
shipped, so `main` sat ahead of the live site and nothing said so. It was noticed only
because somebody opened the URL and counted the chapters.

[`.github/workflows/deploy-site.yml`](../.github/workflows/deploy-site.yml) now runs the
deploy on any push to `main` that touches `site/`. It needs a `CLOUDFLARE_API_TOKEN` repository
secret, and **skips rather than fails when that secret is absent** — a red cross on every push
would train people to ignore red crosses, which is worse than the problem it solves. Until the
secret exists the command above is still the way it ships, and the workflow summary says so on
every run.

**Bump `CACHE` in [`sw.js`](sw.js) whenever the set of precached files changes.** The service
worker builds its precache list at install time, and install only runs when the browser sees a
byte-changed `sw.js` — so adding a chapter without bumping it leaves returning visitors with the
old set and an offline claim that is quietly false. `dotnet run tools/doctor.cs` checks this
(`site/sw-cache`), and `tools/sw-cache.lock` records the set it was last bumped for.

## Relationship to the rest of the repository

This site is the **tutorial** layer: it explains a topic well enough to hold a
conversation about it. The depth lives elsewhere and the chapters link into it —
`course/module-*/` for the full treatment, `labs/Labs.Playground` for demos that make the
behaviour visible, and `src/` for the working implementation.

Read a chapter here to understand a topic. Read the module to be dangerous with it.

`src/LogiFlow.Academy.Api` is the exception to that split: it is not course material, it is
the service this site talks to for accounts. It happens to be worth reading for the same
reason the rest is — it does JWT, refresh rotation, password hashing and optimistic
concurrency in six commented files.
