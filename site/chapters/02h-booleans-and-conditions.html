Booleans, operators and conditions

A bool holds one of two values and is the simplest type in the language, which is why nobody teaches it and why the conditions built out of it are where a surprising amount of production code is quietly wrong. This chapter is the whole operator table with precedence, what short-circuiting really does for you, the third state a bool? has, and the conditions that read as English and mean something else.

Why this chapter exists

Every branch in every program you write is a boolean expression, and the failures are not exotic. A condition that says if (x != 1 || x != 2) is always true. A & where an && was meant crashes on a null check that looked fine. A method with four boolean parameters produces call sites nobody can read. A bool? from a database has three states and the code handles two. None of these are hard once seen; all of them survive review when nobody has been shown them.

The type itself

🧒 Simple

A bool is a yes-or-no. It has exactly two values, true and false, and unlike some languages, C# will not let you pretend that a number or an empty string is one of them. Zero is not false here. It is just zero. 

bool dispatched = false;        // the default for bool is false
bool hasStock = qty > 0;        // a comparison IS a bool — no if needed to make one

if (qty) { }                    // ✗ compile error: int is not bool
if (name) { }                   // ✗ compile error: string is not bool
if (qty != 0) { }               // ✓ say what you mean

bool? approved = null;          // a NULLABLE bool — three states, see below
Line by line
  • qty > 0 is already a bool. Writing if (qty > 0) { hasStock = true; } else { hasStock = false; } is the same expression with nine extra words, and it is the single most common thing to be told to delete in a first code review.
  • C# has no truthiness. No implicit conversion exists from int, string or any reference type to bool, so the JavaScript habits of if (list) or if (count) do not compile. This is deliberate and it removes a whole family of bugs.
  • The default value of a bool is false, which matters for a field nobody assigned — see chapter 02b on defaults. It means "not yet set" and "definitely no" look identical, which is exactly when a bool? is the honest type.
  • A bool occupies a whole byte, not a bit, and an array of them is not a bit field. BitArray and [Flags] enums (chapter 02j) are the compact options, and you will almost never need them.
  • bool.TryParse("true", out var b) exists and is case-insensitive, but accepts only "true" and "false" — not "yes", "1" or "si". Input in those forms is a mapping you write yourself.

The operators, in precedence order

Read this table top to bottom: anything higher binds more tightly than anything below it. That is the entire rule, and it is why a + b > c means (a + b) > c without anybody having to write the brackets.

LevelOperatorsNote
1x++ x-- !x -x ++xunary; ! binds tighter than everything below, which surprises people
2* / %and remember 7 / 2 is 3
3+ -
4< > <= >= is asrelational
5== !=looser than the relational ones, which is why a < b == c < d parses
6& then ^ then |bitwise, and non-short-circuiting when used on bool
7&&short-circuiting AND
8||short-circuiting OR — looser than &&
9??null-coalescing
10c ? a : bthe conditional operator, right-associative
11= += &&= …assignment, loosest of all
 
bool urgent = express || weight > 20 && distance < 50;
// parses as:  express || (weight > 20 && distance < 50)     — AND binds tighter
// if you meant (express || weight > 20) && distance < 50, WRITE the brackets

bool ok = !ready || done;       // ! applies to ready only, not to the whole thing
bool ok2 = !(ready || done);    // completely different question

int flags = 0b_0000_1010;       // bitwise on integers is a different job entirely
bool bothWays = (flags & 0b_0010) != 0;
Line by line
  • && before || is the one precedence fact worth actually knowing, because the mistake it causes reads perfectly well in English: "express, or heavy and close" is ambiguous out loud too.
  • ! binds tighter than everything, so !a == b means (!a) == b. Almost nobody means that. Brackets.
  • == is looser than <, which is why if (a < b == c < d) compiles and compares two booleans. Legal, and worth a comment if you ever genuinely want it.
  • Brackets have no runtime cost whatsoever. The only question is whether a reader would need this table, and if the answer is maybe, add them.
  • 0b_0000_1010 is a binary literal with digit separators. Bitwise work on integers is a different topic from boolean logic, and where it belongs in day-to-day code is [Flags] enums.

Short-circuiting, and why it is not an optimisation

🧒 Simple

&& stops as soon as it knows the answer. If the left side is false, the whole thing is false whatever the right side says, so the right side is never run at all. That is not the computer being clever to save time — it is a promise you are allowed to build on. 

// ✓ the null check protects the call to its right
if (order != null && order.Lines.Count > 0) { }

// ✗ the same line with one ampersand: BOTH sides always run
if (order != null & order.Lines.Count > 0) { }   // NullReferenceException

// ✓ short-circuit OR: the expensive check only runs if the cheap one failed
if (cache.TryGet(sku, out var hit) || database.Exists(sku)) { }

// the modern version of the first line
if (order?.Lines.Count > 0) { }                  // null?.anything > 0 is false
Line by line
  • && evaluates the right side only if the left is true; || evaluates it only if the left is false. Both are guarantees in the language specification, not optimisations, so ordering a guard before the thing it guards is correct code rather than a lucky habit.
  • & and | on booleans are legal and always evaluate both sides. There is essentially no reason to use them on bool, and the single missing character turns a working guard into a crash — which is why a review should stop on any & between two boolean expressions.
  • Put the cheap test first. if (IsLocal(x) && await RemoteCheck(x)) saves the network call whenever the local one settles it. Ordering a condition is a performance decision you get for free.
  • Beware short-circuiting past a side effect. if (a || Log(b)) stops logging as soon as a is true, which is the sort of thing that removes half your audit trail. Anything with a side effect belongs on its own line.
  • order?.Lines.Count > 0 — the null-conditional produces a int?, and comparing null > 0 gives false rather than throwing. That is a lifted operator, and it is why this shorter form is safe.
⚠️ The condition that is always true

if (status != "OPEN" || status != "CLOSED") is true for every possible value, including both of those. If the status is OPEN then it is not CLOSED, so the second half holds; if it is CLOSED the first half holds. The author meant &&. The mirror image, if (x == 1 && x == 2), is always false. Both read like plain English and neither is ever flagged by the compiler, because both are perfectly valid expressions.

bool?, the third state

A nullable boolean has three values: true, false and null — yes, no and "nobody has answered yet". It comes out of databases constantly, because a nullable bit column is exactly this, and code written for two states handles it wrong in a specific and predictable way. 

bool? approved = null;          // the manager has not looked at it yet

if (approved == true)  { }      // ✓ explicit: only when genuinely approved
if (approved == false) { }      // ✓ explicit: only when genuinely rejected
if (approved is null)  { }      // ✓ not yet decided

if (approved) { }               // ✗ compile error — bool? is not bool
if (!approved.Value) { }        // ✗ InvalidOperationException when it IS null

bool safe = approved ?? false;  // "treat unanswered as not approved" — a DECISION

// three-valued logic, as in SQL:
bool? r1 = null & true;         // null — unknown AND true is still unknown
bool? r2 = null | true;         // TRUE  — unknown OR true is true whatever the unknown is
Line by line
  • if (approved) does not compile, and that is the language doing you a favour: it forces you to say which of the three states you meant.
  • approved == true is the idiom, and it is not the redundant comparison it looks like — on a bool? it is the concise way to write "has a value, and that value is true".
  • .Value throws InvalidOperationException when there is no value. Use .HasValue first, or ??, or a pattern.
  • approved ?? false collapses three states into two, and the important part is that you chose the collapse. Defaulting an unreviewed order to "not approved" is right; defaulting an unanswered consent checkbox to "consented" is a legal problem. The ?? is where that decision is recorded.
  • null | true being true is three-valued logic, the same rules SQL uses for NULL. It is the reason WHERE x != 'A' in SQL does not return the rows where x is null — the same principle, and chapter 10 has it from the database side.

Conditions a human can read

The logic being correct is the minimum. The next question a reviewer asks is whether the condition says what it means, and there are four moves that answer it. 

// ✗ correct, unreadable
if (o.Status == 3 && o.Lines.Count > 0 && !o.Hold && o.Weight <= 30 && o.Date >= today)

// ✓ 1 — name the idea
bool isDispatchable = o.Status == OrderStatus.Picked
                   && o.Lines.Count > 0
                   && !o.OnHold
                   && o.Weight <= MaxCourierWeightKg
                   && o.Date >= today;

// ✓ 2 — make it a property of the thing it describes
public bool IsDispatchable => Status == OrderStatus.Picked && !OnHold && Lines.Count > 0;

// ✓ 3 — return the expression; do not branch to produce a bool
bool HasStock(string sku) => _stock.GetValueOrDefault(sku) > 0;

// ✓ 4 — guard clauses instead of nesting
if (order is null)      return Problem("no order");
if (order.OnHold)       return Conflict("on hold");
if (!order.Lines.Any()) return BadRequest("empty");
return Dispatch(order);        // the happy path, unindented, at the end
Line by line
  • Naming the condition is the highest-value edit on this page. if (isDispatchable) tells a reader what the five clauses were for, which no amount of formatting does, and it gives the debugger one variable to inspect.
  • A boolean expression belongs beside the data it asks about. Once IsDispatchable is a property of Order, it cannot drift apart across three call sites — the encapsulation argument from chapter 03, applied to a single line.
  • return x > 0; rather than if (x > 0) return true; else return false;. Same behaviour, a third of the words.
  • Guard clauses invert the nesting. Each failure returns immediately, so the interesting path never indents and every reason for rejection is on one visible line. This is the single structural habit that most separates junior from mid-level code.
  • Prefer positive names. if (!isNotReady) takes a reader two passes. Name the flag IsReady and the double negative cannot be written.
⚠️ The boolean parameter at a call site

Dispatch(order, true, false, true) is unreadable and the compiler is perfectly happy with the arguments in the wrong order. Three fixes, in increasing order of strength: a named argument, Dispatch(order, express: true); an enum instead of a bool, so ShippingMode.Express appears at the call site (chapter 02j); or two methods with names that say what they do. A method with three or more boolean parameters is usually two or three methods that have not been separated yet.

Pattern matching: conditions that read better than operators

if (qty is > 0 and <= 100) { }                  // relational + logical patterns
if (status is OrderStatus.Picked or OrderStatus.Packed) { }
if (order is not null) { }                      // preferred over != null
if (input is string { Length: > 0 } text) { }   // type + property + capture, one line

string band = weightKg switch
{
    <= 2   => "letter",
    <= 30  => "parcel",
    <= 500 => "pallet",
    _      => "freight",                        // _ is required, or it can throw
};
Line by line
  • qty is > 0 and <= 100 — the subject is written once. The operator version, qty > 0 && qty <= 100, repeats it, and repeating it is how x > 0 && y <= 100 gets written by accident.
  • and, or, not inside a pattern are pattern keywords, not the operators — they combine patterns rather than booleans, which is why no subject is repeated after them.
  • is not null reads better than != null and, unlike it, cannot be hijacked by a type that overloads !=. Prefer it.
  • is string { Length: > 0 } text does a type test, a property test and a variable capture at once, and text is in scope afterwards. Four lines replaced by one, with no cast to get wrong.
  • A switch expression returns a value, so it must be exhaustive — the _ arm. Leave it out and an unmatched value throws SwitchExpressionException at run time, which is the compiler telling you it cannot prove you covered everything.

Exercises, with the reasoning shown

Exercise 1 — the filter that filtered nothing

if (status != "OPEN" || status != "CLOSED")
    Process(order);
Every order is processed.
  • If the status is OPEN, it is not CLOSED, so the right-hand side is true; if it is CLOSED, the left-hand side is true; and anything else makes both true. The author wanted &&. Nothing about the syntax is wrong, which is why the compiler is silent and the condition reads fine aloud. Whenever you write two != joined by ||, stop and check.

Exercise 2 — the null check that threw

if (order != null & order.Lines.Count > 0)
    Dispatch(order);
NullReferenceException when order is null.
  • A single & is the non-short-circuiting AND: both sides are evaluated before the result is combined, so the guard on the left never protects the dereference on the right. One missing character. It compiles, it passes every test where the order exists, and it fails in production on the one path where the check mattered.

Exercise 3 — the approval that approved itself

bool? approved = LoadFromDatabase();   // nullable bit column
if (approved != false)
    Ship(order);
Orders nobody has looked at get shipped.
  • null != false is true, so the unreviewed state falls into the approved branch. Written as if (approved == true) the same code ships only genuinely approved orders, and the unreviewed ones wait. With three-state data, test for the state you want rather than against the one you do not — and make the collapse explicit with approved ?? false if you need a plain bool.

Exercise 4 — the precedence that changed the price

bool freeShipping = isMember || total > 100 && weight < 5;
// isMember = false, total = 500, weight = 20
false — and the author expected true.
  • && binds tighter, so this reads as isMember || (total > 100 && weight < 5). The intended rule was almost certainly "(member or big order) and light enough", which needs brackets. Nobody should have to know the precedence table to review a line about shipping charges, and brackets cost nothing at run time.
Try it yourself

Six lines, each printing something people get wrong. Run it, then try to predict each one before you look. 

bool? unknown = null;

  Console.WriteLine(unknown == true);          // False
  Console.WriteLine(unknown == false);         // False  — BOTH are false
  Console.WriteLine(unknown != false);         // True   — the exercise-3 bug
  Console.WriteLine(unknown ?? false);         // False  — the deliberate collapse
  Console.WriteLine((null | true) == true);    // True   — three-valued OR
  Console.WriteLine(false || true && false);   // False  — && binds tighter

  // and the one that proves short-circuiting is a promise:
  string? s = null;
  Console.WriteLine(s != null && s.Length > 0);   // False, no exception
  Console.WriteLine(s != null &  s.Length > 0);   // NullReferenceException
Line by line
  • The first two lines are the point: == true and == false are both false for null, because there are three states and null is the third.
  • unknown != false is true — the same trap as the approval exercise, and the reason to test for the state you want.
  • ?? false is the deliberate collapse from three states to two, and it is where the business decision is recorded.
  • null | true being true is three-valued logic: unknown OR true is true whatever the unknown turns out to be.
  • false || true && false is false because && binds tighter — it reads as false || (true && false).
  • The last pair differ by one character and by an exception: the short-circuit protects the dereference and the single ampersand does not.

The last pair is the whole chapter in two lines. Then take the worst condition in code you have already written, give it a name, and see whether the surrounding method became readable without you touching anything else.

Golden rules

  1. C# has no truthiness. if (count) and if (list) do not compile, deliberately. Say count != 0.
  2. A comparison is already a bool. if (x > 0) return true; else return false; is return x > 0;.
  3. && binds tighter than ||. That one fact causes most precedence bugs; brackets cost nothing and remove the question.
  4. Short-circuiting is a guarantee, not an optimisation — so a guard placed before the thing it guards is correct code, and a single & between two boolean expressions is almost always a bug.
  5. Put the cheap condition first. Ordering a condition is free performance, and it is the difference between one network call and none.
  6. Two != joined by || is always true. Its mirror, two == joined by &&, is always false. Check every one you write.
  7. bool? has three states, so test for the one you want — == true — rather than against the one you do not. null != false is true.
  8. Collapse a bool? with ??, visibly. Which way an unanswered question defaults is a business decision, and that operator is where it is recorded.
  9. Name any condition with more than two clauses. A named bool, or better a property on the type it asks about, tells the reader what the clauses were for.
  10. Guard clauses instead of nesting. Reject early, return immediately, and leave the happy path unindented at the bottom.
  11. No boolean parameters at a call site. Use a named argument, or an enum, or two methods. Three booleans in a signature is usually three methods.
  12. Prefer is not null and relational patterns — qty is > 0 and <= 100 writes the subject once, so it cannot drift.

Interview questions

"What is the difference between & and &&?"

&& short-circuits: if the left side is false the right side is never evaluated. & always evaluates both. On booleans that difference is almost always a bug rather than a choice, because the standard null guard — if (x != null && x.Length > 0) — depends entirely on the short-circuit, and with a single ampersand it throws. Short-circuiting is guaranteed by the language specification, not an optimisation, so I can rely on it for ordering a cheap check before an expensive one. On integers, & is the bitwise AND, which is a different job.

"How do you handle a bool??"

By treating it as three states, not two: true, false, and "no answer". I test the state I actually want with == true or is true, because the tempting != false is true for null as well and silently folds unanswered into approved — which is the classic bug when the value comes from a nullable bit column. When I need a plain bool I collapse it explicitly with ?? false, and I treat which way it collapses as a business decision rather than a default. The logic follows the same three-valued rules as SQL nulls, so null | true is true while null & true is still null.

"This condition is always true — why? if (s != "A" || s != "B")"

Because no single value can be both, so at least one half always holds: if it is "A" then it is not "B", and vice versa. The author meant && — "neither A nor B". The reason it survives review is that it reads correctly in English, and nothing in the syntax is wrong, so the compiler has no reason to object. I treat two != joined by || as a smell worth stopping on, the same way I treat two == joined by &&, which is always false.

"How would you make a complicated condition readable?"

First, name it — assign it to a bool whose name says the idea, so the reader learns what the five clauses were for and the debugger has one thing to inspect. Better, move it onto the type it asks about, as an expression-bodied property like IsDispatchable, so it cannot drift across call sites. Then invert the nesting with guard clauses: reject each bad case with an early return, so the happy path ends up unindented at the bottom and every rejection reason is one visible line. And I would not have a boolean parameter at the call site at all — a named argument at minimum, an enum if the thing genuinely has two named modes.

"Cosa fa il null-conditional in una condizione, tipo order?.Lines.Count > 0?"

Se order è null, l'intera espressione a sinistra diventa null e non viene lanciata nessuna eccezione: il confronto diventa null > 0, che con gli operatori "lifted" dei nullable dà false, non un errore. Quindi quella riga è un modo compatto e sicuro di dire "esiste e ha almeno una riga". La cosa a cui stare attenti è che null dà false anche su <: sia null > 0 sia null < 0 sono false, quindi non si può assumere che uno dei due sia vero.
