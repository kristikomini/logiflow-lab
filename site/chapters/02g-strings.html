Strings, the whole toolbox

Chapter 00b told you a string is immutable and showed you ToUpper. Chapter 02 told you why two identical strings can be the same object. Neither told you how to actually get work done: splitting a CSV line, finding a SKU inside a barcode, building a report without making forty thousand throwaway strings, or comparing two names in a way that will not fail on a Turkish server.

Why this chapter exists

Text is the majority of what a business application touches. Every import, every export, every log line, every identifier a warehouse scanner produces, every name a user types — all string work, and all of it done with about twenty methods. Not knowing them does not stop you; it makes you write ten lines of loop where one call existed, and it makes you reach for == where StringComparison was needed. Both are visible in a code review from across the room.

Immutable, and what that actually costs

🧒 Simple

A string cannot be changed. Not "should not" — cannot. Every method that looks like it edits a string actually builds a brand-new one and hands it back, leaving the original exactly as it was. If you do not catch the new one, nothing has happened at all.

🎓 Professional

Immutability buys thread safety for free, makes a string safe to use as a dictionary key, and allows interning — identical literals sharing one object. It costs an allocation per operation, and the cost only becomes visible when the operations are in a loop. That is precisely what StringBuilder exists for, and why reaching for it before you have a loop is premature. 

string sku = "mi-42-blue";

sku.ToUpper();                 // ✗ does nothing whatsoever — the result is discarded
sku = sku.ToUpper();           // ✓ MI-42-BLUE

string a = "MI-42";
string b = "MI-42";
bool same = ReferenceEquals(a, b);   // true — both literals were interned into one object

string c = string.Concat("MI-", "42");
bool same2 = ReferenceEquals(a, c);  // false — built at run time, a different object
bool equal = a == c;                 // true — == on string compares the CHARACTERS
Line by line
  • sku.ToUpper(); on a line of its own compiles without even a warning and does nothing. Every string method returns the new value; none of them mutate. This is the single most common beginner mistake with strings and it is completely silent.
  • Interning — the compiler puts identical literals in a shared pool, so two literals with the same text are one object. It is an optimisation, not a promise you should rely on, and it does not apply to strings built at run time.
  • == on string is overloaded to compare characters, not references — unlike every other reference type. That is why comparing strings feels natural in C# and is a famous trap in Java.
  • ReferenceEquals ignores that overload and asks the real question, which is the only way to see interning happening.
  • A string is a reference type whose value semantics are bolted on. Chapter 02b calls this out as the one type where location and equality disagree with each other.
⚠️ Concatenating in a loop

total += line + "\n"; inside a loop over ten thousand rows allocates ten thousand progressively longer strings and copies every character of the result each time — quadratic work for a linear job. A five-hundred-line report built this way is imperceptible; a hundred-thousand-line export takes minutes and looks like a database problem. Use StringBuilder the moment the concatenation is inside a loop, and do not bother outside one.

string barcode = "MI-42-BLUE-0007";

bool ours   = barcode.StartsWith("MI-", StringComparison.Ordinal);
int dash    = barcode.IndexOf('-');                    // 2
int lastDash= barcode.LastIndexOf('-');                // 11
string tail = barcode[(lastDash + 1)..];               // "0007" — range operator

if (string.IsNullOrWhiteSpace(userInput))              // covers null, "", "   "

char last  = barcode[^1];                              // '7' — ^1 is "one from the end"
Line by line
  • IndexOf returns −1 when not found, and that is the check — not an exception, not null. Forgetting it and passing −1 straight into Substring is an ArgumentOutOfRangeException in production and the second most common string bug there is.
  • barcode[(lastDash + 1)..] — the range operator. It is Substring with better syntax: s[2..5] is from index 2 up to but not including 5, s[..3] is the first three, s[^4..] is the last four. The end is always exclusive.
  • IsNullOrWhiteSpace versus IsNullOrEmpty — a form field containing three spaces is empty to a human and non-empty to IsNullOrEmpty. For anything a person typed, use the whitespace version.
  • 'M' in single quotes is a char; "M" in double quotes is a string of length one. They are different types and the methods that take a char are measurably faster, so prefer IndexOf('-') over IndexOf("-").
  • s.Length counts UTF-16 code units. For ordinary European text that is the number of characters; for an emoji or certain scripts it is not, and StringInfo is the correct tool. Worth knowing exists; rarely needed.

Making a new string from an old one

string raw = "  mi-42-blue  ";

raw.Trim()                      // "mi-42-blue"  — both ends
raw.TrimStart()                 // "mi-42-blue  "
raw.TrimEnd('-', ' ')           // trims any of the characters given
raw.Trim().ToUpperInvariant()   // "MI-42-BLUE"  — invariant for identifiers
raw.Replace("-", "/")           // "  mi/42/blue  " — every occurrence
raw.Replace("-", "")            // removing = replacing with nothing

"MI-42".PadLeft(10)             // "     MI-42"  — width 10, spaces on the left
"7".PadLeft(5, '0')             // "00007"       — zero-padding a number
"MI-42".PadRight(10) + "|"      // "MI-42     |"

"MI-42-BLUE".Substring(3, 2)    // "42" — start at 3, take 2
"MI-42-BLUE"[3..5]              // "42" — the same thing, and clearer
string.Join(", ", skus)         // "MI-42, BO-7, PR-1" — the tidiest method here
Line by line
  • Trim with no arguments removes whitespace, which includes tabs and newlines — the reason a value copied out of Excel parses fine and the same value from a text file does not.
  • ToUpperInvariant rather than ToUpper for identifiers. ToUpper uses the machine's culture, and in Turkish the upper-case of i is İ, not I — so an uppercased SKU stops matching the one in the database. Use ToUpper only for text a human reads.
  • PadLeft(5, '0') — the correct way to zero-pad a string. If you have a number, n.ToString("D5") says it better, and unlike padding it cannot be defeated by an already-long value.
  • Substring(3, 2) takes a start and a length, while [3..5] takes a start and an end. Mixing the two mental models up is an off-by-one waiting to happen; prefer the range syntax in new code.
  • string.Join — a separator and a sequence, and it handles the "no comma after the last one" problem that every hand-written version gets wrong on the first attempt. It works on any IEnumerable<T>, calling ToString on each element.
Interpolation has a format and an alignment too

$"{sku,-12}{qty,5:N0} kg" pads and formats in one place, which is almost always better than a chain of PadRight and ToString calls. The comma is the width (negative for left-aligned), the colon is the format. Chapter 00e uses it to line up a report.

Splitting and joining: the CSV line

Split is the method you will use most and the one most likely to be used carelessly. Here it is on the job it is actually given. 

string line = "MI-42-BLUE;12;18.40;;Modena";

string[] parts = line.Split(';');                       // 5 parts, one of them empty
string[] tidy  = line.Split(';', StringSplitOptions.TrimEntries
                               | StringSplitOptions.RemoveEmptyEntries);  // 4 parts

// Only split off the first separator — the rest of the line is a free-text note
string[] two = note.Split(':', 2);                      // ["WARN", "bin 7: blocked"]

string rejoined = string.Join(";", parts);              // back to one line
string[] lines  = file.Split('\n', StringSplitOptions.RemoveEmptyEntries);
Line by line
  • Split(';') on two adjacent separators produces an empty string in the middle, not nothing. That is correct — a CSV column can be empty — and it is why RemoveEmptyEntries must be a deliberate choice rather than a habit. Removing empties silently shifts every column after the gap, which corrupts an import in a way that is very hard to see.
  • StringSplitOptions.TrimEntries — trims each piece as it splits, which saves a Select(x => x.Trim()) and is the fix for "the file has a space after every comma".
  • Split(':', 2) — the count limits how many pieces you get; everything left over stays in the last one. This is the right tool for key: value where the value may itself contain the separator.
  • Splitting on '\n' leaves a stray '\r' at the end of each line on a file written by Windows. Use line.TrimEnd(), or better, read lines with File.ReadLines (chapter 02k), which handles it.
  • Split allocates an array and a string per piece. In the hot path of a high-volume parser that matters, and the answer is ReadOnlySpan<char>; everywhere else it does not, and clarity wins.
⚠️ Split is not a CSV parser

A real CSV file may quote a field that contains the separator — "Rossi, Mario";12 — and Split(';') cuts it in half. It also has to cope with quotes inside quotes and with embedded newlines. Every attempt to handle this with Split plus a couple of ifs grows into a broken state machine. Use a library (CsvHelper) the moment the data comes from outside your own program. Split is for formats you control.

Comparing: the argument you are supposed to pass

🧒 Simple

"MI-42" and "mi-42" are the same SKU to a person and different text to a computer. Telling the computer which of those two you meant is a separate argument, and leaving it out means you got whichever answer the machine's language settings felt like giving. 

// ✗ works on your machine, may not on a server in another country
if (input.ToLower() == "yes") { }

// ✓ say what kind of comparison you mean
if (string.Equals(input, "yes", StringComparison.OrdinalIgnoreCase)) { }

bool hasIt  = sku.Contains("BLUE", StringComparison.OrdinalIgnoreCase);
bool starts = file.EndsWith(".csv", StringComparison.OrdinalIgnoreCase);

int order = string.Compare(a, b, StringComparison.CurrentCulture);  // for SORTING for a human
// negative: a first. zero: equal. positive: b first.
Line by line
  • Ordinal is the default you should reach for, and it is not the default C# gives you. It is faster and, more importantly, it gives the same answer on every machine on earth.
  • ToLower() == does the job of OrdinalIgnoreCase while allocating a whole new string and introducing the Turkish-i problem. It is the pattern to stop writing.
  • Equality and ordering are different questions. Equals answers "are these the same", Compare answers "which comes first", and only the second one should be culture-aware — because "which comes first" is genuinely a question about somebody's alphabet.
  • Sorting a list of Italian names with Ordinal puts every capital letter before every lower-case one, so "Zanetti" sorts before "abate". That is the one place culture-aware is correct.
  • A Dictionary<string, T> takes a comparer in its constructor: new Dictionary<string, Order>(StringComparer.OrdinalIgnoreCase). That is how you make case-insensitive lookup a property of the collection rather than something every call site has to remember.
StringComparisonWhat it doesUse it for
Ordinalcompares the raw numeric values of the charactersidentifiers, SKUs, file paths, keys, tokens — the default choice
OrdinalIgnoreCasethe same, ignoring ASCII caseuser input matched against a fixed set, extensions, header names
CurrentCulturethe machine's language rulessorting a list a person will read
InvariantCulturefixed, culture-free linguistic rulesrarely the right answer; prefer Ordinal

StringBuilder, and when it earns its place

var sb = new StringBuilder();

sb.AppendLine("SKU;QTY;WEIGHT");
foreach (var l in order.Lines)
    sb.Append(l.Sku).Append(';')
      .Append(l.Qty).Append(';')
      .Append(l.WeightKg.ToString("F2", CultureInfo.InvariantCulture))
      .AppendLine();

string csv = sb.ToString();      // ONE string, built once, at the end

// A one-off, outside a loop — a StringBuilder here is noise
string label = $"{order.Id} — {order.Customer} ({order.Lines.Count} lines)";
Line by line
  • StringBuilder holds a mutable buffer and grows it, so appending is cheap and only the final ToString allocates a string. Inside a loop over thousands of rows this turns quadratic work into linear.
  • Outside a loop it is worse than interpolation — more code, more allocation, and nothing gained. The rule is genuinely "is this in a loop", not "is this string long".
  • The Append calls chain, because each returns the builder itself. That is the fluent pattern, and it is the same trick LINQ and IServiceCollection use.
  • Append(l.Qty) takes an int overload directly — no ToString needed, and no boxing.
  • InvariantCulture on the weight, because this is a file. Without it the same code writes 18.40 in London and 18,40 in Modena, and the second one has an extra column as far as the reader is concerned. This is chapter 02f's rule, in its most expensive form.
The modern shortcuts

For a multi-line template, a raw string literal is easier than either: three or more double quotes open it, indentation is stripped relative to the closing quotes, and nothing inside needs escaping. Prefix it with $ and interpolation still works. For joining a sequence, string.Join("\n", items.Select(Format)) beats a builder for both length and clarity. 

string sql = """
    SELECT Sku, Qty
    FROM   OrderLines
    WHERE  OrderId = @id       -- no escaping, no + signs, no "\"
    """;

string report = string.Join("\n", order.Lines.Select(l => $"{l.Sku,-12}{l.Qty,5}"));
Line by line
  • """ — three or more double quotes open a raw string literal. Nothing inside needs escaping, so embedded quotes, backslashes and SQL comments are written exactly as they are.
  • The indentation of the closing quotes decides the margin: whatever they are indented by is stripped from every line, so the literal lines up with the surrounding code without carrying that whitespace into the value.
  • string.Join over a Select — shorter than a StringBuilder and it says "one line per item" outright.
  • Prefix the literal with $ and interpolation still works; use more than one $ when the content itself contains braces.

Exercises, with the reasoning shown

Exercise 1 — the method that did nothing

string sku = "mi-42";
sku.ToUpper();
Console.WriteLine(sku);
mi-42.
  • ToUpper returned a new string that nobody caught. Strings are immutable, so no method can change one in place; the compiler does not warn, because calling a method and discarding its result is legal. Every string method needs its result assigned to something.

Exercise 2 — the import that lost a column

string line = "MI-42;12;;Modena";
string[] p = line.Split(';', StringSplitOptions.RemoveEmptyEntries);
string city = p[3];
IndexOutOfRangeException.
  • RemoveEmptyEntries deleted the empty third column, so the array has four entries' worth of data in three slots and p[3] does not exist — and on a row where the empty column happened to be filled, the same code would have read the right value, which is how this survives testing. Positional data must be split without removing empties. Use TrimEntries alone.

Exercise 3 — the search that crashed

string barcode = "BO-7-RED";
string batch = barcode.Substring(barcode.IndexOf('#') + 1);
It returns the whole barcode, which is worse than crashing.
  • IndexOf returns −1 when the character is absent, and −1 + 1 is 0, so Substring(0) cheerfully hands back everything. A batch number is now a barcode, and nothing anywhere threw. Always test the result of IndexOf against −1 before using it.

Exercise 4 — the lookup that failed in Turkey

if (header.ToLower() == "invoice") { }
On a Turkish machine, "INVOICE".ToLower() is "ınvoıce" with dotless i's, and the comparison fails.
  • The culture's casing rules were applied to what is really an identifier. The fix is to stop casing at all and say what you meant: string.Equals(header, "invoice", StringComparison.OrdinalIgnoreCase). It is also faster, because it allocates nothing.

Exercise 5 — the export that took four minutes

string csv = "";
foreach (var l in lines)          // 80,000 lines
    csv += l.Sku + ";" + l.Qty + "\n";
Roughly three billion characters copied.
  • Each += builds a whole new string containing everything so far, so the work grows with the square of the row count — 80,000 rows means about 3.2 billion character copies and a great deal of garbage. A StringBuilder does the same job in one pass. This is the canonical case for it, and essentially the only one.
Try it yourself

A parser for one line of warehouse data, using nine of the methods on this page. Paste it into a console project and then feed it the three broken lines underneath — each breaks a naive version and none of them break this one. 

bool TryParseLine(string? line, out (string Sku, int Qty, decimal Kg) row)
  {
      row = default;
      if (string.IsNullOrWhiteSpace(line)) return false;
      if (line.TrimStart().StartsWith("#", StringComparison.Ordinal)) return false;  // comment

      string[] p = line.Split(';', StringSplitOptions.TrimEntries);
      if (p.Length < 3) return false;

      string sku = p[0].ToUpperInvariant();
      if (!int.TryParse(p[1], out int qty)) return false;
      if (!decimal.TryParse(p[2], NumberStyles.Number,
                            CultureInfo.InvariantCulture, out decimal kg)) return false;

      row = (sku, qty, kg);
      return true;
  }

  // Feed it these:
  //   "mi-42-blue ; 12 ; 18.40"     -> parses, spaces and case handled
  //   "# a comment line"            -> skipped, not an error
  //   "BO-7;three;1.0"              -> rejected cleanly, no exception
Which method does which job
  • IsNullOrWhiteSpace first — it covers null, empty and a line of spaces in one test, which is the whole reason to prefer it over IsNullOrEmpty.
  • TrimStart().StartsWith("#", StringComparison.Ordinal) — a comment line is skipped rather than rejected, and the comparison kind is stated because this is an identifier, not prose.
  • Split(';', StringSplitOptions.TrimEntries) — trims each field as it splits. Note the absence of RemoveEmptyEntries: the data is positional, so a blank field must keep its place.
  • p.Length < 3 — the guard that makes every index below it safe. Without it a short line is an IndexOutOfRangeException rather than a rejected row.
  • ToUpperInvariant on the SKU, because it is an identifier being normalised for storage — the culture-aware version would behave differently on a Turkish machine.
  • TryParse twice, and CultureInfo.InvariantCulture on the decimal, because the number was written by a machine and not by a person.

Now change CultureInfo.InvariantCulture to CultureInfo.CurrentCulture and run it on a machine set to Italian. The weight 18.40 becomes 1840, silently, and your total shipment weight is a hundred times too heavy. That one argument is the whole lesson.

Golden rules

  1. Strings are immutable: every method returns a new one. s.Trim(); on a line by itself does nothing at all, and nothing warns you.
  2. Pass a StringComparison whenever you compare. Ordinal for identifiers, SKUs, paths and keys; OrdinalIgnoreCase when case should not matter; culture-aware only for sorting text a human will read.
  3. Stop writing a.ToLower() == b. It allocates, and it breaks on Turkish machines where the upper-case of i is not I.
  4. IndexOf returns −1, not an exception. Test it before using the result — −1 + 1 is 0, which turns "not found" into "the whole string".
  5. IsNullOrWhiteSpace is almost always the check you meant, because a field containing three spaces is empty to everyone except IsNullOrEmpty.
  6. RemoveEmptyEntries is a deliberate choice, never a habit. On positional data it silently shifts every column after a gap.
  7. Split is not a CSV parser. The moment the data comes from outside your program and may contain quoted separators, use a real library.
  8. StringBuilder when the concatenation is inside a loop, interpolation everywhere else. The rule is about the loop, not about the length.
  9. Use InvariantCulture for any string a machine will read back — files, APIs, URLs, logs — in both directions.
  10. A range, s[3..5], is clearer than Substring(3, 2), because start-and-end and start-and-length are two different mental models and mixing them is an off-by-one.
  11. Give a case-insensitive dictionary a StringComparer, not every call site a ToUpper.

Interview questions

"Why are strings immutable in C#?"

Three payoffs. They are automatically thread-safe, because nothing can change underneath a reader. They are safe as dictionary keys, since a key cannot mutate after it has been hashed into a bucket. And identical literals can be interned into one shared object. The cost is an allocation for every operation, which is invisible outside a loop and quadratic inside one — that is exactly the gap StringBuilder fills. The practical consequence for everyday code is that no string method changes the string: they all return a new one, so s.Trim(); on its own line is a no-op the compiler will not warn you about.

"What is the difference between ==, Equals and ReferenceEquals on strings?"

== is overloaded on string to compare the characters, which is why it feels natural — it behaves unlike every other reference type. Equals does the same, but has an overload taking a StringComparison, which is the one I actually want, because it lets me say ordinal or ordinal-ignore-case explicitly. ReferenceEquals asks whether they are the same object, which for strings is usually only interesting when demonstrating interning. In review I flag any string comparison that does not state its StringComparison, because the default varies by method and by machine.

"When would you use StringBuilder?"

When the concatenation is in a loop. Each += on a string allocates a new string and copies everything accumulated so far, so building an eighty-thousand-line export that way is billions of character copies and minutes of runtime — it usually gets misdiagnosed as a database problem. StringBuilder keeps a mutable buffer and allocates once at the end. Outside a loop it is the wrong choice: interpolation is shorter, clearer and no slower. For joining a sequence I would reach for string.Join before either.

"Why is ToLower() before comparing a bad idea?"

Two reasons. It allocates a whole new string just to throw it away, and it applies the machine's culture rules to something that is usually an identifier — in Turkish the lower-case of I is a dotless ı, so a header check or a SKU lookup that works everywhere else fails on a Turkish machine, with no exception and no clue. The correct version states the intent: string.Equals(a, b, StringComparison.OrdinalIgnoreCase). The same reasoning makes ToUpperInvariant the right call when you genuinely must normalise an identifier for storage.

"Come faresti il parsing di una riga CSV?"

Se il formato è mio e controllo io chi scrive il file, Split con TrimEntries va benissimo — ma senza RemoveEmptyEntries, altrimenti una colonna vuota sposta tutte quelle dopo e l'import si corrompe in silenzio. Se il file arriva da fuori uso una libreria, tipo CsvHelper: un CSV vero può avere il separatore dentro un campo fra virgolette, virgolette dentro le virgolette e a capo dentro un campo, e ogni tentativo di gestirlo con Split più due if diventa una macchina a stati sbagliata. E i numeri li leggo sempre con InvariantCulture, se no 18.40 diventa 1840.
