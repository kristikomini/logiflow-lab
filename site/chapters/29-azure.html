Azure

You are not expected to be a cloud architect. You are expected to know where your application runs, where its secrets live, how it talks to the database without a password in a config file, and where you look when it breaks at eight in the morning.

From the advert

"Familiarità con servizi Cloud (Azure)." Familiarità is the softest word in the whole posting. Understand the handful of services below and you have comfortably exceeded it.

IaaS, PaaS, SaaS

🧒 Simple

You want to eat pasta.

  • On-premises — you grow the wheat, mill the flour, and wash up.
  • IaaS — someone rents you a kitchen. You still cook, and you still clean the oven.
  • PaaS — someone rents you a kitchen with a chef’s assistant who keeps everything working. You just cook.
  • SaaS — you go to a restaurant.

Almost everything a .NET developer touches in Azure is the third one.

🎓 Professional

The distinction is who is responsible for what. With IaaS (Virtual Machines) you own the OS: patching, hardening, the runtime, scaling. With PaaS (App Service, Azure SQL Database) the platform owns all of that and you own your code, your configuration and your data. Less control, dramatically less operational work — which for a small team is almost always the right trade.

How resources are organised

  • Tenant → your organisation’s Entra ID directory.
  • Subscription → the billing and quota boundary. Most companies have at least one per environment.
  • Resource group → a folder with a lifecycle. Everything in it can be deployed and deleted together, which is why one group per environment per application is the usual pattern.
  • Region → where it physically runs. For Italian data, Italy North (Milan) or West Europe (Netherlands) — and where matters, because of latency and because GDPR makes people ask.

Naming conventions look bureaucratic and save real time: rg-logiflow-prod-weu, app-logiflow-api-prod, sql-logiflow-prod, kv-logiflow-prod. When something is on fire at 08:00, being able to guess a resource name is worth a great deal.

Secrets and managed identity

🧒 Simple

A password is a key you copy and hand out. Every copy can be lost, and you never quite know how many exist.

A managed identity is a face the building already recognises. There is nothing to copy, nothing to lose, and nothing to accidentally commit to Git — the door simply knows who you are.

the modern connection string — with no password in it
// appsettings.json — safe to commit
"ConnectionStrings": {
  "Default": "Server=sql-logiflow-prod.database.windows.net;Database=LogiFlow;Authentication=Active Directory Default;"
}
// Program.cs — read the rest of the secrets from Key Vault, as the app's own identity
if (!builder.Environment.IsDevelopment())
{
    builder.Configuration.AddAzureKeyVault(
        new Uri($"https://kv-logiflow-prod.vault.azure.net/"),
        new DefaultAzureCredential());
}
🎓 DefaultAzureCredential is the piece worth understanding

It tries a chain of credential sources in order: environment variables, then the workload or managed identity assigned to the running resource, then Visual Studio, the Azure CLI, and Azure PowerShell. The consequence is that the same code works on your laptop and in production — locally it uses your az login session, in Azure it uses the app’s managed identity. No secret is stored anywhere in either case.

Configuration in App Service

App settings in the portal or pipeline become environment variables, which sit above appsettings.json in the configuration hierarchy (chapter 14). Nested keys use a double underscore: ConnectionStrings__Default, Pricing__TimeoutSeconds. Better still, reference Key Vault directly: @Microsoft.KeyVault(SecretUri=…).

Deployment slots

🧒 Simple

Instead of redecorating the shop while customers are inside, you decorate an identical shop next door, check it is right, and then swap the front doors over. If something is wrong, you swap the doors back.

the swap
# deploy to a staging slot — production is untouched
az webapp deploy --resource-group rg-logiflow-prod \
                 --name app-logiflow-api-prod --slot staging \
                 --src-path ./publish.zip

# warm it up, run smoke tests against https://app-…-staging.azurewebsites.net

# then swap: near-zero downtime, and instantly reversible
az webapp deployment slot swap --resource-group rg-logiflow-prod \
                               --name app-logiflow-api-prod --slot staging

Slots are the cheapest safe-deployment mechanism Azure offers, because the swap warms the new instance first and the rollback is another swap. Mark environment-specific settings as deployment slot settings so they stay with the slot instead of following the swap.

Where you look when it breaks

Application Insights, queried with KQL
// the failing requests in the last hour, worst endpoints first
requests
| where timestamp > ago(1h) and success == "False"
| summarize failures = count(), p95 = percentile(duration, 95) by name
| order by failures desc

// everything belonging to one user's request — the trace id from chapter 14
union requests, dependencies, exceptions, traces
| where operation_Id == "8f2b1c…"
| order by timestamp asc

The second query is why returning a traceId in your error responses matters: a user reports the id and you reconstruct their entire request across every service it touched.

⚠ Cost is a correctness concern

The cloud bills by the hour whether or not anyone is using it. Realistic ways teams lose money: a development environment nobody switched off; a SQL Database over-provisioned "to be safe"; an Application Insights instance ingesting verbose logs at full sampling; and unbounded egress. A developer who asks "what does this cost per month?" in a design discussion is unusual and valued.

Golden rules

  1. PaaS unless you have a reason. Owning an OS is work nobody thanks you for.
  2. One resource group per application per environment. Deleting the group deletes the bill.
  3. Secrets live in Key Vault, never in appsettings.json, never in Git.
  4. Managed identity over connection-string passwords. Nothing to leak.
  5. DefaultAzureCredential makes local and cloud the same code.
  6. App settings override appsettings.json; nested keys use __.
  7. Deploy to a slot and swap. It is warm-up and rollback in one mechanism.
  8. Send logs, metrics and traces to Application Insights, and include a trace id in error responses.
  9. Choose the region deliberately — latency and data residency both matter.
  10. Ask what it costs. Turn off non-production environments outside working hours.
  11. Anything you clicked in the portal will be gone or wrong in six months. Put it in code (chapter 30).

Interview questions

"What is the difference between IaaS and PaaS?"

Who owns the operating system. IaaS gives you a VM and the patching, scaling and hardening that come with it; PaaS gives you a place to put code and takes that work away. Give an example of each: Virtual Machines versus App Service.

"How do you store a connection string in Azure?"

In Key Vault, read at startup using the application’s managed identity — or better, avoid the password entirely with Entra authentication to Azure SQL. Never in appsettings.json, and never in source control.

"What is a managed identity?"

An Entra ID identity assigned to an Azure resource, whose credentials the platform rotates and never exposes. The application authenticates as itself, so there is no secret to store, leak or rotate manually.

"How would you deploy without downtime?"

Deploy to a staging slot, warm it and smoke-test it, then swap. Rollback is a second swap. Add that database migrations must be backward compatible for the duration of the swap, because both versions run against the same schema for a moment — that caveat is what makes the answer sound like experience.

"Your API is slow in production. Where do you start?"

Application Insights: the performance blade for slow endpoints, then dependency durations to see whether the time is in SQL, an HTTP call or your own code, then an end-to-end trace for a single slow operation. Metrics before guesses — and the same discipline as chapter 11.
