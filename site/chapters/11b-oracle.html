Oracle, for a SQL Server developer

Chapters 09 to 11 taught the relational model on SQL Server and T-SQL, because that is what most .NET jobs in the region run. But a good number of adverts add a line: “conoscenza dei database relazionali, preferibilmente Oracle”. The word that matters is preferibilmente — preferred, not required. Nobody rejects a candidate who knows SQL Server and PostgreSQL for not having touched Oracle. What sinks the answer is freezing on “have you used Oracle?” This chapter is the honest bridge: the relational fundamentals are identical, and this is exactly where the dialect, the types and — the one that actually matters — the concurrency model differ.

From the adverts

A Modena consultancy's junior .NET posting lists, under le skill tecniche: “conoscenza fondamentale dei database relazionali (preferibilmente Oracle)”. Read the two qualifiers together: fondamentale asks for the fundamentals, which you have, and preferibilmente makes Oracle itself a plus, not a gate. The right move is not to claim Oracle you have not used — it is to say that your daily engines are SQL Server and PostgreSQL, that the relational fundamentals carry across unchanged, and that you know where Oracle differs. Then be able to name the differences. That answer beats a vague “sì, un po'” from someone who cannot.

What is exactly the same

🧒 Simple

Two cars from different makers. Both have a wheel, three pedals and a gearstick, and if you can drive one you can drive the other. What differs is where the indicator stalk sits and what the warning lights are called — annoying for an afternoon, not a new skill.

SQL Server and Oracle are those two cars. The road — tables, rows, keys, joins, indexes, transactions — is the same road.

🎓 Professional

The relational model does not change between engines. Everything from chapters 09–11 transfers to Oracle unchanged: normalisation, primary and foreign keys, the join types, GROUP BY and aggregates, B-tree indexes, the meaning of a clustered vs non-clustered access path, ACID transactions and the four isolation levels named by the SQL standard. A SELECT ... JOIN ... WHERE ... GROUP BY ... HAVING ... ORDER BY is byte-for-byte the same statement on both.

So the useful way to learn Oracle when you already know SQL Server is not to relearn databases. It is to learn a diff: a short list of places where the same intent is spelled differently, plus one place — how the engine handles concurrent readers and writers — where the behaviour, not just the spelling, is genuinely different. The rest of this chapter is that diff.

  • VARCHAR2, not VARCHAR. Oracle keeps VARCHAR as a reserved word and tells you to use VARCHAR2 for every variable-length string, because it reserves the right to change what a bare VARCHAR means. Using it marks you instantly as someone who has actually read Oracle rather than guessed.
  • NUMBER is one type for everything numeric. There is no separate INT/BIGINT/DECIMAL family — you scale one type with precision and scale, and NUMBER(10) is your integer.
  • DATE already carries a time. An Oracle DATE is a date and a time to the second — unlike a SQL Server DATE, which is date-only. For sub-second or time-zone data you reach for TIMESTAMP.

The one gotcha that catches everyone: '' is NULL

🎓 Professional

Oracle treats an empty string as NULL. On SQL Server, '' and NULL are two different values — an empty string is a string of length zero, and WHERE name = '' can match rows. On Oracle, storing '' stores NULL, and so WHERE name = '' matches nothing, ever, because nothing equals NULL. A validation that worked on SQL Server (“reject blank names”) can silently invert its meaning when the same code runs against Oracle.

This is the single most common cross-engine surprise, and a very common interview probe for anyone who claims both. The defensive habit is to test for IS NULL rather than = '', and to never rely on an empty string being distinct from absence.

Top-N and paging: three eras in one table

You will meet Oracle code from three eras. Modern Oracle (12c and later, which is almost everything still supported) uses the same standard OFFSET ... FETCH as SQL Server. Older code uses ROWNUM, and it is worth being able to read because a maintenance job is mostly reading old code. 

-- Modern Oracle (12c+): the same standard clause SQL Server uses
SELECT id, name
FROM   customers
ORDER  BY name
OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

-- Old Oracle you will inherit: ROWNUM, and why it needs a sub-query
SELECT * FROM (
  SELECT id, name FROM customers ORDER BY name
) WHERE ROWNUM <= 10;
Line by line
  • OFFSET ... FETCH is identical on both engines — it is SQL standard, so the paging you already write for SQL Server runs on Oracle 12c+ unchanged. This is the answer to give first.
  • ROWNUM is assigned before the ORDER BY. That is the trap: SELECT ... WHERE ROWNUM <= 10 ORDER BY name numbers ten arbitrary rows and then sorts them, giving you ten random customers in name order, not the first ten by name.
  • The sub-query fixes it. Sort in the inner query, then let ROWNUM count the already-sorted rows in the outer one. Seeing this pattern and knowing why the nesting is there is the whole point of being able to read legacy Oracle.

Generating keys: sequences and identity

SQL Server hides key generation inside the column with IDENTITY. Oracle historically made it explicit with a standalone SEQUENCE object, and since 12c also offers the same inline GENERATED AS IDENTITY you know. 

-- The classic Oracle pattern, still everywhere in older schemas
CREATE SEQUENCE customer_seq START WITH 1 INCREMENT BY 1;

INSERT INTO customers (id, name)
VALUES (customer_seq.NEXTVAL, 'Ferrari Meccanica srl');

-- Modern, and closest to SQL Server's IDENTITY
CREATE TABLE customers (
  id   NUMBER GENERATED ALWAYS AS IDENTITY,
  name VARCHAR2(200)
);
Line by line
  • A SEQUENCE is a separate object, not a column property. One sequence can feed several tables, and customer_seq.NEXTVAL is how you draw the next value. There is also .CURRVAL, which returns the last value this session drew — not a global “latest”, which is a common misread.
  • Sequences are not gap-free. A rolled-back transaction still consumed its number, exactly like SQL Server IDENTITY. Neither engine promises a contiguous run, and a business requirement for gap-free numbering (invoice numbers) is an application problem on both.
  • GENERATED ALWAYS AS IDENTITY is the modern equivalent of IDENTITY(1,1) and is what you would reach for in a new Oracle schema — it wraps a sequence for you.

PL/SQL is to Oracle what T-SQL procedures are to SQL Server

A stored procedure written in PL/SQL looks unfamiliar for about ten minutes and then reads exactly like the procedural T-SQL you already write — declare variables, run statements, handle errors. The shapes differ; the ideas do not. 

-- PL/SQL: a block declares, does, and handles errors in three sections
DECLARE
  v_count NUMBER;
BEGIN
  SELECT COUNT(*) INTO v_count FROM orders WHERE customer_id = 42;
  IF v_count = 0 THEN
    RAISE_APPLICATION_ERROR(-20001, 'Customer has no orders');
  END IF;
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('nothing matched');
END;
Line by line
  • DECLARE / BEGIN / EXCEPTION / END is the shape of every PL/SQL block: variables first, logic in the middle, error handling last. T-SQL scatters DECLARE through the body and wraps errors in TRY ... CATCH; PL/SQL gives each its own section.
  • SELECT ... INTO reads one row into variables. If it matches no rows it does not return empty — it raises NO_DATA_FOUND, and if it matches more than one it raises TOO_MANY_ROWS. That is the opposite of T-SQL's silent assignment, and it is why the EXCEPTION block exists.
  • Named exceptions, not error numbers to parse. NO_DATA_FOUND, DUP_VAL_ON_INDEX and friends are predefined; you raise your own with RAISE_APPLICATION_ERROR and a number in the -20000 range.
  • DBMS_OUTPUT.PUT_LINE is PRINT. The reusable code lives in packages — a spec plus a body, grouping related procedures and functions, which SQL Server has no direct equivalent of.

The real difference: readers never block writers

🧒 Simple

You want to read a page of a book while someone edits it. One library makes you wait until the editor finishes the sentence. The other hands you a photocopy of the page as it was the moment you asked, and lets the editor keep writing. You never wait, and you never see a half-written sentence.

Oracle is the photocopy library. It has been, by default, since long before SQL Server offered the same thing.

🎓 Professional

This is the difference worth knowing cold, because it is behaviour, not spelling. Oracle's default concurrency is multi-version read consistency (MVCC): a query sees a consistent snapshot of the data as of the moment it started, reconstructed from undo, and readers never block writers and writers never block readers. A long report does not hold up the transactions writing the same tables.

SQL Server's historical default, READ COMMITTED, uses shared read locks, so a reader can block a writer and vice versa — which is the whole reason the WITH (NOLOCK) hint became a cultural reflex on SQL Server codebases, trading correctness for not waiting. SQL Server can behave like Oracle by turning on Read Committed Snapshot Isolation (RCSI), and Azure SQL Database has it on by default — but a classic on-prem SQL Server usually does not.

Say this in an interview and you have said something most candidates with “Oracle” on their CV cannot: on Oracle I would not reach for a NOLOCK equivalent, because the reason it exists on SQL Server — readers and writers blocking each other — is not the default there. There is a cost, of course: the famous ORA-01555 snapshot too old is what you get when a long-running query outlives the undo kept to reconstruct its snapshot.

Schemas, commits and the data dictionary

A few structural differences that come up the first day on an Oracle codebase:

TopicSQL ServerOracle
Top-level containerMany databases on one instance; each has schemasOften one database; a schema is essentially a user, and you have many
Referring acrossDatabase.schema.tableschema.table (the schema is the user who owns it)
DDL and transactionsDDL is transactional; it can sit inside a transaction and roll backDDL auto-commits — a CREATE or ALTER commits the transaction around it
Commit cultureAutocommit per statement by defaultExplicit COMMIT/ROLLBACK; nothing is durable until you commit
“Show me the schema”sys.tables, sys.columns, INFORMATION_SCHEMAUSER_TABLES, ALL_TAB_COLUMNS, DBA_* views
  • DDL auto-commits on Oracle — this catches SQL Server developers who assume a CREATE TABLE inside a transaction will roll back with everything else. It will not, and it commits your pending changes with it.
  • You must COMMIT on Oracle. Coming from SQL Server's per-statement autocommit, forgetting the explicit commit and wondering why another session cannot see your insert is a classic first-day confusion.

From .NET, it is a provider swap

The reassuring part for a .NET developer: your data-access code barely changes. ADO.NET, Dapper and EF Core all have Oracle providers, and at the LINQ or SQL-text level almost everything you wrote for SQL Server carries over — the provider translates the dialect for you. 

// EF Core: the same DbContext, a different provider and connection string
// package: Oracle.EntityFrameworkCore   (vs Microsoft.EntityFrameworkCore.SqlServer)
builder.Services.AddDbContext<LogiFlowDb>(o =>
    o.UseOracle(config.GetConnectionString("Default")));

// Raw ADO.NET: Oracle.ManagedDataAccess.Client instead of Microsoft.Data.SqlClient
using var conn = new OracleConnection(connectionString);
Line by line
  • UseOracle(...) replaces UseSqlServer(...) and that is most of the change. Your entities, your DbSets, your LINQ queries and your migrations stay — EF Core's provider model is exactly this seam.
  • The managed driver is Oracle.ManagedDataAccess (ODP.NET, Managed) — pure managed code, no native Oracle client install, which is the one you want. The OracleConnection / OracleCommand pair mirrors SqlConnection / SqlCommand one for one.
  • Where the abstraction leaks is names and types. Identifier case (below), NUMBER mapping to your C# numeric types, and the empty-string-is-null rule reach through the provider — so the diff in this chapter is exactly the part EF Core does not hide.
  • Case in identifiers: Oracle folds an unquoted Customers to uppercase CUSTOMERS, and only a double-quoted "Customers" stays mixed-case — and then every reference must quote it too. This is why EF Core's default names sometimes need explicit configuration on Oracle.

Golden rules

  1. The relational model does not change between engines. Everything in chapters 09–11 — keys, joins, indexes, transactions, isolation — transfers to Oracle unchanged.
  2. Do not claim Oracle you have not used. Say SQL Server and PostgreSQL are your daily engines, the fundamentals carry across, and you know where Oracle differs — then name the differences.
  3. Use VARCHAR2, never a bare VARCHAR. It is the tell that you have actually read Oracle.
  4. NUMBER is the one numeric type; an Oracle DATE already carries a time; big text is a CLOB.
  5. On Oracle an empty string is NULL. Test IS NULL, never = '', and never assume blank is distinct from absent.
  6. Modern paging is the standard OFFSET ... FETCH, the same as SQL Server. Read ROWNUM only to maintain old code — and remember it is numbered before the sort.
  7. Keys come from a SEQUENCE (.NEXTVAL) or modern GENERATED AS IDENTITY; neither is gap-free, exactly like IDENTITY.
  8. PL/SQL blocks are DECLARE / BEGIN / EXCEPTION / END; SELECT ... INTO raises NO_DATA_FOUND instead of returning empty.
  9. The difference that matters is concurrency: Oracle's default MVCC means readers never block writers, so there is no NOLOCK culture. SQL Server matches it only with RCSI on.
  10. Oracle DDL auto-commits, and nothing is durable until you COMMIT. Coming from SQL Server's autocommit, both surprises bite on day one.
  11. From .NET it is a provider swap: UseOracle and Oracle.ManagedDataAccess. Your entities, LINQ and migrations stay; names, types and the null rule are what leak through.
  12. Inspect the schema with USER_TABLES / ALL_TAB_COLUMNS, not INFORMATION_SCHEMA.

Interview questions

"Have you worked with Oracle?"

Not as a daily engine — my hands-on work is SQL Server and PostgreSQL, and I would not claim Oracle production experience I do not have. But the relational fundamentals are the same across all three, so what I would need to pick up is a dialect, not a new skill: VARCHAR2 instead of VARCHAR, NUMBER as the one numeric type, sequences or GENERATED AS IDENTITY for keys, PL/SQL where I would write a T-SQL procedure, and the thing I would actually watch for — that an empty string is NULL on Oracle. I can be productive quickly.

"Name a real behavioural difference between Oracle and SQL Server, not just syntax."

Concurrency. Oracle's default is multi-version read consistency: a query reads a consistent snapshot as of when it started, so readers never block writers and writers never block readers. SQL Server's historical default, read committed with locks, does let them block each other — which is the entire reason WITH (NOLOCK) became a habit on SQL Server. On Oracle I would not reach for a NOLOCK equivalent because the problem it solves is not the default there. SQL Server matches Oracle's behaviour when you enable Read Committed Snapshot Isolation, and Azure SQL has it on by default.

"You have a validation that rejects blank names. It works on SQL Server. What might happen on Oracle?"

It can invert. On SQL Server '' and NULL are distinct, so WHERE name = '' matches blank rows. Oracle stores an empty string as NULL, so the same predicate matches nothing and the check quietly passes everything. The fix is to test name IS NULL rather than compare to an empty string, and generally never to rely on blank being different from absent.

"How would you get the first ten customers by name on Oracle?"

On any supported version, the standard clause — SELECT ... ORDER BY name FETCH FIRST 10 ROWS ONLY, which is the same statement I would write on SQL Server. If I were reading older code I would expect ROWNUM instead, wrapped in a sub-query that does the ORDER BY first — because ROWNUM is assigned before the sort, so filtering on it in the same query gives ten arbitrary rows, then sorts those ten.

"What changes in a .NET application if the database is Oracle instead of SQL Server?"

Less than people expect. In EF Core it is a provider swap — UseOracle with the Oracle.EntityFrameworkCore package instead of UseSqlServer, and for raw ADO.NET the managed Oracle.ManagedDataAccess driver, whose OracleConnection/OracleCommand mirror the SqlClient ones. My entities, LINQ queries and migrations stay. What leaks through the abstraction is the dialect diff: type mappings around NUMBER, identifier casing — Oracle uppercases unquoted names — and the empty-string-is-null rule.

"Why must you remember to COMMIT on Oracle?"

Because Oracle does not autocommit per statement the way SQL Server does by default. Until I issue an explicit COMMIT, my changes are visible only to my own session and are not durable; another session keeps seeing the old values. The related surprise is that DDL auto-commits — a CREATE or ALTER commits whatever transaction was open, so I cannot rely on wrapping schema changes in a transaction I might roll back.
