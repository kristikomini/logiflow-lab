React, concretely

Chapter 18 explained what a single-page app is; chapter 18b did the Angular half properly. This is the other one: enough real React to open somebody's project, find the file that draws the screen, follow the data back to your own endpoint, and change something without breaking it.

Why this chapter exists

The region's adverts split roughly in two. The ones that come out of consultancies and industrial software houses write the front-end line as "Angular o Blazor", and chapters 18b and 19 answer those. The ones that come out of product companies — logistics platforms, tracking and dispatching, anything with a live operations screen — write it as React, with no alternative offered. In those, the front end is not a plus. It is half the job description.

React is also the harder of the two to fake, for an unobvious reason. Angular tells you where everything goes; React does not, so a React codebase is the team's accumulated decisions rather than the framework's. That means the words that matter are not API names. They are the handful of ideas — render, state, effect, identity — that every one of those codebases is built out of, whatever it decided to call them.

The one idea, and the shape of a project

🧒 Simple

Imagine you are drawing a picture of a shop window, and every time the stock changes somebody asks you to draw the whole window again from scratch. That sounds wasteful, but it is very easy to get right: you never have to remember which label you already changed, because you are not changing labels. You are drawing the window.

React works like that. You write one function that says what the screen should look like for the data you have right now. When the data changes, React calls your function again, compares the new drawing with the old one, and quietly touches only the parts that actually differ.

🎓 Professional

A React component is a plain function that takes props and returns elements. Calling it is a render. React keeps a lightweight tree of what the last render produced, diffs it against the new one, and applies the minimum set of DOM changes — the part usually described as the virtual DOM. There is no template compiler and no change-detection pass: the function is the template, written in JSX, which is JavaScript with an XML-ish syntax for elements.

The consequence that catches people is that a render is expected to be pure. It may be called more times than there were user actions, and it must produce the same output for the same inputs with no side effects on the way through. Anything that touches the world outside — an HTTP call, a timer, a subscription — goes in an effect, which runs after the render has been committed to the screen.

Where Angular ships a router, an HTTP client and a DI container, React ships a renderer and nothing else. Routing is a library (react-router), server data is a library (TanStack Query), forms are a library (react-hook-form), and every project picks its own. That is the real difference between the two frameworks, and it is an organisational difference before it is a technical one.

A project generated with Vite has a layout you can learn in a minute. src/main.tsx is the entry point — the Program.cs of the front end, where the root component is mounted and the global providers are wrapped around it. src/App.tsx is usually the routing table. vite.config.ts is the build and dev-server configuration, including the proxy you will want for /api. package.json lists the dependencies and the scripts, and .env holds the per-environment settings — where the API base URL belongs, and where you will find it hardcoded to localhost in somebody's repository at least once. Only variables prefixed VITE_ reach the browser, and that is a guard rail rather than a secret store: everything in that file ships to the client and is readable by anyone who opens it.

A component, in full

The same screen as the Angular chapter, so you can hold the two side by side: the shipment list for one customer, fed by the API the rest of this course builds. 

// src/features/shipments/ShipmentList.tsx
import { useEffect, useState } from 'react';
import { getShipmentsForCustomer } from './shipmentApi';
import type { Shipment } from './shipment.types';

type Props = { customerId: number; customerName: string };

export function ShipmentList({ customerId, customerName }: Props) {
  const [shipments, setShipments] = useState<Shipment[] | null>(null);
  const [error, setError]         = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    setShipments(null);
    setError(null);

    getShipmentsForCustomer(customerId, controller.signal)
      .then(setShipments)
      .catch(e => { if (e.name !== 'AbortError') setError('Could not load shipments.'); });

    return () => controller.abort();
  }, [customerId]);

  if (error)              return <p className="error">{error}</p>;
  if (shipments === null) return <p>Loading…</p>;

  return (
    <>
      <h2>Shipments for {customerName}</h2>
      {shipments.length === 0 ? (
        <p>No shipments yet.</p>
      ) : (
        <table>
          <tbody>
            {shipments.map(s => (
              <tr key={s.id}>
                <td>{s.reference}</td>
                <td>{formatDate(s.dispatchedAt)}</td>
              </tr>
            ))}
          </tbody>
        </table>
      )}
    </>
  );
}
Line by line
  • function ShipmentList({ customerId, customerName }: Props) — the whole component. There is no class, no decorator and no separate template file: the function is all three. Props are the parameters, and they are read-only — assigning to one is the React equivalent of writing to a method argument and expecting the caller to see it.
  • useState — a React hook: a function that gives this component a slot in React's own memory, surviving across renders. It returns the current value and a setter, and calling the setter schedules another render. It does not change the variable you are holding; the next render receives the new one.
  • Shipment[] | null — deliberately nullable, and this is the three-state trap again. null means "not loaded", an empty array means "none", and a component that starts with useState([]) tells a customer with forty shipments that they have none for the first 300 ms — and forever, if the request fails.
  • useEffect(() => {…}, [customerId]) — run this after the render is on screen, and run it again whenever anything in the dependency array differs from last time. That array is not an optimisation; it is the specification of when the effect is allowed to re-run, and getting it wrong is the commonest bug in React.
  • AbortController plus the returned function — the cleanup. React calls it before re-running the effect and when the component is removed, so switching customers quickly cancels the request for the customer you just left. Without it, a slow first response arrives after a fast second one and overwrites it: the screen shows the wrong customer's data with no error anywhere. This is the race every review asks about.
  • key={s.id} — how React tells one row from another between renders. Use the array index instead and deleting a row makes every row below it change identity: focus jumps, ticks move to the wrong line, and inputs keep the value that belonged to their neighbour. The same failure as a missing track in Angular or @key in Blazor.
  • <>…</> — a fragment: return several elements without wrapping them in a pointless div.
  • className, not class — JSX compiles to JavaScript, where class is a reserved word. The same reason a label's for is written htmlFor.
  • formatDate(s.dispatchedAt) — there are no pipes. Formatting is a function call, because the template is JavaScript and never needed a second language for it.
The dependency array, and the stale closure

Every render creates new local variables and new functions, and an effect captures the ones from the render that created it. Leave a value out of the dependency array and the effect goes on reading the copy it captured the first time — a stale closure. The symptom is a timer, a socket handler or a subscription still using a customer id, a filter or a token that changed ten minutes ago, with no error and no clue on screen.

Then people notice the effect re-running too often, delete the dependency array to make it stop, and buy the stale closure on purpose. The real fixes are the boring ones: put every value the effect reads in the array, and stop the array from changing identity on every render — useCallback for a function, useMemo for an object or array, or move the value out of the component entirely if it never changes. Turn on the react-hooks/exhaustive-deps lint rule and let it tell you; it is right far more often than the person disabling it.

State, and where it is allowed to live

This is the part with no real Angular equivalent, and the part a React interview is actually about. Three rules carry most of it.

One: state belongs at the lowest common ancestor of everything that reads it. Two sibling components that must agree do not talk to each other; the state moves up to their parent and comes back down as props. This is called lifting state up, and a codebase that has not done it is a codebase where one value exists in three places and two of them are wrong.

Two: never store what you can compute. A second useState holding the filtered list, kept in step with the first by an effect, is the classic self-inflicted React bug: two sources of truth, one update path, and a render where they disagree. Derive it during the render instead — const visible = shipments.filter(…) — and reach for useMemo only when a profiler says the filtering is expensive, never on suspicion.

Three: server data is not state. The rows in that table are a cached copy of something the API owns, and they carry questions local state never has. Is this stale? Is it being refetched? Did the refetch fail while we still have the old rows on screen? Do two components asking for the same thing cause two requests? That is why nearly every serious React codebase uses a server-cache library rather than useEffect plus useState, and why the component above — correct as it is — is not what you would ship. 

// The same screen, with the server cache doing the work.
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

export function useShipments(customerId: number) {
  return useQuery({
    queryKey: ['shipments', customerId],
    queryFn:  ({ signal }) => getShipmentsForCustomer(customerId, signal),
    staleTime: 30_000,
  });
}

export function useCreateShipment(customerId: number) {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: createShipment,
    onSuccess:  () => qc.invalidateQueries({ queryKey: ['shipments', customerId] }),
  });
}

// In the component, the whole three-state dance is now four names:
const { data, isPending, isError, refetch } = useShipments(customerId);
Line by line
  • queryKey — the cache key and the dependency array at the same time. Change customerId and it is a different entry: different data, its own loading state, no race to lose. Everything wrong with the hand-written version above is a consequence of not having this.
  • queryFn receives a signal — the same AbortController, created and cancelled for you. Passing it through to fetch is the one line people forget, and skipping it silently gives the cancellation away.
  • staleTime — how long a cached answer is served without going back to the network. It is a TTL by another name, and everything chapter 20 says about invalidation applies unchanged, one tier further out.
  • useMutation — a write. It is separate from a read on purpose: reads are cached and retried, writes are neither. If that split sounds familiar, it is CQRS arriving in the browser from the other direction.
  • invalidateQueries — after a successful POST, mark the list stale so it refetches. This is the answer to "I created a shipment and the table did not update", which is otherwise fixed by reloading the page, which is how you can tell a codebase never answered it.
  • isPending / isError / data — the three states, handed to you rather than hand-tracked. There are more, and the one worth knowing is isFetching: a background refresh while the old data is still on screen, which deserves a quiet spinner in the corner, not an empty table.
Redux, Context, and the question behind the question

"Do you know Redux?" is usually asking whether you know what global state is for. Once server data lives in a query cache, the genuinely global state left over is small: the signed-in user, the theme, a feature flag, which modal is open. That is what React's built-in Context is for, and it is enough for most of it.

Redux Toolkit — or Zustand, which newer projects tend to prefer — earns its place when that remainder gets complicated enough to want reducers, middleware and a time-travelling debugger. Naming the progression in that order is a better answer than any amount of API recall, and it is also true. One trap worth carrying: Context is not a performance tool. Every consumer re-renders when the value changes, so a fast-changing value in a high-up Context re-renders half the application.

Where it breaks: the same boundary

The four ways a .NET API and a TypeScript front end fall out of agreement — camelCase, the silent rename, dates arriving as strings, decimal becoming a double — are identical here, and are set out in chapter 18b. So is the CORS answer: proxy /api through the dev server (server.proxy in vite.config.ts) rather than opening the API to any origin, and remember that CORS is a rule about who may read a response, never a protection on your endpoint.

Two things are specific to React and worth adding. The first is that there is no HttpClient: you call fetch, and fetch does not throw on a 4xx or a 5xx. It rejects only when the network itself failed, so a wrapper that never checks response.ok will happily parse an error page as your DTO. Every codebase has one such wrapper. Find it before you trust it.

The second is StrictMode. In development, React deliberately mounts every component twice and runs every effect twice, to expose effects that are not safe to re-run. Two POSTs in the network tab in development and one in production is not a bug in React — it is React telling you that effect has a side effect it should not have, or is missing its cleanup. The wrong fix is deleting StrictMode.

What to claim, and what not to

The honest sentence

"I am a backend developer who builds the React front end against my own API — components and hooks, a query cache for the server data, routing, forms. I know why a list needs a stable key and why an effect needs a cleanup, because I have shipped both bugs. I am not going to design your component library."

For an advert where React is named with no alternative offered, that is the sentence that keeps you in the room. It concedes the specialism and claims the working competence, and the two concrete details in the middle are what separate it from a claim anybody could make.

Do not claim performance work you have not done. useMemo, useCallback and React.memo are easy to name and easy to be caught on, because the honest answer to "when do you reach for them?" is "when the profiler says to", and the follow-up is which profiler. Do not claim Next.js because you have used React: server components and the rendering modes are a separate subject, and "I have not used Next; I know it does server rendering and brings its own routing" is a perfectly good answer. And if the shop turns out to be an Angular or Blazor shop, say so plainly — 18b and 19 are the ones that pay there.

Interview questions

"Che cos'è un componente React?"

A function that receives props and returns the elements to draw. React calls it again whenever its state or props change, compares the result with the previous one, and updates only the parts of the page that differ. Then add that the function must be pure — same input, same output, no side effects — because that is the sentence that shows you know why effects exist at all.

"What is useEffect's dependency array actually for?"

It declares which values the effect reads, so React can re-run it when one of them changes. Leave a value out and the effect keeps using the copy it captured on the render that created it — a stale closure, with no error anywhere. The two wrong fixes are removing the array, which buys the stale closure deliberately, and disabling the lint rule that told you.

"Why not use the array index as a key?"

Because a key is an identity, not a position. Delete or reorder a row and every index below it now names a different item, so React reuses the wrong DOM nodes: focus moves, ticked boxes jump lines, and typed input attaches to the neighbouring row. It is safe only when the list never reorders and nothing is ever inserted or removed — which is exactly when you did not need a key at all.

"You switch customers quickly and the table shows the wrong one. What happened?"

Two requests in flight and the slower one landing last: the first customer's response arrives after the second's and overwrites it. The fix is cancellation plus cleanup — an AbortController aborted in the effect's cleanup function — or, better, a query cache keyed by customer id, so the two answers can never write to the same place. "I would key the cache" is the answer of somebody who has met this in production.

"Why does my POST fire twice in development but once in production?"

StrictMode. React mounts components twice and runs effects twice in development on purpose, to surface effects that are not safe to re-run. It is a diagnosis, not a defect. Either that effect should not be performing the write at all — a POST usually belongs in an event handler or a mutation, not an effect — or it needs a cleanup that cancels what it started.

"How do you manage state in a React application?"

By splitting it in two first. Server data is a cache of something the API owns, and it goes in a query library that handles staleness, refetching, deduplication and cancellation. What is left is genuine client state: keep it as local as you can, lift it to the nearest common ancestor when two components must agree, put the small global remainder in Context, and reach for Redux Toolkit or Zustand only when that remainder wants reducers and a debugger. Then add the rule underneath: never store what you can derive during the render.

"React o Angular, per questo progetto?"

The same shape of answer as in 18b, and it is about the team rather than the technology. Angular decides for you, which is worth a great deal when the team is large, rotates, or is mostly backend. React decides nothing, which is worth a great deal when there is front-end skill in the building and the UI is the product. Then name the shared constraint: either way the API enforces the rules and the front end only chooses what to show.
