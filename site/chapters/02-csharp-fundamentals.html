C# fundamentals

Value types and reference types

If you understand exactly one thing from this chapter, make it this one. Almost every "why did my change disappear?" bug in C# traces back here.

🧒 Simple

You have a notebook. On one page you write the number 7. On another page you write "the red book on the top shelf".

Now a friend copies both pages. If they rub out their 7 and write 9, your 7 is untouched — they copied the number itself. But if they go to the red book on the top shelf and scribble in it, your book is scribbled in too — because you both copied the same directions, not the book.

A number is a value type. Directions to a thing are a reference type.

🎓 Professional

A value type (int, bool, DateTime, decimal, any struct, any enum) stores its data directly in the variable’s storage location. Assignment copies the bits.

A reference type (class, string, arrays, delegates, record by default) stores a reference to an object on the managed heap. Assignment copies the reference — both variables now denote the same object.

The common shorthand "value types live on the stack" is usually true and not a rule: an int field inside a class lives on the heap with its object, and captured locals are lifted into a compiler-generated class. The reliable statement is about copy semantics, not location.

the bug this causes, in four lines
var original = new List<string> { "a", "b" };
var backup   = original;          // NOT a backup — the same list
original.Add("c");

Console.WriteLine(backup.Count);   // 3, and somebody's afternoon is gone

// A real copy:
var realBackup = new List<string>(original);

The practical guidance: use a class unless you have a measured reason not to. A struct earns its place when it is small (roughly 16 bytes or less), immutable, and allocated in large numbers — a coordinate, a money amount, a database identifier. A large mutable struct is one of the few genuinely bad ideas the language lets you express.

null, and how C# stopped losing to it

🧒 Simple

null means "the page where the directions should be written is blank". If you follow blank directions, you fall over. That falling over is called a NullReferenceException, and for about twenty years it was the single most common way programs crashed.

So C# added a rule: you must now say, in advance, which pages are allowed to be blank. You mark those with a question mark. If you forget to check one, the compiler warns you before the program ever runs.

🎓 Professional

With <Nullable>enable</Nullable> in the project file, reference types are non-nullable by default and string? is the opt-in. The compiler runs flow analysis: it tracks whether each reference has been proven non-null on this path and warns when you dereference one that has not.

Crucially this is a compile-time feature with no runtime representation — string? and string are the same type to the CLR. It cannot protect you at a boundary where data arrives from outside (JSON, a database, reflection), which is exactly why validation at the edge still matters.

the operators, and what each one means
string? name = GetName();          // ? — this one may legitimately be null

// ?.  null-conditional: stop and give null instead of throwing
int? length = name?.Length;

// ??  null-coalescing: a fallback
string shown = name ?? "(unknown)";

// ??= assign only if currently null
name ??= "(unknown)";

// !   null-forgiving: "trust me, compiler." A promise, not a check.
int risky = name!.Length;         // silences the warning, keeps the crash
⚠ The ! operator

! does not make anything safe. It switches off the one thing that was helping you. Every use should be rare, local, and justified by a comment — typically "the framework guarantees this is set after OnModelCreating". Reaching for ! to clear a warning is the C# equivalent of taping over a warning light.

Strings

🧒 Simple

A string in C# is written in permanent ink. You can never change one. When you "add" to a string, what really happens is that a brand new string is written out on a fresh page, and the old one is thrown in the bin.

Do that once, and nobody notices. Do it ten thousand times in a loop, and you have filled the bin with 9,999 sheets of paper for one sentence.

🎓 Professional

string is an immutable reference type. Every operation that appears to modify one — +, Replace, Trim, ToUpper — allocates a new instance. In a loop this is quadratic in both time and allocation, which is why StringBuilder exists: it keeps a mutable buffer and materialises the string once.

Immutability is what makes strings safe to share across threads and usable as dictionary keys, and it is why string literals can be interned — one copy per identical literal for the whole process.

the loop, and the fix
// ✗ 10,000 allocations, each one longer than the last
string csv = "";
foreach (var o in orders)
    csv += o.Id + ",";

// ✓ one buffer, one string at the end
var sb = new StringBuilder();
foreach (var o in orders)
    sb.Append(o.Id).Append(',');
string csv2 = sb.ToString();

// ✓✓ better still, when the shape allows it
string csv3 = string.Join(',', orders.Select(o => o.Id));

Two more string features worth having at your fingertips:

interpolation and raw literals
var total = 1234.5m;

// interpolation — compiles to an efficient handler, not string.Concat
string line = $"Order {order.Id} totals {total:C} on {DateTime.UtcNow:yyyy-MM-dd}";

// raw string literal (C# 11+) — no escaping, keeps the layout
string sql = """
    SELECT o.Id, o.Total
    FROM   dbo.Orders AS o
    WHERE  o.CustomerId = @customerId
    """;
⚠ Culture — and this one is about Italy

{total:C} formats using the current culture. On your Italian colleague's machine that is 1.234,50 €; on the Linux build agent it is ¤1,234.50. The rule: use the current culture for anything a human reads, and InvariantCulture for anything a machine reads — files, URLs, JSON, SQL. decimal.Parse("1,5") giving you fifteen is a real bug that has shipped in real Italian software.

⚠ The const across-assemblies trap

A public const is copied into the consuming assembly at compile time. Ship a new library with a changed constant and every caller keeps the old value until it is recompiled. For anything public that might ever change, use public static readonly instead.

Records and pattern matching

Two modern features that appear constantly in current C# and that an interviewer will expect you to recognise.

records — value-like classes, written once
// One line. You get: constructor, properties, Equals, GetHashCode,
// ToString, deconstruction and a `with` expression.
public record Address(string Street, string City, string Cap);

var a = new Address("Via Emilia 1", "Modena", "41121");
var b = new Address("Via Emilia 1", "Modena", "41121");

Console.WriteLine(a == b);            // True  — value equality, not reference
var moved = a with { City = "Bologna" };  // copy, one field changed

A record is still a reference type — it just compares like a value. record struct gives you the value type. Records are the natural choice for DTOs (chapter 14), for query results, and for anything you want to be immutable.

pattern matching — the switch that replaced if-chains
decimal Shipping(Order o) => o switch
{
    { Total: > 100 }                        => 0m,          // property pattern
    { Country: "IT", Weight: < 2 }          => 4.90m,
    { Country: "IT" }                        => 7.90m,
    { Country: "FR" or "DE" or "ES" }        => 12.00m,   // or-pattern
    null                                    => throw new ArgumentNullException(nameof(o)),
    _                                       => 19.00m       // discard: everything else
};

The compiler checks that a switch expression is exhaustive and warns if it is not — a real advantage over an if/else if chain, which fails silently when a new case appears.

Try it yourself

Predict each line before you run it. Getting all four right means you understand this chapter.

record struct Point(int X, int Y);
class Box { public int Value; }

var p1 = new Point(1, 2);
var p2 = p1;
var b1 = new Box { Value = 1 };
var b2 = b1;

p2 = p2 with { X = 99 };
b2.Value = 99;

Console.WriteLine(p1.X);          // ?
Console.WriteLine(b1.Value);      // ?
Console.WriteLine(p1 == new Point(1, 2));  // ?
Console.WriteLine(b1 == new Box { Value = 1 });  // ?

Answers: 1, 99, True, False. The last one is the whole chapter in one line — two different Box objects are never equal by default, however identical their contents.

Golden rules

  1. Assignment copies what is in the variable: the data for a value type, the reference for a reference type. Every aliasing bug is this rule, forgotten.
  2. "Value types live on the stack" is a useful lie. Reason about copy semantics, not storage location.
  3. Use a class unless you have measured a reason for a struct. Never write a large mutable struct.
  4. Turn nullable reference types on. It is compile-time only, so keep validating data that arrives from outside.
  5. ! is a promise to the compiler, not a check. Rare, local, commented.
  6. Strings are immutable. Concatenation in a loop is a bug at scale; use StringBuilder or string.Join.
  7. Current culture for humans, InvariantCulture for machines. In Italy this is not a theoretical concern.
  8. Never make a public const out of something that might change — it is baked into every caller until they recompile.
  9. record for data you want compared by value; class for things with identity.
  10. Prefer a switch expression to an if/else if chain: the compiler tells you when you have missed a case.

Interview questions

"What is the difference between a value type and a reference type?"

Copy semantics: a value type copies its data on assignment, a reference type copies the reference so both names denote one object. Then mention the consequences — default equality, nullability, and the aliasing bug — because that is what separates a memorised answer from an understood one.

"Why is string immutable?"

Thread safety without locking, safe use as dictionary keys, and interning. The cost is that every apparent mutation allocates, which is why StringBuilder exists.

"Does enabling nullable reference types stop NullReferenceException?"

No — it is compile-time analysis with no runtime representation, so anything crossing a boundary (JSON, database, reflection, an older library) can still hand you a null. It removes a large class of internal bugs and shifts the remainder to the edges, where validation belongs.

"When would you use a record?"

When identity does not matter but contents do: DTOs, query results, value objects, messages. You get value equality, with expressions and a readable ToString for free. Not for entities — an Order with the same values as another Order is still a different order.

"const or static readonly?"

const for things that are true by definition and will never change — Math.PI, the number of days in a week. static readonly for everything else public, because a const is inlined into callers and changing it silently fails to reach them until they rebuild.
