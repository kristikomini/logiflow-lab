How a C# project is built, in order

Every other chapter teaches you one file. This one teaches you the order — which file you write first, what each one is allowed to know about the others, and why a project built in the wrong order fights you the whole way. It is the difference between forty files you copied and nine files you understand.

Read this twice

You are not expected to understand every word here yet. Words like DTO, DbContext and dependency injection get a whole chapter each later on. Right now you only need the shape: what the pieces are called, and which one leans on which.

So read it now for the map, and again after chapter 14 for the meaning. That is the same advice the deeper course gives about its own layer map, and for the same reason: the map is cheap to read early and expensive to skip.

What you are actually building

A typical .NET back end does one thing, over and over: a request arrives from outside, it falls through a short stack of your files, it touches the database, and an answer climbs back up. Every feature you will ever write is another lane through that same stack.

🧒 Simple

Think of a restaurant.

  • The waiter takes your order and brings your food. He never cooks. If you ask for something not on the menu, he says no — politely, and quickly.
  • The kitchen decides what is allowed: no steak after 11pm, no more than four desserts per table. That is where the actual rules live.
  • The storeroom holds the ingredients, on labelled shelves.
  • The menu is a small card. It does not list what the storeroom paid for the beef, or which supplier it came from — it shows only what a customer is allowed to see.

Waiter, kitchen, storeroom, menu. In C# those are called the controller, the service, the database (reached through a DbContext), and the DTO. That is genuinely most of it.

🎓 Professional

The four responsibilities, stated the way you would defend them in an interview:

  • The controller translates between HTTP and C#. It binds the request, calls exactly one thing, and chooses a status code. It contains no business rule — not one if about the domain.
  • The service (or handler, or use case) is the operation. It is the only place a rule is allowed to live, and it is the only file that knows both the storage shape and the wire shape.
  • The entity is the noun — Product, Order. It is the shape the database stores, and in a well-built system it also protects its own invariants.
  • The DTO is what crosses the wire: a deliberately separate class, so that adding a column to a table does not silently add a field to your public API.

The order you write the files

Here is the whole sequence for one feature, start to finish. It is nine steps, and the first time through it takes an afternoon. By the fifth feature it takes twenty minutes, because it is always the same nine steps.

Step 2 — the entity

Start with the noun, because everything else is described in terms of it. A first entity is plain: properties, no behaviour. 

// Domain/Product.cs
public class Product
{
    public int Id { get; set; }
    public string Sku { get; set; } = "";
    public string Name { get; set; } = "";
    public decimal UnitPrice { get; set; }
    public bool IsActive { get; set; }
}
Line by line
  • public class Product — public is an access modifier: every project that references this one may see the type. class declares a reference type, so a variable holds a reference to the object rather than the object itself.
  • public int Id { get; set; } — an auto-property, not a field. The braces are a pair of generated methods, which is what lets a rule be added to set later without any caller changing.
  • Id — named exactly this on purpose. EF Core's convention is that a property called Id, or <TypeName>Id, is the primary key, so nothing has to be configured.
  • string Sku { get; set; } = ""; — the = "" is a property initialiser. Without it the property would start as null and the compiler would warn, because string written without a ? promises never to be null.
  • decimal UnitPrice — decimal and not double, because this is money. See 00b.
  • What is absent matters more. No using of Entity Framework, no attributes, no reference to any other file of yours. That is precisely why it can be written first.

Notice what is not here: no using of Entity Framework, no attributes about tables, no reference to any other file in your project. That is the property that makes it first. Later, chapter 05 and the deeper course will push behaviour back into this class so that an invalid Product cannot be constructed at all — see the real Product.cs in this repository, which has private setters and a static factory for exactly that reason.

Step 3 — the DbContext

// Data/CatalogDbContext.cs
public class CatalogDbContext(DbContextOptions<CatalogDbContext> options)
    : DbContext(options)
{
    public DbSet<Product> Products => Set<Product>();

    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<Product>().Property(p => p.Sku).HasMaxLength(32).IsRequired();
        b.Entity<Product>().HasIndex(p => p.Sku).IsUnique();
        b.Entity<Product>().Property(p => p.UnitPrice).HasPrecision(18, 2);
    }
}
Line by line
  • class CatalogDbContext(...) : DbContext(options) — the colon means inherits from. Your class is a DbContext and gets all of its behaviour; you are adding to it, not starting over.
  • (DbContextOptions<CatalogDbContext> options) — a primary constructor: constructor parameters written on the class line itself. The options carry the connection string, and they arrive from Program.cs rather than being built here.
  • DbContextOptions<CatalogDbContext> — a generic type. The part in angle brackets is a type argument, so these options are known to belong to this context and not to another one.
  • public DbSet<Product> Products => Set<Product>(); — three things at once. DbSet<Product> is the type, a queryable table of products; => makes it an expression-bodied property, recomputed on each access; Set<Product>() is the inherited method call that produces it. This single line is the wire from your code to a table.
  • protected override void OnModelCreating — override replaces a method inherited from DbContext, and protected means only this class and its descendants may call it. You never call it: EF Core does, once, when it first works out the model.
  • b.Entity<Product>().Property(p => p.Sku) — a fluent chain, where each call returns something the next call can be made on. p => p.Sku is a lambda, an unnamed function meaning "given a product, this property" — used here as a way of naming the property, not of running anything.
  • .HasMaxLength(32).IsRequired() — these become NVARCHAR(32) NOT NULL in the generated table. What is configured here decides the shape of the column.
  • .HasPrecision(18, 2) — eighteen digits in total, two after the point. Omit it and SQL Server picks a default that silently rounds money.

This is the first file that has to know about another one: DbSet<Product> is the wire. Everything about how the noun becomes a table is decided here, which is why it comes before the table itself. Chapter 12 is the full treatment.

Step 4 — the migration

dotnet ef migrations add AddProduct
dotnet ef database update
Line by line
  • dotnet ef — a separate tool from dotnet itself, installed once with dotnet tool install --global dotnet-ef. "Command not found" here means the tool is missing, not the SDK.
  • migrations add AddProduct — compares your current model against the last migration and generates a C# file describing the difference. AddProduct is only a name, but make it descriptive: it becomes the filename.
  • database update — a separate step that runs pending migrations against the real database. Generating and applying are deliberately not one command.
  • Read the generated file before running it. A migration that drops a column and one that renames it look almost identical, and only one of them loses data.

You do not write this file; EF Core generates it by comparing your model to the last migration. You do read it before running it — a migration that drops a column looks exactly like a migration that renames one, and only one of those loses data.

⚠️ The commit rule

Add the migration in the same commit as the property that caused it. A model that has drifted from its migrations builds perfectly on your machine and fails on everybody else’s, at startup, with an error about a column that does not exist.

Step 5 — the DTO

// Contracts/ProductDto.cs
public record ProductDto(int Id, string Sku, string Name, decimal UnitPrice);
Line by line
  • public record ProductDto(...) — record declares a reference type compared by value: two ProductDtos with the same contents are equal. That is what you want for data, and not what you want for entities.
  • (int Id, string Sku, ...) — a positional record. This parameter list generates a constructor, one read-only property per parameter, value equality and a readable ToString — the whole class, from one line.
  • The generated properties are init-only: settable while the object is being constructed, frozen afterwards. A DTO is a message, and a message should not change after it is sent.
  • What is missing is the design. No IsActive, no cost price, no navigation back to Order. A DTO is a deliberate subset, and that is the entire reason it exists.

One line, and it is one of the most important lines in the feature. DTO means data transfer object: the shape that crosses the boundary between your program and everyone else’s.

🧒 Why not just send the Product?

Because your Product class is the storeroom’s inventory sheet, and the DTO is the menu. The inventory sheet has the supplier, the cost price and a note saying which shelf it is on. You would hand a customer the menu.

And there is a second reason, which is about time. The inventory sheet changes whenever the storeroom changes. If the customers are reading the inventory sheet, then rearranging your own storeroom breaks their lunch.

🎓 Four failures a DTO prevents
  1. Over-sharing. Add CostPrice to the entity for an internal report and it appears in your public JSON that afternoon, for everyone.
  2. Over-posting. If the entity is also the input type, a caller can send fields you never meant to expose — an Id, an IsActive — and model binding will happily set them.
  3. Cycles. Order has Customer, which has Orders. Serialising that either throws or emits a megabyte.
  4. Accidental API changes. Renaming a column becomes a breaking change for every client, and you find out from them.

Real features usually have more than one DTO per noun — a CreateProductRequest going in and a ProductDto coming out — because what a caller may send and what it may see are different questions. In this repository that pair lives in ProductFeatures.cs.

Step 6 — the service

The interface first, then the class. The interface is what the controller will depend on; the class is the part you will later want to swap in a test. 

// Services/IProductService.cs
public interface IProductService
{
    Task<ProductDto?> GetAsync(int id, CancellationToken ct);
}

// Services/ProductService.cs
public class ProductService(CatalogDbContext db) : IProductService
{
    public async Task<ProductDto?> GetAsync(int id, CancellationToken ct) =>
        await db.Products
                 .Where(p => p.Id == id && p.IsActive)
                 .Select(p => new ProductDto(p.Id, p.Sku, p.Name, p.UnitPrice))
                 .SingleOrDefaultAsync(ct);
}
Line by line
  • public interface IProductService — an interface is a list of members with no bodies: a contract. The leading I is a near-universal C# convention.
  • Task<ProductDto?> GetAsync(int id, CancellationToken ct); — a signature ending in a semicolon, with no body at all. The interface says what; the class says how.
  • Task<ProductDto?> — Task<T> is a promise of a T, later. The method returns as soon as it starts waiting, and the value arrives when the database answers. The ? says the result may legitimately be null — no such product.
  • CancellationToken ct — the caller's way of saying "stop, nobody is waiting any more". Pass it down through every async call; ASP.NET supplies one that is triggered when the browser disconnects.
  • class ProductService(CatalogDbContext db) : IProductService — here the same colon means implements. The context arrives through the constructor and is never created by this class, which is exactly what lets a test hand it a different one.
  • public async Task<...> GetAsync(...) => — async permits await inside and makes the compiler rewrite the method into a state machine. It is an implementation detail rather than part of the contract, which is why the interface does not mention it.
  • db.Products.Where(p => p.Id == id && p.IsActive) — this lambda is not run as C#. It is captured as an expression tree and translated into a SQL WHERE clause. That is the most important sentence on this page about performance.
  • .Select(p => new ProductDto(...)) — the projection, and it sits inside the query, so SQL Server is asked for four columns rather than whole rows. Move it after a .ToList() and it still works, still passes the test, and reads the entire table.
  • .SingleOrDefaultAsync(ct) — the call that actually executes the query. Single means "throw if there is more than one"; OrDefault means "null is acceptable if there are none". First would silently tolerate duplicates, hiding a broken unique index.
  • await — unwraps the Task and hands the thread back to the pool while the database works. It does not create a thread; it releases one.

Two things in that method are worth more than they look. The CatalogDbContext arrives through the constructor — the service never creates one, which is what lets the framework hand it a different one per request. And the .Select sits inside the query, so EF Core asks SQL Server for four columns instead of fetching whole rows and throwing most of them away. Move that .Select after a .ToList() and it still works, still passes the test, and reads the entire table — chapter 06 is about exactly that line.

Step 7 — the controller

// Controllers/ProductsController.cs
[ApiController]
[Route("api/products")]
public class ProductsController(IProductService products) : ControllerBase
{
    [HttpGet("{id:int}")]
    public async Task<ActionResult<ProductDto>> Get(int id, CancellationToken ct)
    {
        ProductDto? dto = await products.GetAsync(id, ct);
        return dto is null ? NotFound() : Ok(dto);
    }
}
Line by line
  • [ApiController] — an attribute: metadata attached to the class, written in square brackets. This one switches on automatic model validation, so an invalid body becomes a 400 before your code runs at all.
  • [Route("api/products")] — the base URL for every action in this class. Attributes take arguments in parentheses because they really are constructor calls.
  • class ProductsController(IProductService products) : ControllerBase — it depends on the interface, never the class. Nothing in this file knows that ProductService exists.
  • ControllerBase — and not Controller. Controller adds view rendering, which an API does not need. The base class is what supplies Ok() and NotFound().
  • [HttpGet("{id:int}")] — the HTTP verb plus the rest of the route. {id} is a route parameter and :int is a route constraint, so /api/products/abc never reaches this method — it simply does not match.
  • ActionResult<ProductDto> — a return type meaning "either a ProductDto or an HTTP result". It is what lets one method return both Ok(dto) and NotFound() while still documenting the success shape for OpenAPI.
  • int id, CancellationToken ct — neither is written by the caller as C#. Model binding fills id from the URL by matching the name, and the framework supplies the token. Matching the route parameter's name is what makes the first one work.
  • dto is null ? NotFound() : Ok(dto) — the conditional operator: a condition, then ? value-if-true, then : value-if-false. is null rather than == null because is cannot be redefined by an overloaded operator.
  • One decision, and it is about HTTP. No db, no Product — only ProductDto. That is the whole job of the file.

Read what this file does not do. It does not touch db. It does not know what Product is — only ProductDto. It contains one decision, and that decision is about HTTP: found or not found. That is the whole job of a controller, and a controller that has grown past about fifteen lines per action is nearly always one that took work belonging to step 6.

Step 8 — Program.cs, the wiring

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<CatalogDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
builder.Services.AddScoped<IProductService, ProductService>();   // the interface, meet the class
builder.Services.AddControllers();

var app = builder.Build();
app.MapControllers();
app.Run();
Line by line
  • WebApplication.CreateBuilder(args) — builds the host: configuration, logging, and an empty service container. args is the command line, so any setting can be overridden at launch.
  • builder.Services — the DI container's registry. Anything added here can later be requested by any constructor. Nothing is created yet; this is a list of recipes.
  • AddDbContext<CatalogDbContext>(o => ...) — registers the context with a scoped lifetime, meaning one per HTTP request. That is the correct lifetime: a DbContext is not thread-safe and tracks changes for a single unit of work.
  • o => o.UseSqlServer(...) — a configuration lambda. The framework hands you an options object and you set it up. It runs once, at registration.
  • GetConnectionString("Default") — reads ConnectionStrings:Default from configuration, so the password never appears in source.
  • AddScoped<IProductService, ProductService>() — the binding, with two type arguments: the contract that will be asked for, and the class that will be supplied. This is the only line in the entire application that knows both names.
  • builder.Build() — the container closes. After this line registrations are fixed, and the app is ready to be configured.
  • app.MapControllers() — scans for [Route] and [HttpGet] attributes and builds the routing table. Omit it and every request returns 404, with no error anywhere.
  • app.Run() — starts listening and blocks. Nothing written after it runs until the process is shutting down.

This is the only file in the whole application that knows both IProductService and ProductService. Everywhere else asks for the interface and is handed an implementation it never named. That single line is dependency injection, and chapter 14 is where it gets its proper explanation.

⚠️ The error every beginner meets once

InvalidOperationException: Unable to resolve service for type 'IProductService' while attempting to activate 'ProductsController'.

It always means the same thing: you wrote the class, but you skipped step 8. The compiler cannot catch it, because registration happens at run time — which is precisely why step 8 is a step and not an afterthought.

Step 9 — the test

Test the service, not the controller. The service is where your rules are; the controller is mostly ASP.NET, and ASP.NET is already tested. Chapter 24 covers what to test and what not to.

Why that order, and not the other one

The order is not a style preference. It falls out of one fact: a file cannot compile until everything it mentions exists.

⚠️ What happens when you start at the controller

It is the tempting place to start, because it is the part you can see in the browser. What follows is always the same: you invent a method name on a service that does not exist, invent a DTO shape to make the signature look right, and then discover at step 2 that the data cannot actually answer the question you promised. Now the fix is four files wide instead of one, and the shapes you invented tend to survive anyway, because changing them means touching all four.

The two other orders that are also right

“Entity first” is the default, not the law. Two other orders are used by good teams, and knowing why is worth a sentence in an interview.

OrderYou start fromUse it when
Inside-out
the nine steps above		 The entity The default. You understand the data, and the API shape is yours to choose.
Outside-in The DTO and the URL The API contract is fixed — a mobile team is waiting for it, or the endpoint is specified in a ticket. Write the DTO and the controller first against a stub service, then fill in downwards.
Test-first A failing test on the service The rule is fiddly and the edge cases matter more than the plumbing — pricing, discounts, stock allocation. The test names the behaviour before you start arguing with the syntax.
All three end in the same place

Every one of them produces the same nine files with the same dependencies. They differ only in which end you push from. If you are new, push from the entity: it is the end where you can always tell whether you are finished.

How the files find each other

“How is this file connected to that one?” has exactly four answers in a C# project. Once you can name which of the four you are looking at, unfamiliar codebases stop being opaque.

WireLooks likeChecked by
Project reference <ProjectReference Include="..\Domain\Domain.csproj" /> in the .csproj The compiler. This is the wire that decides which project is even allowed to mention which.
Namespace and using using Catalog.Domain; at the top of a file The compiler. Cheap, and reversible.
Constructor injection public class ProductService(CatalogDbContext db) The compiler for the type; the container for the instance.
DI registration builder.Services.AddScoped<IProductService, ProductService>(); Nobody, until it runs. This is the one that fails at start-up rather than at build.

Three of the four are the compiler’s problem, so you find out about them in seconds. The fourth is why a .NET application can compile perfectly and then refuse to start, and why an experienced developer’s eye goes straight to Program.cs when it does.

Where the files go

Two layouts are common. Both are defensible; one of them stops scaling at around a dozen features. 

// By kind — the layout every tutorial shows you
Controllers/    ProductsController.cs  OrdersController.cs  CustomersController.cs
Services/       ProductService.cs      OrderService.cs      CustomerService.cs
Models/         Product.cs             Order.cs             Customer.cs
Dtos/           ProductDto.cs          OrderDto.cs          CustomerDto.cs

// By feature — the layout teams end up at
Features/
  Products/     Product.cs  ProductDto.cs  ProductService.cs  ProductsController.cs
  Orders/       Order.cs    OrderDto.cs    OrderService.cs    OrdersController.cs
Line by line
  • Controllers/ Services/ Models/ Dtos/ — organised by kind: everything of a type together. Clear for two features, painful at twenty, because a single change is spread across four folders.
  • Features/Products/ ... — organised by feature: everything one change touches sits in one folder, and the folder can be deleted when the feature is.
  • The principle is the axis of change. Group by what changes together. A change is almost always one feature and almost never one kind.
  • Folders carry no meaning to the compiler. They do not have to match namespaces — though tooling assumes they do, and fighting that is not worth the trouble.

The difference shows up when you change something. A change is almost always one feature and almost never one kind, so the second layout puts everything a change touches in a single folder while the first spreads it across four. Start with by-kind if it helps you see the pattern — it genuinely is clearer for the first two features — and move to by-feature the moment a folder has more than about eight files in it.

🎓 And then the folders become projects

At the next size up, the layers stop being folders and become separate .csproj projects, so that the “may reference” rules are enforced by the compiler rather than by discipline. That is what this repository does — Domain, Application, Infrastructure, Api — and it is the subject of chapter 23. The nine steps do not change; they just land in four projects instead of four folders.

Try it yourself

Build one feature end to end, today, before you read another chapter. Nine files, one noun, something you care about — Book, Cliente, Bicicletta. One GET that returns one row. Do not add a second endpoint until the first one returns real JSON from a real table.

Then do it a second time, from an empty folder, without looking. The second time is the one that teaches you the order; the first only teaches you that an order exists.

Golden rules

  1. Write the file that needs nothing first. The build order is the dependency order, backwards — the entity compiles alone, the controller compiles last.
  2. One noun has several shapes: what it is (the entity), how it is stored (the table), and what the outside may see (the DTO). Confusing them is the most common beginner bug in .NET.
  3. Never return an entity from a controller. It over-shares, it cycles when serialised, and it makes every database column part of your public API.
  4. A controller may do three things: bind the request, call one service, choose a status code. Any if about the business belongs one file down.
  5. The service is the only file that knows both the entity and the DTO. That is what makes it the border, and what makes it the right place to test.
  6. Program.cs is the only file that knows an interface and its implementation. Everything else asks for the interface.
  7. A class nobody registered does not exist at run time. “Unable to resolve service for type…” always means step 8 was skipped.
  8. Commit the migration with the property that caused it. A model that has drifted from its migrations is a deployment that fails on somebody else’s machine.
  9. Folders by feature scale; folders by kind do not. A change is one feature, never one kind.
  10. One thin slice, all the way through, before the second one. Nine files that return one product beat forty files that return nothing.

Interview questions

"Walk me through what happens when a request hits your API."

Follow the chain out loud and name the file at each step: routing matches the URL to a controller action, the action binds the request and calls a service through an interface, the service applies the rules and queries through the DbContext, EF Core translates the LINQ into SQL, and the result comes back projected into a DTO which is serialised as JSON. Naming the DTO is what separates this answer from a memorised one — it shows you know where the boundary is.

"What do you write first when you start a new feature?"

The entity, because it is the only file that depends on nothing, and then outwards: DbContext, migration, DTO, service, controller, registration, test. Then give the reason rather than the list — you build from the end that needs nothing — and add that you would work outside-in instead if the API contract were already fixed by somebody else.

"Why not just return the entity from the controller?"

Four reasons, and give at least two: over-sharing fields that were never meant to be public, over-posting on the way in, serialisation cycles through navigation properties, and coupling your public API to your table schema so that a rename becomes a breaking change. The DTO is the seam that lets the database and the API change independently.

"Where do you put business logic?"

In the service — or in the entity itself when the rule is about that one object’s consistency, since "a price may not be negative" belongs to Product. Not in the controller, which should only speak HTTP, and not in the DbContext, which should only speak storage. The test that follows is a good closing line: if you cannot exercise the rule without starting a web server, it is in the wrong file.

"Your application compiles but throws on start-up. Where do you look?"

Program.cs. Three of the four ways files connect in C# are checked by the compiler; DI registration is the one that is not, so a start-up failure with a message about resolving a service is almost always a missing AddScoped — or a lifetime mismatch, where a singleton has been handed something scoped.
