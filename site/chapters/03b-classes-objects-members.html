Classes, constructors and properties

Chapter 03 answers "what is encapsulation" the way an interviewer asks it. This chapter is the other half: the actual mechanics of building one class well — every kind of member a class can have, the four ways an object gets constructed and which to use, what a property is doing that a field is not, and the access modifier that should be your default rather than public.

Why this chapter exists

A class is the unit of work in C#, and most of the design decisions you make in a day are made inside one: should this be a field or a property, should the constructor validate, should this setter exist at all. Getting them right is what makes an object impossible to put into a broken state — which is worth more than any pattern, because it removes bugs rather than organising them. Getting them wrong produces the class everybody recognises: twelve public settable properties, a parameterless constructor, and validation scattered across four callers.

Everything a class can contain

public class Order
{
    // 1 — a CONSTANT: compile-time, baked into every caller
    public const int MaxLines = 200;

    // 2 — a STATIC FIELD: one for the whole type, not per object
    private static int _created;

    // 3 — an INSTANCE FIELD: the real state, and it is private
    private readonly List<OrderLine> _lines = new();

    // 4 — a PROPERTY: controlled access to state
    public int Id { get; }
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;

    // 5 — a COMPUTED property: derived, stored nowhere
    public decimal Total => _lines.Sum(l => l.Qty * l.Price);
    public bool IsEmpty => _lines.Count == 0;

    // 6 — a read-only VIEW of internal state, not the list itself
    public IReadOnlyList<OrderLine> Lines => _lines;

    // 7 — a CONSTRUCTOR
    public Order(int id) { Id = id; _created++; }

    // 8 — METHODS: the behaviour, which is what the class is FOR
    public void AddLine(OrderLine line) { /* validated below */ }

    // 9 — an EVENT
    public event EventHandler<OrderStatus>? StatusChanged;

    // 10 — a NESTED type, when it only means anything inside here
    public sealed record OrderLine(string Sku, int Qty, decimal Price);
}
Line by line
  • const versus static readonly: a const is substituted into the caller's compiled code, so changing it in a library does not reach anything already built — the same versioning trap optional parameters have. Use const only for things that are true forever, like Math.PI, and static readonly for everything else.
  • Fields are private. Always. A public field cannot be validated, cannot become computed later, cannot raise an event, and cannot be bound by most frameworks. There is no cost to making it a property, and it is the one rule in this chapter with no exceptions.
  • readonly on _lines means the reference cannot be repointed after construction. The list itself is still mutable — you can still Add to it — which is a distinction that catches everybody once.
  • public decimal Total => … is a computed property: it runs every time it is read and stores nothing, so it can never disagree with the lines. A stored total that is updated by four methods eventually disagrees with one of them.
  • IReadOnlyList<OrderLine> rather than List — otherwise any caller can order.Lines.Add(…) and walk straight past AddLine and its validation, which is the commonest way encapsulation leaks in real code.

Access modifiers: start at private and justify every step up

🧒 Simple

Think of a class as a house. Things marked private live in your bedroom — only you can reach them. internal is the rest of the house, where anyone in the family (your own program) is welcome. public is the front porch out on the street, where strangers you will never meet can lean on it — so once you put something there you cannot move it without upsetting someone. The rule that follows is simple: keep everything in the bedroom, and carry a thing out to the porch only when a stranger genuinely needs it.

  • A member with no modifier is private; a top-level class with none is internal. Both defaults are the safe ones, which is deliberate.
  • public is a promise. Inside one application it is merely untidy; in a library it is a contract you cannot change without breaking somebody, and that is the difference between a class being easy to improve and being frozen.
  • protected is a much bigger commitment than it looks — it exposes your internals to every subclass anyone ever writes, forever. Chapter 03's "composition over inheritance" is largely an argument about how expensive that surface is.
  • internal is the one people underuse. Most classes in an application are implementation detail of that application, and marking them internal says so — and lets InternalsVisibleTo give the test project access without making anything public.
  • The access modifier on the setter is a separate decision: public int Qty { get; private set; } is readable by everyone and writable only from inside. That single line is the most useful encapsulation tool in the language.

Properties: what they do that a field does not

🧒 Simple

A property looks like a piece of data and is actually two little methods — one that hands the value out and one that takes a new one in. Because they are methods, you can put a rule in the middle. A field has no middle. 

public class Order
{
    public int Id { get; init; }                    // set once, during construction, then frozen
    public required string Customer { get; init; }  // the compiler REFUSES an object without it

    public OrderStatus Status { get; private set; } // readable by all, writable by me

    private decimal _discount;
    public decimal Discount                          // a full property, because there is a rule
    {
        get => _discount;
        set => _discount = value is >= 0 and <= 100
            ? value
            : throw new ArgumentOutOfRangeException(nameof(value), value, "0-100.");
    }

    public decimal Total => Lines.Sum(l => l.Qty * l.Price);   // computed, no backing field

    public OrderLine this[int index] => Lines[index];          // an INDEXER: order[0]

    public static Order Empty { get; } = new(0) { Customer = "—" };   // static property
}
Line by line
  • { get; set; } is an auto-property: the compiler generates a hidden backing field. You write the full form only when there is something to do in the middle, and not before.
  • init means the property can be set in an object initialiser and never again. It is how you get immutability without writing a constructor with nine parameters, and it works perfectly with with expressions on records.
  • required moves a run-time null check to compile time: an object initialiser that omits Customer does not build. It is the least-known genuinely useful feature added to the language recently.
  • value — the implicit parameter of every setter. The is >= 0 and <= 100 pattern is chapter 02h's, and putting it here means there is one place a discount can be rejected rather than one per caller.
  • A property should be cheap and should not surprise. Reading one twice should give the same answer and should not hit a database; if it is expensive or can fail, make it a method, because that is what a reader expects parentheses to mean.
⚠️ A mutable property that should not exist

public OrderStatus Status { get; set; } lets any caller move an order from Draft straight to Dispatched, skipping every rule you wrote. The class has properties but no behaviour, so all the logic ends up in whoever happens to be holding it, differently each time. The fix is to make the setter private and expose the transitions as methods — Submit(), Pick(), Dispatch() — each checking what it is allowed to do. Then an invalid status change cannot be written, rather than merely being discouraged.

Constructors: the object's one chance to be valid

🧒 Simple

A constructor is the checklist an object has to pass before it is allowed to be born. To make an Order, the constructor asks for the things an order cannot live without — who it is for, its number — and refuses if any are missing or silly, like an id of zero or an empty name. Because nothing can skip the checklist, you never end up holding a half-built order that falls over several steps later. Do the checking here, once, and every order in the whole program is guaranteed to make sense. 

public class Order
{
    private readonly List<OrderLine> _lines = new();      // field initialiser: runs FIRST

    public int Id { get; }
    public string Customer { get; }
    public DateOnly Date { get; }

    // the ONE real constructor, which validates
    public Order(int id, string customer, DateOnly date)
    {
        if (id <= 0) throw new ArgumentOutOfRangeException(nameof(id));
        ArgumentException.ThrowIfNullOrWhiteSpace(customer);

        Id = id; Customer = customer; Date = date;
    }

    // an overload that CHAINS, so validation is never duplicated
    public Order(int id, string customer) : this(id, customer, DateOnly.FromDateTime(DateTime.Today))
    { }

    // a named alternative, when "new" would not say enough
    public static Order Draft(string customer) => new(NextId(), customer);
}

// primary constructor syntax — C# 12, shorter, no validation hook
public class OrderLine(string sku, int qty)
{
    public string Sku { get; } = sku;
    public int Qty { get; } = qty > 0 ? qty : throw new ArgumentOutOfRangeException(nameof(qty));
}
Line by line
  • The constructor is where an object becomes valid, and it is the only place that can guarantee it. Validate here and no instance can ever exist in a broken state; validate in the caller and you are relying on every caller, including the ones not written yet.
  • : this(…) is constructor chaining, and the rule is that every overload should funnel into one real constructor. Duplicated validation across two constructors always drifts apart eventually.
  • Order of execution: field initialisers first, then the base class's constructor, then your body. That is why a field initialiser cannot use a constructor parameter — it has not arrived yet.
  • A static factory method earns its place when the name adds meaning (Order.Draft(…), TimeSpan.FromMinutes(5)), when you want to return a cached instance, or when two constructors would have the same parameter types and different meanings, which is otherwise impossible.
  • A primary constructor puts the parameters on the class declaration and makes them available throughout the body. Shorter, and worth knowing that it gives you no natural place to validate — the expression-bodied hack above is what you are left with.
⚠️ Never call a virtual method from a constructor

The base constructor runs before the derived class's fields are initialised, so a virtual call from the base reaches the derived override while every field it depends on is still null or zero. The result is a NullReferenceException inside a method that looks obviously correct, and it only happens for objects of the derived type. If construction needs a step that subclasses vary, make it an explicit Initialise() call the caller makes afterwards, or pass the value in.

static: one for the type, not one per object

🧒 Simple

static means "one for everybody", not "one each". A normal field is like every pupil having their own notebook; a static field is the single whiteboard at the front of the class that everyone writes on. That is perfect when there is genuinely only one of the thing — a little helper that tidies up a code — and a trap for anything that should belong to each object, because if everyone scribbles on the one whiteboard at the same moment you get a mess nobody can read. 

public static class SkuFormatter          // a static CLASS: cannot be instantiated
{
    public static string Normalise(string raw) => raw.Trim().ToUpperInvariant();
}

public class Order
{
    private static int _created;                  // ONE counter for the whole program
    public  static int Created => _created;

    static Order() { /* runs once, lazily, before the first use */ }
}

// ✗ the trap this becomes
public static class Cache
{
    public static Dictionary<int, Order> Items = new();    // shared, mutable, global
}
Line by line
  • A static member belongs to the type, so there is exactly one and no this inside it. It can only work with what it is given as arguments, which is why it is right for pure functions and wrong for anything with a dependency.
  • A static class cannot be instantiated or inherited, and exists to hold stateless helpers. Math is one; so is every class of extension methods.
  • A static constructor runs once, automatically, before the first use of the type. You cannot control when, it cannot take parameters, and an exception thrown in it makes the type permanently unusable for the life of the process — which is a spectacularly confusing failure. Avoid putting work in one.
  • Static mutable state is global state. Two web requests are two threads sharing that dictionary, so it needs locking or a concurrent type (chapter 08), and it cannot be substituted in a test, so every test that touches it affects every other one.
  • The real cure is dependency injection: register the cache as a singleton service and inject it. You get exactly one instance, and it is still replaceable in a test. That is chapter 14.

class, record, struct: which shape is this thing

🧒 Simple

Three shapes for three jobs. A class is a person: two people with the same name and birthday are still two different people, so what makes one "the same" is who it is, not what it holds. A record is a banknote: any two ten-euro notes are interchangeable, so what makes them equal is their value. A struct is a tiny value you copy rather than share — a point on a map, an amount of money. Choose by asking: does this thing have a life of its own, or is it only its contents?

// identity matters: two orders with the same fields are still two orders
public class Order { public int Id { get; init; } }

// values matter: two DTOs with the same fields ARE the same as far as anyone cares
public record OrderDto(int Id, string Customer, decimal Total);

var a = new OrderDto(1, "Rossi", 10m);
var b = new OrderDto(1, "Rossi", 10m);
bool same = a == b;                        // TRUE for a record, false for a class

var c = a with { Total = 12m };            // a copy with one change — non-destructive

// small, immutable, value-like: a struct, ideally a readonly record struct
public readonly record struct BinId(int Aisle, int Shelf);
Line by line
  • The question is identity versus value. Does this thing have a life of its own that continues even as its contents change — a customer, an order — or is it defined entirely by what is in it right now? The first is a class, the second a record.
  • A record is a class with the boring parts generated: value equality, GetHashCode, a readable ToString, deconstruction, and with. That makes it close to perfect for DTOs, messages and query results.
  • with creates a shallow copy with named changes. If the record holds a list, both copies share the same list — chapter 02i's point again.
  • struct only pays off when the type is small, short-lived and genuinely value-like. Passing a large struct copies every byte, every time, and the boxing that happens when one is used as an object or an interface undoes the benefit entirely.
  • Do not use a record as an EF Core entity. Value equality fights the change tracker, which identifies entities by key, and with produces an object the context has never seen.

Exercises, with the reasoning shown

Exercise 1 — the validation everybody walked past

public class Order
{
    public List<OrderLine> Lines { get; } = new();
    public void AddLine(OrderLine l)
    {
        if (Lines.Count >= 200) throw new InvalidOperationException("too many lines");
        Lines.Add(l);
    }
}
// elsewhere:
order.Lines.Add(line);
The limit is never enforced.
  • Lines is get-only, which stops the list being replaced and does nothing to stop it being modified — and Add on the exposed list bypasses AddLine entirely. Expose IReadOnlyList<OrderLine> instead and the mistake stops compiling. Note that a determined caller can still cast it back; encapsulation protects against accident, not malice.

Exercise 2 — the object that was born broken

var o = new Order();
o.Customer = "Rossi";
// ... forty lines later, in another method
Dispatch(o);          // o.Date was never set
An object that spent forty lines in an invalid state, and one code path where it never became valid.
  • A parameterless constructor plus settable properties means "valid" is something the caller has to remember. Put the required values in the constructor, or mark them required with init setters — then the compiler rejects the incomplete object and the question disappears.

Exercise 3 — the counter that counted everybody's

public class Basket
{
    public static List<Item> Items = new();
    public void Add(Item i) => Items.Add(i);
}
Every user shares one basket, and two simultaneous requests can corrupt the list.
  • static means one for the whole process, not one per object — so every new Basket() adds to the same collection. It is also a public mutable field, so nothing can validate it, and List<T> is not thread-safe, so concurrent Adds can lose items or throw. Remove the static, make the field private, and expose a read-only view.

Exercise 4 — the constructor that threw inside a subclass

public class Base
{
    public Base() => Configure();
    protected virtual void Configure() { }
}
public class Derived : Base
{
    private readonly List<string> _rules = new();
    protected override void Configure() => _rules.Add("default");
}
NullReferenceException on _rules.Add.
  • The base constructor runs before the derived class's field initialisers, so Configure() reaches the override at a moment when _rules is still null. The code is obviously correct in isolation and fails only for the derived type, which makes it a memorable afternoon. Never call a virtual method from a constructor.
Try it yourself

One class, written the way this chapter argues for: private state, a constructor that validates, a read-only view, a private setter, and transitions as methods. Then try to break it from outside and notice that you cannot. 

public class Order
  {
      public const int MaxLines = 200;
      private readonly List<OrderLine> _lines = new();

      public int Id { get; }
      public required string Customer { get; init; }
      public OrderStatus Status { get; private set; } = OrderStatus.Draft;

      public IReadOnlyList<OrderLine> Lines => _lines;
      public decimal Total => _lines.Sum(l => l.Qty * l.Price);
      public bool IsEmpty => _lines.Count == 0;

      public Order(int id)
      {
          if (id <= 0) throw new ArgumentOutOfRangeException(nameof(id), id, "Must be positive.");
          Id = id;
      }

      public void AddLine(string sku, int qty, decimal price)
      {
          if (Status != OrderStatus.Draft)
              throw new InvalidOperationException($"Cannot add lines to a {Status} order.");
          if (_lines.Count >= MaxLines)
              throw new InvalidOperationException($"An order may not exceed {MaxLines} lines.");
          _lines.Add(new OrderLine(sku, qty, price));
      }

      public void Submit()
      {
          if (IsEmpty) throw new InvalidOperationException("An empty order cannot be submitted.");
          Status = OrderStatus.Submitted;
      }

      public sealed record OrderLine(string Sku, int Qty, decimal Price);
  }

  // now try each of these — the first four do not compile, the last two throw
  var o = new Order(1) { Customer = "Rossi" };
  // var bad = new Order(1);              // required Customer missing
  // o.Status = OrderStatus.Dispatched;   // setter is private
  // o.Lines.Add(...);                    // IReadOnlyList has no Add
  // o.Total = 5m;                        // computed, no setter
  o.Submit();                             // throws: the order is empty
  o.AddLine("MI-42", 2, 9.99m);           // throws once submitted
Line by line
  • private readonly List<OrderLine> _lines with IReadOnlyList<OrderLine> Lines => _lines — the state is private and the view is public, so every addition has to go through AddLine.
  • required string Customer { get; init; } — the compiler rejects an object initialiser that omits it, and nothing can change it afterwards.
  • Status { get; private set; } — readable everywhere, writable only in here, which is what forces a caller through Submit.
  • Total and IsEmpty are computed, so they cannot disagree with the lines they are derived from.
  • Both AddLine and Submit check the state before acting and throw InvalidOperationException — the argument is fine, the moment is not.
  • sealed record OrderLine nested inside: it means nothing outside an order, and it is a value rather than a thing with an identity.

Four of those six failures are compile errors rather than exceptions, and that is the point of the whole chapter: the cheapest bug is the one that cannot be written. Now delete the private from the Status setter and see how many of the rules in Submit become optional.

Golden rules

  1. Fields are private; state is exposed through properties. A public field cannot be validated, computed or bound, and there is no cost to the property.
  2. Start every member at private and justify each step up. internal is right for most classes in an application; public is a promise you have to keep.
  3. The setter's accessibility is a separate decision. { get; private set; } is the most useful encapsulation tool in the language.
  4. The constructor is where an object becomes valid. Validate there and no instance can ever exist broken; validate in the caller and you are trusting every caller not yet written.
  5. Chain constructor overloads into one real constructor with : this(…), so validation exists once and cannot drift.
  6. Never call a virtual method from a constructor. The derived override runs before the derived fields are initialised.
  7. Prefer required and init over a settable property when a value must be supplied once and then stop changing — it moves the check to compile time.
  8. Expose a collection as IReadOnlyList<T>, never as the list itself. Otherwise every caller can walk past the method that validates additions.
  9. Compute what can be computed. A stored total maintained by four methods eventually disagrees with one of them; an expression-bodied property cannot.
  10. A property should be cheap and repeatable. If it is expensive or can fail, make it a method — that is what parentheses promise a reader.
  11. Static mutable state is global state. It is shared across requests, needs locking, and cannot be substituted in a test. Use dependency injection with a singleton instead.
  12. Identity is a class, value is a record, small and short-lived is a struct — and a record is a poor EF Core entity, because value equality fights the change tracker.

Interview questions

"What is the difference between a field and a property?"

A field is storage; a property is a pair of methods that look like storage. Because they are methods, a property can validate in the setter, compute rather than store, raise an event, be virtual, sit on an interface, and have different accessibility on get and set. It can also be changed later without recompiling callers, whereas turning a public field into a property is a binary-breaking change. The practical rule I follow is that fields are always private — usually readonly — and anything public is a property, even when it is a plain auto-property today, because the cost is nothing and the option is worth a lot.

"What should a constructor do?"

Bring the object into a valid state and then stop. That means taking the values that are genuinely required, validating them, and assigning them — ideally to readonly fields or get-only properties, so the object cannot drift out of validity afterwards. What it should not do is real work: no database calls, no I/O, nothing that can block or fail for environmental reasons, because a constructor cannot be asynchronous and an exception there is much harder to handle than one from a method. If I have several overloads I chain them into one real constructor with : this(…), and I never call a virtual method from inside one, because the derived class's fields do not exist yet.

"When would you use a record instead of a class?"

When the thing is defined by its values rather than by having an identity. A DTO, a message on a queue, a query result, a coordinate — two of them with identical contents are interchangeable, so value equality is what I want, and the generated GetHashCode, ToString and with expression are all useful. An Order is the opposite: it has an id and a life of its own, and two orders with identical fields are still two orders, so it is a class. The one place I avoid records is EF Core entities, where value equality works against a change tracker that identifies things by key.

"Why is public not a good default?"

Because it is a promise. Every public member is something callers can depend on and therefore something you cannot change without breaking them, so the more public surface a class has, the less free you are to improve it. Starting at private and opening up deliberately also tends to produce better designs, because the question "who actually needs this" gets asked. In an application most classes should be internal — they are implementation detail of that application, and InternalsVisibleTo still lets the test project reach them. I am particularly careful with protected, which exposes internals to every subclass anyone ever writes.

"Perché esporre una List<T> pubblica è un problema?"

Perché anche se la proprietà è solo get, la lista resta modificabile: il chiamante non può sostituirla ma può fare Add e Remove, quindi scavalca il metodo che contiene le regole — il limite di righe, il controllo sullo stato dell'ordine. La incapsulazione sembra esserci e non c'è. Io tengo la lista in un campo privato readonly, espongo un IReadOnlyList<T> e faccio passare ogni modifica da un metodo che valida. Vale la pena aggiungere che è una protezione dall'errore, non dal malintenzionato: con un cast si arriva comunque alla lista.
