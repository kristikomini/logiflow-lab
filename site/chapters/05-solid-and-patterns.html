SOLID and design patterns

The previous chapter gave you the tools: classes, interfaces, inheritance. This one is about when to reach for them. SOLID is five pieces of advice about where to put a seam; a design pattern is a solution somebody else already debugged, with a name attached so you can say it in one word.

Why this chapter exists

This is not in the advert you are reading. It is here because Italian .NET adverts name "principi SOLID" and "design pattern" constantly, and because it is the easiest thing in the world for an interviewer to ask: "mi spiega SOLID?" Every candidate has memorised the five words. Very few can point at code they wrote and say which principle it obeys. That gap is the whole opportunity.

What a principle is actually for

🧒 Simple

Imagine a Lego castle glued together. It looks great. Now your friend wants a drawbridge instead of a door. With glue, you have to smash part of the castle and hope the rest survives. With studs — the little bumps Lego bricks click onto — you pull the door off and click the drawbridge on.

SOLID is five bits of advice about where to put the studs. Not everywhere: a castle made of nothing but studs falls over. Just at the places somebody will want to change.

🎓 Professional

SOLID is a set of heuristics for managing coupling and cohesion. Code that is highly cohesive (one module, one reason to exist) and loosely coupled (modules meet at interfaces, not at concrete types) is cheaper to change, because the blast radius of a change stays small.

The key word is heuristics. They are not laws, they have costs, and applied religiously they produce the thing they were meant to prevent: a codebase where a one-line behaviour change means touching eight files. The honest senior answer to "do you follow SOLID?" is "where the change is likely — yes; speculatively, no."

The five, one at a time

S — Single Responsibility

🧒 Simple

A pencil should not also be a stapler. If someone complains about the stapling, you should not have to touch the drawing.

🎓 Professional

The usual phrasing — "a class should do one thing" — is uselessly vague. Uncle Bob's later and better version: a module should have one reason to change, meaning one group of people who request changes to it.

An Invoice class that calculates totals and renders a PDF has two audiences: finance and design. Finance changing the VAT rules should not risk breaking the layout. Two reasons to change, two modules.

O — Open/Closed

🧒 Simple

A power socket lets you add a new lamp without rewiring the house. You extend what the house can do without opening the walls.

🎓 Professional

Open for extension, closed for modification: you should be able to add behaviour by adding a type, not by editing a switch that every other feature also depends on.

The smell is a growing if/else if chain over a type or an enum, repeated in several places. The fix is usually Strategy. But note the qualifier: OCP is worth paying for on the axis that actually varies. A shipping-cost calculator gains new countries forever, so make that extensible. It will never gain a new currency arithmetic, so do not abstract that.

L — Liskov Substitution

🧒 Simple

If the sign says "this is a bird", and you take it home and it sinks in the bath and bites the cat, the sign lied. Anything labelled a bird has to behave like one.

🎓 Professional

A subtype must be usable anywhere its base type is, without the caller knowing. Concretely, a derived class must not strengthen preconditions (demand more) or weaken postconditions (promise less).

The classic violation is Square : Rectangle: setting Width on a Rectangle leaves Height alone, but a Square must change both, so code written against Rectangle breaks. The everyday violation is a method that throws NotSupportedException — a subtype announcing that it is not, in fact, one of these.

I — Interface Segregation

🧒 Simple

A TV remote with 60 buttons when you only ever use four. Give people the small remote.

🎓 Professional

No client should be forced to depend on methods it does not use. A fat IRepository with twenty methods means every implementation, every test double and every mock has to deal with all twenty.

In this repository, look at IRepositories.cs: the read side and write side are separate, and each repository interface carries only what its aggregate needs. That is ISP, and it is also what makes the handler tests short.

D — Dependency Inversion

🧒 Simple

You do not build your kitchen around one particular kettle. You put a socket in the wall. Any kettle that fits the socket works. The kitchen doesn't know about kettles; the kettle knows about sockets.

🎓 Professional

Two halves, and people usually quote only the first:

  • High-level modules should not depend on low-level modules; both depend on abstractions.
  • Abstractions should not depend on details; details depend on abstractions.

The second half is the one that decides where the interface lives. If IOrderRepository sits in the Infrastructure project next to its SQL implementation, you have not inverted anything — Application still points at Infrastructure. Put the interface in Application, the implementation in Infrastructure, and the arrow flips. That single move is what clean architecture is built on.

Strategy, the one that pays for itself

before: the growing if-chain
public decimal Discount(Order order, CustomerTier tier)
{
    if (tier == CustomerTier.Bronze) return 0m;
    if (tier == CustomerTier.Silver) return order.Total * 0.02m;
    if (tier == CustomerTier.Gold)   return order.Total * 0.05m;
    // ...and the same chain appears in the invoice, the quote,
    // and the export. Adding "Platinum" means finding all four.
    throw new ArgumentOutOfRangeException(nameof(tier));
}
after: one type per rule, resolved by DI
public interface IDiscountPolicy
{
    CustomerTier Tier { get; }
    decimal DiscountFor(Order order);
}

public sealed class GoldDiscount : IDiscountPolicy
{
    public CustomerTier Tier => CustomerTier.Gold;
    public decimal DiscountFor(Order order) => order.Total * 0.05m;
}

// Registration: every policy in the assembly, found once.
services.Scan(s => s.FromAssemblyOf<IDiscountPolicy>()
    .AddClasses(c => c.AssignableTo<IDiscountPolicy>())
    .AsImplementedInterfaces()
    .WithSingletonLifetime());

// Use: the chain is gone, and so is the throw.
public sealed class DiscountCalculator(IEnumerable<IDiscountPolicy> policies)
{
    private readonly Dictionary<CustomerTier, IDiscountPolicy> _byTier =
        policies.ToDictionary(p => p.Tier);

    public decimal For(Order order, CustomerTier tier) =>
        _byTier.TryGetValue(tier, out var p) ? p.DiscountFor(order) : 0m;
}

Adding Platinum is now one new file and zero edits — that is Open/Closed, concretely. Note also what it did to testability: GoldDiscount is a class with no dependencies, so its test is three lines.

Decorator, the one this repository leans on

A decorator implements the same interface as the thing it wraps, does something, and delegates. Because the shape is identical, you can stack them, and nothing downstream notices. This repository's Behaviors/ folder is four decorators around every single request:

⚠ The mistake candidates make

An interface for every class. IOrderMapper, IEmailFormatter, IPriceRounder — each with exactly one implementation, forever. This is cargo-cult DIP. An interface earns its keep when there is a second implementation, a test double you actually need, or a boundary you want the compiler to police. Otherwise it is a file you have to open twice to read one method.

A good interviewer will push on this deliberately. "Would you put an interface on this?" is often a test of whether you can say no with a reason.

⚠ The other one

Repository wrapped around DbContext, badly. DbSet<T> is already a repository and DbContext is already a Unit of Work, so a GenericRepository<T> that just forwards calls adds a layer and removes capability — you lose Include, projections, split queries and everything else in chapter 12.

A repository is worth having when it is aggregate-shaped: methods that speak the domain's language (GetWithLinesAsync, NextOrderNumberAsync), not a generic IQueryable<T> Query() that leaks EF Core back out again.

The patterns deliberately not here

  • Singleton (the static-instance kind) — the DI container already gives you one instance with a controlled lifetime and a way to substitute it in tests. A static Instance property gives you a global variable you cannot mock. See the captive-dependency trap in chapter 14.
  • Service Locator — injecting IServiceProvider and resolving inside a method. It hides dependencies from the constructor, so nothing tells you what a class needs until it throws at runtime. Widely considered an anti-pattern.
  • Abstract Factory, Visitor, Flyweight — real patterns, rare in line-of-business .NET. Recognise them; do not go looking for places to use them.

Golden rules

  1. SOLID is five heuristics about where to put a seam, not five laws.
  2. SRP: one reason to change means one group of people asking for changes.
  3. OCP earns its cost only on the axis that genuinely varies. Guess wrong and it is pure overhead.
  4. LSP: a subtype that throws NotSupportedException is announcing it is not a subtype.
  5. ISP: narrow interfaces make short tests. Wide ones make mock setup.
  6. DIP is decided by which project the interface file lives in, not by using an interface.
  7. An interface with one implementation and no test double is a file, not an abstraction.
  8. A pattern is a name for a solution. Naming it is the benefit; forcing it is the cost.
  9. Decorators stack because they share a shape. Order them deliberately.
  10. Prefer the DI container to Singleton, and constructor injection to Service Locator.
  11. A repository should speak the domain's language, not expose IQueryable.
  12. If you cannot name the change a pattern is protecting you from, you do not need it yet.

Interview questions

"Mi spiega i principi SOLID?"

Name the five, but spend your time on one. Everybody recites the list; the answer that lands is "…and the one I actually use daily is Dependency Inversion — for example, in my project the repository interfaces live in the Application layer and the EF Core implementations in Infrastructure, so the business rules compile without a database and the unit tests need no container."

"Which design patterns have you used?"

Pick two you can describe from code, not from a diagram. Decorator is a strong choice because the example is vivid: "logging, validation, caching and transactions are four wrappers around the handler, so the handler has business logic and nothing else." Then say what it cost — stack traces get deeper, and the execution order is a real design decision.

"Is the Repository pattern an anti-pattern over EF Core?"

This is a trap and a good one. The right answer is "it depends what it wraps". A generic Repository<T> forwarding to DbSet<T> adds indirection and removes capability, because DbContext is already Unit of Work + Repository. An aggregate-shaped repository with domain-named methods is useful: it keeps query construction out of handlers and gives you a seam for tests. Say which one you have written.

"Give me an example of code that violates the Single Responsibility Principle."

Use something concrete and slightly embarrassing rather than a textbook example: a controller that validated input, called the database, formatted currency for the UI and sent a confirmation email. Four audiences, four reasons to change. Then say what you did about it, and — better — what you deliberately left alone because it was not changing.

"When would you not introduce an interface?"

When there is one implementation, no test needs to replace it, and it does not sit on a layer boundary. Add that speculative abstraction has a real cost: navigation, indirection, and the illusion of flexibility along an axis nobody will ever use. YAGNI is a SOLID principle in practice even though it is not in the acronym.
