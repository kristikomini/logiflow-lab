Inheritance, polymorphism and interfaces, with use cases

Chapter 03 defines the four pillars and gives you the sentence an interviewer wants. This chapter is the part that decides whether your code is any good: what each one looks like in a real feature, when an abstract class beats an interface, why virtual and new are not variants of the same idea, and the specific ways an inheritance hierarchy goes wrong three months after somebody drew it.

Why this chapter exists

Inheritance is the feature most often used for the wrong reason. It is taught with animals and shapes, where it always works, and then applied to CustomerOrder : Order, where it produces a base class that grows a flag for every subclass and a hierarchy nobody can change. Meanwhile interfaces — the thing that actually makes code testable and replaceable — get treated as ceremony. Getting this round the right way is the difference between a codebase that absorbs a new requirement and one that resists it.

Polymorphism, in the one sentence that matters

🧒 Simple

You have a list of shipments. Some go by courier, some by pallet, some by post. You want to print a label for each. Instead of asking each one what it is and choosing, you tell each one to print its own label, and it knows how. That is the whole idea: one instruction, different behaviour, chosen by the thing itself. 

// without polymorphism: every new kind means editing this method
decimal Cost(Shipment s)
{
    if (s.Kind == "courier") return 12m + s.Weight * 0.8m;
    if (s.Kind == "pallet")  return 60m;
    if (s.Kind == "post")    return 4m;
    throw new NotSupportedException(s.Kind);          // and the one somebody forgot
}

// with polymorphism: every new kind is a new file, and nothing existing changes
public abstract class Shipment
{
    public decimal Weight { get; init; }
    public abstract decimal Cost { get; }             // no body: subclasses MUST supply one
}

public sealed class CourierShipment : Shipment
{
    public override decimal Cost => 12m + Weight * 0.8m;
}
public sealed class PalletShipment : Shipment
{
    public override decimal Cost => 60m;
}

decimal total = shipments.Sum(s => s.Cost);           // does not know or care which is which
Line by line
  • The call is resolved at run time from the actual object, not at compile time from the declared variable. That single fact is polymorphism; everything else is syntax.
  • abstract on the member means no body and every subclass must supply one. Add a new kind of shipment and the compiler tells you what is missing — unlike the if chain, which tells you at run time, in production, via NotSupportedException.
  • This is the open/closed principle with the abstraction actually filled in. A new shipment type is a new file; nothing already tested is edited. That is the payoff, and it is the only reason to accept the extra indirection.
  • sealed on the leaves, deliberately: they are not designed to be derived from further, and saying so lets the runtime devirtualise the call as well as telling a reader the hierarchy stops here.
  • Note what the if version costs even before it breaks: Kind as a string, one method that must know about every type forever, and a NotSupportedException that exists only because the design cannot be checked.

virtual, override, new, sealed — and the one that lies

public class Courier
{
    public virtual decimal Quote(decimal kg) => 12m + kg * 0.8m;   // may be replaced
    public decimal Book(decimal kg) => Quote(kg) * 1.22m;          // calls the REPLACEMENT
}

public class ExpressCourier : Courier
{
    public override decimal Quote(decimal kg) => base.Quote(kg) * 1.5m;   // extends it
}

public class WeirdCourier : Courier
{
    public new decimal Quote(decimal kg) => 5m;    // HIDES it — a different method entirely
}

Courier c1 = new ExpressCourier();
Courier c2 = new WeirdCourier();
c1.Quote(10);        // 30  — the override runs. The object decided.
c2.Quote(10);        // 20  — the BASE runs. The variable decided.
((WeirdCourier)c2).Quote(10);   // 5 — same object, different answer
Line by line
  • override replaces; new hides. An override is chosen by the object's real type, so it wins wherever the object goes. A new member is chosen by the declared type of the variable, so the same object behaves differently depending on what you are holding it in — which is essentially never what anybody wants.
  • new exists for one honest reason: a base class you do not own adds a member whose name collides with yours, and new lets you keep compiling. Treat every other use as a mistake. Without the keyword the compiler warns, and that warning is the one never to suppress.
  • base.Quote(kg) — extending rather than replacing. When an override ignores base entirely, ask whether inheritance was the right tool at all.
  • Book is not virtual and calls a virtual method, so the base class decides the algorithm and subclasses supply one step. That is the template method pattern, and it is inheritance used well.
  • sealed on a class stops derivation; sealed override on a member stops further overriding while keeping the one you wrote. Both are worth applying by default — you can always unseal later, and you can never take back a hierarchy people have built on.
⚠️ The overload/override confusion, which is one sentence

Overloads are chosen at compile time from the declared type; overrides at run time from the actual type. That sentence explains why new behaves as it does above, why passing a string held in an object variable picks the object overload, and why adding an overload to a base class can silently change which method an existing call site resolves to. Chapter 02e has it from the overload side.

TypicalShipment, ControllerIOrderRepository, IDisposable
 
// an INTERFACE: the seam. Everything the application needs, nothing about how.
public interface IOrderRepository
{
    Task<Order?> FindAsync(int id, CancellationToken ct);
    Task SaveAsync(Order order, CancellationToken ct);
}

// two implementations, and neither knows the other exists
public sealed class SqlOrderRepository : IOrderRepository { /* EF Core */ }
public sealed class InMemoryOrderRepository : IOrderRepository { /* a test */ }

// an ABSTRACT CLASS: shared state and a shared algorithm, one varying step
public abstract class ImportJob
{
    protected ILogger Log { get; }
    protected ImportJob(ILogger log) => Log = log;

    public async Task RunAsync(string path, CancellationToken ct)   // the algorithm — fixed
    {
        Log.LogInformation("Importing {Path}", path);
        int n = 0;
        await foreach (var line in File.ReadLinesAsync(path, ct))
            if (await HandleLineAsync(line, ct)) n++;               // the step — varies
        Log.LogInformation("Imported {Count} rows", n);
    }

    protected abstract Task<bool> HandleLineAsync(string line, CancellationToken ct);
}
Line by line
  • The interface is what makes the application testable. The service depends on IOrderRepository, so a test supplies the in-memory one and never touches a database. That is the dependency-inversion half of SOLID, and it is the single most practical reason interfaces exist.
  • The abstract class earns its place when there is real shared behaviour — here, the logging, the loop and the counting, written once. An interface could not hold any of that without repeating it in every implementation.
  • A class may implement many interfaces and derive from one class. That is usually the deciding constraint: if a type needs to be two things, at most one of them can be a base class.
  • Adding a member to a published interface is a breaking change for everyone who implements it. Default interface methods exist to soften this and are a versioning tool, not a way to put logic in interfaces.
  • The honest default in application code is an interface plus one implementation, and no inheritance at all. Reach for an abstract class only when you catch yourself copying the same method into two classes that are genuinely the same kind of thing.

Abstraction, which is not the same as an abstract class

🧒 Simple

Abstraction is deciding what to leave out. A light switch offers "on" and "off" and hides the wiring — not because the wiring is secret, but because knowing about it would not help you and would stop the electrician ever changing it. 

// ✗ an abstraction that leaks its implementation into its own signature
public interface IOrderRepository
{
    SqlDataReader RunQuery(string sql);         // the caller now depends on SQL Server
    DbContext Context { get; }                  // and on EF Core, and on the schema
}

// ✓ an abstraction that could be re-implemented over a file, an API or a test double
public interface IOrderRepository
{
    Task<Order?> FindAsync(int id, CancellationToken ct);
    Task<IReadOnlyList<Order>> FindPendingAsync(DateOnly before, CancellationToken ct);
}
Line by line
  • The test of an abstraction is whether it could be implemented a second, completely different way. If the answer is no, it is not hiding anything — it is paperwork over one implementation.
  • IQueryable on a repository interface is the subtle version of the same leak: it looks abstract, and it silently requires every implementation to have a LINQ provider and lets callers build queries the repository never anticipated.
  • An abstraction is defined by what its caller needs, not by what the implementation happens to have. FindPendingAsync is a question the business asks; RunQuery is a technique.
  • Fewer, more meaningful methods beat many small technical ones. An interface with sixteen members is usually two interfaces, which is the interface-segregation principle in chapter 05.
  • abstract class is a keyword; abstraction is a design activity. You can write a perfectly abstract interface and a completely leaky abstract class.

The four ways a hierarchy goes wrong

  1. Inheriting to reuse code. class OrderService : DatabaseHelper because the helper has a method you want. Now every order service is a database helper, its public surface includes methods nobody meant to expose, and the two are permanently welded. Inheritance means "is a", not "uses". Make the helper a dependency and inject it.
  2. The base class that grows a flag per subclass. if (this is PalletShipment) inside the base is the hierarchy telling you it is upside-down: the base now knows about its children, so adding one means editing it and nothing is closed for modification.
  3. Breaking the substitution principle. The classic is Square : Rectangle, where setting the width has to change the height and any code holding a Rectangle now behaves unexpectedly. In business code it looks like an override that throws NotSupportedException: the subclass cannot do what the base promised, so it was never really that kind of thing.
  4. Depth. Three levels and a behaviour's real definition is somewhere across four files, with base calls that may or may not be made. Debugging becomes archaeology. Two levels is plenty; if you need more, the varying part probably wants to be a separate injected object rather than a subclass.
// the smell, and the cure
public class PriceCalculator { public virtual decimal Apply(decimal x) => x; }
public class NoDiscount : PriceCalculator { public override decimal Apply(decimal x) => x; }
public class TenPercent  : PriceCalculator { public override decimal Apply(decimal x) => x * 0.9m; }

// ✓ the same thing, composed rather than inherited: an injected strategy
public interface IDiscount { decimal Apply(decimal amount); }

public sealed class PercentageDiscount(decimal pct) : IDiscount
{
    public decimal Apply(decimal amount) => amount * (1 - pct / 100m);
}

public sealed class Checkout(IDiscount discount)          // composition: HAS a discount
{
    public decimal Total(Order o) => discount.Apply(o.Total);
}
Line by line
  • Composition is a field; inheritance is a type. A field can be swapped at run time, chosen by configuration, decorated, and replaced in a test. A base class is fixed at compile time and forever.
  • The composed version also combines: a CompositeDiscount holding several IDiscounts needs no new language feature. Two subclasses cannot be combined at all.
  • Every override that throws is a design error being reported at run time. It means the subclass is not really substitutable for its base, so the hierarchy is claiming a relationship that does not hold.
  • The one test worth applying: can a caller holding the base type be given any subclass without needing to know which? If not, it is not a subtype.
  • None of this makes inheritance bad. It makes it specific: use it when several things genuinely are the same kind of thing and share real behaviour, as Shipment does.

How the runtime finds the right method

Worth knowing once, because it explains three separate behaviours you would otherwise have to memorise individually.

  • A class with any virtual member has a method table. A call to a virtual member looks the method up in the table of the object's real type, which is why the override wins wherever the object goes.
  • A non-virtual call is resolved at compile time and written directly into the IL — which is exactly why new follows the variable rather than the object.
  • is and as ask the object about its real type, so if (s is PalletShipment p) works on anything, including something in a variable declared as object.
  • sealed lets the JIT prove no override can exist and turn a virtual call into a direct one. Real, but small — seal for design reasons first.
  • An interface call goes through a separate dispatch table, which is why a type can implement many interfaces but derive from only one class: one method table, many interface maps.

Exercises, with the reasoning shown

Exercise 1 — the method that depended on the variable

class A { public void Go() => Console.WriteLine("A"); }
class B : A { public new void Go() => Console.WriteLine("B"); }

A x = new B();
x.Go();
((B)x).Go();
A then B — the same object, two answers.
  • Go is not virtual, so the call is resolved at compile time from the declared type of the variable. new did not replace anything; it declared a second, unrelated method that happens to share a name. Making the base virtual and the derived override gives B both times, which is what anybody reading this expected.

Exercise 2 — the subclass that could not keep the promise

public class Order { public virtual void AddLine(OrderLine l) => _lines.Add(l); }
public class DispatchedOrder : Order
{
    public override void AddLine(OrderLine l) => throw new NotSupportedException();
}
Any code holding an Order can now crash by doing the one thing Order promised it could do.
  • That is a substitution-principle violation: DispatchedOrder is not usable everywhere an Order is, so it is not really a subtype. The state is not a kind of order, it is a phase of one — so model it as status on the order with AddLine checking it, exactly as chapter 03b does.

Exercise 3 — the base class that knew its children

public abstract class Shipment
{
    public decimal Cost()
    {
        if (this is PalletShipment) return 60m;
        if (this is PostShipment)   return 4m;
        return 12m + Weight * 0.8m;
    }
}
The hierarchy is inside out.
  • The base knows every subclass, so adding a fourth means editing the base and re-testing all three, and nothing tells you if you forget — you simply get the courier price. Making Cost abstract moves each answer to the class it belongs to and turns the omission into a compile error. The if (this is …) shape inside a base class is always worth stopping on.

Exercise 4 — the inheritance that was really a dependency

public class OrderService : SqlHelper
{
    public Order Get(int id) => QuerySingle<Order>("SELECT ...", id);   // inherited
}
Every order service is now a SQL helper, publicly.
  • Callers can reach QuerySingle and run arbitrary SQL through your service; the service cannot be tested without a database; and it can never derive from anything else, because C# allows one base class. The relationship is "uses", not "is a". Inject an ISqlHelper as a constructor dependency and all four problems disappear at once — which is what "favour composition over inheritance" actually buys you.
Try it yourself

Both shapes in one file: an abstract class where there is real shared behaviour, and an interface where there is a seam. Run it, then add a third shipment type and notice that you edit nothing. 

public abstract class Shipment
  {
      public required string Reference { get; init; }
      public decimal WeightKg { get; init; }

      public abstract decimal Cost { get; }                 // every kind MUST answer
      public virtual string Label => $"{Reference} — {Cost:C}";   // may be replaced
  }

  public sealed class CourierShipment : Shipment
  {
      public override decimal Cost => 12m + WeightKg * 0.8m;
  }

  public sealed class PalletShipment : Shipment
  {
      public override decimal Cost => 60m;
      public override string Label => $"PALLET {Reference} — {Cost:C}";   // extends
  }

  // the seam: the application depends on this, not on a courier's API
  public interface IQuoteSource { decimal Quote(Shipment s); }

  public sealed class LocalRates : IQuoteSource
  {
      public decimal Quote(Shipment s) => s.Cost;           // the cheap implementation
  }

  public sealed class Checkout(IQuoteSource quotes)          // composition, injected
  {
      public decimal Total(IEnumerable<Shipment> all) => all.Sum(quotes.Quote);
  }

  Shipment[] load =
  [
      new CourierShipment { Reference = "MI-42", WeightKg = 18.4m },
      new PalletShipment  { Reference = "BO-7",  WeightKg = 400m  },
  ];

  foreach (var s in load) Console.WriteLine(s.Label);        // polymorphism
  Console.WriteLine(new Checkout(new LocalRates()).Total(load));
Line by line
  • abstract decimal Cost — no body, so every kind of shipment must answer, and the compiler names the one you forgot.
  • virtual string Label — a default that may be replaced. PalletShipment replaces it and CourierShipment does not, which is the difference between abstract and virtual in two lines.
  • sealed on both leaves: the hierarchy stops here, deliberately, and saying so lets the runtime turn the virtual calls into direct ones.
  • IQuoteSource is the seam — Checkout depends on the interface, so a test can hand it a fixed-price implementation and change nothing else.
  • Checkout(IQuoteSource quotes) is composition, not inheritance: Checkout has a quote source rather than being one, which is what makes it swappable.
  • all.Sum(quotes.Quote) — a method group passed where a function is expected, and the loop never asks what kind of shipment it is holding.

Two exercises with it. First add PostShipment: one new file, and the compiler tells you the one member you must write. Then write a second IQuoteSource that returns a fixed price — that is a test double, and the fact that Checkout needed no change at all is the entire argument for the interface.

Golden rules

  1. Inheritance means "is a", never "uses". If you are deriving to get at a method, you wanted a constructor dependency.
  2. Interfaces are for capabilities and seams; abstract classes are for genuinely shared behaviour. A type can implement many interfaces and derive from one class, and that constraint usually decides it.
  3. override replaces, new hides. A hidden member follows the variable rather than the object, so the same instance answers differently — never suppress the compiler warning that tells you so.
  4. Overloads are chosen at compile time from the declared type; overrides at run time from the actual type. One sentence, three behaviours explained.
  5. An override that throws NotSupportedException is a design error. The subclass cannot keep the base's promise, so it is not a subtype.
  6. if (this is SomeSubclass) inside a base class means the hierarchy is upside down. Make the member abstract and let each subclass answer.
  7. Seal by default. You can unseal later; you cannot take back a hierarchy people have already built on.
  8. Two levels of inheritance is plenty. Past that, a behaviour's real definition is spread across four files and debugging becomes archaeology.
  9. An abstraction is only an abstraction if it could be implemented a second, different way. SqlDataReader or DbContext in an interface is a leak wearing a contract.
  10. Define an interface by what the caller needs, not by what the implementation happens to have. Sixteen members is usually two interfaces.
  11. Adding a member to a published interface breaks every implementer. Default implementations are a versioning tool, not a place for logic.
  12. Composition can be swapped, combined, configured and tested; inheritance is fixed at compile time. That is the whole of "favour composition over inheritance".

Interview questions

"What is the difference between an abstract class and an interface?"

Mechanically: a class can implement many interfaces but derive from only one base class, and an abstract class can hold state, fields and constructors while an interface cannot. In terms of intent, an abstract class says "this is a kind of that" and exists to share real behaviour — a template method where the algorithm is fixed and one step varies. An interface says "this can do that" and exists as a contract and a seam, which is what makes code testable. My default in application code is an interface, because I want the dependency inversion; I only introduce an abstract base when I catch myself copying the same implemented method into two classes that genuinely are the same kind of thing. One practical difference worth mentioning is versioning: adding a member to an abstract class is free, and adding one to a published interface breaks every implementer.

"virtual, override and new — what is the difference?"

virtual marks a member as replaceable; override replaces it, and the replacement is chosen at run time from the object's actual type, so it wins wherever that object goes. new does not replace anything — it declares a separate member that hides the base one, and which of the two you get depends on the declared type of the variable you are holding. So the same instance can give two different answers depending on the variable, which is essentially never intended. The one legitimate use is when a base class you do not control adds a member that collides with yours. Without the keyword the compiler warns, and that is a warning I would never suppress.

"Give me an example of when inheritance is the wrong choice."

Anywhere the relationship is "uses" rather than "is a" — the classic being a service deriving from a data-access helper to get at its methods. That welds the two together permanently, exposes the helper's members on the service's public surface, makes the service untestable without a database, and burns the one base class the type will ever have. The other one I watch for is a subclass representing a phase rather than a kind: DispatchedOrder : Order ends up overriding methods to throw, which breaks substitutability. Both are solved by composition — inject the helper, model the phase as status with the rules inside the methods.

"What does the Liskov substitution principle mean in practice?"

That any code holding a base type can be handed any subclass and keep working, without knowing which it got. In practice I look for three symptoms. An override that throws NotSupportedException, which says the subclass cannot keep the base's promise. An override that strengthens a precondition or weakens a guarantee — rejecting input the base accepted, or returning null where the base never did. And callers that test is against subclasses before deciding what to do, which means substitution is already not working. When I hit one of these, the answer is usually that the hierarchy is modelling something that is not really a subtype, and composition or a status field expresses it honestly.

"Perché si dice di preferire la composizione all'ereditarietà?"

Perché la composizione è un campo e l'ereditarietà è un tipo. Un campo lo posso sostituire a runtime, sceglierlo da configurazione, decorarlo, combinarne più di uno e rimpiazzarlo nei test; una classe base è decisa a compile time ed è per sempre, e me ne posso permettere una sola. L'ereditarietà inoltre accoppia molto più di quanto sembri: i membri protected diventano superficie pubblica verso ogni sottoclasse futura, e una modifica alla base può rompere codice che non ho scritto io. Non vuol dire che l'ereditarietà sia sbagliata — quando più cose sono davvero lo stesso tipo di cosa e condividono comportamento reale, come le spedizioni, è la scelta giusta. Vuol dire che è specifica, non predefinita.
