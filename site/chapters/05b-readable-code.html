Code other people can read

SOLID is about where to put the seams between classes. This chapter is one level down: names, methods, comments, errors and state — the decisions you make forty times an hour, which nobody interviews you on and everybody judges you by in the first code review.

Why this chapter exists

An advert asks for "buona conoscenza del linguaggio C#" and a team asks for something else entirely: code they can change on a Tuesday without reading it all again. Those are not the same skill and only the first one is taught. The gap shows up immediately — the first pull request of your first job is where a team decides how much supervision you need, and it is decided on the things in this chapter, not on whether you know what a ValueTask is.

The good news is that it is the cheapest ground to gain in this whole course. Nothing here is hard to understand. All of it is hard to do consistently, which is why doing it consistently is worth so much.

What a principle is worth, and what it is not

🧒 Simple

Think about how a kitchen is arranged. Nobody wrote a law saying the knives go near the chopping board — but they do, everywhere, because that is where your hand goes when you need one. A stranger can cook in your kitchen.

Code principles are that. Not laws. Just the arrangement that means a stranger — including you, in six months — can find things where their hand already went.

🎓 Professional

Code is read far more often than it is written, and almost all of the reading is done under pressure: something is broken, or something must change by Friday. Every practice in this chapter buys the same thing, the time between opening a file and understanding it, and pays for it in keystrokes now.

That is also the test for whether a principle applies. "Is this DRY?" is the wrong question. "Will the next person understand this faster, or slower?" is the right one, and it has a different answer in different places — which is why these are all heuristics and why a codebase that applies them religiously is as unpleasant to work in as one that ignores them.

Names: the cheapest thing you will ever get right

🧒 Simple

Imagine a kitchen where every jar is labelled jar1, jar2, tmp. All the food is there. All of it is correct. Making dinner now takes an hour and involves opening everything.

🎓 Professional

A name is the only documentation that is read every single time. It is also the only one the compiler forces you to keep in one place, which makes it the only documentation that cannot go stale.

The rule that produces good names is not "long names" — it is the name answers the question the reader is about to ask. At the call site, the reader asks what does this do to what. Inside a two-line loop, they already know, so x is fine there and nowhere else. Name length should be roughly proportional to the distance between where a thing is declared and where it is used. 

// Before
public List<Order> Get(int d, bool f)
{
    var list = _db.Orders.Where(o => o.Date > DateTime.Now.AddDays(-d));
    if (f) list = list.Where(o => o.Status == 3);
    return list.ToList();
}

// After
public List<Order> GetRecentOrders(int withinDays, bool unshippedOnly)
{
    var cutoff = _clock.UtcNow.AddDays(-withinDays);
    var orders = _db.Orders.Where(o => o.PlacedAtUtc > cutoff);

    if (unshippedOnly)
        orders = orders.Where(o => o.Status == OrderStatus.AwaitingShipment);

    return orders.ToList();
}
Line by line
  • Get(int d, bool f) — the method name says nothing the type did not already say, and d and f are unreadable at the call site: Get(30, true) tells the reader nothing at all.
  • GetRecentOrders(int withinDays, bool unshippedOnly) — now GetRecentOrders(30, unshippedOnly: true) reads as a sentence. The parameter names did the work; nothing else changed.
  • bool f — a boolean parameter is a design smell whatever it is called, because at the call site it is a bare true. Two smaller methods are often better than one with a flag. Named arguments are the cheap fix when they are not.
  • o.Status == 3 — a magic number. Three what? The enum version cannot be misremembered, cannot drift from the database, and is the one line in this method a reviewer would have stopped at.
  • DateTime.Now inside the query — two problems in six characters: it is machine-local time rather than UTC, and it makes the method untestable, because a test cannot decide what "now" is. _clock.UtcNow is the same value from an injected dependency you can control.
  • var cutoff = … — pulling the expression out and naming it is the smallest refactoring there is and often the highest-yield. A named intermediate is a comment the compiler checks.
The conventions C# actually has

These are not opinions — the .NET ecosystem agrees on them, and breaking them reads as inexperience even when the code is right.

  • PascalCase for types, methods, properties, constants and public anything.
  • camelCase for locals and parameters; _camelCase for private fields.
  • I prefix for interfaces (IOrderRepository) — a C# habit, unusual elsewhere, and universal here.
  • Async methods end in Async. See chapter 07.
  • Booleans read as an assertion: IsActive, HasLines, CanShip — never Flag or Status for a two-state fact.
  • No Hungarian notation, no m_, no type in the name. strName and listOrders date the code more precisely than a comment could.

Methods that fit in your head

🧒 Simple

A recipe that says "make dinner" is useless. A recipe with two hundred steps is also useless. A good one has a handful of steps, each of which you could look up separately if you needed to.

🎓 Professional

"Methods should be short" is the advice everyone repeats and it is not quite the rule. The rule is one level of abstraction per method: a method either orchestrates named steps or performs one step, never both. A method that opens a database connection and formats a currency string is asking the reader to change altitude mid-sentence.

Shortness is a consequence of that, not the goal. The number worth watching is cyclomatic complexity — how many independent paths run through the method — because that is what decides how many tests it needs and how many ways it can be wrong. 

// Arrow code: the real logic is indented five levels deep
public Result Ship(Order order)
{
    if (order != null)
    {
        if (order.Lines.Count > 0)
        {
            if (order.Status == OrderStatus.Paid)
            {
                if (_stock.IsAvailable(order))
                {
                    _carrier.Book(order);
                    return Result.Ok();
                }
                else return Result.Fail("no stock");
            }
            else return Result.Fail("not paid");
        }
        else return Result.Fail("empty");
    }
    else return Result.Fail("null");
}

// Guard clauses: every refusal is stated once, at the top, and left behind
public Result Ship(Order order)
{
    ArgumentNullException.ThrowIfNull(order);

    if (order.Lines.Count == 0)                  return Result.Fail("Order has no lines.");
    if (order.Status != OrderStatus.Paid)         return Result.Fail("Order is not paid.");
    if (!_stock.IsAvailable(order))               return Result.Fail("Stock is not available.");

    _carrier.Book(order);
    return Result.Ok();
}
Line by line
  • The shape is the point. Both versions do the same thing and pass the same tests. The second one can be read top to bottom without holding an else in your head, because nothing is nested.
  • ArgumentNullException.ThrowIfNull(order) — a guard clause: it deals with a case that must not happen and returns the reader's attention to the main path. Note the difference from the ones below it — a null argument is a programming error, so it throws; an unpaid order is a business outcome, so it returns a result. Mixing those two up is a mistake with its own section.
  • return Result.Fail("Order has no lines.") — every refusal happens at the same indentation, which means the reader can scan the guards as a list of preconditions. That list is also, exactly, the test cases.
  • The happy path is the last two lines, unindented. In the first version it was the most deeply buried thing in the method, which is backwards: the common case should be the easiest to find.
  • Multiple returns are fine. The single-exit rule comes from C, where you had to free memory by hand. In C# it produces exactly the arrow code above.

Comments: the ones worth writing

🧒 Simple

If you stick a note on a door saying "this is a door", you have not helped anybody. If you stick one saying "pull hard, the hinge is dropped", you have saved everyone who comes after you ten seconds and one swear word.

🎓 Professional

A comment cannot be compiled, tested or refactored, so every comment is a promise you might break. That makes the calculation simple: write the comment only when it says something the code cannot say.

Code says what. Comments say why — why this weird order, why this magic constant, why the obvious approach was rejected. A comment that says why is the most valuable line in a file; a comment that says what is a line that will one day be a lie. 

// Worthless: says what the next line already says, and will be wrong
// after the first edit.
// increment the counter
counter++;

// Worthless and dangerous: a comment nobody updated.
// Retries three times.
for (var i = 0; i < 5; i++) { … }

// Worth its space: it records a decision, and a reason you cannot infer.
// Ordered by PlacedAtUtc DESC, not by Id: the ids come from a Hi/Lo
// generator, so they are not monotonic across application instances.
// Sorting by Id here put yesterday's orders on top of today's twice.
return orders.OrderByDescending(o => o.PlacedAtUtc).ToList();
Line by line
  • // increment the counter — the classic. It adds a line to read and no information. If counter++ is unclear, the fix is a better name for counter, not a sentence about it.
  • // Retries three times. above a loop to five — this is the real cost of comments that describe code. Somebody changed the number and not the sentence, and now the file contains a confident falsehood that a reader will believe over the code.
  • The third comment cannot be derived from anything. It names the bug that was caused, the alternative that was rejected and why. Delete the code and you can rewrite it; delete that comment and the next person repeats the outage.
  • Commented-out code is not a comment. It is deleted code that nobody had the nerve to delete. Git already remembers it and can tell you who removed it and when, which the commented-out block cannot.
  • /// <summary> XML docs are a different tool with a different job: they are for a public API somebody consumes without reading the source, where they become IntelliSense. On an internal class they are usually the "what" comment in a smarter hat.

Make the wrong thing impossible

🧒 Simple

A plug will not fit into the wrong socket. Nobody has to remember the rule, nobody has to be careful, and nobody writes a note about it — the shape does the remembering.

🎓 Professional

Most bugs are an object being in a state its author never pictured: an order with no lines, a discount of minus fifty, an address half-populated because the second setter threw. The defence that scales is not more validation calls — it is designing the type so the bad state cannot be constructed.

Two levers do most of the work. Constructors that enforce the invariants, so nothing exists until it is valid, and immutability, so nothing that was valid can quietly stop being so. A class whose properties all have public setters has no invariants; it has hopes. 

// A bag of setters. Every caller can build a broken one, and will.
public class Discount
{
    public decimal Percentage { get; set; }
    public DateTime ExpiresAtUtc { get; set; }
}

// The invariants live in one place and are checked once.
public sealed class Discount
{
    public Discount(decimal percentage, DateTime expiresAtUtc)
    {
        if (percentage <= 0 || percentage > 90)
            throw new ArgumentOutOfRangeException(nameof(percentage),
                "A discount is between 0 and 90 percent.");

        if (expiresAtUtc.Kind != DateTimeKind.Utc)
            throw new ArgumentException("Expiry must be UTC.", nameof(expiresAtUtc));

        Percentage   = percentage;
        ExpiresAtUtc = expiresAtUtc;
    }

    public decimal Percentage { get; }
    public DateTime ExpiresAtUtc { get; }

    public bool IsLiveAt(DateTime utcNow) => utcNow < ExpiresAtUtc;
}
Line by line
  • { get; set; } on both properties — the first class can be constructed empty and filled in later, so every method that receives one has to re-check it. That check will be written in four places and forgotten in a fifth.
  • public Discount(decimal percentage, …) — a constructor that takes what the object needs makes new Discount() impossible. There is now no way to hold a Discount that was never validated.
  • throw new ArgumentOutOfRangeException(nameof(percentage), …) — nameof rather than "percentage", so renaming the parameter renames the message too. The message states the rule, not the failure: the person reading it in a log needs to know what was expected.
  • { get; } with no setter — immutable after construction. A Discount that was valid stays valid for its whole life, so no caller anywhere can invalidate it by assignment. (init and record give you the same guarantee with less typing; see chapter 02.)
  • IsLiveAt(DateTime utcNow) — behaviour on the type that owns the data, rather than an if written out at each of the nine call sites. This is the difference between a domain model and a DTO, and it is what people mean by an anemic model when they say it as a criticism.
  • sealed — the default worth preferring. Inheritance is a contract you have to keep forever; not offering one costs nothing until somebody genuinely needs it.

Failing in a way somebody can act on

🧒 Simple

If the smoke alarm goes off and you take the battery out, the kitchen is still on fire. You have removed the news, not the problem.

🎓 Professional

There are three honest things to do with an exception: handle it (you can genuinely recover), add context and rethrow, or let it go past. Everything else — logging it and continuing, catching and returning null, swallowing it silently — converts a loud failure into a corrupted result that shows up somewhere else, hours later, with none of the information.

The rule of thumb is catch what you can do something about, at the level that can do it. A repository cannot decide what to do about a timeout; the endpoint above it can. 

// Three different ways of destroying the evidence
try { Import(file); }
catch (Exception) { }                              // silent
catch (Exception ex) { return null; }               // the caller now crashes instead
catch (Exception ex) { _log.Error(ex); throw ex; }  // stack trace reset to HERE

// What to write instead
try
{
    Import(file);
}
catch (IOException ex)
{
    // Specific, and genuinely recoverable: the file is locked by the
    // scanner for a second or two after it lands in the drop folder.
    _log.LogWarning(ex, "Import of {File} deferred; file was locked.", file.Name);
    _retryQueue.Enqueue(file);
}
catch (CsvFormatException ex)
{
    // Cannot be recovered here, but the caller has no idea which row.
    throw new ImportFailedException($"Row {ex.Line} of {file.Name} is malformed.", ex);
}
Line by line
  • catch (Exception) { } — the empty catch. It says "I do not care what went wrong", and it is the single most expensive line a beginner writes, because the bug it hides is found by a customer instead of by a log.
  • catch … { return null; } — the failure has not gone away, it has moved. The caller now gets a NullReferenceException in a method that did nothing wrong, with a stack trace pointing at the innocent party.
  • throw ex; — subtle and worth memorising for the interview: throw ex resets the stack trace to this line, throwing away every frame below it. The bare throw; preserves it. If you need to add information, wrap in a new exception with the original as innerException — never re-throw the same object by name.
  • catch (IOException ex) — catch the narrowest type you can act on. This catch exists because there is a real recovery for this exact case, and the comment records the reason the case exists at all.
  • _log.LogWarning(ex, "…{File}…", file.Name) — the message template and the value are passed separately so the log is searchable by field, and the exception goes in the first parameter so its stack trace is kept. String-concatenating it into the message throws the trace away.
  • throw new ImportFailedException($"Row {ex.Line}…", ex) — rethrowing with context the lower layer had and the upper layer needs, with the original attached. This is the pattern worth using by default.

DRY, and the day it is wrong

🎓 Professional

DRY is stated as "don't repeat yourself" and understood as "no two blocks of code may look alike", which is not what it says. The original is about knowledge: every piece of knowledge should have one authoritative representation. Two methods that happen to contain the same four lines, for different reasons, are not a violation of anything.

Merging them is, though. The moment one of the two callers needs the behaviour to differ, a parameter appears; then another; then an if on one of them. That is how a shared helper becomes a function with five flags that nobody can change safely — the coupling you created is now more expensive than the duplication you removed.

The working rule: duplicate until you know why it is the same. Wait for the third occurrence, and look at whether the copies change together. If they always will, extract. If they might diverge, leave them alone and let them.

The question that settles it

"If this rule changes, must both places change?" — yes, extract it; no, it is a coincidence, leave it. VAT rules and shipping rules both being "amount × rate" is a coincidence. Two controllers both mapping the same entity to the same DTO is not.

Simple beats clever, every single time

🧒 Simple

A magic trick is fun to watch once. You do not want the light switch in your house to be a magic trick.

🎓 Professional

Debugging is harder than writing. Write code at the very limit of your cleverness and you are, by definition, not clever enough to debug it — and neither is the colleague who inherits it at 2 a.m. This is the whole of KISS and it is not a style preference; it is a statement about the difficulty of the two activities.

YAGNI is the same argument applied to time. The interface with one implementation, the configuration setting nobody has ever changed, the plugin system for the second customer who has not signed: each one is a real cost paid now for a benefit that is a guess. And the guess is usually wrong in an interesting way — when the second customer does arrive, they need a different axis of flexibility than the one you built.

Premature optimisation is the third face of it. Not "never think about performance" — think about it at the level that matters, which is the query, the algorithm and the round trip, never the micro-syntax. Everything else waits for a measurement.

Leaving it better than you found it

🎓 Professional

Technical debt is a good metaphor because it names the part everyone forgets: the interest. A shortcut is not a one-off cost, it is a small tax on every future change in that area. Some debt is worth taking — shipping in time for a trade fair is a real business reason — and the test of a team is whether it is recorded, not whether it exists.

The boy scout rule — leave the code a little better than you found it — is how debt gets paid without a project to pay it. Not a rewrite: a name, a guard clause, one test. It works because it puts the improvement where somebody is already reading, which is exactly where it is worth most.

The counterweight is keep the diff honest. A pull request that fixes a bug and reformats four hundred lines is a pull request nobody can review. Refactoring goes in its own commit — see chapter 26.

⚠ The mistake candidates make

Treating these as a checklist to apply everywhere. Every principle here is a trade, and applying one without naming what it bought produces its own pathology: names so long the line wraps, methods so small you need six of them open to follow one thought, a constructor with eleven guard clauses for arguments that are always valid.

In an interview this is what separates two candidates who both recite the same list. "I use guard clauses" is a memorised answer. "I use guard clauses because nesting is what made the original version unreadable, and here is the one place I left the nesting in, because the conditions genuinely belong together" is an engineer.

⚠ The other one

Rewriting somebody else's code on your first week. The instinct is right and the timing is fatal. Code that looks stupid usually has a reason attached that is not written down — a customer who does something odd, a bug in a supplier's API, a rule from the gestionale it replaced. Find the reason first. If there is genuinely none, the change is still easier to get merged as a small one with a test than as a rewrite.

Try it yourself

Do this on your own code, not on an example — it is the only version of this exercise that teaches anything. Open the longest method you have ever written and answer four questions in writing:

  1. Can you name what it does in one sentence with no "and" in it? If not, that is the seam.
  2. How many if, while, case and && does it contain? That number, plus one, is roughly how many tests it needs.
  3. Which of its local variables would a stranger have to read the body to understand?
  4. Is the happy path the least-indented thing in the method, or the most?

Then change exactly one thing — extract one step, rename one variable, invert one if into a guard — and read it again. The point of the exercise is to feel how much of the improvement comes from the smallest edit.

Golden rules

  1. Code is read far more often than it is written; optimise for the reader under pressure.
  2. A name should answer the question the reader is about to ask, and grow with the distance from its declaration.
  3. A magic number or a bare true at a call site is a name that was not written.
  4. One level of abstraction per method: orchestrate, or do, never both.
  5. Guard clauses first, happy path last and unindented. Nesting is where bugs hide.
  6. Comments say why. The code already says what, and only the code stays true.
  7. Commented-out code is deleted code with a hostage. Delete it; Git remembers.
  8. Enforce invariants in the constructor, so an invalid object cannot exist to be checked later.
  9. Prefer immutable: a thing that was valid then cannot be invalid now.
  10. Catch the narrowest exception you can act on, at the layer that can act on it.
  11. throw; preserves the stack trace, throw ex; destroys it.
  12. DRY is about knowledge, not text. Extract when the copies must change together.
  13. Duplication is cheaper than the wrong abstraction, because it is easier to undo.
  14. Simple beats clever: debugging is harder than writing, and you will be doing it tired.
  15. Leave it better than you found it, in its own commit.

Interview questions

"What makes code readable?"

Resist the urge to list adjectives. Pick one concrete thing and show that you know what it costs: "names that answer the question at the call site — GetRecentOrders(30, unshippedOnly: true) instead of Get(30, true). It costs nothing to type and it is the difference between reading a line and looking up a method."

"When is a comment a good idea?"

"When it says something the code cannot: why this order, why this constant, which obvious approach was tried and failed." Then add the corollary, because it shows judgement rather than a rule: "which also means the number of comments in a file is not a quality measure in either direction."

"Is duplication always bad?"

This is a test for dogma and the honest answer wins. "No — the wrong abstraction is worse, because duplication is easy to undo and a shared helper with five flags is not. I duplicate until I can say why the two are the same, and then extract." If you have a real example of a helper that grew flags, use it.

"Your colleague's pull request has a method with a hundred lines. What do you do?"

They are testing how you behave in a review, not whether you know it is too long. Say what you would actually write: ask what the method is called and whether the name has an "and" in it, suggest one extraction rather than a rewrite, and note whether it is new code or a small edit to something already that long — the answer changes, because a review is not the moment to open old debt.

"What is the difference between throw; and throw ex;?"

Small, precise, and a favourite because it separates people who have debugged production from people who have not. "throw; rethrows the same exception with its stack trace intact. throw ex; resets the trace to that line, so the log points at the catch block instead of the bug. If I need to add context I wrap it in a new exception with the original as the inner one."
