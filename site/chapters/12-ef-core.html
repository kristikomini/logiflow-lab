Entity Framework Core

EF Core writes SQL for you. That is a genuine productivity win and a genuine hazard, because the SQL it writes is invisible unless you go and look. Everything in this chapter is about making it visible.

From the advert

"Conoscenza di ASP.NET Core MVC e Entity Framework Core" — optional, and listed after T-SQL. That ordering is the whole attitude: EF Core is a convenience over SQL, not a replacement for knowing it.

What an ORM is for

🧒 Simple

You speak C#. The database speaks SQL. An ORM is an interpreter who stands between you.

Interpreters are wonderful — until you say something long and complicated and they translate it into something technically correct but ridiculous. So you should always be able to ask: "what did you actually say to them?" That is what logging the generated SQL is for, and you should have it switched on while you learn.

🎓 Professional

An ORM resolves the object–relational impedance mismatch: objects have identity, references and inheritance; tables have keys, foreign keys and joins. EF Core provides three things — a translation of LINQ expression trees into SQL, a change tracker that computes an UPDATE statement by comparing an entity against the snapshot taken when it was loaded, and a unit of work that batches all pending changes into one transaction at SaveChanges.

Program.cs — switch the SQL on while you learn
builder.Services.AddDbContext<LogiFlowDbContext>(o =>
{
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default"));

    if (builder.Environment.IsDevelopment())
    {
        o.EnableSensitiveDataLogging();   // shows parameter VALUES — dev only
        o.EnableDetailedErrors();
    }
});

// appsettings.Development.json — the single most useful setting in this chapter
// "Microsoft.EntityFrameworkCore.Database.Command": "Information"
Line by line
  • AddDbContext<LogiFlowDbContext>(o => { ... }) — registers the context with a scoped lifetime: one per HTTP request. That is the only correct default, because a DbContext is not thread-safe and represents a single unit of work.
  • o => — a configuration lambda, run once at registration. The framework hands you an options builder; you set it up.
  • GetConnectionString("Default") — reads ConnectionStrings:Default from configuration, so no password is in source.
  • builder.Environment.IsDevelopment() — the guard that matters. Everything inside it is unsafe in production.
  • EnableSensitiveDataLogging() — logs parameter values, not just the SQL. Enormously useful when a query returns nothing, and a data breach in production: it writes customer names, emails and anything else you filtered on into the log.
  • EnableDetailedErrors() — identifies which property failed on a materialisation error. Costs performance, so it is also development-only.
  • "Microsoft.EntityFrameworkCore.Database.Command": "Information" — a log-level setting in JSON, and the single most useful line in the chapter. It prints every SQL statement EF generates. Most EF problems stop being mysterious the moment you can see the SQL.

DbContext and entity configuration

the context
public class LogiFlowDbContext(DbContextOptions<LogiFlowDbContext> options)
    : DbContext(options)
{
    public DbSet<Order>    Orders    => Set<Order>();
    public DbSet<Customer> Customers => Set<Customer>();

    protected override void OnModelCreating(ModelBuilder b)
        // keep configuration out of this file — one class per entity
        => b.ApplyConfigurationsFromAssembly(typeof(LogiFlowDbContext).Assembly);
}
Line by line
  • LogiFlowDbContext(DbContextOptions<LogiFlowDbContext> options) : DbContext(options) — a primary constructor forwarding to the base. The options carry the provider and connection string and arrive from Program.cs.
  • DbContextOptions<T> is generic in the context type, which is what allows two different contexts in one application without their options being confused.
  • public DbSet<Order> Orders => Set<Order>(); — an expression-bodied property rather than the older { get; set; } form. It cannot be null and nothing outside can reassign it.
  • A DbSet<T> is a query root, not a collection. It is an IQueryable<T>: touching it builds a query, it does not load a table.
  • OnModelCreating — called once, when EF first builds the model, and cached thereafter. It is not per-request.
  • ApplyConfigurationsFromAssembly(...) — finds every IEntityTypeConfiguration<T> by reflection. Without it this method becomes a thousand-line file that every developer edits and every merge conflicts on.
  • typeof(LogiFlowDbContext).Assembly — names the assembly to scan via a type known to be in it. More robust than a string, because a rename cannot break it.
configuration — Fluent API, not attributes
public class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.ToTable("Orders", "dbo");
        b.HasKey(o => o.Id);

        b.Property(o => o.OrderNumber).HasMaxLength(20).IsRequired();
        b.Property(o => o.Total).HasPrecision(18, 2);      // DECIMAL(18,2), not FLOAT
        b.Property(o => o.RowVersion).IsRowVersion();       // optimistic concurrency

        b.HasIndex(o => o.OrderNumber).IsUnique();
        b.HasIndex(o => new { o.CustomerId, o.CreatedAtUtc });  // ch. 08 — order matters

        b.HasOne(o => o.Customer)
         .WithMany(c => c.Orders)
         .HasForeignKey(o => o.CustomerId)
         .OnDelete(DeleteBehavior.Restrict);           // do not cascade silently

        // Lets the entity keep a private list and stay encapsulated (ch. 03)
        b.Metadata.FindNavigation(nameof(Order.Lines))!
         .SetPropertyAccessMode(PropertyAccessMode.Field);
    }
}
Line by line
  • IEntityTypeConfiguration<Order> — one class per entity, discovered by the scan above. This is where the shape of the table is decided.
  • b.ToTable("Orders", "dbo") — table name and schema, explicitly. Conventions would guess; guessing is what breaks when someone renames the class.
  • b.HasKey(o => o.Id) — the primary key. The lambda is used to name the property, not to run anything.
  • .HasMaxLength(20).IsRequired() — becomes NVARCHAR(20) NOT NULL. Without HasMaxLength you get NVARCHAR(MAX), which cannot be indexed and is a silent performance decision.
  • .HasPrecision(18, 2) — DECIMAL(18,2). Omit it and EF picks a default that quietly rounds money.
  • .IsRowVersion() — maps to SQL Server's rowversion, giving optimistic concurrency. EF adds the old value to the WHERE of every UPDATE; if another writer got there first, zero rows match and EF throws DbUpdateConcurrencyException. That exception is the feature working.
  • b.HasIndex(o => new { o.CustomerId, o.CreatedAtUtc }) — a composite index, and the anonymous type's property order is the column order. Equality columns first, then range and sort columns; reversed, the index cannot serve the query.
  • HasOne(...).WithMany(...).HasForeignKey(...) — the relationship, stated from both ends. One order has one customer; that customer has many orders.
  • OnDelete(DeleteBehavior.Restrict) — refuse to delete a customer who has orders. The default for a required relationship is Cascade, which would delete the orders too — silently, and usually not what anyone intended.
  • The private-collection mapping at the end is what lets Order keep a private readonly List<OrderLine> and still be persisted — encapsulation from chapter 03 surviving contact with the ORM.

Prefer the Fluent API over data annotations: it keeps persistence concerns out of your domain classes, and it can express things attributes cannot — composite keys, filtered indexes, delete behaviour, backing fields.

Change tracking

AsNoTracking — the free performance win
// ✓ read-only query: no snapshot, less memory, measurably faster
var list = await db.Orders
    .AsNoTracking()
    .Where(o => o.CustomerId == id)
    .Select(o => new OrderDto(o.Id, o.Total, o.Status))   // project! (see below)
    .ToListAsync(ct);

// ✗ tracking a thousand entities you will never modify
var list2 = await db.Orders.Where(o => o.CustomerId == id).ToListAsync(ct);
Line by line
  • By default EF takes a snapshot of every entity it returns so SaveChanges can work out what changed. That snapshot costs memory and time on every row.
  • .AsNoTracking() — skip it. Correct for any query whose results you will not modify, which is most of them, and measurably faster on large result sets.
  • .Where(...) before .Select(...) — both are translated to SQL, so ordering is about readability, not performance. Both run on the server.
  • .Select(o => new OrderDto(...)) — the projection, and it makes AsNoTracking redundant: EF never materialises an Order, so there is nothing to track. Projecting is the better habit.
  • ToListAsync(ct) — the terminal call that executes the query, with the cancellation token passed down.
  • The second version tracks a thousand entities you will never modify, and does it invisibly. It is correct and wasteful, which is the hardest kind of problem to notice in a code review.

Note that projecting with Select into a DTO makes the query no-tracking automatically — there is no entity to track. Projection is the better habit anyway: it fetches three columns instead of twenty.

Loading related data — and the N+1 problem

🧒 Simple

You need the phone numbers of thirty classmates. You could ring the school office thirty-one times: once for the list of names, then once per name. Thirty-one phone calls.

Or you could ring once and say "please send me all thirty names with their numbers".

The first way is called the N+1 problem, and it is by far the most common reason a .NET page is slow.

the bug, and how to see it
// ✗ N+1 — one query for the orders, then one MORE per order
var orders = await db.Orders.ToListAsync(ct);            // 1 query
foreach (var o in orders)
    Console.WriteLine(o.Customer.Name);                 // + 1 query EACH
// 500 orders → 501 round trips. Each one is a network hop.

// ✓ eager loading — one query with a JOIN
var orders2 = await db.Orders
    .Include(o => o.Customer)
    .Include(o => o.Lines).ThenInclude(l => l.Product)
    .ToListAsync(ct);

// ✓✓ better — project only what the caller needs. No Include required.
var dtos = await db.Orders
    .Select(o => new OrderDto(o.Id, o.Customer.Name, o.Lines.Count))
    .ToListAsync(ct);
Line by line
  • await db.Orders.ToListAsync(ct) — one query, all orders. So far so good.
  • o.Customer.Name — the disaster, and it does not look like a database call. Customer is a navigation property that was not loaded, so EF fetches it — one round trip per order.
  • 500 orders means 501 queries. Each is a network hop of a millisecond or two, so a page that should take 5 ms takes a second, and the code looks perfectly innocent.
  • It is worse with lazy loading enabled, because then it happens with no visible Include anywhere. This is exactly why the SQL logging setting in the first block matters: N+1 is obvious in the log and invisible in the source.
  • .Include(o => o.Customer) — eager loading. One query with a JOIN.
  • .Include(o => o.Lines).ThenInclude(l => l.Product) — ThenInclude continues from the last include, going one level deeper. Note that including several collections multiplies rows — the "cartesian explosion" — which EF mitigates with AsSplitQuery().
  • .Select(o => new OrderDto(o.Id, o.Customer.Name, o.Lines.Count)) — best, and no Include is needed. Referring to o.Customer.Name inside a projection makes EF generate the join itself, and o.Lines.Count becomes a subquery rather than loading the lines.
  • The rule: Include when you need whole entities to modify them; project when you need data to display. Most endpoints are the second case.
StrategyHowUse when
Eager.Include()You know you need the related data. The default choice.
Projection.Select()Almost always better still — fetches only the columns used.
Explicit.Entry(o).Collection(...).LoadAsync()You decide later, conditionally.
LazyProxies + virtual navigationsRarely. It makes N+1 invisible and silent.
⚠ Cartesian explosion — when Include is the problem

Two collection Includes on one query produce a cross product: an order with 10 lines and 10 payments returns 100 rows, and EF must de-duplicate them in memory. The fix is .AsSplitQuery(), which issues one statement per collection. Knowing this exists marks you out immediately — most people have never heard of it.

Writing data

insert, update, delete
// INSERT
var order = Order.Create(customerId, orderNumber);   // factory keeps invariants (ch. 03)
db.Orders.Add(order);
await db.SaveChangesAsync(ct);                        // order.Id is populated here

// UPDATE — no Update() call needed; the tracker noticed
var existing = await db.Orders.FindAsync([id], ct);
existing!.Submit();
await db.SaveChangesAsync(ct);

// DELETE
db.Orders.Remove(existing);
await db.SaveChangesAsync(ct);

// Bulk operations (EF Core 7+): one statement, no loading, no tracking
await db.Orders
    .Where(o => o.CreatedAtUtc < cutoff && o.Status == OrderStatus.Draft)
    .ExecuteDeleteAsync(ct);

await db.Orders
    .Where(o => o.Status == OrderStatus.Pending)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Expired), ct);
Line by line
  • Order.Create(...) — a static factory rather than new, so the invariants from chapter 03 are enforced and an invalid order cannot exist.
  • db.Orders.Add(order) — marks it Added in the change tracker. Nothing has been sent to the database yet.
  • await db.SaveChangesAsync(ct) — the only line that talks to the database. It wraps everything in a transaction automatically, so either all changes land or none do.
  • order.Id is populated after SaveChanges — the database generated it, and EF reads it back into the object.
  • FindAsync([id], ct) — look-up by primary key, and the only query that checks the change tracker first and can return without touching the database. The square brackets are a collection expression, because a key may be composite.
  • existing!.Submit() — the ! is the null-forgiving operator: FindAsync returns null when not found and you have asserted it will not be.
  • No Update() call. The entity is tracked, so SaveChanges compares it to the snapshot and issues an UPDATE containing only the changed columns. Calling Update() would mark every property modified.
  • ExecuteDeleteAsync / ExecuteUpdateAsync (EF Core 7+) — one SQL statement, no loading, no tracking, for bulk work. The old way loaded every matching row into memory to delete it.
  • The catch: they run immediately, outside SaveChanges, so they are not part of its transaction and the change tracker does not know about them. Entities already in memory are now stale.
  • s => s.SetProperty(o => o.Status, OrderStatus.Expired) — two lambdas: one naming the property, one supplying the value. It reads oddly and it is what lets the whole update be translated to SQL.

ExecuteUpdate/ExecuteDelete bypass the change tracker entirely, so they do not fire SaveChanges interceptors or update already-loaded entities. That is the point — and the caveat.

Migrations

the workflow
# 1. change your entity or its configuration
# 2. generate a migration — READ IT before you trust it
dotnet ef migrations add AddOrderRowVersion -p src/LogiFlow.Infrastructure -s src/LogiFlow.Api

# 3. apply it locally
dotnet ef database update -p src/LogiFlow.Infrastructure -s src/LogiFlow.Api

# 4. for production: generate idempotent SQL and let a DBA review it
dotnet ef migrations script --idempotent -o migrate.sql
Line by line
  • # — shell comments. These are terminal commands, not C#.
  • dotnet ef migrations add AddOrderRowVersion — compares the model to the last migration and generates the difference as a C# file. The name becomes part of the filename, so make it descriptive.
  • READ IT before you trust it. A rename that EF interprets as a drop plus an add is data loss that looks exactly like a rename in the diff.
  • -p src/LogiFlow.Infrastructure — the project containing the DbContext and where migration files are written.
  • -s src/LogiFlow.Api — the startup project, needed for configuration and the connection string. Two different projects, which is why both flags are required and why forgetting one is the commonest EF tooling error.
  • dotnet ef database update — applies pending migrations. A separate step from generating them, deliberately.
  • migrations script --idempotent — emits SQL that checks the __EFMigrationsHistory table before each step, so it can be run against a database at any version safely.
  • Why a script for production rather than database update: a DBA can review it, it can run in a maintenance window, and the application does not need schema-modifying permissions at run time.
⚠ Never Database.Migrate() at application startup

It is in every tutorial and it is wrong in production: several instances start at once and race, a failed migration takes down the app rather than the deployment, and nobody reviewed the DDL. Migrations belong in the release pipeline as a deliberate, reviewable step.

Related: never edit a migration that has already been applied elsewhere. Add a new one. And read the generated file — EF will happily produce a DROP COLUMN for a rename, which is data loss, not a schema change.

When to drop to SQL

EF Core is not an all-or-nothing commitment. Complex reporting queries, window functions, and anything where the plan matters are legitimately better hand-written — which is exactly why the advert asks for T-SQL.

both escape hatches
// Map raw SQL onto entities — parameters are still parameters
var orders = await db.Orders
    .FromSqlInterpolated($"EXEC dbo.usp_GetCustomerOrders @CustomerId = {id}")
    .AsNoTracking()
    .ToListAsync(ct);

// Or bypass EF entirely with Dapper for a read-heavy path
var rows = await connection.QueryAsync<OrderRow>(
    "SELECT Id, Total FROM dbo.Orders WHERE CustomerId = @id",
    new { id });
Line by line
  • FromSqlInterpolated($"...") — raw SQL mapped onto entities. Despite the $, the interpolation holes become SQL parameters, not concatenated text — that is the whole point of this method and why it is safe.
  • {id} — becomes @p0 in the generated statement. FromSqlRaw with a manually built string is the version that is injectable; prefer the interpolated one.
  • EXEC dbo.usp_GetCustomerOrders — a stored procedure. The result columns must match the entity EF is mapping to.
  • .AsNoTracking().ToListAsync(ct) — LINQ still composes onto raw SQL, though a stored procedure limits what can be appended, since SQL Server cannot always wrap one in a subquery.
  • connection.QueryAsync<OrderRow>(...) — Dapper, a micro-ORM. No change tracking, no model, no LINQ translation: SQL in, objects out. Faster and the right tool for a read-heavy reporting path.
  • new { id } — an anonymous object supplying parameters by name. The shorthand { id } creates a property called id from the variable, matching @id in the SQL.
  • When to drop out of EF: a query LINQ cannot express, a bulk operation, or a hot path where the translation overhead is measurable. Not because the LINQ is hard to write — that usually means the query is worth rethinking.

DbContext lifetime

AddDbContext registers it as scoped — one per HTTP request. This is correct and deliberate: DbContext is not thread-safe, and it is a unit of work whose natural boundary is the request. Never make it a singleton (it accumulates tracked entities for ever and is shared across threads); use IDbContextFactory in a background service or when you genuinely need two at once.

Try it yourself

Turn on Microsoft.EntityFrameworkCore.Database.Command: Information and then, for each of these, look at the SQL in the console:

  1. Load orders, then touch o.Customer.Name in a loop. Count the queries.
  2. Add .Include(o => o.Customer). Count again.
  3. Replace it with a .Select(...) projection. Look at the column list.
  4. Add a second collection Include. Count the returned rows, then add .AsSplitQuery().
  5. Write .Where(o => MyLocalMethod(o)) and read the error — EF Core refuses to silently evaluate on the client, and that refusal is a feature.

Golden rules

  1. Log the generated SQL in development. An ORM you cannot see is an ORM you cannot debug.
  2. AsNoTracking() on every read-only query — or better, project into a DTO.
  3. N+1 is the default failure mode. Include or Select, never a navigation property inside a loop.
  4. Prefer projection to Include: fetch the columns you use, not the table.
  5. Two collection Includes cause a cartesian explosion. AsSplitQuery().
  6. Avoid lazy loading. It turns N+1 into something invisible.
  7. SaveChanges is one transaction. Group related writes into one call.
  8. DbContext is scoped and not thread-safe. Never a singleton, never two concurrent operations on one instance.
  9. Fluent API over attributes. Keep persistence out of the domain model.
  10. Read every generated migration. A "rename" can arrive as DROP COLUMN.
  11. Apply migrations from the pipeline, not from Program.cs.
  12. Drop to SQL when the query is genuinely relational. That is judgement, not defeat.

Interview questions

"What is the N+1 problem?"

One query returns N rows, then accessing a navigation property on each issues one more query — N+1 round trips instead of one. Fix with Include or a projection. Then say how you would detect it: SQL logging, or a spike in query count per request in telemetry.

"What does AsNoTracking do and when would you use it?"

It skips the identity-resolution and snapshot bookkeeping the change tracker needs, so reads use less memory and are faster. Use it whenever you will not modify the entities — which is most read paths in a Web API.

"IQueryable or IEnumerable — why does it matter here?"

IQueryable is translated to SQL; the moment it becomes IEnumerable the rest runs in memory over whatever was already fetched. A ToList() before a Where is the difference between three rows and the entire table. (Chapter 06.)

"How do you handle two users editing the same record?"

A rowversion concurrency token; EF then includes it in the WHERE of the UPDATE, so a stale write affects zero rows and throws DbUpdateConcurrencyException, which you handle by reloading and showing the conflict.

"When would you not use EF Core?"

Bulk operations over large row counts, complex reporting with window functions, and anywhere the execution plan needs hand control — use raw SQL, a stored procedure or Dapper there. Mixing them in one codebase is normal and is a sign of judgement rather than inconsistency.
