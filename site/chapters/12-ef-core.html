Entity Framework Core

EF Core writes SQL for you. That is a genuine productivity win and a genuine hazard, because the SQL it writes is invisible unless you go and look. Everything in this chapter is about making it visible.

From the advert

"Conoscenza di ASP.NET Core MVC e Entity Framework Core" — optional, and listed after T-SQL. That ordering is the whole attitude: EF Core is a convenience over SQL, not a replacement for knowing it.

What an ORM is for

🧒 Simple

You speak C#. The database speaks SQL. An ORM is an interpreter who stands between you.

Interpreters are wonderful — until you say something long and complicated and they translate it into something technically correct but ridiculous. So you should always be able to ask: "what did you actually say to them?" That is what logging the generated SQL is for, and you should have it switched on while you learn.

🎓 Professional

An ORM resolves the object–relational impedance mismatch: objects have identity, references and inheritance; tables have keys, foreign keys and joins. EF Core provides three things — a translation of LINQ expression trees into SQL, a change tracker that computes an UPDATE statement by comparing an entity against the snapshot taken when it was loaded, and a unit of work that batches all pending changes into one transaction at SaveChanges.

DbContext and entity configuration

the context
public class LogiFlowDbContext(DbContextOptions<LogiFlowDbContext> options)
    : DbContext(options)
{
    public DbSet<Order>    Orders    => Set<Order>();
    public DbSet<Customer> Customers => Set<Customer>();

    protected override void OnModelCreating(ModelBuilder b)
        // keep configuration out of this file — one class per entity
        => b.ApplyConfigurationsFromAssembly(typeof(LogiFlowDbContext).Assembly);
}
configuration — Fluent API, not attributes
public class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.ToTable("Orders", "dbo");
        b.HasKey(o => o.Id);

        b.Property(o => o.OrderNumber).HasMaxLength(20).IsRequired();
        b.Property(o => o.Total).HasPrecision(18, 2);      // DECIMAL(18,2), not FLOAT
        b.Property(o => o.RowVersion).IsRowVersion();       // optimistic concurrency

        b.HasIndex(o => o.OrderNumber).IsUnique();
        b.HasIndex(o => new { o.CustomerId, o.CreatedAtUtc });  // ch. 08 — order matters

        b.HasOne(o => o.Customer)
         .WithMany(c => c.Orders)
         .HasForeignKey(o => o.CustomerId)
         .OnDelete(DeleteBehavior.Restrict);           // do not cascade silently

        // Lets the entity keep a private list and stay encapsulated (ch. 03)
        b.Metadata.FindNavigation(nameof(Order.Lines))!
         .SetPropertyAccessMode(PropertyAccessMode.Field);
    }
}

Prefer the Fluent API over data annotations: it keeps persistence concerns out of your domain classes, and it can express things attributes cannot — composite keys, filtered indexes, delete behaviour, backing fields.

Change tracking

AsNoTracking — the free performance win
// ✓ read-only query: no snapshot, less memory, measurably faster
var list = await db.Orders
    .AsNoTracking()
    .Where(o => o.CustomerId == id)
    .Select(o => new OrderDto(o.Id, o.Total, o.Status))   // project! (see below)
    .ToListAsync(ct);

// ✗ tracking a thousand entities you will never modify
var list2 = await db.Orders.Where(o => o.CustomerId == id).ToListAsync(ct);

Note that projecting with Select into a DTO makes the query no-tracking automatically — there is no entity to track. Projection is the better habit anyway: it fetches three columns instead of twenty.

Loading related data — and the N+1 problem

🧒 Simple

You need the phone numbers of thirty classmates. You could ring the school office thirty-one times: once for the list of names, then once per name. Thirty-one phone calls.

Or you could ring once and say "please send me all thirty names with their numbers".

The first way is called the N+1 problem, and it is by far the most common reason a .NET page is slow.

the bug, and how to see it
// ✗ N+1 — one query for the orders, then one MORE per order
var orders = await db.Orders.ToListAsync(ct);            // 1 query
foreach (var o in orders)
    Console.WriteLine(o.Customer.Name);                 // + 1 query EACH
// 500 orders → 501 round trips. Each one is a network hop.

// ✓ eager loading — one query with a JOIN
var orders2 = await db.Orders
    .Include(o => o.Customer)
    .Include(o => o.Lines).ThenInclude(l => l.Product)
    .ToListAsync(ct);

// ✓✓ better — project only what the caller needs. No Include required.
var dtos = await db.Orders
    .Select(o => new OrderDto(o.Id, o.Customer.Name, o.Lines.Count))
    .ToListAsync(ct);
StrategyHowUse when
Eager.Include()You know you need the related data. The default choice.
Projection.Select()Almost always better still — fetches only the columns used.
Explicit.Entry(o).Collection(...).LoadAsync()You decide later, conditionally.
LazyProxies + virtual navigationsRarely. It makes N+1 invisible and silent.
⚠ Cartesian explosion — when Include is the problem

Two collection Includes on one query produce a cross product: an order with 10 lines and 10 payments returns 100 rows, and EF must de-duplicate them in memory. The fix is .AsSplitQuery(), which issues one statement per collection. Knowing this exists marks you out immediately — most people have never heard of it.

Writing data

insert, update, delete
// INSERT
var order = Order.Create(customerId, orderNumber);   // factory keeps invariants (ch. 03)
db.Orders.Add(order);
await db.SaveChangesAsync(ct);                        // order.Id is populated here

// UPDATE — no Update() call needed; the tracker noticed
var existing = await db.Orders.FindAsync([id], ct);
existing!.Submit();
await db.SaveChangesAsync(ct);

// DELETE
db.Orders.Remove(existing);
await db.SaveChangesAsync(ct);

// Bulk operations (EF Core 7+): one statement, no loading, no tracking
await db.Orders
    .Where(o => o.CreatedAtUtc < cutoff && o.Status == OrderStatus.Draft)
    .ExecuteDeleteAsync(ct);

await db.Orders
    .Where(o => o.Status == OrderStatus.Pending)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Expired), ct);

ExecuteUpdate/ExecuteDelete bypass the change tracker entirely, so they do not fire SaveChanges interceptors or update already-loaded entities. That is the point — and the caveat.

Migrations

the workflow
# 1. change your entity or its configuration
# 2. generate a migration — READ IT before you trust it
dotnet ef migrations add AddOrderRowVersion -p src/LogiFlow.Infrastructure -s src/LogiFlow.Api

# 3. apply it locally
dotnet ef database update -p src/LogiFlow.Infrastructure -s src/LogiFlow.Api

# 4. for production: generate idempotent SQL and let a DBA review it
dotnet ef migrations script --idempotent -o migrate.sql
⚠ Never Database.Migrate() at application startup

It is in every tutorial and it is wrong in production: several instances start at once and race, a failed migration takes down the app rather than the deployment, and nobody reviewed the DDL. Migrations belong in the release pipeline as a deliberate, reviewable step.

Related: never edit a migration that has already been applied elsewhere. Add a new one. And read the generated file — EF will happily produce a DROP COLUMN for a rename, which is data loss, not a schema change.

When to drop to SQL

EF Core is not an all-or-nothing commitment. Complex reporting queries, window functions, and anything where the plan matters are legitimately better hand-written — which is exactly why the advert asks for T-SQL.

both escape hatches
// Map raw SQL onto entities — parameters are still parameters
var orders = await db.Orders
    .FromSqlInterpolated($"EXEC dbo.usp_GetCustomerOrders @CustomerId = {id}")
    .AsNoTracking()
    .ToListAsync(ct);

// Or bypass EF entirely with Dapper for a read-heavy path
var rows = await connection.QueryAsync<OrderRow>(
    "SELECT Id, Total FROM dbo.Orders WHERE CustomerId = @id",
    new { id });

DbContext lifetime

AddDbContext registers it as scoped — one per HTTP request. This is correct and deliberate: DbContext is not thread-safe, and it is a unit of work whose natural boundary is the request. Never make it a singleton (it accumulates tracked entities for ever and is shared across threads); use IDbContextFactory in a background service or when you genuinely need two at once.

Try it yourself

Turn on Microsoft.EntityFrameworkCore.Database.Command: Information and then, for each of these, look at the SQL in the console:

  1. Load orders, then touch o.Customer.Name in a loop. Count the queries.
  2. Add .Include(o => o.Customer). Count again.
  3. Replace it with a .Select(...) projection. Look at the column list.
  4. Add a second collection Include. Count the returned rows, then add .AsSplitQuery().
  5. Write .Where(o => MyLocalMethod(o)) and read the error — EF Core refuses to silently evaluate on the client, and that refusal is a feature.

Golden rules

  1. Log the generated SQL in development. An ORM you cannot see is an ORM you cannot debug.
  2. AsNoTracking() on every read-only query — or better, project into a DTO.
  3. N+1 is the default failure mode. Include or Select, never a navigation property inside a loop.
  4. Prefer projection to Include: fetch the columns you use, not the table.
  5. Two collection Includes cause a cartesian explosion. AsSplitQuery().
  6. Avoid lazy loading. It turns N+1 into something invisible.
  7. SaveChanges is one transaction. Group related writes into one call.
  8. DbContext is scoped and not thread-safe. Never a singleton, never two concurrent operations on one instance.
  9. Fluent API over attributes. Keep persistence out of the domain model.
  10. Read every generated migration. A "rename" can arrive as DROP COLUMN.
  11. Apply migrations from the pipeline, not from Program.cs.
  12. Drop to SQL when the query is genuinely relational. That is judgement, not defeat.

Interview questions

"What is the N+1 problem?"

One query returns N rows, then accessing a navigation property on each issues one more query — N+1 round trips instead of one. Fix with Include or a projection. Then say how you would detect it: SQL logging, or a spike in query count per request in telemetry.

"What does AsNoTracking do and when would you use it?"

It skips the identity-resolution and snapshot bookkeeping the change tracker needs, so reads use less memory and are faster. Use it whenever you will not modify the entities — which is most read paths in a Web API.

"IQueryable or IEnumerable — why does it matter here?"

IQueryable is translated to SQL; the moment it becomes IEnumerable the rest runs in memory over whatever was already fetched. A ToList() before a Where is the difference between three rows and the entire table. (Chapter 06.)

"How do you handle two users editing the same record?"

A rowversion concurrency token; EF then includes it in the WHERE of the UPDATE, so a stale write affects zero rows and throws DbUpdateConcurrencyException, which you handle by reloading and showing the conflict.

"When would you not use EF Core?"

Bulk operations over large row counts, complex reporting with window functions, and anywhere the execution plan needs hand control — use raw SQL, a stored procedure or Dapper there. Mixing them in one codebase is normal and is a sign of judgement rather than inconsistency.
