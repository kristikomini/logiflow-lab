Files and folders

Reading a file is one line. Reading a file correctly — on a server, in a container, in another country, while another process is writing to it, without loading two gigabytes into memory — is the rest of this chapter. Every integration you will ever be handed starts as a folder somebody drops files into, so this is not a beginner topic that you outgrow.

Why this chapter exists

Almost every warehouse, ERP and logistics integration in the real world is still a file: a CSV of orders from a customer, a fixed-width export to a courier, an XML the accounting system watches for. The code is short enough that nobody reviews it carefully, which is why the same five defects appear in all of them — a hard-coded backslash that dies on Linux, a ReadAllLines on a file that outgrew memory, a decimal that means a thousand times more than it should, a half-written file picked up by the process downstream, and a lock that stays behind because nothing disposed the stream.

The whole file at once

🧒 Simple

For a small file there is a single method for each direction: give it a path and get the text, or give it a path and some text and it writes it. That is genuinely all there is, and it is right until the file gets big. 

string text    = File.ReadAllText(path);          // the entire file, one string
string[] lines = File.ReadAllLines(path);         // split into lines for you
byte[] bytes   = File.ReadAllBytes(path);         // for anything not text

File.WriteAllText(path, text);                    // creates or OVERWRITES, silently
File.AppendAllText(log, line + Environment.NewLine);
File.WriteAllLines(path, skus);                   // one per line

// async versions exist for all of them, and belong in any web request
string t = await File.ReadAllTextAsync(path, ct);

bool there = File.Exists(path);
long size  = new FileInfo(path).Length;
Line by line
  • WriteAllText overwrites without asking and creates the file if it is missing. There is no "fail if it exists" overload; if that matters, check first and accept that the check and the write are not atomic.
  • Environment.NewLine is \r\n on Windows and \n elsewhere. WriteAllLines uses it for you; hand-built strings need it, or need \n chosen deliberately because the consumer is a Unix tool.
  • Every one of these loads the whole file into memory. Fine for a configuration file or a thousand-row CSV; fatal for the six-hundred-megabyte export somebody will eventually send. A string also has a length limit, and a large byte[] goes on the large object heap where it is expensive to collect.
  • Use the Async versions inside a web application. A synchronous read blocks a thread-pool thread for the duration of a disk or network round trip, and under load that is how a server stops responding — chapter 07 is why.
  • File.Exists returning true is not a promise the file will still be there one line later, and it returns false for a path you lack permission to look at. Checking before opening is a hint, not a guard; the try is the guard.

Paths: the bug that only happens on the server

// ✗ works on your Windows laptop, fails in the Linux container
string bad = folder + "\\" + name;
string alsoBad = "C:\\imports\\orders.csv";

// ✓ let the framework decide the separator
string path = Path.Combine(folder, "in", name);

Path.GetFileName(path)              // "orders.csv"
Path.GetFileNameWithoutExtension(p) // "orders"
Path.GetExtension(path)             // ".csv"  — with the dot
Path.GetDirectoryName(path)         // the folder
Path.GetFullPath(relative)          // resolve against the current directory
Path.GetTempFileName()              // a unique temp file, created for you

string data = Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData);
string here = AppContext.BaseDirectory;      // where the app itself lives
Line by line
  • Path.Combine, always. It uses the platform's separator and handles the trailing-slash question, so two people can concatenate the same two pieces and get the same answer. A hard-coded backslash is the single most common reason perfectly good code fails the moment it is containerised.
  • Path.Combine has a sharp edge worth knowing: if any argument is rooted, everything before it is discarded. Path.Combine("/data", "/etc/passwd") is "/etc/passwd", which is a security hole when the second piece came from a user.
  • Never build a path from user input without validating it. Path.Combine(uploads, fileName) where fileName is "../../appsettings.json" is path traversal. Take Path.GetFileName of it first, then confirm the resolved full path still starts with your folder.
  • AppContext.BaseDirectory is where the application was deployed; Directory.GetCurrentDirectory() is wherever the process happened to be started, which under a scheduled task or a service is rarely what you assumed. Prefer the first.
  • Windows paths are case-insensitive and Linux paths are not, so a file referenced as Orders.csv and stored as orders.csv works on a laptop and vanishes on the server. Match the case exactly.

One line at a time, for a file you did not size

// ✓ constant memory, whatever the file size
foreach (string line in File.ReadLines(path))       // note: ReadLines, not ReadAllLines
{
    if (TryParseLine(line, out var row))
        Import(row);
}

// the same thing with the stream in your hands — and a using, always
using var reader = new StreamReader(path, Encoding.UTF8);
string? line2;
while ((line2 = reader.ReadLine()) is not null)
    Import(line2);

// writing, one line at a time
using var writer = new StreamWriter(outPath, append: false, Encoding.UTF8);
foreach (var o in orders)
    await writer.WriteLineAsync($"{o.Sku};{o.Qty}");

// async streaming, the modern shape
await foreach (string l in File.ReadLinesAsync(path, ct))
    Import(l);
Line by line
  • ReadLines versus ReadAllLines — one letter, and the difference between constant memory and the whole file at once. ReadLines returns a lazy IEnumerable<string> that reads as you walk it, which is the iterator machinery from chapter 02e.
  • using var — the file handle is released when the variable goes out of scope, whether the method returned normally or threw. Without it the file stays locked until the garbage collector eventually runs, and the next process to open it fails with a message about another process using the file. Chapter 08 is the full story.
  • (line2 = reader.ReadLine()) is not null — assignment inside the condition, which is idiomatic here precisely because the end-of-file signal is the null. It is one of the few places assignment in a condition reads well.
  • await foreach over ReadLinesAsync is an IAsyncEnumerable: lazy and asynchronous at once, so a huge file streams through a web request without blocking a thread or filling memory.
  • A cancellation token on every async file call. A cancelled HTTP request should stop reading a two-gigabyte file, not finish it politely.
⚠️ The file that was still being written

A folder watcher that picks up orders.csv the moment it appears will regularly read half a file, because the sender is still writing it. The fix is not a retry loop — it is a protocol: the sender writes to orders.csv.tmp and then renames it, because a rename within one volume is atomic and the file appears complete or not at all. If you cannot change the sender, wait for the size to stop changing, or open with FileShare.None and treat the resulting exception as "not ready yet".

Encoding, and the accented name that arrived as three symbols

🧒 Simple

A file holds bytes, not letters. Turning bytes into letters needs a codebook, and there is more than one. Use the wrong codebook and every accented character comes out as nonsense — and only the accented ones, which is why nobody notices until a customer is called Müller. 

// .NET defaults to UTF-8 without a BOM, and detects a BOM if one is present
string t = File.ReadAllText(path);                        // usually right

// a file from an old ERP, written in Windows-1252
var latin = System.Text.Encoding.GetEncoding("windows-1252");
string legacy = File.ReadAllText(path, latin);

// writing a file Excel will open by double-click, in Italy
var utf8Bom = new UTF8Encoding(encoderShouldEmitUTF8Identifier: true);
File.WriteAllText(outPath, csv, utf8Bom);

// numbers and dates in a FILE are always invariant
string cell = weight.ToString("F2", CultureInfo.InvariantCulture);
DateTime.TryParse(s, CultureInfo.InvariantCulture,
                  DateTimeStyles.None, out var when);
string iso = when.ToString("O");                          // round-trip format
Line by line
  • UTF-8 is the answer for anything you control. The question only arises with files produced by something older, and the symptom is characteristic: ASCII is fine and accented characters are replaced by ? or by two or three odd symbols.
  • A byte order mark — a BOM — is a few bytes at the start announcing the encoding. .NET reads it when present and writes UTF-8 without one by default. Excel, on an Italian Windows machine, needs the BOM to open a UTF-8 CSV correctly — the single most common "your export is broken" support ticket there is.
  • Encoding.GetEncoding("windows-1252") requires Encoding.RegisterProvider(CodePagesEncodingProvider.Instance) on .NET Core first, or it throws. A one-line surprise when porting from .NET Framework.
  • Culture is a second, separate decision from encoding, and the one that costs more. 18.40 written under it-IT is 18,40, which in a semicolon-separated file is still one field and in a comma-separated one is two — a corrupted row with no error. Files are read by machines: InvariantCulture, both directions.
  • "O" is the round-trip date format — ISO 8601 with offset, unambiguous everywhere. Never write a date to a file as 03/04/2026; half the world reads it as April and half as March.

Folders, and finding what is in them

Directory.CreateDirectory(folder);           // creates the whole tree; no error if it exists

foreach (string f in Directory.EnumerateFiles(inbox, "*.csv"))
    Process(f);

// recursive, and lazy — EnumerateFiles, not GetFiles
var all = Directory.EnumerateFiles(root, "*.xml", SearchOption.AllDirectories);

// ordering by age, for an inbox that must be processed in sequence
var oldest = new DirectoryInfo(inbox)
    .EnumerateFiles("*.csv")
    .OrderBy(f => f.CreationTimeUtc)
    .ToList();

File.Move(src, dst, overwrite: false);       // rename or relocate; atomic within a volume
File.Copy(src, dst, overwrite: true);
File.Delete(path);                            // NO error if the file is not there
Directory.Delete(folder, recursive: true);    // this one DOES throw if it is missing
Line by line
  • EnumerateFiles is lazy and GetFiles builds the whole array first. On a folder with two hundred thousand files that is the difference between starting immediately and waiting. Same pairing as ReadLines/ReadAllLines.
  • CreateDirectory is idempotent — it creates the whole path and does nothing if it already exists, so the if (!Directory.Exists) around it is noise.
  • File.Delete on a missing file succeeds silently, while Directory.Delete throws. An inconsistency worth remembering rather than understanding.
  • The search pattern is a glob, not a regular expression: * and ? only. Its Windows heritage includes one genuine trap — "*.csv" also matches orders.csv.bak on some platforms, because of short-name matching. Filter on Path.GetExtension if it matters.
  • File.Move within one volume is a rename and therefore atomic; across volumes it is a copy-then-delete and is not. That distinction is what makes the write-then-rename pattern safe, and it is why it stops being safe when the temp folder is on a different drive.

Writing a file nobody catches half-written

This is the pattern worth taking away from the whole chapter. It is six lines and it removes the two worst file bugs at once: a partial file read by whatever is watching the folder, and an original destroyed by a write that failed halfway. 

static async Task WriteAtomicAsync(string path, string content, CancellationToken ct)
{
    string tmp = path + ".tmp";                       // same folder = same volume

    await File.WriteAllTextAsync(tmp, content, new UTF8Encoding(true), ct);

    File.Move(tmp, path, overwrite: true);            // atomic rename — all or nothing
}

// and reading something that may be locked, without pretending it cannot happen
try
{
    using var s = new FileStream(path, FileMode.Open, FileAccess.Read, FileShare.Read);
    // FileShare.Read: others may read while we do, but nobody may write
}
catch (IOException ex)
{
    _log.LogWarning(ex, "{Path} is not ready yet", path);   // it will be, next sweep
}
Line by line
  • Write to a temporary name, then rename. Readers see the final name only when the content is complete, because the rename is a single filesystem operation. The temp file must be in the same folder, or the move is a copy and the guarantee evaporates.
  • FileShare declares what other processes may do while you hold the file. FileShare.Read lets others read and blocks writers; FileShare.None is an exclusive lock, which is a crude but effective way to ask "has the sender finished".
  • IOException is the type to catch for a locked or in-use file, and there is no more specific one worth reaching for. Do not catch it and continue silently — log it, and let the next sweep try again.
  • Every file operation can fail for reasons that are nobody's bug: a full disk, a revoked permission, a disconnected network share, a file open in Excel. File code without a try is unfinished code, which is the argument chapter 02l makes in general.
  • Nothing here uses File.Exists as a guard, deliberately. Between the check and the open, anything can happen; the exception handler is the only real protection.

Exercises, with the reasoning shown

Exercise 1 — the path that only worked on a laptop

string path = importFolder + "\\" + fileName;
FileNotFoundException in the Linux container.
  • On Linux the separator is /, so the backslash becomes part of the file name — a file called imports\orders.csv, which nothing created. Path.Combine(importFolder, fileName) is the fix, and it also handles the case where importFolder already ends with a separator, which the concatenation turns into a doubled one.

Exercise 2 — the import that ran out of memory

foreach (var line in File.ReadAllLines(path))   // path is 1.4 GB
    Import(line);
OutOfMemoryException, and a server that gets slow before it gets there.
  • ReadAllLines loads the whole file and then allocates a separate string per line, so peak memory is well over twice the file size, on the large object heap. File.ReadLines — one letter shorter — returns a lazy sequence that reads as the loop walks it, in constant memory. The loop body does not change at all.

Exercise 3 — the file that stayed locked

var reader = new StreamReader(path);
string first = reader.ReadLine();
return first;
The handle is never released, and the next process to open the file fails.
  • Returning early skipped any cleanup, and nothing here would have cleaned up anyway. The reader holds an operating-system handle until it is disposed, or until the garbage collector eventually runs a finaliser — which may be minutes later, or never during a short-lived process. using var reader = … releases it at the end of the method, including on the early return and including if ReadLine throws.

Exercise 4 — the weights that were a thousand times too heavy

// written on a server set to it-IT
File.WriteAllText(path, $"{sku};{weightKg:F2}");
// read back on a server set to en-GB
decimal.Parse(parts[1]);
18.40 kg is written as 18,40 and read back as 1840.
  • No exception either way: the comma is a valid thousands separator in en-GB, so the parse succeeds and returns a plausible number. Both sides needed CultureInfo.InvariantCulture. This is the single most expensive file bug in this chapter, because everything downstream — freight cost, pallet count, vehicle loading — is wrong and nothing reports an error.
Try it yourself

A complete little importer: it creates its own folders, writes a file the safe way, reads it back lazily, and survives a locked file. Thirty lines, and every rule on this page is in it. 

string root  = Path.Combine(AppContext.BaseDirectory, "demo");
  string inbox = Path.Combine(root, "in");
  string done  = Path.Combine(root, "done");
  Directory.CreateDirectory(inbox);
  Directory.CreateDirectory(done);

  // write one, atomically, with an invariant number and a BOM Excel will accept
  string file = Path.Combine(inbox, "orders.csv");
  string tmp  = file + ".tmp";
  string body = string.Join(Environment.NewLine,
  [
      "SKU;QTY;KG",
      $"MI-42;12;{18.4m.ToString("F2", CultureInfo.InvariantCulture)}",
      $"BO-7;3;{4.05m.ToString("F2", CultureInfo.InvariantCulture)}",
  ]);
  await File.WriteAllTextAsync(tmp, body, new UTF8Encoding(true));
  File.Move(tmp, file, overwrite: true);

  // read it back lazily, skipping the header
  foreach (string line in File.ReadLines(file).Skip(1))
  {
      string[] p = line.Split(';', StringSplitOptions.TrimEntries);
      if (p.Length < 3) continue;
      if (!decimal.TryParse(p[2], NumberStyles.Number,
                            CultureInfo.InvariantCulture, out decimal kg)) continue;
      Console.WriteLine($"{p[0],-10}{p[1],4}{kg,8:N2}");
  }

  File.Move(file, Path.Combine(done, Path.GetFileName(file)), overwrite: true);
  Console.WriteLine($"moved to {done}");
Line by line
  • AppContext.BaseDirectory rather than the current directory, so the demo folder lands beside the application wherever it is started from.
  • CreateDirectory twice with no Exists check — it is idempotent and creates the whole path.
  • The write is to .tmp and then File.Move onto the real name: the atomic rename, with both files in the same folder so it stays atomic.
  • new UTF8Encoding(true) emits the byte order mark, which is what lets Excel open the file correctly.
  • Both numbers are written and read with InvariantCulture, and ReadLines(...).Skip(1) streams the file lazily while dropping the header.
  • The final File.Move into done is what makes the inbox listing double as the work queue.

Now break it on purpose. Open orders.csv in Excel and run it again — the File.Move throws an IOException, which is exactly the real-world failure the try in the previous section exists for. Then swap both InvariantCulture arguments for CurrentCulture on an Italian machine and watch 18.40 become 1840 with no error at all.

Golden rules

  1. Build every path with Path.Combine. A hard-coded backslash is the commonest reason working code dies the moment it is containerised.
  2. Never build a path from user input unvalidated. Take Path.GetFileName first and confirm the resolved full path is still inside your folder — Path.Combine discards everything before a rooted argument.
  3. ReadLines, not ReadAllLines, unless you know the file is small. One is lazy and constant-memory; the other loads everything.
  4. Every stream needs a using. Without it the handle stays open and the file stays locked until the garbage collector gets round to it.
  5. Use the Async overloads inside a web application, with a cancellation token. A synchronous read blocks a pool thread for the whole round trip.
  6. Write to a temporary name in the same folder, then rename. The rename is atomic, so nothing downstream ever sees a half-written file.
  7. Numbers and dates in files are InvariantCulture, both directions. 18,40 read as 1840 throws no exception and is wrong by a factor of a hundred.
  8. Write dates with the "O" round-trip format. 03/04/2026 is March to half the world and April to the other half.
  9. UTF-8 for anything you control, and UTF-8 with a BOM for a CSV somebody will open in Excel.
  10. File.Exists is a hint, not a guard. Anything can happen between the check and the open; the try is the real protection.
  11. Every file operation can fail for reasons that are nobody's bug — a full disk, a lost share, a file open in Excel. Catch IOException and log it.
  12. File.Delete on a missing file succeeds; Directory.Delete throws. Remember it rather than trying to understand it.

Interview questions

"What is the difference between File.ReadAllLines and File.ReadLines?"

ReadAllLines reads the entire file and returns a string[], so peak memory is the file size plus a string per line. ReadLines returns a lazy IEnumerable<string> that reads as you enumerate, so memory stays constant no matter how big the file is. The loop body is identical, which is what makes this an easy win and an easy thing to get wrong: the code that worked on the test file with two hundred rows falls over on the production export with four million. I default to ReadLines unless I know the file is small and I want to close the handle immediately.

"How would you write a file that another process is watching for?"

Write to a temporary name in the same folder and then rename it onto the final name. A rename within a single volume is atomic at the filesystem level, so the watcher sees the file appear complete or not at all — it can never read a half-written one. Writing directly to the final name means the watcher will regularly pick up a partial file, and a retry loop or a delay is a guess rather than a fix. The one constraint is that the temp file has to be on the same volume; across volumes the move becomes a copy and delete, and the guarantee is gone.

"Why does your file code need using?"

Because a FileStream, StreamReader or StreamWriter holds an operating-system handle, and that is unmanaged — the garbage collector does not know it is scarce and will not hurry. Until it is disposed, the file stays locked and whatever writes to it next fails with "the process cannot access the file". A using guarantees release at the end of the scope, including on an early return and including when the body throws, which is the case that matters. It also flushes a writer — without disposal you can lose the last buffer of what you wrote, which looks like a truncated file.

"What goes wrong reading a CSV written on a machine with a different culture?"

Numbers and dates. A decimal written under it-IT is 18,40, and parsed under an English culture the comma reads as a thousands separator, so you silently get 1840 — no exception, a plausible number, and everything downstream wrong. If the file is comma-separated the same value also breaks the column count. Dates are worse, because 03/04/2026 parses successfully under both cultures and means different months. The rule I follow is that files are read by machines: InvariantCulture on both write and read, and the "O" round-trip format for dates. Separately from that there is encoding — UTF-8 for anything I control, and with a BOM if Excel will open it.

"Come gestiresti una cartella in cui un cliente deposita file di ordini?"

Elenco i file in modo lazy con EnumerateFiles, ordinati per data di creazione, così l'ordine di elaborazione è deterministico. Ogni file lo apro dentro un try, perché può essere ancora in scrittura: una IOException non è un bug, è "non è ancora pronto" e lo riprendo al giro dopo. Leggo riga per riga con ReadLines, parso sempre con InvariantCulture, e quando ho finito sposto il file in una cartella done con File.Move, così l'elenco della cartella di ingresso è anche la coda di lavoro. Se posso mettere mano a chi scrive, chiedo il pattern scrivi-come-.tmp-e-rinomina, che elimina il problema alla radice.
