Securing an API

The previous chapter built an API that anyone can call. This one is about who is allowed to, how the server knows, and the handful of mistakes that put real companies in the newspaper. None of it is exotic: authentication, authorization, and about six recurring bugs.

Why this chapter exists

The advert says "sviluppo di Web API" and stops there — but there is no such thing as an unsecured production API. Italian adverts name autenticazione, autorizzazione and JWT explicitly, and in interviews this is the standard follow-up once you have answered the REST questions well. It is also the area where a junior can look unusually strong, because most candidates can define a JWT and very few can say what it cannot do.

Authentication vs authorization

🧒 Simple

At the school gate the guard checks your face against the photo on your card. That is authentication: are you who you say you are?

Then you try to walk into the staff room. The guard knows exactly who you are — and says no anyway. That is authorization: are you allowed to do this?

Two different questions, and always in that order. You cannot decide whether someone is allowed in before you know who they are.

🎓 Professional

Authentication (AuthN) establishes identity and populates HttpContext.User with a ClaimsPrincipal. Authorization (AuthZ) evaluates a policy against that principal and the resource.

In ASP.NET Core they are two separate middlewares, and the order in Program.cs is not a style choice: 

app.UseAuthentication();   // who are you  → fills HttpContext.User
app.UseAuthorization();    // may you      → reads HttpContext.User
Line by line
  • UseAuthentication() — who are you. It reads the credential (here a bearer token), validates it, and fills HttpContext.User with a ClaimsPrincipal. It never rejects anyone: an anonymous request simply arrives with an empty identity.
  • UseAuthorization() — may you. It reads the user that the first line produced and decides. This is the one that returns 401 or 403.
  • Order is not stylistic. Authorization reads what authentication wrote, so reversing these two means every policy evaluates an empty user and denies everything — or worse, allows it, if the policy only checks for a specific failing claim.
  • Both must sit after UseRouting and before the endpoints. Authorization needs to know which endpoint matched in order to read its attributes, and it has to run before that endpoint executes.
  • 401 versus 403 falls straight out of the split: 401 means "I do not know who you are", 403 means "I know, and no". Returning 401 for a permission failure is the commonest mix-up.

Reverse them and authorization runs against an empty principal. Every request is then anonymous, every [Authorize] fails, and — worse, in some configurations — a policy written as "deny if role X" quietly passes. This is a genuinely common production bug and a favourite interview question.

What a JWT actually is

🧒 Simple

A festival wristband. It says your name and which stages you can enter, and it has a special pattern printed on it that only the festival can print. Security staff do not phone the ticket office — they just look at the pattern and know it is real.

Two things follow, and they are the whole chapter. First: anyone can read your wristband. It is not a secret, just hard to fake. Second: if you get thrown out, the wristband still looks fine until it expires — nobody can reach out and un-print it.

🎓 Professional

A JSON Web Token is three Base64Url segments joined by dots: header.payload.signature.

  • Header — the algorithm, e.g. {"alg":"HS256","typ":"JWT"}.
  • Payload — the claims: sub (subject), iss (issuer), aud (audience), exp (expiry), plus whatever you added such as roles.
  • Signature — an HMAC or RSA signature over the first two parts.

It is signed, not encrypted. The payload is Base64, which is an encoding, not a cipher — anyone holding the token can read every claim in it. The signature guarantees integrity (nobody altered it) and authenticity (it came from the holder of the key), and nothing else.

The consequence people miss: a JWT is stateless, so there is nothing to revoke. Until exp passes, a stolen or a fired-employee token is still valid. The mitigations are short lifetimes (15–60 minutes) plus a refresh token you can revoke, because the refresh token is checked against a database.

Wiring it up in ASP.NET Core

validation parameters — every one of these matters
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer           = true,   // who minted it
            ValidateAudience         = true,   // who it was minted for
            ValidateLifetime         = true,   // exp / nbf
            ValidateIssuerSigningKey = true,   // the signature itself
            ValidIssuer   = jwt.Issuer,
            ValidAudience = jwt.Audience,
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(jwt.SigningKey)),
            ClockSkew = TimeSpan.FromSeconds(30)  // default is 5 MINUTES
        };
    });
Line by line
  • AddAuthentication(JwtBearerDefaults.AuthenticationScheme) — sets the default scheme. An application can have several — cookies for the UI, bearer for the API — and the default is what runs when nothing names one.
  • TokenValidationParameters — every one of these four is a separate check, and every one can be switched off. Turning one off to make a test pass is how real breaches begin.
  • ValidateIssuer — who minted it. Without it, a token from any identity provider is accepted, including one the attacker controls.
  • ValidateAudience — who it was minted for. Without it, a perfectly valid token for a different application of yours works here too, which is a real privilege-escalation path in a suite of services.
  • ValidateLifetime — the exp and nbf claims. Note there is a default five-minute clock skew allowance, so a token is accepted slightly past its expiry; that is deliberate, and adjustable.
  • ValidateIssuerSigningKey — the signature itself, and the one that must never be off. A JWT is not encrypted: anyone can read the payload, and without a signature check anyone can also rewrite it. The alg: none family of attacks lives exactly here.
  • A JWT is signed, not secret. Never put anything in it you would not put on a postcard — the middle segment is base64, not encryption.

Turning any of the first four to false to "make it work" is how tokens from a completely different system end up being accepted. The default ClockSkew of five minutes also surprises people: a token you believe expired is still accepted for five more minutes unless you narrow it.

Roles, claims and policies

A claim is a statement about the user (role=Manager, department=Warehouse). A policy is a named rule over claims. Prefer policies at the endpoint:

named policies, not scattered role strings
// Defined once…
builder.Services.AddAuthorization(o =>
{
    o.AddPolicy(AuthorizationPolicies.CatalogManager, p =>
        p.RequireRole("Admin", "CatalogManager"));
});

// …referenced everywhere.
app.MapPost("/products", CreateProduct)
   .RequireAuthorization(AuthorizationPolicies.CatalogManager);
Line by line
  • AddPolicy(name, p => ...) — the policy is defined once, centrally, and referenced by name everywhere else.
  • AuthorizationPolicies.CatalogManager — a constant rather than a string literal. A typo in a policy name is not a compile error: the endpoint just fails closed, or worse, is silently unprotected if the attribute is missed entirely.
  • p.RequireRole("Admin", "CatalogManager") — multiple roles are OR, not AND. Either role satisfies it, which is what people usually want and occasionally do not.
  • Policies beat scattering [Authorize(Roles = "...")] everywhere. When the rule changes you edit one line rather than grepping for a string, and the policy can later become "role or claim or resource check" without touching a single endpoint.
  • .RequireAuthorization(...) — the minimal-API spelling of [Authorize]. Attach it to a whole route group and every endpoint inside inherits it — which is the safer default, because it fails closed when someone adds an endpoint and forgets.

Why this and not [Authorize(Roles = "Admin,CatalogManager")] on twenty endpoints? Because when the rule changes to "must have the catalog:write scope" or "must be in this Entra ID group", you edit one policy definition instead of finding every endpoint. That is Open/Closed applied to security. This repository does it in Authentication.cs.

The mistakes that actually ship

⚠ 1. Broken object-level authorization (IDOR)

The endpoint checks that you are logged in. It does not check that /orders/1042 is yours. Change the number in the URL and read a competitor's order. This is number one on the OWASP API list, it is trivially exploitable, and no amount of correct JWT configuration prevents it. 

// ✗ authenticated, but not authorized for THIS row
var order = await db.Orders.FindAsync(id);

// ✓ ownership is part of the query, not an afterthought
var order = await db.Orders
    .Where(o => o.Id == id && o.CustomerId == currentUserCustomerId)
    .FirstOrDefaultAsync(ct);
Line by line
  • db.Orders.FindAsync(id) — authenticated but not authorized for this row. The user is genuinely logged in and genuinely has the role; they are simply reading somebody else's order.
  • This is IDOR — insecure direct object reference — and it is one of the most common real API vulnerabilities. Change the number in the URL and read another customer's data.
  • && o.CustomerId == currentUserCustomerId — ownership is part of the query, not a check afterwards. It cannot be forgotten on one code path, and there is no window between reading and checking.
  • FirstOrDefaultAsync returning null — and the correct response is 404, not 403. Saying "forbidden" confirms the order exists, which leaks information to anyone probing ids.
  • Role checks are not enough on their own. Roles answer "may you do this kind of thing"; only the data can answer "may you do it to this".

Return 404 rather than 403 when even confirming the row exists would leak something.

⚠ 2. Over-posting / mass assignment

Binding the request body straight onto your entity means a caller can send {"total": 10, "isApproved": true} and set fields you never intended to expose. The fix is the same DTO discipline from chapter 14: bind to a request model containing exactly the fields a client may set, then map.

⚠ 3. Secrets in appsettings.json

A signing key in a committed config file is a signing key in your git history forever, and anyone holding it can mint a token for any user with any role. Locally use dotnet user-secrets; in production use environment variables or Key Vault with a managed identity — see chapter 29. If one has already been committed, rotating the key is the fix; deleting the line is not.

⚠ 4. AllowAnyOrigin plus credentials

CORS is a browser mechanism, not a firewall — it never protects the server, it only tells browsers which sites may read the response. Widening it to AllowAnyOrigin().AllowAnyHeader().AllowCredentials() to stop an error message means any website your user visits can call your API with their cookies. Name your origins. (CORS is explained from the browser side in chapter 17.)

⚠ 5. Errors that explain too much

A stack trace, a SQL fragment or "user not found" versus "wrong password" all hand something over. Return Problem Details with a trace id, log the detail server-side, and let support correlate the two. This repository does it in GlobalExceptionHandler.cs.

Two more, covered elsewhere because they belong there: SQL injection is parameterisation, in chapter 10 — and is largely ended by EF Core, with the exception of FromSqlRaw and string-concatenated SQL. CSRF matters for cookie-authenticated server-rendered forms, in chapter 16; a bearer-token API is not vulnerable to it, because the browser does not attach the header automatically.

If you ever store a password

🎓 Professional

First: try not to. ASP.NET Core Identity, Entra ID or any OpenID Connect provider has solved this, and the reputational downside of doing it yourself badly is enormous.

If you must: hash with a deliberately slow, salted algorithm — Argon2id, bcrypt, scrypt, or PBKDF2 (what Identity uses by default). Never MD5 or plain SHA-256: they are fast, which is exactly wrong — a modern GPU tries billions of SHA-256 guesses per second. Never "encrypt" passwords, because encryption is reversible and hashing is the point. And compare hashes with a fixed-time comparison so response timing does not leak.

Try it yourself

Prove to yourself that a JWT is readable. Mint one, then take it apart:

dotnet user-jwts create --project src/LogiFlow.Api --role CatalogManager
# copy the token it prints, then decode the middle segment:
echo '<paste-the-payload-segment>' | base64 -d
Line by line
  • dotnet user-jwts create — a built-in tool that mints a development token and configures the API to trust it. No identity provider needed to test an endpoint.
  • --role CatalogManager — adds a role claim, so you can exercise the policy from the previous block.
  • # — a shell comment.
  • base64 -d — decodes the payload, and this is the exercise. A JWT is three dot-separated base64 segments: header, payload, signature. Decoding the middle one requires no key and no permission.
  • Do it once and the lesson sticks. Everything in that token — the user id, the roles, the expiry — is readable by anyone holding it, including the browser it was sent to and anything that logged the header.
  • The signature is what makes it trustworthy, not private. Tampering is detected; reading is not, and never can be.

You will see your own claims in plain JSON, with no key and no tooling. Now change one character anywhere in the token, call the API with it, and watch the 401: readable, but not forgeable. Then set ValidateAudience = false, call it with a token minted for a different audience, and watch it sail through — that is what those four booleans are for.

Golden rules

  1. UseAuthentication() before UseAuthorization(). Always.
  2. 401 = I do not know you. 403 = I know you, and no.
  3. A JWT is signed, not encrypted. Assume the payload is public.
  4. Nothing secret in a token, and nothing you cannot bear to have read.
  5. Short-lived access token plus a revocable refresh token. There is no other way to revoke.
  6. Validate issuer, audience, lifetime and signing key. Turning one off to "fix" a bug is the bug.
  7. Check ownership of the row, not just the presence of a token.
  8. Bind to a request DTO, never to the entity.
  9. Secrets come from user-secrets, environment variables or Key Vault — never from a committed file.
  10. Name your CORS origins. CORS protects browsers, not servers.
  11. Hash passwords slowly and with a salt; never encrypt them.
  12. Errors return a trace id to the caller and the detail to the log.

Interview questions

"Che differenza c'è fra autenticazione e autorizzazione?"

Identity versus permission — but do not stop at the definition. Add the ASP.NET Core detail: they are two middlewares, the order is fixed, the first fills HttpContext.User and the second reads it, and swapping them is a real production bug. That second sentence is what separates you from the other candidates.

"Is a JWT encrypted?"

No — signed. Base64 is an encoding; anyone holding the token can read every claim. The signature proves integrity and authenticity only. Then volunteer the consequence, because it is the real question underneath: you cannot revoke a stateless token, so you keep lifetimes short and pair it with a refresh token that is checked against storage.

"How would you stop a user reading someone else's order?"

Make ownership part of the query rather than a check after loading, and prefer 404 to 403 where existence itself is sensitive. Name it: broken object-level authorization, OWASP API number one. Add that [Authorize] alone never prevents it, because it validates the token, not the row.

"Where do you keep the signing key?"

Not in the repository. dotnet user-secrets locally, environment variables or Azure Key Vault accessed with a managed identity in production, so no credential exists to leak. If asked what to do about one already committed: rotate it — removing the line does not remove it from history.

"Does CORS make my API secure?"

No, and the question is testing exactly that. CORS is enforced by the browser and tells it which origins may read a response. A script, curl or Postman ignores it entirely. Authorization is what secures the API; CORS just decides which web pages may consume it.
