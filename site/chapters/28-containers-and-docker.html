Containers and Docker

You have already used containers in this site half a dozen times: every "try it yourself" that started SQL Server, Redis or Elasticsearch was one docker run. This chapter explains what was actually happening, and how to put your own application inside one.

Why this chapter exists

"Docker" and "microservizi" travel together through adverts in Milano and Bologna, and containers are the thing that makes a CI pipeline (chapter 30) reproducible. It is also, honestly, the fastest way to stop saying "it works on my machine" — which is the sentence this entire technology exists to eliminate.

What a container actually is

🧒 Simple

Think about moving house. One way: pack everything loose into a van and hope the new house has the right shelves. The other way: put everything in a sealed crate that includes its own shelves. Anywhere the crate goes, the contents are already arranged correctly.

A container is the crate. Your program, the exact .NET version it needs, and its files — all sealed together. The computer it lands on does not need .NET installed. It just needs to be able to open crates.

🎓 Professional

A container is a process on the host kernel, isolated using Linux namespaces (its own view of the filesystem, network, and process table) and limited with cgroups (CPU, memory).

The distinction people get wrong: a container is not a virtual machine. A VM virtualises hardware and runs a whole guest kernel — gigabytes, and tens of seconds to boot. A container shares the host kernel and ships only the userland it needs — tens of megabytes, and milliseconds to start. That difference in start-up cost is precisely what makes disposable test databases and per-request scaling practical.

Two nouns to keep separate: an image is the immutable, layered template; a container is a running instance of one. Same relationship as a class and an object.

A Dockerfile for a .NET API

This repository ships a docker-compose.yml for its dependencies (SQL Server, Redis, Elasticsearch) but no Dockerfile for the API itself, because the course runs it with dotnet run. Here is the one you would add, and every line in it is a decision:

Dockerfile — multi-stage, cache-friendly, non-root
# ── build stage: has the full SDK, ~800 MB. Thrown away at the end. ──
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

# Copy ONLY the project files first, then restore. This layer is cached
# until a .csproj changes — so an ordinary code edit skips restore entirely.
COPY Directory.Build.props Directory.Packages.props global.json ./
COPY src/LogiFlow.Api/*.csproj            src/LogiFlow.Api/
COPY src/LogiFlow.Application/*.csproj    src/LogiFlow.Application/
COPY src/LogiFlow.Domain/*.csproj         src/LogiFlow.Domain/
COPY src/LogiFlow.Infrastructure/*.csproj src/LogiFlow.Infrastructure/
RUN dotnet restore src/LogiFlow.Api/LogiFlow.Api.csproj

# Now the source. Changing a .cs file invalidates from here down only.
COPY . .
RUN dotnet publish src/LogiFlow.Api/LogiFlow.Api.csproj -c Release -o /app --no-restore

# ── runtime stage: no SDK, no source, no NuGet cache. ~110 MB. ──
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
COPY --from=build /app .

# Run as a non-root user. The default in the image is root, and a container
# escape from root is a much worse day than one from an unprivileged user.
USER $APP_UID

ENV ASPNETCORE_HTTP_PORTS=8080
EXPOSE 8080
ENTRYPOINT ["dotnet", "LogiFlow.Api.dll"]
🎓 Why the two stages

Without them your production image contains the SDK, your source code, the NuGet cache and any build secrets — around 800 MB of attack surface for an application that needs 110 MB to run. Multi-stage builds mean the final image contains the published output and nothing else.

And the COPY *.csproj before COPY . . is not fussiness. Docker caches each instruction's layer and invalidates everything after the first change. Copying source first means every build re-downloads every NuGet package — the difference between a 15-second and a 3-minute CI build, on every commit, forever.

Compose, for everything your app needs

One container is rarely the point. Compose describes a set of them, on a shared network, in one file — which is exactly what docker-compose.yml in this repository does: 

services:
  sql:
    image: mcr.microsoft.com/mssql/server:2022-latest
    environment: { ACCEPT_EULA: "Y", MSSQL_SA_PASSWORD: "Str0ng!Passw0rd" }
    ports: ["1433:1433"]              # host:container
    volumes: [sqldata:/var/opt/mssql]  # survives `down`, not `down -v`
    healthcheck: { ... }               # "started" ≠ "ready to accept connections"

  redis:
    image: redis:7-alpine
    ports: ["6380:6379"]              # shifted: 6379 is often already taken

Two details worth internalising. Service names are hostnames on the compose network: from another container the connection string is Server=sql,1433, not localhost — inside a container, localhost means that container. And healthchecks matter: SQL Server accepts a TCP connection several seconds before it will accept a login, so depends_on without condition: service_healthy produces a race that fails only on slow machines and in CI.

The commands you will actually type

CommandDoes
docker build -t logiflow-api .Build an image from the Dockerfile here
docker run -d -p 8080:8080 logiflow-apiRun it detached, host 8080 → container 8080
docker ps / docker ps -aRunning containers / including stopped ones
docker logs -f <id>Follow its stdout — your first debugging move
docker exec -it <id> shA shell inside the container
docker compose up -dStart everything in the compose file
docker compose down -vStop and delete the volumes — your data is gone
docker image prune -aReclaim the tens of GB Docker has quietly taken
⚠ The four that bite everybody
  • :latest — not a version, just a default tag. Your build is then irreproducible: the image that passed CI on Tuesday is not the one that deploys on Thursday. Pin a real tag.
  • Running as root — the default. One USER $APP_UID line.
  • Secrets baked into the image — a connection string in a COPY'd config file or an ENV is in a layer forever, and anyone who can pull the image can read it. Secrets are injected at run time.
  • localhost inside a container — refers to the container, not your machine. Use the compose service name, or host.docker.internal to reach the host.

And Kubernetes?

🧒 Simple

Docker is knowing how to make one sandwich. Kubernetes is running the whole sandwich shop: deciding how many people are making sandwiches right now, replacing anyone who faints, and putting up a bigger sign when the queue grows.

🎓 Professional

Kubernetes is an orchestrator: you declare desired state (five replicas of this image, this much memory, restart on failure, route traffic here) and it continuously reconciles reality towards it. It adds scheduling, service discovery, rolling deploys, autoscaling and secret management.

It also adds a great deal of operational cost, and for one .NET API with a SQL Server behind it, Azure App Service or Azure Container Apps does the useful 90% with none of it. Being able to say that in an interview is worth more than reciting the object model — juniors who have "done Kubernetes" from a tutorial are common; juniors who can say when not to reach for it are not.

Try it yourself

Save the Dockerfile above to the repository root, then:

docker build -t logiflow-api .
docker images logiflow-api          # see the size — should be ~110 MB, not ~800 MB
docker compose up -d                # the dependencies
docker run --rm -p 8080:8080 \
  --network logiflow_default \
  -e "ConnectionStrings__Default=Server=sql,1433;Database=LogiFlow;User Id=sa;Password=Str0ng!Passw0rd;TrustServerCertificate=true" \
  logiflow-api

Note the double underscore: ConnectionStrings__Default is how a nested appsettings.json key becomes an environment variable, and it is the mechanism every container platform uses to configure a .NET app. Then run the build a second time, changing nothing, and watch every layer report CACHED. Now edit one .cs file and build again — restore is still cached, compile is not. That is what the COPY *.csproj ordering bought you.

Golden rules

  1. An image is the template; a container is a running instance of it.
  2. A container is a process, not a virtual machine. No guest kernel.
  3. Multi-stage builds: the SDK never reaches production.
  4. Copy .csproj files and restore before copying source. Cache order is build time.
  5. Never :latest. Pin the tag or your build is not reproducible.
  6. USER $APP_UID. Root by default is a choice you did not make on purpose.
  7. Configuration and secrets come in at run time, never baked into a layer.
  8. ConnectionStrings__Default — double underscore for nested config keys.
  9. Service names are hostnames. localhost inside a container is the container.
  10. Healthchecks plus condition: service_healthy, or you have a race in CI.
  11. docker compose down -v deletes your volumes. Read the flag before you type it.
  12. Containers are cattle: never store state inside one. Volumes or a database.

Interview questions

"Qual è la differenza fra un container e una macchina virtuale?"

A VM virtualises hardware and runs its own kernel; a container is an isolated process sharing the host kernel. Then give the consequence rather than stopping at the definition: megabytes instead of gigabytes, milliseconds instead of seconds — which is why a disposable SQL Server per test run is realistic and a disposable VM per test run is not.

"Why is a Dockerfile multi-stage?"

So the SDK, the source and the NuGet cache stay out of the shipped image — roughly 800 MB down to 110 MB, and a much smaller attack surface. If they follow up on build speed, the answer is layer caching: copy the project files and restore before copying source, or every commit re-downloads every package.

"How do you get configuration into a container?"

Environment variables at run time, with __ for nested keys (ConnectionStrings__Default), and secrets from the platform's secret store — Key Vault with a managed identity on Azure. Say explicitly what you do not do: bake a connection string into a layer, because anyone who can pull the image can read it.

"My container starts and immediately exits. Why?"

A container lives exactly as long as its main process. If the entrypoint finishes — or crashes on startup — the container stops. First move is always docker logs <id>; for a .NET API the usual culprits are a missing connection string, a port already bound, or a startup exception. Answering this well signals you have actually run containers rather than read about them.

"Do you know Kubernetes?"

Be honest about the level, then show judgement. Something like: "I understand what it does — declarative desired state, scheduling, rolling deploys — and I have run things locally, but I have not operated a production cluster. For a single API I would reach for App Service or Container Apps first." That answer is respected; an overclaim collapses on the next question.
