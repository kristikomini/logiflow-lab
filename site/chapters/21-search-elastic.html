Search with ElasticSearch / OpenSearch

A relational database answers "which rows match exactly?". A search engine answers "which documents are most relevant?" — a different question, needing a different data structure. Understanding why LIKE '%…%' cannot be made fast is most of this chapter.

From the advert

"Esperienza con sistemi di ricerca (ElasticSearch/OpenSearch)." The slash matters: OpenSearch is Amazon’s open-source fork of Elasticsearch 7.10, created in 2021 after a licence change. For everything in this chapter they behave the same way.

Why LIKE stops being enough

the query every project starts with
SELECT * FROM dbo.Products WHERE Name LIKE '%pompa idraulica%';

Four separate problems, and none of them is fixable with an index:

  1. It cannot use an index. A leading % means the engine has no prefix to seek on, so it scans every row — and it gets linearly worse as you grow. (Chapter 11.)
  2. It is literal. "pompa idraulica" does not match "pompe idrauliche". A plural defeats it.
  3. It has no notion of better. Every matching row is equally matching. There is no "most relevant first".
  4. It is unforgiving. A user typing "pompa idralica" gets nothing at all.
🧒 Simple

You want every page in a big book that talks about elephants. You could read all five hundred pages, every time somebody asks. That is LIKE.

Or, once, you could go through the book and write a list: "elephant — pages 12, 88, 312", "lion — pages 4, 91". After that, any question is answered instantly by reading your list instead of the book.

That backwards list — from words to pages, instead of from pages to words — is called an inverted index, and it is the whole idea.

text vs keyword — the mapping decision that matters

a mapping, with an Italian analyzer
PUT /products
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",              // analysed → for searching
        "analyzer": "italian",       // Italian stemming + stop words
        "fields": {
          "keyword": { "type": "keyword" }   // NOT analysed → sort, filter, aggregate
        }
      },
      "category": { "type": "keyword" },   // exact values only
      "price":    { "type": "double" },
      "inStock":  { "type": "boolean" },
      "createdAt":{ "type": "date" }
    }
  }
}
⚠ The mistake everyone makes once

A text field is broken into tokens, so you cannot sort or group by it — "Pompa Idraulica" was stored as pomp and idraul, and there is no original string left to sort. A keyword field is stored whole and untouched, so it is exact-match only and useless for real searching.

The answer is the multi-field above: index the same value both ways, then use name for matching and name.keyword for sorting, filtering and aggregating.

🎓 Why the Italian analyzer is not a detail here

Italian is heavily inflected. The italian analyzer applies Italian stop words (di, che, per, il…), a light stemmer that reduces idrauliche / idraulici / idraulico to a common stem, and elision handling for l’acqua → acqua. With the default standard analyzer, a search for "pompe" simply will not find "pompa" — and that is what a user will report as "the search is broken".

Querying

match, term, and bool
POST /products/_search
{
  "query": {
    "bool": {
      // must → contributes to the relevance score
      "must": [
        { "match": { "name": "pompe idrauliche" } }
      ],
      // filter → yes/no only. No scoring, and cacheable — much faster.
      "filter": [
        { "term":  { "category": "ricambi" } },
        { "range": { "price": { "lte": 500 } } },
        { "term":  { "inStock": true } }
      ],
      // should → optional; a match pushes the document up the list
      "should": [
        { "match": { "brand": "bosch" } }
      ],
      "must_not": [
        { "term": { "discontinued": true } }
      ]
    }
  },
  "from": 0, "size": 20,
  "sort": [ "_score", { "name.keyword": "asc" } ],
  "highlight": { "fields": { "name": {} } }
}
ClauseEffectUse for
matchAnalyses the query text, then matches tokensWhat the user typed
termExact, unanalysedkeyword, numbers, booleans, ids
mustRequired, and scoredThe search phrase
filterRequired, not scored, cachedEvery facet and toggle. Prefer this.
shouldOptional, boosts scorePreferences: same brand, in stock, recent
fuzzinessTolerates typos (edit distance)"fuzziness": "AUTO" for user-facing search boxes

Relevance is scored with BM25: a term counts for more when it appears often in this document (term frequency) and rarely across the whole index (inverse document frequency). That is why "idraulica" — present in half your catalogue — contributes far less than a specific part number.

From C#

the Elastic.Clients.Elasticsearch client
builder.Services.AddSingleton(_ =>
{
    var settings = new ElasticsearchClientSettings(new Uri(cfg["Elastic:Url"]!))
        .DefaultIndex("products");
    return new ElasticsearchClient(settings);
});

public async Task<IReadOnlyList<ProductDto>> SearchAsync(
    string text, string? category, CancellationToken ct)
{
    var response = await _client.SearchAsync<ProductDocument>(s => s
        .Index("products")
        .Query(q => q.Bool(b => b
            .Must(m => m.Match(mm => mm
                .Field(f => f.Name)
                .Query(text)
                .Fuzziness(new Fuzziness("AUTO"))))
            .Filter(f => f.Term(t => t
                .Field(ff => ff.Category)
                .Value(category ?? "")))))
        .Size(20), ct);

    if (!response.IsValidResponse)
    {
        _log.LogError("Search failed: {Debug}", response.DebugInformation);
        // degrade: fall back to a SQL query rather than showing an error page
        return await _sqlFallback.SearchAsync(text, category, ct);
    }

    return response.Documents.Select(d => d.ToDto()).ToList();
}

Keeping it in sync — the real hard part

🎓 Professional

SQL Server remains the source of truth. The search index is a derived, eventually consistent projection of it — and treating it as anything else is the root of most production problems with search. Never write only to Elasticsearch, and never read a value from it that must be exactly right at that instant (a price at checkout, a stock level at reservation): search to find the ids, then read the authoritative row from SQL.

StrategyHowTrade-off
Dual writeWrite to SQL and Elastic in the same method Simple, and wrong under failure: the second write can fail after the first succeeded, leaving them permanently divergent.
OutboxWrite an event row in the same SQL transaction; a worker publishes it The correct default. Atomic with the business data, retryable, at-least-once.
Periodic reindexA job re-reads changed rows every N minutes Easy and robust; staleness is bounded by N. Often enough.
CDCChange Data Capture / Debezium reads the transaction log No application changes; more infrastructure to own.
Reindexing without downtime

Mappings are largely immutable — you cannot change a field’s type in place. The standard move is an alias: the application always queries products, which is an alias pointing at products_v3. To change the mapping you build products_v4 alongside it and atomically repoint the alias. Zero downtime, and instant rollback. This is a very good thing to know.

Golden rules

  1. SQL answers "which rows match". A search engine answers "which documents are most relevant". Different questions.
  2. LIKE '%x%' cannot use an index and cannot rank. That is why this technology exists.
  3. The inverted index maps terms → documents. That inversion is the whole trick.
  4. The same analyzer must run at index time and query time, or the two never meet.
  5. Use the Italian analyzer for Italian text. The default will not match plurals.
  6. text to search, keyword to sort, filter and aggregate. Index both with a multi-field.
  7. Prefer filter to must for anything not contributing to relevance — it is unscored and cached.
  8. SQL Server stays the source of truth. The index is a derived, eventually consistent projection.
  9. Sync with an outbox, not a dual write. A dual write diverges the first time the second call fails.
  10. Never read a value that must be exact from the index. Search for ids, then read the row.
  11. Use aliases so you can reindex and repoint atomically.
  12. Search must degrade gracefully. If the cluster is down, fall back to a SQL query rather than an error page.

Interview questions

"Why not just use LIKE?"

A leading wildcard cannot use an index, so it scans; it is literal, so plurals and typos fail; and it cannot rank results. Full-text search solves all three with an inverted index and relevance scoring.

"What is an inverted index?"

A map from term to the list of documents containing it, plus frequency information for scoring. It is built once at index time so that queries never scan the documents themselves.

"text or keyword?"

text is analysed into tokens for searching and therefore cannot be sorted; keyword is stored whole for exact matching, sorting and aggregation. Use a multi-field to get both from one value.

"How do you keep the index in sync with the database?"

Outbox pattern: write the event in the same transaction as the business data, then a worker publishes it — atomic and retryable. Reject the dual write explicitly, because the second call can fail after the first committed. And say plainly that the index is eventually consistent, so anything requiring exactness is read from SQL.

"What is the difference between Elasticsearch and OpenSearch?"

OpenSearch is AWS’s fork of Elasticsearch 7.10, created after Elastic changed the licence away from Apache 2.0 in 2021. The core concepts, query DSL and analyzers are the same; the clients and newer features have diverged. For work at this level they are interchangeable.
