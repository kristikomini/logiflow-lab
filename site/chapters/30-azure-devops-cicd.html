Azure DevOps and CI/CD

The difference between a team that deploys on a Tuesday afternoon and a team that deploys on a Friday night with everyone watching is not talent. It is a pipeline that runs the same way every time, and that anyone can read.

From the advert

"Familiarità con … strumenti di CI/CD (Azure DevOps)." Azure DevOps specifically, rather than GitHub Actions, is the norm in Italian enterprise .NET — often alongside on-premises TFS history.

What CI and CD actually mean

🧒 Simple

Four people are building one Lego castle, each working on their own piece at home. If they only bring the pieces together at the very end, nothing fits and everyone blames everyone.

So instead they meet every single day and click the pieces together. If something does not fit, they find out that day, when it is one small mistake — not in three months, when it is a hundred tangled ones.

That daily meeting is continuous integration. Doing it automatically, on every change, is what a pipeline is.

🎓 Professional
  • Continuous Integration — every push builds and runs the tests on a clean agent. The value is not automation; it is the short feedback loop, and the fact that "it works on my machine" stops being an argument.
  • Continuous Delivery — every successful build produces an artifact that could be released. A human decides when.
  • Continuous Deployment — it goes automatically. Needs real test coverage and real monitoring to be sane.

Most enterprise teams do CI plus continuous delivery: automatic to a test environment, an approval gate before production. Saying which one you have practised, and why, is a better answer than reciting the definitions.

A pipeline, in full

azure-pipelines.yml
trigger:
  branches:
    include: [ main, 'release/*' ]

pr:
  branches:
    include: [ main ]          # validate every pull request too

variables:
  buildConfiguration: 'Release'

stages:
# ───────────────────────── BUILD ─────────────────────────
- stage: Build
  jobs:
  - job: BuildAndTest
    pool:
      vmImage: 'ubuntu-latest'
    steps:
    - task: UseDotNet@2
      inputs:
        useGlobalJson: true          # the SDK pin from chapter 01

    - script: dotnet restore
      displayName: Restore

    - script: dotnet build --no-restore -c $(buildConfiguration)
      displayName: Build

    - script: |
        dotnet test --no-build -c $(buildConfiguration) \
          --logger trx --collect:"XPlat Code Coverage"
      displayName: Test

    - task: PublishTestResults@2
      condition: succeededOrFailed()   # publish results even when tests fail
      inputs:
        testResultsFormat: VSTest
        testResultsFiles: '**/*.trx'

    # the database change, as a reviewable script — not Database.Migrate() (ch. 09)
    - script: |
        dotnet tool install --global dotnet-ef
        dotnet ef migrations script --idempotent \
          -p src/LogiFlow.Infrastructure -s src/LogiFlow.Api \
          -o $(Build.ArtifactStagingDirectory)/migrate.sql
      displayName: Generate migration script

    - script: dotnet publish src/LogiFlow.Api -c $(buildConfiguration)
                --no-build -o $(Build.ArtifactStagingDirectory)/app
      displayName: Publish

    - publish: $(Build.ArtifactStagingDirectory)
      artifact: drop

# ───────────────────────── DEPLOY ────────────────────────
- stage: DeployTest
  dependsOn: Build
  condition: succeeded()
  jobs:
  - deployment: Test
    environment: 'logiflow-test'       # environments carry approvals and checks
    strategy:
      runOnce:
        deploy:
          steps:
          - task: SqlAzureDacpacDeployment@1
            inputs: { deployType: SqlTask, sqlFile: '$(Pipeline.Workspace)/drop/migrate.sql' }
          - task: AzureWebApp@1
            inputs:
              appName: app-logiflow-api-test
              package: '$(Pipeline.Workspace)/drop/app'

- stage: DeployProd
  dependsOn: DeployTest
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
  - deployment: Prod
    environment: 'logiflow-prod'       # ← the approval gate lives on this
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureWebApp@1
            inputs:
              appName: app-logiflow-api-prod
              deployToSlotOrASE: true
              slotName: staging
              package: '$(Pipeline.Workspace)/drop/app'
          - task: AzureAppServiceManage@0
            inputs: { action: 'Swap Slots', sourceSlot: staging }

Database changes are the hard part

⚠ During a slot swap, two versions run at once

For a few seconds the old code and the new code both talk to the same schema. So a migration that drops or renames a column breaks the version still serving traffic.

The discipline is expand / contract, across two releases:

  1. Expand — add the new column, nullable. Deploy code that writes both old and new and reads whichever is present.
  2. Backfill the data.
  3. Contract — in the next release, once nothing reads the old column, drop it.

Slower, and the only way to change a schema without a maintenance window. Describing this is one of the strongest things you can say in a deployment question.

Branch policies — where quality is actually enforced

A pipeline that runs after merging tells you what broke. A branch policy stops it being merged. On main, the standard set:

  • Require a pull request — no direct pushes.
  • At least one reviewer approval, and reset approvals when new commits are pushed.
  • The build must succeed, including the tests.
  • All comments resolved.
  • A linked work item — the audit trail.
  • Merge strategy fixed (squash is common) so history stays readable.

Secrets in pipelines

  • Variable groups linked to Key Vault, so the pipeline never stores the secret itself.
  • Service connections with a workload identity federation, rather than a long-lived service principal secret.
  • Secret variables are masked in logs — and are not passed to pipelines triggered by a pull request from a fork, deliberately.
  • Never echo a secret to diagnose it. The masking is best-effort.

Infrastructure as code

Anything you clicked in the Azure portal is undocumented and unreproducible. Bicep is the Azure-native option and reads far better than raw ARM templates.

main.bicep — a fragment
param location string = resourceGroup().location
param appName  string

resource plan 'Microsoft.Web/serverfarms@2023-01-01' = {
  name: 'plan-${appName}'
  location: location
  sku: { name: 'P1v3' }
  properties: { reserved: true }
}

resource web 'Microsoft.Web/sites@2023-01-01' = {
  name: 'app-${appName}'
  location: location
  identity: { type: 'SystemAssigned' }      // managed identity (ch. 18)
  properties: {
    serverFarmId: plan.id
    siteConfig: { linuxFxVersion: 'DOTNETCORE|10.0', alwaysOn: true }
  }
}
Try it yourself

Azure DevOps is free for small teams, and so is GitHub Actions — the concepts transfer exactly, so use whichever you can sign into.

  1. Push a small .NET project and add a pipeline that restores, builds and tests.
  2. Break a test deliberately and push. Watch the build go red and the PR become unmergeable. That feedback loop is the entire point.
  3. Add dotnet format --verify-no-changes and push badly formatted code.
  4. Add a second stage with an environment and an approval, and watch the pipeline wait for you.
  5. Publish an artifact in stage one and consume it in stage two — prove to yourself it is the same build.

Golden rules

  1. Build once, deploy many. The artifact you tested is the artifact you ship.
  2. Configuration differs between environments; the build does not.
  3. Pipelines live in YAML in the repository, versioned and reviewed with the code.
  4. Branch policies are where quality is enforced. A pipeline alone only reports.
  5. Every rule a human would have to remember becomes a build step.
  6. Keep CI under about ten minutes. Slower than that and people stop waiting for it.
  7. A red build is the top priority. A build that is red "normally" is worth nothing.
  8. Migrations run as a reviewed script from the pipeline, never from application startup.
  9. Schema changes are expand/contract across two releases. Two versions run at once during a swap.
  10. Secrets come from Key Vault via variable groups, never from the YAML.
  11. Automate rollback and practise it. An untested rollback is a hope.
  12. Infrastructure in Bicep or Terraform. Anything created by clicking is undocumented.

Interview questions

"What is the difference between continuous delivery and continuous deployment?"

Delivery means every build is releasable and a human chooses when; deployment means it goes automatically. Then say which one the situation warrants — automatic to production needs the test coverage and monitoring to back it up.

"How do you handle database migrations in a deployment?"

Generate an idempotent script at build time, review it, and run it as an explicit pipeline step before deploying the code. Never Database.Migrate() at startup — instances race and nobody reviewed the DDL. Then expand/contract for anything destructive.

"A deployment broke production. What do you do?"

Restore service first — swap the slot back — then diagnose, because investigating while users are down is the wrong order. Afterwards: a regression test that would have caught it, and a blameless look at why the pipeline let it through. Interviewers listen for whether "rollback" comes before "root cause".

"What would you put in a build pipeline besides compile and test?"

Format verification, static analysis, dependency vulnerability scanning, secret scanning, and publishing test results and coverage. The principle worth stating: anything a reviewer would otherwise have to remember should be a build step.

"Why keep the pipeline in YAML rather than the classic editor?"

It is versioned with the code, reviewable in a pull request, branchable, and reproducible. A UI-defined pipeline has no history and no review, and cannot differ per branch.
