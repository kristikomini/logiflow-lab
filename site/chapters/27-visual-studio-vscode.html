Visual Studio and VS Code

"Utilizzo fluido" does not mean knowing where the menus are. It means you can find a bug in code you have never seen, in an application you did not start, without adding a single Console.WriteLine. That skill is visible within ten minutes of pair programming.

From the advert

"Utilizzo fluido di Visual Studio e/o VS Code." The e/o means either is fine. What is not fine is being unable to debug.

Debugging — the part that matters

🧒 Simple

Imagine watching a film and being able to pause it at any moment, walk into the scene, and open every character’s pockets to see what they are carrying. Then press play for one single frame and look again.

That is a debugger. People who have not learned to use one are stuck shouting questions at the screen and hoping the film answers — which is what Console.WriteLine really is.

Breakpoints that do more than stop

This is where "fluent" starts. A plain breakpoint in a loop over ten thousand orders is useless; these are not.

KindHowUse it to
ConditionalRight-click the breakpoint → Conditions → order.Id == 4471 Stop only on the one row that is wrong.
Hit countConditions → Hit Count → = 500 Stop on the 500th iteration.
TracepointActions → "Log a message", {order.Id} = {order.Total} Print without stopping — Console.WriteLine with no recompile and no code change.
ExceptionDebug → Windows → Exception Settings Break the moment an exception is thrown, before anything catches and hides it.
Data breakpointRight-click a field in Locals (C++, and .NET via the Watch window in recent versions) Break when a value changes, when you do not know who is changing it.
🎓 The exception settings window is the underused one

A swallowed exception — catch (Exception) { } somewhere in a library, or a try that logs at Debug level — is invisible in normal running. Ticking "Common Language Runtime Exceptions" in Exception Settings makes the debugger break at the throw, before any handler runs, so you see the original stack and the original values. It is the single fastest way to diagnose "it just returns null and I do not know why".

A method for finding bugs

🎓 Professional

Debugging is not poking at code until it works. It is a loop, and saying it out loud in an interview is worth more than any shortcut:

  1. Reproduce it reliably. A bug you cannot reproduce is a bug you cannot confirm you have fixed. Ideally, reproduce it in a failing test.
  2. Form a hypothesis. "The total is wrong because the discount is applied twice." Specific, and falsifiable.
  3. Find the smallest observation that would disprove it. One conditional breakpoint, one watch expression.
  4. Bisect. Halve the search space each time — in the call stack, or across history with git bisect.
  5. Fix the cause, not the symptom. Then keep the test.

Candidates who describe this look experienced. Candidates who say "I add logging and look" describe step 3 only.

VS Code for .NET

.vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug API",
      "type": "coreclr",
      "request": "launch",
      "preLaunchTask": "build",
      "program": "${workspaceFolder}/src/LogiFlow.Api/bin/Debug/net10.0/LogiFlow.Api.dll",
      "cwd": "${workspaceFolder}/src/LogiFlow.Api",
      "env": { "ASPNETCORE_ENVIRONMENT": "Development" },
      "serverReadyAction": {
        "action": "openExternally",
        "pattern": "\\bNow listening on:\\s+(https?://\\S+)"
      }
    },
    {
      "name": "Attach to process",
      "type": "coreclr",
      "request": "attach"
    }
  ]
}
Line by line
  • This is .vscode/launch.json, JSON with no comments.
  • "type": "coreclr" — the .NET debugger. It is what the C# extension installs, and the wrong value here is why "nothing happens on F5".
  • "request": "launch" — start the process. The alternative is "attach", for debugging something already running such as a container.
  • "preLaunchTask": "build" — runs a task from tasks.json first. Without it you debug the previous build and wonder why a breakpoint moved.
  • "program" — the DLL, not the project. The path embeds Debug and net10.0, so it breaks on a framework upgrade — an unpleasant five minutes.
  • ${workspaceFolder} — a variable substituted by VS Code, so the file is portable between machines.
  • "env": { "ASPNETCORE_ENVIRONMENT": "Development" } — what selects appsettings.Development.json and the developer exception page. Omit it and the app runs as Production locally.
  • "serverReadyAction" — watches the output for the listening URL and opens a browser at it.

Extensions worth having: C# Dev Kit, REST Client (send HTTP requests from a .http file — better than Postman for things you want in source control), Docker, GitLens, and SQL Server (mssql).

requests.http — testable, reviewable, committed
@host = https://localhost:7001

### fetch an order
GET {{host}}/api/v1/orders/42
Accept: application/json

### create one
POST {{host}}/api/v1/orders
Content-Type: application/json

{ "customerId": 42, "notes": "consegna urgente" }
Line by line
  • A .http file, executable from VS Code or Rider. It lives beside the code and is committed, which is the entire advantage over a Postman collection on somebody else's laptop.
  • @host = ... — a variable, referenced below as {{host}}. Change one line to point at staging.
  • ### — the request separator. Each block is one request, and the editor puts a clickable Send above it.
  • GET {{host}}/api/v1/orders/42 — verb, URL, then headers on following lines. The blank line before the body is required, exactly as in raw HTTP.
  • Content-Type: application/json — without it ASP.NET Core returns 415 and does not bind the body, per chapter 14.
  • See requests/logiflow.http in this repository, which walks the whole order flow in about six clicks.

The CLI is part of the tooling

what you run without an IDE at all
dotnet watch                        # rebuild and restart on save
dotnet test --filter "Category=Unit"
dotnet format                       # apply .editorconfig across the solution
dotnet list package --vulnerable    # known CVEs in your dependencies
dotnet ef migrations list           # (ch. 09)

# diagnosing a running process — the tools that impress
dotnet-counters monitor -p <pid>    # live GC, thread pool, request rate
dotnet-dump collect  -p <pid>       # a memory dump to analyse offline
dotnet-trace collect -p <pid>       # CPU profile of a live process
Line by line
  • dotnet watch — rebuild and restart on save, with hot reload for many edits. The tightest feedback loop available without an IDE.
  • --filter "Category=Unit" — runs the tests tagged with [Trait("Category", "Unit")], so the slow container-backed suite stays out of the inner loop.
  • dotnet format — applies .editorconfig across the solution. Its real value is in CI as --verify-no-changes, which ends formatting arguments in code review permanently.
  • dotnet list package --vulnerable — known CVEs in your dependencies. Add --include-transitive, because the risky package is usually one you never chose.
  • dotnet-counters monitor -p <pid> — live counters on a running process: GC collections, heap size, thread pool queue length, requests per second. No profiler, no restart.
  • These are the tools that impress in an interview, because they answer "the service is slow in production and I cannot attach a debugger" — alongside dotnet-dump and dotnet-trace.
.editorconfig

This repository has one, and it is not decoration: it makes formatting and analyser severity a property of the repository rather than of each developer’s settings. That ends the "whole file reformatted" diff, and lets a team promote a warning to an error once and have it apply everywhere — including in CI.

Try it yourself

Practise on the API from chapter 14. Each of these is a skill, not a fact:

  1. Put a breakpoint in a loop and add the condition i == 500. Never again step through five hundred iterations.
  2. Convert it to a tracepoint that logs a value and does not stop.
  3. In Exception Settings, tick CLR exceptions. Run something that swallows one and watch the debugger break at the throw.
  4. Pause on a breakpoint and, in the Immediate window, call a service method and inspect what comes back.
  5. Use Set Next Statement to jump back three lines and re-run a block with a value you changed by hand.
  6. Start the app without debugging, then attach to it (Debug → Attach to Process). This is how you debug something already running.

Golden rules

  1. Learn the debugger properly. It repays the hour within a week.
  2. Conditional breakpoints and hit counts instead of stepping through loops.
  3. Tracepoints instead of adding Console.WriteLine and recompiling.
  4. Break on thrown exceptions to find the ones something is swallowing.
  5. The Immediate window is a REPL against a live process — test the fix before writing it.
  6. Read the call stack. The answer is often two frames up.
  7. Reproduce → hypothesise → observe → bisect → fix the cause. Keep the test.
  8. Go to anything and Find all references are how you read unfamiliar code.
  9. Debug builds are for debugging. Never measure performance in one.
  10. Commit .editorconfig and launch.json; the toolchain belongs to the repository.
  11. Know the CLI as well as the IDE. Build agents have no IDE.

Interview questions

"How do you debug a problem you cannot reproduce locally?"

Start from evidence rather than the debugger: structured logs with a correlation id, metrics and traces (chapter 30), and a memory or CPU dump from the running process with dotnet-dump or dotnet-trace. Then work towards a local reproduction with the real data shape — because until it reproduces, you cannot prove a fix.

"What is the difference between step over and step into?"

Step over executes the whole line including any call; step into enters the called method. Step out finishes the current method and returns to the caller. Simple, and asked as a sanity check.

"How would you find a memory leak in a .NET service?"

Watch it first with dotnet-counters to confirm the heap is actually growing, then take two dumps some minutes apart and diff them — the type whose instance count grows without bound names the culprit. Common causes: a static collection that only ever grows, an event handler never unsubscribed, and a captive scoped dependency inside a singleton (chapter 14).

"Visual Studio or VS Code?"

Both, for different jobs: VS for large solutions, deep debugging and profiling; VS Code for speed, YAML, front-end and remote work. Having a reasoned preference is the answer; insisting one is objectively better is not.
