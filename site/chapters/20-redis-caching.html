Caching with Redis

A cache is a bet: that the same question will be asked again before the answer goes stale. When the bet is right it removes most of your database load. When it is wrong it serves confidently incorrect data, which is worse than being slow.

From the advert

"Esperienza con sistemi di ricerca e caching (ElasticSearch/OpenSearch, Redis)." Redis on a requirements list is a symptom: somebody measured, found the same queries repeating thousands of times a minute, and reached for a cache.

Why cache at all

🧒 Simple

Every time someone asks what day Christmas falls on this year, you could walk to the calendar in the other room, look, and walk back. Or you could look once and write the answer on a sticky note by your desk.

The sticky note is a cache. It is much faster — and it has exactly one danger: someone changes the calendar and forgets to change your note. Now you are answering wrong, quickly and with total confidence.

🎓 Professional

Caching trades freshness for latency and load. It is worth doing when the read/write ratio is high, the computation or query is expensive, and the data tolerates being briefly out of date. A rough sense of the numbers is what makes the decision concrete:

Where the answer comes fromOrder of magnitude
In-process memorytens of nanoseconds
Redis on the same networka fraction of a millisecond
SQL Server, indexed querya few milliseconds
SQL Server, unindexed on a large tablehundreds of milliseconds, or worse

Note the order: fix the query first. A cache in front of a missing index hides the problem until the cache is cold, and then everything falls over at once.

⚠ IMemoryCache hands back a reference

It stores the object itself, not a copy. If a caller mutates what they got from the cache, they have mutated the cached entry for everyone. Cache immutable types — records or DTOs — or clone on read.

The cache-aside pattern

Ninety per cent of application caching is this one pattern. Learn it as a shape.

read: try cache, else load, then store
public sealed class CachedOrderService(
    IOrderRepository repo,
    IDistributedCache cache,
    ILogger<CachedOrderService> log) : IOrderService
{
    private static string Key(int id) => $"order:v1:{id}";
    //                                    ↑ version the key: a DTO shape change
    //                                      then cannot collide with old entries

    public async Task<OrderDto?> GetAsync(int id, CancellationToken ct)
    {
        var key = Key(id);

        // 1. try the cache — and never let a cache failure fail the request
        try
        {
            var cached = await cache.GetStringAsync(key, ct);
            if (cached is not null)
                return JsonSerializer.Deserialize<OrderDto>(cached);
        }
        catch (RedisConnectionException ex)
        {
            log.LogWarning(ex, "Cache unavailable; falling through to the database.");
        }

        // 2. miss → the real source
        var dto = await repo.GetAsync(id, ct);
        if (dto is null) return null;

        // 3. store, with an expiry that is NOT optional
        await cache.SetStringAsync(key,
            JsonSerializer.Serialize(dto),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10),
                SlidingExpiration               = TimeSpan.FromMinutes(2)
            }, ct);

        return dto;
    }

    public async Task UpdateAsync(int id, UpdateOrder cmd, CancellationToken ct)
    {
        await repo.UpdateAsync(id, cmd, ct);
        await cache.RemoveAsync(Key(id), ct);   // evict, do not update
    }
}
🎓 Why evict rather than overwrite on write

Writing the new value into the cache looks tidier and introduces a race: two concurrent updates can leave the cache holding the older of the two. Deleting the key is idempotent and safe — the next read repopulates from the source of truth. Invalidate, do not update.

Expiry and invalidation

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton

StrategyHowRight for
Absolute TTLExpires N minutes after being writtenThe default. Bounds staleness whatever else happens.
SlidingThe clock resets on each readSession-like data. Always pair it with an absolute cap, or a hot key never expires.
Explicit evictionRemoveAsync on writeData you own and can reliably intercept every write to.
Key versioningorder:v2:42Shape changes on deploy — the whole old generation is orphaned at once.
⚠ Never cache without an expiry

A cache entry with no TTL is a memory leak with a business-logic bug attached. Even when you invalidate explicitly, set a TTL as a backstop: some day a write will happen through a path you did not intercept — a stored procedure, an integration job, someone in SSMS — and the TTL is what limits the damage to minutes instead of for ever.

The two failure modes worth naming

🧒 Simple — the stampede

One popular sticky note falls off the desk. In the same second, five hundred people ask the question — and all five hundred walk to the other room to check the calendar, because none of them knows the others are already going.

The room, which comfortably handles one visitor, now has five hundred people in it.

the fix: one loader, everyone else waits
// HybridCache does this for you — a single flight per key
var dto = await hybrid.GetOrCreateAsync(
    Key(id),
    async token => await repo.GetAsync(id, token),
    new HybridCacheEntryOptions { Expiration = TimeSpan.FromMinutes(10) },
    cancellationToken: ct);

// By hand: a per-key SemaphoreSlim, or add jitter to the TTL so a whole
// generation of keys does not expire on the same tick.

The second failure mode is cache penetration: repeated requests for a key that does not exist miss the cache every time and hit the database every time. The fix is to cache the absence too — a short-TTL null marker.

Redis is more than a cache

It is an in-memory data structure server: strings, hashes, lists, sets, sorted sets, streams, pub/sub, and atomic operations like INCR. Common uses beyond caching are distributed rate limiting, ASP.NET Core data-protection key storage, AddStackExchangeRedis as a SignalR backplane, and distributed locks (with Redlock’s caveats). Mentioning one of these shows you know it is not just a hashtable in the sky.

Golden rules

  1. Fix the query and the index before you add a cache. A cache over a missing index just moves the failure.
  2. Cache-aside is the default pattern: try, load, store.
  3. Always set a TTL. No exceptions, even with explicit invalidation.
  4. Pair sliding expiration with an absolute cap.
  5. On write, evict the key. Do not try to update it.
  6. Version your keys so a deployed shape change cannot read old entries.
  7. A cache outage must degrade to slow, never to broken. Catch and fall through.
  8. Guard against stampedes with single-flight loading or TTL jitter.
  9. Cache negative results too, briefly, or a missing key hits the database every time.
  10. IMemoryCache per instance; Redis when there is more than one instance.
  11. Never cache data whose staleness has financial or legal consequences.
  12. Measure the hit rate. A cache below roughly 80% is often costing more than it saves.

Interview questions

"When would you add a cache?"

After measuring: a read-heavy path, an expensive query, and data that tolerates being a little stale. Say explicitly that the first move is to look at the execution plan and the index, and that a cache is what you reach for when the query is already as good as it can be.

"IMemoryCache or Redis?"

Memory is faster but per-instance, so behind a load balancer you get N inconsistent copies and invalidation that only works on one of them. Redis is shared and survives restarts, at the cost of a network hop and a new dependency.

"How do you invalidate a cache?"

TTL as the backstop, explicit eviction on write, key versioning for shape changes. Be honest that the hard case is a write path you do not control — a stored procedure or an integration job — which is exactly why the TTL is never optional.

"What is a cache stampede?"

A hot key expires and every concurrent request misses simultaneously, so they all hit the database at once. Fix with single-flight loading (one request loads, the rest wait) or by adding jitter to expiry times so keys do not expire together.

"What happens if Redis goes down?"

It should degrade to slow, not to broken: catch connection failures and fall through to the database. Then note the real risk — if the system was sized assuming an 80% hit rate, a cold cache means five times the database load arriving at once, so a circuit breaker and some load shedding belong in the design.
