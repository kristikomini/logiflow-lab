The .NET Framework app you will inherit

Everything up to here taught you ASP.NET Core. Your first ticket will probably be against something else: a web application on .NET Framework 4.8, written before middleware existed, still earning the company money. This chapter is how to open it, be useful in it, and eventually move it — without the panic that makes juniors avoid the legacy repository.

Why this chapter exists

Read the adverts again. One lists "ASP.NET" and "ASP.NET Core" as two separate required skills. Another names .NET Framework 4.8 by version, in the duties, next to .NET Core, and adds "aggiornamento e migrazione tecnologica su framework .NET". Chapter 00 read the slash in "framework .NET / .NET Core" the same way: they have both.

That is not a wish list, it is a description of their repository. And it is good news — every bootcamp graduate you are competing against can do the Core half. Almost none of them can read a Global.asax without flinching.

Two frameworks, one team

🧒 Simple

A company has two buildings. The old one was built in 1998: thick walls, a doorman who greets every visitor personally, and wiring you are not allowed to move. The new one is glass and open plan, and everything is on wheels.

Both buildings are full of people doing real work. Nobody is going to demolish the old one this year, because the accounts department is inside it. Your job is to be someone who can walk into either building and find the light switch.

🎓 Professional

.NET Framework 4.8 is the end of a line. It is the final version, it ships as part of Windows, and it receives security and reliability fixes for as long as the operating system does — but no new features, ever. That is precisely why so much code still sits on it: it is not deprecated, it is finished. There is no forcing function, only a business case.

"ASP.NET" and "ASP.NET Core" share a name and almost no code. Chapter 01 gave you the table; the practical version is that the two stacks disagree about the four things you touch every day — how a request is handled, how configuration is read, how dependencies are supplied, and how async behaves.

The pipeline that is not middleware

ASP.NET Core taught you one mental model: a chain of middleware, each one calling the next, built in Program.cs in the order you wrote it. Framework has a pipeline too, but it is event-based rather than nested — a fixed sequence of stages that your code subscribes to, and the order comes from the stage, not from your file.

That difference has a consequence worth saying out loud: in Framework, there is no "on the way back". A module that wants to touch the response subscribes to a late event such as EndRequest. In Core, the same code is whatever you write after await next(). When you port a module and it stops working, this is usually why.

Global.asax.cs — the Program.cs of 2010
public class MvcApplication : System.Web.HttpApplication
{
    // Runs once, when the application pool starts the app. Everything that
    // Program.cs does at start-up used to live here.
    protected void Application_Start()
    {
        AreaRegistration.RegisterAllAreas();
        GlobalConfiguration.Configure(WebApiConfig.Register);   // Web API 2 routes
        FilterConfig.RegisterGlobalFilters(GlobalFilters.Filters);
        RouteConfig.RegisterRoutes(RouteTable.Routes);          // MVC 5 routes — a SECOND table
        BundleConfig.RegisterBundles(BundleTable.Bundles);
    }

    // Runs on every request. This is the module pipeline, inlined.
    protected void Application_BeginRequest()
    {
        HttpContext.Current.Items["CorrelationId"] = Guid.NewGuid().ToString("n");
    }

    // The last-chance handler. The ancestor of UseExceptionHandler.
    protected void Application_Error()
    {
        var ex = Server.GetLastError();
        Log.Error(ex, "Unhandled");
        Server.ClearError();
        Response.Redirect("~/Error");
    }
}
⚠ The trap

Application_Start runs again every time the application pool recycles, and a pool recycles far more often than a server reboots — on a memory threshold, on a web.config edit, on a schedule, or after an idle timeout. Any state you put in a static field is therefore not "for the lifetime of the server", it is "until the next recycle". That is the mechanism behind the classic report: "the first person in after lunch waits fifteen seconds".

web.config, and configuration before IConfiguration

Core taught you layered configuration: appsettings, then environment-specific overrides, then environment variables, then secrets, with the later ones winning. Framework has one XML file that is simultaneously the application's settings, its dependency wiring, its IIS configuration and part of its security policy.

🎓 Professional

Transforms. Environment-specific values come from Web.Release.config and friends, applied at publish time by XDT: 

<add name="LogiFlow" connectionString="…prod…"
     xdt:Transform="SetAttributes" xdt:Locator="Match(name)" />

Two things follow. First, the transform is applied by the build, so what runs on the server is a file nobody has in source control — when production disagrees with your machine, read the deployed web.config, not the one in the repository. Second, this is why connection strings with passwords end up committed. If you find one, chapter 26 has the drill: rotate first, clean history second.

WebForms, in survival terms

You will not be asked to write new WebForms. You may well be asked to fix one. The goal here is to read an .aspx page without being surprised by it.

🧒 Simple

WebForms pretends the web is a desktop application. You drag a button onto a page, you double-click it, you write SaveButton_Click, and it feels exactly like WinForms.

The illusion is maintained by a trick: every time you click anything, the entire page is posted back to the server, and the server sends the whole page back. To make the boxes still contain what you typed, the page smuggles its own state along in a hidden field. That hidden field is ViewState, and when someone complains the page is slow, it is usually the reason.

Orders.aspx — markup with server controls
<%@ Page Language="C#" CodeBehind="Orders.aspx.cs"
    Inherits="LogiFlow.Web.Orders" %>

<asp:GridView ID="OrdersGrid" runat="server" AutoGenerateColumns="false"
    <!-- turn this OFF on a read-only grid and the page gets dramatically smaller -->
    EnableViewState="false">
  <Columns>
    <asp:BoundField DataField="OrderNumber" HeaderText="Order" />
  </Columns>
</asp:GridView>

<asp:Button ID="Refresh" runat="server" Text="Refresh"
    OnClick="Refresh_Click" />
Orders.aspx.cs — the code-behind
public partial class Orders : System.Web.UI.Page
{
    protected void Page_Load(object sender, EventArgs e)
    {
        // THE line that matters. Page_Load runs on the first visit AND on every
        // postback. Without this guard you re-bind the grid before the click
        // event fires, and the click appears to do nothing.
        if (!IsPostBack)
        {
            BindGrid();
        }
    }

    protected void Refresh_Click(object sender, EventArgs e) => BindGrid();
}
⚠ The two bugs that are always this
  1. "The button does nothing." Almost always a missing if (!IsPostBack). The lifecycle runs Page_Load before the control event, so an unguarded re-bind throws away the state the click was about to act on.
  2. "The page takes eight seconds and the HTML is two megabytes." ViewState on a large GridView. The whole grid is serialised into __VIEWSTATE and round-tripped on every postback. Set EnableViewState="false" on anything the user does not edit.

The lifecycle order is worth carrying: Init → LoadViewState → Load → control events → PreRender → SaveViewState → Render → Unload. Control events run after Page_Load; changes you want rendered must happen by PreRender.

MVC 5 and Web API 2, versus the Core versions

Framework had two controller stacks that look almost identical and share nothing: MVC 5 for HTML, Web API 2 for JSON. Core merged them. Most porting confusion is a symptom of that merge.

⚠ Same name, different type

Look at the filters row again. Both are called ActionFilterAttribute. Put the System.Web.Mvc one on a Web API controller and it compiles, deploys, and never runs — no error, no warning, just a filter that silently does nothing. When a legacy authorisation or logging filter "isn't firing", check the using first. This is the single most common wasted afternoon in a mixed codebase.

HttpContext.Current, and why it cannot exist in Core

Framework code reaches the current request from anywhere — a service, a static helper, a data-access class — through a static property:

the thing you must un-learn
// Framework: works anywhere, needs nothing injected, and is a hidden dependency
// on "there is a request in flight on this thread".
var user = HttpContext.Current.User.Identity.Name;

// …and this is why it is dangerous. Off the request thread, Current is null.
Task.Run(() => Log.Info(HttpContext.Current.User.Identity.Name));  // NullReferenceException

// Core: the dependency is declared, so it can be supplied — and tested.
public AuditService(IHttpContextAccessor accessor) => _accessor = accessor;

The ambient static is also what makes Framework code hard to unit test: there is no seam. When you port a class and discover it cannot be constructed in a test, HttpContext.Current is usually the reason, and the fix is to pass the two values it actually wanted as parameters.

The async trap — why the old app deadlocks and the new one does not

Chapter 07 taught you never to block on an async call. On ASP.NET Core, breaking that rule costs you a thread. On ASP.NET Framework, it hangs the request permanently. Same code, different outcome — and this is the highest-value thing in this chapter, because it is both a real production bug and a favourite interview question.

the classic deadlock
public ActionResult Index()
{
    // On ASP.NET Framework this NEVER RETURNS.
    var data = _service.GetAsync().Result;
    return View(data);
}

private async Task<Data> GetAsync()
{
    await _http.GetStringAsync(url);
    // ↑ the continuation below is posted back to the request's
    //   SynchronizationContext, which allows only ONE thread at a time —
    //   and that one thread is blocked on .Result, waiting for this method.
    return Parse();
}
🎓 Professional

This is what ConfigureAwait(false) was for. It says "I do not need to resume on the captured context", which breaks the cycle. Hence the old advice, still correct on Framework: use it on every await in library code.

And hence the modern confusion. On ASP.NET Core there is no context to capture, so ConfigureAwait(false) in application code does nothing. Both pieces of advice are right; they are about different runtimes. Being able to say that sentence is what separates a memorised answer from an understood one.

Note the direction of danger. Blocking code ported from Framework to Core stops deadlocking and starts silently starving the thread pool instead — the bug does not announce that it was fixed, it changes disguise. Fix it properly: make the whole path async.

IIS: pools, recycles, and the first request after lunch

🧒 Simple

IIS is a building manager. Your application lives in a room called an application pool. The manager will, without asking, occasionally clear the room out and set it up again — because it is using too much memory, because someone changed a config file, or just because it is Tuesday. Everything you left lying around in there is gone, and the next visitor waits while the room is re-made.

What that means concretely:

  • In-process session and cache are per-pool and per-recycle. Anything in Session or a static dictionary disappears on recycle, and does not exist at all on the other server if the app is load-balanced. That is the bug behind "users get logged out at random". The fix is an out-of-process store — SQL Server or Redis (chapter 20).
  • Editing web.config restarts the application. Immediately, in production, for everyone. It is not a configuration reload, it is a restart.
  • The first request after a recycle is slow — JIT, start-up wiring, warming caches. Idle-timeout recycling is what makes this land on a real user rather than a health check. Set the pool's idle timeout to 0 and enable Always On / preload, or point a health check at it (chapter 25).
  • 32-bit pools still exist. An old pool with Enable 32-Bit Applications set is capped near 2 GB no matter how much RAM the server has, and reports itself as out-of-memory on a machine with 60 GB free.
Core on IIS is a different arrangement

When the new services are also behind IIS, IIS is not hosting them — the ASP.NET Core Module is reverse-proxying to Kestrel, either in-process (default, faster) or out-of-process. So "it is on IIS" tells you nothing about which stack it is. Look for web.config with an aspNetCore element: that is Core.

Moving it: the migration they will ask you about

"Aggiornamento e migrazione tecnologica" is a listed duty in one of these adverts. The interview version of this question is not "how do you do it" — it is "how do you do it without stopping delivery for eight months", and there is a wrong answer that sounds confident.

⚠ The answer that loses you the job

"I would rewrite it in .NET 8." A rewrite means no new features for however long it takes, a hard cutover with no rollback, and re-discovering ten years of undocumented business rules that exist only as bug fixes in that code. Companies that try it usually stop halfway and end up maintaining two systems. Say the incremental answer instead, and say why.

Step 2 — the incremental route

Put a reverse proxy in front of the old application. Move one route at a time to a new ASP.NET Core app behind the same proxy. Anything not yet moved falls through to the old app. Both run in production, together, for as long as it takes — and every step is independently releasable and independently revertable. This is the strangler fig pattern; chapter 31 applies the same idea to desktop.

🎓 Professional

Two pieces make this practical, and naming them is what shows you have read past a blog post:

  • Microsoft.AspNetCore.SystemWebAdapters — lets code that still calls HttpContext.Current compile and run on ASP.NET Core, and can share session state between the two apps during the transition. It is a bridge, not a destination: it buys you the right to move a class before you have finished rewriting it.
  • netstandard2.0 — retarget shared class libraries to it and both applications can reference the same assembly. Do this to your domain and business-logic projects early; it is usually where most of the value is, and it is low risk.

Step 3 — what breaks at run time, not at compile time

The compiler catches the easy half. These are the ones that reach production:

  • Configuration. ConfigurationManager returns null for a missing key; IConfiguration binding may silently leave a default. A setting that quietly stops arriving is worse than one that throws — validate options at start-up.
  • The synchronisation context. Covered above. Blocking code stops deadlocking and starts starving.
  • Culture and encoding. Framework leaned on the machine's locale; modern .NET uses ICU, and on Linux the defaults differ again. An Italian machine formatting a decimal is chapter 23's territory, and a migration is exactly when it bites.
  • Case-sensitive paths, if the new app lands on Linux. Views/Order.cshtml and views/order.cshtml were the same file on Windows and are not any more.
  • Cookies and auth. Different default SameSite, different protection of the auth cookie. Users get logged out on the first deploy unless key material is shared.
Try it yourself

No legacy application to hand? Build the interesting half of one in ten minutes:

  1. In Visual Studio, create an ASP.NET Web Application (.NET Framework), MVC template, targeting 4.8. Read Global.asax.cs, App_Start/RouteConfig.cs and web.config. Everything in this chapter is in those three files.
  2. Add an action that does Task.Delay(1000).Result and request it. Watch it hang. Add ConfigureAwait(false) to the awaited call inside and watch it stop hanging. You have now reproduced the deadlock that costs teams days.
  3. Put the same action in a new ASP.NET Core project. It returns. Explain, out loud, why.
  4. Run upgrade-assistant analyze on the Framework project and read the report. Note how much of it is "this will be fine" — the fear is bigger than the work.

Golden rules

  1. ASP.NET and ASP.NET Core share a name and almost no code. Ask which one before you answer any question about "the ASP.NET app".
  2. Framework's pipeline is events on a fixed sequence; Core's is nested middleware. There is no "on the way back" in Framework — a late event is the substitute.
  3. Application_Start runs again on every pool recycle. Static state lasts until then, not until reboot.
  4. Blocking on async deadlocks on Framework and starves the pool on Core. Same bug, two disguises. Make the whole path async instead.
  5. ConfigureAwait(false) matters on Framework and is a no-op in Core application code. Both pieces of advice are correct, for different runtimes.
  6. if (!IsPostBack) is the WebForms bug. Control events run after Page_Load.
  7. ViewState is a hidden field carrying your grid. Turn it off on anything read-only.
  8. The two ActionFilterAttribute types are different classes. The wrong using gives you a filter that silently never runs.
  9. HttpContext.Current is a hidden dependency and null off the request thread. In Core, inject IHttpContextAccessor — or better, pass the value.
  10. Editing web.config restarts the application. In production. For everyone.
  11. Migrate incrementally behind a proxy, never by rewrite. Retarget shared libraries to netstandard2.0 first; it is the cheapest real progress.
  12. Legacy competence is a hiring advantage here. Everyone can do greenfield Core. Far fewer will willingly open the 2011 solution.

Interview questions

"What is the difference between ASP.NET and ASP.NET Core?"

Not "one is newer". They share a name and almost no code: Framework is Windows and IIS only, built on System.Web, with an event-based pipeline, web.config, and no built-in DI. Core is cross-platform, self-hosted on Kestrel, with nested middleware, layered configuration and DI as a first-class concern. Then the sentence that shows real experience: and there is no synchronization context in Core, which changes how async behaves.

"Why does .Result deadlock on ASP.NET but not on ASP.NET Core?"

Framework installs a synchronization context that allows one thread on the request at a time. Blocking on .Result holds that thread while the continuation waits to re-enter the same context — mutual wait, forever. Core has no synchronization context, so the continuation resumes on any pool thread. Finish honestly: it still wastes a thread, so it is a scalability bug rather than a hang. That is what ConfigureAwait(false) was for, and why the advice sounds outdated on Core.

"How would you migrate a .NET Framework web app to .NET 8?"

Analyse first with Upgrade Assistant and identify what genuinely cannot port — WebForms, WCF hosting, System.Web, AppDomains. Then do the safe mechanical step on Framework and ship it: packages.config to PackageReference, SDK-style projects. Retarget shared libraries to netstandard2.0 so both apps can use them. Then put YARP in front and move route by route, using the System.Web adapters for code that is not ready, with both applications live. Explicitly reject the big-bang rewrite and say why: no rollback, no delivery, and ten years of undocumented rules living only in that code.

"What is ViewState?"

A base64 hidden field (__VIEWSTATE) that carries server-control state across a postback, so WebForms can pretend the page is stateful. It is also the usual reason a WebForms page is enormous and slow — a data-bound grid serialises its whole contents into it. Disable it on read-only controls. It is integrity-protected by a MAC, so it is tamper-evident, but treating it as a secure store is still a mistake.

"A filter on a legacy controller isn't running. Where do you look?"

First at the using. MVC 5 and Web API 2 each define an ActionFilterAttribute with the same name in different namespaces, and the MVC one on an ApiController compiles and silently never fires. After that: whether it is registered globally in the right table — RouteConfig and WebApiConfig are two separate worlds.

"Users are randomly logged out. The app is on two IIS servers."

In-process session state. It lives in one application pool's memory, so it is lost when the pool recycles and is invisible to the other server, meaning every request that lands on the wrong node looks logged out. Fix by moving session out of process — SQL Server or Redis — and by sharing the key material that protects the auth cookie across both machines. Mention sticky sessions as the stopgap, not the fix.

"Why is the first request after a quiet period slow?"

The application pool recycled — idle timeout, memory limit, schedule, or a web.config edit — so Application_Start is running again, code is being JIT-compiled again, and caches are cold. Set the idle timeout to zero with Always On or preload, and keep it warm with the health check you needed anyway.
