Arrays and the shapes of data

Chapter 00c gave you a one-dimensional array and a List<T> and told you the difference is Length versus Count. That is enough to hold a row of values. This chapter is the rest of the shape: a grid, a ragged set of rows, the static helpers on Array that replace loops you would otherwise write, and the two ways of copying an array that both look like copying and only one of which is.

Why this chapter exists

An array is the one collection that appears in every layer — a string[] from Split, a byte[] from a file, a args from the command line, a JSON array from an API, a grid of warehouse bins. It is also the collection with the sharpest edges: fixed length, zero-based, no bounds check until run time, and a copy that quietly shares its contents. Nothing here is advanced, and all of it is assumed by every later chapter.

One dimension, and the four ways to make one

string[] a = new string[3];                      // 3 slots, all null
int[]    b = new int[3];                         // 3 slots, all 0 — not null
string[] c = { "MI-42", "BO-7", "PR-1" };        // literal, length inferred
string[] d = new[] { "MI-42", "BO-7" };          // same, type inferred
int[]    e = [1, 2, 3];                          // C# 12 collection expression

c[0] = "MI-99";              // positions are 0 .. Length - 1
int n = c.Length;            // 3 — a property, arrays use Length
string last = c[^1];         // "PR-1" — one from the end
string[] two = c[1..];       // a NEW array with the last two — a range
Line by line
  • new int[3] fills with the element type's default: zero for numbers, false for bool, null for any reference type. A string[3] is three nulls, and iterating it without a check is a NullReferenceException waiting to happen — see chapter 02b on defaults.
  • The length is fixed at creation and can never change. There is no Add. Array.Resize exists and is a lie: it allocates a new array, copies everything across, and repoints your variable. In a loop that is exactly the quadratic trap that += on strings is.
  • c[^1] — the index-from-end operator. It is the readable form of c[c.Length - 1], which is the expression people get wrong by one.
  • c[1..] — a range, and on an array it allocates a new array and copies. On a Span<T> the same syntax copies nothing at all, which is the whole point of spans.
  • An array is a reference type even when its elements are not, so passing one to a method passes the note, not the contents — and the method can change your elements.
⚠️ IndexOutOfRangeException is a run-time error

c[3] on a three-element array compiles perfectly and throws when it runs. The compiler does not track lengths, so nothing warns you. Every off-by-one you will ever write lives in this gap, and the reason foreach is preferred over for is simply that foreach cannot make the mistake.

Two dimensions: a grid, and a ragged set of rows

🧒 Simple

There are two ways to store a table. One is a real rectangle — every row has exactly the same number of slots, like a warehouse aisle where every rack is identical. The other is a list of rows, each free to be its own length, like a stack of orders where each has a different number of lines. C# has separate syntax for each, and they are not interchangeable. 

// RECTANGULAR — one object, aisles × shelves, always square
int[,] stock = new int[4, 6];             // 4 aisles, 6 shelves each
stock[2, 3] = 17;
int aisles  = stock.GetLength(0);         // 4  — NOT .Length
int shelves = stock.GetLength(1);         // 6
int cells   = stock.Length;               // 24 — the TOTAL, which surprises everyone

// JAGGED — an array of arrays; each row is its own object, its own length
int[][] orderLines = new int[3][];
orderLines[0] = new[] { 12, 4 };
orderLines[1] = new[] { 7, 7, 7, 1 };     // a different length, quite legally
orderLines[2] = Array.Empty<int>();       // an empty row, not null
int firstRow = orderLines[1].Length;      // 4 — each row has its own Length

foreach (int[] row in orderLines)
    foreach (int qty in row)
        Console.WriteLine(qty);
Line by line
  • int[,] with a comma is rectangular: a single allocation laid out as one contiguous block, so it is compact and cache-friendly, and every row must be the same length. int[][] is jagged: an array of references, each pointing at a separate array.
  • .Length on a rectangular array gives the total number of cells, not the number of rows. Use GetLength(0) and GetLength(1). This is the single most common mistake with [,].
  • A jagged array's rows start as null, not as empty arrays. new int[3][] gives three null references, and the loop above only works because each row was assigned. Prefer Array.Empty<int>() to new int[0] for an empty row — it returns a shared cached instance and allocates nothing.
  • Jagged is usually the right choice in business code, because real data is ragged: orders have different numbers of lines. Rectangular earns its place for genuine grids — a heat map, an image, a matrix, a warehouse layout.
  • Neither works with LINQ the way you expect. A int[,] implements only the non-generic IEnumerable, so .Where() is not available without .Cast<int>() first. Jagged arrays are fine, because each row is an ordinary array.

The Array statics: loops you do not have to write

CallDoesNote

Array.IndexOf(a, v)the position, or −1linear scan

int[] counts = { 5, 3, 9, 1 };

Array.Sort(counts);                   // counts is now { 1, 3, 5, 9 } — IN PLACE
int where = Array.IndexOf(counts, 5); // 2
Array.Reverse(counts);                // { 9, 5, 3, 1 }

int[] blanks = new int[10];
Array.Fill(blanks, -1);               // -1 means "not counted"; 0 would mean "counted zero"

// LINQ does the same jobs without mutating, which is usually what you want
int[] sorted = counts.OrderBy(x => x).ToArray();   // a NEW array; counts untouched
int biggest  = counts.Max();
bool anyLow  = counts.Any(x => x < 2);
Line by line
  • Array.Sort mutates and returns void. OrderBy returns a new sequence and leaves the original alone. Which you want is a real decision: mutating is cheaper, and it also changes an array somebody else may be holding a reference to.
  • Array.Fill(blanks, -1) — the reason to bother is that 0 is a legitimate count. Distinguishing "we counted zero" from "we have not counted" needs a sentinel value, or a nullable element type, and choosing one deliberately is the whole point.
  • BinarySearch on an unsorted array does not throw — it returns a wrong answer. It is fast because it assumes order; if you did not sort it, that assumption is yours to keep.
  • Array.Empty<T>() returns the same cached instance every time, so returning it from a method costs nothing. Return an empty array, never null — then no caller has to guard, and no caller forgets to.
  • Array.Resize takes its argument by ref precisely because it cannot resize anything: it makes a new array and repoints your variable. If you find yourself calling it in a loop, you wanted a List<T>.
⚠️ Clone copies the array, not the things in it

var copy = orders.Clone() as Order[]; gives you a genuinely new array — adding to one does not affect the other — whose slots hold the same objects. Change copy[0].Status and orders[0].Status changes too, because there is only one order. That is a shallow copy, and it is also what ToArray(), ToList() and Array.Copy all do. A deep copy has to be written by hand, element by element, or avoided entirely by making the elements immutable — which is one of the reasons record exists.

Array, List, or something else

UseWhenWhy not the others
T[]the size is known and fixed; a buffer; an API gives you onecannot grow; no Add

// ✗ returning the internal array hands out write access to your own state
public string[] GetSkus() => _skus;              // caller can do GetSkus()[0] = "hack"

// ✓ return a read-only view, or a copy
public IReadOnlyList<string> Skus => _skus;      // a view — cheap, and not writable
public string[] SkusCopy() => _skus.ToArray();   // a copy — writable, and theirs

// the O(n) mistake, in a loop that runs for every order
bool known = allSkus.Contains(sku);              // array/list: scans everything
bool fast  = skuSet.Contains(sku);               // HashSet: one hash lookup
Line by line
  • Never return your own array. An array is a reference, so the caller is holding your state and can rewrite it — past every validation method on the class. This is chapter 03's encapsulation, in the place it most often leaks.
  • IReadOnlyList<T> is a view, not a snapshot: it costs nothing, and it still changes when you change the underlying list. If the caller must have a stable picture, give them ToArray() and accept the copy.
  • Contains on an array or a List<T> is a linear scan. Inside a loop over orders that is the classic accidental O(n²), and it is invisible with a hundred SKUs and fatal with fifty thousand. A HashSet<T> built once before the loop fixes it in two lines.
  • Span<T> is a window onto memory somebody else owns, so slicing costs nothing. Its restrictions — stack only, no fields, no async — are what make that safe. It belongs in parsing hot paths and nowhere else, and chapter 06 is the wider tour.
  • Most of the time the honest answer is List<T>. Arrays are for when something hands you one, or when the length is genuinely fixed.

Walking one safely

// ✓ foreach — cannot go out of bounds, and says what it means
foreach (string sku in skus)
    Console.WriteLine(sku);

// ✓ for — when you need the index, or you are modifying elements in place
for (int i = 0; i < counts.Length; i++)
    counts[i] *= 2;                       // foreach could NOT do this on a value type

// ✓ index and value together, without a counter you maintain
foreach (var (sku, i) in skus.Select((s, i) => (s, i)))
    Console.WriteLine($"{i + 1}. {sku}");

// ✗ modifying the collection while enumerating it
foreach (var o in orders)
    if (o.Cancelled) orders.Remove(o);    // InvalidOperationException on a List

// ✓ decide first, act afterwards
foreach (var o in orders.Where(x => x.Cancelled).ToList())
    orders.Remove(o);
Line by line
  • foreach over an array of value types gives you a copy of each element, so assigning to the loop variable changes nothing — and the compiler forbids it outright, which is a mercy. To modify elements in place you need for and the index.
  • Over an array of reference types the loop variable is a reference to the real object, so o.Status = … inside the loop does change it. That asymmetry catches everyone once.
  • .Select((s, i) => (s, i)) — the overload of Select that gives you the index. Cleaner than maintaining your own counter, and impossible to get out of step.
  • Removing while enumerating throws. A List<T> keeps a version number and the enumerator checks it. The .ToList() in the fix is not decoration — it materialises the matches into a separate list first, so the enumeration and the mutation are over different objects.
  • The tidier version of that whole problem is orders.RemoveAll(x => x.Cancelled), which does it in one pass and one line.

Exercises, with the reasoning shown

Exercise 1 — the grid that reported twenty-four rows

int[,] stock = new int[4, 6];
for (int i = 0; i < stock.Length; i++) { /* ... */ }
The loop runs 24 times, not 4.
  • .Length on a rectangular array is the total number of cells — rows times columns. The row count is stock.GetLength(0) and the column count is GetLength(1). The loop as written does not throw, because it never indexes with i; add stock[i, 0] inside it and it throws on the fifth pass.

Exercise 2 — the copy that was not a copy

Order[] backup = (Order[])orders.Clone();
orders[0].Status = "CANCELLED";
Console.WriteLine(backup[0].Status);
CANCELLED.
  • Clone made a new array of references to the same order objects. The array is genuinely independent — assigning orders[0] = somethingElse would not touch backup — but the objects inside it are shared. Every built-in copy in .NET is shallow. A real backup needs each element copied, which for a record is o with { } and for a class is a method you write.

Exercise 3 — the rows that were null

int[][] grid = new int[3][];
grid[0][0] = 1;
NullReferenceException.
  • new int[3][] allocated the outer array only; its three slots hold null, because the element type int[] is a reference type. Each row has to be created before it can be indexed: grid[0] = new int[6];. A rectangular new int[3, 6] would have worked immediately, which is one honest advantage it has.

Exercise 4 — the import that got slower every day

foreach (var row in importedRows)              // 50,000 rows
    if (knownSkus.Contains(row.Sku))          // knownSkus is a string[] of 30,000
        Accept(row);
1.5 billion string comparisons.
  • Contains on an array is a linear scan, so the work is rows times SKUs. It was fine when the catalogue had three hundred entries and became a twenty-minute job as it grew, which is why it was reported as a database problem. Building var set = knownSkus.ToHashSet(StringComparer.OrdinalIgnoreCase); once before the loop makes each check a single hash lookup, and the whole import finishes in seconds. Two lines, and it also fixes the case-sensitivity nobody had noticed.
Try it yourself

A warehouse grid and a ragged order list in one file, so the two shapes sit side by side. Paste it into a console project and change the numbers until the difference is obvious. 

// A real grid: every aisle has the same number of shelves.
  int[,] stock = new int[3, 4];
  Array.Clear(stock);                       // already zero, but says so
  stock[1, 2] = 17;

  for (int aisle = 0; aisle < stock.GetLength(0); aisle++)
  {
      for (int shelf = 0; shelf < stock.GetLength(1); shelf++)
          Console.Write($"{stock[aisle, shelf],4}");
      Console.WriteLine();
  }
  Console.WriteLine($"cells: {stock.Length}");        // 12, not 3

  // Ragged data: every order has a different number of lines.
  int[][] orders =
  [
      [12, 4],
      [7, 7, 7, 1],
      [],
  ];

  foreach (int[] order in orders)
      Console.WriteLine($"{order.Length} lines, {order.Sum()} units");

  // And the copy question, demonstrated:
  int[] a = { 1, 2, 3 };
  int[] b = a;                 // NOT a copy — the same array, two names
  int[] c = a.ToArray();       // a real copy, because int is a value type
  b[0] = 99;
  Console.WriteLine($"{a[0]} {b[0]} {c[0]}");        // 99 99 1
Line by line
  • GetLength(0) and GetLength(1) in the loop bounds, never Length — which is 12 here and would run the inner loop off the end.
  • {stock[aisle, shelf],4} — one subscript with a comma, and an alignment width of 4 so the grid prints as a grid.
  • The jagged literal uses a collection expression for both levels, and one row is deliberately empty — Length 0, Sum() 0, no special case needed.
  • int[] b = a; is not a copy: one array with two names, which is why writing through b changes a.
  • a.ToArray() is a real copy here only because the elements are int. Make them a mutable class and the same call shares every element.

Then change int[] to an array of a small class with one mutable property and repeat the last block. c now changes too, because ToArray copied the references and not the objects. That is the difference between a shallow copy and a deep one, in six lines.

Golden rules

  1. An array's length is fixed at creation. Array.Resize allocates a new one and copies; if you are calling it in a loop you wanted a List<T>.
  2. new int[3] is three zeros; new string[3] is three nulls. The slots hold the element type's default, and for reference types that is a null waiting to be dereferenced.
  3. On a rectangular array, .Length is the total cell count. Rows and columns are GetLength(0) and GetLength(1).
  4. A jagged array's rows start as null and must each be created before use. Rectangular for genuine grids, jagged for ragged real-world data.
  5. Every built-in copy is shallow. Clone, ToArray, ToList and Array.Copy all duplicate the slots and share the objects in them.
  6. Array.Sort mutates; OrderBy returns a new sequence. Choose deliberately, because mutating also changes the array anybody else is holding.
  7. BinarySearch on an unsorted array returns a wrong answer rather than throwing. Sorting is your side of the bargain.
  8. Return Array.Empty<T>(), never null. It allocates nothing and removes a guard from every caller.
  9. Never return your own array from a property. The caller can rewrite your state past every validation you own. Return IReadOnlyList<T> for a view or ToArray() for a copy.
  10. Contains on an array or list is a full scan. Inside a loop that is an accidental O(n²); build a HashSet<T> once, outside it.
  11. Prefer foreach; it cannot go out of bounds. Use for only when you need the index or must assign to elements of a value-type array.
  12. Never add to or remove from a collection you are enumerating. Materialise the matches first, or use RemoveAll.

Interview questions

"What is the difference between an array and a List<T>?"

An array has a fixed length decided when it is created and exposes Length; a List<T> wraps an array, grows it as needed, and exposes Count. Growing is not free — when the internal buffer fills, the list allocates a bigger one and copies — but it is amortised, whereas Array.Resize in a loop is quadratic. In practice I default to List<T> for anything I build up, and use an array when something hands me one, when the length is genuinely fixed, or when I need a buffer. For the type I return, I would use IReadOnlyList<T>, so callers cannot write into my state.

"Rectangular versus jagged arrays — when would you use each?"

int[,] is one contiguous allocation and every row is the same length, so it is compact and cache-friendly and right for a genuine grid: an image, a matrix, a warehouse layout. int[][] is an array of references to separate arrays, so each row can be a different length and each is its own object — which is what real business data usually looks like, since orders have different numbers of lines. The two gotchas I watch for: .Length on a rectangular array is the total cell count rather than the row count, and a jagged array's rows start out null and have to be created individually.

"You copy an array of objects with ToArray() and then change one. What happens?"

The other array sees the change. ToArray — like Clone, ToList and Array.Copy — is a shallow copy: it duplicates the slots, so the two arrays are independent, but the slots hold references to the same objects. Replacing an element in one array does not affect the other; mutating an element affects both. If I genuinely need a deep copy I have to write it, element by element — with record types with { } makes that cheap. More often the right answer is to make the elements immutable so the question does not arise.

"Why is Contains on a list sometimes a performance problem?"

Because it is a linear scan — O(n) — and it is usually found inside a loop, which makes the whole thing O(n×m). The symptom is characteristic: perfectly fast in testing, fine in production for a year, then gradually unbearable as the reference data grows, and it gets blamed on the database. The fix is a HashSet<T> or a Dictionary built once outside the loop, turning each check into a single hash lookup. I would also pass a StringComparer to it while I am there, since a set's comparer is the right place to put case-insensitivity rather than calling ToUpper at every site.

"Cosa succede se modifichi una lista mentre ci fai foreach?"

Parte una InvalidOperationException: la lista tiene un numero di versione che l'enumeratore controlla a ogni passo, quindi qualunque Add o Remove durante l'iterazione la fa fallire subito — ed è un bene, perché l'alternativa sarebbe saltare elementi in silenzio. La soluzione è separare la decisione dall'azione: prima materializzo i candidati con .Where(...).ToList() e poi rimuovo, oppure uso direttamente RemoveAll, che fa tutto in una passata. Vale anche per i dizionari.
