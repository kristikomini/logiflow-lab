Looks simple, isn't

Eleven pieces of C# that a reasonable person reads, understands, and gets wrong. None of them are trick questions and none are obscure: every one has cost somebody a real afternoon, and most of them are asked in interviews for exactly that reason.

How to read this chapter

Predict before you scroll. Each one is a short program and a question. Say the answer out loud, or write it down, then read the explanation. Being wrong while paying attention is what makes these stick; reading the explanation of a puzzle you never attempted teaches nothing at all, which is why a list of "C# gotchas" on a blog is forgotten by Thursday.

They are ordered roughly by how often they bite. The first four will happen to you in your first year.

Numbers

1 — The discount that is always zero

decimal price = 200m;
decimal discount = price * (5 / 100);

Console.WriteLine(discount);      // ?
Why
  • It prints 0. Not 10.
  • 5 / 100 — both sides are int literals, so this is integer division, decided entirely by the operands and not at all by what it is being assigned to. It evaluates to 0, discarding the remainder, before decimal is ever involved.
  • price * 0 — the multiplication is then perfectly correct and perfectly useless. Nothing warns, because nothing is wrong: the compiler was asked to divide two integers and it did.
  • The fix is one character: 5m / 100m, or 5 / 100m — one decimal operand promotes the whole expression. 0.05m is better still, because it removes the arithmetic entirely.
  • Why it survives review: the line reads as mathematics, and mathematics has no integer division. Everybody knows the rule and nobody sees it here, which is the definition of this chapter.

2 — The total that does not equal itself

double total = 0;
for (var i = 0; i < 10; i++) total += 0.1;

Console.WriteLine(total == 1.0);        // ?
Console.WriteLine(total);                // ?

decimal exact = 0m;
for (var i = 0; i < 10; i++) exact += 0.1m;

Console.WriteLine(exact == 1.0m);       // ?
Why
  • False, then 0.9999999999999999, then True.
  • double — a binary fraction. One tenth cannot be written exactly in binary any more than one third can be written exactly in decimal, so each += 0.1 adds something very slightly wrong and the error accumulates.
  • total == 1.0 — and this is why you never compare floating-point values with ==. You compare the difference against a tolerance, or you use a type that does not have the problem.
  • decimal — a decimal fraction, so one tenth is exact. This is the whole reason the type exists, and the reason money goes in it.
  • The version that actually loses money: not this, but a double column in a database summed over a year of invoices, where the rounding drift shows up as a balance that is out by a few cents and nobody can explain it.
  • decimal is slower and has a smaller range. That is the trade, and it is the right trade for money and the wrong one for physics — see chapter 00b.

References, values and copies

3 — Two strings that are equal but not the same

string a = "logiflow";
string b = "logiflow";
string c = new("logiflow".ToCharArray());

Console.WriteLine(a == b);                        // ?
Console.WriteLine(a == c);                        // ?
Console.WriteLine((object)a == (object)b);        // ?
Console.WriteLine((object)a == (object)c);        // ?
Why
  • True, True, True, False. The last one is the surprise, and the third is the reason the last one surprises.
  • a == b and a == c — string overloads == to compare contents. This is a special case; almost no other reference type does it.
  • (object)a == (object)b — casting to object changes which == the compiler picks, at compile time, to the reference comparison. It still prints True, because identical literals are interned: the runtime stores one copy and both variables point at it.
  • (object)a == (object)c — c was built at run time, so it is a different object with the same letters. False. Nothing about the code says so, and the line above it suggested the opposite.
  • The rule to take away: which == runs is decided by the declared type of the variables, not by what is in them. When in doubt use string.Equals(a, c, StringComparison.Ordinal), which says what it means and cannot be changed by a cast.
  • Where it bites for real: a Dictionary<object, …>, a cache keyed on object, or a generic method that compares T with == — which silently becomes a reference comparison for every reference type.

4 — The struct that refuses to be updated

struct Point { public int X; public int Y; }

var points = new List<Point> { new() { X = 1 }, new() { X = 2 } };

foreach (var p in points) { var q = p; q.X = 99; }
Console.WriteLine(points[0].X);            // ?

var array = points.ToArray();
array[0].X = 99;                         // compiles
Console.WriteLine(array[0].X);             // ?

points[0].X = 99;                        // does NOT compile — why?
Why
  • 1, then 99, and the last line is a compiler error. Three different answers for what looks like the same operation.
  • var q = p — Point is a value type, so this is a copy. Setting q.X changes the copy and the list never hears about it. The loop is a no-op that looks like work.
  • array[0].X = 99 — an array indexer returns a reference to the element, so this writes into the array itself. It compiles and it works.
  • points[0].X = 99 — List<T>'s indexer is a property, and a property returns a copy. Assigning to a field of a temporary copy would be pure waste, so the compiler refuses: "cannot modify the return value … because it is not a variable". The error is the language protecting you from the bug in the first line.
  • The fix, and the lesson: points[0] = points[0] with { X = 99 }, or read-modify-write the whole element. Better: make mutable structs readonly record struct so the question cannot come up. Mutable value types are the single most confusing corner of C# and the guidance from Microsoft is to avoid them.

5 — The dictionary that loses your key

class Sku
{
    public string Code = "";
    public override bool Equals(object? o) => o is Sku s && s.Code == Code;
}

var stock = new Dictionary<Sku, int>();
stock[new Sku { Code = "A-1" }] = 10;

Console.WriteLine(new Sku { Code = "A-1" }.Equals(new Sku { Code = "A-1" }));  // ?
Console.WriteLine(stock.ContainsKey(new Sku { Code = "A-1" }));                 // ?
Why
  • True, then False. Two objects that are equal, in a dictionary that cannot find one using the other.
  • Equals overridden, GetHashCode not — the inherited GetHashCode is based on the object's identity, so two equal Skus get different hash codes.
  • How a hash lookup works: hash first to pick a bucket, then Equals within that bucket. Two equal objects in different buckets never meet, so Equals is never even called. The lookup is not slow — it is wrong.
  • The contract: equal objects must return equal hash codes. The reverse is not required (collisions are legal and normal). The compiler warns about this one — CS0659 — which is a good argument for not ignoring warnings.
  • The fix: override both, or use a record, which generates a matching pair for you. Then never mutate an object while it is a key — changing Code after insertion moves the object's hash and strands it in the old bucket, which is the same bug arriving by a different route.

Things that have not happened yet

6 — The query that gives two different answers

var rng = new Random(1);
var numbers = new[] { 1, 2, 3, 4 };

var noisy = numbers.Select(n => n + rng.Next(100));

Console.WriteLine(noisy.Sum());            // ?
Console.WriteLine(noisy.Sum());            // the same?
Console.WriteLine(noisy.Count() == noisy.Count());  // ?
Why
  • Two different sums. noisy is not a sequence of numbers — it is a recipe for producing one, and it is followed again from the start every time something asks for the items.
  • Select — deferred execution. Nothing ran on this line. No Random was called, no array was walked; an object was created that knows how to do it later.
  • noisy.Sum() — this is what runs the recipe, drawing four fresh random numbers. The second Sum() runs it again and draws four more.
  • Multiple enumeration is the general name for the bug, and it is much worse with EF Core: an IQueryable that is enumerated in three places is three round trips to SQL Server, which is how a page that "only loads a list" makes ninety queries.
  • The fix is one call: .ToList() at the point where you want the work to happen. The rule of thumb: pass IEnumerable around while you are still composing, materialise once when you start using the results.
  • And the reason it is not simply a mistake: the same laziness is what lets Where().Select().Take(10) stop after ten items instead of transforming a million. See chapter 06.

7 — The file that closes too early

static IEnumerable<string> ReadLines(string path)
{
    using var reader = new StreamReader(path);

    string? line;
    while ((line = reader.ReadLine()) != null)
        yield return line;
}

var lines = ReadLines("orders.csv");      // does the file open here?
File.Delete("orders.csv");                  // does this throw?
Console.WriteLine(lines.Count());          // ?
Why
  • No, no, and the last line throws FileNotFoundException. The method body has not run at all yet.
  • yield return — the compiler rewrites the whole method into a state machine. Calling ReadLines constructs that machine and returns immediately: not one line of the body executes until something enumerates it.
  • using var reader — so the StreamReader is not created on the call either. The using is real and does work — but only during enumeration, and it disposes when the enumeration finishes or is abandoned.
  • File.Delete — succeeds, because nothing has the file open. A reader who believes the file is open at this point has the model exactly inverted.
  • The subtle production version: a method like this returned from a repository, enumerated by a caller who stops at the first match. The stream is disposed correctly on foreach exit — but if the caller stores the IEnumerable and enumerates it twice, the file is opened twice.
  • The rule: a method that both owns a resource and yields is a method whose laziness is part of its contract. Say so in its name (StreamLines), or return a List and be honest about reading it all.

8 — The closure that captured the wrong thing

var actions = new List<Action>();

for (var i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));

foreach (var a in actions) a();          // ?

var others = new List<Action>();

foreach (var n in new[] { 0, 1, 2 })
    others.Add(() => Console.Write(n));

foreach (var a in others) a();           // ?
Why
  • 333, then 012. Same shape, two different answers, and the difference is a language change from 2012.
  • for (var i = 0; …) — there is one i for the whole loop. All three lambdas capture that one variable, not its value at the time, so by the time they run it holds 3.
  • foreach (var n in …) — C# 5 made the foreach variable a fresh variable per iteration, precisely because this was the most reported bug in the language. So each lambda captures its own n.
  • The for loop was deliberately left alone, because i is genuinely one variable that the loop body is allowed to change. The inconsistency is the price of not breaking existing code.
  • The fix: copy it inside the loop — var captured = i; actions.Add(() => Console.Write(captured));
  • Where you will meet it: event handlers wired in a loop, and Task.Run in a loop — where the timing makes it non-deterministic and therefore much harder to see. More in chapter 04.

Time, threads and waiting

9 — The web request that hangs forever

// In an ASP.NET (Framework) controller or a WinForms handler
public ActionResult Index()
{
    var data = LoadAsync().Result;      // what happens here?
    return View(data);
}

private async Task<Data> LoadAsync()
{
    var json = await _http.GetStringAsync(_url);
    return Parse(json);                // ← never reached
}
Why
  • It deadlocks. No exception, no timeout, no log line — the request simply never finishes, and under load the thread pool fills with requests doing the same thing.
  • .Result — blocks the current thread until the task completes, and that thread is holding the request's synchronisation context.
  • await _http.GetStringAsync(_url) — when the HTTP call comes back, the continuation (return Parse(json)) needs to resume on that same context, which is the thread that is blocked waiting for it. Each is waiting for the other.
  • Why it seems to work on some projects: ASP.NET Core removed the synchronisation context, so the same code merely wastes a thread instead of hanging. Move it to a WinForms app or a .NET Framework site — the region is full of them, see chapter 16b — and it hangs.
  • The fix is the boring one: async all the way up. Make the action public async Task<ActionResult> Index() and await LoadAsync(). ConfigureAwait(false) in the library avoids the deadlock too, but it treats the symptom.
  • And async void is the same family: nothing can await it, so an exception inside it is not caught by the caller's try — it goes straight to the process. Only event handlers may be async void. Chapter 07 has the full version.

10 — The timestamp that is an hour out twice a year

var placed = DateTime.Now;                      // stored in the database
var deadline = placed.AddHours(24);

Console.WriteLine(deadline - placed);            // ?

var fromDb = new DateTime(2026, 3, 29, 10, 0, 0);   // Kind = Unspecified
var now = DateTime.UtcNow;                      // Kind = Utc

Console.WriteLine(fromDb < now);                 // comparing what, exactly?
Why
  • The first prints 24:00:00 — which is the bug. On the night the clocks change, twenty-four hours after 10 a.m. is not 10 a.m.
  • DateTime.Now — local time on this machine, with no record of which time zone that was. The same instant recorded on a server in Milan and a laptop in London produces two different values that look equally valid.
  • AddHours(24) on a local DateTime — adds elapsed hours, not calendar days. AddDays(1) is a different operation, and on a DST boundary they give different answers. Neither is wrong; they answer different questions.
  • fromDb < now — DateTime comparison ignores Kind entirely. One value is UTC, the other is "we did not say", and the operator compares the raw ticks as though they were the same clock. Silently out by your offset for half the year.
  • The rules that avoid the whole family: store and compute in DateTime.UtcNow; convert to local only when rendering for a human; use DateTimeOffset when you need to keep the offset the event happened at; never put a local time in a database column.
  • The interview version: "what is the difference between DateTime.Now and DateTime.UtcNow" is a screening question, and the answer that lands is the second half — and that is why everything stored is UTC.

11 — The list you are deleting from while reading it

var ids = new List<int> { 1, 2, 2, 3 };

foreach (var id in ids)
    if (id == 2) ids.Remove(id);        // ?

var more = new List<int> { 1, 2, 2, 3 };

for (var i = 0; i < more.Count; i++)
    if (more[i] == 2) more.RemoveAt(i);   // ?
Why
  • The first throws InvalidOperationException; the second leaves a 2 behind. The second is worse, because it is silent.
  • foreach over a modified list — List<T> keeps a version number and the enumerator checks it: "Collection was modified; enumeration operation may not execute." A loud, immediate, honest failure.
  • RemoveAt(i) inside a forward for — removing index 1 shifts everything down, so the second 2 moves into index 1 and i++ steps straight over it. Every removal skips its neighbour.
  • The three fixes, in order of preference: ids.RemoveAll(id => id == 2); iterate a copy with foreach (var id in ids.ToList()); or walk the for loop backwards, where removals only shift items you have already passed.
  • The concurrent version of the same mistake is not a skipped element but a corrupted list: two threads writing to a List<T> can leave it in a state with no valid contents at all. ConcurrentDictionary and friends exist for that — chapter 08.
⚠ What these have in common

Every one of them is a case where the code says one thing and the mental model says another, and the mental model is the one you read with. Not one is fixed by knowing more syntax.

Three mental models cause most of them, and they are worth stating as models rather than as rules, because a model generalises to the puzzle you have not met yet:

  • When does this run? — LINQ, yield return, Task. The line that creates the work is not the line that does it.
  • Am I holding the thing, or a copy of it? — value types, structs in collections, DateTime, string immutability.
  • Which overload did the compiler actually pick? — == on object, integer division, implicit conversions. It decides from the declared types, not from your intention.
Try it yourself

Run them. Every one of these fits in a scratch console app, and the versions of them you are told about are forgotten a great deal faster than the versions you watched print the wrong thing: 

dotnet new console -o Puzzles
cd Puzzles
# paste one puzzle into Program.cs, then:
dotnet run
Line by line
  • dotnet new console -o Puzzles — a throwaway project, outside this repository. Nothing here needs to be kept.
  • dotnet run — builds and runs in one step. Change one character, run again: that loop is the fastest way to test a mental model there is.
  • Then break them on purpose. In puzzle 4, change struct to class and predict the new output before you run it. In puzzle 8, change the for to a foreach. Being able to predict the change is what proves the model, not being able to recite the answer.
  • Keep the file. The week before an interview, reading your own scratch file of things that surprised you is worth more than any list somebody else wrote.

Golden rules

  1. Integer division is decided by the operands, never by the variable it is assigned to.
  2. Never compare double values with ==; money goes in decimal.
  3. Which == runs depends on the declared type, so a cast to object changes the answer.
  4. Value types copy on assignment, including into and out of a collection.
  5. Override Equals and you must override GetHashCode, or hash lookups silently fail.
  6. LINQ is a recipe, not a result: enumerate twice and the work happens twice.
  7. A method with yield return runs none of its body until it is enumerated.
  8. A lambda captures the variable, not its value — and for has one variable for the whole loop.
  9. .Result and .Wait() on a context-bound thread is a deadlock; go async all the way up.
  10. Store UTC, render local, and remember DateTime comparison ignores Kind.
  11. Never modify a collection you are iterating; RemoveAll, a copy, or iterate backwards.
  12. When the output surprises you, the bug is in your model of when the code runs — start there.

Interview questions

"Why is 0.1 + 0.2 == 0.3 false?"

Almost universal as a warm-up. Answer the mechanism, not the fact: "double is binary, and one tenth has no exact binary representation, so both operands are already slightly off before the addition." Then get the point in: "which is why money is decimal — it is a decimal fraction, so tenths and hundredths are exact."

"What is deferred execution, and why does it matter?"

"A LINQ query is a description of work, not the results of it — nothing happens until you enumerate." Then the consequence that shows you have hit it: "so enumerating twice does the work twice, and over IQueryable that is two trips to the database. I materialise with ToList at the point where I stop composing and start using."

"If I override Equals, what else must I do?"

"GetHashCode, consistently — equal objects must hash equal, or a Dictionary or HashSet will not find them." The sentence that makes it concrete: "the lookup does not go slow, it comes back false, which is much harder to notice."

"You call an async method with .Result and the app freezes. What is happening?"

Name the mechanism in one sentence: "the continuation after the await needs the synchronisation context, and .Result is blocking the thread that owns it, so each waits for the other." Then the fix and the caveat: "async all the way up; ConfigureAwait(false) also breaks the cycle but only hides the design problem, and on ASP.NET Core there is no context, so the same code silently just wastes a thread."

"Why does modifying a list inside a foreach throw?"

"The enumerator holds a version number and checks it on every step, so the failure is deliberate rather than incidental." Then the part that shows experience: "the for loop with RemoveAt is the one I worry about more — it does not throw, it just skips the next element, and that reaches production."

"Give me an example of a bug that was hard to find."

Anything on this page is a legitimate answer if it actually happened to you, and this question is asked constantly. The structure that works: the symptom first ("a total was out by a few cents, but only on some orders"), the false lead, then the mechanism — and finish with what you changed so the whole class of it cannot come back, not just the line.
