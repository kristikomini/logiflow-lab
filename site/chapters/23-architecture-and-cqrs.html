Layers, clean architecture and CQRS

You now know C#, SQL, EF Core and HTTP. This chapter is about the question that comes after all of them and has no compiler to answer it: where does this code go? Get it consistently right and a stranger can find anything in your codebase in thirty seconds. Get it wrong and every change touches every file.

Why this chapter exists

"Clean architecture", "DDD" and "CQRS" appear in backend adverts across Bologna, Modena and Milano constantly, usually with no explanation of what the company means by them. More importantly, "dove metteresti questa regola?" — where would you put this rule? — is how a reviewer finds out in one question whether you have worked on a real codebase or only on tutorials.

Why layers at all

🧒 Simple

Think of a kitchen. Ingredients in the pantry, cooking at the stove, plates out through the hatch. Now imagine a kitchen where the pantry is also the stove and the hatch, all in one heap. You could still cook — for a while. Then somebody wants to change the menu and has to move the fridge.

Layers are just deciding, once, which shelf each thing lives on, so that everyone puts things back in the same place.

🎓 Professional

Layering is about the direction of dependencies, not about folders. Anyone can create four folders. The value appears only when there is a rule about which may reference which, and something that enforces it.

The rule in clean architecture (also called hexagonal, ports-and-adapters, or onion — they are variations on one idea) is: dependencies point inwards, towards the business rules, and the business rules point at nothing. Everything volatile — the database, the web framework, the message broker, the clock — sits on the outside where it can be replaced without the centre noticing.

The four projects, and the one rule

ProjectContainsMay reference
DomainEntities, value objects, business rules, domain eventsnothing but the BCL
ApplicationUse cases (one class per operation), interfaces it needs, DTOsDomain
InfrastructureEF Core, repositories, Redis, HTTP clients, the clockApplication, Domain
Api / WebEndpoints, model binding, auth, DI compositionApplication (+ Infrastructure at startup only)
🎓 What this actually buys you

Not "we could swap SQL Server for MongoDB" — nobody does that. Three real things:

  • Fast tests. Domain rules test in milliseconds with no container, because Order has no idea a database exists.
  • A place for every rule. New joiners stop asking, and stop guessing differently each time.
  • Framework churn is contained. The web framework you use will change over ten years; the rule about when an order may be cancelled will not.

Where does this rule go?

This is the question worth being able to answer instantly. A rough decision procedure:

The ruleGoes inBecause
"An order must have at least one line"DomainTrue regardless of who asks, or how
"A cancelled order cannot be submitted"DomainAn invariant of the aggregate itself
"Only a manager may cancel over €10 000"ApplicationNeeds the current user — a use-case concern
"Reserve stock, then save, in one transaction"ApplicationOrchestration across aggregates
"Retry the e-mail send three times"InfrastructureA property of that particular technology
"Return 409 when the state is wrong"ApiHTTP is a delivery detail
"The date must not be empty"Api / ApplicationInput validation, not a business rule
⚠ The anemic domain model

The most common failure. Order becomes a bag of public setters, and every rule lives in a service that reaches in and mutates it. You now have the ceremony of four projects with none of the benefit: the invariants are scattered, nothing stops the next handler from setting Status = Cancelled directly, and the "domain" is a database row with a class around it.

The tell is a setter. In this repository Order exposes behaviour (AddLine, Submit, Cancel) and its state is private, so an illegal transition does not compile.

CQRS: what it really separates

🧒 Simple

In a café there is a queue for ordering and a queue for picking up. They are different queues, because they need different things: ordering needs someone who can take money and get it right; pickup just needs to be fast.

CQRS is that: one lane for things that change something, another for things that only look. Same café, two lanes.

🎓 Professional

Command Query Responsibility Segregation says: use a different model for writing than for reading. That is all it says. In particular it does not require two databases, event sourcing, or eventual consistency — those are things people often build alongside it, and conflating them is the most common misunderstanding.

The motivation is that the two sides genuinely want opposite things. A write must protect invariants, so it loads a whole aggregate and works through behaviour. A read wants three columns joined across four tables, shaped for a screen, as fast as possible — and loading aggregates to build it is pure waste.

So in this repository: commands go through the domain and EF Core with change tracking; queries are IOrderQueries / IReportingQueries, projecting straight to DTOs with AsNoTracking or Dapper. Same database, two paths.

One handler per operation

the shape every use case takes
// The request: a record, no behaviour, names the intent.
public sealed record CreateOrderCommand(
    Guid CustomerId,
    IReadOnlyList<OrderLineDto> Lines) : IRequest<Result<Guid>>;

// The handler: orchestration only. No HTTP, no SQL, no logging,
// no transaction — those are behaviours wrapped around it.
public sealed class CreateOrderCommandHandler(
    ICustomerRepository customers,
    IOrderRepository orders,
    IOrderNumberGenerator numbers) : IRequestHandler<CreateOrderCommand, Result<Guid>>
{
    public async Task<Result<Guid>> HandleAsync(
        CreateOrderCommand request, CancellationToken ct)
    {
        var customer = await customers.GetByIdAsync(request.CustomerId, ct);
        if (customer is null) return OrderErrors.CustomerNotFound;

        var order = Order.Create(customer, await numbers.NextAsync(ct));
        //          ↑ the rules live in here, not out here
        ...
    }
}

Notice what the handler does not contain: no try/catch for logging, no BeginTransaction, no validation, no cache lookup. Those are the four pipeline behaviours from chapter 05, wrapped around every request. That is the practical reason CQRS-with-a-mediator is popular: once every operation has the same shape, cross-cutting concerns become one class instead of a line in two hundred methods.

Vertical slices beat horizontal folders

Inside Application, organise by feature, not by kind. Not Commands/, Handlers/, Validators/, Dtos/ — that spreads one change across four folders forever. Instead: 

Features/Orders/
    CreateOrder.cs        // command + handler + validator, one file
    SubmitOrder.cs
    CancelOrder.cs
    GetOrderById.cs
    SearchOrders.cs

Changing "create order" means opening one file. Deleting the feature means deleting one file. This is the layout this repository uses, and it is the single easiest improvement to make to a codebase that already has layers.

⚠ Architecture as costume

Four projects, a mediator and a repository over a CRUD app with nine tables and no business rules is more expensive than a controller talking to DbContext, not less. Be able to say this out loud, because an interviewer who has been burned by an over-engineered internal tool is listening for it.

The honest test: does this application have rules that must hold no matter who asks? If yes, the domain layer earns its keep. If it is forms over data, a tidy two-layer app is the professional answer.

Try it yourself

Watch the architecture defend itself. Add this line to any file in the Domain project:

using Microsoft.EntityFrameworkCore;
dotnet test tests/LogiFlow.ArchitectureTests

It fails, by name, in milliseconds — see LayeringTests.cs. That is the difference between a convention written in a README and a rule the build enforces. Then try the opposite direction: reference LogiFlow.Infrastructure from LogiFlow.Application and watch it fail too.

Golden rules

  1. Layers are about dependency direction. Folders alone achieve nothing.
  2. Dependencies point inwards. The Domain references nothing.
  3. The interface lives with the code that needs it, not with the code that implements it.
  4. A rule that is always true belongs in the Domain; a rule about this use case belongs in Application.
  5. HTTP status codes, JSON and headers are delivery details. Keep them in the Api project.
  6. Public setters on an entity are the beginning of an anemic domain model.
  7. CQRS separates models, not databases. Two databases is a later, separate decision.
  8. Commands change state and return little; queries return data and change nothing.
  9. One file per use case, grouped by feature, not by artefact type.
  10. Cross-cutting concerns are pipeline behaviours, not lines inside handlers.
  11. Enforce the layering with architecture tests, or it will decay within a year.
  12. Do not put four layers around an application that has no rules to protect.

Interview questions

"Che cos'è la clean architecture?"

One sentence: dependencies point inwards, and the business rules depend on nothing. Then make it concrete with the file-location trick — the repository interface lives in Application and the EF Core implementation in Infrastructure, so Infrastructure depends on Application and never the reverse. Finish with the benefit you actually get: the domain tests run in milliseconds with no database.

"What is CQRS, and does it need two databases?"

Different models for reads and writes; no, it does not. Say plainly that CQRS is routinely confused with event sourcing and read replicas, which are separate choices you might add later. Then describe your own version: aggregates and change tracking on the write side, AsNoTracking projections straight to DTOs on the read side, one database.

"Where would you put the rule 'only a manager can cancel an order over €10 000'?"

Application, not Domain — it depends on who is asking, and the Domain does not know about users or the current request. The Domain owns "a cancelled order cannot be submitted", which is true no matter who asks. The distinction they are testing is invariant versus policy, so name it.

"Is this not over-engineering for a small application?"

Sometimes yes, and say so. Give the test you apply: does the application have invariants that must hold regardless of the caller? If it is forms over data, a controller and a DbContext is the right answer and four projects are cost with no return. An interviewer asking this is usually checking for judgement, not loyalty to a diagram.

"How do you stop the architecture decaying?"

Tests over the dependency graph. NetArchTest asserts that Domain references nothing and that Application does not reference Infrastructure; they run in milliseconds because they only read assembly metadata. Conventions in a README decay silently — a red build does not.
