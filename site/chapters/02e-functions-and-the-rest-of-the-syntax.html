Functions, and the rest of the syntax

Chapter 00c taught you to write a method that takes two numbers and returns one. Real code is full of method declarations that look nothing like that — static, this, params, out var, =>, yield return, a tuple in the return position, an attribute on the line above. None of it is hard. All of it is unreadable until somebody names it, which is what this chapter does.

Why this chapter exists

This is the gap between "I can write C#" and "I can read C#". The course goes from the basics straight into OOP, LINQ and async, each of which assumes you already recognise the shapes on this page — an extension method, a local function, an expression-bodied property, an iterator. A reader who has not met them spends their attention decoding the declaration instead of following the argument. Everything here is syntax; nothing here is deep. That is precisely why not knowing it is so expensive.

The anatomy of a declaration

🧒 Simple

A method declaration is a label on a machine. Reading left to right it says: who is allowed to use this, whether it belongs to the class or to one object, what comes out, what it is called, and what has to go in. Every extra word you have never seen is answering one of those five questions and nothing else. 

public static async Task<int> CountAsync(string code, int max = 10)
{
    return await Repository.CountAsync(code, max);
}

private int Add(int a, int b) => a + b;   // expression-bodied

internal void Log(string message) { … }      // void: returns nothing
Line by line
  • public — the access modifier. private is this class only, internal this assembly, protected this class and anything deriving from it, public everyone. Omit it entirely and a class member defaults to private, which is the right default and why you can often say nothing at all.
  • static — the method belongs to the type, not to an instance, so there is no this inside it and callers write Maths.Add(…) rather than creating an object first.
  • async — permission to use await in the body. It is not part of the signature a caller sees: what they see is Task<int>. You can remove async and return the task directly without breaking anyone — chapter 07.
  • Task<int> — the return type. void means nothing comes back, and a method returning nothing is a method that exists for its side effect.
  • int max = 10 — an optional parameter. The default must be a compile-time constant, and it is baked into the call site, which matters for exactly the same versioning reason const does in chapter 02c.
  • => a + b; — an expression-bodied method: shorthand for a body that is a single expression. There is an implied return. The same arrow works on properties, constructors, indexers and operators.

Parameters: the five ways a value gets in

Ship("MI-42", express: true);              // named argument — order-free, self-documenting

int Sum(params int[] n) => n.Sum();
Sum(1, 2, 3);                                // params: any number of arguments
Sum();                                       // legal — an empty array

if (int.TryParse(text, out var n))         // out var: declare it right there
    Console.WriteLine(n);                    // and n is in scope out here too

void Swap(ref int a, ref int b)
{
    (a, b) = (b, a);                         // tuple swap — no temporary needed
}
Line by line
  • express: true — a named argument. It is the cure for the boolean at a call site that nobody can read: Ship("MI-42", true) tells you nothing, and this tells you everything. Named arguments may also be given out of order, and mixing them with positional ones is allowed as long as the positional ones come first.
  • params int[] n — any number of arguments, gathered into an array by the compiler. Must be the last parameter. Calling with none gives an empty array, not null, which is why Sum() is 0 rather than a crash.
  • out var n — declaring the variable in the argument list. Before C# 7 this needed a separate line above. Note the scope: n lives on after the if, which is what makes the pattern readable.
  • ref int a — the method operates on the caller's variable. Both call site and declaration must say ref, deliberately: a reader at the call site can see that their variable might change.
  • (a, b) = (b, a); — a tuple assignment. The right-hand side is fully evaluated before anything is assigned, so this swaps correctly with no temporary variable. It works for any number of values.
⚠️ Optional parameters are baked into the caller

Write void Send(string to, int retries = 3) in a library, ship it, then change the default to 5. Every already-compiled caller keeps passing 3, because the default was copied into their call site at compile time, not looked up at run time. Inside a single application this never matters. Across an assembly boundary it is the same versioning trap as const, and the fix is the same: use an overload instead when the value may genuinely change.

Overloading: several methods, one name

void Print(int n)     => Console.WriteLine($"int {n}");
void Print(double d)  => Console.WriteLine($"double {d}");
void Print(object o)  => Console.WriteLine($"object {o}");

Print(1);        // int 1
Print(1.0);      // double 1
Print("x");      // object x
Print(null);     // object  — the only one that accepts it

byte b = 1;
Print(b);        // int 1 — byte widens to int, the closest match
Line by line
  • Three methods, one name, different parameter lists. That is the entire definition of an overload. The return type is not part of it: two methods differing only in what they return will not compile.
  • Print(1) — overload resolution picks the most specific applicable one. An int could widen to double or box to object, and the exact match wins over both.
  • Print(null) — null is not an int or a double, so only the object version applies. Add a Print(string) overload and this line silently changes meaning, because string is more specific than object. That is the danger of overloading on reference types.
  • Print(b) with a byte — no exact match, so the compiler looks for the cheapest implicit conversion: byte to int beats byte to double. The rules are long and you should not need them; if you are consulting them, the design is too clever.
  • The practical guidance: overload when the methods genuinely do the same thing to different inputs. When they do different things, give them different names. Save and SaveAndNotify read better than two Saves.

Returning more than one thing

// A tuple: names are optional but always worth writing
(bool ok, string error) Validate(Order o)
{
    if (o.Quantity <= 0) return (false, "quantity must be positive");
    return (true, "");
}

var (ok, error) = Validate(order);            // deconstruct into two variables
var result = Validate(order);                 // or keep it whole
Console.WriteLine(result.error);              // and use the names

record Result(bool Ok, string Error);          // when it crosses a public boundary
Line by line
  • (bool ok, string error) — a value tuple as a return type. Two values, no class to declare. Without the names it would be (bool, string) and callers would write .Item1, which is how you lose an afternoon.
  • return (false, "…"); — a tuple literal. The parentheses are the whole syntax.
  • var (ok, error) = … — deconstruction, splitting the tuple into two ordinary variables. Use _ for a slot you do not want, as in chapter 02c.
  • record Result(…) — the alternative, and the right one for anything public. Tuples are perfect inside a method or between two private helpers; they are poor on an API surface, because the names are a compiler convenience and carry no documentation, no validation and no place to add a third field without breaking callers.

Local functions, and lambdas as arguments

int Total(List<Line> lines)
{
    static decimal LineTotal(Line l) => l.Price * l.Qty;   // local function

    decimal sum = 0;
    foreach (var l in lines) sum += LineTotal(l);
    return (int)sum;
}

var big = lines.Where(l => l.Qty > 10).ToList();      // lambda as an argument
Func<Line, bool> isBig = l => l.Qty > 10;            // the same lambda, stored
var same = lines.Where(isBig).ToList();
Line by line
  • static decimal LineTotal(…) inside a method — a local function. It exists only inside Total, which is the point: a helper that is nobody else's business does not belong on the class.
  • The static on a local function means it may not capture anything from the enclosing method. Write it whenever it compiles: it documents that the helper depends only on its arguments, and it avoids a hidden allocation.
  • l => l.Qty > 10 — a lambda: an unnamed function written where it is used. The parameter type is inferred from the method being called.
  • Func<Line, bool> — the type of a function. Func<A, B, R> takes A and B and returns R; Action<A> takes A and returns nothing; Predicate<A> is a Func<A, bool> with a better name. Once functions have types, they can be parameters and return values like anything else — chapter 04 is where that becomes a design tool rather than a curiosity.

Extension methods: adding a verb to somebody else's type

public static class StringExtensions
{
    public static bool IsOrderCode(this string s) =>
        s is { Length: 5 } && s.StartsWith("MI-");
}

bool ok = "MI-42".IsOrderCode();       // reads like a built-in method
bool same = StringExtensions.IsOrderCode("MI-42");   // what it compiles to
Line by line
  • static class — extension methods must live in one. A static class cannot be instantiated and holds nothing but static members.
  • this string s — the this modifier on the first parameter is the entire mechanism. It tells the compiler this method may be called as though it were a member of string.
  • "MI-42".IsOrderCode() — the call, which looks like a method on string and is not. Nothing is added to string; the compiler rewrites this into the plain static call on the line below.
  • Two consequences worth knowing. An extension method is found only if its namespace is in scope, which is why a missing using makes methods "disappear" — LINQ is entirely extension methods on IEnumerable<T>, which is why forgetting using System.Linq; hides Where and Select. And a real instance method always wins over an extension of the same name, so adding one to the class later silently takes over.
  • It also works on null: ((string)null).IsOrderCode() does not throw on the call itself, because there is no instance to dereference. The method body then does.

Iterators: yield return

A method that returns IEnumerable<T> and contains yield return is not a method that builds a list. It is a method that gets paused and resumed, producing one item each time the caller asks for the next — which is why it can describe an infinite sequence without running out of memory. 

IEnumerable<int> EvensUpTo(int max)
{
    Console.WriteLine("starting");        // does NOT run at the call
    for (int i = 0; i <= max; i += 2)
        yield return i;                   // hand one out, then pause here
}

var seq = EvensUpTo(6);                 // nothing printed, nothing computed
foreach (var n in seq) Console.Write(n);  // "starting" then 0246
var first = seq.First();                // runs it again, from the top
Line by line
  • IEnumerable<int> plus yield return — the compiler rewrites the whole method into a state machine class. Your code never sees it, but that is what the locals are stored in between items.
  • Console.WriteLine("starting") — deferred. Calling EvensUpTo(6) runs none of the body; it only constructs the state machine. The first line does not execute until the first item is requested.
  • yield return i; — hand out one value and freeze. The loop variable i survives the pause. There is also yield break; to stop early.
  • seq.First() — enumerates the sequence again, from the beginning, printing "starting" a second time. An IEnumerable is a recipe, not a result — the same deferred-execution point exercise 13 of chapter 02d makes about LINQ, which is built out of exactly this mechanism.
  • Where it earns its keep: reading a million-row file. Return IEnumerable<string> with a yield return per line and memory stays flat, because only one line exists at a time. Return List<string> and the whole file is in RAM.

The members that are not methods

public class Cart
{
    private readonly List<Line> _lines = [];

    public Cart(string owner) => Owner = owner;      // constructor

    public string Owner { get; }                     // get-only property
    public int Count => _lines.Count;                // computed — no storage
    public required string Code { get; init; }      // set once, at creation

    public Line this[int i] => _lines[i];            // indexer: cart[0]

    public static Cart operator +(Cart c, Line l)     // operator overload
    {
        c._lines.Add(l);
        return c;
    }
}
Line by line
  • public Cart(string owner) — a constructor: no return type, same name as the class. Writing none gives you a free parameterless one; writing any takes that away.
  • public string Owner { get; } — a get-only auto-property, assignable only in the constructor. This is the property equivalent of readonly.
  • public int Count => _lines.Count; — an expression-bodied property. It is a getter that runs every time it is read, storing nothing. The arrow is the tell: a property with => is computed, one with { get; set; } has a hidden field behind it.
  • required … { get; init; } — init allows assignment in an object initialiser and never again, and required makes the caller supply it. Together they are how you get "must be set, cannot change" with no constructor.
  • this[int i] — an indexer, which is what lets you write cart[0]. It is a property whose name is this and which takes arguments.
  • operator + — an operator overload. Legal, occasionally lovely, usually a mistake: cart + line hides a mutation behind a symbol that every reader expects to be pure. Overload operators on value-like types — money, vectors, dates — and nowhere else.

The syntax around the code

namespace LogiFlow.Orders;              // file-scoped — no braces, no indent

using System.Text;
using static System.Math;             // then Sqrt(x) with no Math. prefix
using Codes = LogiFlow.Legacy.Codes;   // alias, for a name clash

[Obsolete("Use ShipAsync instead")]      // an attribute: metadata, not code
public sealed partial class Shipper
{
    public const string Prefix = nameof(Shipper);   // "Shipper", checked by the compiler
}
Line by line
  • namespace LogiFlow.Orders; — the file-scoped namespace, ending in a semicolon rather than wrapping the file in braces. Modern default; the braced form still works and is what you will see in older code.
  • using static System.Math; — imports the members of a static class, so Sqrt(x) works unqualified. Use sparingly: it removes the word that told the reader where a method came from.
  • using Codes = …; — an alias, for when two namespaces both define a Codes and you need to name one without typing its full path.
  • [Obsolete("…")] — an attribute: data attached to a declaration and read by the compiler, a framework or a tool. This one produces a build warning at every call site. Attributes are how ASP.NET routing, EF Core mapping, JSON serialisation and test discovery all work — they look like magic exactly until you know they are ordinary classes deriving from Attribute.
  • sealed prevents inheritance; partial lets one class be split across several files, which is how designers and source generators add to your class without touching your file.
  • nameof(Shipper) — produces the string "Shipper" at compile time. Rename the class and this follows; type the string by hand and it silently rots. Use it in exceptions, logging and property-changed notifications.

Exercises, with the reasoning shown

Exercise 1 — the method that ran nothing

IEnumerable<int> Numbers()
{
    throw new InvalidOperationException("nope");
    yield return 1;
}

var seq = Numbers();
Console.WriteLine("still here");
foreach (var n in seq) { }
It prints "still here", then throws at the foreach — line by line
  • var seq = Numbers(); — because the method contains yield return, it is an iterator, and calling it runs none of the body. The exception is not thrown here.
  • Console.WriteLine("still here") — prints normally.
  • foreach — asks for the first item, the body finally runs, and the exception surfaces here, at a line that contains no obvious call.
  • This is why argument validation in an iterator is written as a non-iterator wrapper method that checks its arguments and then returns a private iterator. Otherwise ArgumentNullException arrives at whatever line happened to enumerate, possibly in a different class.

Exercise 2 — which overload wins

void Show(object o) => Console.WriteLine("object");
void Show(string s) => Console.WriteLine("string");

object o = "hello";
Show(o);
Show("hello");
It prints object, string — line by line
  • object o = "hello"; — the object is a string, but the variable's declared type is object.
  • Show(o) — overload resolution happens at compile time from declared types, and the compiler only knows object. Prints object.
  • Show("hello") — the literal is a string, so the more specific overload wins. Prints string.
  • The contrast worth holding onto: overloads are chosen by declared type, overrides by actual type. That single sentence explains this exercise, the virtual versus new exercise in chapter 02c, and the boxed-int equality exercise in chapter 02b. Three puzzles, one rule.

Exercise 3 — the default that was already decided

// In a class library, version 1:
public void Retry(int times = 3) => Run(times);

// The caller, compiled against version 1:
service.Retry();

// The library ships version 2, changing the default to 5.
// The caller is NOT recompiled. How many times does it retry?
Three — line by line
  • service.Retry(); — the compiler inserts the default at the call site. The compiled caller literally contains Retry(3).
  • Shipping a new library does not change already-compiled code, so the caller keeps passing 3 and nothing anywhere reports a mismatch.
  • Recompiling the caller picks up 5. Which means the behaviour depends on when each assembly was built — the worst kind of dependency, because it is invisible in the source.
  • The fix for a public API is an overload: Retry() calling Retry(5). The default then lives in the library's own code, where changing it actually changes behaviour. Inside one application, optional parameters are fine and pleasant — the trap needs an assembly boundary to exist.
Try it yourself

Take any method you have already written and rewrite it four ways: as an expression-bodied member, as a local function inside its only caller, as an extension method, and as a Func<> stored in a variable. Three of the four will feel wrong for that particular method, and noticing which three, and why, is the exercise. Then write one iterator — a method that reads a file with yield return per line — and put a breakpoint on its first line to watch when it is actually hit.

Golden rules

  1. A signature answers five questions, always in the same order: who may call it, whether it belongs to the type or the object, what comes back, what it is called, what must go in. Anything unfamiliar in a declaration is one of those five.
  2. async is not the caller's contract — the Task is. It is only permission to use await in the body, and it can be removed by returning the task directly.
  3. Overloads are chosen by declared type; overrides by actual type. One sentence that explains overload resolution, virtual versus new, and why two boxed ints are not ==.
  4. Overload only when the methods do the same thing to different inputs. When they do different things, give them different names.
  5. Across an assembly boundary, use an overload rather than an optional parameter. The default is copied into each caller when they compile, so changing it in a library does not reach code already built.
  6. Name the argument when the value alone says nothing — a bare true at a call site is unreadable, and express: true is not.
  7. out for the Try… pattern; ref is rare enough to be a design smell in business code; in exists to avoid copying a large struct and for nothing else.
  8. Tuples inside a method, records on a public boundary. Tuple element names are a compiler convenience with no documentation, no validation and no room to grow.
  9. static on a local function whenever it compiles. It documents that the helper depends only on its arguments, and stops a later edit quietly reaching into the enclosing scope.
  10. Validate arguments in a non-iterator wrapper, never inside the iterator. A method with yield return runs none of its body until the first item is asked for, so the exception would surface at somebody else's foreach.
  11. An extension method is found by namespace. A missing using is why methods "disappear", and a real instance method of the same name always wins.
  12. nameof, never a hand-typed symbol name. The string follows a rename; the literal rots silently.
  13. Overload operators on value-like types only — money, vectors, dates. A + that mutates its left operand is a trap, because every reader expects the symbol to be pure.

Interview questions

"What is an extension method, and how does it work?"

A static method in a static class whose first parameter is marked this. The compiler then lets you call it as if it were an instance method on that parameter's type, and rewrites the call back into the plain static call. Nothing is added to the original type, so it works on types you do not own and cannot change — which is exactly what LINQ is: extension methods on IEnumerable<T>. Two things follow: the namespace has to be imported for the method to be visible, and a real instance method of the same name always wins.

"What does yield return do?"

It turns the method into an iterator. The compiler rewrites it as a state machine, so calling the method runs none of the body — it only builds the machine — and each time the caller asks for the next item, the body runs up to the next yield return and then freezes there, keeping its local variables. That gives you lazy evaluation and constant memory over a huge source, and it gives you one surprise: exceptions and argument validation surface at the foreach, not at the call, so validation belongs in a non-iterator wrapper.

"ref and out — when would you use each?"

out for the Try… pattern, where the method returns a bool for success and the real answer through the parameter; the caller does not have to assign it first and the method must assign it before returning. ref when the method genuinely modifies a variable the caller already owns, which is rare enough that I treat it as a design smell in ordinary business code — returning a new value, or a tuple, is almost always clearer. There is also in, which passes by reference read-only, and its only real use is avoiding the copy of a large struct.

"Che differenza c'è tra un metodo static e uno di istanza?"

Un metodo static appartiene al tipo, non all'oggetto: lo chiami come Classe.Metodo() e dentro non hai this, quindi può lavorare solo su quello che riceve come parametri. Un metodo di istanza ha accesso allo stato dell'oggetto. In pratica static va bene per le funzioni pure, tipo helper e conversioni; appena il metodo dipende da una dipendenza iniettata — un repository, un logger — deve essere di istanza, altrimenti quella dipendenza diventa uno stato globale e il codice non è più testabile.
