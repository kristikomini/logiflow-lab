Logging and observability

Chapter 27 is about the debugger. This one is about what you do when you cannot use it — because the code is running on Azure App Service, it failed once at 14:32 for one customer, and nobody can reproduce it. Observability is the discipline of building software that can answer questions you did not think to ask in advance.

Why this chapter exists

Adverts ask for "monitoraggio" and "troubleshooting in produzione" without saying what that means. It means this. It is also the skill that most visibly separates somebody who has supported software in production from somebody who has only written it — and an interviewer can tell within one answer.

The problem

🧒 Simple

Imagine a friend tells you their bike made a horrible noise yesterday afternoon. Not now — yesterday. You cannot hear it, and it will not do it again while you watch.

So instead you fit the bike with a little recorder that writes down what happened and when. Next time it makes the noise, you do not have to be there. You just read the notes.

Logging is writing the notes. The trick is writing down the right things, before anything goes wrong.

🎓 Professional

Monitoring answers questions you prepared for: is CPU high, is the site up. Observability is the property of being able to answer questions you did not prepare for, from the data the system already emits — "why were these three customers slow, only on Tuesday, only on checkout?"

It is conventionally built from three signals, and they answer different questions:

  • Logs — discrete events. What happened?
  • Metrics — numbers aggregated over time. How much, how often, how fast?
  • Traces — one request's journey across services. Where did the time go?

Structured logging — the single most useful habit

🧒 Simple

Two ways to keep a diary. One: "Today I ran 5 km in 30 minutes." Two: a table with columns date, distance, minutes.

Both say the same thing. But only the table lets you ask "which of my runs were slower than 6 minutes per kilometre?" without reading every page.

🎓 Professional

The difference is one character, and it is the highest-value thing in this chapter: 

logger.LogInformation($"Handled {name} in {ms}ms");        // ✗ one opaque string
logger.LogInformation("Handled {Name} in {Ms}ms", name, ms); // ✓ message + fields
Line by line
  • $"Handled {name} in {ms}ms" — interpolation, and it is wrong here. The values are baked into one opaque string before the logger ever sees them.
  • You cannot query it. "Show me every request slower than 500 ms" is impossible once ms is part of a sentence, and every distinct duration becomes its own unique message.
  • "Handled {Name} in {Ms}ms", name, ms — structured logging. The template and the values are stored separately, so Name and Ms arrive as queryable fields.
  • The braces are positional, matched to the arguments in order, not by name — so swapping two arguments silently mislabels both. The names are for the log system, not for binding.
  • The template is also the group key. Identical templates aggregate, which is what lets a dashboard say "this message occurred 40,000 times" — impossible with interpolation.
  • Analyzer CA2254 catches this, and it is worth turning on as an error.

The second form reaches Seq or Application Insights with Name and Ms as separately indexed properties. You can then ask "every request over 500 ms, grouped by name, last 24 hours" as a query. With interpolation you get a million unique strings and the only tool left is text search.

The Roslyn analyser CA2254 exists to catch exactly this. Turn it on and let the compiler enforce it.

Correlation: one id through everything

A single request touches the endpoint, a handler, EF Core, Redis and maybe another service. Ten concurrent users produce interleaved log lines. What makes them separable is a correlation id attached to every line — and in .NET you get one for free, because Activity.Current.TraceId is set by the framework.

a scope makes it stick to every line inside
using (logger.BeginScope(new Dictionary<string, object>
{
    ["CorrelationId"] = Activity.Current?.TraceId.ToString() ?? traceId,
    ["RequestName"]   = typeof(TRequest).Name
}))
{
    logger.LogInformation("Handling {RequestName}", name);
    var response = await next();          // everything in here inherits the scope,
    //                                        including EF Core's own logging
    logger.LogInformation("Handled {RequestName} in {Ms}ms", name, sw.ElapsedMilliseconds);
    return response;
}
Line by line
  • logger.BeginScope(...) — attaches fields to every log written inside the using, at any depth. You annotate once instead of passing an id through twelve method signatures.
  • using (...) as a statement with braces — the scope's lifetime is exactly the block. Disposal is what pops it.
  • Activity.Current?.TraceId — the W3C trace id that .NET maintains automatically and propagates across HTTP calls through the traceparent header. Correlation across services is already there; the job is to surface it.
  • ?? traceId — a fallback for when no activity is in flight, such as a background job.
  • typeof(TRequest).Name — the request type as a field, so logs can be grouped by use case.
  • await next() — this is a pipeline behaviour, the decorator from chapter 23. Everything inside inherits the scope, including EF Core's own logging — so the SQL statements are tagged with the correlation id too, which is what makes an incident traceable end to end.

Two things follow. First, this belongs in one place — a pipeline behaviour, not in every handler; see LoggingBehavior.cs. Second, return the trace id to the caller in your error response, as chapter 14 does with Problem Details. Then a customer can say "the error said 0HN7…" and you have their entire request in one query.

Health checks

liveness and readiness are different questions
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, tags: ["ready"])
    .AddRedis(redisConnection,      tags: ["ready"]);

// "Am I alive?" — if this fails, restart me.
app.MapHealthChecks("/health/live", new() { Predicate = _ => false });

// "Can I serve traffic?" — if this fails, take me out of rotation
// but do NOT restart me: the database being down is not my fault.
app.MapHealthChecks("/health/ready", new() { Predicate = h => h.Tags.Contains("ready") });
Line by line
  • AddHealthChecks() then .AddSqlServer(...) — checks that actually open a connection, rather than returning 200 because the process is alive.
  • tags: ["ready"] — labels, and the labels are what make the two endpoints below different.
  • /health/live with Predicate = _ => false — runs no checks at all. It answers only "is this process responding". If it fails, restart me.
  • /health/ready with the ready tag — "can I serve traffic". If it fails, take me out of rotation but do not restart me: the database being down is not something restarting fixes.
  • Conflating the two causes an outage. Put the database check on the liveness probe and a brief database blip makes Kubernetes restart every instance simultaneously, turning a degradation into a total failure.
  • A readiness check must also be cheap. It runs every few seconds per instance, so a query that scans a table is a self-inflicted load test.

Collapsing these into one endpoint is a classic outage amplifier: the database has a five-second blip, every instance reports unhealthy, the orchestrator restarts all of them at once, and now you have a cold start storm on top of a database blip.

⚠ Logging personal data

logger.LogInformation("Login attempt {@Request}", request) where the request contains a password, a token, an IBAN or a customer's address. It is now in your log backend, replicated, retained for ninety days and readable by anyone with dashboard access.

Under GDPR that is a processing activity you probably have not documented, and in Italy it is the kind of thing a DPO asks about directly. Log identifiers, not people: a customer id, not a name and e-mail. Never serialise a whole request object without knowing every field in it.

⚠ Log and rethrow
catch (Exception ex)
{
    logger.LogError(ex, "Failed");
    throw;                      // …and the layer above does the same
}
Line by line
  • logger.LogError(ex, "Failed"); throw; — the anti-pattern, and it looks responsible.
  • The layer above does the same thing, and so does the one above that. One failure becomes five stack traces in the log, which makes it look like five incidents.
  • "Failed" — and no context. No id, no parameters, nothing to search for. The stack trace says where; nothing says which.
  • Log where you handle, not where you catch. If you are rethrowing, you are not handling — so add context and let it travel, or do not catch at all.
  • One place should log unhandled failures: the global exception handler from chapter 14. It has the request, the trace id and the user, which is exactly the context this catch lacks.

One failure, five stack traces, and the on-call engineer counting how many incidents there were. Handle it or log it — not both. Log once, at the boundary that decides what the caller sees; a global exception handler is that boundary. And use throw;, never throw ex;, which resets the stack trace to the line you are standing on.

Line by line
  • docker compose up -d — starts the supporting containers detached. Note compose as a subcommand, not the older docker-compose binary.
  • In this repository the collector is optional. Program.cs asks "is an OTLP endpoint configured?" rather than "is this Development?" — a capability check, not an environment check, and the better habit.
  • dotnet run --project src/LogiFlow.Api — the API, which now exports traces and metrics to the collector started above.
  • Without the collector, traces and metrics are still recorded in-process and Serilog still writes to the console. Nothing is shipped anywhere, and nothing fails.

Make a request, then take the trace id from the response and find everything it touched:

curl -i http://localhost:5000/orders/does-not-exist
# the Problem Details body carries a traceId — grep the console for it
Line by line
  • curl -i — -i includes the response headers, which is where traceparent appears.
  • The 404 is deliberate. An error response is the one you most want to be able to trace, and it exercises the whole chain.
  • The Problem Details body carries a traceId, per chapter 13. That is the field a user can read out over the phone.
  • # — a shell comment.
  • Grep the console for it, and that is the exercise: one id, quoted by a user, finding the exact request in the log. Everything in this chapter exists to make that thirty seconds instead of an afternoon.

Then the experiment worth doing: change one log call in LoggingBehavior from a message template to string interpolation, restart, and look at the output. The line still reads fine to a human — and the structured fields are gone. That is the whole argument, visible in ten seconds.

Golden rules

  1. Message templates with named placeholders. Never string interpolation. Enable CA2254.
  2. Log identifiers, never people. No passwords, tokens, IBANs or addresses — ever.
  3. One correlation id, attached with a scope, returned to the caller on failure.
  4. Log once, at the boundary. Log-and-rethrow multiplies one failure into five.
  5. throw; preserves the stack trace. throw ex; destroys it.
  6. If everything is an Error, nothing is. Reserve it for "a user is affected".
  7. Cross-cutting logging is a pipeline behaviour, not a line in every method.
  8. Liveness and readiness are different endpoints with different consequences.
  9. Metrics answer "how many"; logs answer "what happened"; traces answer "where did the time go".
  10. Instrument with OpenTelemetry so the backend stays a configuration choice.
  11. Never log inside a tight loop — you will DoS your own log backend and your bill.
  12. A log line nobody would ever query is noise. Write it for the incident, not for now.

Interview questions

"What is structured logging and why does it matter?"

Logging a message template plus named fields rather than one formatted string, so the backend indexes the fields. Give the payoff as a question you can answer with one and not the other: "show me every request over 500 ms grouped by endpoint" is a query with structured logs and a text search with interpolated ones. Mention CA2254 — it shows you have actually enforced it.

"An error happened in production at 14:32 for one customer. What do you do?"

This is really "have you ever supported software?" Walk the path: get the trace id from the customer or from the error response, query the log backend filtered on it, and read the whole request across every component in order. Then say what makes that possible — a correlation id on every line and the trace id returned in the Problem Details body — because that is the part you have to build in advance.

"What are the three pillars of observability?"

Logs, metrics, traces — and immediately what each is for: discrete events, aggregated numbers, one request's path across services. Add that they are only useful joined, which is what the trace id does, and that OpenTelemetry is the standard for emitting all three so the backend stays swappable.

"What would you never put in a log?"

Passwords, tokens, card numbers, and personal data you have no reason to retain. Frame it as GDPR, not just tidiness: logs are replicated and retained, so a serialised request object with a customer's name and address is undocumented processing. Log the customer id instead.

"Difference between a liveness and a readiness probe?"

Liveness asks "is this process broken" and the remedy is a restart. Readiness asks "can it serve traffic right now" and the remedy is removal from the load balancer. Then give the reason to keep them apart: if a database blip fails liveness, every instance restarts simultaneously and you have turned a small blip into an outage.
