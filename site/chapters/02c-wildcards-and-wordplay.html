Wildcards, symbols and words that lie

C# reuses a small set of punctuation marks for a large number of unrelated jobs, and it reuses ordinary English words for things that are not what the English word means. Both are cheap to learn and expensive to guess at. This chapter is the decoder ring: what every symbol means in every position it can appear, and which pairs of near-identical words are actually asking different questions.

Why this chapter exists

You cannot look up a symbol. Typing ? or _ into a search box returns nothing useful, so the one thing a beginner most needs to ask about is the one thing they cannot ask about — and they carry on reading code with a hole in it. The word pairs are the same problem wearing a different coat: ref and out look interchangeable, const and readonly both mean "does not change", and nothing on the page tells you they are different questions until a code review does.

The underscore: the wildcard that means "I do not care"

🧒 Simple

When you fill in a form and a box does not apply to you, you draw a line through it. That is what _ is. It tells the compiler "something goes here, I know, and I am deliberately not giving it a name because I am never going to use it."

That is worth more than it sounds. A variable with a name is a promise that someone will read it later. A _ is a promise that nobody will — and it is a promise the compiler keeps, because you cannot accidentally use it afterwards. 

// 1 — discard an out parameter you do not want
if (int.TryParse(text, out _))
    Console.WriteLine("it is a number");

// 2 — the catch-all arm of a switch expression
string label = status switch
{
    1 => "new",
    2 => "shipped",
    _ => "unknown",
};

// 3 — skip a slot when deconstructing
(var _, var y) = GetPoint();

// 4 — a lambda parameter you will not use
button.Click += (_, _) => Save();

// 5 — NOT a discard: a private field, by convention
private readonly ILogger _logger;
Line by line
  • out _ — a discard. TryParse insists on somewhere to put the number; _ is a bin. No variable is created, so nothing is left in scope for you to misuse afterwards.
  • _ => "unknown" — the discard pattern in a switch expression: matches anything not already matched. It is the modern default:, and it must come last because arms are tried in order.
  • (var _, var y) = GetPoint(); — deconstruction. The method returns two things and you want the second, so the first slot is discarded by position.
  • (_, _) => Save() — two discards in one lambda, which is legal precisely because they are not variables: two real parameters both named _ would be a duplicate-name error. This is the common shape for an event handler that ignores sender and e.
  • _logger — the odd one out. An identifier that starts with an underscore is an ordinary variable with an ordinary name; the convention marks it as a private field so a reader can tell _logger from a local logger at a glance. The compiler attaches no meaning to it whatsoever.
⚠️ _ = SomethingAsync(); is a sentence, not a shrug

Assigning to a discard is how you say "I know this returns something and I am ignoring it on purpose". It silences the analyser warning — which is exactly why it deserves suspicion in review. Ignoring a returned Task means ignoring its exceptions too: if it faults, nothing anywhere will tell you. Chapter 07 covers what to do instead. The discard is honest; what it is being honest about may still be a bug.

Wildcards inside patterns

Pattern matching is where C# looks most like a language with wildcards, because a pattern is a shape with holes in it, and the holes come in three kinds: match anything and forget it (_), match anything and name it (var x), and match anything, several times (.., in a list pattern). 

string Describe(object o) => o switch
{
    null                       => "nothing at all",
    int n when n < 0          => "a negative number",
    int or long                => "a whole number",
    string { Length: 0 }      => "an empty string",
    string s                   => $"text of {s.Length} characters",
    Order { Quantity: > 100 }  => "a big order",
    var other                  => $"a {other.GetType().Name}",
};

int[] codes = [1, 2, 3, 4, 5];
bool startsWithOne = codes is [1, ..];        // true — 1, then anything
bool oneToFive     = codes is [1, .., 5];     // true — 1, anything, 5
bool threeLong     = codes is [_, _, _];    // false — exactly three items
Line by line
  • int n when n < 0 — a type pattern with a guard. The when clause is an ordinary boolean test bolted onto the pattern; it is what you reach for when the condition cannot be expressed as a shape.
  • int or long — an or pattern. There is and and not too, so not null and >= 1 and <= 9 are both patterns you can write inline.
  • string { Length: 0 } — a property pattern: the right type and a condition on one of its members. Ordering matters here — this arm must come before the plain string s arm, or the general one swallows it.
  • var other — the var pattern. It matches anything, like _, but gives the value a name so the arm can use it. It also matches null, which is why the null arm has to be first.
  • [1, ..] — a list pattern with a slice pattern. The .. means "any number of elements, including none" — the closest thing in the language to a true * wildcard. Only one .. may appear per list pattern, for the same reason a glob cannot have two * and stay unambiguous.
  • [_, _, _] — three single-element wildcards. Each _ stands for exactly one item, so this matches a three-item array and nothing else. That is the whole difference: _ is one, .. is any number.
👔 Professional

The reason interviewers like switch expressions is exhaustiveness. Over an enum without a _ arm, the compiler warns when a new member is added and nobody handled it — a genuinely useful warning. Adding _ => … silences it forever. So: a catch-all on unbounded input like object, yes; a catch-all over your own enum, think twice. You are choosing between a runtime surprise and a compile-time reminder.

The question mark, four different jobs

Four unrelated features share this character, and telling them apart is entirely about position: after a type, after a value, between two values, or paired with a colon.

WrittenCalledMeansCareful
int?nullable type this value type may also hold null On a value type it is a real, different type: Nullable<int>.
string?nullable annotation a note to the compiler that this reference may be null Changes nothing at run time. It buys warnings, not protection.
a?.Bnull-conditional evaluate .B only if a is not null The result becomes nullable, even when B is not.
a ?? bnull-coalescing use a, unless it is null, then b 0 and "" are not null, so they pass through.
a ??= bnull-coalescing assignment assign b to a only if a is null Reads as "fill in if missing". Handy, easy to misread as =.
c ? x : yconditional (ternary) an if that is an expression Nothing to do with null. Nesting two of these is how code stops being readable.
a?[0]null-conditional index index only if the collection is not null Guards the collection, never the element you get back.
 
string? city = customer?.Address?.City;        // null if either link is null
string shown = city ?? "(unknown)";            // a real string, always
int len = customer?.Name?.Length ?? 0;         // chain, then a floor value

cache ??= new Dictionary<string, int>();      // create it once, lazily

string verdict = total > 100 ? "large" : "small";  // nothing to do with null

int count = list?.Count ?? 0;                 // the idiomatic "count or nothing"
int wrong = list.Count ?? 0;                  // error: int is never null
Line by line
  • customer?.Address?.City — short-circuiting all the way. If customer is null, Address is never touched and the whole expression is null. One ?. per link that could be null; a missing one is where the NullReferenceException comes from.
  • city ?? "(unknown)" — the only place the nullable becomes non-nullable. The compiler knows this and stops warning after it.
  • cache ??= new … — expands to if (cache is null) cache = new …. Fine for a private field; not a substitute for a lock in concurrent code, where two threads can both see null. Chapter 08 has that.
  • total > 100 ? "large" : "small" — the ternary conditional, the only operator in C# taking three operands, and the reason people call it "the ternary". Both branches must produce the same type.
  • list.Count ?? 0 — a compile error worth meeting deliberately. Count is an int and an int cannot be null, so ?? has nothing to do. The ?. is what makes the left side nullable in the first place — which is why the working line needs both symbols, in that order.

The exclamation mark, three jobs — and one you should distrust

if (!isReady) return;                    // 1 — logical not
if (a != b) return;                      // 2 — not equal

string name = customer!.Name;              // 3 — null-forgiving: "trust me"

public required string Code { get; init; }  // the honest alternative
Line by line
  • !isReady — logical negation, and the most misread character in any codebase. A long condition beginning with ! is worth a named variable: bool notReady = …; costs one line and saves the reader a reversal.
  • a != b — inequality. It follows whatever == does for that type, which is why the four kinds of equality in chapter 02b apply here unchanged.
  • customer!.Name — the null-forgiving operator. It does nothing at run time. It does not check, convert or guard — it only tells the compiler to stop warning. If you were wrong, you get exactly the same NullReferenceException you would have had, with the warning that predicted it deleted.
  • required — the alternative for the usual case. Most ! marks exist because a property is set after construction and the compiler cannot see it; required makes the caller set it and removes the warning honestly.
⚠️ ! is a promise you make to the compiler on your own authority

Treat every ! in a pull request as a claim requiring evidence. Sometimes the claim is true and unprovable — a value the framework guarantees, a field set in OnInitialized — and then a comment saying why belongs next to it. Sometimes it was added to make a build go green at half past five. The two look identical in the diff, which is precisely the problem.

The rest of the punctuation, each in its place

SymbolWhereWhat it does
$"…"before a string interpolation: {expr} inside the quotes is evaluated and inserted.
@"…"before a string verbatim: backslashes are literal and newlines are allowed. For paths and regexes.
@classbefore an identifier a completely different job: "this word is a name, not a keyword". Rare, and always a smell.
"""…"""around a string raw string literal: no escaping at all, ideal for JSON and SQL.
=>in a lambda "goes to": the parameters on the left, the body on the right.
=>after a member signature expression-bodied member: int Total => a + b; is a getter, not a field.
:after a class name inherits from, or implements.
:in a switch, or a label ends a case arm in the old statement form.
:in a ternary, an argument, a format the else half; a named argument (name: x); a format string {d:yyyy-MM-dd}.
..in an index or a pattern a range: s[1..4], s[..^1] — and the slice wildcard in a list pattern.
^before an index "from the end": items[^1] is the last item. Nothing to do with exponents.
paramson the last parameter "any number of these" — a wildcard on the argument list rather than on a value.
#at the start of a line a directive to the compiler, not code: #if, #region, #nullable.
 
string path  = @"C:\logs\today.txt";        // verbatim: backslash means backslash
string greet = $"Ciao {name}, {total:C}";      // interpolated, with a format
string both  = $@"C:\out\{name}.csv";         // both prefixes, in either order

int[] items = [10, 20, 30, 40];
int last  = items[^1];                       // 40
int[] mid = items[1..3];                     // 20, 30 — end is exclusive
int[] most = items[..^1];                    // everything but the last

int Sum(params int[] values) => values.Sum();
Sum(1, 2, 3);                                // no array at the call site
Line by line
  • @"C:\logs\today.txt" — verbatim. Without the @, \t is a tab and \l is a compile error. This is why Windows paths and regular expressions almost always carry one.
  • $"… {total:C}" — the part after the colon is a format specifier, not a type annotation. C is currency, N2 is two decimals, yyyy-MM-dd is a date. It uses the current culture, which is a real source of "it works on my machine" bugs — chapter 00b has the detail.
  • items[^1] — an index from the end. ^1 is the last element, not ^0: think of it as "length minus this", so ^0 is one past the end and throws.
  • items[1..3] — a range. The start is inclusive and the end is exclusive, matching Substring and every other .NET convention, so this is two elements rather than three. Off-by-one errors here are expected; read it as "from 1, up to but not including 3".
  • params int[] values — a variable-length parameter list. The compiler builds the array at the call site. It must be the last parameter, and there can only be one — the same uniqueness rule .. has, for the same reason.

The other wildcards: globs, LIKE and regex

Everything above is C# syntax. The word "wildcard" in a job advert usually means one of the three text-matching systems you will meet the same week — and all three use different characters for the same idea, which is exactly why people mix them up.

Any run of charactersExactly one characterWhere you meet it
File glob*? Directory.GetFiles(dir, "*.csv"), .gitignore, a shell.
SQL LIKE%_ T-SQL WHERE Code LIKE 'MI-%' — see chapter 10.
Regex.*. Regex.IsMatch, routing constraints, validation.
⚠️ The underscore is a SQL wildcard, and a customer's name can contain one

LIKE 'MI_42' matches MI-42, MI042 and MIx42, because _ means "any one character" there. So a user searching for the literal text a_b gets far more rows than they asked for — and % pasted into a search box matches everything, which is a denial-of-service by accident. If the pattern comes from a human, escape it, and note that parameterising the query does not escape wildcards: it prevents injection, which is a different problem. Chapter 15 draws that line. 

// A glob: * is any run of characters, ? is exactly one
foreach (var f in Directory.EnumerateFiles(dir, "order-*.csv"))
    Process(f);

// Recursive, because the default is this folder only
var all = Directory.EnumerateFiles(dir, "*.csv", SearchOption.AllDirectories);

// The same idea in SQL, with different characters
//   WHERE Code LIKE 'MI-%'     → starts with MI-
//   WHERE Code LIKE 'MI-__'    → MI- and exactly two more characters

// And in a regex, where * means something else entirely
bool ok = Regex.IsMatch(code, @"^MI-\d{4}$");
Line by line
  • "order-*.csv" — a search pattern, not a regex. Only * and ? mean anything; every other character is literal.
  • SearchOption.AllDirectories — the missing default. Without it the search does not descend, which is the usual reason a file "is not found" when it plainly exists.
  • LIKE 'MI-__' — two underscores, two characters. In SQL _ is the single-character wildcard, which is the opposite of what the same character means in a C# pattern, where it matches one element and discards it. Related idea, unrelated syntax.
  • @"^MI-\d{4}$" — a regex, where ^ means "start of string" — not "index from the end", which is what ^ means in C# twenty lines earlier. Three systems, one page, three meanings for two characters. This is the whole reason the chapter exists.

Words that lie: pairs that look identical and are not

🧒 Simple

English gives us pairs like "fewer" and "less", where most people use either and nobody is hurt. Programming languages have pairs that look just as interchangeable and are not: pick the wrong one and the program compiles, runs, and does something subtly different. The list below is the pairs that actually cost people time.

These look the sameThe actual question each one answers
const vs readonly "Never changes, ever, and is baked into every caller at compile time" vs "set once, at run time, in the constructor". Change a const in a library and callers keep the old value until they are rebuilt.
ref vs out vs in "I will read and write this" vs "I will definitely write this and you need not have filled it" vs "I promise only to read". The compiler enforces all three.
is vs as "Is it?" — a bool. vs "Treat it as, or give me null" — a value. as on a value type does not compile without a nullable.
== vs .Equals Chosen at compile time from declared types vs chosen at run time from actual ones. The boxed-int exercise in 02b is this pair disagreeing.
virtual vs abstract vs new "Here is a default you may replace" vs "There is no default, you must" vs "I am hiding the base member" — and new is almost always a mistake, because the base type's variable still calls the base method.
throw vs throw ex "Rethrow, keeping where it came from" vs "Rethrow, pretending it started here". The second erases the stack trace and is never what you wanted.
string.Empty vs null "A text with no characters" vs "No text at all". "".Length is 0; null.Length throws.
Length vs Count Arrays and strings have Length; lists and dictionaries have Count; IEnumerable has neither until you call .Count(), which may enumerate the whole thing.
First vs FirstOrDefault "There is one, and I want to hear about it if not" vs "There may not be, and I will handle that". The second returning null silently is how a NullReferenceException appears three methods away.
Task vs void in async "Await me, and my exceptions reach you" vs "You cannot await me, and my exceptions crash the process". async void is for event handlers only.
Parse vs TryParse "Bad input is a bug, throw" vs "Bad input is expected, tell me". A human typed it — TryParse.
IEnumerable vs IQueryable "Filter in memory, after fetching everything" vs "Turn my filter into SQL". Same-looking LINQ, wildly different bill — chapter 12.
 
public const int MaxRetries = 3;              // compile-time, copied into callers
public readonly DateTime StartedAt;          // run-time, set in the constructor

void Swap(ref int a, ref int b) { … }         // both must be assigned first
bool TryGet(string key, out int value) { … }   // value need not be, and must be set

if (o is Order ord) Use(ord);                 // test and bind in one go
Order? maybe = o as Order;                     // null if it is not one

try { Risky(); }
catch (Exception ex) { Log(ex); throw; }     // keeps the original stack trace
Line by line
  • const int MaxRetries = 3; — substituted at compile time. Every assembly that references this one bakes in the literal 3. Ship a new version with 5 and old callers keep retrying three times until rebuilt. Use const for things that are true by definition — minutes in an hour — and static readonly for everything else.
  • readonly DateTime StartedAt; — assignable only in the constructor, then frozen. Note what it does not promise for a reference type: a readonly List cannot be reassigned, and can still be added to.
  • ref vs out — the difference is who must have assigned it. ref requires the caller to have a value already; out requires the method to set one before returning. Both let the method change the caller's variable, which is the part people remember.
  • o is Order ord — a declaration pattern: tests the type and introduces ord in the same breath. It replaced the old as-then-null-check idiom entirely, and is what modern C# expects to see.
  • throw; — a bare rethrow. Writing throw ex; instead resets the exception's origin to this line, so the log says the error happened in your catch block rather than where it really did. It is a one-word difference that destroys the single most useful piece of evidence you have — chapter 08c has the full list of these.

Exercises, with the reasoning shown

Exercise 1 — count the meanings

int? a = null;
int b = a ?? (a is null ? 1 : 2);
Console.WriteLine(b);
Line by line
  • int? — question mark job one: nullable type.
  • a ?? … — job three: null-coalescing. a is null, so the right-hand side is evaluated.
  • a is null ? 1 : 2 — job four: the ternary, whose ? and : have nothing to do with null. The condition is true, so this is 1.
  • It prints 1 — and there are three unrelated uses of one character in eleven tokens. That is the density this chapter exists for, not a style to imitate.

Exercise 2 — the wildcard that matched too much

string term = Console.ReadLine();       // the user types: 50%
var sql = "SELECT * FROM Product WHERE Name LIKE @t";
cmd.Parameters.AddWithValue("@t", term + "%");
Line by line
  • term — the user typed 50%, meaning a discount. To LIKE, that % is a wildcard.
  • AddWithValue — the query is parameterised, so this is not SQL injection. The value never becomes part of the statement.
  • The pattern that reaches SQL Server is 50%%, which matches every product whose name starts with 50 followed by anything — and a bare % would match the whole table. On a large catalogue that is an accidental full scan per keystroke.
  • The fix is to escape the wildcards in user text before appending your own: %, _ and [, using LIKE @t ESCAPE '\'. Parameterising and escaping solve different problems, and this is the exercise that separates them.

Exercise 3 — the pattern that is never reached

string Label(object o) => o switch
{
    var x   => "something",
    null    => "nothing",
    int n   => "a number",
};
Line by line
  • var x => — the var pattern matches everything, including null, and it is first.
  • The two arms below it are therefore unreachable, and the compiler says so: error CS8510, "the pattern is unreachable". This is the good case — the compiler catches it.
  • Reorder to null, then int n, then var x and it compiles and behaves. Arms are tried top to bottom, so specific patterns go above general ones, always.
  • The same rule in a different disguise: put _ anywhere but last and everything after it is dead. That is why the catch-all arm is conventionally written at the bottom even when the compiler would let you get away with more.

Exercise 4 — two words, two different programs

class Base    { public virtual string Name() => "base"; }
class Child   : Base { public override string Name() => "child"; }
class Hidden  : Base { public new string Name() => "hidden"; }

Base a = new Child();
Base b = new Hidden();
Console.WriteLine(a.Name());
Console.WriteLine(b.Name());
Line by line
  • override — replaces the base implementation in the object's method table. The call goes to Child.Name no matter what type the variable is declared as. Prints child.
  • new — hides rather than replaces. Two methods now exist, and which one runs is decided by the declared type of the variable, not the actual object. The variable is a Base, so this prints base.
  • Change the declaration to Hidden b = new Hidden(); and the very same object prints hidden. One object, two answers, depending on which variable you asked through. That is the entire argument against new.
  • The new keyword here is also job two for that word — it is the same spelling as new Order(), which creates an object, and has nothing to do with it. Another entry for the list above.
Try it yourself

Open the largest C# file you can find — one of this course's examples, or any class in a real project — and use your editor's find to count the ? characters in it. For each one, say out loud which of the four jobs it is doing before you move to the next. Then do the same for _ and for =>. It takes ten minutes once, and afterwards you stop losing the thread of a line because of a character you skimmed.

Golden rules

  1. Read a symbol by its position, not by its shape. ? does four unrelated jobs and _ does five; which one is meant is decided entirely by where it sits.
  2. _ means "I will not use this". A leading underscore on a field name means nothing at all to the compiler — it is a convention for the reader, and it is not a discard.
  3. The catch-all arm goes last, because arms are tried top to bottom and anything after a pattern that matches everything is unreachable. The same applies to a var pattern, which also matches null.
  4. Over your own enum, think twice before adding _. Without it the compiler warns when somebody adds a member and nobody handled it; with it, that warning is gone forever.
  5. ?? does not catch "" or 0, because neither is null. When empty should count as missing, say so with IsNullOrWhiteSpace.
  6. ! does nothing at run time. It is a claim, not a check. Every one deserves a comment saying why it is safe — or, more often, a required property instead.
  7. Parameterising is not escaping. A parameter stops SQL injection; it does nothing about % and _ in user text reaching a LIKE. Escape those separately.
  8. Three wildcard alphabets, kept apart: glob uses * and ?, LIKE uses % and _, regex uses .* and .. A filter that silently matches nothing is usually two of them mixed.
  9. const only for what is true by definition; static readonly for everything else. A const is copied into every caller at compile time, so changing it does not reach code already built — and an optional parameter's default has the identical trap.
  10. readonly freezes the reference, not the object. A readonly List can still be added to.
  11. throw;, never throw ex; — the second resets the stack trace and tells the log the error started in your catch block.
  12. override, not new. Hiding a member makes one object give two different answers depending on which variable you asked through.

Interview questions

"What is the difference between const and readonly?"

const is resolved at compile time and substituted into every caller, so it must be a literal and it cannot depend on anything computed. readonly is assigned at run time, in the constructor or the field initialiser, and then cannot change. The practical consequence people miss is versioning: if a library exposes a const and changes it, everything that referenced the old value keeps using it until recompiled. So I use const only for things that are true by definition, and static readonly otherwise.

"What does the ! in customer!.Name actually do?"

Nothing at run time. It is the null-forgiving operator, and it only tells the compiler to stop warning about a possible null on that expression. If the value is null anyway you get the same NullReferenceException you always would have, minus the warning that predicted it. I treat it as a claim that needs a comment explaining why it is safe, and where the real problem is a property set after construction, required is the honest fix.

"A user's search text contains %. The query is parameterised. Is there a problem?"

Not an injection problem — the parameter is never part of the statement. But % and _ are LIKE wildcards, so the search matches far more rows than the user asked for, and a bare % matches everything, which on a big table is a full scan the user triggered by accident. Parameterising prevents injection; escaping prevents this. They are different defences and you need both.

"Cosa fa il carattere _ in C#?"

Dipende da dove sta, ed è la cosa più importante da dire. Come discard significa "qui ci va qualcosa che non mi interessa": in un out, in una deconstruction, o come parametro di una lambda che non uso. Dentro uno switch è il pattern che prende tutto il resto, e va per ultimo. Invece un identificatore che inizia con underscore, tipo _logger, non è un discard: è solo la convenzione per i campi privati, e il compilatore non gli dà nessun significato.
