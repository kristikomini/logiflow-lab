Blazor

Blazor is components like the previous chapter, written in C#. No npm, no bundler, no second language. For a region full of teams maintaining large WinForms and WPF applications with no JavaScript developer in the building, that is not a detail — it is the whole reason Blazor turns up in Bologna job adverts.

Why this chapter exists

Emilia-Romagna's software estate is heavily Microsoft and heavily desktop: gestionali, shop-floor supervisors and internal tools written in WinForms or WPF over SQL Server, some of them fifteen years old and still earning money. Those applications have to reach the browser eventually, and the team that will do it writes C#. Ads in Bologna now name Blazor Server and WebAssembly explicitly. This repository ships src/LogiFlow.Web — a Blazor front end over the API — for exactly that reason.

The idea

🧒 Simple

Imagine you only speak Italian, and to build a website you were told you also had to learn Japanese. Annoying. Blazor is someone saying: actually, you can build it in Italian.

There are two ways it works. Either your program stays on the big computer at the office and sends the screen down a wire very fast — or your whole program is copied into the browser and runs there. Same code. Different place.

🎓 Professional

Blazor is a component model where components are .razor files: markup plus C#, compiled into ordinary .NET classes. The framework builds a render tree, diffs it after each state change, and applies the difference to the DOM — conceptually the same as React's virtual DOM.

The interesting decision is where the C# runs, and Blazor gives you four render modes:

Render modeRunsCostsGood for
Static SSRon the server, onceno interactivitycontent pages, forms with a POST
InteractiveServeron the server, over a SignalR circuita live connection per user; latency is feltinternal LAN apps — the region's default
InteractiveWebAssemblyin the browser, on a .NET runtimemulti-MB first load; no direct DB accesspublic apps, offline, static hosting
InteractiveAutoserver first, then WASM once cachedmost complexity; two environments to supportpublic apps wanting a fast first visit

What a component looks like

Orders.razor — markup and C# in one file
@page "/orders"
@rendermode InteractiveServer
@inject LogiFlowApiClient Api

<h1>Ordini</h1>

@if (_orders is null)
{
    <p><em>Caricamento…</em></p>      // null means "not loaded yet" —
}                                       // empty list means "none exist". Different.
else if (_orders.Count == 0)
{
    <p>Nessun ordine.</p>
}
else
{
    <table>
    @foreach (var o in _orders)
    {
        <tr @key="o.Id">                          // @key: keeps the diff stable
            <td>@o.OrderNumber</td>
            <td>@o.Total.ToString("C", _it)</td>  // 1.234,56 € — see module 23
            <td><StatusPill Status="o.Status" /></td>
        </tr>
    }
    </table>
}

@code {
    private List<OrderSummary>? _orders;
    private readonly CultureInfo _it = CultureInfo.GetCultureInfo("it-IT");

    protected override async Task OnInitializedAsync()
        => _orders = await Api.GetOrdersAsync();
}

Everything you already know applies: @inject is the DI container from chapter 14, OnInitializedAsync is ordinary async, and StatusPill is a component you wrote. No new language, no build chain.

The four that cost everyone an afternoon

⚠ OnInitializedAsync runs twice

With prerendering, the component initialises once on the server to produce the initial HTML, then again when the interactive circuit starts. Two loads, two API calls, and any side effect happens twice. Guard side effects with OnAfterRenderAsync(bool firstRender), or disable prerendering for that component and know why you did.

⚠ Injecting a DbContext into a component

A Blazor Server component can live for hours, and a scoped DbContext injected into it lives exactly as long — accumulating tracked entities, holding a connection, and breaking the moment two events overlap, because DbContext is not thread-safe. Use IDbContextFactory<T> and create one per operation. This is the Blazor-shaped version of the captive-dependency trap.

⚠ Updating state from a timer or an event

Anything that changes state outside a UI event — a System.Threading.Timer, a SignalR message, a background callback — must marshal back with InvokeAsync(StateHasChanged). Without it the screen simply does not update, and you spend an hour looking for a bug in your data.

⚠ Secrets in a WebAssembly app

WebAssembly code is downloaded to the user's machine. Anything in it — an API key, a connection string, a "hidden" admin check — is readable. Client-side authorisation in Blazor WASM controls what the UI shows, never what the user may do. The API must enforce every rule again, exactly as in chapter 15. Blazor Server does not have this problem: the code never leaves the server.

Migrating a desktop application, honestly

🧒 Simple

Imagine a very old bridge that everyone still drives over every day. You cannot close it for two years to build a new one — the town would stop.

So you build the new bridge one lane at a time, right next to it, and move the traffic across lane by lane. For a while both bridges are standing and that looks silly. Then one day the old one has no cars on it, and you take it away.

🎓 Professional

This is the conversation a Modena or Reggio Emilia employer is actually having, and having an opinion about it is worth more than knowing Blazor's API surface.

Chapter 31 covers those applications from the inside; this is the part where they reach the browser.

The naive plan is a rewrite: freeze the WinForms application, build the replacement, switch over. It fails for the usual reason — the old system keeps changing during the two years you are not shipping, and fifteen years of undocumented business rules do not survive a re-derivation.

The strangler fig approach instead: put an API in front of the existing database, move one screen at a time to Blazor, and run both until the desktop application has nothing left. Each step ships. Each step is reversible. The awkward parts are shared authentication, and the fact that business logic buried in form event handlers has to be lifted into a service layer before either UI can call it — which is precisely what chapter 23 is about.

Try it yourself
dotnet run --project src/LogiFlow.Web
# then open the orders page and watch the network tab

On an InteractiveServer page, click around and notice that almost nothing is transferred except small WebSocket frames — the HTML is being diffed on the server. Then the experiment worth doing: open developer tools, throttle the connection to "Slow 3G", and type in a filter box. Every keystroke now visibly lags, because every keystroke is a round trip. That single observation is the whole Server-versus-WebAssembly decision, and it is why a factory LAN and a public website give opposite answers.

Golden rules

  1. Components are C# classes. Everything you know about DI and async still applies.
  2. Choose the render mode from the network, not from fashion.
  3. InteractiveServer: a circuit and server memory per user, and latency on every interaction.
  4. WebAssembly: a multi-megabyte first load, and your code is on the user's machine.
  5. Never put a secret in a WebAssembly app. Client-side authorisation is cosmetic.
  6. The API enforces the rules. The UI only decides what to show.
  7. OnInitializedAsync runs twice with prerendering. Plan for it.
  8. IDbContextFactory, never an injected DbContext, in a long-lived component.
  9. State changed outside a UI event needs InvokeAsync(StateHasChanged).
  10. @key on anything rendered in a loop that can reorder.
  11. null means "not loaded"; an empty list means "none". Render them differently.
  12. Migrate a desktop app one screen at a time behind an API. Never a big-bang rewrite.

Interview questions

"Blazor Server o WebAssembly?"

Refuse the false choice and give the deciding factors: network quality, whether the app must work offline, how many concurrent users, and whether any secret would end up client-side. Then commit: for an internal application on a company network, InteractiveServer — simpler, instant first paint, and it can reach the database directly. For a public or offline app, WebAssembly.

"What is the circuit, and what happens when it drops?"

A SignalR connection holding that user's component state on the server. Drop it — a tunnel, a laptop lid, a deploy — and the UI freezes with a reconnect banner; if it cannot resume, the state is gone. So keep anything that matters in the database rather than in component fields, and be honest that this is Blazor Server's main operational weakness.

"Why is my page not updating?"

Almost always state changed outside a UI event without InvokeAsync(StateHasChanged). Blazor re-renders automatically after its own event handlers, not after a timer tick or a background callback. Naming this instantly signals you have actually built something in Blazor.

"We have a WinForms application from 2011. How would you move it to the web?"

This is the region's real question. Strangler fig: an API over the existing database, one screen at a time in Blazor, both running side by side until the desktop app is empty. Name the hard parts — shared authentication, and lifting business logic out of form event handlers into a service layer — and say plainly why you would not do a big-bang rewrite.

"Is Blazor a real alternative to Angular or React?"

For internal line-of-business applications in a C# team, yes — one language, one toolchain, no npm supply chain, and your DTOs are literally shared types rather than copies. Be fair about the costs too: a smaller ecosystem and hiring pool, and JavaScript interop the moment you want a specific charting or mapping library. Balance is what makes the answer credible.
