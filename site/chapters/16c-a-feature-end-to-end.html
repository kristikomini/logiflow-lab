A feature, end to end

Almost every ticket you will ever pick up has the same shape: the system needs to store one new kind of thing and let a user see and change it. This chapter walks a single feature down through every layer — entity, DbContext, migration, repository, service, view model, controller, view — in the order you actually write them, with the rule for each layer stated where you meet it. It is the recipe the rest of Part 2 and Part 3 taught in pieces, assembled once.

The feature we are adding

LogiFlow needs to track carriers (vettori) — the couriers a shipment can be handed to. A carrier has a name, a short code, and an active flag. It is a deliberately small feature so nothing hides the shape: this is the same eight steps whether the thing is a carrier, an invoice or a return.

The shape of a ticket

🧒 Simple

Think of a relay race. The browser hands a request to the controller, the controller hands the real work to a service, the service asks the repository, the repository asks the database. Then the answer runs back up the same line. Each runner does one job and passes the baton — and the baton changes shape along the way: it is a form on the way in, an entity in the middle, and a screen model on the way out.

🎓 Professional

The layers exist so that a change stays local. A new database column touches the entity, the configuration and a migration — and nothing above the repository. A change to a screen touches the view and its view model — and nothing below the controller. When those two kinds of change collide in one class, every edit risks the other, and that class is where bugs breed. The dependency rule is one-directional: outer layers know about inner ones, never the reverse.

Where each file lands

LogiFlow is Clean Architecture: four projects, and a file's project is decided by what it is allowed to know. The entity knows nothing; LogiFlow.Domain. The service knows the domain and the abstractions; LogiFlow.Application. EF Core, the DbContext and the repository know the database; LogiFlow.Infrastructure. The controller and the view know the web; LogiFlow.Web.

Step 1 — The entity

The entity is the thing itself, as the business understands it — before any database or any screen. Start here, because every later layer is shaped by it.

src/LogiFlow.Domain/Carriers/Carrier.cs
namespace LogiFlow.Domain.Carriers;

public class Carrier
{
    public int Id { get; private set; }              // identity — the database owns it
    public string Name { get; private set; } = "";
    public string Code { get; private set; } = "";
    public bool IsActive { get; private set; } = true;
    public DateTime CreatedUtc { get; private set; }

    private Carrier() { }                             // EF needs a parameterless ctor; keep it private

    public Carrier(string name, string code)
    {
        Rename(name);
        SetCode(code);
        CreatedUtc = DateTime.UtcNow;
    }

    public void Rename(string name)
    {
        if (String.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Carrier name is required.", nameof(name));
        Name = name.Trim();
    }

    public void SetCode(string code) => Code = code.Trim().ToUpperInvariant();
    public void Activate()   => IsActive = true;
    public void Deactivate() => IsActive = false;
}
The rules for an entity class
  • It is a plain C# class, not a database table. No using of EF Core, no attributes tying it to a column. The domain must compile with the database ripped out — that is what makes it testable and what keeps SQL out of the business rules.
  • Id { get; private set; } — every entity needs identity. An int is the house default; the database assigns it, so the setter is private. Two carriers are the same carrier when their Id matches, not when their fields do.
  • Setters are private; state changes through methods. Rename, SetCode, Activate. This is the difference between an entity and a bag of public properties: the object cannot be put into an invalid state, because the only doors in enforce the rules.
  • = "" and = true — sensible defaults so a new entity is never half-null. A required string defaults to empty, not null.
  • private Carrier() { } — EF Core materialises rows by calling a parameterless constructor and then setting properties. Keep it private so your own code cannot build a nameless carrier; only EF, via reflection, uses it.
  • The public constructor takes what is mandatory (name, code) and runs it through the same guard methods. There is no way to construct an invalid carrier.
  • DateTime.UtcNow, never DateTime.Now — store instants in UTC and convert for display. A server that moves timezone, or a second server in another region, must not change what a timestamp means.
⚠ The anaemic entity

The most common shape you will see — and the one to grow out of — is a class of public get/set properties with no methods, all the rules living in services. It works, but every caller now has to remember to trim the name and uppercase the code, and one that forgets creates the bad row. Behaviour on the entity means the rule lives in exactly one place. Start with guarded setters; reach for a full value object only when a rule gets its own weight.

Step 2 — The DbContext

The DbContext is the bridge between your entities and the database. Adding a feature means two edits: a DbSet so EF knows the entity exists, and a configuration class that says how it maps to a table. See chapter 12 for the full picture; here is only what one new entity adds.

src/LogiFlow.Infrastructure/Persistence/LogiFlowDbContext.cs — the one new line
public class LogiFlowDbContext(DbContextOptions<LogiFlowDbContext> options)
    : DbContext(options)
{
    public DbSet<Order>    Orders    => Set<Order>();
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Carrier>  Carriers  => Set<Carrier>();   // ← the new entity

    protected override void OnModelCreating(ModelBuilder b)
        => b.ApplyConfigurationsFromAssembly(typeof(LogiFlowDbContext).Assembly);
}
Line by line
  • public DbSet<Carrier> Carriers => Set<Carrier>(); — the query root. This is how you reach carriers in a query, and its presence is what tells EF to include a Carriers table when it builds the model.
  • => Set<Carrier>() — an expression-bodied property rather than an auto-property with a setter. It resolves the set on demand and cannot be reassigned to null, which is the current house style.
  • ApplyConfigurationsFromAssembly — already there. It scans the assembly for IEntityTypeConfiguration<T> classes, so you do not touch OnModelCreating again — you add a configuration file and it is found automatically.
src/LogiFlow.Infrastructure/Persistence/Configurations/CarrierConfiguration.cs
public class CarrierConfiguration : IEntityTypeConfiguration<Carrier>
{
    public void Configure(EntityTypeBuilder<Carrier> b)
    {
        b.ToTable("Carriers");
        b.HasKey(c => c.Id);

        b.Property(c => c.Name).IsRequired().HasMaxLength(120);
        b.Property(c => c.Code).IsRequired().HasMaxLength(12);
        b.HasIndex(c => c.Code).IsUnique();          // no two carriers share a code

        b.Property(c => c.CreatedUtc);
    }
}
The rules for a configuration class
  • Mapping lives here, not on the entity. This is Fluent API configuration — the alternative to sprinkling [Required] and [MaxLength] attributes on the domain class. Keeping it here is what let the entity in step 1 stay free of EF.
  • IsRequired() and HasMaxLength(120) — these become NOT NULL and nvarchar(120) in the table. Set the max length: the default is nvarchar(max), which cannot be indexed and quietly wastes space.
  • HasIndex(c => c.Code).IsUnique() — a database-level uniqueness guarantee. A check in C# races under load; a unique index is enforced by the one component that sees every write. It also becomes a migration step in the next section.
  • One configuration class per entity, found by the assembly scan. Adding a feature never means editing a giant OnModelCreating that everyone touches and nobody can merge.

Step 3 — The migration

The model and the database now disagree: the code has a Carriers set and table mapping, the database has no such table. A migration is the versioned, checked-in script that closes that gap — and the record of exactly how the schema got to where it is.

generate it — run from the solution root
dotnet ef migrations add AddCarrier -p src/LogiFlow.Infrastructure -s src/LogiFlow.Api
# then apply it to your local database
dotnet ef database update -p src/LogiFlow.Infrastructure -s src/LogiFlow.Api
Line by line
  • migrations add AddCarrier — EF compares the current model to the snapshot of the last migration and writes a new file for the difference. The name is a sentence in the schema's history; AddCarrier reads well in a list, Migration2 does not.
  • -p src/LogiFlow.Infrastructure — the project the migration files are written into: where the DbContext lives.
  • -s src/LogiFlow.Api — the startup project EF runs to discover the connection string and DI configuration. In a split solution these are two different projects, and forgetting the second is the most common first error.
  • database update — applies every pending migration in order, recording each in the __EFMigrationsHistory table so it is never run twice. Locally this is fine; in production the same migrations run from the release pipeline, never by hand.
Migrations/20260916_AddCarrier.cs — what EF generated (read it, always)
public partial class AddCarrier : Migration
{
    protected override void Up(MigrationBuilder b)
    {
        b.CreateTable(
            name: "Carriers",
            columns: t => new
            {
                Id        = t.Column<int>(nullable: false)
                              .Annotation("SqlServer:Identity", "1, 1"),
                Name      = t.Column<string>(maxLength: 120, nullable: false),
                Code      = t.Column<string>(maxLength: 12,  nullable: false),
                IsActive  = t.Column<bool>(nullable: false),
                CreatedUtc = t.Column<DateTime>(nullable: false),
            },
            constraints: t => t.PrimaryKey("PK_Carriers", x => x.Id));

        b.CreateIndex("IX_Carriers_Code", "Carriers", "Code", unique: true);
    }

    protected override void Down(MigrationBuilder b)
        => b.DropTable("Carriers");
}
The rules for a migration
  • A migration is generated, then read. EF wrote this from your model, but you own it: check it into git, review it in the PR, and never edit an already-applied one.
  • Up moves the schema forward; Down reverses it. The unique index matches the HasIndex(...).IsUnique() from step 2 — a config change you cannot see in the database until a migration carries it there.
  • The name in the file is the audit trail. Anyone can read the Migrations folder top to bottom and see how the schema was built, one intent per file.
  • To change a not-yet-shipped migration, delete it and re-add. dotnet ef migrations remove drops the last one; then fix the model and generate again. Editing an applied migration desynchronises the snapshot and the next add produces garbage.
  • Renaming a column or dropping data is where EF guesses wrong — it may drop-and-recreate and lose rows. On those, read Up especially carefully and hand-write the safe version.

Step 4 — The repository

The repository is the collection-like doorway to persistence: give me the carrier with this code, add this one. The interface belongs to the application (it is what the service needs); the implementation belongs to infrastructure (it is how EF answers).

src/LogiFlow.Application/Carriers/ICarrierRepository.cs
namespace LogiFlow.Application.Carriers;

public interface ICarrierRepository
{
    Task<Carrier?> GetByIdAsync(int id, CancellationToken ct);
    Task<bool>      CodeExistsAsync(string code, CancellationToken ct);
    Task<IReadOnlyList<Carrier>> ListActiveAsync(CancellationToken ct);
    void Add(Carrier carrier);
}
The rules for a repository interface
  • The interface lives in the layer that uses it (Application), not the one that implements it. That is dependency inversion: the service depends on an abstraction it owns, and infrastructure plugs in behind it. It is also what makes the service testable with a fake repository.
  • Methods speak the domain: GetByIdAsync, CodeExistsAsync — not Query() that leaks IQueryable and lets a caller write SQL from three layers up.
  • Reads are async with a CancellationToken; if the user closes the tab, the query is abandoned. IReadOnlyList as a return type signals the caller cannot add to the result.
  • Add is not async and does not save. It stages the entity with the change tracker; the actual write happens once, in the service, via the unit of work. Persisting inside Add would make every insert its own transaction.
src/LogiFlow.Infrastructure/Persistence/CarrierRepository.cs
public class CarrierRepository(LogiFlowDbContext db) : ICarrierRepository
{
    public Task<Carrier?> GetByIdAsync(int id, CancellationToken ct) =>
        db.Carriers.FirstOrDefaultAsync(c => c.Id == id, ct);

    public Task<bool> CodeExistsAsync(string code, CancellationToken ct) =>
        db.Carriers.AnyAsync(c => c.Code == code, ct);

    public async Task<IReadOnlyList<Carrier>> ListActiveAsync(CancellationToken ct) =>
        await db.Carriers.AsNoTracking()
                        .Where(c => c.IsActive)
                        .OrderBy(c => c.Name)
                        .ToListAsync(ct);

    public void Add(Carrier carrier) => db.Carriers.Add(carrier);
}
Line by line
  • (LogiFlowDbContext db) — the context is injected. It is registered scoped, so every repository in one HTTP request shares the same context and the same change tracker.
  • AsNoTracking() on the list — a read-only query does not need the change tracker's snapshots, and turning them off is measurably faster on a table you only display. Use it for reads; leave it off when you intend to modify what you load.
  • CodeExistsAsync pushes the existence check to SQL as SELECT ... WHERE EXISTS — it never loads a row. Do not fetch a list and check .Any() in memory.
  • Add only tells the tracker "this is new". Nothing hits the database until SaveChangesAsync runs — which the service owns, next.
⚠ Do you even need a repository over EF Core?

Fair question, and a real interview one. DbContext already is a unit of work and each DbSet already is a repository, so a thin pass-through class adds a layer that earns nothing. The defensible reasons to add one: to keep IQueryable and EF types out of the application layer, to name queries in domain terms, and to give services something trivial to fake in a unit test. If none of those apply on your project, injecting the DbContext straight into the service is a legitimate choice — know the trade, do not cargo-cult the pattern.

Step 5 — The service

The service is the application layer: it holds the use case — create a carrier — and the rules that are about the operation rather than about a single entity. It is the only place that decides a transaction has completed.

src/LogiFlow.Application/Carriers/CarrierService.cs
public record CreateCarrier(string Name, string Code);   // the request DTO — plain data

public class CarrierService(ICarrierRepository repo, IUnitOfWork uow)
{
    public async Task<int> CreateAsync(CreateCarrier input, CancellationToken ct)
    {
        var code = input.Code.Trim().ToUpperInvariant();

        if (await repo.CodeExistsAsync(code, ct))
            throw new ConflictException($"Carrier code '{code}' already exists.");

        var carrier = new Carrier(input.Name, code);   // the entity enforces its own invariants
        repo.Add(carrier);

        await uow.SaveChangesAsync(ct);                // one transaction — commit or nothing
        return carrier.Id;                            // now populated by the database
    }
}
The rules for a service
  • Input is a DTO, not the entity and not the view model. CreateCarrier is a record of exactly the fields the use case needs. The web layer maps its form onto this; the service never sees an HTTP type.
  • Cross-entity rules live here. "The code must be unique" is not something one Carrier can check about itself — it needs the repository. So it is a service rule, expressed as an early throw.
  • Invariants of one entity live on the entity. Trimming the name, requiring it — the service does not repeat those; it constructs a Carrier and trusts the constructor from step 1.
  • ConflictException — a domain-meaningful failure, which the web layer will translate into an HTTP 409 or a form error. The service does not know about status codes.
  • await uow.SaveChangesAsync(ct) — the one commit point. The service decides the transaction boundary; everything staged since the request began is written together, or nothing is.

Step 6 — The view model

Now we cross into the web layer. The view model is shaped for the screen — the fields the form has, the labels the user reads, the validation messages in their language. It is emphatically not the entity. This is the same argument as chapter 16, applied to the new feature.

src/LogiFlow.Web/Models/CreateCarrierViewModel.cs
public class CreateCarrierViewModel
{
    [Display(Name = "Nome vettore")]
    [Required(ErrorMessage = "Il nome è obbligatorio.")]
    [StringLength(120, ErrorMessage = "Massimo 120 caratteri.")]
    public string? Name { get; set; }

    [Display(Name = "Codice")]
    [Required(ErrorMessage = "Il codice è obbligatorio.")]
    [StringLength(12, MinimumLength = 2, ErrorMessage = "Da 2 a 12 caratteri.")]
    public string? Code { get; set; }
}
The rules for a view model
  • Only the fields the form has. No Id, no IsActive, no CreatedUtc — the user does not set those, so they are not on the model a user can post. That closes over-posting (mass assignment) by construction.
  • Properties are nullable with public setters — the opposite of the entity. Model binding must be able to leave a field unset so that [Required] can report it, rather than the binder silently supplying an empty string.
  • [Display] and [Required(ErrorMessage = ...)] — label and message live beside the field, in Italian, because the user reads them. The same rules run on the server; annotations here are validated on POST, not just in the browser.
  • The web layer maps this to the service's DTO (new CreateCarrier(vm.Name!, vm.Code!)). Two small types, two responsibilities: one is a screen, one is a use-case request.

Step 7 — The controller

The controller binds the input, calls one service, and chooses a result. If it is longer than about ten lines, work has leaked into it that belongs below. This is the whole discipline of chapter 16 — here it is, doing the new feature.

src/LogiFlow.Web/Controllers/CarriersController.cs
public class CarriersController(CarrierService service) : Controller
{
    // GET /Carriers/Create
    [HttpGet]
    public IActionResult Create() => View(new CreateCarrierViewModel());

    // POST /Carriers/Create
    [HttpPost, ValidateAntiForgeryToken]
    public async Task<IActionResult> Create(CreateCarrierViewModel vm, CancellationToken ct)
    {
        if (!ModelState.IsValid)
            return View(vm);                       // redisplay with errors and the user's input

        try
        {
            var id = await service.CreateAsync(new(vm.Name!, vm.Code!), ct);
            TempData["Success"] = $"Vettore creato (#{id}).";
            return RedirectToAction(nameof(Index));   // Post/Redirect/Get
        }
        catch (ConflictException ex)
        {
            ModelState.AddModelError(nameof(vm.Code), ex.Message);
            return View(vm);                       // a domain conflict is a form error here
        }
    }
}
The rules for a controller action
  • Bind, delegate, choose a result — and nothing else. There is no query, no rule, no formatting in this method. Everything real is one service.CreateAsync call.
  • if (!ModelState.IsValid) return View(vm) — on invalid input, redisplay the same view model so the user keeps what they typed and sees the messages. Never lose their input.
  • [ValidateAntiForgeryToken] on the POST — mandatory on every state-changing action in a cookie-authenticated app; the <form> tag helper emits the matching hidden field.
  • RedirectToAction after success — Post/Redirect/Get, so F5 does not re-create the carrier.
  • The service's ConflictException becomes a ModelState error. Translating a domain failure into the right shape for this UI is a controller job — an API controller would translate the same exception into a 409 instead.

Step 8 — The view

Last step, and the only one the user sees. The view displays the view model and posts it back. It makes no decisions and runs no queries — tag helpers turn the model's annotations into the form's names, ids and validation for free.

src/LogiFlow.Web/Views/Carriers/Create.cshtml
@model CreateCarrierViewModel
@{
    ViewData["Title"] = "Nuovo vettore";
}

<h1>@ViewData["Title"]</h1>

<form asp-action="Create" method="post">
    <div asp-validation-summary="ModelOnly" class="text-danger"></div>

    <div class="mb-3">
        <label asp-for="Name" class="form-label"></label>
        <input asp-for="Name" class="form-control" />
        <span asp-validation-for="Name" class="text-danger"></span>
    </div>

    <div class="mb-3">
        <label asp-for="Code" class="form-label"></label>
        <input asp-for="Code" class="form-control" />
        <span asp-validation-for="Code" class="text-danger"></span>
    </div>

    <button type="submit" class="btn btn-primary">Salva</button>
    <a asp-action="Index" class="btn btn-link">Annulla</a>
</form>
The rules for a view
  • @model CreateCarrierViewModel — the view is strongly typed. Rename a property and this view is a compile error, not a silent blank field.
  • asp-for="Name" — one attribute produces the label text (from [Display]), the input name and id, the current value, and the HTML5 validation attributes (from [Required]/[StringLength]). The name it emits is exactly what model binding expects back — the round trip stays in sync from one source.
  • The <form> tag helper injects the antiforgery field automatically; that is why the controller's [ValidateAntiForgeryToken] just works.
  • No Id, no query, no if over business state. If you find yourself wanting one in the .cshtml, the answer belongs in the view model or the controller. The view displays; it does not decide.

Wiring it up

The one piece that is easy to forget: the new classes must be registered with the dependency injection container, or the app throws at the first request that needs them.

Program.cs / the composition root — three lines per feature
builder.Services.AddScoped<ICarrierRepository, CarrierRepository>();
builder.Services.AddScoped<CarrierService>();
// IUnitOfWork and LogiFlowDbContext are already registered — added once, for all features
Line by line
  • AddScoped<ICarrierRepository, CarrierRepository>() — "when someone asks for the interface, build the implementation, once per request". Scoped matches the DbContext's own lifetime, so they share a change tracker.
  • AddScoped<CarrierService>() — the service has no interface here, so it is registered as itself. The controller asks for CarrierService and the container supplies it with its repository and unit of work already wired.
  • This is the composition root — the one place that knows the concrete types. Every other class asked for abstractions and received them; only here are the wires actually joined.

Golden rules

  1. Write the layers in order: entity first, view last. Each one is shaped by the one before.
  2. The entity is a plain domain class with private setters and behaviour — it knows nothing about EF, HTTP or the screen.
  3. Mapping goes in an IEntityTypeConfiguration, not as attributes on the entity.
  4. Every schema change is a migration: generated, checked in, reviewed, and never edited once applied.
  5. A repository interface lives in the layer that uses it; the EF implementation lives in infrastructure. Do not leak IQueryable upward.
  6. The service owns cross-entity rules and the single SaveChangesAsync transaction boundary.
  7. Three distinct data shapes: entity (domain), DTO (use case), view model (screen). Never let one do another's job.
  8. The controller binds, delegates and chooses a result — ten lines, Post/Redirect/Get, antiforgery on every POST.
  9. The view is strongly typed, uses tag helpers, and makes no decisions.
  10. Register the new repository and service with DI, or the app throws on first use.

Interview questions

"Walk me through how you'd add a new entity to this system."

Entity in the domain with private setters and behaviour; a DbSet and an IEntityTypeConfiguration; a migration, generated and reviewed; a repository interface in Application and its EF implementation in Infrastructure; a service holding the use case and the transaction boundary; then view model, controller and view in the web layer; and DI registration. Name what each layer is allowed to know — that is the part they are actually testing.

"Why three types — entity, DTO, view model — for what feels like the same data?"

Because they answer to different masters. The entity answers to the business and the database; the DTO to the use case's inputs; the view model to the screen and its validation messages. Merging them couples a form to a table, which is where over-posting and "I renamed a column and the UI broke" come from.

"Do you really need a repository if EF Core already gives you one?"

Not always. DbContext is a unit of work and DbSet is a repository. I add one to keep IQueryable out of the application layer, to name queries in domain terms, and to make services trivially testable. On a small CRUD app I might inject the context directly and say so — the point is to choose, not to add the layer reflexively.

"Where does validation happen?"

In three places, on purpose. The entity guards its own invariants in its constructor and methods. The view model carries data annotations for the user-facing rules, checked on the server via ModelState. The service checks cross-entity rules like uniqueness, which no single entity can see. Client-side validation is a convenience on top, never the enforcement.

"What can go wrong with the migration?"

Forgetting the startup project (-s) so EF can't find the connection; editing a migration that's already applied and desyncing the snapshot; and trusting EF on a rename or a drop, where it may recreate the table and lose data. The habit that prevents all three: always read the generated Up before you run it.
