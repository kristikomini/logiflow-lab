Numbers, Math and money

Chapter 00b told you to keep money in a decimal and warned you that 7 / 2 is 3. That is the smallest possible amount of arithmetic a working developer needs. This chapter is the rest of it: the Math class, the five rounding modes and which one your invoice needs, percentages that add up, a random number that is actually random, and the moment a int silently goes negative.

Why this chapter exists

Almost every bug that makes it past review and into a customer's invoice is an arithmetic bug, and almost none of them are hard. A total short by one cent, a discount applied twice, a pallet count that rounds the wrong way at exactly .5, a percentage calculated on the post-VAT figure — each is a single line, each survives every unit test that used round numbers, and each is noticed first by an accountant rather than by you. Nothing on this page is conceptually difficult. All of it is the sort of thing you are simply expected to already know.

Three numeric types, and how to choose in five seconds

🧒 Simple

There are a lot of number types and you only really need three. Whole things you can count — boxes, orders, people — are int. Money is decimal. Measurements from the physical world — weights, temperatures, distances — are double. If you can remember those three sentences you have made the right choice roughly every time.

🎓 Professional

The distinction that matters is base. double is binary floating point: it stores a number as a power of two, so a tenth is no more representable in it than a third is in decimal, and errors accumulate over a sum. decimal stores a scaled integer in base ten, so 0.1 is exact and so is the sum of ten of them. decimal is roughly ten times slower and has a much smaller range, and neither of those costs matters in the sort of code that handles money. A double in a currency column is the single most expensive type choice in business software. 

int pallets      = 37;              // counting — no fractional pallet exists
long ordersEver  = 12_400_000_000;  // counting, but past 2.1 billion
decimal price    = 19.99m;          // money — the m suffix is REQUIRED
double weightKg  = 18.4;            // a measurement, from a scale
float sensorTemp = 4.5f;            // a measurement, half the size, half the digits

decimal vat = price * 0.22m;        // 4.3978 — exact
double drift = 0.1 + 0.2;           // 0.30000000000000004 — not a bug, a base
Line by line
  • 12_400_000_000 — the underscores are digit separators. The compiler ignores them entirely; they exist so a human can see the magnitude at a glance. Put them wherever you like, in any grouping.
  • 19.99m — the m suffix is not decoration. A bare 19.99 is a double literal, and assigning it to a decimal is a compile error. The letter stands for "money", historically.
  • 4.5f — float is half of double: about seven significant digits rather than fifteen. It exists for memory-bound work — a million sensor readings, a graphics buffer. Default to double; reach for float only when something measured tells you to.
  • 0.1 + 0.2 — every language with binary floating point prints this, and it is not a defect. The nearest double to a tenth is slightly over a tenth, and two of those errors do not cancel.
  • Both int and decimal are value types, so all of chapter 02b's rules about copies, defaults and equality apply unchanged.
⚠️ Never compare two doubles with ==

0.1 + 0.2 == 0.3 is false, and so is the equivalent line in any language you will ever use. Compare within a tolerance instead: Math.Abs(a - b) < 0.0001, choosing the tolerance from what the number means — a tenth of a gram, a hundredth of a degree. For decimal, == is fine and exact, which is one more reason money belongs in it.

The Math class, member by member

Math is a static class of plain functions. There is nothing to construct and nothing to inject — you call Math.Abs(x) and get a number back. These are the members that come up in ordinary business code, with the warehouse use case each one actually appears in.

const int PerPallet = 12;
int boxes = 41;

int palletsNeeded = (int)Math.Ceiling(boxes / (double)PerPallet);   // 4
int fullPallets   = boxes / PerPallet;                              // 3 — integer division
int leftover      = boxes % PerPallet;                              // 5 — the remainder

int priority = Math.Clamp(requested, 1, 5);     // no if, no validation ladder
int shortBy  = Math.Abs(counted - expected);    // magnitude, direction ignored

Line by line
  • boxes / (double)PerPallet — the cast is the whole trick. Without it both operands are int, C# does integer division, 41 / 12 is 3, and Math.Ceiling(3) is 3 — so the code compiles, runs, and under-orders a pallet forever. Cast one side and the other is promoted for you.
  • (int)Math.Ceiling(...) — Ceiling returns a double (or a decimal for a decimal input), never an int. You always cast the result back, and that cast is safe here because ceiling has already removed the fraction.
  • boxes % PerPallet — the modulo operator, the remainder after division. fullPallets and leftover together always reconstruct the original, which is why the pair is worth computing together.
  • Math.Clamp — three lines of validation replaced by one call, and unlike a hand-written ladder it cannot get the boundary wrong. It throws if you pass lo greater than hi, which is the right behaviour: that is a bug in your constants, not in the data.
  • Math.Abs on int.MinValue throws OverflowException — the one edge, and it exists because two's complement has one more negative value than positive.
⚠️ Ceiling and Floor are not "round up" and "round down"

They are "toward positive infinity" and "toward negative infinity", which only agree with up and down while the number is positive. Math.Floor(-2.1) is -3, not -2. If you meant "drop the fraction" you wanted Math.Truncate, which is toward zero. Negative quantities appear in real systems more than you expect — a stock correction, a refund line, a temperature below zero — and this is where they first bite.

Rounding: one call, five decisions

🧒 Simple

Everyone knows that 2.4 rounds to 2 and 2.6 rounds to 3. Nobody agrees about 2.5. C#'s default answer is 2, which surprises almost every person who meets it, and it is not a mistake — it is a deliberate choice you are allowed to override.

🎓 Professional

Math.Round defaults to banker's rounding: exact halves go to the nearest even number, so 2.5 becomes 2 and 3.5 becomes 4. Over many values the upward and downward pushes cancel, so a column of rounded figures keeps the same total as the unrounded column — which is precisely what an accountant wants and what always-round-half-up does not give. It is also what IEEE 754 specifies, which is why it is the default. Italian invoicing, however, conventionally wants half away from zero, and you get that by asking for it. 

Math.Round(2.5m)                                     // 2  — banker's, the default
Math.Round(3.5m)                                     // 4  — banker's again
Math.Round(2.5m, MidpointRounding.AwayFromZero)      // 3  — "what everyone expects"
Math.Round(2.345m, 2)                                // 2.34 — two decimal places, banker's
Math.Round(2.345m, 2, MidpointRounding.AwayFromZero) // 2.35 — an invoice line

decimal net   = 100.005m;
decimal shown = Math.Round(net, 2, MidpointRounding.AwayFromZero);  // 100.01
decimal vat   = Math.Round(shown * 0.22m, 2, MidpointRounding.AwayFromZero);
Line by line
  • MidpointRounding is an enum, and it has five members: ToEven (the default), AwayFromZero, ToZero, ToNegativeInfinity and ToPositiveInfinity. Chapter 02j is what an enum is; this is the most useful one in the framework.
  • The mode only ever matters for an exact midpoint. Every other value rounds the same way under every mode, which is exactly why the bug hides: your tests used 2.4 and 2.6.
  • Round the displayed figure, then compute VAT from the rounded figure — not the other way round. Otherwise the invoice shows a net and a VAT that do not add to the total printed beneath them, and no customer accepts that explanation.
  • Round once, at the edge, when you write the value down or show it. Rounding in the middle of a calculation and then again at the end is double rounding, and it can move the answer by a full unit: 2.44 → 2.4 → 2, where one step gives 2… and 2.46 → 2.5 → 3 where one step also gives 2.
  • Math.Round(x, 2) on a double can still surprise you, because the double you are rounding may already not be the number you typed. On decimal it does what it says.
⚠️ The ninety-seven cent total

Split €10.00 three ways, round each share to two places, and you have €3.33 × 3 = €9.99. A cent has evaporated. There is no rounding mode that fixes this, because the problem is not the rounding — it is that you rounded three times independently. Give the remainder to somebody explicitly: compute n - 1 shares, then make the last share the total minus the sum of the others. Which party absorbs it is a business decision, and the fact that you asked is what makes you look senior.

Money arithmetic that survives an audit

Four operations cover almost every monetary calculation in a line-of-business application, and each has one way of getting it wrong that is common enough to have a name. 

// 1 — VAT, added to a net figure
decimal net   = 84.50m;
decimal vat   = Math.Round(net * 0.22m, 2, MidpointRounding.AwayFromZero);  // 18.59
decimal gross = net + vat;                                                  // 103.09

// 2 — VAT, extracted from a gross figure (NOT gross * 0.22)
decimal netFromGross = Math.Round(gross / 1.22m, 2, MidpointRounding.AwayFromZero);

// 3 — a percentage discount, applied once, in a named step
decimal discountPct = 15m;
decimal discount    = Math.Round(net * discountPct / 100m, 2, MidpointRounding.AwayFromZero);
decimal payable     = net - discount;

// 4 — splitting a total so the parts still add up
decimal total = 10.00m;
int parts = 3;
decimal share = Math.Round(total / parts, 2, MidpointRounding.ToZero);  // 3.33
decimal last  = total - share * (parts - 1);                            // 3.34 — the remainder
Line by line
  • Extracting VAT is a division, not a multiplication. A gross of €122 contains €22 of VAT, and 122 * 0.22 is 26.84. The correct figure is 122 / 1.22 for the net, and the difference for the tax. This single line is wrong in a remarkable amount of production code.
  • A percentage is not a rate until you divide by a hundred, and the bug is always the same: someone stores 15 in a column called DiscountRate and someone else multiplies by it. Name the variable for its unit — discountPct versus discountRate — and the mistake becomes visible at the call site.
  • MidpointRounding.ToZero on the share, deliberately: rounding each share down guarantees the remainder is positive and can be handed to the last party. Round to nearest instead and last can come out smaller than the others, which looks like a bug even when the total is right.
  • Never apply two percentages by adding them. A 10% discount then a 5% discount is not 15% — it is 14.5%, because the second applies to the already reduced figure. Write the two steps out; do not simplify them into one number.
  • Every line here is decimal from end to end. One double anywhere in the chain reintroduces the base-two error that the whole exercise is avoiding.
What professionals do next

A real system does not pass decimal around at all — it passes a Money type carrying an amount and a currency, so adding euros to pounds cannot compile. A record struct Money(decimal Amount, string Currency) with an operator is about fifteen lines and removes an entire class of bug. That pattern is chapter 05's "make the wrong thing impossible"; the arithmetic inside it is this page.

Random, and why yours repeats

🧒 Simple

A computer cannot actually be random. It follows a recipe that produces numbers which look scattered, and the recipe needs a starting point. Start two recipes at the same point and they produce exactly the same "random" numbers. 

// ✗ the classic bug — a new Random per call
string BadCode() => new Random().Next(1000, 9999).ToString();
// Called in a tight loop on .NET Framework, every call returns the SAME number:
// the seed came from a clock that had not ticked yet.

// ✓ .NET 6 and later — a thread-safe shared instance
int bin = Random.Shared.Next(1, 61);              // 1..60 — upper bound EXCLUSIVE
double jitter = Random.Shared.NextDouble();        // 0.0 <= x < 1.0

// ✓ reproducible, for a test
var seeded = new Random(12345);                    // same seed, same sequence, forever

// ✓ when it must be unguessable — tokens, passwords, coupon codes
int secure = System.Security.Cryptography.RandomNumberGenerator.GetInt32(100000, 999999);
Line by line
  • Next(1, 61) — the lower bound is inclusive and the upper is exclusive, so this gives 1 to 60. Every off-by-one with Random is this line. NextDouble follows the same rule: it can return 0.0 and can never return 1.0.
  • Random.Shared — one instance for the whole process, safe to call from many threads. Before it existed, sharing a Random across threads could corrupt its internal state and make it return zeros forever, and the usual "fix" of a new instance per call caused the repeat above.
  • new Random(12345) — a fixed seed. This is what you want in a test: the numbers are arbitrary but identical on every run, so a failure is reproducible. A test that uses Random.Shared fails once a fortnight and nobody can ever recreate it.
  • RandomNumberGenerator — Random is predictable by design. Given a few outputs, its next output can be computed. Never use it for a password reset token, a session id, a coupon code or anything an attacker profits from guessing; that is a security bug, not a style preference.

Turning a number into text a human reads

A number has no commas, no currency symbol and no fixed number of decimal places — those are all properties of the text you render it as, and they depend on who is reading. Getting this wrong is how a German customer sees a price of €1.234,00 as one euro twenty-three. 

decimal amount = 1234.5m;

amount.ToString("F2")        // "1234.50"  — fixed, two places
amount.ToString("N2")        // "1,234.50" — with a thousands separator
amount.ToString("C")         // "€1,234.50" — currency, from the current culture
amount.ToString("P1")        // for a RATE: 0.155m.ToString("P1") is "15.5 %"
(42).ToString("D5")          // "00042"    — padded, integers only
(0.000012).ToString("E2")    // "1.20E-005" — scientific

$"Total: {amount:N2} kg"                          // format inside interpolation
$"Picked {picked,6} of {total,-6}"                // ,6 right-aligns, ,-6 left-aligns

var it = new CultureInfo("it-IT");
amount.ToString("C", it)                          // "1.234,50 €" — dots and commas SWAPPED
amount.ToString(CultureInfo.InvariantCulture)     // "1234.5" — for a file, an API, a log
Line by line
  • "F2" versus "N2" — both give two decimal places; N adds the grouping separator. Pick N for anything a person reads and F for anything of fixed width.
  • "C" takes the currency symbol from the culture, not from your data. An amount in euros formatted under en-US prints a dollar sign, cheerfully and wrongly. If the currency is a property of the money, pass the matching culture explicitly or write the symbol yourself.
  • "P" multiplies by 100. Pass it 15m expecting "15 %" and you get "1,500 %". It wants the rate, 0.15m.
  • {picked,6} — the number after the comma is an alignment width, positive for right-aligned and negative for left. It pairs with a format: {amount,10:N2}. This is how a console report gets columns that line up without a single PadLeft.
  • CultureInfo.InvariantCulture — for machines. Any number written to a file, a URL, a JSON payload or a log must be invariant, or the same code produces different output on an Italian server and an American one. Every Parse reading it back needs the same argument. This is the most common "works on my machine" defect in the whole framework.
⚠️ ToString("N2") is not rounding

It is display, and it rounds only the text. The stored value is unchanged, so a total computed from stored values will not match the total a user adds up from what they can see. If the two must agree — and on an invoice they must — round the value itself with Math.Round and store that, then format the rounded value for display.

The edges: overflow, division by zero, and NaN

Each numeric family fails differently at its boundary, and the differences are not intuitive. This table is worth knowing by sight, because two of these five rows fail silently.

int big = int.MaxValue;      // 2,147,483,647
int wrapped = big + 1;       // -2,147,483,648 — no error, no warning, no log entry

{
    int caught = big + 1;    // OverflowException — you asked to be told
}

double d = 1.0 / 0.0;        // Infinity, quite legally
double n = 0.0 / 0.0;        // NaN — "not a number"

bool right = double.IsNaN(n);// true — this is the only correct test
Line by line
  • checked — a block (or a single expression, checked(a + b)) in which integer overflow throws instead of wrapping. It is off by default for speed. Turn it on project-wide with <CheckForOverflowUnderflow>true</CheckForOverflowUnderflow> in the .csproj — for business code that is almost always the right setting, and chapter 00d is where that file lives.
  • unchecked is the opposite, and has one honest use: hash-code arithmetic, where wrapping is intended.
  • int.MaxValue is about 2.1 billion, which sounds enormous until it is a row id, a milliseconds counter, or a running total of grams. long costs four extra bytes and removes the question.
  • NaN != NaN is not a C# quirk — it is the IEEE 754 standard, and it is the reason a sort can throw, a Distinct() can keep duplicates and a Max() can return the wrong element once a NaN is in the data. Always test with double.IsNaN.
  • A double that has become Infinity stays infinite through every subsequent operation and lands in the database as an unreadable value, hundreds of lines from the division that caused it.

Exercises, with the reasoning shown

Cover the answer, decide, then read. All four are single lines that have shipped.

Exercise 1 — the pallet count that is one short

int boxes = 41, perPallet = 12;
int pallets = (int)Math.Ceiling(boxes / perPallet);
// What is pallets?
3, and it should be 4.
  • Both operands are int, so 41 / 12 is evaluated as integer division before Math.Ceiling ever sees it — it receives 3 and dutifully returns 3. The cast on the outside is doing nothing useful; the cast needed to be on the inside, on one operand: boxes / (double)perPallet. Note that the code is correct for every input where the division happens to be exact, which is exactly the input a test tends to use.

Exercise 2 — the discount that was applied to the wrong figure

decimal gross = 122.00m;          // includes 22% VAT
decimal vat = gross * 0.22m;      // how much VAT is in there?
// What is vat, and what should it be?
It gives 26.84; the right answer is 22.00.
  • The VAT is 22% of the net, not of the gross. The net is gross / 1.22m = 100.00, and the VAT is the difference. Multiplying the gross overstates the tax by 22% of the tax itself — about 4.84 here, and the error scales with the invoice.

Exercise 3 — the total that will not reconcile

decimal[] lines = { 3.335m, 3.335m, 3.335m };
decimal shown = lines.Sum(x => Math.Round(x, 2, MidpointRounding.AwayFromZero));
decimal total = Math.Round(lines.Sum(), 2, MidpointRounding.AwayFromZero);
// shown vs total?
shown is 10.02, total is 10.01.
  • Rounding each line first pushes three separate half-cents upward; rounding the sum pushes one. Neither is wrong arithmetically — they answer different questions — but an invoice must pick one and use it in both places. The convention that keeps auditors happy is to round each line, store those rounded lines, and make the total the sum of the stored figures. Then the document adds up when a human checks it with a calculator, which is the only test that counts.

Exercise 4 — the loop that never ends

double x = 0.0;
while (x != 1.0)
{
    x += 0.1;
}
// When does this stop?
Never.
  • Ten additions of the nearest double to a tenth land on 0.9999999999999999, and the loop sails past its exit condition and runs forever. Two fixes, both correct: compare with while (x < 1.0) rather than for equality, or — better — count in integers and divide only when you need the value: for (int i = 0; i < 10; i++) { double v = i / 10.0; }. The general rule is that a loop counter should never be a floating-point number.
Try it yourself

Make a console project and paste this in. Every line prints something that catches people out, and seeing them together is worth more than reading about any one of them. 

Console.WriteLine(0.1 + 0.2);                                  // 0.30000000000000004
  Console.WriteLine(0.1m + 0.2m);                                // 0.3
  Console.WriteLine(7 / 2);                                      // 3
  Console.WriteLine(7 / 2.0);                                    // 3.5
  Console.WriteLine(-7 % 3);                                     // -1, not 2
  Console.WriteLine(Math.Round(2.5));                            // 2
  Console.WriteLine(Math.Round(2.5, MidpointRounding.AwayFromZero)); // 3
  Console.WriteLine(Math.Floor(-2.1));                           // -3
  Console.WriteLine(Math.Truncate(-2.1));                        // -2
  Console.WriteLine(int.MaxValue + 1);                           // large negative
  Console.WriteLine(1.0 / 0.0);                                  // ∞
  Console.WriteLine(double.NaN == double.NaN);                   // False
  Console.WriteLine(1234.5m.ToString("C", new CultureInfo("it-IT")));
Why each line prints what it prints
  • The first two are base: binary floating point cannot hold a tenth exactly, and base-ten decimal can.
  • Lines three and four are integer division — one fractional operand is all it takes to change the answer.
  • -7 % 3 is -1 because C# takes the sign of the dividend. Several languages answer 2 here, which is why it is worth seeing once.
  • The two Math.Round lines are the same number rounded two ways, which is the whole argument for passing the mode explicitly.
  • Floor and Truncate disagree only on negatives — toward negative infinity against toward zero.
  • The last three are the silent failures: an overflow with no exception, a division by zero that is legal for double, and a value that is not equal to itself.

Then change one thing: put <CheckForOverflowUnderflow>true</CheckForOverflowUnderflow> into the .csproj and run it again. The int.MaxValue + 1 line now throws. Decide whether you would want that on in a system that handles money.

Golden rules

  1. Money is decimal, measurements are double, counts are int. A double in a currency column is the most expensive type choice in business software, and it is never caught by a test with round numbers.
  2. Never compare two doubles with ==. Compare within a tolerance chosen from what the number means. decimal compares exactly, which is one more reason money lives there.
  3. Integer division happens before anything outside it can help. Math.Ceiling(41 / 12) is 3. Cast one operand, not the result.
  4. Math.Round defaults to banker's rounding — halves go to the nearest even number. For an invoice, pass MidpointRounding.AwayFromZero explicitly, and pass it everywhere so the same number never rounds two ways.
  5. Round once, at the edge. Rounding mid-calculation and again at the end can move the answer by a whole unit.
  6. When you split a total, give the remainder to somebody explicitly. Three independent roundings of a third of €10 lose a cent, and no rounding mode fixes it.
  7. VAT comes out of a gross figure by division, not multiplication. gross / 1.22m for the net; the difference is the tax.
  8. Ceiling and Floor mean toward infinity, not up and down. Math.Floor(-2.1) is -3. "Drop the fraction" is Truncate.
  9. Format for machines with InvariantCulture and for humans with a real culture. Anything written to a file, URL, log or API that does not say invariant is a bug waiting for a server in another country.
  10. Random is predictable by design. Use Random.Shared for ordinary work, a fixed seed in tests, and RandomNumberGenerator for anything an attacker would profit from guessing.
  11. Integer overflow is silent and double overflow is silent. Turn on CheckForOverflowUnderflow in business code, and test a double with double.IsNaN rather than ==.

Interview questions

"Why should money never be a double?"

Because double is binary floating point: it stores numbers as powers of two, so a value like 0.1 has no exact representation and every operation carries a small error that accumulates across a sum. decimal stores a scaled integer in base ten, so decimal fractions are exact and a column of them totals exactly. The practical symptom is an invoice that is a cent out, or a reconciliation that fails on one row in ten thousand — late, intermittently, and in production. decimal is slower and has a smaller range, and neither of those costs is relevant to money.

"What does Math.Round(2.5) return, and why?"

2. The default is MidpointRounding.ToEven, banker's rounding: an exact half goes to the nearest even number, so 2.5 goes down and 3.5 goes up. The reason is statistical — always rounding halves up biases a large column of figures upward, while alternating keeps the rounded total matching the unrounded one. It is also the IEEE 754 default. When the business wants the school rule I pass MidpointRounding.AwayFromZero explicitly, and I make sure it is passed everywhere, because the worst outcome is the same amount rounding two different ways in two parts of the system.

"You need 4 pallets for 41 boxes at 12 per pallet. Why does (int)Math.Ceiling(41 / 12) give 3?"

Because the division is evaluated first, and both operands are int, so C# does integer division and hands Math.Ceiling the value 3 — there is no fraction left to round up. The cast on the outside comes too late. The fix is to cast one operand before dividing, 41 / (double)12, or to avoid floating point entirely with (41 + 12 - 1) / 12, which is the integer ceiling-division idiom.

"How would you split €10 three ways?"

Not by rounding each third, because 3.33 three times is 9.99 and a cent has gone missing. I compute n - 1 shares rounded down, then make the final share the total minus the sum of the others — so the parts always reconstruct the whole by construction, not by luck. Which party gets the extra cent is a business decision rather than a technical one, and it is worth asking, because the answer differs between a refund, a commission split and a tax allocation.

"Perché 0.1 + 0.2 non fa 0.3?"

Perché double è in virgola mobile binaria: rappresenta i numeri come potenze di due, e un decimo in base due è periodico esattamente come un terzo in base dieci. Quindi 0.1 è in realtà il double più vicino a un decimo, leggermente diverso, e sommandone due gli errori non si annullano. Con decimal, che è in base dieci, il risultato è esatto. La conseguenza pratica è che due double non si confrontano mai con == ma con una tolleranza, e che i soldi stanno in decimal.
