Indexes, plans and transactions

Anyone can write a WHERE clause. Explaining why it does a table scan, and what happens when two people submit the same order at the same moment, is the thing that separates a candidate with three years of experience from one with one year repeated three times.

From the advert

"Buona conoscenza di T-SQL e dei principali RDBMS." This chapter is where "buona" becomes visible. It is also the chapter that explains why they needed Redis.

Indexes

🧒 Simple

A book about animals, five hundred pages, no order. To find "elephant" you turn every page. That is a scan.

Now someone adds an index at the back: every animal in alphabetical order with its page number. You flip to E, read "elephant — page 312", and go straight there. That is a seek.

The catch: every time a new animal is added to the book, someone must also write it into the index. Finding gets faster; adding gets slower. That is the whole trade, and it never goes away.

🎓 Professional

An index is a B-tree keyed on one or more columns, with pointers back to the rows. Depth is typically 3–4 levels even for millions of rows, so a seek is a handful of page reads regardless of table size — O(log n) versus the O(n) of a scan.

The cost is real: every INSERT, UPDATE and DELETE must maintain every affected index, and each index consumes storage and memory. A table with twelve indexes has a write path twelve times more expensive than it needs to be. Indexing is a deliberate trade, not a default.

creating indexes that earn their keep
-- Composite index. Column ORDER is not arbitrary.
CREATE INDEX IX_Orders_Customer_Created
    ON dbo.Orders (CustomerId, CreatedAtUtc);

-- Covering index: INCLUDE carries extra columns in the leaf pages, so the
-- query is answered entirely from the index — no lookup back to the table.
CREATE INDEX IX_Orders_Status_Covering
    ON dbo.Orders (Status)
    INCLUDE (CustomerId, Total, CreatedAtUtc);

-- Filtered index: only index the rows anyone queries. Stays small even when
-- the table holds ten years of delivered orders.
CREATE INDEX IX_Orders_Open
    ON dbo.Orders (CreatedAtUtc)
    WHERE Status IN (2, 3);
🎓 The leftmost-prefix rule

An index on (CustomerId, CreatedAtUtc) is a phone book sorted by (Surname, FirstName). It serves:

QueryResultWhy
WHERE CustomerId = @cseek"all the Rossis"
WHERE CustomerId = @c ORDER BY CreatedAtUtcseek"the Rossis, already in order"
WHERE CustomerId = @c AND CreatedAtUtc > @dseek"the Rossis since March"
WHERE CreatedAtUtc > @dscan ⚠"everyone called Marco" — the second column is only sorted within a surname

Rule of thumb: equality columns first, then range and sort columns.

SARGability — how to accidentally disable your own index

the same filter, indexed and not
-- ✗ a function on the COLUMN: the engine must compute it for every row
WHERE YEAR(o.CreatedAtUtc) = 2026
WHERE UPPER(c.Name) = 'ROSSI'
WHERE o.OrderNumber LIKE '%2026%'          -- leading wildcard: unusable
WHERE CAST(o.CustomerId AS NVARCHAR) = @id  -- implicit conversions do this too

-- ✓ leave the column alone; transform the PARAMETER instead
WHERE o.CreatedAtUtc >= '2026-01-01' AND o.CreatedAtUtc < '2027-01-01'
WHERE c.Name = 'Rossi'            -- default collation is case-insensitive anyway
WHERE o.OrderNumber LIKE '2026%'  -- trailing wildcard can still seek
⚠ The one that catches everyone

An NVARCHAR parameter compared against a VARCHAR column causes an implicit conversion on the column — and instantly turns a seek into a scan on a table that has a perfectly good index. It is invisible in the query text and obvious in the execution plan, which is precisely why you learn to read plans.

Reading an execution plan

In SSMS: Ctrl+M then run, or Ctrl+L for the estimated plan. Read it right to left. Four things to look for, in order:

What you seeWhat it means
Clustered Index Scan / Table Scan on a big table No usable index, or you broke SARGability. Where you start.
Key Lookup The index found the rows but not all the columns, so it goes back to the table once per row. Fix with INCLUDE.
A fat arrow Arrow thickness is row count. A fat arrow early means you are filtering too late.
Estimated rows ≫ actual rows Stale statistics — the optimiser chose a plan for a table shape that no longer exists. UPDATE STATISTICS.
measure, do not guess
SET STATISTICS IO, TIME ON;
-- your query here

-- "logical reads" is the number to watch: it is the count of 8 KB pages touched,
-- and unlike elapsed time it does not change with cache state or machine load.
-- Before an index: logical reads 14,882.  After: 6.  That is the whole story.

Temp tables and table variables

Both hold intermediate results, both live in tempdb, and choosing wrongly is a common cause of a query that is fast on ten rows and hopeless on a hundred thousand. The difference that matters is whether the optimiser knows how many rows are in there.

#temp — temp table@table — table variable
StatisticsYes — the optimiser sees the real row countNo — historically estimated at one row
IndexesAny, added after creationOnly what you declare inline
Survives a ROLLBACKNo — it is transactionalYes — which is occasionally exactly what you want
Visible to a called procedureYesNo — scoped to the batch
Good forMany rows, joins, anything needing an indexA handful of rows, passed around
⚠ The one-row estimate

Load 200,000 rows into a table variable and join it to a large table, and the optimiser plans as though there were one row — so it picks a nested loop and executes it two hundred thousand times. The plan looks tidy; the query does not finish. Swapping @t for #t is often a one-character fix with a thousand-fold effect, and it is worth trying before anything cleverer.

SQL Server 2019 improved this with deferred compilation for table variables under compatibility level 150, so the estimate is taken after population. Know that it exists; plenty of production databases still run lower, and the rule of thumb below is unaffected.

The rule of thumb: a few rows you are passing along — a table variable. Anything you will join, filter or index — a temp table. And the rollback row is not trivia: a table variable survives a rolled-back transaction, which is how you keep a record of why something failed when the transaction that failed took everything else with it.

Transactions and ACID

🧒 Simple

Moving money between two piggy banks: take €10 out of one, put €10 into the other. If the phone rings between those two steps and you never finish, €10 has vanished from the world.

A transaction is a promise that both steps count as one step. Either both happen or neither does. There is no "in between" that anyone else can ever observe.

🎓 Professional
  • Atomicity — all statements commit, or none do.
  • Consistency — constraints hold before and after.
  • Isolation — concurrent transactions do not see each other’s partial work. How much is configurable, and that is the interesting part.
  • Durability — once committed, it survives a power cut, because the write-ahead log was flushed first.
the shape, with error handling
BEGIN TRANSACTION;
BEGIN TRY
    UPDATE dbo.Accounts SET Balance = Balance - 10 WHERE Id = 1;
    UPDATE dbo.Accounts SET Balance = Balance + 10 WHERE Id = 2;
    COMMIT;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK;
    THROW;                   -- rethrow; do not swallow
END CATCH;

Isolation levels

Each level trades correctness against concurrency. Know the default and know the two you would actually change it to.

LevelDirty readNon-repeatable readPhantomNotes
READ UNCOMMITTEDpossiblepossiblepossible Same as WITH (NOLOCK). Can read rows that are rolled back seconds later.
READ COMMITTEDnopossiblepossible The SQL Server default.
REPEATABLE READnonopossibleHolds shared locks to the end.
SERIALIZABLEnononoSafest, least concurrent. Range locks.
SNAPSHOTnonono Readers never block writers — uses row versions in tempdb. Often the right answer.
⚠ WITH (NOLOCK) is not "make it fast"

It is scattered through Italian enterprise codebases as a performance incantation. What it actually does is permit dirty reads: you can read data that is rolled back a moment later, read a row twice, or miss a row entirely if a page split moves it mid-scan. It is acceptable on an approximate dashboard. On an invoice total it is a bug waiting for an auditor. If the real problem is readers blocking writers, the correct answer is SNAPSHOT isolation. Saying that in an interview lands very well.

Deadlocks and concurrency

Three defences, in order of value:

  1. Always take locks in the same order across the codebase. Alphabetical by table name is arbitrary and works. This prevents most deadlocks outright.
  2. Keep transactions short. Never call an HTTP API or wait for user input inside one.
  3. Retry. Error 1205 is transient by definition — the victim can simply try again, and often succeeds immediately.

Optimistic concurrency — the lost update

🧒 Simple

Two people open the same shared document. Anna changes the title, Marco changes the title differently, both press save. Marco saved last, so Anna’s change is gone — and nobody was told.

The fix is a version number on the page. Marco’s save says "I am updating version 4", but the page is already at version 5, so his save is refused and he is shown what changed.

rowversion — the standard solution
-- SQL Server increments this automatically on every UPDATE
ALTER TABLE dbo.Orders ADD RowVersion ROWVERSION;
// EF Core: mark it, and concurrent updates now throw instead of silently losing data
builder.Property(o => o.RowVersion).IsRowVersion();

try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    // somebody else changed this row since we loaded it →
    // reload, show the conflict, or merge. Never just overwrite.
}
Try it yourself

Two SSMS query windows side by side. This is the single most useful ten minutes you can spend on this chapter. 

-- Window 1: open a transaction and do NOT commit
BEGIN TRANSACTION;
UPDATE dbo.Orders SET Total = 999 WHERE Id = 1;

-- Window 2: now try to read it
SELECT Total FROM dbo.Orders WHERE Id = 1;         -- ← hangs. Blocked.
SELECT Total FROM dbo.Orders WITH (NOLOCK) WHERE Id = 1;  -- ← returns 999

-- Window 1:
ROLLBACK;
-- Window 2 read 999. That number never existed. That is a dirty read.

Then create a table with a million rows, query it unindexed with SET STATISTICS IO ON, add the index, and compare the logical reads. Watching 14,882 become 6 is more persuasive than any explanation.

Golden rules

  1. An index makes reads fast and writes slower. Every one must be justified.
  2. One clustered index — it is the table. Many non-clustered ones.
  3. Composite index column order: equality first, then range and sort. Leftmost prefix only.
  4. A function on a column, a leading %, or an implicit type conversion each kill index usage. Transform the parameter, not the column.
  5. INCLUDE turns a Key Lookup into a covering index — often the single highest-value fix available.
  6. Read plans right to left. Look for scans on large tables, key lookups, and fat arrows.
  7. SET STATISTICS IO ON, and compare logical reads. Time lies; page counts do not.
  8. READ COMMITTED is the default. SNAPSHOT is usually the right answer when readers block writers.
  9. NOLOCK permits dirty reads. Never on anything financial.
  10. Deadlocks come from inconsistent lock ordering. Fix the order, keep transactions short, retry on 1205.
  11. Never hold a transaction open across a network call or user input.
  12. Use rowversion for optimistic concurrency. Silently overwriting somebody else’s edit is data loss, not a merge.

Interview questions

"What is the difference between a clustered and a non-clustered index?"

The clustered index is the table, stored in key order — one per table. A non-clustered index is a separate sorted structure with pointers back, and you can have many. Add that a non-clustered index missing a needed column causes a Key Lookup, fixed with INCLUDE.

"This query is slow. Walk me through what you do."

Look at the actual execution plan; check for a scan on a large table; check whether the predicate is SARGable; check for key lookups; check estimated versus actual rows for stale statistics. Then measure with SET STATISTICS IO before and after — and say explicitly that you would not add an index without measuring, because of the write cost.

"What are the isolation levels, and what is the default?"

Read uncommitted, read committed (the default in SQL Server), repeatable read, serializable, plus snapshot. Map each to the anomaly it prevents: dirty read, non-repeatable read, phantom.

"What causes a deadlock and how do you fix it?"

Two transactions acquiring the same locks in opposite orders. Fix by standardising lock order, shortening transactions and retrying the victim. Note that a deadlock is a cycle, not a timeout — SQL Server detects it and kills one side deliberately.

"Two users edit the same order at once. What happens?"

Without protection, last write wins and the first edit is lost silently. With a rowversion column and EF Core's concurrency token, the second save throws DbUpdateConcurrencyException and you can reload and show the conflict. That is optimistic concurrency; pessimistic locking is the alternative and scales far worse.
