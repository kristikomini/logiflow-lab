Real-time: WebSocket and SignalR

Every chapter so far has the browser asking and the server answering. This one is about the other direction: the server having something to say, and a screen that has to show it without anybody pressing refresh. It is the transport under every live map, every dispatch board and every notification bell you will be asked to build.

Why this chapter exists

The word real-time appears in adverts far more often than the course admitted. Tracking and dispatching, warehouse and plant screens, order boards, anything where an operator is watching rather than searching — all of them need the server to push. Until now the only place this site mentioned a WebSocket was chapter 19, as the pipe under a Blazor circuit, which is a special case and a misleading one to generalise from.

Real-time also has the highest ratio of easy demo to hard production of anything in this course. A chat sample works in twenty lines. Then the second server arrives, the train goes into a tunnel, the truck sends a position every second for eight hours, and every one of those is a different problem with a different answer. Those answers are what an interviewer is checking for, because they are what separates somebody who followed the tutorial from somebody who ran the thing.

Polling, and why the server has to be able to speak

🧒 Simple

Imagine waiting for a parcel. You could walk to the front door every thirty seconds and check. Most of those trips you find nothing, you have worn yourself out, and when the parcel does come you still find out up to thirty seconds late.

Or you could give the courier a doorbell. Now you do no walking at all, and you hear about the parcel the moment it is there. The doorbell costs you something — a wire has to stay connected to your house — but it beats the walking, and this chapter is about the wire.

🎓 Professional

HTTP is request/response: a connection is opened by the client, one answer comes back, it closes. Nothing in that shape lets a server speak first. Polling fakes it by asking repeatedly, and it is not automatically wrong — at a thirty-second interval with a handful of users it is the correct, boring choice, and it survives load balancers, proxies and offline gaps for free. What kills it is the arithmetic: latency is half the interval on average, and the request count is users × frequency whether or not anything changed.

A WebSocket replaces that with one connection that stays open and carries frames in both directions. It starts life as an ordinary HTTP GET carrying Upgrade: websocket; the server answers 101 Switching Protocols and the same TCP connection stops being HTTP. From then on either side may send at any time.

Server-Sent Events is the third option and the forgotten one: a single HTTP response that never finishes, streaming text down to the browser. It is one-directional, it reconnects by itself, and for a dashboard that only ever receives, it is simpler than a WebSocket and goes through more proxies. When the answer to "does the client need to send too?" is no, it deserves the shortlist.

SignalR is not a fourth transport. It is ASP.NET Core's library on top of those three: it negotiates the best available one, falls back to SSE and then to long polling, and adds the parts you would otherwise write yourself — a method-call protocol in both directions, connection ids, groups, automatic reconnect and a scale-out story.

A hub, in full

A hub is a class whose public methods the browser can call, and whose Clients property lets the server call the browser back. It is a transport edge and nothing more — the same role a controller has in chapter 14, with the same rule about not putting your domain logic in it. 

// TrackingHub.cs — what the browser is allowed to call.
[Authorize]
public sealed class TrackingHub : Hub<ITrackingClient>
{
    public async Task WatchZone(string zoneId, CancellationToken ct)
    {
        // The connection asked for a zone. Check it is allowed to have it —
        // the hub method is a public endpoint, exactly like an action.
        if (!await _zones.UserMayWatchAsync(Context.UserIdentifier!, zoneId, ct))
        {
            throw new HubException("Not your zone.");
        }

        await Groups.AddToGroupAsync(Context.ConnectionId, $"zone:{zoneId}", ct);
    }

    public Task StopWatchingZone(string zoneId) =>
        Groups.RemoveFromGroupAsync(Context.ConnectionId, $"zone:{zoneId}");
}

// The strongly-typed client contract. The browser implements these names.
public interface ITrackingClient
{
    Task VehicleMoved(VehiclePositionDto position);
    Task ZoneSnapshot(IReadOnlyList<VehiclePositionDto> all, long asOfVersion);
}

// Pushing from OUTSIDE the hub — a background worker, a message consumer,
// an endpoint. This, not the hub itself, is where most sends come from.
public sealed class PositionBroadcaster(IHubContext<TrackingHub, ITrackingClient> hub)
{
    public Task PublishAsync(VehiclePositionDto p) =>
        hub.Clients.Group($"zone:{p.ZoneId}").VehicleMoved(p);
}
Line by line
  • Hub<ITrackingClient> — the generic form. Without it you write Clients.Group(x).SendAsync("VehicleMoved", p) and the method name is a string nothing checks; with it, renaming the method breaks the build instead of the screen. Always take the generic one.
  • [Authorize] — hubs are endpoints. Everything chapter 15 says applies, and the attribute is checked once when the connection is established, not per message. A token that expires mid-connection does not end it, which is a real question and is answered further down.
  • WatchZone is callable by anyone connected, with any argument they like. Authorising the zone inside the method is not belt-and-braces; without it, any signed-in user joins any group by typing its name into the console.
  • Groups.AddToGroupAsync — a group is a named set of connection ids, and it is the mechanism for "this screen only wants the vehicles in zone 4". Groups are cheap, created on first use, and disappear when the last member leaves. Note they hold connections, not users: one user with two tabs is two connections.
  • Context.ConnectionId — identifies the connection, and it changes on every reconnect. Storing it in your database as though it named a person is the mistake that produces "notifications stop after the laptop sleeps". Context.UserIdentifier is the stable one, and Clients.User(id) reaches every connection that user has open.
  • throw new HubException — the one exception type whose message is sent to the client. Everything else arrives as a generic error, deliberately, so an internal message cannot leak to the browser.
  • IHubContext<THub, TClient> — how anything that is not a hub method pushes: a BackgroundService, a broker consumer from chapter 22, an ordinary endpoint after it commits. Inject it; never new up a hub yourself. Hub instances are created per call and disposed immediately, so holding one is always a bug.
  • ZoneSnapshot(..., long asOfVersion) — the method that exists because of the next section. A client that has just reconnected needs the whole picture and a version to count from, not a replay of what it missed.

The browser end

The React side is short, and every line of it is load-bearing. This is the shape that survives a tunnel. 

// useZoneTracking.ts — one connection, owned by an effect.
import { HubConnectionBuilder, HttpTransportType, LogLevel } from '@microsoft/signalr';

export function useZoneTracking(zoneId: string, onMoved: (p: VehiclePosition) => void) {
  const handler = useRef(onMoved);
  useEffect(() => { handler.current = onMoved; }, [onMoved]);

  useEffect(() => {
    const conn = new HubConnectionBuilder()
      .withUrl(`${import.meta.env.VITE_API_URL}/hubs/tracking`, {
        accessTokenFactory: () => getFreshAccessToken(),
      })
      .withAutomaticReconnect({ nextRetryDelayInMilliseconds: r => Math.min(1000 * 2 ** r.previousRetryCount, 30_000) })
      .configureLogging(LogLevel.Warning)
      .build();

    conn.on('VehicleMoved',  p => handler.current(p));
    conn.on('ZoneSnapshot',  (all, v) => replaceAll(all, v));
    conn.onreconnected(() => conn.invoke('WatchZone', zoneId));

    conn.start()
        .then(() => conn.invoke('WatchZone', zoneId))
        .catch(() => setStatus('offline'));

    return () => { conn.stop(); };
  }, [zoneId]);
}
Line by line
  • handler in a useRef, refreshed by its own effect — this is the stale closure from the React chapter, in the place it actually bites. If onMoved went in the main dependency array, every render would tear down and rebuild the connection; if it were captured directly and left out of the array, the handler would keep calling the version from the first render forever. A ref is the fix, and knowing why is worth more than the line itself.
  • accessTokenFactory — a function, not a token, so it is called again on every reconnect and a refreshed token is used. Handing it a string captured at mount is how a long-lived screen starts failing to reconnect after an hour, in a way nobody reproduces in a morning's testing.
  • withAutomaticReconnect with explicit backoff — the default gives up after four attempts, at 0, 2, 10 and 30 seconds. An operations screen that is meant to run all day should retry forever, with a cap, and show its state.
  • onreconnected re-invoking WatchZone — group membership does not survive a reconnect. The new connection has a new id and is in no groups. Forgetting this is the classic real-time bug: it works, the train goes through a tunnel, and the screen is silent for the rest of the shift with the connection showing green.
  • ZoneSnapshot on reconnect, rather than a replay — see the next section. Ask for the current picture; do not ask for what you missed.
  • conn.stop() in the cleanup — without it, changing zone leaves the old connection open and the browser accumulates one socket per navigation until it refuses to open more.
  • The transport is not pinned here on purpose. Pinning to HttpTransportType.WebSockets is the right call behind a load balancer you control — it lets you skip negotiation and therefore skip sticky sessions — and the wrong call on a corporate network that only lets HTTPS through, where the fallback is the entire reason it works at all.

The four things that make it hard

One: the second instance. Connections live in the memory of the process that accepted them. Scale to two instances and a message published on instance 1 reaches nobody connected to instance 2 — no error, no log, half your users silently stale. The fix is a backplane: AddStackExchangeRedis makes every instance publish to Redis and forward what it reads back to its own clients, which is the same backplane chapter 20 mentions in one line. Azure SignalR Service does the same job by taking the connections off your servers entirely. Separately from the backplane, the negotiate handshake and the connection that follows it must land on the same instance, so you need sticky sessions unless clients are configured to use WebSockets only and skip negotiation.

Two: nothing here is durable. A hub is not a queue. A message sent to a group while your connection was down is not buffered anywhere; it is gone. So the rule is: on reconnect, re-read state; never ask for a replay. Send a snapshot plus a version, and let the client diff. If a particular event genuinely must not be missed — a dispatch assignment, a payment — then it belongs in a durable store or a broker (chapter 22) with the socket used only as the nudge that says "there is something new for you". The socket is the doorbell, never the parcel.

Three: a fast producer and a slow client. Two hundred vehicles emitting a position per second is twelve thousand messages a minute into a laptop on hotel wi-fi, and the client cannot refuse them. What the screen needs is not every event: it is the current position, at a rate an eye can use. Throttle server-side to a fixed tick — coalesce to the latest position per vehicle and send one batch per second per zone — and the problem disappears along with most of your bandwidth bill. Doing it in the browser instead only moves the queue to the place with the least memory.

Four: authentication over a socket. A browser WebSocket cannot set an Authorization header, so the SignalR JavaScript client puts the token in the query string as access_token — where it lands in access logs, proxy logs and anything that records URLs. Keep those tokens short-lived, make the server read them explicitly for hub paths only, and scrub the query string in your logging (chapter 25). Then know the second half: authorisation is evaluated when the connection is established, so an expiring token does not end an open connection by itself. Long-lived screens need the connection to be closed and re-established on expiry, or a re-check of the claim on the operations that matter.

"It works on my machine" is structural here

One developer machine has one instance, one client, a perfect network and no proxy. Every one of the four problems above is invisible in exactly that configuration, which is why real-time code reaches production broken more often than anything else in this course. The three tests worth doing before you say it works: run two instances behind a proxy, kill the network for sixty seconds and bring it back, and leave one screen open overnight.

Add the infrastructure ones, because they are not yours and will not appear in your logs. Nginx, IIS and most cloud load balancers need explicit configuration to carry an upgraded connection, and an idle-timeout shorter than SignalR's keep-alive will cut healthy connections on a schedule. A connection that drops every sixty or a hundred and twenty seconds, exactly, is never your code.

Choosing, and saying so

The competent answer to "how would you do the live screen?" starts by refusing the premise. How stale is too stale, how many concurrent viewers, and does the client need to send? Thirty-second polling is right far more often than the word real-time in an advert suggests, it costs nothing to operate, and proposing it where it fits is a stronger signal than reaching for a socket by reflex.

Above that line: SSE when the flow is one-directional and the stack is not .NET-centric; SignalR when it is .NET, because the fallbacks, groups, reconnect and backplane are all written already; a raw WebSocket when the other end is not a browser and a protocol is fixed for you, which in this region usually means a machine or a gateway rather than a person (chapter 32b). And a broker stays a broker: it moves work between services durably, and the hub only tells a screen that something moved.

Interview questions

"Che differenza c'è fra polling e WebSocket?"

Polling is the client asking on a timer: simple, proxy-friendly, and it costs one request per client per interval whether or not anything changed, with latency averaging half the interval. A WebSocket is one connection, upgraded from an HTTP GET, that stays open so either side can send at any time. Then give the judgement, because that is what is being asked: polling is the right answer for low frequency and few users, and the socket earns its complexity when the data changes faster than you would want to poll.

"What does SignalR give you over a raw WebSocket?"

Transport negotiation with fallback to Server-Sent Events and long polling, a remote-method protocol in both directions instead of hand-rolled message framing, connection ids and groups, automatic reconnect, and a backplane for running more than one server. It is not a different protocol — on a healthy network it is a WebSocket underneath.

"You scale the API to three instances and half the users stop getting updates. Why?"

Connections live in the memory of the instance that accepted them, so a message published on one instance never reaches clients attached to the other two. You need a backplane — Redis, or Azure SignalR Service — so every instance forwards to its own clients. And separately, sticky sessions, because the negotiate handshake and the connection that follows it must land on the same instance unless the client is pinned to WebSockets and skips negotiation.

"A client reconnects after two minutes offline. What should happen to the messages it missed?"

Nothing, because there are none to have: a hub is not durable and nothing was buffered. The correct design is to re-read state on reconnect — ask for a snapshot with a version and diff from there — and to rejoin any groups, because group membership belongs to the old connection id and is gone. If some event genuinely cannot be missed, it does not belong on the socket at all; it belongs in a broker or a table, with the socket used only to say that something is waiting.

"Two hundred vehicles, one position each per second, forty operators watching. Concerns?"

The client cannot apply back-pressure, so the answer is to not send it. Coalesce server-side to the latest position per vehicle and emit one batch per second per zone, scope the groups so an operator receives only their zone, and send deltas rather than whole objects. Then say what you would measure: connection count, messages per second, and the send queue, because the failure mode is memory on the server and a frozen tab on the client rather than an exception anywhere.

"How is a hub connection authenticated, and what is the catch?"

A browser WebSocket cannot set headers, so the token travels in the query string as access_token and the server is configured to read it on the hub path. The catch is twofold: query strings get written to access and proxy logs, so the tokens must be short-lived and the logging must scrub them; and authorisation is evaluated at connection time, so an expiring token does not close an already-open connection. A screen that runs all day needs to re-establish rather than assume.

"The connection drops every sixty seconds, exactly. Where do you look?"

Not in your code. An interval that regular is an idle timeout in something between the browser and the process — a load balancer, a reverse proxy, an application gateway — cutting a connection it thinks is dead. Either raise that timeout or lower SignalR's keep-alive beneath it. The related one-off version is a proxy not configured to forward an upgraded connection at all, where SignalR silently falls back to long polling and everything works but feels wrong.
