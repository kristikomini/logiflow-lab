Object-oriented programming

Four words get recited in every interview — encapsulation, abstraction, inheritance, polymorphism. Reciting them is worth nothing. Knowing which one solves which problem, and knowing that experienced developers use the third one least, is worth a great deal.

From the advert

"…e familiarità con la programmazione ad oggetti (OOP)." Listed in the same breath as C# itself, which means they expect you to design types, not only call them.

What OOP is actually for

🧒 Simple

Think about a television remote. It has buttons on the front and a tangle of electronics inside. You press volume up and the sound gets louder. You have no idea how, and that is the entire point — the tangle is hidden behind the buttons.

Now: your friend has a different remote. Different shape, different colour, different electronics. But it also has a volume up button, so you already know how to use it.

Hiding the tangle is encapsulation. "Every remote has volume up" is abstraction. "Any remote you hand me, I can turn it up" is polymorphism. And "a TV remote is a kind of remote" is inheritance.

🎓 Professional

OOP is a strategy for managing change in large systems. Its unit is the type: data and the operations valid on that data, bound together so that invariants can be enforced in one place. The four principles are not decorations — each one buys a specific freedom:

  • Encapsulation → freedom to change internals without breaking callers.
  • Abstraction → freedom to depend on a contract rather than an implementation, which is what makes testing and dependency injection possible.
  • Inheritance → freedom to reuse behaviour … at the cost of a permanent, tight coupling to a base class.
  • Polymorphism → freedom to add a new case without editing existing code — the Open/Closed principle in practice.

Encapsulation, done properly

Most code that claims to be encapsulated is not. A class with fifteen public setters is a struct wearing a costume: any caller can put it into an invalid state, so the rules end up duplicated in every caller.

✗ not encapsulated — the rules live everywhere
public class Order
{
    public OrderStatus Status { get; set; }
    public List<OrderLine> Lines { get; set; } = new();
    public decimal Total { get; set; }
}

// Every caller must remember all three steps, and eventually one will not:
order.Lines.Add(line);
order.Total = order.Lines.Sum(l => l.Price);   // forgotten here → wrong invoice
order.Status = OrderStatus.Draft;
✓ encapsulated — the rules live in one place
public class Order
{
    private readonly List<OrderLine> _lines = new();

    // Read-only to the outside. Callers can look, not reach in.
    public IReadOnlyList<OrderLine> Lines => _lines;
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;
    public decimal Total => _lines.Sum(l => l.Price);   // cannot drift

    public void AddLine(OrderLine line)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Cannot change a submitted order.");
        _lines.Add(line);
    }

    public void Submit()
    {
        if (_lines.Count == 0)
            throw new InvalidOperationException("An order needs at least one line.");
        Status = OrderStatus.Submitted;
    }
}

The second version cannot be misused. There is no sequence of public calls that produces an empty submitted order or a total that disagrees with the lines. That is encapsulation — not the mechanical act of writing private on a field.

⚠ The leak most people miss

Returning List<T> from a property hands the caller your internal collection. They can Add to it, bypassing every rule in AddLine. Expose IReadOnlyList<T> instead — and remember it is a view, not a copy: it prevents the caller from mutating, it does not freeze the list.

abstract class vs interface

The perennial question. The distinction is about what you are modelling.

 abstract classinterface
ModelsWhat something isWhat something can do
How manyOne base class onlyAs many as you like

Practical rule: an interface for every dependency that crosses a boundary (a repository, a mail sender, a clock), because that is what lets you substitute a fake in tests and register the real one in the DI container. An abstract class only when several types genuinely share implementation, not merely a name.

both, in the shape you will meet daily
// A capability. Anything can claim it. This is the seam.
public interface INotificationSender
{
    Task SendAsync(Notification n, CancellationToken ct);
}

// Shared machinery for the family that needs retries.
public abstract class RetryingSender : INotificationSender
{
    public async Task SendAsync(Notification n, CancellationToken ct)
    {
        for (var attempt = 1; ; attempt++)
        {
            try { await SendCoreAsync(n, ct); return; }
            catch (TransientException) when (attempt < 3)
            {
                await Task.Delay(200 * attempt, ct);
            }
        }
    }

    // The one thing each subclass must supply.
    protected abstract Task SendCoreAsync(Notification n, CancellationToken ct);
}

public sealed class EmailSender : RetryingSender
{
    protected override Task SendCoreAsync(Notification n, CancellationToken ct)
        => _smtp.SendAsync(n.To, n.Body, ct);
}

That structure has a name — the Template Method pattern: the base fixes the algorithm, the subclass fills in one step. It is the case where inheritance genuinely earns its keep.

virtual, override, new and sealed

the four keywords, and the one that lies
public class Base
{
    public virtual string Describe() => "base";      // may be replaced
}

public class Good : Base
{
    public override string Describe() => "good";    // truly replaces it
}

public class Bad : Base
{
    public new string Describe() => "bad";         // only HIDES it
}

Base a = new Good();
Base b = new Bad();

Console.WriteLine(a.Describe());     // good  — dispatched on the real type
Console.WriteLine(b.Describe());     // base  — dispatched on the variable's type ⚠
Console.WriteLine(((Bad)b).Describe()); // bad   — same object, different answer
⚠ Why new is a trap

An object that answers differently depending on which variable you hold it in has broken the fundamental promise of polymorphism. new exists for one narrow case — a base class you do not control added a member that collides with yours — and virtually every other use is an accident. This is a favourite interview question precisely because it separates people who have read about OOP from people who have debugged it.

sealed is the opposite move: it forbids further inheritance. Making classes sealed by default is a good habit — it documents intent, prevents a whole category of fragile-base-class problems, and lets the JIT devirtualise calls.

Composition over inheritance

🧒 Simple

Inheritance is being born into a family: you get your family's nose whether you want it or not, and you can never change families. Composition is hiring people: you pick who helps you, you can swap them, and if one is unavailable you hire someone else for the afternoon. Most of the time, hiring is easier than being born again.

🎓 Professional

Inheritance is the tightest coupling the language offers: the derived type depends on the base’s implementation, not merely its contract, and that dependency is fixed at compile time. Change a base method and every subclass in the codebase may silently change behaviour — the fragile base class problem. Deep hierarchies also collide with reality quickly, because real domains are rarely trees.

Composition — holding a dependency behind an interface and injecting it — keeps the coupling at the contract, is swappable at run time, and is testable. This is why modern C# codebases are wide and shallow: many small types, few base classes, and interfaces at every boundary.

the same requirement, both ways
// ✗ Inheritance: what happens when an order is BOTH discounted and urgent?
class Order { }
class DiscountedOrder : Order { }
class UrgentOrder : Order { }
// class UrgentDiscountedOrder : ??? — the combinatorial explosion begins

// ✓ Composition: rules are a list, and the list can grow
public sealed class PriceCalculator(IEnumerable<IPricingRule> rules)
{
    public decimal Price(Order o) =>
        rules.Aggregate(o.Subtotal, (total, rule) => rule.Apply(o, total));
}

SOLID, in one screen

Five principles that mostly restate the paragraph above. Know what each letter stands for and be able to give one concrete example — that is all an interview at this level needs.

LetterPrincipleIn one sentence
SSingle Responsibility A class should have one reason to change. If you cannot name it without "and", split it.
OOpen/Closed Adding a new case should mean adding a class, not editing a switch in five files.
LLiskov Substitution Any subclass must be usable wherever the base is, without surprises. If an override throws NotSupportedException, the hierarchy is wrong.

DDependency Inversion Depend on abstractions. This is literally what the DI container in chapter 14 exists to do.
⚠ The classic Liskov example

Square : Rectangle. Mathematically obvious, and wrong: code that sets Width = 5; Height = 4; and expects an area of 20 gets 16 from a square. A square is a rectangle, but a mutable square is not a substitutable mutable rectangle. "Is a" in English is not "is a" in code.

Try it yourself

Take the Order class from the "not encapsulated" example above and, without looking back, rewrite it so that these three things become impossible, not merely discouraged:

  1. submitting an order with no lines;
  2. adding a line to an order that is already submitted;
  3. a Total that disagrees with the lines.

Then ask the harder question: how would you enforce them if Order had to be reconstructed by EF Core from the database? (Answer in chapter 12 — a private constructor and a backing field.)

Golden rules

  1. Encapsulation is measured by what callers cannot do. Fifteen public setters is not encapsulation.
  2. Never expose List<T>; expose IReadOnlyList<T> and keep the mutation methods.
  3. Interface = what it can do. Abstract class = what it is, when real code is shared.
  4. Put an interface at every boundary you might need to fake in a test.
  5. override replaces; new only hides, and produces objects that answer differently depending on the variable holding them. Avoid it.
  6. sealed by default. Design for inheritance deliberately or forbid it.
  7. Prefer composition. Inheritance is the tightest coupling C# has, and it is fixed at compile time.
  8. If an override throws NotSupportedException, you have violated Liskov and the hierarchy is wrong.
  9. Deep hierarchies are a smell. Wide and shallow, with interfaces at the seams, ages better.

Interview questions

"What are the four pillars of OOP?"

Name them, then immediately give one concrete consequence each — the interviewer has heard the list a hundred times and is listening for whether anything follows it. Finish with the honest remark that inheritance is the one you use least.

"Abstract class or interface?"

Interface for a capability and for anything you need to substitute in tests; abstract class when several types share real implementation and state. Then mention that C# allows only one base class but many interfaces, which often settles it on its own.

"What does virtual do, and how is new different?"

virtual enables runtime dispatch on the object’s actual type; override participates in it. new hides the member instead, so the method called depends on the compile-time type of the variable. Offer the three-line demonstration — it is far more convincing than the definition.

"Why prefer composition over inheritance?"

Inheritance couples you to a base implementation permanently and at compile time; composition couples you to a contract, swappable at run time and fakeable in tests. Add the combinatorial argument: two independent variations already need four classes with inheritance, and two injected rules with composition.

"Give me an example of the Single Responsibility Principle from your own code."

Have one ready. The usual honest answer is a controller that was doing validation, mapping, business rules and persistence, split into a request model, a handler and a repository. Being able to describe the before is what makes it credible.
