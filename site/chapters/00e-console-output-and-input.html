Output and input at the console

Chapter 00a got one line onto the screen and one line back off the keyboard. That is enough to run a program and not nearly enough to write one. This chapter is everything else the console does: formatting a number so it lines up, reading a quantity that might not be a number, a menu loop that cannot be broken by a stray Enter key, and the arguments a program is given before it starts.

Why this chapter exists

Almost nothing you build for a living has a console front end — it will be an API, a web page or a service. But every one of those is debugged through a console, every utility and migration script you write is a console app, and every technical test you sit asks for one. More importantly, this is where input validation is learned. The loop that refuses to accept "twelve" as a quantity is the same loop, structurally, as the model validation on a controller — and a developer who never wrote the console version tends to write the web version by trusting the input.

Writing: the three calls, and the one that is not a call

🧒 Simple

There are only two ways to put text on the screen: one that moves to a new line afterwards and one that does not. Everything else on this page is about making the text itself look right before you hand it over. 

Console.WriteLine("Order dispatched.");   // writes, then moves to a new line
Console.Write("Quantity: ");              // writes, and the cursor STAYS on this line
Console.Error.WriteLine("Bin not found"); // goes to the error stream, not the output stream

int picked = 37, total = 40;
Console.WriteLine($"Picked {picked} of {total}");          // interpolation — the normal way
Console.WriteLine("Picked {0} of {1}", picked, total);     // composite — the old way
Console.WriteLine("Picked " + picked + " of " + total);    // concatenation — avoid
Line by line
  • Write versus WriteLine — the only difference is the newline at the end. Write is what you want immediately before a ReadLine, so the prompt and the answer sit on the same line, which is how every command-line tool you have ever used behaves.
  • Console.Error — a separate stream. It matters the moment somebody redirects your program's output to a file: with myapp > out.txt the normal output goes into the file and the errors still appear on screen, which is exactly what you want. Write diagnostics there, results to Console.Out.
  • $"…" — string interpolation. The $ in front lets you put an expression inside braces, and the compiler turns the whole thing into an efficient formatted write. This is the default choice.
  • "{0} of {1}" — composite formatting, the pre-2015 way. You will still meet it constantly, because logging APIs deliberately kept it: a logger wants the template and the values separately so it can index them. That is the one place you should still write it.
  • Concatenation with + works and reads badly, and inside a loop it is genuinely slow — see chapter 02g on why every + makes a whole new string.
One Console.WriteLine you should never ship

Using the console to trace what a web application is doing works on your machine and disappears in production, where nothing is attached to that stream and nobody can filter it. Real applications log through ILogger, which adds a level, a timestamp, a category and structured fields a search engine can query. That is chapter 25. Console output is for console programs.

Making the output line up

A list of orders printed with plain interpolation is unreadable the moment one order id is longer than another. The alignment syntax inside interpolation fixes it with no helper methods at all. 

Console.WriteLine($"{"SKU",-12}{"Qty",6}{"Weight",10}");
Console.WriteLine(new string('-', 28));

foreach (var line in order.Lines)
    Console.WriteLine($"{line.Sku,-12}{line.Qty,6}{line.WeightKg,10:N2}");

// SKU              Qty    Weight
// ----------------------------
// MI-42-BLUE        12     18.40
// BO-7               3      4.05
Line by line
  • {value,-12} — the number after the comma is an alignment width. Negative means left-aligned (pad on the right), positive means right-aligned. Text reads best left-aligned and numbers read best right-aligned, which is why the columns above are mixed.
  • {line.WeightKg,10:N2} — alignment and format together, in that order: comma first, then colon. Getting the order backwards is a compile error rather than a bug, mercifully.
  • new string('-', 28) — a constructor that repeats one character. It is the tidiest way to draw a rule, and it works for any character.
  • The width is a minimum, not a maximum. A value longer than the field pushes the rest of the row out rather than being cut off, so choose widths from the longest value you can actually have — or truncate deliberately with Substring.
  • Every format string here is the same one used by ToString and by ILogger, so learning them once pays three times. Chapter 02f has the numeric table.

Reading: everything the user types is a string

🧒 Simple

The keyboard only ever gives you text. If you asked for a quantity and the person typed 12, what arrives is the two characters "1" and "2", not the number twelve. Turning that text into a number is your job, and so is deciding what happens when they typed "twelve", or nothing at all. 

Console.Write("Quantity: ");
string? input = Console.ReadLine();       // string? — it CAN be null

if (int.TryParse(input, out int qty))
{
    Console.WriteLine($"Reserving {qty}.");
}
else
{
    Console.WriteLine("That is not a whole number.");
}

// ✗ what beginners write, and what it does to the program
int bad = int.Parse(Console.ReadLine()!);   // FormatException on "twelve"
                                            // NullReferenceException on Ctrl+Z
Line by line
  • string? — ReadLine returns null at end of input, not an empty string. That happens on Ctrl+Z (Windows) or Ctrl+D (Linux), and whenever the program's input is a file that has run out. Empty string means "they pressed Enter"; null means "there is no more input, ever" — two different situations that deserve two different responses.
  • int.TryParse — the Try… pattern: it returns a bool for whether it worked and hands the value back through out. It is the right tool whenever failure is expected, and a human typing is the definition of expected failure.
  • out int qty — declared right there in the argument list, and still in scope after the if. When parsing fails, qty is set to 0, never left undefined — which is itself a trap, because 0 looks like a real answer.
  • int.Parse — throws on anything unparseable. It is correct for input you control, like a constant or a value you have already validated, and wrong for input a person typed. Chapter 02l is the general rule: exceptions are for the exceptional, and a typo is not exceptional.
  • The ! on ReadLine()! is the null-forgiving operator — it silences the compiler's warning without making the value any less null. Writing it to make a warning go away is how the NullReferenceException in that last line got shipped.
⚠️ Parsing a decimal typed by an Italian user

decimal.Parse("1,5") succeeds under it-IT and gives 1.5; under en-US it gives 15, because a comma is the thousands separator there. The same program, the same keystrokes, two answers, and no error either time. Decide deliberately: for text a human typed, parse with CultureInfo.CurrentCulture (the default) and make sure the server's culture is set; for text from a file or an API, always pass CultureInfo.InvariantCulture.

The validation loop, which is the whole point

This is the shape worth memorising. It appears in every console program, and the same three parts — prompt, parse, range check — appear in every web form and every API endpoint you will ever write. 

int ReadQuantity(int max)
{
    while (true)                               // loop until we get a good answer
    {
        Console.Write($"Quantity (1-{max}): ");
        string? line = Console.ReadLine();

        if (line is null)                      // end of input — no point asking again
            throw new OperationCanceledException("Input ended.");

        if (!int.TryParse(line.Trim(), out int qty))
        {
            Console.Error.WriteLine("  Whole numbers only.");
            continue;                          // ask again
        }

        if (qty < 1 || qty > max)
        {
            Console.Error.WriteLine($"  Must be between 1 and {max}.");
            continue;
        }

        return qty;                            // the ONLY way out with a value
    }
}
Line by line
  • while (true) with a return inside — deliberately. The alternative, a flag variable tested by the while, needs the answer to exist before it is valid, which means declaring it with a fake value. One exit point that returns the real answer is clearer than two.
  • line.Trim() — a trailing space is the single most common reason a perfectly typed number fails to parse. Trim before you parse, always.
  • continue — abandons this pass and goes back to the prompt. Compare it with break, which would leave the loop entirely and fall out of the method with no answer.
  • The null check comes first and does not loop. Re-prompting when there is no more input is an infinite loop that prints the prompt forever — a real bug, and one that only shows up when the program's input is redirected from a file.
  • Error messages go to Console.Error, so a user redirecting the results to a file still sees why their input was rejected.
The same loop, three layers up

In a web API there is no loop, because the browser is the loop — but the three steps survive exactly: model binding does the parse (and gives you a 400 when it fails), a validation attribute does the range check, and the response tells the caller which field was wrong. When chapter 14 describes [ApiController] automatically returning a 400 for a bad model, it is describing this method with the prompting removed.

Menus, keys and clearing

while (true)
{
    Console.WriteLine();
    Console.WriteLine("1) Pick list   2) Dispatch   3) Stock count   Q) Quit");
    Console.Write("> ");

    ConsoleKeyInfo key = Console.ReadKey(intercept: true);   // no Enter needed
    Console.WriteLine();

    switch (char.ToUpperInvariant(key.KeyChar))
    {
        case '1': ShowPickList();  break;
        case '2': Dispatch();      break;
        case '3': StockCount();    break;
        case 'Q': return;
        default:  Console.Error.WriteLine("Unknown option."); break;
    }
}
Line by line
  • Console.ReadKey — returns as soon as one key is pressed, without waiting for Enter. intercept: true stops the character being echoed, which is what you want for a menu (and what you must have for a password).
  • A named argument on intercept: true. A bare Console.ReadKey(true) is legal and tells a reader nothing — the same point chapter 02e makes about booleans at call sites.
  • char.ToUpperInvariant — so q and Q both quit. The invariant version matters more than it looks: in Turkish, upper-casing i does not give I, and menu code that used the culture-aware version has genuinely failed on Turkish machines. For comparisons, always invariant.
  • default: — every switch over user input needs one. Chapter 00c covers the statement; chapter 02 covers the expression form, which forces you to handle it.
  • Console.Clear() exists and throws an IOException when output is redirected. Guard it with if (!Console.IsOutputRedirected) or leave it out.

Arguments: input the program gets before it starts

Every console program is also a tool somebody will want to run from a script, unattended, with no one there to answer a prompt. That is what arguments are for, and supporting them is about six lines. 

// Program.cs, top-level statements: args is already in scope
if (args.Length == 0)
{
    Console.Error.WriteLine("usage: dispatch <order-id> [--dry-run]");
    return 2;                                   // a non-zero exit code means failure
}

string orderId = args[0];
bool dryRun = args.Contains("--dry-run");

if (!Guid.TryParse(orderId, out Guid id))
{
    Console.Error.WriteLine($"Not a valid order id: {orderId}");
    return 1;
}

Dispatch(id, dryRun);
return 0;                                       // success
Line by line
  • args — a string[] the runtime fills in from the command line. With top-level statements it simply exists; in the older static void Main(string[] args) form it is the parameter. It never contains the program's own name — that is a C and C++ convention C# does not follow — so args[0] is the first real argument.
  • The exit code is the return value of the program. Zero means success and anything else means failure, and that is the only thing a build server, a scheduled task or a shell script looks at. A program that prints "ERROR" and returns 0 will be treated as having worked.
  • args.Contains("--dry-run") — fine for one flag. Past two or three, use a real parser (System.CommandLine) rather than growing this by hand; the edge cases — combined flags, --key=value, quoting — are not worth reimplementing.
  • Never put a secret in an argument. The full command line of every running process is visible to other users on the machine and lands in shell history. Passwords and API keys come from environment variables or a secret store, which is chapter 15.
  • Guid.TryParse — the same Try… pattern, on a different type. Almost every parseable type in .NET has one.

Exercises, with the reasoning shown

Exercise 1 — the prompt on its own line

Console.WriteLine("Quantity: ");
string? qty = Console.ReadLine();
The user types their answer on the line below the prompt.
  • Not a crash, just an interface that looks broken. WriteLine moved the cursor down before the user got to type. Use Console.Write for a prompt — every time, without exception.

Exercise 2 — the quantity that became zero

int.TryParse(Console.ReadLine(), out int qty);
Reserve(sku, qty);
Typing "twelve" reserves zero units, silently.
  • TryParse did its job perfectly — it returned false — and the code ignored the return value. On failure the out parameter is set to default, which for int is 0: a value that looks entirely legitimate to everything downstream. Calling TryParse without using its result is strictly worse than calling Parse, because at least Parse would have told somebody.

Exercise 3 — the loop that printed forever

while (true)
{
    Console.Write("Name: ");
    string? name = Console.ReadLine();
    if (name == "") break;
    Greet(name);
}
Run it with its input redirected from a file and it prints the prompt forever.
  • At end of input ReadLine returns null, not "", so the break never fires and every subsequent call returns null immediately — a loop with nothing to slow it down. The test must be if (string.IsNullOrEmpty(name)) break;, or better, two branches: null means the input ended and empty means the user just pressed Enter.

Exercise 4 — the report that worked in testing

Console.WriteLine($"{sku,-10}{qty,5}");
// sku = "MI-42-BLUE-XL-2024", qty = 3
The columns stop lining up.
  • The width is a minimum, not a maximum: an 18-character SKU occupies 18 characters and shoves the quantity column to the right for that row only. If the field must be exactly ten, truncate it yourself — sku.Length <= 10 ? sku : sku[..9] + "…" — and choose the ellipsis deliberately, so a reader knows something was cut rather than believing a wrong SKU.
Try it yourself

A complete miniature of everything on this page: a prompt that stays on its line, a parse that cannot crash, a range check, a formatted table, and an exit code. It is about thirty lines and it is the skeleton of every console tool you will write. 

var lines = new List<(string Sku, int Qty)>();

  while (true)
  {
      Console.Write("SKU (blank to finish): ");
      string? sku = Console.ReadLine();
      if (sku is null || sku.Trim().Length == 0) break;

      Console.Write("  Quantity: ");
      if (!int.TryParse(Console.ReadLine()?.Trim(), out int qty) || qty < 1)
      {
          Console.Error.WriteLine("  Ignored — quantity must be a whole number above zero.");
          continue;
      }

      lines.Add((sku.Trim().ToUpperInvariant(), qty));
  }

  if (lines.Count == 0)
  {
      Console.Error.WriteLine("Nothing to dispatch.");
      return 1;
  }

  Console.WriteLine();
  Console.WriteLine($"{"SKU",-20}{"Qty",6}");
  Console.WriteLine(new string('-', 26));
  foreach (var (sku, qty) in lines)
      Console.WriteLine($"{sku,-20}{qty,6}");
  Console.WriteLine(new string('-', 26));
  Console.WriteLine($"{"TOTAL",-20}{lines.Sum(l => l.Qty),6}");
  return 0;
What each guard in it is for
  • sku is null || sku.Trim().Length == 0 — the two end conditions in one test: no more input at all, and the blank line that means "I have finished". Both stop the loop, and neither is an error.
  • Console.ReadLine()?.Trim() — the null-conditional, so a null at end of input reaches TryParse as null rather than throwing on Trim. TryParse returns false for null quite happily.
  • || qty < 1 — the range check, sharing the branch with the parse failure because the user needs the same message either way.
  • continue after an error, not break — one bad line should cost the line, not the whole session.
  • lines.Sum(l => l.Qty) in the last row and return 1 on the empty case — the total is computed rather than accumulated, and the exit code tells a script whether anything was dispatched.

Then try three things that break naive versions of it: type a quantity of abc, press Enter on the SKU straight away, and run the program with its input coming from a file (dotnet run < orders.txt). All three are handled above. Remove one guard at a time and watch which one each failure needed.

Golden rules

  1. Console.Write for a prompt, WriteLine for a result. A prompt that ends with a newline makes the program look broken before it has done anything wrong.
  2. Everything the user types is a string. Converting it is your job, and so is deciding what happens when it cannot be converted.
  3. TryParse for anything a human typed; Parse only for input you control. A typo is expected, and expected failure is a return value, not an exception.
  4. Never ignore what TryParse returned. On failure it writes default into the out variable — 0 for a number — which is indistinguishable downstream from a real answer.
  5. ReadLine returns null at end of input, and "" when the user pressed Enter. Treating them as the same thing is how a prompt loop runs forever under redirected input.
  6. Trim() before you parse. A trailing space is the most common reason a correctly typed number is rejected.
  7. Diagnostics go to Console.Error, results to Console.Out. It costs nothing and it is what makes a program usable inside a script.
  8. Alignment is {value,-10} and format is {value:N2}, comma before colon. The width is a minimum, so choose it from the longest value that can really occur.
  9. The return value of the program is its exit code: zero is success. A build server reads nothing else, so printing an error and returning 0 means the failure is invisible.
  10. Never pass a secret as a command-line argument. Command lines are visible to other processes and land in shell history.
  11. Use Console.WriteLine for console programs, ILogger for everything else. Console output in a hosted application goes nowhere anybody can search.

Interview questions

"What is the difference between Parse and TryParse?"

Parse returns the value and throws — FormatException for bad text, ArgumentNullException for null, OverflowException for out of range. TryParse returns a bool and hands the value back through an out parameter, setting it to default on failure. The choice is about whether failure is expected: for a value a person typed or a line from an imported file it is entirely expected, so TryParse; for a constant or a value already validated upstream, Parse is right, because a failure there is a bug and I want the exception. The thing to watch is that ignoring TryParse's return value is worse than using Parse, since a silent zero propagates.

"Console.ReadLine returns string?. When is it null?"

At end of input — Ctrl+Z on Windows, Ctrl+D on Unix, or simply the end of a file when the program's input has been redirected. It is not the same as the user pressing Enter, which gives an empty string. The distinction matters in a prompt loop: if you test for "" only, then under redirected input the loop never terminates and spins at full speed printing the prompt. I test null separately and treat it as "there will never be any more input", which usually means stop rather than ask again.

"How would you validate a numeric input from a user?"

A loop with three steps: prompt with Write, Trim and TryParse, then a range check — and a separate check for null input, which exits rather than re-prompting. Each failure prints to Console.Error and continues; the only way out with a value is the return. It is worth saying that this is the same structure as validation in a web API, just with the prompting removed: model binding is the parse, a validation attribute is the range check, and the 400 response is the error message.

"Why should a console program set an exit code?"

Because it is the only thing an automated caller can see. A shell script, a scheduled task, a CI step or a Docker health check all branch on the process's exit code and none of them read your output. Zero means success, non-zero means failure, and it is conventional to use distinct non-zero values for distinct failures — usage error versus not-found versus a genuine fault — so that a script can react differently. A program that prints an error and returns zero is treated by the build server as having succeeded, which is how a broken deployment goes green.

"Come leggeresti un numero decimale scritto da un utente italiano?"

Con attenzione alla cultura, perché decimal.Parse("1,5") dà 1,5 con it-IT e 15 con en-US — nessuna eccezione, due risultati diversi. Per un valore digitato da una persona uso la cultura corrente e mi assicuro che il server sia configurato con quella giusta; per un valore che arriva da un file, da un'API o da un log uso sempre CultureInfo.InvariantCulture, sia in lettura sia in scrittura. La regola che tengo a mente è: cultura reale per gli umani, invariante per le macchine.
