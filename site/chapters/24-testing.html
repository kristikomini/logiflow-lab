Testing

Tests are not about proving your code works today. They are about being able to change it in eight months without fear, and about the reviewer being able to see what you intended. This chapter is xUnit, test doubles, integration tests against a real database, and — just as important — what not to test.

Why this chapter exists

"Test unitari", xUnit and NUnit are on a large share of .NET adverts in the region, usually under "gradita conoscenza di". But the real reason is blunter: the most common silent rejection for a junior take-home exercise is a correct solution submitted with no tests. Nobody writes back to explain that. Four good tests would have changed the outcome.

What a test is for

🧒 Simple

You build a tower of blocks. Every time you add one, you give the table a little shake to check nothing falls. The shake is the test.

Now imagine the tower has 400 blocks and your friend adds one while you are at lunch. Without the shake, the only way to know it is still standing is to look at all 400. With the shake, you find out in one second — and you find out which block moved.

🎓 Professional

Three things a good test suite gives you, in order of value:

  • Confidence to change. The cost of a codebase is not writing it, it is modifying it later. Tests are what make refactoring an ordinary Tuesday instead of a gamble.
  • Executable specification. A test named Submit_fails_when_the_order_has_no_lines tells a new joiner a business rule that no comment would have survived to state.
  • Design pressure. Code that is hard to test is usually badly coupled. If you need six mocks to construct one class, the test has told you something true about the class.

Your first xUnit test

arrange, act, assert
public sealed class OrderTests
{
    [Fact]
    public void Submit_fails_when_the_order_has_no_lines()
    {
        // Arrange — build the world
        Order order = Order.Create(ACustomer(), OrderNumber.Create(2026, 1).Value).Value;

        // Act — do the one thing under test
        Result result = order.Submit();

        // Assert — state one expectation
        result.IsFailure.ShouldBeTrue();
        result.Error.ShouldBe(OrderErrors.CannotSubmitEmptyOrder);
    }

    [Theory]                       // same test, several inputs
    [InlineData(0)]
    [InlineData(-1)]
    [InlineData(-100)]
    public void A_line_quantity_must_be_positive(int quantity)
    {
        var result = OrderLine.Create(AProduct(), quantity);
        result.IsFailure.ShouldBeTrue();
    }
}
Line by line
  • [Fact] — xUnit's attribute for a test with no parameters. The parameterised sibling is [Theory] with [InlineData].
  • Submit_fails_when_the_order_has_no_lines — the name is documentation. Underscores because it is a sentence, and it should read as the rule being asserted. A failing test's name is the first thing anyone sees.
  • Arrange, Act, Assert — and the blank lines between them are deliberate. Two acts in one test means two tests.
  • Order.Create(...).Value — the factory returns a Result<T>, so .Value unwraps it. Fine in a test where failure would itself be a bug.
  • ACustomer() — a builder helper. It keeps irrelevant setup out of the test so only the detail that matters is visible.
  • result.IsFailure.ShouldBeTrue() — one expectation. Asserting five things means the first failure hides the other four.
  • This is a unit test in the true sense: no database, no container, no mock. The domain has no dependencies, which is exactly what chapter 23's layering bought.

xUnit creates a new instance of the test class for every test. That is not trivia — it is why xUnit tests do not leak state into each other, and it is a good interview answer to "why xUnit rather than NUnit?"

Test doubles: mock what you cannot control

🧒 Simple

When actors rehearse a scene with a bicycle, they do not bring a real bicycle. They use a cardboard one. It is the right shape, it stands where the bicycle stands, and it never gets a puncture halfway through.

But they use a real script. You never fake the thing the rehearsal is actually about.

🎓 Professional

The vocabulary interviewers use loosely, and you should not:

  • Stub — returns canned answers. Used for input.
  • Mock — a stub you also make assertions about. Used for output ("the e-mail was sent").
  • Fake — a real, working, simplified implementation. An in-memory repository backed by a Dictionary.
  • Spy — records calls for inspection afterwards.

The rule that matters more than the vocabulary: mock what you cannot control, use the real thing for what you own. Databases, clocks, HTTP calls, message brokers, random-number generators — fake those. Your own entities and value objects — never.

a handler test — I/O substituted, domain real
public sealed class CreateOrderHandlerTests
{
    // This repository uses NSubstitute. Moq is the other common one
    // and the concepts map one-to-one: Mock<T>.Object ≈ Substitute.For<T>().
    private readonly ICustomerRepository _customers = Substitute.For<ICustomerRepository>();
    private readonly IOrderRepository    _orders    = Substitute.For<IOrderRepository>();

    [Fact]
    public async Task Fails_when_the_customer_is_inactive()
    {
        // A REAL Customer, deactivated. Not a mocked one —
        // the rule under test lives inside this object.
        Customer customer = ACustomer(active: false);
        _customers.GetByIdAsync(customer.Id, Arg.Any<CancellationToken>())
                  .Returns(customer);

        var result = await _handler.HandleAsync(ACommandFor(customer), default);

        result.Error.ShouldBe(OrderErrors.CustomerInactive);
        await _orders.DidNotReceive().AddAsync(Arg.Any<Order>(), Arg.Any<CancellationToken>());
        //        ↑ asserting the absence of a side effect is often the real test
    }
}
Line by line
  • Substitute.For<ICustomerRepository>() — a test double from NSubstitute. Moq is the other common choice and the concepts map one to one.
  • You can only substitute an interface, which is why the handler depends on one. Testability is a consequence of the dependency rule, not a separate goal.
  • private readonly fields — xUnit creates a new instance of the test class per test, so these are fresh every time. No shared state, no ordering dependencies.
  • Stub what the code needs; verify only what matters. Asserting that every method was called with exact arguments produces a test that fails on every refactor while catching no bugs.
  • Mock at the boundary, never the internals. A test that substitutes your own domain objects is testing the mocking framework.
⚠ Mocking your own domain

Substitute.For<Order>() and then asserting order.Received().Submit() tests that your handler called the method you expected it to call. It will pass forever, even when Submit() is completely broken, because the real one never ran. You have tested your own memory of the design, not the behaviour.

Same family of mistake: asserting the exact order of calls, or the exact number. Those tests break on every harmless refactor, everyone learns to "just update the test", and the suite stops meaning anything.

Integration tests, and the in-memory trap

the real application, a throwaway database
public sealed class LogiFlowApiFactory : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly MsSqlContainer _sql = new MsSqlBuilder().Build();

    public Task InitializeAsync() => _sql.StartAsync();   // a real SQL Server, ~10s once

    protected override void ConfigureWebHost(IWebHostBuilder builder) =>
        builder.ConfigureAppConfiguration(c => c.AddInMemoryCollection(
            new Dictionary<string, string?>
            {
                ["ConnectionStrings:Default"] = _sql.GetConnectionString()
            }));
    // Everything else is production: the same Program.cs, the same DI,
    // the same middleware, the same endpoints. Only the connection string moves.
}
Line by line
  • WebApplicationFactory<Program> — boots the real application in memory: the real pipeline, the real DI container, the real middleware. The generic argument is why Program must be reachable, which is what InternalsVisibleTo or a public partial class Program is for.
  • MsSqlContainer — Testcontainers. A real SQL Server in Docker, started for the test run.
  • This is the point of the chapter. The EF Core in-memory provider is not a database: no constraints, no transactions, no SQL translation. A test against it passes for queries SQL Server rejects, which is worse than no test.
  • IAsyncLifetime — xUnit's async setup and teardown. InitializeAsync starts the container.
  • ~10 seconds, once — shared across the whole test class or collection. Per-test would be unusable; per-run is a price worth paying.
  • AddInMemoryCollection — overrides configuration so the application points at the container's connection string instead of the developer's local server.
⚠ UseInMemoryDatabase is not a database

It is a LINQ-to-Objects shim in a DbContext costume. It has no schema, so it accepts a 500-character string in an nvarchar(20) column. It has no constraints, so unique indexes and CHECK constraints silently do nothing. It cannot do real transactions, raw SQL, or rowversion concurrency — all of which are in chapter 11 and chapter 12 precisely because they matter.

Every one of those gaps is a place where the tests pass and production fails. Microsoft's own documentation now advises against it. Testcontainers starts the genuine article in seconds, and a passing integration test then means something.

What not to test

  • Framework code. You are not testing that EF Core can save a row or that ASP.NET Core can bind JSON. Microsoft has those tests.
  • Getters and setters. A test that Name returns what you set is a test of the C# compiler.
  • Private methods. If a private method needs its own test, it wants to be a public method on its own class. Making it internal plus InternalsVisibleTo just to reach it is a smell.
  • Everything, to reach a coverage number. Coverage measures which lines ran, not whether anything was verified. 100% coverage with no assertions is achievable and worthless. Use it to find untested areas, never as a target.

The counterweight: every bug you fix gets a test first. That one is not negotiable, and it is a strong thing to say in an interview — it turns a bug into permanent knowledge instead of a fix somebody undoes later.

Try it yourself
dotnet test                                         # everything
dotnet test tests/LogiFlow.Domain.Tests             # fast, no Docker
dotnet test --filter "FullyQualifiedName~Order"    # just the order tests
dotnet test --collect:"XPlat Code Coverage"        # coverlet
Line by line
  • dotnet test — every test project in the solution.
  • dotnet test tests/LogiFlow.Domain.Tests — fast, and no Docker. This is the one to run on every save; the integration suite is for before a push.
  • --filter "FullyQualifiedName~Order" — ~ means contains. Other operators are = and !=, and Category works with [Trait].
  • --collect:"XPlat Code Coverage" — coverlet, producing a Cobertura file that a tool such as ReportGenerator turns into HTML.
  • Coverage measures what ran, not what was checked. A test with no assertions scores the same as a good one, which is why a coverage target becomes a number people game rather than a quality signal. Use it to find code nothing touches.

Then do the exercise that teaches the most: open src/LogiFlow.Domain, break one business rule on purpose — invert a comparison, delete a guard clause — and run the domain tests. Watch which test names go red. A good suite tells you what you broke, not just that you broke something. If the failing test name does not explain the bug, the name is wrong.

Golden rules

  1. Test names are sentences: Submit_fails_when_the_order_has_no_lines.
  2. Arrange, Act, Assert — and one Act per test.
  3. Mock what you cannot control. Never mock your own domain objects.
  4. Assert on outcomes and state, not on which methods were called in which order.
  5. [Theory] with [InlineData] instead of five copy-pasted tests.
  6. Many domain tests, some handler tests, a few integration tests. Watch the shape.
  7. Integration tests use a real database. UseInMemoryDatabase is not one.
  8. A test that needs a comment to explain it needs a better name.
  9. Never test private methods; test the behaviour that reaches them.
  10. Coverage is a diagnostic, never a target.
  11. Every bug gets a failing test before it gets a fix.
  12. A flaky test is worse than no test — quarantine or fix it the day it appears.

Interview questions

"Che differenza c'è fra unit test e integration test?"

A unit test exercises one unit in isolation with its I/O substituted and runs in milliseconds; an integration test exercises real components together — real HTTP, real database — and runs in seconds. Then add the reason the distinction is worth having: speed determines how often the suite gets run, and a suite nobody runs protects nobody.

"What do you mock, and what do you not?"

Mock what you cannot control: databases, clocks, HTTP, brokers. Use the real thing for what you own. Then give the failure mode, because it shows you have made the mistake: mocking your own aggregate produces a test that asserts you called the method you meant to call, and it passes happily while the business rule is broken.

"Do you use the EF Core in-memory provider for tests?"

No, and be specific about why: no schema, no constraints, no real transactions, no rowversion. It passes on data a real database would reject. Testcontainers gives a real SQL Server in seconds, which is what this repository does. Microsoft advises against the in-memory provider for the same reasons.

"What code coverage do you aim for?"

A number is the wrong answer to this question and they usually know it. Say that coverage shows which lines executed, not whether anything was asserted, so it is useful for finding blind spots and destructive as a target — teams asked to hit 90% write tests with no assertions. What you do commit to is that the domain rules are covered and every fixed bug has a test.

"Do you practise TDD?"

Answer honestly rather than aspirationally; interviewers can tell. A good honest version: not strictly for everything, but always for bug fixes — reproduce with a failing test first — and usually for anything with awkward branching, because writing the test first is what shows the API is awkward before you have built anything on top of it.
