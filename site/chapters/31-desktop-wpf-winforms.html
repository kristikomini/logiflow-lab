The desktop that pays the bills

The largest single body of C# in Emilia-Romagna is not on the web. It is a WinForms application from 2009 that runs a warehouse, and a WPF supervisor screen bolted to a machine in Sassuolo. Somebody has to keep those alive and move them forward — and quite often that somebody is the junior who just started.

Why this chapter exists

There are consistently twenty-five or more live WPF listings in Italy, and most gestionale and industrial adverts that say only "sviluppatore C# .NET" mean a desktop client. No bootcamp teaches this, because courses teach the web — so the ratio of open roles to prepared candidates is unusually good. It is also, bluntly, the most likely shape of a first job here: maintaining something you did not write.

Why desktop did not die

🧒 Simple

Your grandfather has a drill from 1985. It is heavy, it is ugly, and it makes holes perfectly. Buying a new one would cost money and it would still just make holes.

But there is more to it: his drill plugs straight into the wall. The shiny new one needs Wi‑Fi and an app, and in his workshop there is no Wi‑Fi. Sometimes the old thing is not just cheaper — it is the only one that works where the work is.

🎓 Professional

Everyone's first instinct is "why is this not a web app?" There are real answers, and knowing them is what separates a useful opinion from an eye-roll:

  • Hardware. Serial ports, industrial scales, label printers with raw ZPL, barcode guns, cameras, PLC driver DLLs. A browser sandbox exists precisely to stop pages doing this.
  • The network. The OT network from the next chapter often has no internet at all, and the application must keep working when the server does not.
  • Latency and density. An operator entering four hundred rows a shift wants keyboard-only, zero-lag data entry. A round trip per keystroke is not acceptable.
  • Sunk value. Fifteen years of business rules, most of them undocumented, several of them the only reason the company is compliant with something.

So the honest position — and a good one to hold in an interview — is that the desktop application is usually not a mistake to be corrected. It is an asset to be maintained, and selectively moved.

the same screen, two philosophies
// WinForms — push. The form reaches into controls and sets values.
private void LoadOrders()
{
    var orders = _service.GetOrders();        // (blocking — see below)
    dataGridView1.DataSource = orders;
    lblTotal.Text = orders.Sum(o => o.Total).ToString("C");
    btnSubmit.Enabled = orders.Count > 0;      // and you must remember to
}                                              // do this again on EVERY change


// WPF — bind. The view describes what it wants; the data pushes itself.
<DataGrid ItemsSource="{Binding Orders}" />
<TextBlock Text="{Binding Total, StringFormat=C}" />
<Button Content="Invia" Command="{Binding SubmitCommand}" />
// Enabled/disabled comes from the command's CanExecute. Nothing to remember.
Line by line
  • WinForms is "push": the form reaches into controls and sets their values. Every line here is an instruction to a widget.
  • dataGridView1 — the designer-generated name, and its survival into real code is characteristic. The form and the UI are one class.
  • .DataSource = orders — a plain List<T> here means the grid never updates again. Only a BindingList<T> raises the change notifications the grid listens for.
  • ToString("C") — culture-sensitive currency, correct for a human reading a screen in Italy.
  • btnSubmit.Enabled = orders.Count > 0 — and you must remember to do this everywhere. Every other method that changes the list must repeat it, and the one that forgets leaves a button enabled over an empty grid.
  • That repetition is the argument for MVVM. Not elegance: the bug is a rule expressed in five places instead of one.
  • _service.GetOrders() — blocking, and the next block is about why that freezes the window.

That is the whole difference, and it is why WPF leads to MVVM and WinForms tends not to. Once the view only describes what it wants, the thing supplying it does not need a screen to exist — which means it can be tested.

MVVM, the pattern they will ask about

🧒 Simple

A puppet show. The puppet is what the audience sees. The puppeteer decides what it does. The story is what actually happens.

The clever part is that the puppeteer never touches the audience and the puppet has no opinions. You can swap the puppet for a bigger one, or rehearse the puppeteer with no puppet at all — which is exactly how you test it.

🎓 Professional
  • Model — the domain and the data. Knows nothing about screens.
  • View — XAML. Layout and binding expressions, ideally no code-behind.
  • ViewModel — the state of this screen and the commands it offers. Knows nothing about WPF controls, which is precisely what makes it testable with chapter 24's tools and no UI at all.

Two interfaces carry it. INotifyPropertyChanged tells the binding a property changed; ICommand gives a button both an action and a rule for when it is enabled. Writing those by hand is tedious, so nobody does any more:

a ViewModel with CommunityToolkit.Mvvm source generators
public partial class OrdersViewModel(IOrderService service) : ObservableObject
{
    [ObservableProperty]                // generates the Orders property
    private ObservableCollection<OrderDto> _orders = [];  // + PropertyChanged

    [ObservableProperty]
    [NotifyCanExecuteChangedFor(nameof(SubmitCommand))]   // re-evaluate the button
    private bool _isBusy;

    [RelayCommand]                     // generates LoadCommand
    private async Task LoadAsync(CancellationToken ct)
    {
        IsBusy = true;
        try
        {
            var result = await service.GetOrdersAsync(ct);   // off the UI thread
            Orders = new(result);                          // back on it, automatically
        }
        finally { IsBusy = false; }
    }

    [RelayCommand(CanExecute = nameof(CanSubmit))]
    private Task SubmitAsync() => service.SubmitAsync(Orders, default);

    private bool CanSubmit() => !IsBusy && Orders.Count > 0;
}
Line by line
  • : ObservableObject — from CommunityToolkit.Mvvm. It supplies INotifyPropertyChanged, the interface the entire binding system rests on.
  • partial — required, because a source generator writes the other half of this class at compile time.
  • [ObservableProperty] on _orders — generates a public Orders property that raises PropertyChanged on assignment. You write the field; the generator writes the ceremony.
  • ObservableCollection<T> — raises events on add and remove, which is a different notification from the property changing. A List<T> here binds once and never updates — the same trap as the previous block.
  • [NotifyCanExecuteChangedFor(nameof(SubmitCommand))] — this attribute is the answer to the WinForms repetition. Setting IsBusy re-evaluates the button's availability automatically, everywhere, forever. The rule is stated once.
  • nameof(...) — compile-time, so a rename cannot silently break the wiring.
  • [RelayCommand] — generates an ICommand from a method. Commands are how a view model exposes actions without referencing a button, which is what makes the class testable with no window at all.

Note what is not here: no Dispatcher, no button.Enabled = , no reference to a control. This class can be constructed in a unit test, have a fake IOrderService handed to it, and be asserted on — which is the entire argument for MVVM, and the answer to "why bother".

The UI thread, which explains most desktop bugs

the three ways it goes wrong, and the fixes
// ✗ 1. Blocking the UI thread. The window goes white and Windows says "Non risponde".
var orders = _service.GetOrdersAsync().Result;    // also deadlocks — chapter 07

// ✓ await it. The handler returns, the pump keeps turning, and the continuation
// comes back on the UI thread by itself because await captured the context.
private async void Button_Click(object s, RoutedEventArgs e)   // the ONE place
{                                                            // async void is correct
    try    { Orders = await _service.GetOrdersAsync(); }
    catch (Exception ex) { ShowError(ex); }   // unhandled here = process death
}

// ✗ 2. Touching a control from a background thread. Throws, or corrupts silently.
_timer.Elapsed += (s, e) => lblClock.Text = DateTime.Now.ToString();

// ✓ marshal back onto the UI thread
_timer.Elapsed += (s, e) => Dispatcher.InvokeAsync(
    () => Clock = DateTime.Now.ToString("T"));       // WinForms: Control.BeginInvoke

// ✗ 3. The leak nobody sees: a long-lived object holding a short-lived window alive.
_backgroundService.DataArrived += OnDataArrived;   // window closes… and never dies,
                                                   // because the service still holds it
// ✓ unsubscribe on close, or use a weak event.
Closed += (s, e) => _backgroundService.DataArrived -= OnDataArrived;
Line by line
  • .Result on the UI thread — the window goes white and Windows says "Non risponde". The message pump is the thread you just blocked, so nothing repaints and no input is processed.
  • It also deadlocks, for the reason in chapter 07: the continuation must run on the UI synchronization context, and that context is occupied by the thread waiting for it.
  • async void — and an event handler is the one legitimate use of it. Everywhere else it is a bug: an async void method cannot be awaited, and an exception inside it crashes the process rather than surfacing at a caller.
  • await in a handler — the handler returns immediately, the pump keeps turning, and the window stays responsive.
  • The continuation comes back on the UI thread by itself. The captured synchronization context — the same thing that causes the deadlock above — is here doing you a favour, which is why no Invoke or Dispatcher call is needed.
  • Wrap the body in try/catch regardless: with async void there is nowhere else for an exception to go.
⚠ Why the leak matters more here than on the web

A web request lives for 40 ms and then everything is garbage. A desktop process runs from 07:00 until the operator goes home, so a window leaked on every open is a process using 3 GB by the afternoon. Event handlers are the number one cause: the publisher holds a reference to the subscriber, so a form that subscribes to anything long-lived and never unsubscribes cannot be collected. The pair is the rule — every += gets a -=.

Modernising without a rewrite

🎓 Professional

Two separate jobs that people confuse. Retargeting is moving the same application from .NET Framework 4.8 to .NET 10 — both WinForms and WPF are fully supported there (Windows-only), and you get modern C#, a much faster runtime, and a supported platform. Modernising is changing the architecture. Do them in that order and never at the same time. 

dotnet tool install -g upgrade-assistant
upgrade-assistant upgrade MyApp.sln        # also a Visual Studio extension;
                                           # offers in-place or side-by-side
Line by line
  • -g — installs the tool globally rather than into a project.
  • upgrade-assistant upgrade MyApp.sln — and desktop is the best case for this tool. WinForms and WPF both exist on modern .NET, so unlike Web Forms there is a real target.
  • In-place or side-by-side — side-by-side keeps the old project building while you work, which makes the change reviewable instead of a cliff.
  • What actually blocks a desktop port: third-party control suites without a .NET 8+ build, anything using AppDomain, and WCF clients. The tool's analyse step names them.
  • The payoff is worth the effort: modern .NET, current C#, single-file publish, and the same SDK-style project as the rest of your solution.

It converts the project file, retargets, and flags incompatibilities. What it cannot fix, and what actually consumes the week: AppDomains, .NET Remoting, WCF clients (there is CoreWCF, but it is a port not a no-op), app.config becoming appsettings.json, ConfigurationManager, and third-party control suites — DevExpress, Telerik, Infragistics — whose modern versions need a current licence. That last one is a budget conversation, not a technical one, and it is often the real blocker.

⚠ Deployment, the part nobody warns you about

You are not deploying to one server. You are deploying to two hundred machines, some of which are switched off, one of which is a panel PC in a wet area running an image from 2016. ClickOnce (still supported on modern .NET) or MSIX give you versioning and auto-update; a copy to a shared folder gives you a support call in six months when half the plant is on the old version. Ask about this in the interview — the answer tells you a great deal about the team.

Try it yourself
dotnet new wpf -o DesktopDemo && cd DesktopDemo

Line by line
  • dotnet new wpf -o DesktopDemo — a WPF project on modern .NET, from the normal SDK. No Visual Studio required.
  • dotnet add package CommunityToolkit.Mvvm — the source generators from the second block. Small, official, and it removes most MVVM boilerplate.
  • dotnet run — Windows only, since WPF and WinForms are Windows technologies. That is the honest constraint of this whole chapter.
  • Then bind a control to a view-model property and change it in code. Watching the UI update with no code touching the control is the moment the pattern makes sense.

Then feel the bug rather than reading about it. In the button handler, first write:

Thread.Sleep(4000);              // drag the window while it runs
Line by line
  • Thread.Sleep(4000) — blocks the thread for four seconds. On a UI thread that is four seconds of no repainting and no input.
  • Drag the window while it runs. It will not move, the contents go white, and Windows offers to close it — the exact behaviour users report as "the program crashed".
  • This is chapter 07's abstract rule made physical, which is why it is worth ten seconds of your time.
await Task.Delay(4000);         // now drag it again
Line by line
  • await Task.Delay(4000) — a timer, not a sleep. No thread is held; a continuation is scheduled for when it fires.
  • Now drag it again — the window moves, redraws and responds throughout, and the code above and below the await is otherwise identical.
  • One keyword, and the difference between a frozen application and a responsive one. That is the whole lesson of async on a UI, and no explanation lands as hard as doing it twice.

The first freezes the window solid and Windows greys it out; the second leaves it perfectly draggable, and the code after it still runs on the UI thread and can set a label. Same four seconds of waiting, completely different application. Then bind a ListBox to an ObservableCollection on a ViewModel, add an item from a Task.Run, and watch it throw — that is the marshalling rule, learned the fastest possible way.

Golden rules

  1. There is one UI thread. Only it may touch a control.
  2. Never block it. No .Result, no .Wait(), no synchronous I/O.
  3. async void is correct for an event handler and wrong everywhere else — and it must catch its own exceptions.
  4. Anything from a background thread comes back via Dispatcher.InvokeAsync or Control.BeginInvoke.
  5. Every += needs a -=. In a process that runs all day, leaks are visible.
  6. WinForms pushes values into controls; WPF binds controls to data. That is the whole difference.
  7. MVVM exists so the screen's logic can be tested without a screen. If it is not testable, it is not MVVM.
  8. No business logic in code-behind or in a button handler. That is what blocks every future move.
  9. Retarget to .NET 10 first, then change architecture. Never both at once.
  10. Third-party control licences are usually the real migration blocker. Find out early.
  11. Migrate by strangler: extract the rules, put an API in front, replace screens one at a time.
  12. Know how the application reaches two hundred machines before you promise a release date.

Interview questions

"Che differenza c'è fra WinForms e WPF?"

Start with the concrete list — XAML versus designer code, DirectX versus GDI+, resolution independence, styles and templates. Then give the sentence that shows you have used both: in WinForms you push values into controls and must remember to do it again on every change; in WPF you bind, and that is what makes MVVM natural. Add that both are supported on .NET 10 and Windows-only, so neither is "dead".

"What is MVVM, and why not just put the code in the form?"

Model, View, ViewModel — with the ViewModel holding this screen's state and commands and knowing nothing about controls. The reason is testability: you can construct it with a fake service and assert on it with no UI at all. Mention INotifyPropertyChanged and ICommand as the mechanics, and CommunityToolkit.Mvvm generating both, so it does not sound theoretical.

"The application freezes for four seconds when the user clicks Load. Why?"

Something is blocking the UI thread — a synchronous query, or .Result on a task. The message pump stops, so nothing repaints and Windows shows "Non risponde". The fix is to await the work and let the continuation come back on the UI thread. This is the single most common desktop ticket, and answering it crisply is worth a lot.

"The process uses 3 GB by the afternoon. Where do you look first?"

Event handlers that were never unsubscribed — a long-lived service holding a reference to every window that was ever opened, so none can be collected. Say how you would confirm it rather than guess: take two memory snapshots an hour apart in the Visual Studio diagnostic tools or dotMemory and compare instance counts of the window type.

"We have a WinForms app on .NET Framework 4.8. What would you propose?"

Two phases, explicitly separated. First retarget to .NET 10 with the Upgrade Assistant, changing nothing else — and name what usually breaks: AppDomains, WCF, config, third-party control licences. Then, only after that ships, extract the business rules out of the form handlers into a library, put an API over it, and replace screens one at a time — with WebView2 as the option for hosting a new web screen inside the existing window. What earns the nod is refusing the big-bang rewrite and saying why.

"Would you rather work on something modern?"

A trap for the impatient, and they are usually asking because the job is 70% maintenance. The honest, strong answer: maintaining a system real people depend on teaches things greenfield work never does — reading unfamiliar code, changing it safely, and understanding a business. Then show ambition in the right direction: you would want to bring tests and a migration path to it, not to rewrite it.
