Variables, types and conversion

A variable is a named box. A type is the rule about what may go in it. Almost every confusing thing a beginner meets in C# — why 5 / 2 is 2, why money must not be a double, why the text "7" is not the number 7 — is one of those rules, met without warning.

Declaring a variable

🧒 Simple

A variable is a labelled box. You say what kind of thing the box holds, you write a label on it, and you put something in. Later you say the label and get the thing back.

The unusual part in C# is the first step: you must say what kind of thing the box holds, and after that the box will refuse anything else. A box marked "whole numbers" will not accept the word "banana", and you find out immediately rather than an hour later. 

int age = 30;                  // declare, and assign, in one statement
age = 31;                       // assign again — the type is not repeated

int count;                      // declare with no value: legal, but unusable so far
count = 0;                      // now it has one, and may be read
Line by line
  • int — the type. It is a keyword, and it means a whole number. Writing the type first is a declaration: it creates the variable and fixes what it may hold for the rest of its life.
  • age — the identifier, your name for it. Must start with a letter or underscore, no spaces, and cannot be a keyword. Convention is camelCase for locals.
  • = — assignment. Right side first: work out the value on the right, then put it in the box on the left. It is not a statement of equality.
  • 30 — an integer literal. Written without quotes and without a decimal point, so the compiler types it as int.
  • age = 31; — assignment without declaration. The type is absent because age already exists and already has a type. Writing int age = 31; again would be an error: the name is taken.
  • int count; — a declaration with no assignment. C# calls this unassigned and will not let you read it until something is put in. Definite assignment is the compiler rule that guarantees this, and it is why C# has no "undefined variable" bugs.

⚠️ Money is decimal, and this is not a preference

double stores numbers in binary, and 0.1 has no exact binary form — just as ⅓ has no exact decimal form. The error is tiny and it accumulates. 

double a = 0.1 + 0.2;      // 0.30000000000000004  ← not 0.3
decimal b = 0.1m + 0.2m;   // 0.3                 ← exact
Line by line
  • 0.1 — a literal with a decimal point, which C# types as double by default.
  • 0.1m — the m is a literal suffix meaning "this is a decimal" (m for money). Without it, the compiler would make a double and then refuse to put it in a decimal box. The other suffixes are L for long, f for float and d for double.

An invoice that is out by 0.00000000000004 fails a reconciliation, and the bug is discovered by an accountant, months later. Use decimal for anything with a currency symbol in front of it.

Writing var instead of the type

var total = 10;              // compiler reads the right side: this is an int
var name  = "Kristi";        // …and this is a string

total = 20;                   // fine — still an int
total = "twenty";             // ERROR CS0029: cannot convert string to int
Line by line
  • var — type inference, not a type. It tells the compiler "work the type out from the right-hand side and use that". The variable is still int; you simply did not type the word.
  • total = "twenty"; — still an error, and this is the point. var is not the loosely-typed var of JavaScript and it is not dynamic. The type was decided once, at compile time, and it is now permanent.
  • var x; on its own — would not compile at all. With no right-hand side there is nothing to infer from.

Conversion: the part that catches everyone

Values change type constantly, and C# has four different mechanisms for it with four different failure behaviours. Knowing which one you are looking at is most of the skill.

1. Implicit — safe, silent, automatic

int small = 42;
long big = small;              // int → long: allowed with nothing written
double d = small;             // int → double: also allowed
Line by line
  • long big = small; — an implicit conversion. C# permits it with no syntax at all because it cannot lose information: every int fits in a long. This is called widening.
  • The reverse, int n = big;, would not compile. Most long values do not fit in an int, so C# refuses to do it behind your back and makes you ask.

2. Cast — you assert it, and you own the consequences

double price = 3.99;
int whole = (int)price;        // 3   ← truncated, NOT rounded

long huge = 5_000_000_000;
int wrapped = (int)huge;      // 705032704  ← silently wrong
Line by line
  • (int) — a cast. A type name in parentheses in front of a value. Read it as "I know this may lose something; do it anyway."
  • (int)3.99 is 3 — casting a decimal number to a whole one truncates, it does not round. (int)3.99 and (int)3.01 are both 3. If you want rounding you must ask for it: Math.Round(price).
  • 5_000_000_000 — the underscores are digit separators. They are ignored by the compiler and exist purely so humans can count the zeroes.
  • (int)huge — the number does not fit, so the extra bits are discarded and you get nonsense. No error, no warning, at compile time or run time. This is what "you own the consequences" means, and it is why a cast should always be a decision rather than a way to make a red squiggle go away.

3. Parsing — text into a number

This is the one you will need constantly, because everything arriving from outside your program — the console, a web form, a file, a query string — arrives as text. 

string typed = "42";

int n = int.Parse(typed);                    // 42 — but THROWS if it is not a number

bool ok = int.TryParse(typed, out int m);   // true, and m is 42
bool no = int.TryParse("banana", out int z);  // false, and z is 0 — no exception
Line by line
  • int.Parse — a static method on the int type. Static means you call it on the type itself, not on a value. It takes text and returns a number.
  • It throws. Given "banana" it raises a FormatException and, unless you catch it, the program stops. So Parse is correct only when text that is not a number is genuinely a bug rather than an expected event.
  • int.TryParse — the same conversion that reports failure instead of throwing. It returns a bool: did it work?
  • out int m — an out parameter. The method has two things to give back — did it work, and the value — and a method can only return one. out is the second channel. out int m also declares m right there, which is why there is no separate line for it.
  • z is 0 on failure — not null, not left alone. That is why you must check the bool: a 0 from a failed TryParse is indistinguishable from a genuine 0 if you ignore it.
🎓 Which one, in one sentence

Use TryParse for anything a user typed, because a typo is not an exceptional condition — it is Tuesday. Use Parse for data you control, a constant or a value your own code just wrote, where bad text really would be a bug you want to hear about loudly.

4. ToString — anything into text

int quantity = 7;
string s1 = quantity.ToString();          // "7"
string s2 = $"qty: {quantity}";             // "qty: 7" — calls ToString for you
string s3 = "qty: " + quantity;             // "qty: 7" — so does +

decimal price = 1234.5m;
string s4 = price.ToString("N2");           // "1,234.50" — N2 = number, 2 decimals
Line by line
  • quantity.ToString() — called on the value with a dot, unlike int.Parse which is called on the type. Every value in C# has a ToString(), so this never fails to compile.
  • $"qty: {quantity}" and "qty: " + quantity — both call ToString() for you. Prefer the interpolated form: it reads better and it does not build a chain of throwaway strings.
  • ToString("N2") — a format string. N2 means "number, grouped, two decimal places". Others worth knowing: C for currency, P for percent, yyyy-MM-dd for a date.
⚠️ Formatting is culture-dependent, and you are in Italy

1234.5m.ToString("N2") is "1,234.50" on an English machine and "1.234,50" on an Italian one — the separators swap. That is correct for something a person reads and catastrophic for something a machine parses.

The rule: current culture for humans, InvariantCulture for machines — files, APIs, databases, logs. Chapter 02 returns to this.

Operators, and the division that surprises everyone

int a = 5, b = 2;              // two declarations of the same type, one statement

int sum  = a + b;               // 7
int diff = a - b;               // 3
int prod = a * b;               // 10
int quot = a / b;               // 2   ← not 2.5
int rem  = a % b;               // 1   ← the remainder

double real = (double)a / b;    // 2.5 ← cast one side FIRST
Line by line
  • int a = 5, b = 2; — one declaration statement, two variables, comma separated. Both are int; the type is written once.
  • a / b is 2 — integer division. When both operands are whole numbers the result is a whole number, and the fraction is discarded. This is the single most common surprise in the language and it is silent.
  • % — the modulo or remainder operator. 5 % 2 is 1. It is how you test divisibility: n % 2 == 0 means "even".
  • (double)a / b — the cast applies to a alone, because a cast binds tighter than division. One side being double is enough: C# widens the other automatically, and the division becomes a real one.
  • (double)(a / b) would be 2.0 — the parentheses would make the integer division happen first and then widen the wrong answer. Where the cast goes is the whole thing.
int score = 10;
score += 5;                     // 15 — shorthand for score = score + 5
score++;                        // 16 — add exactly one

bool passed = score >= 10;      // true  — comparison produces a bool
bool exact  = score == 16;      // true  — two equals signs
bool both   = passed && exact;  // true  — AND: both must hold
bool either = passed || exact;  // true  — OR: at least one
bool not    = !passed;          // false — NOT: flips it
Line by line
  • += — a compound assignment. Read and write in one step. -=, *= and /= work the same way.
  • ++ — increment by one. It is what drives nearly every for loop you will write in the next chapter.
  • >= — a comparison operator. Comparisons produce a bool, which is why the results can be stored in bool variables. The others are <, >, <= and != (not equal).
  • == — equality, two characters. One character is assignment. In C# this mistake is usually caught, because if (x = 5) produces an int where a bool is required and will not compile — a deliberate design fix for a famous C bug.
  • && and || — logical AND and OR. They short-circuit: if the left side of && is false the right side is never evaluated at all. That is not an optimisation you can ignore — it is what makes if (name != null && name.Length > 0) safe.

Strings behave unlike everything else

string first = "Kristi";
string greeting = $"Ciao, {first}!";      // "Ciao, Kristi!"

int len = first.Length;                    // 6 — a property, so no parentheses
string up = first.ToUpper();               // "KRISTI" — a method, so parentheses

Console.WriteLine(first);                  // still "Kristi" — up is a NEW string
Line by line
  • first.Length — a property. Properties look like data and are accessed without parentheses. first.Length() is an error.
  • first.ToUpper() — a method, so it needs parentheses. The rough rule: a property describes the thing, a method does something.
  • up is a new string, and first is unchanged. Strings in C# are immutable — nothing can modify one once it exists. Every method that appears to change a string actually returns a new one, so first.ToUpper(); on a line by itself accomplishes precisely nothing, and the compiler will not stop you.

Null, and the question mark

string? maybe = null;              // ? means: null is allowed here
int length = maybe.Length;         // WARNING — and a crash if it really is null

int safe = maybe?.Length ?? 0;    // 0 — no crash
Line by line
  • null — the absence of an object. Not zero, not an empty string: nothing at all. Asking a nothing for its Length is the famous NullReferenceException.
  • string? — the ? declares that null is expected here. A plain string declares that it is not, and the compiler warns when you break either promise. This is compile-time analysis only; nothing checks it at run time.
  • ?. — the null-conditional operator. "If the left side is null, stop and produce null; otherwise carry on." It turns a crash into a null.
  • ?? — the null-coalescing operator. "Use the left side, unless it is null, in which case use the right." Together, ?. and ?? read as: length, or zero if there is nothing to measure.

Values that must not change

const double Vat = 0.22;                    // fixed at compile time, baked into callers
static readonly DateTime Start = DateTime.Now;  // fixed at run time, once
Line by line
  • const — a compile-time constant. Its value is copied into every place that uses it. Only for things true by definition, because changing a public const does not reach code that was compiled against the old value until that code is rebuilt.
  • readonly — assigned once, at run time, then frozen. Necessary here because DateTime.Now is not knowable when compiling, and const would not compile at all.
Try it yourself

Finish the Celsius converter from 00a. Read the line, TryParse it, and print the result to one decimal place. Then type abc at it on purpose — it must say something polite, not crash. Then write it a second time with int.Parse and watch exactly how it dies, so you recognise a FormatException when you meet one for real.

Golden rules

  1. decimal for money, double for measurement. Binary floating point cannot represent 0.1, and the error accumulates.
  2. int / int is an int. 5 / 2 is 2, and nothing warns you. Cast one side before dividing.
  3. A cast (int) truncates and can silently overflow. It is an assertion, not a conversion — use Math.Round if you meant rounding.
  4. TryParse for anything a human typed; Parse only where bad input would be a bug you want to hear about.
  5. A failed TryParse leaves 0, not null. Check the bool.
  6. var is inference, not dynamic typing. The type is fixed at compile time; you just did not write it.
  7. Strings are immutable. Every method returns a new one, so ignoring the return value does nothing at all.
  8. Properties have no parentheses, methods do. Length versus ToUpper().
  9. && and || short-circuit, which is what makes a null check before a dereference actually work.
  10. Current culture for humans, InvariantCulture for machines. In Italy the decimal separator is a comma, and this will bite you.

Interview questions

"Why should money never be a double?"

double is binary floating point, so decimal fractions like 0.1 have no exact representation and the rounding error accumulates across operations. decimal is base-10 and exact for the values money actually takes. The cost is speed and range, neither of which matters for an invoice.

"What is the difference between Parse and TryParse?"

Parse returns the value and throws a FormatException on bad input; TryParse returns a bool and hands the value back through an out parameter. Choose by whether bad input is expected: user input is expected, so TryParse. Exceptions are also expensive, so parsing a large file with Parse in a try/catch is slow as well as wrong.

"Is var dynamic typing?"

No. It is compile-time type inference — the compiler determines the type from the initialiser and it is fixed from then on, exactly as if you had written it. dynamic is the keyword that actually defers type resolution to run time, and it is a different thing entirely.

"What does ?. do?"

The null-conditional operator short-circuits the whole expression to null when the left side is null, instead of throwing. It is usually paired with ?? to supply a fallback. It does not make null go away — it makes the null travel instead of crashing, which is sometimes the wrong choice, because a null that arrives somewhere far away is harder to diagnose than one that threw at the source.
