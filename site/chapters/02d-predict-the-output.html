Predict the output

Twenty short programs. Every one of them is simple enough to read in ten seconds and confusing enough to get wrong, and each is confusing for exactly one reason that has a name. Cover the explanation, commit to an answer, then read. Being wrong here is the entire point — it is a great deal cheaper than being wrong in a screening test.

How to use this chapter

Say your prediction out loud, or write it down, before reading the dissection. An unspoken prediction is one you will silently revise while reading and then believe you had all along — which teaches you nothing and feels like learning. The exercises get harder down the page but each one stands alone, so this is also a chapter to dip into for ten minutes on a Tuesday.

Numbers

1 — The half that vanished

Console.WriteLine(5 / 2);
Console.WriteLine(5 / 2.0);
Console.WriteLine(5.0 / 2);
Console.WriteLine((double)(5 / 2));
It prints 2, 2.5, 2.5, 2 — line by line
  • 5 / 2 — two ints, so integer division: the remainder is discarded, not rounded. 2.
  • 5 / 2.0 — one side is a double, so the other is promoted and the whole operation is floating point. 2.5.
  • 5.0 / 2 — identical reasoning, other side. 2.5. Only one operand has to be fractional.
  • (double)(5 / 2) — the brackets decide everything. The division happens first, in int, and the cast then widens the answer 2. Converting after the loss does not undo the loss — a sentence worth keeping.

2 — Two numbers that are not equal

double a = 0.1 + 0.2;
Console.WriteLine(a == 0.3);
Console.WriteLine(a);
Console.WriteLine(0.1m + 0.2m == 0.3m);
It prints False, 0.30000000000000004, True — line by line
  • 0.1 + 0.2 — double is binary floating point, and 0.1 has no exact binary form, just as one third has no exact decimal form. Both inputs are already slightly wrong before the addition.
  • a == 0.3 — False, and this is not a bug in C#; every language with IEEE 754 doubles does this. Never compare doubles with ==; compare the difference against a tolerance.
  • Console.WriteLine(a) — modern .NET prints the shortest string that round-trips, so you see the error rather than a tidied 0.3. Older versions hid it, which made this bug much harder to find.
  • 0.1m + 0.2m — decimal is base ten, so tenths are exact. True. This is the whole reason money is a decimal — see chapter 00b.

3 — The modulo of a negative

Console.WriteLine(7 % 3);
Console.WriteLine(-7 % 3);
Console.WriteLine(7 % -3);
It prints 1, −1, 1 — line by line
  • 7 % 3 — the remainder after integer division. 1, as expected.
  • -7 % 3 — −1, not 2. In C# the result takes the sign of the left operand, because % is defined so that (a / b) * b + a % b == a holds.
  • 7 % -3 — 1. Same rule: the right operand's sign is irrelevant to the sign of the answer.
  • Where this bites: index % length to wrap around a circular buffer gives a negative index as soon as index goes negative, and the exception appears one layer away from the arithmetic. The fix is ((index % length) + length) % length.

4 — Before or after

int i = 5;
Console.WriteLine(i++);
Console.WriteLine(i);
Console.WriteLine(++i);
It prints 5, 6, 7 — line by line
  • i++ — post-increment: the value of the expression is the old one, and the variable is incremented afterwards. Prints 5.
  • i — the increment did happen. 6.
  • ++i — pre-increment: increment first, then the expression is the new value. 7.
  • The professional position is that neither belongs inside a larger expression. arr[i++] = i; is legal and nobody should have to work out what it means. As a statement on its own, i++; is fine and the two forms are identical.

5 — The sum that went backwards

int big = 2_000_000_000;
Console.WriteLine(big + big);
Console.WriteLine((long)big + big);
Console.WriteLine((long)(big + big));
It prints −294967296, 4000000000, −294967296 — line by line
  • big + big — 4 billion does not fit in an int, whose ceiling is about 2.1 billion, so it wraps to a negative number. No exception, no warning.
  • (long)big + big — the cast makes the left operand a long, so the right is promoted too and the addition happens in 64 bits. Correct.
  • (long)(big + big) — the brackets again. The addition overflows first, then the wrong answer is widened. Same value as line one.
  • The rule these three share with exercise 1: a cast on the outside cannot fix arithmetic on the inside. Widen an operand, not the result.

Strings

6 — The method that did nothing

string s = "hello";
s.ToUpper();
s.Replace("l", "L");
Console.WriteLine(s);
It prints hello — line by line
  • s.ToUpper(); — strings are immutable. The method builds a new string and returns it; this line drops the answer on the floor.
  • s.Replace(…); — the same. Two lines of code, zero effect.
  • Console.WriteLine(s) — hello, unchanged and unchangeable.
  • Recognising this in review is a skill worth having: a statement whose whole body is a method call on a string is dead code, unless that method is on a StringBuilder. The analyser flags it as CA1806 if it is switched on.

7 — Same text, different question

string a = "MI-42";
string b = "mi-42";
Console.WriteLine(a == b);
Console.WriteLine(a.Equals(b, StringComparison.OrdinalIgnoreCase));
Console.WriteLine(ReferenceEquals(a, "MI-42"));
It prints False, True, True — line by line
  • a == b — string compares contents, so this is a real character-by-character comparison, and case is part of the content. False.
  • OrdinalIgnoreCase — the same comparison with case folded away. True. Use the ordinal forms for codes and identifiers; the culture-aware ones can genuinely differ between machines.
  • ReferenceEquals(a, "MI-42") — True, and this one surprises people. Identical string literals in one assembly are interned: the runtime keeps one copy and hands out the same reference.
  • Never rely on that. Build the same text at run time — "MI-" + "42" from variables — and it is a different object, so the same line prints False. Interning is an optimisation, not a guarantee you can program against.

8 — Adding nothing

string? a = null;
Console.WriteLine(a + "x");
Console.WriteLine((a + "x").Length);
Console.WriteLine(a.Length);
It prints x, 1, then throws — line by line
  • a + "x" — concatenation treats a null string as empty, by definition. Prints x.
  • .Length on that result — 1. The result of a concatenation is never null, so this is safe.
  • a.Length — NullReferenceException. Calling a member on null is the failure; being an operand of + is not.
  • This asymmetry is why string.IsNullOrEmpty exists and gets used everywhere: the two states behave the same in some operations and differently in others, so the only safe habit is to test for both at once.

9 — Growing a string in a loop

string s = "";
for (int i = 0; i < 3; i++)
    s += i;
Console.WriteLine(s);
Console.WriteLine(s.Length);
It prints 012, 3 — line by line
  • s += i — an int meeting a string under + becomes text, so this appends the digits, it does not add.
  • Each iteration builds a whole new string and throws the previous one away: three strings for three iterations, and ten thousand for ten thousand.
  • s.Length — 3. Characters, not items.
  • The answer is correct and the method is wrong, which is the interesting part. Nothing about the output tells you this loop is quadratic — that only shows up when the loop gets long, in production, on somebody else's data. StringBuilder exists for exactly this shape.

Collections

10 — One list, two names

var a = new List<int> { 1, 2 };
var b = a;
var c = new List<int>(a);
b.Add(3);
c.Add(4);
Console.WriteLine($"{a.Count} {b.Count} {c.Count}");
It prints 3 3 3 — line by line
  • var b = a; — aliasing. One list, two names.
  • var c = new List<int>(a); — a copy: a genuinely new list holding the same two items.
  • b.Add(3) — grows the shared list, so a and b are both 3.
  • c.Add(4) — grows the copy: also 3, coincidentally, because it started at 2. The equal numbers hide the difference, which is exactly why this is the version worth practising — add another element to b and the illusion breaks.
  • And the copy is shallow: with a List<Order> you would get a new list pointing at the very same orders. Copying the container is not copying the contents.

11 — Editing while looking

var items = new List<string> { "a", "b", "c" };
foreach (var x in items)
    if (x == "b") items.Remove(x);
Console.WriteLine(items.Count);
It throws InvalidOperationException — line by line
  • foreach — asks the list for an enumerator, which records the list's version number when it starts.
  • items.Remove(x) — bumps that version. The next step of the loop notices and throws "Collection was modified; enumeration operation may not execute."
  • It throws on the next iteration, not on the Remove — which is why removing the last item sometimes appears to work. That is the worst possible behaviour: a bug that depends on the data.
  • The fixes, in order of preference: items.RemoveAll(x => x == "b");, or build a new list with LINQ, or loop backwards with a for and index. Never "collect into a second list and remove afterwards" if a one-liner will do.

12 — The order nobody promised

var d = new Dictionary<string, int>();
d["zeta"] = 1;
d["alpha"] = 2;
d["zeta"] = 3;
Console.WriteLine(d.Count);
Console.WriteLine(d["zeta"]);
It prints 2, 3 — line by line
  • d["zeta"] = 1; — the indexer adds or replaces, silently. This is the difference from d.Add("zeta", 1), which throws on a duplicate key.
  • d["zeta"] = 3; — replaces, so the count stays at 2 and the value is 3.
  • Reading a key that is absent throws KeyNotFoundException — note the asymmetry: writing is forgiving, reading is not. TryGetValue is the forgiving read.
  • And the trap that is not in the output: enumeration order is not specified. It often looks like insertion order and is not guaranteed to be, so code that depends on it works until a rehash. Sort explicitly, or use an ordered structure.

13 — The query that ran twice

var nums = new List<int> { 1, 2, 3 };
var big = nums.Where(n => { Console.Write("."); return n > 1; });
Console.WriteLine(big.Count());
Console.WriteLine(big.Count());
It prints ...2 then ...2 — line by line
  • nums.Where(…) — nothing runs here. LINQ operators are lazy: this line builds a description of a query and no dot is printed yet.
  • The first Count() — forces enumeration. Three dots, then 2.
  • The second Count() — three more dots. The query is not a result, it is a recipe, and asking twice cooks twice.
  • Harmless with a Console.Write and a three-item list. With a database behind it this is two round trips, and with a network call in the predicate it is the bug that makes a page mysteriously slow. .ToList() once, then reuse — chapter 06.

References, structs and copies

14 — The struct that would not change

struct P { public int X; }

var list = new List<P> { new P { X = 1 } };
var item = list[0];
item.X = 99;
Console.WriteLine(list[0].X);
It prints 1 — line by line
  • struct P — a value type, so every assignment is a copy of the whole thing.
  • var item = list[0]; — the indexer returns a copy. There are now two P's: the one in the list and the one in item.
  • item.X = 99; — changes the copy. The list never hears about it.
  • Change struct to class and the same code prints 99, because the indexer would return the reference instead. One keyword, opposite behaviour, and the compiler is silent in both directions. This is the strongest argument for making structs immutable: then the copy cannot be misleading, because nothing can be changed through it.

15 — Passing an object to a method

void Rename(Order o) { o.Code = "B"; }
void Replace(Order o) { o = new Order { Code = "C" }; }

var order = new Order { Code = "A" };
Rename(order);   Console.WriteLine(order.Code);
Replace(order);  Console.WriteLine(order.Code);
It prints B, B — line by line
  • Rename — the method receives a copy of the reference, which still points at your order. Setting .Code goes through the reference and changes the real object. Prints B.
  • Replace — assigns to the parameter, which is the method's own local copy of the address. Your variable still holds the old address.
  • So the second line prints B, not C. The new order is created, pointed at by nobody once the method returns, and collected.
  • The precise phrasing that survives an interview: C# passes everything by value; for a reference type, the thing passed by value is the reference. Adding ref to Replace's parameter is what makes the reassignment visible to the caller.

16 — The copy that was not a copy

record Customer(string Name, List<string> Tags);

var a = new Customer("Rossi", ["vip"]);
var b = a with { Name = "Bianchi" };
b.Tags.Add("late");
Console.WriteLine($"{a.Name} {a.Tags.Count}");
It prints Rossi 2 — line by line
  • a with { Name = … } — a non-destructive copy: a new record with one member changed. a.Name is still Rossi, as promised.
  • b.Tags — but with performs a shallow copy, so the Tags field of the copy holds the very same list reference.
  • b.Tags.Add("late") — mutates the shared list, so a.Tags.Count is 2. The record was immutable; the list inside it never was.
  • The lesson is that immutability is not transitive by default. A record of records is genuinely safe; a record holding a List is a promise with a hole in it. Use ImmutableArray<T> or IReadOnlyList<T> plus a defensive copy when the promise has to hold.

Closures, nulls and order

17 — Three lambdas, one variable

var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));
foreach (var a in actions) a();
It prints 333 — line by line
  • () => Console.Write(i) — a closure. It captures the variable i, not the value i had when the lambda was written.
  • A for loop has one i for the whole loop, so all three lambdas share it.
  • By the time any of them runs, the loop has finished and i is 3 — the value that made the condition false. Hence 333.
  • Two fixes. Copy inside the loop: int copy = i; and capture copy, which is a fresh variable each iteration. Or use foreach, whose iteration variable is a new one per pass — that was changed in C# 5 precisely because this bug was so common. The for version was deliberately left alone, so it still bites.

18 — The default that was not null

string? name = null;
int count = 0;
Console.WriteLine(name ?? "missing");
Console.WriteLine(count == 0 ? "zero" : "some");
Console.WriteLine("" ?? "missing");
It prints missing, zero, then an empty line — line by line
  • name ?? "missing" — name is null, so the fallback is used.
  • count == 0 ? … — the ternary, nothing to do with null. Prints zero.
  • "" ?? "missing" — an empty string is not null, so ?? passes it straight through and you get a blank line. This is the single most common misunderstanding of the operator.
  • When "empty counts as missing" is what you mean, say so: string.IsNullOrWhiteSpace(name) ? "missing" : name. The whitespace variant is usually the right one for anything a human typed into a form.

19 — Which one runs first

int Side(string tag) { Console.Write(tag); return 1; }

bool r1 = Side("a") > 0 || Side("b") > 0;
bool r2 = Side("c") > 0 | Side("d") > 0;
It prints a then cd — line by line
  • || — short-circuits. The left side is true, so the right is never evaluated and b is never printed.
  • | — the non-short-circuiting boolean or. Both sides are evaluated whatever happens, so you get cd.
  • The same pair exists for and: && stops when the left is false, & does not. Almost every guard in real code relies on short-circuiting: if (o != null && o.Count > 0) works only because the right side is skipped.
  • Which is why the single-character version in a null guard is a genuine bug and not a style preference — it evaluates o.Count on a null o and throws. A one-character typo with a stack trace attached.

20 — The finally that changed the answer

int Compute()
{
    try    { return 1; }
    finally { Console.Write("cleanup "); }
}
Console.WriteLine(Compute());
It prints "cleanup 1" — line by line
  • return 1; — the return value is computed and stored, but the method has not left yet.
  • finally — runs before control actually leaves, which is the whole guarantee: it happens on the way out, whether that is a return, an exception, or falling off the end.
  • So cleanup is printed first, and only then does WriteLine receive 1. The output is on one line because Write does not add a newline.
  • The reason to know this: using is compiled into exactly this shape, which is why a disposed resource is still disposed when you return from inside the block. And a return inside finally would replace the returned value and swallow any in-flight exception — which is why the compiler forbids it.
Try it yourself

Put all twenty into one console project, one method each, and run it. Then go back and change exactly one token in each — struct to class, for to foreach, || to |, double to decimal — and predict the new output before running again. The second pass is where these stop being trivia and start being a model of what the language does, because you are no longer remembering answers, you are deriving them.

Golden rules

  1. Commit to the prediction before you read the answer. An unspoken guess gets silently revised while you read, which feels like learning and is not.
  2. int / int is an int, and the fraction is discarded rather than rounded. Widen an operand before dividing, and use decimal when it is money.
  3. Never compare two doubles with ==. Compare the difference against a tolerance. 0.1 + 0.2 is not 0.3 in any language with binary floating point.
  4. A string method call with no = in front of it is dead code. Strings are immutable; every method returns a new one.
  5. Do not modify a collection you are enumerating. It throws on the next iteration, which is why removing the last item sometimes seems to work — a bug that depends on the data. Use RemoveAll, rebuild with LINQ, or loop backwards by index.
  6. A LINQ query is a recipe, not a result. Enumerating twice runs it twice. ToList() once, then reuse.
  7. Copying a container is not copying its contents. A record's with is shallow too, so an immutable record holding a List is a promise with a hole in it.
  8. Lambdas capture the variable, not the value. A for loop has one loop variable for every iteration — copy it inside the body before capturing. foreach does not have the bug.
  9. && and || short-circuit; & and | do not. In a null guard that one-character difference is a real bug with a stack trace attached.
  10. finally runs on the way out, including after a return and during an exception. That is exactly what using compiles into.
  11. Getting one wrong here is the point. It is a great deal cheaper than getting it wrong in a screening test, which is the same format — see chapter 37.

Interview questions

"Why does this loop print 3, 3, 3 instead of 0, 1, 2?"

Because the lambdas capture the variable rather than its value, and a for loop has a single loop variable for all iterations. By the time the delegates run, the loop has finished and that shared variable holds 3. The fix is to copy it into a new variable inside the loop body and capture the copy — or use foreach, whose iteration variable is fresh each pass, which is why the same bug does not occur there.

"A method changes an object I passed in, but reassigning it has no effect. Why?"

C# passes everything by value, and for a reference type what is passed by value is the reference. So the method has its own copy of the address: following it changes the shared object, which you can see, but assigning a new object to the parameter only changes the method's copy of the address, which you cannot. Marking the parameter ref is what makes the reassignment visible to the caller.

"Perché 0.1 + 0.2 non fa 0.3?"

Perché double è virgola mobile binaria, e 0.1 in binario è periodico — come un terzo in decimale. Quindi già i due valori di partenza sono approssimati, e l'errore si vede nel risultato. Per i soldi uso decimal, che è in base dieci e rappresenta i decimi in modo esatto; double lo tengo per le misure, dove un errore alla quindicesima cifra non interessa a nessuno. E due double non li confronto mai con ==: confronto la differenza contro una tolleranza.
