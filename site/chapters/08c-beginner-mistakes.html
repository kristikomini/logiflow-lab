The mistakes beginners make

Not a list of things you should feel bad about. Every one of these is reasonable — it is what a careful person writes before they have seen what it costs — and each is written here the same way: why you write it, what it actually costs, and the smallest change that fixes it.

Why this chapter exists

A junior is not distinguished from a mid-level developer by syntax. They are distinguished by a set of habits, almost all of which were learned by being burned once. That is a slow and expensive way to learn them, and the burn usually happens in front of a customer.

This chapter is the short cut: the same habits, with the burn described rather than experienced. It is also, bluntly, an interview asset — "what is the worst bug you have caused?" and "what would you do differently?" are asked in almost every technical round, and the answers that land are specific.

Errors: hiding the news

Catching everything, doing nothing

🧒 Simple

You are given a letter saying the roof is leaking. You put it in a drawer. The roof is still leaking, and now nobody knows.

Why you write it. The program crashed, you wrapped the line in try/catch, and it stopped crashing. That felt like fixing it. It is the single most natural mistake in programming, because the feedback is instant and positive.

What it costs. The failure did not go away — it became a wrong answer. The order is saved without its lines; the import reports success having written nothing; the cache holds null for the next hour. You will find out days later from a customer, with no log line, no stack trace and no idea which of the hundred runs was the bad one. A crash is information. Hiding it is the most expensive thing on this page.

The fix. Catch the narrowest type you can actually do something about, at the layer that can do it, and let everything else travel to the top where one handler logs it and returns a sensible error to the caller. The rule is in chapter 05b and the machinery in chapter 07.

⚠ The related one nobody tells you about

Exceptions as control flow. try { return int.Parse(s); } catch { return 0; } works, and it is roughly a thousand times slower than int.TryParse when the input is often bad — exceptions capture a stack trace, and that is not free. Use the Try… method when failure is expected; save exceptions for the case that is genuinely exceptional.

Not reading the error message

Why you do it. A wall of red text with forty lines of stack trace does not look like a sentence, so the eye slides off it and goes to a search engine instead.

What it costs. Usually twenty minutes, and occasionally the whole afternoon: the message very often names the file, the line, the parameter and the value. The habit of searching the exception type instead of reading the exception text is the most reliable difference between a beginner debugging and a professional debugging.

The fix. Read three things, in this order, every time: the exception type, the message, and the first line of the stack trace that names a file you wrote. That last one is the whole trick — the top of the trace is usually inside a framework, and the first frame in your own code is where to look. Then check for an InnerException, which is where the real cause hides when a framework wraps it.

Nulls and the code that guesses

Returning null to mean "nothing found"

// Before: three different meanings, one value
public List<Order>? GetOrders(int customerId)
{
    if (customerId <= 0) return null;      // bad input
    var found = _db.Orders.Where(...).ToList();
    return found.Count == 0 ? null : found;  // no rows
}

// Every caller, forever:
var orders = GetOrders(id);
if (orders != null) foreach (var o in orders) { … }

// After: empty is a perfectly good answer, and invalid is not an answer at all
public IReadOnlyList<Order> GetOrders(int customerId)
{
    if (customerId <= 0)
        throw new ArgumentOutOfRangeException(nameof(customerId));

    return _db.Orders.Where(...).ToList();
}

foreach (var o in GetOrders(id)) { … }      // no check needed, ever
Line by line
  • return null; for bad input — a programming error returned as data. The caller now has to distinguish "you asked wrongly" from "there is nothing", using the same value, which it cannot.
  • found.Count == 0 ? null : found — the expensive one. An empty collection is already the right answer for "no rows": you can iterate it, count it, and it produces nothing. Turning it into null converts a normal result into a landmine.
  • if (orders != null) — this check now appears at every call site forever, and one of them will be forgotten. That forgotten one is a NullReferenceException in production, in a method that did nothing wrong.
  • IReadOnlyList<Order> — the return type also stops callers mutating the list you handed them, which is a second bug class removed by a type name.
  • throw new ArgumentOutOfRangeException — the input error becomes loud, immediate and attributable: the stack trace points at the caller who passed the bad id.
  • When null IS right: a single item that genuinely may not exist — FindById returning Order?. Then say so in the type with the question mark, turn on nullable reference types, and let the compiler make every caller handle it.

Checking for null everywhere instead of deciding

Why you write it. You were burned by a NullReferenceException, so now every method starts with three if (x == null) return; lines. It feels like defensive programming.

What it costs. It moves the crash rather than removing it, and it hides which component was wrong. Worse, it makes the code lie: a method that silently returns when handed null looks like it did the job.

The fix. Decide, per parameter, whether null is legal. If it is not, ArgumentNullException.ThrowIfNull(x) — one line, loud, at the boundary. If it is, handle it deliberately and say so in the signature with ?. Then turn on nullable reference types (<Nullable>enable</Nullable> in the project file) so the compiler does the checking you were doing by hand. Use string.IsNullOrWhiteSpace(s) rather than s == null || s == "", because the third case — a string of spaces from a web form — is the one that reaches you.

Strings, money and SQL

Expecting a string to change itself

var name = "  Mario Rossi  ";
name.Trim();                            // does nothing to `name`
name.Replace("Rossi", "Bianchi");      // also nothing
Console.WriteLine($"[{name}]");          // [  Mario Rossi  ]

name = name.Trim().Replace("Rossi", "Bianchi");   // the answer is returned

// And the one that shows up as a timeout in production
var csv = "";
foreach (var order in orders)          // 50,000 of them
    csv += order.Id + ";" + order.Total + "\n";

var sb = new StringBuilder();
foreach (var order in orders)
    sb.Append(order.Id).Append(';').Append(order.Total).Append('\n');
Line by line
  • name.Trim(); on its own — strings are immutable, so every method that "changes" one actually returns a new one. Discarding the return value discards the work. The compiler warns about some of these and not all of them.
  • name = name.Trim()… — the fix is always the same: assign the result. Once you have the model — a string method is a question, not a command — the whole family of these disappears at once.
  • csv += … in a loop — each += allocates a whole new string and copies everything so far into it. Fifty thousand rows means fifty thousand copies of an ever-growing string: quadratic work, hundreds of megabytes of garbage, and a request that times out.
  • new StringBuilder() — one growable buffer, appended to in place. The same loop finishes in milliseconds.
  • Do not over-correct: a + b + c on one line is compiled into a single efficient call and is better than a StringBuilder. The rule is specifically concatenation in a loop.

Building SQL by gluing strings together

// The most damaging line a beginner writes
var sql = "SELECT * FROM Orders WHERE Reference = '" + input + "'";

// input: x' OR '1'='1   → returns every row
// input: x'; DROP TABLE Orders; --   → does what it says

// The fix, in raw ADO.NET
using var cmd = new SqlCommand(
    "SELECT * FROM Orders WHERE Reference = @reference", connection);
cmd.Parameters.AddWithValue("@reference", input);

// The fix, in EF Core — already parameterised, nothing to remember
var orders = await _db.Orders
    .Where(o => o.Reference == input)
    .ToListAsync(ct);
Line by line
  • "… = '" + input + "'" — the value and the code arrive at the database as one string, so the database has no way to tell which part was meant to be data. That is the entire mechanism of SQL injection; there is nothing more to it.
  • x' OR '1'='1 — the quote closes the literal and the rest is read as SQL. No tooling required, and it is the first thing anyone tries.
  • @reference plus Parameters.AddWithValue — the value travels separately from the command text, so it can never be parsed as SQL no matter what is in it. Escaping quotes by hand is not an equivalent fix and never has been.
  • .Where(o => o.Reference == input) — EF Core parameterises for you, which is a real security argument for an ORM. Note the exception: FromSqlRaw with an interpolated string puts you straight back in the first case. Use FromSqlInterpolated, which parameterises the holes.
  • The interview line: being asked "what is SQL injection" and answering "you have to escape the input" is a wrong answer that sounds right. The answer is separate the data from the command. See chapter 15.

Money in a double, dates in a string

Why you write it. double is the type you were taught for "a number with a decimal point", and a date arrives from a form as text, so storing it as text feels like one less conversion.

What it costs. double cannot represent a tenth exactly, so totals drift by cents that nobody can reconcile — see the second puzzle in chapter 08b. A date in a varchar column cannot be sorted, cannot be compared with a range, has no time zone and will one day contain "31/02/2026", because nothing was stopping it.

The fix. decimal for money, always, in C# and in the database column. DateTime in UTC, or DateTimeOffset when the offset matters, and DateOnly for a date with no time — a birthday is not an instant. Parse at the boundary with decimal.TryParse / DateTime.TryParse and an explicit CultureInfo, because a machine set to Italian reads 1,5 as one and a half and a machine set to English reads it as fifteen.

Resources, threads and the things that leak

Not disposing what you opened

Why you write it. C# has a garbage collector, and you were told it handles memory. It does — and that is exactly the trap, because a file handle, a database connection and a socket are not memory.

What it costs. A connection not returned to the pool is a connection nobody else can have. The symptom is not an error on the line that leaked: it is "Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool", appearing under load, in a completely different part of the application, half an hour later.

The fix. If a type implements IDisposable, it goes in a using — using var conn = new SqlConnection(...); and the compiler writes the try/finally for you. The exception worth knowing is HttpClient, which is the opposite: creating one per request exhausts the operating system's sockets, so it is registered once with IHttpClientFactory and reused. Chapter 08 is the long version.

Using async as decoration

Why you write it. Async is "the modern way", so it goes on everything, and where the compiler complains it gets .Result or Task.Run until it stops.

What it costs. .Result and .Wait() deadlock a context-bound application outright (puzzle 9). async void makes exceptions uncatchable by the caller and takes the process down with them. Task.Run around a database call moves the waiting to a different thread instead of removing it, so the thread pool is now busier for no benefit at all.

The fix. Async exists to stop occupying a thread while waiting for something outside the process — a disk, a network, a database. Use it for those, all the way up the call chain, and pass the CancellationToken along. Do not use it for work that is purely computation, and never mix it with a blocking wait.

Putting changeable state in something shared

Why you write it. A static field is the easiest way to reach something from anywhere, and registering a service as a singleton looks like a performance win.

What it costs. A web server handles requests in parallel. Anything shared and changeable is being written by several requests at once, so one user sees another user's data — a bug that is untestable locally (one user, one request), intermittent in production, and a genuine data-protection problem rather than an inconvenience. The classic version is a DbContext registered as a singleton: it is not thread-safe and it caches every entity it ever loaded.

The fix. Shared means immutable. If it has to change, it belongs in a per-request (scoped) service, or behind a type built for the job such as ConcurrentDictionary. And remember the reverse trap: a singleton that takes a scoped dependency in its constructor captures the first one forever.

Shape and habits

Magic numbers, magic strings, copy-paste

Why you write it. if (status == 3) is quicker to type than creating an enum, and copying a working block is quicker than working out how to share it.

What it costs. Magic values cannot be searched for reliably — 3 appears everywhere — and they cannot be renamed. Copy-paste costs on the day the logic changes: you will fix it in the two places you remember and leave the third, and the third is the one in the nightly job that nobody watches.

The fix. An enum or a const for values, nameof for anything that is really a member name, and configuration for anything that differs per environment. For duplication, apply the rule from chapter 05b rather than a reflex: extract when the copies must change together, and leave them apart when they merely look alike.

Building for a future nobody ordered

Why you write it. You have just learned interfaces, generics and patterns, and they are genuinely exciting. A generic base repository with a plugin system feels like engineering.

What it costs. Every abstraction is a file to open, a name to learn and an indirection to follow, paid by every reader from now on for a flexibility nobody asked for. It is also usually the wrong flexibility — when the second requirement arrives it varies along an axis you did not build. The reviewer's version of this is blunt: "what change is this protecting us from?"

The fix. Write the simplest thing that passes the test. Add the seam when a second case actually exists, which is usually a five-minute refactor because the tests are there. This is YAGNI, and juniors under-apply it more than any other principle because it feels like not trying.

Ignoring the compiler when it is being helpful

Why you do it. The build succeeded. The warnings are yellow, there are already sixty of them, and one more makes no difference.

What it costs. Sixty warnings is the same as none, because nobody can see the one that matters. And the ones that matter really do: CS0659 is the dictionary that loses your key, CS4014 is a task nobody awaited — a fire-and-forget operation whose exceptions vanish — and the nullable warnings are a null-reference exception that has not happened yet.

The fix. Keep the count at zero, from the first day of a project, which is the only time it is cheap. Set <TreatWarningsAsErrors>true</TreatWarningsAsErrors> and turn on nullable reference types. Where a warning is genuinely wrong, suppress that one with a comment saying why — which is a decision, recorded, rather than a yellow triangle.

Testing and shipping

"I tested it by running it"

🧒 Simple

Checking that the light comes on by flicking the switch is fine. Doing that for every light in the building, by hand, every time anybody changes anything, is not.

Why you do it. Clicking through the screen is immediate and obviously real, whereas writing a test is work that produces no feature.

What it costs. Nothing, the first week. The cost arrives when you change something and cannot tell what else you broke, so you either test everything by hand or ship and hope. That is the moment a codebase starts getting slower to change, and it never speeds up again on its own.

The fix. Start with the tests that are almost free: the pure calculation, the parser, the validation rules. One arrange-act-assert per behaviour, named for the behaviour. Do not chase a coverage number — cover the logic that would be embarrassing to get wrong. Chapter 24 is the whole argument.

⚠ The mistake that comes after this one

Testing the mock. Once mocking clicks, it is easy to write a test that sets up a fake repository to return two orders, calls the service, and asserts that the fake was called. That test passes when the code is wrong, fails when the code is merely rearranged, and asserts nothing about behaviour. If the assertion is about how the code worked rather than what it produced, it is usually a test to delete.

"It works on my machine"

Why it happens. Your machine has a connection string, a certificate, a file in a folder, a time zone, a culture and a database with your test data in it. None of those are in the repository, so none of them are on the build server or your colleague's laptop.

What it costs. The first day of every new team member, repeatedly, and a deployment that fails at the worst possible moment for a reason that has nothing to do with the change being deployed.

The fix. Anything the app needs to run is either in the repository or in documented configuration: a docker-compose for the dependencies, a README with the steps, migrations for the schema, seed data in code. The test is simple and worth running once: can a colleague clone it and get it running without asking you a question? See chapter 28 and chapter 30.

Working for two days without committing

Why you do it. Committing feels like it should be reserved for finished work, and a branch with half-working code feels untidy.

What it costs. Two days of work with no way back to a point where it ran. The first ninety-minute mess of "it worked an hour ago and now it does not, and I cannot remember what I changed" is the one that teaches this, and everybody has it once.

The fix. Commit whenever it builds and the tests pass, in small pieces, with a message saying why rather than what — the diff already says what. Push the branch daily so it exists somewhere other than your laptop. Keep refactoring in its own commit so the review of the real change is readable. Chapter 26 has the commands and the recovery routes.

Being stuck silently

Why you do it. Asking feels like admitting you cannot do the job, especially in the first months, and especially if everyone else looks busy.

What it costs. The team's time, not yours — a colleague would rather spend five minutes on Tuesday than discover on Friday that the ticket went nowhere. Most teams have an informal rule of thirty to sixty minutes of genuine attempts before asking, and not asking after that is the thing that gets noticed.

The fix. Ask in a shape that costs the other person nothing: what you are trying to do, what you tried, what happened, and what you think is going on. Half the time you will solve it while writing the message, which is why rubber ducking has a name. And say it in the stand-up rather than privately — see chapter 34 for why a blocker is a status, not a confession.

Try it yourself

Audit your own repository against this page. Every one of these is greppable, and the point of doing it with a search rather than by memory is that you will find some: 

grep -rn "catch" --include=*.cs . | grep -v "catch ("   # bare catch
grep -rn "\.Result\|\.Wait()" --include=*.cs .           # blocking on async
grep -rn "double .*[Pp]rice\|double .*[Tt]otal" --include=*.cs .
grep -rn "static " --include=*.cs . | grep -v "static readonly\|const"
dotnet build -warnaserror                              # how many are there really?
Line by line
  • grep -v "catch (" — leaves only catch with no type, which is the widest possible catch. Each hit is a question: what exactly was this protecting against?
  • \.Result\|\.Wait() — every one of these is either a deadlock waiting for a synchronisation context or a thread held for nothing. In a console Main it may be legitimate; anywhere else, look twice.
  • double .*[Pp]rice — crude, and it finds real money in double more often than anyone expects, including in database models where it also fixed the column type.
  • static minus static readonly and const — what is left is mutable shared state. In a web application each one is a question about concurrency.
  • dotnet build -warnaserror — the number that comes back is the honest one. Do not fix them all today; write the number down, then make sure it never goes up.

Golden rules

  1. A crash is information. An empty catch converts it into a wrong answer nobody reports.
  2. Read the exception type, the message, and the first frame in code you wrote — in that order.
  3. Return an empty collection, never null, when the answer is "nothing found".
  4. Decide per parameter whether null is legal, then let the compiler enforce it.
  5. String methods return a new string; the one you called them on is unchanged.
  6. Concatenating in a loop is quadratic. StringBuilder for loops, + for lines.
  7. Never build SQL by concatenation. Parameters keep data and command apart, and escaping does not.
  8. decimal for money, UTC for instants, and parse with an explicit culture.
  9. Anything IDisposable goes in a using; HttpClient is the exception that is reused.
  10. Async is for waiting on something outside the process, all the way up, never with .Result.
  11. Shared state must be immutable, or it is a bug that only appears under load.
  12. A magic number is a name nobody wrote; an enum cannot be misremembered.
  13. Do not build a seam until a second case exists. Speculative flexibility is usually the wrong axis.
  14. Keep the warning count at zero; sixty warnings is the same as none.
  15. Commit whenever it builds, in small pieces, with a message that says why.
  16. Try for half an hour, then ask — with what you tried and what happened.

Interview questions

"What is the worst bug you have caused?"

Asked far more often than people expect, and the wrong answer is "nothing serious". Pick a real one, tell it in four beats — what broke, how it was noticed, what the actual cause was, what you changed so the whole class of it cannot come back — and do not skip the middle beat where you were looking in the wrong place. Owning a mistake plainly reads as senior; an evasion reads as someone who will hide the next one.

"When would you catch an exception?"

"When I can genuinely do something about it at that level — retry, fall back, or add context the caller needs." Then say the rest out loud, because it is the part most candidates leave out: "otherwise I let it travel to one handler at the top that logs it and turns it into a sensible response. A catch that only logs and carries on is how a failure becomes a wrong answer."

"How do you avoid SQL injection?"

The short correct answer is parameterised queries — the data never travels in the same string as the command. Say explicitly that escaping quotes is not an equivalent defence, and add the one caveat that shows real use: "an ORM does it for you, except on the raw-SQL escape hatch, where FromSqlInterpolated parameterises and FromSqlRaw with an interpolated string does not."

"You have inherited code with no tests. Where do you start?"

A judgement question, and "write tests for everything" is the answer that fails it. "I would not retrofit coverage — I would put a test around the next thing I have to change, so the change is safe, and start with the pure logic because it needs no setup. Over a few months the tested area is exactly the area that changes, which is where the tests are worth most."

"What do you do when you are stuck?"

They are asking whether you will disappear for three days. Give the shape of your process: read the error properly, reduce it to the smallest thing that reproduces it, check the assumption you have not checked — and then a time limit and a question with what you tried in it. Mentioning the time limit is what makes the rest believable.
