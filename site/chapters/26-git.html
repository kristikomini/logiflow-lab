Git

Listed last, and marked optional, which in practice means assumed. Git is the tool you touch most often after the compiler, and the one where a moment of confusion costs a colleague an afternoon. Learn the model, and the commands stop needing memorising.

From the advert

"Utilizzo di Git per il controllo di versione." Treat it as mandatory. Nobody will ask you to explain git commit; they may well ask what you do when a rebase goes wrong.

The model — three places, not one

🧒 Simple

You are packing a parcel to post.

  • Your desk is covered in things — that is your working folder.
  • You put some of them in a box, but do not seal it yet. That is staging: choosing what goes in.
  • You seal and label the box. That is a commit — and now it cannot change.
  • You take it to the post office. That is push.

Everything on your desk and in the box is still only yours. Nobody else sees a thing until the last step.

The daily commands

what you type every day
git status                          # where am I? Run this constantly.
git switch -c feature/order-export  # new branch, and move to it

git add src/LogiFlow.Api/           # stage specific paths…
git add -p                          # …or review hunk by hunk — the habit worth building

git commit -m "Add CSV export for orders"
git push -u origin feature/order-export

git switch main
git pull                            # fetch + merge from the remote

git log --oneline --graph --decorate -20
git diff                            # working tree vs staged
git diff --staged                   # staged vs last commit
Line by line
  • git status — run it constantly. Nearly every confusing git situation is answered by it, and it prints the command you probably want next.
  • git switch -c feature/order-export — create and move. switch is the modern verb; checkout still works and does too many unrelated things, which is why it was split.
  • git add src/LogiFlow.Api/ — stage specific paths. The staging area is git's distinctive idea: what you have changed and what you are about to commit are separate.
  • git add -p — review hunk by hunk, and the habit worth building. It catches the debug line and the stray formatting change before they reach the diff a colleague reads.
  • git push -u origin feature/... — -u sets the upstream, so later git push and git pull need no arguments. Only needed the first time.
  • git pull — a fetch plus a merge. Knowing it is two operations is what makes --rebase and its merge commits understandable rather than magic.

git switch and git restore replaced the overloaded git checkout, which did both jobs and was the source of endless confusion. Use the newer ones; expect to see checkout in older documentation and older colleagues' fingers.

Branching

🎓 What a branch actually is

A branch is not a copy of anything. It is a 41-byte file containing a commit hash — a movable label pointing at one commit. Committing moves the label forward. That is why creating and deleting branches is instant, and why "we do not branch, it is too expensive" (a real thing people say, carried over from older systems) is simply untrue in Git.

HEAD is another pointer, pointing at the branch you are currently on. "Detached HEAD" just means it points directly at a commit instead of at a branch.

Merge or rebase?

both, and the safe rule
# bring main into your branch — safe, always
git switch feature/x
git merge main

# or replay your commits on top of main — tidier history
git rebase main

# after resolving conflicts during a rebase:
git add <files>
git rebase --continue
# or, at any point:
git rebase --abort            # puts everything back. Nothing is lost.
Line by line
  • git merge main — brings main into your branch and creates a merge commit. Safe, always: it adds history rather than rewriting it.
  • git rebase main — replays your commits on top of main, producing a linear history. Each commit is rewritten, so they get new hashes.
  • The rule that keeps you safe: never rebase a branch other people have pulled. Rewriting shared history forces everyone else into a recovery they did not ask for.
  • git add <files> then git rebase --continue — note there is no commit step. Staging the resolution is what tells the rebase to proceed.
  • A rebase conflicts per commit, so a long branch can present the same conflict repeatedly — which is the honest argument for merging instead.
  • git rebase --abort — puts everything back, and nothing is lost. Worth knowing before you start, because it turns a rebase from frightening into reversible.
⚠ The golden rule of rebasing

Never rebase a branch that someone else has pulled. Rebasing creates new commits with new hashes, so a colleague’s copy and yours no longer share history — and their next pull produces a horrible tangle of duplicated commits.

Rebase your own unpushed work freely. On a shared branch, merge. If you must force-push your own feature branch after a rebase, use --force-with-lease, which refuses if someone else pushed in the meantime. Plain --force silently destroys their work.

Conflicts

A conflict is not an error. It is Git saying "two people changed the same lines and I will not guess."

what you see, and what to do
<<<<<<< HEAD
    var total = lines.Sum(l => l.Price * l.Quantity);
=======
    var total = lines.Sum(l => l.NetPrice) * (1 + vatRate);
>>>>>>> feature/vat
Line by line
  • These seven-character markers are inserted into your file by git. They are not a special format to learn; the file is now invalid text that you must edit.
  • <<<<<<< HEAD — the start of your side. HEAD is where you currently are.
  • ======= — the divider. Above it yours, below it theirs.
  • >>>>>>> feature/vat — the end, labelled with where the other change came from.
  • During a rebase the sides are swapped from what you expect, because your commits are being replayed onto theirs. That is why "HEAD" is worth reading rather than assuming.
  • The example is a real conflict, not a textual one. One side sums gross prices, the other applies VAT to net ones. No tool can merge that, because the answer requires knowing which is correct.
# Above the ======= is YOUR side; below it is theirs.
# Edit the file into what it should ACTUALLY be — often neither version —
# delete all three markers, then:
git add src/Order.cs
git commit                    # or: git rebase --continue

git merge --abort             # escape hatch: undo the whole merge
Line by line
  • "Often neither version" is the important sentence. Two people changed the same line for different reasons, and the right result is frequently a third thing.
  • Delete all three markers. Leaving one behind commits <<<<<<< into the source, and it compiles nowhere — which is at least a fast failure.
  • git add src/Order.cs — staging is how you declare the conflict resolved. Until then git refuses to continue.
  • git commit with no message — for a merge, git supplies one. For a rebase you use --continue instead.
  • git merge --abort — the escape hatch. Undoes the whole merge and returns you to before it started.
  • Build and run the tests after resolving. A conflict resolved into something that compiles is not the same as one resolved correctly.

The most common mistake is resolving mechanically — picking one side to make the markers go away — without reading what the other person was trying to do. A conflict is a conversation, and sometimes the honest resolution is to walk over and ask.

Undoing things

The table people actually need. Note which of these are safe.

git reflog — the command that saves you

Git records every position HEAD has held, including ones no branch points at any more. A bad reset --hard, a rebase gone wrong, a branch deleted by mistake — almost all of it is recoverable for about 90 days: 

git reflog                    # find the commit you were on before the mistake
git reset --hard HEAD@{3}     # go back to it
Line by line
  • git reflog — the undo history, and the single most useful command in this chapter. It records every position HEAD has held, including commits no branch points at any more.
  • HEAD@{3} — "where HEAD was three moves ago". The reflog lists them with what each move was, so you can read rather than guess.
  • git reset --hard HEAD@{3} — move the branch back and match the working tree to it. --hard discards uncommitted changes, so commit or stash first.
  • Almost nothing in git is truly lost. A bad reset, a deleted branch, a botched rebase — the commits survive in the reflog for weeks. Knowing this converts most git panic into a two-command fix.
  • The exception is genuinely uncommitted work. The reflog records commits, so anything never committed is gone — which is an argument for committing early and tidying later.

Knowing this exists is the difference between a bad ten minutes and a lost day. It is also a genuinely good thing to mention when asked about Git.

Line by line
  • Subject line, blank line, body. The blank line is structural: git treats the first line as the subject everywhere, and without the blank line the whole message becomes one.
  • Imperative mood — "Fix", not "Fixed" or "Fixes". It completes the sentence "this commit will…", which is the convention git's own tooling uses.
  • About 50 characters, and no full stop. It appears in git log --oneline, in blame views and in pull request lists.
  • The body explains WHY. The diff already shows what changed; it cannot show that the discount was subtracted in two places. That is the sentence a colleague needs in eighteen months.
  • Wrap the body at ~72 characters. Git does not wrap it for you, and terminals indent it.
  • Fixes #482 — GitHub closes the issue when this merges, and links the two permanently. Free traceability for one line.

Subject in the imperative, under about 50 characters, no full stop. Blank line. Body explaining why, because the what is already in the diff. Six months from now, this message is the only record of the reasoning.

.gitignore — for .NET, the essentials
bin/
obj/
.vs/
*.user
appsettings.Development.json    # if it contains anything real
*.env
Line by line
  • .gitignore is patterns, one per line. A trailing / means a directory.
  • bin/ and obj/ — build output, regenerated every time. Committing them causes conflicts on binary files nobody can resolve.
  • .vs/ and *.user — per-developer IDE state. * is a wildcard.
  • appsettings.Development.json — and the comment is the judgement. Ignore it only if it contains anything real; a template with no secrets is better committed, so a new colleague can run the project.
  • # — a comment in a .gitignore.
  • Ignoring does not untrack. A file already committed stays tracked forever; git rm --cached is needed, and the secret remains in history until it is rewritten. Rotate the credential rather than trusting the deletion.
⚠ A committed secret is a leaked secret

Deleting it in the next commit does not help — it remains in the history, and if it was pushed, in everyone’s clone. The only correct response is to rotate the credential immediately, and then, separately, consider rewriting history. Say it in that order in an interview; the rotation is the part that matters.

Try it yourself

Cause a conflict deliberately, in a scratch folder. Ten minutes, and it removes the fear.

git init conflict-demo && cd conflict-demo
echo "line one" > file.txt
git add . && git commit -m "Initial commit"

git switch -c feature
echo "feature version" > file.txt
git commit -am "Change on feature"

git switch main
echo "main version" > file.txt
git commit -am "Change on main"

git merge feature            # ← conflict. Open the file and look at the markers.
Line by line
  • && — the shell's "only if the previous succeeded". Not git.
  • echo "line one" > file.txt — > overwrites, >> appends. One character between "change the file" and "destroy the file".
  • git commit -am "..." — -a stages every tracked file. It does not pick up new ones, which is why the first commit here needs git add . and the later ones do not.
  • Two branches, one file, one line — the minimum reproduction of a conflict, and it takes about thirty seconds.
  • git merge feature — the conflict. Open the file and look at the markers from the earlier block, in a situation you created deliberately and can throw away.
  • Do this once, before it happens for real. Meeting your first conflict in a shared repository at five o'clock is how people learn to fear the tool instead of using it.

Then, in the same repository:

  1. Resolve it, commit, and read git log --graph --oneline.
  2. git reset --hard HEAD~1 to "lose" the merge, then recover it with git reflog.
  3. Make a commit, push it nowhere, and undo it with reset --soft. Then make another and undo it with revert. Compare the two histories — that comparison is the answer to a common interview question.

Golden rules

  1. Working tree → staging → local repository → remote. Every command moves between two of these.
  2. A branch is a pointer, not a copy. Creating one is free.
  3. Commit small and often. Push when it is coherent.
  4. Subject line imperative and short; the body explains why.
  5. Rebase your own unpublished work. Merge anything shared.
  6. Never rewrite public history. --force-with-lease, never bare --force.
  7. revert to undo something already pushed; reset only locally.
  8. git reflog recovers almost anything. Learn it before you need it.
  9. Read what the other side was doing before resolving a conflict.
  10. Never commit secrets. If you do, rotate the credential first and clean history second.
  11. git status constantly. It is free and it prevents most mistakes.
  12. git add -p makes you read your own diff before anyone else does.

Interview questions

"What is the difference between merge and rebase?"

Merge creates a commit joining two histories and preserves the branch shape; rebase replays your commits on top of another branch, producing new hashes and a linear history. Then the rule that shows judgement: never rebase anything others have pulled.

"reset or revert?"

reset moves the branch pointer and rewrites local history — fine before pushing. revert adds a new commit undoing an old one, which is the only safe option once something is shared.

"You committed a password. What now?"

Rotate the credential immediately — it must be assumed compromised. Then remove it from history with git filter-repo or BFG and force-push with coordination, and add the file to .gitignore with a secret-scanning check in CI. Leading with rotation is what makes the answer credible.

"How do you handle a conflict?"

Read both sides, understand the two intentions, write the version that is actually correct, remove the markers, test it, then continue the merge or rebase. Mention --abort: knowing there is always a way back is what stops people panicking.

"What branching strategy have you used?"

Describe the real one and why it fitted — trunk-based with short-lived branches for continuous deployment, GitFlow where releases are scheduled and old versions supported. Having an opinion, with a reason, beats naming the fashionable one.
