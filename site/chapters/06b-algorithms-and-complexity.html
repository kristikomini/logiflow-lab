Algorithms and complexity worth knowing

You will not be asked to invent a sorting algorithm in a .NET job — the framework's is better than anything you would write. What you are asked is quieter and more important: to notice that a loop inside a loop over a growing list is a time bomb, to pick the collection that makes a slow thing fast, and, in a screening test, to recognise the handful of shapes the puzzles keep reusing. This chapter is the practical algorithms a working developer actually needs, and the interview ones on top.

Why this chapter exists

Chapter 06 gave you the cost table for each collection, and chapter 37 covers the timed screening test as an event. This chapter is the layer between them: the intuition for why those costs are what they are, the one move that turns most accidental slowness back into fast code, and the small set of algorithmic patterns — a frequency map, two pointers, a sliding window — that answer the majority of coding-round questions once you can see them. The goal is not to grind puzzles; it is to never write the accidental O(n²) in the first place, and to not freeze when a test asks for one of five familiar shapes.

Big O: the shape, not the stopwatch

🧒 Simple

Big O answers one question: when the pile of work gets ten times bigger, does the time get ten times bigger, a hundred times bigger, or barely move at all? It is not how many seconds something takes — it is how the seconds grow. Finding a name in a sorted phone book by opening the middle barely grows as the book gets fatter; reading every name to find one grows straight in line with it.

GrowthNameWhat it feels likeWhere you meet it
O(1)constantsame time no matter the sizea dictionary look-up, an array index
O(log n)logarithmichalving each step; barely growsbinary search, a balanced tree, an index seek
O(n)linearten times the data, ten times the timea single pass, a foreach
O(n log n)linearithmica pass, done a log-n number of timesa good sort — OrderBy, List.Sort
O(n²)quadraticten times the data, a hundred times the timea loop inside a loop over the same list

Two rules make Big O usable in practice. Constants and small terms drop out: O(2n + 5) is written O(n), because the shape is what survives as the data grows. And the worst nested loop wins: a method that does an O(n) scan inside an O(n) loop is O(n²), and no amount of tidying the inner loop changes the shape — only removing the nesting does.

The data structure is the algorithm

The single most valuable algorithmic move in day-to-day .NET is not clever code; it is replacing a repeated linear search with a hash look-up. It is the difference between a report that returns instantly and one that times out once the customer table grows — the same example as chapter 06, stated as an algorithm.

O(n×m) becomes O(n + m) by choosing the right collection
// ✗ O(orders × customers): First scans the whole customer list for every single order
foreach (var order in orders)
{
    var customer = customers.First(c => c.Id == order.CustomerId);   // O(customers), every time
    Print(order, customer);
}

// ✓ O(customers + orders): build a look-up once, then every match is O(1)
var byId = customers.ToDictionary(c => c.Id);                       // one pass, O(customers)
foreach (var order in orders)
{
    var customer = byId[order.CustomerId];                          // O(1), hashed
    Print(order, customer);
}
Line by line
  • customers.First(c => c.Id == …) inside the loop — a linear scan of every customer for every order. Ten thousand orders against ten thousand customers is a hundred million comparisons: the accidental O(n²) that passes in testing and dies in production.
  • customers.ToDictionary(c => c.Id) — one pass to build a hash map keyed by id. Hashing means the map jumps straight to the bucket, so a look-up does not depend on how many customers there are.
  • byId[order.CustomerId] — O(1) average. The nested scan is gone; the total is one pass to build plus one pass to use, which is O(n + m), not O(n×m).
  • When you cannot change the shape, change the structure. Reach for Dictionary for "look up by key", HashSet for "have I seen this / is this in the set", and a sorted list with binary search when you also need range or order.
  • The tell in code review is a First, Any, Contains or Where on a List inside a loop over another list. That is almost always a dictionary waiting to be built before the loop.

Searching: linear, and why sorted changes everything

binary search needs sorted data and pays for it with O(log n)
// linear search: works on anything, O(n)
int index = list.FindIndex(x => x == target);

// binary search: needs a SORTED list, but O(log n)
int pos = sorted.BinarySearch(target);
if (pos < 0)
{
    int insertAt = ~pos;          // the bitwise complement is where it WOULD go
    sorted.Insert(insertAt, target); // keeps the list sorted for the next search
}
Line by line
  • FindIndex — a linear scan. It has no requirements and no cleverness: it looks at each element until it finds one, O(n). For a one-off search of an unsorted list, this is the correct answer — sorting first would cost more than the scan you saved.
  • sorted.BinarySearch(target) — halves the search space each step by comparing the middle, so a million items take about twenty comparisons. It only works because the data is sorted; on unsorted data it returns nonsense.
  • ~pos — a detail worth knowing: when the item is absent, BinarySearch returns the bitwise complement of where it belongs, so ~pos is the correct insertion index that keeps the list sorted.
  • The trade is set-up cost against query cost. Sorting is O(n log n) once; each binary search is O(log n). Sort once and search many times and you win; sort to search once and you have lost. This is exactly why a database index exists — chapter 11.
  • Most of the time you do not write either. A Dictionary or HashSet gives O(1) look-up without keeping anything sorted; choose binary search when you also need "nearest", "next larger" or an ordered range.

Sorting: use the framework's, and control it with a comparer

do not hand-roll a sort — steer the built-in one
// ✓ OrderBy is O(n log n), STABLE, and returns a new sequence (deferred)
var ranked = orders
    .OrderByDescending(o => o.Priority)
    .ThenBy(o => o.CreatedAt);

// in place, with a custom rule, when you own the list
orders.Sort((a, b) => a.Priority == b.Priority
    ? a.CreatedAt.CompareTo(b.CreatedAt)
    : b.Priority.CompareTo(a.Priority));
Line by line
  • You will never beat the framework's sort in an application. Array.Sort and List.Sort use introsort — quicksort that falls back to heapsort to avoid the O(n²) worst case — and OrderBy is a stable merge sort. Writing your own is a way to introduce a bug, not to go faster.
  • OrderByDescending(...).ThenBy(...) — LINQ sorting is stable, so equal-priority orders keep their original relative order, and ThenBy breaks ties. It is also deferred: nothing sorts until you enumerate.
  • orders.Sort((a, b) => …) — sorts the list in place using a Comparison<T>. The delegate returns negative, zero or positive for "a before b", "equal", "a after b". Note List.Sort is not stable, unlike OrderBy.
  • A comparer is the Strategy pattern (chapter 05c): you inject the ordering rule into a general sort. The same list sorts by priority, by date or by name depending only on the IComparer<T> you hand it.
  • The trap is an inconsistent comparer — one where "a < b" and "b < a" can both be true because the rule is not a total order. It throws "IComparer.Compare() returned inconsistent results" at runtime, on some inputs and not others.

Recursion, and when it turns into a crash

🧒 Simple

Recursion is solving a problem by solving a smaller version of the same problem, like Russian dolls: to open the big doll you open the one inside, and the one inside that, until you reach the tiny one that opens on its own. That last one is the base case. Forget it and the dolls never end — which, for a computer, means it runs out of shelf and falls over.

the same computation, three ways
// ✗ naive recursion: recomputes the same values exponentially — O(2ⁿ)
long Fib(int n) => n < 2 ? n : Fib(n - 1) + Fib(n - 2);

// ✓ memoised: remember each answer once — O(n)
long Fib(int n, Dictionary<int, long> memo) =>
    n < 2 ? n : memo.TryGetValue(n, out var v) ? v
        : memo[n] = Fib(n - 1, memo) + Fib(n - 2, memo);

// ✓ iterative: no stack growth at all — O(n), O(1) memory
long Fib(int n)
{
    long a = 0, b = 1;
    for (int i = 0; i < n; i++) (a, b) = (b, a + b);
    return a;
}
Line by line
  • The naive version is a trap because it is elegant. Fib(50) recomputes Fib(48) millions of times; the shape is O(2ⁿ) and it hangs. Elegant and slow is still slow.
  • Memoisation stores each answer the first time it is computed and returns the stored one afterwards. One dictionary turns the exponential shape into O(n) — the same "remember instead of recompute" idea as a cache.
  • The iterative version keeps only the last two values and loops, so it uses constant memory and never grows the call stack. When recursion depth could be large, convert to a loop or an explicit Stack<T>.
  • Deep recursion overflows the stack. C# has no general tail-call optimisation you can rely on, so a recursion that could go tens of thousands deep — walking a huge tree, a long linked list — risks a StackOverflowException, which cannot be caught and takes the process down.
  • Turning "recompute" into "remember" is dynamic programming in one sentence. Most DP interview questions are a naive recursion plus a memo, arrived at in exactly these two steps.

The interview shapes that keep coming back

Chapter 37 lists these as "the shapes that keep coming back". Here they are as C#. Recognising which shape a puzzle is drives ninety percent of the coding round; the rest is not panicking.

a frequency map and a seen-set solve a surprising share of them
// FREQUENCY MAP: "most common", "appears more than once", "is it an anagram" — count with a Dictionary
var counts = new Dictionary<char, int>();
foreach (char ch in text)
    counts[ch] = counts.GetValueOrDefault(ch) + 1;

// SEEN-SET: "first duplicate", "contains a pair that…" — remember what you have passed, O(n)
var seen = new HashSet<int>();
foreach (int x in numbers)
    if (!seen.Add(x)) return x;      // Add returns false if it was already there

// TWO POINTERS: on a SORTED array, walk in from both ends — O(n), no nested loop
int lo = 0, hi = arr.Length - 1;
while (lo < hi)
{
    int sum = arr[lo] + arr[hi];
    if (sum == target) return (lo, hi);
    if (sum < target) lo++; else hi--;
}
Line by line
  • Frequency map — any question about counting, duplicates, "most common" or anagrams is a Dictionary of item to count. GetValueOrDefault avoids the "is the key there yet" branch. One pass, O(n).
  • Seen-set — HashSet.Add returns false when the value was already present, so "find the first repeat" is a single loop with a set, O(n), instead of the nested-loop O(n²) that first comes to mind.
  • Two pointers — on sorted data, a pointer at each end moving toward the middle replaces a double loop. "Two numbers that sum to a target" drops from O(n²) to O(n) because each step rules out a whole row of the pair grid.
  • The unnamed fourth is the sliding window: a start and end pointer that expand and contract over a run — "longest substring without a repeat", "smallest window that contains all of X". It is the two-pointer idea over a contiguous range.
  • The meta-skill is classification. Before writing anything, ask which of these the question is. Almost every screening puzzle is a frequency map, a set, two pointers, a sliding window, or a tree/graph walk — and knowing which one is most of the answer.
Trees and graphs, in one breath

You meet trees and graphs more than you think — a folder tree, an org chart, a dependency graph, the DOM. The two ways to walk them are breadth-first (a Queue: level by level, and the shortest path in an unweighted graph) and depth-first (a Stack, or recursion: all the way down one branch first). Swapping the queue for a stack turns one into the other. For anything with weights or "shortest / cheapest", the name to reach for is Dijkstra, and the honest interview answer is usually "I would use a library rather than reimplement it".

⚠ The algorithmic bug hiding in LINQ

LINQ is deferred, so a query is re-run every time you enumerate it. Calling .Count() and then foreach-ing the same IEnumerable runs the whole thing twice; doing that inside a loop quietly rebuilds an O(n) query into O(n²). If you enumerate a query more than once, ToList() it first so the work happens once. And a .Where(...).Count() that only needs "is there any" should be .Any(...), which stops at the first match instead of counting them all.

Exercises, with the reasoning shown

Exercise 1 — the report that got slower every month

var result = new List<Row>();
foreach (var sale in sales)                                   // n sales
{
    var product = products.Single(p => p.Sku == sale.Sku);   // scans m products
    result.Add(new Row(sale, product));
}
O(n×m): fine with a hundred products, a timeout with fifty thousand.
  • products.Single(p => p.Sku == sale.Sku) is a full scan of the product list for every sale, so the cost is sales times products. It was fast in the demo because both lists were tiny, and it fell over in production because one of them grew. Build the look-up once before the loop: var bySku = products.ToDictionary(p => p.Sku);, then bySku[sale.Sku] inside it. The shape drops from O(n×m) to O(n + m), and the report is instant again. The general lesson: a Single/First/Where over a list inside a loop is the signature of an accidental quadratic.

Exercise 2 — the recursion that overflowed the stack

long Sum(Node? node) =>
    node is null ? 0 : node.Value + Sum(node.Next);   // a linked list of 100,000 nodes
StackOverflowException — one stack frame per node, and it cannot be caught.
  • Each call to Sum waits for the next before it can add, so a hundred thousand nodes means a hundred thousand nested stack frames, and the stack is not that deep. C# will not optimise this tail call away, and a StackOverflowException takes the whole process down — you cannot catch it. Rewrite it as a loop: long total = 0; for (var n = node; n is not null; n = n.Next) total += n.Value; return total;. Same O(n) time, but O(1) stack. Recursion is for depth that is bounded and small — a balanced tree is about log n deep, which is fine; a list or a degenerate tree is not.
Try it yourself

Write "two numbers in an array that add up to a target" three ways and watch the shape change. First the obvious double loop — O(n²). Then sort the array and use two pointers — O(n log n) for the sort plus O(n) for the walk. Then use a seen-set in one pass — O(n), and it does not need the array sorted. Time all three on a large random array and notice that the O(n) version is not just faster, it is a different curve: doubling the input barely moves it. 

// one pass, a set of "numbers I have already seen", O(n)
(int, int)? TwoSum(int[] nums, int target)
{
    var seen = new Dictionary<int, int>();     // value → its index
    for (int i = 0; i < nums.Length; i++)
    {
        int need = target - nums[i];
        if (seen.TryGetValue(need, out int j)) return (j, i);
        seen[nums[i]] = i;
    }
    return null;
}
Line by line
  • For each number, ask whether the value that would complete the pair has already been seen — a dictionary look-up, O(1).
  • seen[nums[i]] = i records the current number and its index after the check, so a number is never paired with itself.
  • One pass, O(n), and no sort needed — the set does the work the second loop used to do, which is the whole "data structure is the algorithm" idea in eight lines.

Golden rules

  1. Big O is about growth, not seconds. Constants drop out, and the worst nested loop decides the shape.
  2. A search or Contains on a list inside a loop is an accidental O(n²). Build a Dictionary or HashSet before the loop and it becomes O(n).
  3. Binary search buys O(log n) but demands sorted data. Sort once, search many; a hash look-up is simpler when you do not also need order.
  4. Never hand-roll a sort. OrderBy is stable and deferred; List.Sort is in place and not stable; steer both with an IComparer<T>, which is Strategy.
  5. A naive recursion that recomputes is exponential. Add a memo to make it O(n); that is dynamic programming.
  6. Deep recursion overflows an uncatchable stack. Convert unbounded depth to a loop or an explicit Stack<T>.
  7. Classify the puzzle first. Frequency map, seen-set, two pointers, sliding window, or a tree/graph walk covers most screening questions.
  8. Do not enumerate a LINQ query twice. ToList() it if you will, and use Any() when you only need to know that something exists.

Interview questions

"This loop calls list.First(...) inside a foreach over another list. What is wrong, and how do you fix it?"

It is an accidental O(n×m): First scans the inner list for every item of the outer one, so the cost is the product of the two sizes. It looks fine in testing because the lists are small and becomes a timeout when one of them grows. I fix it by building a Dictionary keyed by the match field once, before the loop, and doing an O(1) look-up inside it — total O(n + m). That single move, replacing a repeated linear search with a hash look-up, is the most common performance fix I make in real code.

"What does O(log n) mean, and where does it come from?"

It means the work is halved at each step, so the number of steps grows like the logarithm of the size: a million items take about twenty steps, a billion about thirty. It comes from repeatedly discarding half the remaining possibilities — binary search on a sorted array, descending a balanced tree, a database seeking through a B-tree index. The practical point is that O(log n) is almost as good as constant time for any realistic size, which is why sorted structures and indexes are worth their upkeep.

"When would you use recursion, and when would you avoid it?"

I use it when the problem is naturally self-similar and the depth is bounded and small — walking a balanced tree, which is about log n deep, or parsing nested structure. I avoid it, or convert it to a loop, when the depth could be large: a long linked list or a skewed tree can be tens of thousands deep, and C# does not guarantee tail-call optimisation, so it overflows the stack — and a StackOverflowException cannot be caught, it kills the process. If a recursion recomputes the same sub-answers I add a memo, which turns exponential work into linear and is the essence of dynamic programming.

"Should you write your own sorting algorithm?"

Almost never in application code. Array.Sort and List.Sort use introsort, which is quicksort with a heapsort fallback to avoid the quadratic worst case, and OrderBy is a stable merge sort. I will not beat them, and hand-rolling one is a way to add a bug. What I do write is the comparison — an IComparer<T> or a ThenBy chain — to say what "sorted" means for my data. Knowing the sort algorithms by name matters for the interview; using the framework's matters for the job.

"Perché una Dictionary rende veloce un codice lento?"

Perché sostituisce una ricerca lineare ripetuta con una ricerca a chiave in tempo costante. Il caso classico è un ciclo che, per ogni elemento, cerca il corrispondente in un'altra lista con First o Where: è O(n×m), e diventa un timeout quando i dati crescono. Costruisco una Dictionary una volta sola prima del ciclo — O(n) — e poi ogni corrispondenza è O(1) grazie all'hashing, quindi il totale è O(n + m). È la stessa idea di un indice sul database: pagare una volta per cercare tante volte in fretta.
