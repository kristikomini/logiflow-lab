Single-page apps: Angular and React

Chapter 17 gave you the DOM and fetch. This one is what happens when a team decides the browser should stop asking for pages and start asking for data. You are not going to become a front-end specialist here — the goal is to be the backend developer who can read the front end, fix the screen their own API feeds, and design a contract the other half does not hate.

Why this chapter exists

Search Bologna job adverts for .NET and you will find Angular beside it more often than Razor. Companies like BIP, Deda and Software Partner Italia advertise Angular, React and TypeScript for enterprise web work, and plenty of "backend" roles in the region are quietly full-stack. Being able to say "I have consumed my own API from an Angular app and I know where the contract breaks" is worth far more than a framework certificate.

What a single-page app actually is

🧒 Simple

Old way: every time you turn a page in a book, someone takes the whole book away and brings you a new book, printed from scratch, with one page different.

New way: you get the book once, and when you want a new page, someone just hands you the words for that page and you write them in. Much faster after the first time — but getting that first book takes longer, because it is a big book.

🎓 Professional

A single-page application loads one HTML shell plus a JavaScript bundle. After that, the browser never requests another page: routing happens client-side, and every interaction that needs data calls your API and receives JSON. The framework re-renders the affected part of the DOM.

What you gain: an app-like feel, no full-page flash, and a clean separation where the back end serves only data. What you pay: a build step, a larger first load, client-side state management, worse SEO by default, and two deployables instead of one — which is the part that surprises .NET developers used to shipping one artefact.

Components, the one idea both share

🧒 Simple

A component is a Lego brick that knows how to draw itself. You tell it "you are an order row, here is the order", and it produces the little piece of screen for that order. Put fifty of them in a list and you have a table — but you only ever described one row.

🎓 Professional

A component is a unit of UI with its own state, its own template and a declared input contract. You describe what the screen should look like for a given state, and the framework works out the DOM operations. That is the shift from chapter 17: you stop writing document.createElement and start describing the result.

Angular and React disagree about almost everything except this. Angular is a full framework — TypeScript by default, dependency injection, routing, HTTP and forms in the box, opinionated structure. React is a library — you assemble routing, data fetching and state from the ecosystem yourself. Angular is more common in Italian enterprise and consulting work; React dominates product companies and startups.

Angular — a class, a template, and typed injection
export interface OrderDto {
  id: string;
  orderNumber: string;
  total: number;
  status: 'Draft' | 'Submitted' | 'Cancelled';  // mirrors the C# enum
}

@Component({
  selector: 'app-order-list',
  standalone: true,
  imports: [CommonModule],
  template: `
    @if (loading()) { <p>Caricamento…</p> }
    @for (order of orders(); track order.id) {
      <tr><td>{{ order.orderNumber }}</td><td>{{ order.total | currency:'EUR' }}</td></tr>
    }
  `
})
export class OrderListComponent {
  orders = signal<OrderDto[]>([]);
  loading = signal(true);

  // Constructor injection — the same idea as ASP.NET Core's DI.
  constructor(private http: HttpClient) {
    this.http.get<OrderDto[]>('/api/orders')
      .subscribe(o => { this.orders.set(o); this.loading.set(false); });
  }
}
React — a function that returns markup
export function OrderList() {
  const [orders, setOrders] = useState<OrderDto[]>([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch('/api/orders')
      .then(r => r.json())
      .then(o => { setOrders(o); setLoading(false); });
  }, []);                       // [] = run once. Forget it and you loop forever.

  if (loading) return <p>Caricamento…</p>;
  return <>{orders.map(o => <tr key={o.id}><td>{o.orderNumber}</td></tr>)}</>;
}

Read both. The shape is the same: some state, a fetch, a loop that renders one item. If you can follow this much you can open a ticket in either codebase, which is genuinely all a backend role requires.

In development the front end runs on its own port and your API on another, which means the browser sees two origins and applies the same-origin policy. There are two ways out, and only one of them is right:

development: proxy, do not widen CORS
// angular.json / proxy.conf.json — the dev server forwards /api to .NET,
// so the browser only ever sees ONE origin and CORS never enters the picture.
{
  "/api": { "target": "https://localhost:7001", "secure": false }
}

The wrong fix is AllowAnyOrigin() on the server so the error goes away in development — and then shipping it. See the CORS trap in chapter 15: it is a browser rule about who may read your responses, and widening it protects nothing while exposing everything.

The contract, and the trick worth knowing

The interesting part of this chapter for a .NET developer is not the framework. It is that your C# DTOs and their TypeScript interfaces are the same types written twice, and the second copy silently rots. Rename Total to GrandTotal in C# and nothing breaks at compile time; it breaks in the browser, as undefined, in front of a user.

generate the client from OpenAPI instead of writing it
# Your API already publishes a schema (chapter 14). Use it.
npx nswag openapi2tsclient \
  /input:https://localhost:7001/swagger/v1/swagger.json \
  /output:src/app/api/logiflow-client.ts \
  /template:Angular

# now a C# rename breaks the TypeScript BUILD, not the user's screen

Wire that into CI and the contract becomes machine-checked. This is a genuinely strong thing to mention in an interview, because it shows you think about the seam between two teams rather than only about your own side of it.

⚠ Where to put the token

The reflex is localStorage.setItem('token', jwt). It is readable by any script on the page, so a single compromised npm dependency or an XSS hole exfiltrates it. The safer pattern for a first-party SPA is an httpOnly, Secure, SameSite cookie issued by your own backend — JavaScript cannot read it at all — with antiforgery protection, because cookies bring CSRF back (chapter 16).

Know the trade-off rather than a slogan: cookies need same-site or a proper CORS setup and CSRF defence; localStorage needs you to be certain about every script you ship. Say which one you chose and why.

⚠ The client-side N+1

A list renders fifty rows, and each row component fetches its own customer name. Fifty HTTP calls where one would do. It is exactly the EF Core N+1 problem wearing different clothes, and the fix is the same: shape the response for the screen. Design one endpoint that returns the rows already joined, rather than a "pure" resource per entity.

Try it yourself
npm create vite@latest logiflow-ui -- --template react-ts
# or: npx @angular/cli new logiflow-ui --standalone --style css
cd logiflow-ui && npm install && npm run dev

Point it at the running API from chapter 14 and render a list of orders. Then do the experiment that teaches the lesson: rename a property on the C# DTO, rebuild the API, refresh the browser. Nothing errors — a column just goes blank. Now regenerate the TypeScript client from the OpenAPI document and watch the same rename become a red squiggle before you ever open a browser. That difference is the entire argument for generating the client.

Golden rules

  1. An SPA is one shell plus JSON. The server stops producing HTML.
  2. Two deployables, two build pipelines, one contract between them.
  3. Components describe the result for a given state; the framework does the DOM.
  4. Angular ships batteries and structure; React ships a renderer and choices.
  5. In development, proxy /api through the dev server. Never widen CORS to fix a local error.
  6. Generate the TypeScript client from OpenAPI. A hand-written copy of your DTOs will drift.
  7. Shape endpoints for screens, or you get an N+1 in the browser instead of the database.
  8. Prefer an httpOnly cookie to localStorage for tokens — and then handle CSRF.
  9. node_modules is a supply chain. Commit the lock file and read what you add.
  10. An SPA needs JavaScript and is poor for SEO by default. Public content may not want one.
  11. Know enough to read the front end and fix your own screen. That is the bar for a backend role.
  12. If the screen behaves like a document, server-rendering is not the old way — it is the right way.

Interview questions

"Hai esperienza con Angular o React?"

Answer at the level that is true and useful: "I have built and consumed my own API from a small Angular front end — components, HTTP, routing. I am not a front-end specialist, but I can read a component, follow where data comes from, and fix a screen that my endpoint feeds." That is exactly the level most .NET adverts in Bologna are actually asking for, and it is much stronger than an overclaim they will test.

"How do you keep the front end and back end in sync?"

Generate the client from the OpenAPI document rather than hand-writing interfaces, and run that generation in CI. Then explain the failure it prevents: rename a C# property and the TypeScript build breaks, instead of a column silently rendering as undefined in production. Very few juniors have thought about this.

"You get a CORS error in development. What do you do?"

Proxy /api through the front-end dev server so the browser sees one origin. Say explicitly what you do not do: add AllowAnyOrigin to make the message go away. Then show you know what CORS is — a browser rule about who may read a response, not a server-side protection — which is the real question underneath.

"Where would you store the JWT in a browser app?"

Prefer an httpOnly Secure SameSite cookie issued by your own backend, because scripts cannot read it, and pair it with antiforgery since cookies reintroduce CSRF. localStorage is convenient and readable by any script you ship, including dependencies. State the trade-off rather than a rule; that is what they are listening for.

"When would you not build an SPA?"

When the screen is a document rather than an application: public content that needs SEO, a form-heavy internal tool, anything where a second build pipeline and a second deployable is cost without benefit. Add the alternatives you would reach for instead — Razor Pages, MVC, or Blazor — since that shows the answer is judgement, not preference.
