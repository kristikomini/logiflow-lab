Enums, and naming a fixed set

An enum is a type whose values are a list of names you wrote down. It is the smallest piece of design in the language: the moment a field can only be one of four things, an enum turns a magic number into a word the compiler checks, and turns a comment explaining that 3 means "picked" into a thing that cannot be got wrong.

Why this chapter exists

Every line-of-business application is full of small closed sets — order status, shipping mode, unit of measure, priority, error category — and every one of them starts life as an int with a comment, or a string compared against a literal. Both work, both drift, and both produce the bug where a status nobody expected reaches a switch that has no branch for it. Enums are also where three subtleties live that catch people in interviews: an enum is not actually restricted to its named values, its numbers are a storage contract, and [Flags] is a different thing wearing the same syntax.

Declaring one, and what it really is

🧒 Simple

An enum is a list of allowed answers with names. Instead of writing "the status is 3" and keeping a note somewhere saying what 3 means, you write OrderStatus.Picked, and nobody has to find the note. 

public enum OrderStatus
{
    Draft     = 0,      // the default — worth making it a real, sensible state
    Submitted = 1,
    Picked    = 2,
    Packed    = 3,
    Dispatched= 4,
    Cancelled = 99,     // deliberately far away: room to add states before it
}

OrderStatus s = OrderStatus.Picked;

if (s == OrderStatus.Picked) { }             // readable, and the compiler checks the name
int stored = (int)s;                         // 2 — an explicit cast, both directions
OrderStatus back = (OrderStatus)2;           // Picked
string name = s.ToString();                  // "Picked"
Line by line
  • An enum is an int underneath, with names attached at compile time. That is why casting works in both directions and why it costs nothing at run time — an enum is a value type with no allocation and no indirection.
  • Assign the numbers explicitly. Left implicit they start at 0 and count up, which means inserting a member in the middle silently renumbers everything after it — and every row already stored in the database now means something different. This is the single most expensive enum mistake and it is completely invisible in a diff.
  • Draft = 0 — zero is the default value of the enum, the one a field gets when nobody assigned it, and the one a database column gets on a NOT NULL DEFAULT 0. Give it to a state that is genuinely the starting point, or to an explicit Unknown. Leaving zero unnamed means the default value is a value with no name.
  • Cancelled = 99 — leaving a gap so new states can be added in order later without renumbering. Cheap now, priceless in two years.
  • ToString() on an enum uses reflection and is slower than you would guess. Inside a loop over a hundred thousand rows it shows up in a profile; nameof or a switch expression does not.
⚠️ An enum variable is not limited to its named values

(OrderStatus)57 compiles, runs, and gives you an OrderStatus whose ToString() is "57". The compiler only checks names you write as names; a cast from an int — from a database column, a JSON payload, a query string — is unchecked. That is exactly how a value with no case reaches a switch. Validate anything cast from outside with Enum.IsDefined, and give every switch a default.

Switching on one, exhaustively

string Describe(OrderStatus s) => s switch
{
    OrderStatus.Draft      => "not submitted yet",
    OrderStatus.Submitted  => "waiting for the warehouse",
    OrderStatus.Picked or
    OrderStatus.Packed     => "in the warehouse",
    OrderStatus.Dispatched => "with the courier",
    OrderStatus.Cancelled  => "cancelled",
    _ => throw new ArgumentOutOfRangeException(nameof(s), s, "Unknown status"),
};

// and the guard for a value that came from outside
if (!Enum.IsDefined(status))
    return BadRequest($"{(int)status} is not a valid status.");
Line by line
  • A switch expression returns a value, so every path must produce one — which is why the _ arm is mandatory. That is the compiler forcing the question "what about the ones you did not list".
  • Throw in the default rather than returning a fallback. A silent "unknown" string turns a new enum member that somebody forgot to handle into a cosmetic oddity on a screen; an exception turns it into a failing test on the day it is added. The second is much cheaper.
  • Picked or Packed — an or pattern, which is how several values share an arm. In the older statement form this is two case labels with no code between them.
  • Enum.IsDefined — the validation for any enum that arrived as a number from outside the program. It uses reflection, so it is not free, but the cost is irrelevant at an API boundary, which is the only place it belongs.
  • C# cannot enforce exhaustiveness over an enum, precisely because of the unnamed-value problem above. That is why the default arm is not optional discipline, it is the only line standing between you and a silent wrong answer.

Text in, text out

// text -> enum, the safe way
if (Enum.TryParse<OrderStatus>(input, ignoreCase: true, out var status)
    && Enum.IsDefined(status))
{
    order.Status = status;
}

// enum -> text
string s1 = status.ToString();               // "Picked"
string s2 = nameof(OrderStatus.Picked);      // "Picked" — a compile-time constant, free

// every member, for a dropdown
foreach (OrderStatus v in Enum.GetValues<OrderStatus>())
    Console.WriteLine($"{(int)v,3}  {v}");
Line by line
  • Enum.TryParse succeeds on a number. Give it the string "57" and it returns true with an OrderStatus of 57, which is why the IsDefined check is chained on. Together they are the correct parse; separately, each is insufficient.
  • ignoreCase: true — a named argument, because a bare true at this call site would tell a reader nothing.
  • nameof is resolved at compile time and produces a plain string constant with no reflection at all — and it stops compiling if somebody renames the member, which a string literal does not.
  • Enum.GetValues<T>() is how a dropdown gets its options without anyone maintaining a parallel list. Pair it with a [Display(Name = "…")] attribute when the on-screen wording must differ from the identifier — and it must, as soon as a second language is involved.
  • Never send a raw enum number over an API. The name is self-describing and survives a renumbering; the number means nothing to the caller and silently changes meaning if the enum is edited. Serialise as a string (JsonStringEnumConverter) at the boundary, whatever you store internally.

[Flags]: one value holding several answers

🧒 Simple

Normally an enum answers "which one of these". Sometimes the question is "which of these, possibly several" — a courier that is both insured and refrigerated. A flags enum stores that set of yes-or-no answers inside a single number, one bit each. 

[Flags]
public enum Handling
{
    None         = 0,
    Fragile      = 1,       // 0001 — powers of two, always
    Refrigerated = 2,       // 0010
    Hazardous    = 4,       // 0100
    Insured      = 8,       // 1000

    ColdChain = Refrigerated | Insured,      // a named combination, quite legal
}

var h = Handling.Fragile | Handling.Insured;    // combine with |   -> 9
bool isFragile = h.HasFlag(Handling.Fragile);   // true
bool fast      = (h & Handling.Fragile) != 0;   // the same test, without boxing
h |= Handling.Hazardous;                        // add one
h &= ~Handling.Insured;                         // remove one
Console.WriteLine(h);                           // "Fragile, Hazardous"
Line by line
  • The values must be powers of two — 1, 2, 4, 8, 16 — so each occupies its own bit and no combination collides. Number them 1, 2, 3 and Fragile | Refrigerated equals Hazardous, and everything downstream is quietly wrong.
  • [Flags] itself changes nothing about the arithmetic. It only tells ToString() to print a comma-separated list rather than a number, and tells a human reader what the type is for. The powers of two are what make it work.
  • None = 0 is required by convention: zero is the default value, and you want it to mean "no flags set" rather than being a real flag. A flag valued zero can never be tested with HasFlag, which always returns true for it.
  • ~ is bitwise NOT, so h &= ~Insured keeps every bit except that one — the idiom for removing a flag.
  • HasFlag boxes its argument and is noticeably slower than the & test. Irrelevant in ordinary code, worth knowing if it turns up in a tight loop.
⚠️ HasFlag with a combination asks ALL, not ANY

h.HasFlag(Handling.ColdChain) is true only when both Refrigerated and Insured are set, because it tests whether every bit in the argument is present. For "any of these", use (h & Handling.ColdChain) != 0. The two read almost identically and answer different questions, and the difference only shows up on the rows where exactly one of the flags is set.

Storing one, and the day somebody reorders it

The moment an enum value is written to a database, sent over an API, or put in a message queue, its numbers stop being an implementation detail and become a contract with data you no longer control. 

// EF Core stores an enum as its underlying int by default
public class Order
{
    public OrderStatus Status { get; set; }        // column: int NOT NULL
}

// store the NAME instead — bigger, slower, and readable in a query window
modelBuilder.Entity<Order>()
    .Property(o => o.Status)
    .HasConversion<string>();

// over HTTP, always the name
builder.Services.ConfigureHttpJsonOptions(o =>
    o.SerializerOptions.Converters.Add(new JsonStringEnumConverter()));
Line by line
  • Storing the int is compact and fast, and it makes the numbers a permanent contract: nobody may ever renumber, and an ORDER BY Status sorts by whatever the numbers happen to be. Anyone reading the table sees a 2.
  • Storing the name costs a few bytes and makes the table legible to support staff, which is worth a great deal at 3am. It also changes the failure mode: renaming a member breaks on read with a clear error, rather than silently meaning something else.
  • Never renumber, never reuse, never delete a member. Deleting Packed = 3 does not delete the 3s in the table; it just removes the name for them. Mark it [Obsolete] and leave it where it is.
  • A JsonStringEnumConverter at the API boundary is close to mandatory. Callers read "Dispatched" rather than 4, and your internal numbering stops being part of the public contract.
  • In SQL Server the column is a plain int or nvarchar; there is no enum type to map onto and a CHECK constraint is the nearest equivalent — chapter 09.
When an enum stops being enough

An enum holds a name and a number and nothing else. As soon as each member needs behaviour or extra data — a display label, a colour, a list of statuses it may move to — you end up with a switch over the enum in five places, and every new member means finding all five. That is the signal to move to a class with static readonly instances, or to a dictionary keyed by the enum, or to the strategy pattern from chapter 05. The enum is not wrong; it has simply been asked a question it cannot answer.

Exercises, with the reasoning shown

Exercise 1 — the release that changed every order

// before
enum Status { Draft, Submitted, Picked, Dispatched }
// after — one member inserted
enum Status { Draft, Submitted, Approved, Picked, Dispatched }
Every order in the database that was "Picked" is now "Approved".
  • The values were implicit, so Picked was 2 and is now 3, Dispatched was 3 and is now 4, and the rows storing 2 did not move. Nothing fails, nothing logs, and the error is discovered by a warehouse manager. Always assign values explicitly, and add new members at the end with a new number.

Exercise 2 — the status that matched nothing

var s = (OrderStatus)7;
string text = s switch
{
    OrderStatus.Draft => "draft",
    OrderStatus.Picked => "picked",
};
SwitchExpressionException at run time.
  • The cast was never validated: an enum variable can hold any number its underlying type can hold, named or not. Two things were missing — an Enum.IsDefined check where the value entered the program, and a _ arm that throws with the actual value in the message. The second one turns an unhelpful exception into one that names the 7.

Exercise 3 — the flags that collided

[Flags]
enum Handling { Fragile = 1, Refrigerated = 2, Hazardous = 3, Insured = 4 }

var h = Handling.Fragile | Handling.Refrigerated;
Console.WriteLine(h.HasFlag(Handling.Hazardous));
True — and nothing is hazardous.
  • The values are not powers of two: 1 | 2 is 3, which is exactly Hazardous. Every combination of the first two flags is indistinguishable from the third. [Flags] does not check this for you; it only changes how ToString prints. The values must be 1, 2, 4, 8, and the compiler will never tell you otherwise.

Exercise 4 — the API that broke its clients

// the API returns { "status": 4 }
// six months later somebody adds a member in the middle of the enum
Every client now interprets 4 as the wrong state, and no version number changed.
  • The enum's numbering leaked into the public contract, so an internal refactor became a breaking change with no compile error anywhere — not in your build, and not in theirs. Serialising as a string with JsonStringEnumConverter makes the name the contract, and a rename then fails loudly at deserialisation instead of silently meaning something else.
Try it yourself

Three enums in one file: an ordinary one, a flags one, and the validation both need. Everything here prints something worth seeing. 

public enum OrderStatus { Draft = 0, Submitted = 10, Picked = 20, Dispatched = 30 }

  [Flags]
  public enum Handling { None = 0, Fragile = 1, Refrigerated = 2, Hazardous = 4, Insured = 8 }

  // 1 — an enum is not restricted to its names
  var rogue = (OrderStatus)57;
  Console.WriteLine(rogue);                          // "57"
  Console.WriteLine(Enum.IsDefined(rogue));          // False

  // 2 — TryParse happily accepts a number
  Console.WriteLine(Enum.TryParse<OrderStatus>("57", out var p));   // True
  Console.WriteLine(Enum.TryParse<OrderStatus>("picked", true, out var q)); // True, Picked

  // 3 — flags combine, print and test
  var h = Handling.Fragile | Handling.Insured;
  Console.WriteLine(h);                              // "Fragile, Insured"
  Console.WriteLine((int)h);                         // 9
  Console.WriteLine(h.HasFlag(Handling.Fragile));    // True
  Console.WriteLine(h.HasFlag(Handling.Fragile | Handling.Hazardous));  // False — ALL, not ANY
  Console.WriteLine((h & (Handling.Fragile | Handling.Hazardous)) != 0); // True — ANY

  // 4 — every member, as a dropdown would need them
  foreach (var v in Enum.GetValues<OrderStatus>())
      Console.WriteLine($"{(int)v,4}  {v}");
What each block demonstrates
  • 1 — a cast from an out-of-range number succeeds, and ToString falls back to printing the digits. Enum.IsDefined is the only thing that knows the difference.
  • 2 — TryParse returning true for "57" is why it must be paired with IsDefined; the second call shows the case-insensitive overload doing what you would want.
  • 3 — combining with | gives 9, and the two HasFlag lines are the all-versus-any distinction that the bitwise test answers differently.
  • 4 — GetValues is the dropdown, with the stored number beside each name so the storage contract is visible.
  • The gaps in the numbering — 0, 10, 20, 30 — are the room to insert a state later without renumbering anything already written to a database.

Then change Picked = 20 to Picked = 21 and imagine the table of ten million orders that still contains 20. That is the whole argument for treating an enum's numbers as permanent the moment anything outside the program has seen one.

Golden rules

  1. Use an enum the moment a field can only be one of a fixed set. It replaces a magic number and the comment explaining it with a name the compiler checks.
  2. Assign every value explicitly. Implicit numbering means inserting a member in the middle silently renumbers the rest, and the rows already stored do not move.
  3. Give zero a real meaning. It is the default for an unassigned field and a DEFAULT 0 column, so make it Draft, None or Unknown — never leave it unnamed.
  4. An enum variable is not limited to its named values. A cast from an int is unchecked, so validate anything from outside with Enum.IsDefined.
  5. Every switch over an enum needs a default that throws. C# cannot check exhaustiveness, and a silent fallback hides the member somebody forgot to handle.
  6. Enum.TryParse accepts numbers too, so pair it with IsDefined or it will happily return a status of 57.
  7. [Flags] values must be powers of two. The attribute only changes ToString; nothing checks the numbering, and colliding values are undetectable afterwards.
  8. HasFlag with a combination asks "all of these", not "any". For any, use (value & mask) != 0.
  9. Never renumber, reuse or delete a member once it has been stored. Mark it [Obsolete] and leave the number where it is.
  10. Serialise as the name at every boundary. A number over an API makes your internal numbering part of somebody else's contract.
  11. When members start needing behaviour or extra data, the enum has outgrown itself. Five switches over the same enum is the signal to move to a class or a dictionary.

Interview questions

"What is an enum, and what is it underneath?"

A value type whose allowed values are a set of named constants, backed by an integral type — int unless you say otherwise. That is why casting works both ways and why it costs nothing at run time. The important consequence is that the names are a compile-time convenience rather than a run-time restriction: (OrderStatus)57 is perfectly legal and gives you a value with no name, which is how an unhandled state reaches a switch. So I validate anything cast from outside with Enum.IsDefined, and I always assign the numbers explicitly, because implicit numbering makes inserting a member in the middle a silent data-corrupting change.

"What does [Flags] do?"

Almost nothing, which is the point worth making. It is a hint: it changes ToString() to print a comma-separated list of the set members instead of a number, and it tells a reader the type is a bit set. What actually makes a flags enum work is that the values are powers of two, so each occupies its own bit and combinations with | do not collide. The attribute does not enforce that, so an enum numbered 1, 2, 3 with [Flags] on it is broken in a way nothing will ever report. I also watch HasFlag with a combined argument, because it tests for all of the bits rather than any of them.

"How would you store an enum in a database?"

Either way works, and the choice is about the failure mode. As an int it is compact and fast, but the numbers become a permanent contract — nobody may renumber, and the table is unreadable to anyone without the source. As a string it costs a few bytes and makes the data legible in a query window at three in the morning, and a rename then fails loudly on read rather than silently meaning something else. In EF Core that is one HasConversion<string>() call. Either way the rule is the same: once a value has been written, never renumber, reuse or delete a member — mark it obsolete and leave it.

"Why not just use a string or an int for a status?"

Because neither is checked. With an int, nothing stops a 7 and nothing tells a reader what 2 means; with a string, nothing catches "Dispatced", and every comparison needs a StringComparison decision you will eventually get wrong. An enum gives you compile-time names, IntelliSense at every call site, a compiler error when a member is renamed, and a single place where the set is defined. The honest limit is that it holds only a name and a number — once each member needs a label, a colour or a set of legal transitions, I would move to a class with static instances rather than maintain five switch statements.

"Cosa succede se aggiungi un valore in mezzo a un enum già in produzione?"

Se i valori sono impliciti, tutti quelli dopo si rinumerano e i dati già salvati cambiano significato senza che niente fallisca: un ordine che era "Picked" diventa un altro stato e se ne accorge il magazzino, non il compilatore. Per questo assegno sempre i numeri esplicitamente e i membri nuovi li aggiungo in fondo con un numero nuovo, lasciando dei buchi fra i valori proprio per poterlo fare. E un membro già usato non lo rinomino, non lo riciclo e non lo cancello: lo marco [Obsolete] e resta lì, perché cancellarlo non cancella i numeri già scritti nel database.
