Exceptions, from the ground up

Chapter 07 covers exceptions the way an interviewer asks about them — filters, rethrow, the stack trace — from inside a chapter about async. This one is the ladder underneath: what an exception actually is, the hierarchy and which types you are allowed to throw, try/catch/finally and the order it runs in, writing your own exception type, and the far more important question of when not to throw at all.

Why this chapter exists

Error handling is where inexperience shows fastest. A catch (Exception) { } with an empty body turns a crash into a wrong answer, which is strictly worse. A throw ex; destroys the only evidence of where the problem was. An exception used for "customer not found" makes a normal code path cost a thousand times what it should. None of these produce a compiler warning, all of them appear in real codebases, and a reviewer spots each of them instantly.

What an exception actually is

🧒 Simple

When a method cannot do what it was asked, it has two ways to say so: hand back an answer meaning "no", or stop and shout. Shouting is an exception. It abandons the current work immediately and travels back up through everyone who called you, until somebody catches it — and if nobody does, the program ends.

🎓 Professional

An exception is an object carrying a message, a stack trace and optionally an inner exception, thrown onto a stack that then unwinds frame by frame until a matching handler is found. The unwinding is the expensive part — capturing the stack and walking it costs on the order of microseconds, thousands of times a plain return — which is why exceptions must be reserved for the genuinely exceptional. The other half of that rule is about meaning, not cost: an exception says "this method's contract could not be honoured", and "no customer has that id" honours the contract perfectly well. 

Order Get(int id)
{
    if (id <= 0)
        throw new ArgumentOutOfRangeException(nameof(id), id, "Id must be positive.");

    return _db.Orders.Find(id)
        ?? throw new OrderNotFoundException(id);      // throw as an EXPRESSION
}

// what the caller sees when nobody catches it:
// OrderNotFoundException: Order 4711 was not found.
//    at LogiFlow.Orders.OrderService.Get(Int32 id) in OrderService.cs:line 42
//    at LogiFlow.Api.OrderEndpoints.GetById(Int32 id) in OrderEndpoints.cs:line 17
Line by line
  • nameof(id) as the parameter name — a compile-time constant that survives a rename, unlike the string "id". Every argument exception takes the parameter name first; getting that argument order backwards is so common that the framework's own message reads oddly when you do.
  • ?? throw new … — throw as an expression, which is why it can sit on the right of a null-coalescing operator. It is the tidiest way to say "this or fail".
  • The stack trace is captured when the exception is thrown, not when it is caught, and it is the single most valuable thing in the object. Everything in this chapter about throw; versus throw ex; is about not destroying it.
  • The message is read by a developer at three in the morning. Put the values in it — which id, which file, which limit. "Invalid input" has never once helped anybody.
  • An exception with no handler anywhere ends the process, and in a web application the framework's own top-level handler catches it first and turns it into a 500. That is chapter 14.

The hierarchy, and which ones are yours

Everything derives from Exception. What matters in practice is which ones you should throw, which you should catch, and which you should leave strictly alone.

TypeMeansYours to throw?
ArgumentNullExceptiona required argument was nullyes — at the top of a public method
ArgumentOutOfRangeExceptionan argument was outside its allowed rangeyes
ArgumentExceptionan argument was wrong in some other wayyes, when neither of the above fits
InvalidOperationExceptionthe object is in the wrong state for this callyes — the most useful one
NotSupportedExceptionthis operation is not available hereyes
OperationCanceledExceptiona cancellation token firedno — let it pass, never log it as an error
IOException, SqlException, HttpRequestExceptionthe outside world failedno — catch these
NullReferenceExceptiona bug in your codenever — fix the bug
IndexOutOfRangeExceptiona bug in your codenever
Exceptionnothing in particularnever throw it; catch it only at the very top
StackOverflowException, OutOfMemoryExceptionthe process is finishedcannot be caught usefully
  • InvalidOperationException is the one to reach for most often and the one people forget exists. "You cannot dispatch an order that has no lines" is not a bad argument — the argument was fine — it is a bad state.
  • Never throw a bare Exception. It gives the caller no way to handle your failure specifically, so their only option is catch (Exception), which then swallows everything else too. Your carelessness becomes their bug.
  • NullReferenceException is never something to handle; it is a report that you dereferenced something you had not checked. Catching one hides a defect rather than managing a condition.
  • OperationCanceledException is normal. A user navigated away and the request was cancelled. Logging it as an error fills your alerting with noise, and an overly broad catch (Exception) is usually how it gets there.
  • Since .NET 6, ArgumentNullException.ThrowIfNull(x) and ArgumentOutOfRangeException.ThrowIfNegative(n) exist, and they produce a better message than the version you would write by hand.

try, catch, finally — and the order they run in

try
{
    return Import(path);                     // 1 — runs; if it throws, jump to a catch
}
catch (FileNotFoundException ex)             // 2 — MOST SPECIFIC first
{
    _log.LogWarning(ex, "{Path} was not there", path);
    return ImportResult.Skipped;
}
catch (IOException ex) when (ex.HResult == -2147024864)   // a filter: file in use
{
    return ImportResult.Retry;               // 3 — only entered if the filter is true
}
catch (Exception ex)                          // 4 — broadest LAST, and it rethrows
{
    _log.LogError(ex, "Import of {Path} failed", path);
    throw;                                    // bare throw — keeps the original stack
}
finally
{
    _lock.Release();                          // 5 — ALWAYS runs, return or throw or not
}
Line by line
  • Catch blocks are tested in order, so the most specific must come first. Put catch (Exception) above catch (IOException) and the compiler refuses, because the second could never be reached — one of the few places it protects you from this.
  • when (…) is an exception filter, and it is evaluated before the stack unwinds. That is not a detail: catching an exception to test a condition and then rethrowing loses information that a filter preserves.
  • finally runs whether the block completed, returned, or threw. It is for releasing things, and for nothing else — never return from a finally, which silently discards an exception on its way past.
  • A return inside try still runs the finally, after the return value has been evaluated. That ordering is a favourite puzzle question, and chapter 02d has one.
  • using is try/finally with the finally written for you. If the only thing in your finally is a Dispose, delete the whole construction and write using — chapter 08.
⚠️ throw ex; destroys the evidence

throw ex; resets the stack trace to the line it is written on, so your log points at your own catch block instead of the twelve frames down where the failure happened. A bare throw; rethrows the current exception with its trace intact. There is no case in ordinary code where throw ex; is what you wanted, and the difference is one word that nothing warns you about. If you genuinely need to move an exception across threads with its trace, that is ExceptionDispatchInfo.Capture(ex).Throw().

When not to throw: the most valuable section here

🧒 Simple

A fire alarm is for a fire. If you set it off every time somebody asks for a product you do not stock, two things happen: the building empties constantly, and eventually nobody comes when it really matters. 

// ✗ an exception for an ordinary, expected outcome
Order Get(int id)
{
    var o = _db.Find(id);
    if (o is null) throw new Exception("not found");     // happens 200 times a minute
    return o;
}

// ✓ the Try pattern — failure is a return value
bool TryGet(int id, out Order? order) => (order = _db.Find(id)) is not null;

// ✓ a nullable return, when "not there" needs no explanation
Order? Find(int id) => _db.Find(id);

// ✓ a result object, when the caller needs to know WHY it failed
public readonly record struct Result(bool Ok, Order? Value, string? Error);

// ✓ and validation, which is a list of problems rather than one failure
if (!ModelState.IsValid) return ValidationProblem(ModelState);
Line by line
  • The test is whether the caller could reasonably have expected it. A lookup that misses, a login with the wrong password, a file that has not arrived yet — all expected, all ordinary results. A database that is unreachable, an argument that is null, a state machine in an impossible state — exceptional.
  • TryGet with an out parameter is the framework's own idiom (int.TryParse, Dictionary.TryGetValue) and it is the right shape when the answer is "found it, here it is" or "no".
  • Validation is not an exception, because there is usually more than one problem and the user wants all of them at once. Throwing on the first bad field gives them one error per round trip.
  • The cost is real but secondary: an exception is on the order of a thousand times a plain return. It only matters in a hot path — and "customer not found" on a lookup endpoint is precisely a hot path.
  • The reverse mistake exists too. Do not return null or false for something genuinely broken: a method that swallows a database failure and returns an empty list has turned an outage into silently missing data, which nobody will notice for a week.

Writing your own exception type

Define one when a caller might plausibly want to catch that particular failure and do something specific about it. If nobody would ever write catch (YourException), an existing type with a good message is better. 

public class OrderNotDispatchableException : InvalidOperationException
{
    public int OrderId { get; }
    public string Reason { get; }

    public OrderNotDispatchableException(int orderId, string reason)
        : base($"Order {orderId} cannot be dispatched: {reason}")
    {
        OrderId = orderId;
        Reason  = reason;
    }

    // keep the chain when you are translating a lower-level failure
    public OrderNotDispatchableException(int orderId, string reason, Exception inner)
        : base($"Order {orderId} cannot be dispatched: {reason}", inner)
    {
        OrderId = orderId;
        Reason  = reason;
    }
}

// wrapping a low-level failure in a meaningful one, without losing it
try { await _courier.BookAsync(order, ct); }
catch (HttpRequestException ex)
{
    throw new OrderNotDispatchableException(order.Id, "courier unreachable", ex);
}
Line by line
  • Derive from the closest meaningful base, not from Exception. Deriving from InvalidOperationException means code that already catches that keeps working, which is a genuine kindness to callers.
  • Carry the data as properties. OrderId as a property lets a handler act on it; an order id buried in the message text can only be read by a human.
  • Always provide the inner overload and use it when translating. The inner exception is what tells the person debugging that the real cause was a timeout to the courier's API — without it you have replaced the evidence with your summary of it.
  • Name it …Exception, and make it public if callers outside the assembly are meant to catch it.
  • The old [Serializable] attribute and the protected serialisation constructor are obsolete in modern .NET. Do not copy them from older examples.
Where exceptions should be caught

Not in the method that threw, and usually not in the one that called it. Catch where you can actually do something: retry, substitute a default, translate to an HTTP status code, or tell the user. In a web application that is normally one place — a global exception-handling middleware that turns each known exception type into a ProblemDetails response and logs the rest as a 500. Every try/catch scattered through the business layer that only logs and rethrows is duplicating that middleware and making the code harder to read.

The four that get flagged in review

// 1 — the empty catch. Strictly worse than crashing.
try { Save(order); } catch { }

// 2 — catch, log, rethrow, in ten places. The middleware already does this.
try { Save(order); } catch (Exception ex) { _log.LogError(ex, "failed"); throw; }

// 3 — the lost stack trace.
try { Save(order); } catch (Exception ex) { throw ex; }

// 4 — exceptions as control flow.
try { return int.Parse(s); } catch { return 0; }        // TryParse exists
Line by line
  • The empty catch is the worst line in this chapter. The program continues in a state where the operation did not happen, so the failure surfaces later, somewhere unrelated, with no trace of the original. A crash at least tells you the truth. If you genuinely intend to ignore something, catch the specific type and write a comment saying why.
  • Log-and-rethrow duplicates the log entry at every level it appears, so one failure produces six stack traces in your alerting and each looks like a separate incident. Log once, at the boundary that handles it.
  • throw ex; — covered above, and worth repeating because it is invisible and irreversible.
  • Exceptions as control flow is slow and it hides real failures. That catch also swallows an OutOfMemoryException and returns 0. int.TryParse exists for exactly this.
  • A fifth, subtler one: catch (Exception) anywhere below the top level also catches OperationCanceledException, so cancelled requests start appearing as errors and your error rate becomes meaningless.

Exercises, with the reasoning shown

Exercise 1 — the log that pointed at the wrong line

try { Dispatch(order); }
catch (Exception ex) { _log.LogError(ex, "boom"); throw ex; }
The stack trace in the log starts at this catch block.
  • throw ex; rethrows the object but resets its trace to the current line, so every frame between here and the real failure is gone — and that is the only information you had. A bare throw; preserves it. The two differ by three characters and nothing warns you.

Exercise 2 — the order that was never saved

try { _db.SaveChanges(); }
catch { }
return Ok();
The API returns 200 and nothing was written.
  • The empty catch turned a database failure into a successful-looking response, so the client believes the order exists and the warehouse never sees it. The failure surfaces days later as a reconciliation mismatch with nothing in the logs. A crash here would have been a better outcome for everyone.

Exercise 3 — the endpoint that took four seconds

foreach (var row in rows)                  // 5,000 rows
{
    try { total += decimal.Parse(row.Amount); }
    catch { /* blank cells */ }
}
Four hundred exceptions thrown and caught, each costing a stack capture and an unwind.
  • Blank cells are expected input, not an exceptional condition, so this is control flow wearing a try. The version with decimal.TryParse is the same length, runs in milliseconds, and — the part that matters more — stops silently swallowing the genuinely malformed rows that somebody should be told about.

Exercise 4 — the cancelled request that paged somebody

try { await LongQueryAsync(ct); }
catch (Exception ex) { _log.LogError(ex, "query failed"); throw; }
Every user who closes a slow page raises an error alert.
  • Cancellation is delivered as an OperationCanceledException, and it is normal behaviour, not a fault. catch (Exception) catches it along with everything else. Either filter it out — catch (Exception ex) when (ex is not OperationCanceledException) — or, better, do not catch broadly here at all and leave it to the middleware that already knows the difference.
Try it yourself

Run this and read the output rather than the code. The ordering of finally, the difference the rethrow makes, and the cost of using exceptions as control flow are all things that are much more convincing when measured. 

// 1 — what order does it happen in?
  static int Demo()
  {
      try { Console.WriteLine("try"); return 1; }
      finally { Console.WriteLine("finally"); }      // prints AFTER "try", BEFORE the return lands
  }
  Console.WriteLine(Demo());                         // try / finally / 1

  // 2 — the stack trace, with and without
  static void Deep() => throw new InvalidOperationException("the real problem");

  try { try { Deep(); } catch (Exception ex) { throw ex; } }      // <- destroys it
  catch (Exception ex) { Console.WriteLine(ex.StackTrace?.Split('\n')[0]); }

  try { try { Deep(); } catch (Exception) { throw; } }            // <- preserves it
  catch (Exception ex) { Console.WriteLine(ex.StackTrace?.Split('\n')[0]); }

  // 3 — the cost, measured
  var sw = System.Diagnostics.Stopwatch.StartNew();
  int ok = 0;
  for (int i = 0; i < 100_000; i++)
      if (int.TryParse("x", out _)) ok++;
  Console.WriteLine($"TryParse: {sw.ElapsedMilliseconds} ms");

  sw.Restart();
  for (int i = 0; i < 100_000; i++)
      try { int.Parse("x"); } catch { }
  Console.WriteLine($"Parse+catch: {sw.ElapsedMilliseconds} ms");
What each block demonstrates
  • 1 — the output is try, finally, then 1. The return value is evaluated first, finally runs next, and the return lands last, which is why returning from a finally can discard an exception on its way past.
  • 2 — the two stack traces differ in their first line: throw ex; names the catch block, and throw; names Deep. That first line is the whole cost.
  • ex.StackTrace?.Split('\n')[0] — only the top frame is printed, because that is the one that moved.
  • 3 — the same work done twice, once with TryParse and once with an exception per iteration. The ratio is usually several hundred.
  • Note what the timing is not an argument for: the reason to avoid an exception for "not found" is that it is not exceptional, and the speed only confirms it.

The third block is usually a factor of several hundred, and that number is the argument. Then note what it is not the argument for: the reason to avoid an exception for "not found" is that it is not exceptional, and the speed is only the confirmation.

Golden rules

  1. Exceptions are for the exceptional. If the caller could reasonably have expected the outcome — not found, wrong password, file not there yet — it is a return value, not a throw.
  2. Never write an empty catch. It converts a failure into a wrong answer that surfaces later somewhere unrelated, which is worse than a crash.
  3. throw;, never throw ex;. The second resets the stack trace to your catch block and destroys the only evidence you had.
  4. Catch the most specific type you can, and order catch blocks specific to broad. catch (Exception) belongs at the top of the application and almost nowhere else.
  5. Never throw a bare Exception — it leaves the caller no way to handle your failure without swallowing everything else too.
  6. Never catch NullReferenceException or IndexOutOfRangeException. They are reports of your own bugs, not conditions to manage.
  7. Do not log and rethrow at every level. One failure then produces six stack traces; log once, where it is actually handled.
  8. Let OperationCanceledException through. It is a user navigating away, not an error, and logging it makes your alerting useless.
  9. Put the values in the message. Which id, which path, which limit — "invalid input" has never helped anybody at three in the morning.
  10. When you translate an exception, pass the original as inner. Otherwise you have replaced the evidence with your summary of it.
  11. A custom exception type earns its place only if somebody would catch it specifically, and it should derive from the closest meaningful base and carry its data as properties.
  12. finally is for releasing things, and using is finally written for you. Never return from a finally.

Interview questions

"When should you throw an exception, and when should you not?"

The test I use is whether the caller could reasonably have expected the outcome. "No customer with that id", "wrong password", "the file has not arrived yet" are all ordinary results, so they should be a nullable return, a Try method or a result object. An exception says the method's contract could not be honoured at all — a null argument, an unreachable database, an object in a state that should be impossible. The cost matters too, since an exception is roughly a thousand times a plain return and "not found" is usually a hot path, but that is the confirmation rather than the reason. The reverse mistake is just as bad: swallowing a real database failure and returning an empty list turns an outage into silently missing data.

"What is the difference between throw; and throw ex;?"

A bare throw; rethrows the current exception with its stack trace intact. throw ex; throws the same object but resets the trace to that line, so everything between the catch block and the original failure is lost — and that was the only information anyone had for debugging it. There is no ordinary case where throw ex; is what you meant. If I need to rethrow something captured elsewhere, for instance across a thread boundary, the correct tool is ExceptionDispatchInfo.Capture(ex).Throw(), which preserves the trace. It is also worth saying that an exception filter, catch (…) when (…), avoids the whole question, because it decides before the stack unwinds.

"Why is an empty catch block considered so bad?"

Because it does not remove the failure, it removes the report of it. The program continues with the operation not having happened, so an API returns 200 for an order that was never saved, and the problem surfaces days later as a reconciliation mismatch with nothing in the logs to explain it. A crash would have been more honest and much cheaper to diagnose. It also swallows things nobody intended to catch — cancellation, out of memory, a genuine bug. If I really do want to ignore a specific failure, I catch that specific type and put a comment saying why, so the next reader knows it was a decision.

"Where should exceptions be caught in a web application?"

As close as possible to where something can actually be done about them, which in practice is usually one place: a global exception-handling middleware that maps known exception types to HTTP status codes and a ProblemDetails body, and logs everything else as a 500. Below that I catch only where I have a real response — a retry on a transient courier failure, a fallback to cache, translating a low-level exception into a domain one with the original as inner. What I do not want is a try/catch in every service that logs and rethrows, because then one failure produces six stack traces in the alerting and each looks like a separate incident.

"Quando scriveresti un'eccezione personalizzata?"

Solo se qualcuno la catturerebbe davvero in modo specifico — cioè se esiste un chiamante che vuole reagire a quel fallimento e non a un fallimento generico. Se non esiste, un tipo già presente con un buon messaggio è meglio. Quando la scrivo, derivo dalla base più vicina come InvalidOperationException e non da Exception, così chi già cattura quella continua a funzionare; metto i dati come proprietà, per esempio l'OrderId, e non solo dentro il messaggio; e prevedo sempre l'overload con inner, perché quando traduco un errore di più basso livello la causa vera deve restare attaccata.
