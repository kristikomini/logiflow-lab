Your first C# program

From nothing installed to a program you wrote, running on your machine, in about fifteen minutes. This chapter assumes nothing — not a line of C#, not a line of any other language. Every character in every example below is explained.

Who this chapter is for

If you can already write a for loop in any language, skim it for the dotnet commands and go to 00b. If you cannot, this is the right first page and nothing before it is missing.

Installing the thing that runs C#

🧒 Simple

C# is a language for writing instructions. Your computer does not understand it. You need two things: a translator that turns what you wrote into something the machine can run, and an engine that runs it.

Both come in one download called the .NET SDK. Get it from dotnet.microsoft.com/download and take the newest version offered.

When it has finished, open a terminal — PowerShell on Windows, Terminal on macOS or Linux — and check it is really there: 

dotnet --version        # ask the tool to print its own version and stop
10.0.100                # what it prints back. Any 10.x is fine.
Line by line
  • dotnet — the command-line tool the SDK installed. It is one program that does many jobs, chosen by the word after it. You will type it hundreds of times.
  • --version — an option (also called a flag or switch). Two hyphens is the convention for the long, readable form of an option. It is not C#; this is the shell, not the language.
  • 10.0.100 — the output, printed by the program. Your terminal shows it on the next line. If instead you see "dotnet is not recognised", the install did not finish or the terminal was open before it did — close the terminal, open a new one, and try again.
  • # — starts a comment in a shell. Everything after it on that line is ignored. Comments in these examples explain the line; you never type them. Note that C# uses // for this, not # — different language, different comment marker.
🎓 What you actually installed

Two separate things, and the distinction is a real interview question:

  • The runtime executes a finished application. A server that only runs your app needs nothing else.
  • The SDK contains the runtime plus the compiler and the dotnet tool. It is what a developer machine and a build server need.

That is why a production container is usually built in two stages: compile with the SDK image, then copy the result into the much smaller runtime image and throw the SDK away. Chapter 01 goes properly into this.

Making a project

C# is not run one file at a time. It is organised into projects, and the tool creates one for you: 

dotnet new console -o Hello   # create a console project in a new folder called Hello
cd Hello                      # move the terminal into that folder
Line by line
  • new — the sub-command. It tells dotnet which of its jobs you want: create something from a template.
  • console — the template name. A console application is one that talks to a terminal through text. Other templates you will meet are classlib (a library, no entry point), webapi and blazor.
  • -o Hello — the output option and its argument. -o is the short form of --output; one hyphen for short, two for long. Hello is the folder to create.
  • cd — "change directory", a shell command, nothing to do with .NET. Every command after this runs inside the project folder, which matters because dotnet run looks in the current folder for something to run.

What it made:

Hello/
├── Hello.csproj     // the project file: what to build, and with what
├── Program.cs       // your code. .cs is the extension for a C# source file
├── bin/             // generated: the built application. Never edited, never committed
└── obj/             // generated: the compiler's scratch space. Same
Line by line
  • Hello.csproj — the project file, and it is XML rather than C#. It lists the target framework, the NuGet packages and any referenced projects. Project is the unit .NET builds: one .csproj produces one assembly.
  • Program.cs — a source file. .cs is the extension for C#. Nothing lists it in the project file, because every .cs under the folder is compiled automatically.
  • bin/ — the build output: the .dll the compiler produced, plus everything needed to run it.
  • obj/ — the compiler's intermediate working files. Deleting either folder costs nothing but a rebuild.
  • // in this listing — not real syntax. A folder tree is not a language; the comments are annotations for you, and there is nothing here to type.
⚠️ bin and obj are not yours

They are produced by the build and reproduced from scratch every time. Deleting them costs you nothing but a rebuild. They must never go into git — the template ships a .gitignore that excludes them, and a repository containing bin/ is a reliable sign nobody checked.

The program, character by character

Open Program.cs. The whole file is two lines: 

// See https://aka.ms/new-console-template for more information
Console.WriteLine("Hello, World!");
Line by line
  • // See https://… — a comment. Two forward slashes make the compiler ignore the rest of the line. It is a note for humans and has no effect whatsoever on what the program does. Delete it.
  • Console — a class, which here means a named box of related functionality that Microsoft wrote and shipped with .NET. It represents the terminal window. It is capitalised because C# names types in PascalCase — every word capitalised, no underscores — and that convention is how you will recognise a type on sight.
  • . — the member access operator. Read it as "the … of …". Console.WriteLine is "the WriteLine of Console". You will see this dot everywhere; it is the single most common character in C#.
  • WriteLine — a method. A method is a named block of instructions you can trigger by name; other languages call it a function. This one prints text and then moves to a new line. Its sibling Console.Write prints without the new line.
  • ( … ) — the parentheses that call it. This is the part beginners miss: Console.WriteLine on its own only names the method. Adding () is what actually runs it. What you put inside is the argument — the information the method needs to do its job.
  • "Hello, World!" — a string literal. Double quotes mean "the characters between these quotes, exactly". Literal means the value is written out in the source rather than calculated. Single quotes would be wrong here: in C# 'A' is a char, exactly one character, and "A" is a string. They are different types.
  • ; — the semicolon that ends the statement. C# needs one at the end of every statement. Forgetting it is the single most common error a beginner sees, and the compiler will tell you which line.

Running it

dotnet run
Hello, World!
What that one word did
  • Restore. Read Hello.csproj and download anything the project depends on. For this project, nothing.
  • Build. Run the compiler over every .cs file. It checks your code makes sense and translates it into an assembly — a .dll file under bin/.
  • Run. Start the runtime and hand it that assembly.
🎓 Two kinds of error, and the difference matters
  • A compile-time error happens during the build. The program never runs. The compiler found something it cannot make sense of — a missing semicolon, a misspelled name, a type mismatch. These are the cheap ones: you are told before anything happens.
  • A run-time error happens while the program is running. It compiled fine, but something was wrong that could not be known in advance — a file that was not there, a number that was actually text, dividing by zero.

Most of what a language designer does is move errors from the second category into the first. That is what people mean when they call C# a statically typed language, and it is why the next chapter is about types.

Reading an error message

Delete the semicolon and run again. Do this — meeting an error on purpose, while everything else is known to be fine, is much cheaper than meeting your first one by accident. 

Program.cs(2,42): error CS1002: ; expected [C:\Hello\Hello.csproj]
Line by line
  • Program.cs — the file. With several files, this is how you know which.
  • (2,42) — line 2, column 42. In that order, always. Most editors show the same pair in a corner, so you can navigate straight to it.
  • error — the severity. An error stops the build. A warning does not — the program still runs — but a warning is the compiler saying "this is legal and I do not believe you meant it", and they are worth reading.
  • CS1002 — the error code. CS is the C# compiler. This code is the thing to paste into a search engine, because it is exact and the surrounding words are not.
  • ; expected — the message. It says what the compiler wanted at that position, not necessarily what you did wrong. The fault is often on the line above the one reported, because the compiler only notices something is missing when it reaches whatever came next.

Reading something in

Put the semicolon back, then replace the whole file with this:

Console.Write("What is your name? ");   // Write, not WriteLine: stay on this line
string? name = Console.ReadLine();       // wait for the user, keep what they typed

Console.WriteLine($"Hello, {name}!");     // print it back inside a sentence
Line by line
  • Console.Write — prints without a trailing new line, so the cursor stays beside the question. The trailing space inside "…name? " is deliberate: it keeps the typing off the question mark.
  • string — a type. It says what kind of value this box can hold: text. C# is statically typed, meaning every value has a type known at compile time, and the compiler refuses code that mixes them wrongly.
  • ? — makes it string?, a nullable string. It marks that the value is allowed to be null — "no value at all", which is different from an empty string. It is here because ReadLine genuinely can return null, and the type is telling you the truth about that.
  • name — the variable name, chosen by you. Local variables are camelCase: first word lower, later words capitalised. That is how you tell a variable from a type at a glance, since types are PascalCase.
  • = — assignment, not equality. It means "put the thing on the right into the box on the left". Comparing two values for equality is ==, with two characters, and confusing the two is a classic bug.
  • Console.ReadLine() — a method call that returns a value. The program stops and waits until Enter is pressed, then the whole expression becomes the typed text, which assignment then stores in name. Empty parentheses mean it needs no arguments — but they are still required, because they are what makes it a call.
  • $"…" — an interpolated string. The $ in front changes the rules inside the quotes: {name} is no longer those six characters, it is replaced by the value of name. Without the $ the program would literally print Hello, {name}!.
  • {name} — the hole. Whatever is inside the braces is evaluated and converted to text. {2 + 2} would print 4.
⚠️ A conversion is happening here that you did not write

Console.WriteLine takes text, but {2 + 2} is a number. C# calls ToString() on the value for you and inserts the result. Every type has a ToString(), so this always compiles — which is convenient right up until it prints something useless like System.Int32[] for an array, because the default ToString() of most types is just its own name.

What the two-line file is hiding

A program has to start somewhere. In C# that place is a method called Main, and until 2021 you had to write all of it yourself. That form still exists, and you will meet it in older code, so it is worth seeing once: 

using System;                                   // make the names in System usable unqualified

namespace Hello                                 // a surname for the types in this file
{
    internal class Program                     // a class to hold the method, because methods need one
    {
        static void Main(string[] args)          // THE entry point: where the program begins
        {
            Console.WriteLine("Hello, World!");  // the only line that does anything
        }
    }
}
Line by line
  • using System; — a using directive. Console is really called System.Console; this line lets you write the short name. It is not an import of code — the code is already there — only of names. Modern projects switch this on for common namespaces automatically, which is why the two-line version needs no using at all.
  • namespace Hello — a namespace, a surname for types. It exists so that your Program and somebody else's Program can coexist. It creates no object and costs nothing at run time.
  • { … } — braces delimit a block: everything belonging to the namespace, then the class, then the method. C# ignores indentation entirely — the braces are what define the structure. Indentation is for you.
  • internal — an access modifier: visible inside this project, invisible outside it. Its opposite is public.
  • class Program — declares a class. In C# a method cannot float on its own; it must live inside a type. That is why this class exists even though nothing ever creates one.
  • static — means the method belongs to the class itself, not to an object made from it. It has to be static: at start-up no object exists yet, so there is nothing to call it on.
  • void — the return type, and this one means "returns nothing". Every method states what it hands back. string would mean it hands back text; void means it just does something.
  • Main — the name the runtime looks for. Spelled with a capital M, exactly. C# is case-sensitive: main is a different name and the program would not start.
  • string[] args — the parameter. A parameter is the name a method gives to something handed in; an argument is the actual value handed in. string[] is "array of string" — the words typed after the program name on the command line.
🎓 Top-level statements

The two-line Program.cs is the same program. The compiler generates the namespace, the class and the Main around your statements — the feature is called top-level statements, and only one file in a project may use it. The args array is still available, and so is await, because the generated Main adapts.

So it is not a beginner's toy that you graduate from. It is the same thing with the ceremony written for you, and new projects use it.

Try it yourself

Make a second project, dotnet new console -o Temperature, and write a program that asks for a temperature in Celsius and prints it in Fahrenheit. You do not know enough yet — converting the typed text into a number is the next chapter. Get as far as printing the question and echoing the answer back, and leave it open.

Golden rules

  1. The SDK builds and runs; the runtime only runs. Your machine needs the SDK, a production server needs the runtime.
  2. A method is only called when you write the parentheses. WriteLine names it; WriteLine() runs it.
  3. Every statement ends in a semicolon, and blocks are delimited by braces. Indentation is for humans; C# does not read it.
  4. C# is case-sensitive and conventional: PascalCase for types and methods, camelCase for variables and parameters.
  5. = assigns, == compares. They are not interchangeable and the compiler will not always save you.
  6. Read the error code, not just the message. CS1002 is exact; "; expected" is not, and the real fault is often on the line above.
  7. A compile-time error costs you a minute; a run-time error costs you a user. Most of what the type system does is convert the second kind into the first.
  8. bin/ and obj/ are generated. Never edit them, never commit them.
  9. "a" is a string and 'a' is a char. Different quotes, different types.
  10. Top-level statements are not a lesser form of Main. They are Main, with the ceremony generated.

Interview questions

"What is the difference between the .NET SDK and the .NET runtime?"

The SDK builds and runs — it contains the compiler, the CLI and the runtime. The runtime only executes an already-built application. Developer machines and build agents need the SDK; a production container only needs the runtime, which is why a Dockerfile builds in an SDK image and copies the output into a runtime image.

"What is the entry point of a C# program?"

A static method called Main. It is static because no instance exists at start-up. Since C# 9 a single file may use top-level statements instead, and the compiler generates the class and the Main around them — it is the same entry point, not a different mechanism.

"What does using System; actually do?"

It imports names, not code. The assembly is already referenced; the directive only lets you write Console instead of System.Console. Modern project templates enable implicit usings for the common namespaces, which is why new files often have none.
