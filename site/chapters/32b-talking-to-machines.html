Talking to machines

Chapter 32 gave you the vocabulary. This one is the wire: what a register actually is, what OPC UA buys you over it, why you must never poll for events, and who pays when your consumer cannot keep up with a machine that will not slow down for anybody.

From the adverts

System Logistics in Fiorano Modenese wants “supervisione e gestione del traffico” and “tracking” for automated warehouses, in C#, .NET, T-SQL and WPF. A Modena SME wants C# desktop applications with OPC-UA concepts and Siemens PLC. The technology is the technology you already know. What is missing is this chapter.

Everything here runs on your laptop with no hardware, no licence and no factory: dotnet run modbus, dotnet run tags and dotnet run labs/opc-ua.cs.

The machine layer has no schema

🧒 Simple

Imagine a friend who can only ever say numbers. You ask how they are and they say “one”. You ask how warm it is and they say “two hundred and twenty-five”.

They are not being difficult — that is genuinely all they can say. Somebody once wrote on a piece of paper that one means happy and that you have to divide the temperature by ten. If you lose the paper, the numbers still arrive and they no longer mean anything.

That piece of paper is the whole problem, and it is usually a spreadsheet.

🎓 Professional

Modbus is a number at an address. That is the entire data model. Published in 1979, free of licence, small enough for a four-euro microcontroller — which is why it is in an enormous amount of equipment that is still running and will still be running in ten years.

Run the demo and read the bytes:

$ dotnet run modbus

   →  00 01 00 00 00 06 01 03 00 00 00 04
      ─┬─── ─┬─── ─┬─── ┬─ ┬─ ─┬─── ─┬───
       │     │     │    │  │    │     └ quantity  = 4 registers
       │     │     │    │  │    └────── start     = 0
       │     │     │    │  └─────────── function  = 3
       │     │     │    └────────────── unit id   = 1
       │     │     └─────────────────── length    = 6 bytes follow
       │     └───────────────────────── protocol  = 0 (always)
       └─────────────────────────────── transaction id = 1

   ←  00 01 00 00 00 0B 01 03 08 00 01 00 01 86 A3 00 E1
Line by line
  • Seven bytes of header, then the request. That header is called the MBAP, and the whole protocol fits on one page. The demo implements a working server and client over a raw TcpListener with no package at all.
  • transaction id — yours to choose; the device echoes it. It exists so you can match a reply to a request when several are in flight.
  • length = 6 bytes follow — and it counts the unit id plus the request, so it is one more than you expect. Get this wrong and the stream desynchronises: every subsequent frame is garbage, which presents as “it worked for ten minutes” — the worst kind of bug to be handed.
  • function = 3 — read holding registers. There are a couple of dozen function codes and you will use three of them.
  • start = 0 — and the spreadsheet says 40001. The 4xxxx prefix means “holding register” and the rest is one-based. Every Modbus integration loses an afternoon to that exactly once.
  • The reply is 17 bytes and the last 8 are the payload — four registers, big-endian, and nothing else. No names, no units, no types, no timestamp, no quality flag.

The trap that is not in any specification

A 32-bit counter does not fit in a 16-bit register, so it is split across two. Modbus fixes the byte order inside a register and says nothing about the order between two of them. The same eight bytes therefore have two readings, and the demo prints both: 

   40002/40003 — one counter in two registers:
      high-word-first :      100,003
      word-swapped    : 2,258,829,313   ← same bytes
Line by line
  • Both numbers are decodings of identical bytes. Roughly half the devices in the field use each convention, and there is no field anywhere that tells you which.
  • You find out because the number is absurd — or, far worse, because it is plausible. A counter reading 100,003 when it should read 3 looks like a machine that has been busy.
  • The fix is procedural, not technical: on day one, change a value you can see and watch which decoding tracks it. Do that before anything is built on top.
  • The same applies to scaling. 225 is 22.5 °C only because a spreadsheet says tenths, and signed only because the same spreadsheet says so. Read it unsigned and −1 °C becomes 65,526 tenths.
The rule that follows

Scaling and units live in one place in your code — a tag definition — and never as an inline / 10.0 at a call site. The day the device is replaced with one that sends hundredths, you want to change one line, not hunt divisions through a codebase.

OPC UA: the spreadsheet, moved into the protocol

Every trap above is an absence. OPC UA is what filling those absences looks like. The lab starts a real server, connects a real client and asks for the same temperature: 

$ dotnet run labs/opc-ua.cs

   name             Oven temperature
   description      Chamber temperature, thermocouple TC-1
   value            22.9
   type             Double
   status           Good [0x00000000]
   source timestamp 02:22:08.465   ← when the MACHINE says it was true
   server timestamp 02:22:08.465   ← when the SERVER saw it
   gap              0 ms   ← and here is the honest part
Line by line
  • name, description — written by whoever built the machine and travelling with the value, instead of sitting beside it in an .xls.
  • type Double — a real type, not two guessed words in a guessed order.
  • status Good — quality. A sensor is allowed to say Uncertain, which is not the same as zero and must never be averaged with real readings.
  • Two timestamps, in the protocol, for free. The gap between them is your latency — measurable without adding a clock of your own.
  • gap 0 ms — and the demo says why: its server and its “machine” are the same process, so there is nothing for the value to be late by. It refuses to fake a plausible 40 ms, because a tool that lies about its own fidelity is worse than one that admits a limit.
  • And you can browse. Line1.Oven can be asked what it contains and it answers. Modbus has no request that means what do you have.
The sentence to have ready

“OPC UA moves the spreadsheet into the protocol, and the spreadsheet is what was going to go wrong.”

Three things that are not in the marketing

Security is certificates, and it is where every project actually starts. Client and server each hold an X.509 certificate and each must trust the other's before a session is permitted. The practical consequence: the first connection to a new server always fails. The fix is a person moving a .der file out of the rejected folder into the trusted folder, on both machines, usually over a phone call, usually at the worst moment. The demo sets SetAutoAcceptUntrustedCertificates(true) so it can run at all — that means “trust anybody”, and it belongs in a commissioning tool and a test fixture, never in what you leave behind.

Sampling and publishing are two different intervals. Sampling is how often the server reads the device; publishing is how often it talks to you. Sampling is work for the device — asking for 10 ms on 5,000 tags is how you bring a PLC to its knees from the comfort of your desk. They are separate on purpose, so a slow link cannot force you to miss fast events: samples queue and arrive together, each carrying the timestamp it actually had. Which only works if QueueSize is greater than 1, and the default is 1.

The deadband decides your storage bill. Only tell me when it moves by more than 0.5 °C. On a real plant that is the difference between a database that fills in a week and one that fills in a decade, and it is the first thing to ask about when somebody tells you OPC UA is slow.

Two things people get wrong out loud

“OPC” is ambiguous. Classic OPC (OPC DA) is COM/DCOM, Windows only, and configuring DCOM across a domain boundary is a rite of passage nobody enjoyed. OPC UA is a different protocol with a different stack. If somebody says “we have OPC”, find out which — it changes what you are being asked to do.

ISA-95 does not define OPC UA. They are named in the same breath, and there is an ISA-95 companion specification for OPC UA, but ISA-95 is the model of the levels and B2MML is MESA's XML implementation of it. Saying “ISA-95 defines OPC UA” is the kind of small wrongness a person who has been in the room will notice.

Never poll for events

🧒 Simple

You want to know if the light in the next room ever flickers. You open the door once a minute and look.

The light flickered for a tenth of a second, twice, while the door was shut. Your report says the light has been on all day, and your report is not approximately wrong — it is missing something that happened.

🎓 Professional

dotnet run tags simulates three seconds of a machine with a fault lasting 60 ms, and polls at 1 Hz — a generous rate for a supervisor watching a few hundred tags: 

   polling at 1 Hz  : saw states [running, running, running]
   subscription     : saw 3 transitions —
                          0 ms  → running
                       1370 ms  → FAULTED
                       1430 ms  → running
Line by line
  • The poller reports a perfect shift. As far as the database is concerned the fault did not happen, and the maintenance report is missing an event rather than being slightly off.
  • Polling faster does not fix it. The events that matter most on a line are the shortest — a micro-stop cleared in eight seconds, a sensor glitching for 40 ms. A 100 ms poll still misses a 60 ms pulse, and now you are doing ten times the work.
  • And the work lands on the device, not on you. This is the part web habits do not prepare you for: hammering your own database is a problem you can see, but here the thing you degrade belongs to somebody else and shows up as the machine got slower.
  • Where polling is still right: slow, non-event data where you want a heartbeat rather than edges — a daily counter, a setpoint only a human changes, an “is the gateway alive” check. The rule is not never poll; it is never poll for events.

Two clocks, and the column everybody drops

Every reading has two times attached: source, when the machine says the value was true, and receive, when you had it. OPC UA carries both. Almost every quick implementation stores one, and the one it stores is the receive time — or worse, DateTime.Now at the moment of the INSERT, which is a third clock nobody asked for. 

public readonly record struct TelemetrySample(
    EquipmentId EquipmentId,
    string Tag,
    double Value,
    Quality Quality,                       // Good | Uncertain | Bad
    DateTimeOffset SourceTimestampUtc,     // when the MACHINE says it was true
    DateTimeOffset ReceivedAtUtc)          // when THIS PROCESS had it
{
    public TimeSpan Age => ReceivedAtUtc - SourceTimestampUtc;

    public bool IsTrustworthy => Quality == Quality.Good;
}
Line by line
  • This is real code in this repository — TelemetrySample.cs — not a sketch.
  • Age — the cheapest diagnostic you will ever have. Normally 30 ms; when it becomes 900 ms a gateway is struggling or a link is saturated, and you know before an operator notices the screen lagging.
  • It is allowed to go negative, and that is a finding rather than a bug to clamp: it means the device's clock is ahead of yours. PLCs are often not on NTP.
  • IsTrustworthy excludes Uncertain deliberately. A value the device will not vouch for is not a value you may quietly average — an hour of thermocouple dropouts recorded as 0 °C drags a shift average down by a plausible amount and is never found, because there is no error anywhere.
  • Order by source time, not arrival time. A gateway that buffered through a dropped link delivers a burst afterwards, out of order — exactly when you are investigating something.

The machine does not wait for your consumer

This is the sentence that separates a work queue from a machine feed. dotnet run tags sends a burst of 60 tag changes — a pallet arrives and everything changes at once — into a bounded channel of 16, with a consumer needing ~15 ms each because it writes to a database: 

                 held the      delivered   ids that
                 machine for   to the DB   arrived
                 ───────────   ─────────   ────────────
   Wait             765 ms       60/60      #0 … #59
   DropOldest         0 ms       16/60      #44 … #59
   DropWrite          0 ms       16/60      #0 … #15
Line by line
  • Read the last column, not the counts. Both drop policies lost the same number of events and lost completely different events — and only one of those two mistakes is visible on an operator's screen.
  • Wait — loses nothing and charges the producer 765 ms. Correct for a work queue, wrong for a machine: you cannot actually make a conveyor wait. The loss still happens; you have moved it into a lag and then into a socket buffer with no counter on it.
  • DropOldest — ends on #59, the newest. You stay current and lose history. Right for a live screen, where a value from four seconds ago is worse than useless because somebody is deciding from it.
  • DropWrite — ends on #15 and never learns what happened after. Almost never right for telemetry; exactly right for an alarm sequence you must not reorder.
  • The real answer is both paths at once: DropOldest into the live view, and a separate durable path — a file, a queue, an outbox — for what you are legally required to still have in three years. The screen and the record have opposite requirements and should never share a queue.
Count the drops, or the failure is invisible by construction

DropOldest throws data away with no exception, no log line and no return value. In .NET, TryWrite returns true whether or not it discarded something — so code that checks the return value is counting nothing while looking like it counts. The only way to observe it is the itemDropped callback on Channel.CreateBounded. Put that counter on the dashboard next to throughput.

One port, two adapters

The machine layer is the one dependency you genuinely cannot have on your laptop — there is no LocalDB for a filling line. That single fact decides the architecture, and it decides it in a direction this repository has already argued once, about IDistributedCache: depend on an interface, choose the implementation with a capability check, and ship with the real one switched off. 

public interface IEquipmentGateway
{
    string Description { get; }                                  // which adapter is live
    IReadOnlyList<EquipmentDescriptor> Fleet { get; }            // commissioning data

    IAsyncEnumerable<TelemetrySample> SubscribeAsync(CancellationToken ct);
    Task<CommandAck> SendAsync(EquipmentCommand command, CancellationToken ct);
    Task<CommandAck> AcknowledgeAsync(EquipmentId id, string by, CancellationToken ct);
}
Line by line
  • No ReadRegister(int). That would not be an abstraction, it would be Modbus with C# syntax — and the day the next line speaks OPC UA you would find “register number” had leaked into three hundred call sites.
  • No GetCurrentState(), deliberately. Offering a snapshot is an invitation to poll. A caller who needs the current value keeps a projection of the stream in memory — a dictionary, not a round trip to the floor.
  • SendAsync returns an acknowledgement, not a result. A conveyor does not finish moving a pallet inside your await; the outcome arrives later on the stream. Modelling it as Task<MoveResult> produces a supervisor that holds a request open for ninety seconds and falls over the first time a pallet jams.
  • AcknowledgeAsync has its own method because it is separately audited — who cleared the fault, when, on whose authority.
  • Fleet is commissioning data rather than discovery, because Modbus has no request meaning what do you have. An OPC UA adapter would fill it by browsing; the interface is the same either way, which is the point of having one.

It is all in this repository and it runs with no hardware: the port, the simulator, the Modbus adapter. Chapter 32c is what runs on top of them.

Which protocol you will actually meet

You do not choose. This is what catches people who prepare by picking a favourite: the protocol is a property of the installation, and a single plant routinely has all of these at once.

What you findWhat it means for you
OPC UABest case. Ask about deadbands and sampling intervals before anything else.
Siemens S7 / Modbus / EtherNet/IPYou will be handed a register map as a spreadsheet. See the top of this chapter.
MQTTNewer sensors, or an existing push-to-cloud path. Ask who owns the broker and what the topic convention is — there is always one and it is never documented.

A barcode scannerIt presents as a keyboard. The whole design question is which control had focus.

The question that shows you have done this

“What do the machines speak, and is there already a gateway or a historian?” If there is, most of this chapter is somebody else's problem and your job is the layer above it. If there is not, you have just found out what your first three months are.

Golden rules

  1. The documented register number and the wire address differ by one. 40001 is address 0.
  2. Word order between two registers is a guess until you verify it against a value you can change and watch.
  3. Scaling and units live in exactly one place in your code, because they do not live in the protocol at all.
  4. Read the registers you need in one request. A request per tag is how a supervisor that worked at your desk falls over on a real line.
  5. An OPC UA value carries name, type, quality and two timestamps. That is the whole argument for it.
  6. The first OPC UA connection always fails on certificate trust. Budget for it; never solve it in production by auto-accepting everything.
  7. Sampling interval and publishing interval are different, and QueueSize = 1 silently discards everything between publishes.
  8. Never poll for events. Poll only for heartbeats and slow values.
  9. Store both timestamps, and order by source time.
  10. Quality is a column, not a filter. Uncertain is a reading, and recording it as zero corrupts an average nobody will ever un-corrupt.
  11. The machine never waits for your consumer. Backpressure is a choice between losing the past and losing the present, and it must be made deliberately.
  12. Count every drop. A silent discard is a failure mode invisible by construction.

Interview questions

"How would you get data out of a PLC?"

Ask what is already there before proposing anything, because the answer is usually decided. OPC UA if the installation is modern — a subscription, not a poll, with an information model carrying type, unit, quality and a source timestamp. MQTT for newer IIoT sensors and for pushing outward. A direct driver — S7, Modbus TCP, EtherNet/IP — for older or cheaper equipment, where the register map arrives as a spreadsheet. And in practice also: a barcode scanner behaving as a keyboard, an operator choosing a stop reason from a list, and a CSV dropped on a share every ten minutes by a machine from 2004.

"Why is subscription better than polling here?"

Because you cannot poll fast enough. A fault lasting 60 ms is invisible at 1 Hz, and the events that matter most are the shortest. Polling also costs the device rather than you: asking 5,000 tags every second is real work for a PLC with a scan cycle to meet. Subscription inverts it — the server samples at an interval you agree and publishes only what changed.

"You are given a 32-bit counter split across two Modbus registers. What could go wrong?"

The word order between the two registers is not specified by Modbus, so the same bytes decode to two wildly different numbers depending on convention, and roughly half the devices in the field use each. Nothing in the data says which. You verify it on day one against a value you can change and watch — because the failure mode is not an error, it is a plausible number.

"Your consumer cannot keep up with the tag stream. What do you do?"

Decide what to lose, explicitly. Blocking the producer is correct for a work queue and wrong for a machine — the line will not slow down, so you have converted data loss into an unbounded lag and a buffer overflowing somewhere you cannot see. Usually drop the oldest for the live screen so it stays current, and put anything legally required down a separate durable path. Then fix the consumer, because both of those are triage. And count the drops, or you have built a system whose failure mode is invisible.

"Why store two timestamps on every reading?"

Because they are different, and the gap between them is free latency measurement: a source time the machine stands behind, and a receive time from your own clock. A gap that is normally 30 ms and becomes 900 ms tells you a gateway is struggling before an operator notices. It also lets you detect a device whose clock is wrong, which is common because PLCs are often not on NTP — and it lets you order by when things happened rather than when they arrived, which matters precisely when a gateway has buffered through an outage.
