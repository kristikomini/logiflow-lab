Generics, delegates and events

Three features that look like syntax and are actually the foundations. Every LINQ query, every dependency injection registration, every await, every button click and every piece of ASP.NET Core middleware in this site is built out of them. Learn them once and a dozen later chapters stop being magic.

Why this chapter exists

"Che cos'è un delegate?" and "perché i generics?" are asked in almost every junior technical round, because they are cheap to ask and reveal instantly whether you have read C# or only used it. They are also the answer to "how does LINQ actually work", which is the follow-up.

Generics

🧒 Simple

Imagine a lunchbox factory. You could make a sandwich box, a fruit box, a biscuit box — three factories, three sets of drawings, and if you improve the lid you have to improve it three times.

Or you make one box with a label on the side saying what goes in it. Same box, and the label stops someone putting biscuits in the fruit one.

List<T> is that box. T is the label.

🎓 Professional

Generics give you type safety and code reuse at the same time, which before C# 2.0 you had to choose between. The old way was ArrayList, which stored object: 

// Before generics — compiles fine, explodes at runtime.
ArrayList list = new();
list.Add(42);
list.Add("quarantadue");              // nobody stopped you
int x = (int)list[1];             // InvalidCastException, in production

// With generics — the mistake does not compile.
List<int> numbers = [42];
numbers.Add("quarantadue");           // CS1503, on your machine, today
Line by line
  • ArrayList — the pre-generics collection. It stores object, which every type converts to, so it accepts anything.
  • list.Add(42) — a hidden boxing conversion. int is a value type, object is a reference type, so the value is copied onto the heap inside a wrapper. Invisible in the source, and an allocation per item.
  • (int)list[1] — an unboxing cast. The compiler permits it because the static type is object and it cannot know better; at run time the object is a string, so it throws InvalidCastException.
  • List<int> numbers = [42]; — <int> is a type argument, closing the generic type. The square brackets are a collection expression (C# 12), the modern spelling of new List<int> { 42 }.
  • numbers.Add("quarantadue") — CS1503 at compile time. The method's parameter is genuinely int, not object.
  • Generics buy two things at once: the error moves from run time to compile time, and the boxing disappears — a List<int> stores actual integers in one array. Type safety and speed from the same feature.

Three benefits, and you should be able to name all three: compile-time safety (errors move from runtime to build), no casting (less noise, fewer mistakes), and no boxing for value types — ArrayList heap-allocates every int you put in it, and List<int> does not. That third one is chapter 08, and it is the answer most candidates miss.

constraints: what the method is allowed to assume
// Without a constraint, T could be anything, so you can do almost nothing with it.
public static T Largest<T>(IEnumerable<T> items) where T : IComparable<T>
{
    T best = items.First();
    foreach (T item in items)
        if (item.CompareTo(best) > 0) best = item;   // legal because of the where
    return best;
}
Line by line
  • Largest<T> — <T> after the method name declares a type parameter. It is a placeholder filled in per call, and by convention it is named T.
  • Without a constraint T is almost useless. The compiler must assume the worst, so only members of object are available — a > b would not compile, because most types have no >.
  • where T : IComparable<T> — the constraint. It is a promise the caller must keep and a permission the method body gains: inside, every T is known to have CompareTo.
  • item.CompareTo(best) > 0 — the convention for comparison: positive means greater, zero means equal, negative means less. Legal here only because of the where.
  • items.First() — throws on an empty sequence. This method has a latent bug for that case, which a constraint cannot express.
  • Other constraints worth knowing: where T : class, where T : struct, and where T : new(), which permits new T() inside the body.

Delegates

🧒 Simple

You know how you can save a friend's phone number and then ring it without remembering the digits? A delegate is a saved phone number — but for a method.

That means you can hand somebody a method the way you hand them a number: "here, call this when you're done." They do not need to know whose number it is.

🎓 Professional

A delegate is a type-safe reference to a method. It is a real type (deriving from MulticastDelegate), not a syntax trick, which is what makes it different from a C function pointer: it carries the target instance as well as the method, and the signature is checked by the compiler.

In practice you almost never declare your own any more, because the framework provides them: 

Func<int, int, int>   add   = (a, b) => a + b;   // takes 2 ints, returns int
Action<string>         log   = m  => Console.WriteLine(m); // returns void
Predicate<Order>      isBig = o  => o.Total > 1000m;  // returns bool

// The last type argument of Func is ALWAYS the return type. That is the
// one detail people get wrong under pressure.
Line by line
  • A delegate is a type whose values are methods. A variable that holds a method the way another holds an int — that is the whole idea, and it is what LINQ, DI, async and every event handler are built from.
  • Func<int, int, int> — the last type argument is always the return type; everything before it is a parameter. So this takes two ints and returns an int. This is the detail people get wrong under pressure.
  • (a, b) => a + b — a lambda. No types are written because they are inferred from Func<int, int, int> on the left. An expression body means its value is the return value; no return keyword is needed.
  • Action<string> — Action returns void. It has no return type argument at all, which is the whole difference from Func.
  • m => Console.WriteLine(m) — a single parameter needs no parentheses. (m) => ... is equally valid.
  • Predicate<Order> — identical in effect to Func<Order, bool>, and older. LINQ uses Func; a few List<T> methods still ask for Predicate, and the two are not implicitly convertible even though they describe the same shape.

And this is where LINQ comes from. Where does not contain your condition — you hand it one: 

// This...
orders.Where(o => o.Total > 1000m)

// ...is this. The lambda IS a Func<Order, bool>.
public static IEnumerable<T> Where<T>(this IEnumerable<T> source,
                                       Func<T, bool> predicate)
{
    foreach (T item in source)
        if (predicate(item))      // ← calling the method you passed in
            yield return item;
}
Line by line
  • orders.Where(o => o.Total > 1000m) — the lambda is a Func<Order, bool>. Nothing magical is happening; Where is an ordinary method taking an ordinary argument.
  • this IEnumerable<T> source — this on the first parameter makes it an extension method. That is the entire mechanism behind LINQ's fluent syntax: orders.Where(...) compiles to Enumerable.Where(orders, ...).
  • Func<T, bool> predicate — the parameter is a delegate. The caller supplies behaviour, not data.
  • predicate(item) — calling the method that was passed in. Parentheses on a delegate variable invoke whatever it currently refers to.
  • yield return item; — makes this an iterator. The compiler rewrites the method into a state machine that produces one element, suspends, and resumes on the next request. This is what makes LINQ lazy, and why the body does not run until you enumerate.
  • Ten lines is the whole of Where. Once this is not magic, neither is the rest of LINQ.

Generics plus delegates, eight lines, and you have written the core of LINQ. That is a genuinely good thing to be able to say out loud — see chapter 06 for the rest.

⚠ Closures capture variables, not values

A lambda does not copy the variables it uses — it captures them, and keeps the live variable alive. Which produces this: 

var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));

foreach (var a in actions) a();     // 333 — not 012
Line by line
  • new List<Action>() — a list of methods. Nothing runs when one is added.
  • () => Console.Write(i) — a lambda taking no parameters. Empty parentheses are required. It captures i.
  • The capture is of the variable, not its value. A for loop declares i once, so all three lambdas close over the same storage location.
  • a() in the second loop — the first time any of them runs. By then the loop has finished and i is 3, so all three print 3: 333, not 012.
  • The fix is a fresh variable per iteration: int copy = i; inside the loop, capturing copy. Each iteration then has its own storage.
  • A foreach does not have this bug — its variable is a new one per iteration. The language was changed in C# 5 for exactly this reason, and the for loop was deliberately left alone, because there i is genuinely one counter.

All three lambdas captured the same i, and by the time they run it is 3. It is a favourite interview puzzle precisely because it looks wrong.

Events

🧒 Simple

A newsletter. You give the shop your address and they post you something when there is news. You do not phone the shop every morning to ask.

And notice the rules: you can subscribe, and you can unsubscribe — but you cannot send the newsletter to everybody else, and you cannot delete the shop's whole address book. Only the shop can do those. That restriction is the entire reason the event keyword exists.

🎓 Professional

An event is a delegate field with restricted access. Without event, a public delegate field lets any caller do two things they should not: invoke it (raise your event on your behalf) and assign to it with =, wiping every other subscriber. With event, outside code may only += and -=. That is the whole answer to "what is the difference between a delegate and an event", and it is asked often.

the standard shape, including the two details people forget
public sealed class OrderService
{
    // EventHandler<T> is the convention: (object? sender, TArgs e)
    public event EventHandler<OrderSubmittedEventArgs>? OrderSubmitted;

    public void Submit(Order order)
    {
        order.Submit();
        // ?.Invoke — an event with no subscribers is null, and calling it throws.
        OrderSubmitted?.Invoke(this, new(order.Id));
    }
}

// Subscribing…
service.OrderSubmitted += OnOrderSubmitted;

// …and the line everybody forgets, which is a memory leak in a long-lived app.
service.OrderSubmitted -= OnOrderSubmitted;
Line by line
  • public event EventHandler<...>? OrderSubmitted; — event is a restricted delegate field. Outside the class only += and -= are permitted — nobody else can invoke it or replace the whole subscriber list, which is precisely what a plain public delegate field would allow.
  • EventHandler<TArgs> — the convention: (object? sender, TArgs e) returning void. Following it means the event works with tooling and reads the way every other .NET event does.
  • ? on the type — an event with no subscribers is null, not an empty list. That is the source of the classic NullReferenceException.
  • OrderSubmitted?.Invoke(this, new(order.Id)) — ?. handles the no-subscribers case. Invoke calls every subscriber in turn, on the current thread, synchronously: a slow handler blocks the publisher, and a throwing handler stops the ones after it.
  • new(order.Id) — a target-typed new. The parameter type is known, so the type name is not repeated.
  • += and -= — subscribe and unsubscribe. -= is the line everybody forgets: the event holds a reference to the subscriber, so a short-lived object subscribed to a long-lived publisher can never be collected. That is the classic .NET memory leak.

Try it yourself

Write Where yourself. It is genuinely eight lines:

public static class MyLinq
{
    public static IEnumerable<T> MyWhere<T>(
        this IEnumerable<T> source, Func<T, bool> predicate)
    {
        foreach (T item in source)
            if (predicate(item))
                yield return item;
    }
}
Line by line
  • public static class MyLinq — extension methods must live in a static, non-nested class. The compiler enforces it.
  • this IEnumerable<T> source — this makes it an extension. The method becomes callable as though it were declared on IEnumerable<T>, without modifying that interface or any of its implementations.
  • An extension method is not really a member. It is a static method with friendlier syntax, resolved at compile time, and it can therefore be shadowed by a real instance method with the same name.
  • yield return item; — makes it lazy in exactly the way the real Where is lazy. Nothing runs until enumeration begins, and it streams one element at a time rather than building a list.
  • The point of writing this yourself is that LINQ stops being a feature and becomes a library — extension methods plus generics plus delegates plus iterators, all of which you now have.
  • An extension is only visible where its namespace is in scope, which is why the odd using makes new methods appear on a type you did not write.

Then call it with .MyWhere(x => x > 2) and put a breakpoint inside the foreach. Watch the debugger jump out of your method at yield return and come back in on the next iteration — that is deferred execution, seen rather than described. Then run the for-loop closure snippet above and watch it print 333. Two experiments, ten minutes, and both are interview answers.

Golden rules

  1. Generics buy compile-time safety, no casting, and no boxing. Name all three.
  2. Constraints are what let a generic method actually do something with T.
  3. C# generics are reified, not erased. The runtime knows the type argument.
  4. A delegate is a type-safe method reference that carries its target instance.
  5. Func returns a value, Action returns void, and Func's last type argument is the return type.
  6. A lambda is just a delegate written inline. LINQ is generics plus delegates.
  7. Closures capture variables, not values — and a for loop variable is one variable.
  8. An event is a delegate that outsiders may only += and -=.
  9. Raise with ?.Invoke. An event with no subscribers is null.
  10. Follow the EventHandler<T> convention unless you have a reason not to.
  11. Every += needs a -=. The publisher holds the subscriber alive.
  12. Events are synchronous and in-process. Across a boundary, use chapter 22.

Interview questions

"Che cos'è un delegate?"

A type-safe reference to a method, so you can pass behaviour as a value. Give the concrete payoff immediately rather than stopping at the definition: it is what makes LINQ possible — Where takes a Func<T,bool> and calls the method you gave it. Mention that Func, Action and Predicate mean you rarely declare one yourself.

"What is the difference between a delegate and an event?"

An event is a delegate with restricted access: outside the declaring type you may only subscribe and unsubscribe. A plain public delegate field would let any caller raise it, and let one careless = wipe every other subscriber. That encapsulation is the entire reason the keyword exists.

"Why generics instead of object?"

Compile-time type safety, no casts, and no boxing for value types. Make it concrete: ArrayList heap-allocates every int you add and lets you mix in a string that throws on the way out; List<int> does neither. If they push further, add that C# generics are reified rather than erased, so the runtime knows the type argument.

"What does this print?" (the for loop closure)

333. All three lambdas captured the same variable, and it is 3 by the time they run. Then say the fix — a fresh variable inside the loop — and the nuance that earns the point: foreach was changed in C# 5 to give a fresh variable per iteration, but for was not.

"Why do event handlers cause memory leaks?"

Because subscribing makes the publisher hold a reference to the subscriber. If the publisher outlives the subscriber and nobody unsubscribes, the subscriber can never be collected. Say where it bites hardest — a long-running desktop process or a BackgroundService, not a 40 ms web request — and that the rule is to pair every += with a -=.
