Collections and LINQ

Two topics that must be learned together, because the second one hides the first. LINQ makes every collection look the same — and the cost of choosing the wrong one, or of not noticing when a query runs, stays completely invisible until production.

From the advert

"Ottima conoscenza del linguaggio C#." LINQ is the part of C# most likely to appear in a live-coding round, and IQueryable vs IEnumerable is the question that connects this chapter to EF Core.

Picking a collection

🧒 Simple

A List is a row of numbered lockers. Locker 7 is instant — you walk straight to it. But "which locker has the red bag in it?" means opening every single one.

A Dictionary is a cloakroom with tickets. You hand over ticket MO-4471 and the attendant fetches your coat immediately, however many coats there are. The catch is that you must have kept the ticket — you cannot ask for "the third coat".

A HashSet is a guest list. Its only real talent is answering "is this name on it?" instantly, and it refuses to write the same name twice.

🎓 Professional

Choose by the operation you perform most, and know its cost. List<T> is a growable array: O(1) indexing and amortised O(1) append, but O(n) search and O(n) removal from the middle. Dictionary<K,V> and HashSet<T> are hash tables: O(1) average lookup, at the cost of memory and of requiring a correct GetHashCode.

the O(n²) that hides in plain sight
// ✗ For every order, scan the whole customer list.
//   1,000 orders × 10,000 customers = 10,000,000 comparisons.
foreach (var order in orders)
{
    var customer = customers.First(c => c.Id == order.CustomerId);   // O(n) each time
    ...
}

// ✓ Index once, then every look-up is free.
//   10,000 + 1,000 operations.
var byId = customers.ToDictionary(c => c.Id);
foreach (var order in orders)
{
    var customer = byId[order.CustomerId];                          // O(1)
    ...
}

This exact transformation — "build a dictionary first" — is the single most common answer to "this endpoint got slow" in line-of-business .NET, and it is a very common live-coding exercise.

Which interface should a method return?

Return the least capability the caller genuinely needs. It keeps your options open and tells the reader what they may do.

What LINQ actually is

🧒 Simple

Imagine asking for "all the red sweets, sorted by size". You could tip the whole bag on the table, push the red ones into a pile, then line them up. Or you could hand your instructions to a machine that picks up one sweet at a time, throws away anything not red, and passes the rest along a little conveyor belt.

LINQ is the conveyor belt. And — this is the surprising part — the belt does not move at all until somebody stands at the end of it holding out a bowl.

🎓 Professional

LINQ operators are extension methods on IEnumerable<T> that return iterators, not results. Where does not filter anything when you call it; it builds an object that knows how to filter when asked. Nothing executes until something enumerates the chain — a foreach, or a terminal operator like ToList, Count, First, Any, Sum. This is deferred execution, and it is the source of both LINQ’s efficiency and its two classic bugs.

The two bugs deferred execution causes

bug 1 — multiple enumeration
var expensive = orders.Where(o => SlowCheck(o));   // nothing has run yet

Console.WriteLine(expensive.Count());              // runs SlowCheck on everything
foreach (var o in expensive) Print(o);            // runs SlowCheck on everything AGAIN

// ✓ Materialise once when you will use it more than once.
var list = orders.Where(o => SlowCheck(o)).ToList();
bug 2 — the captured variable
var threshold = 100m;
var big = orders.Where(o => o.Total > threshold);   // captures the VARIABLE

threshold = 1000m;                                  // ← changed before enumeration

var result = big.ToList();   // filters on 1000, not 100. The query ran now.

The lambda closes over the variable, not its value at the time of the call. Chapter 07 and module 02 go into closures properly; for now, treat "a LINQ query is a recipe, not a meal" as the rule.

IEnumerable vs IQueryable — the question that matters

This is the bridge between this chapter and every database chapter that follows, and it is asked in interviews constantly.

🧒 Simple

You want the three tallest children in a school of eight hundred.

IEnumerable is: bring all eight hundred children into the room, then measure them and pick three. It works. The room is very full.

IQueryable is: send a note to the school office saying "please send me your three tallest". Three children arrive. The office did the sorting, because the office has the records.

🎓 Professional

IEnumerable<T> takes Func<T,bool> — compiled code, executable only in .NET. IQueryable<T> takes Expression<Func<T,bool>> — a data structure describing the lambda, which a provider (EF Core) can read and translate into T-SQL.

The moment you call .AsEnumerable(), .ToList(), or any operator EF Core cannot translate, the query stops being translatable: everything after that point runs in memory, on whatever rows have already been fetched.

the same code, a thousandfold difference
// ✓ IQueryable — one efficient statement, three rows come back
var top = await db.Orders
    .Where(o => o.CustomerId == id)
    .OrderByDescending(o => o.Total)
    .Take(3)
    .ToListAsync();

// SELECT TOP(3) ... FROM Orders WHERE CustomerId = @id ORDER BY Total DESC


// ✗ ToList() first — the whole table crosses the network, then LINQ runs on it
var top2 = db.Orders
    .ToList()                          // ← SELECT * FROM Orders. Every row. Every column.
    .Where(o => o.CustomerId == id)
    .OrderByDescending(o => o.Total)
    .Take(3)
    .ToList();
⚠ How to spot it in a code review

Look for .ToList(), .AsEnumerable() or .ToArray() appearing before a Where or OrderBy. Nine times out of ten it is there because somebody hit a translation error and made it go away. It did not go away; it moved to the network.

The operators worth memorising

filtering, projecting, ordering
orders.Where(o => o.Total > 100)              // filter
orders.Select(o => o.CustomerName)            // project (map)
orders.SelectMany(o => o.Lines)               // flatten one level
orders.OrderBy(o => o.Date).ThenByDescending(o => o.Total)
orders.Distinct() / .Skip(20).Take(10)        // dedupe / page
the four "get me one" operators — and their differences
orders.First(o => o.Paid)            // throws if none
orders.FirstOrDefault(o => o.Paid)   // null if none          ← the usual choice
orders.Single(o => o.Id == 7)        // throws if none OR if more than one
orders.SingleOrDefault(o => o.Id == 7) // null if none, throws if many

Single is a claim: "exactly one of these exists, and if that is ever untrue I want to know immediately." Use it on unique keys — the exception is doing its job. Use First when several matches are legitimate and you want the earliest.

aggregation and grouping
orders.Any(o => o.Paid)                 // ✓ cheap — stops at the first match
orders.Count(o => o.Paid) > 0           // ✗ counts every one first

orders.Sum(o => o.Total)
orders.Max(o => o.Date)

// GroupBy — the shape SQL calls GROUP BY
var perCustomer = orders
    .GroupBy(o => o.CustomerId)
    .Select(g => new
    {
        CustomerId = g.Key,
        Count      = g.Count(),
        Revenue    = g.Sum(o => o.Total)
    });
⚠ Any() vs Count() > 0

A small, real difference that interviewers like because it shows whether you think about cost. Any() stops at the first match; Count() walks the entire sequence. Against a database it is the difference between EXISTS and COUNT(*). Against an infinite sequence, Count() never returns at all.

Query syntax

Both forms compile to the same thing. Method syntax is far more common; query syntax is genuinely nicer for joins and multi-level grouping, so you should be able to read it.

the same query, twice
var a = orders.Where(o => o.Paid)
              .OrderBy(o => o.Date)
              .Select(o => o.Id);

var b = from o in orders
        where o.Paid
        orderby o.Date
        select o.Id;
Try it yourself

Run this and explain the output before reading the note. It is the whole chapter in eight lines. 

var source = new List<int> { 1, 2, 3 };

var query = source.Select(n =>
{
    Console.WriteLine($"  evaluating {n}");
    return n * 2;
});

Console.WriteLine("query built");
source.Add(4);                              // ← added AFTER building the query
Console.WriteLine("first enumeration:");
foreach (var n in query) { }
Console.WriteLine("second enumeration:");
foreach (var n in query) { }

"query built" prints before any evaluation; the 4 is included, because the query reads the list when it runs, not when it was written; and everything is evaluated twice. Three separate surprises, all from the same cause.

Golden rules

  1. List<T> by default; Dictionary<K,V> the moment you find yourself searching inside a loop.
  2. A nested loop over two collections is O(n×m). Build a dictionary first.
  3. Return the least capable type that serves the caller — usually IReadOnlyList<T>.
  4. LINQ operators are lazy. A query is a recipe; a terminal operator is the cooking.
  5. Enumerating twice executes twice. ToList() once if you will use it more than once.
  6. Lambdas capture variables, not values. A query built before a variable changes will see the new value.
  7. IQueryable is translated to SQL; IEnumerable runs in memory. ToList() in the wrong place moves the work — and the whole table — onto your server.
  8. Any(), never Count() > 0.
  9. Single asserts uniqueness; First takes the earliest of many. Pick the one that states your intent.
  10. Project with Select before materialising: fetch the four columns you need, not the twenty that exist.

Interview questions

"What is deferred execution?"

LINQ operators return iterators rather than results; nothing is evaluated until the sequence is enumerated. Then give the payoff: it allows chaining without intermediate collections and lets First() stop early — and it causes double execution when you enumerate the same query twice.

"IEnumerable or IQueryable?"

IEnumerable holds compiled delegates and runs in memory; IQueryable holds an expression tree that a provider translates — to T-SQL, in EF Core’s case. Getting this wrong is how you accidentally load a whole table to find three rows.

"When would you use a Dictionary over a List?"

Whenever look-up by key dominates. O(1) versus O(n) — and note the requirements: the key must have a stable, correct GetHashCode, and a mutable key is a bug because the entry becomes unreachable in its own dictionary.

"What does SelectMany do?"

Flattens one level: orders.SelectMany(o => o.Lines) turns a sequence of orders into a single sequence of all their lines. It is the LINQ equivalent of a join across a collection property.

"This endpoint takes eight seconds. Where do you look?"

First at whether a query is being executed inside a loop (the N+1 problem — chapter 12), then at whether a ToList() appears before the filtering, then at whether a search is happening inside a loop that a dictionary would make constant. Those three account for most of it.
