T-SQL: querying

SQL is not read in the order it is written. Understanding the order it runs in explains half the errors beginners hit, and it is the foundation for joins, grouping and window functions — the three things a T-SQL screening question is almost always about.

From the advert

"Buona conoscenza di T-SQL." T-SQL is Microsoft’s dialect of SQL: standard SQL plus Microsoft extensions (TOP, ISNULL, OFFSET/FETCH, variables, procedural code).

The order SQL actually runs in

🧒 Simple

You write your shopping list as "buy apples, from the market, only the red ones". But you cannot do it in that order — you have to go to the market first, then look at what is there, then pick the red ones, and only then put them in your bag.

SQL is written in the wrong order on purpose, because that order reads nicely in English. The computer quietly reorders it.

🎓 Professional

The logical processing order is fixed, and it explains a specific family of errors: why you cannot use a SELECT alias in a WHERE clause (the alias does not exist yet), why WHERE cannot contain an aggregate (the groups have not been formed), and why ORDER BY can use an alias (it runs last).

the three errors this explains
-- ✗ "Invalid column name 'Rev'" — WHERE runs before SELECT
SELECT SUM(Total) AS Rev FROM dbo.Orders WHERE Rev > 1000;

-- ✗ "An aggregate may not appear in the WHERE clause" — groups do not exist yet
SELECT CustomerId FROM dbo.Orders WHERE SUM(Total) > 1000 GROUP BY CustomerId;

-- ✓ filter the groups with HAVING; ORDER BY may use the alias
SELECT   CustomerId, SUM(Total) AS Rev
FROM     dbo.Orders
GROUP BY CustomerId
HAVING   SUM(Total) > 1000
ORDER BY Rev DESC;
Line by line
  • -- — a SQL comment to end of line. The block comment is /* ... */.
  • WHERE Rev > 1000 fails — the alias does not exist yet. SQL is evaluated in a logical order that is not the order you write it: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.
  • AS Rev — an alias, created in SELECT. Since WHERE runs before SELECT, the name is not yet defined.
  • WHERE SUM(Total) > 1000 fails for a related reason: WHERE filters rows, and it runs before GROUP BY, so no groups exist to aggregate.
  • HAVING SUM(Total) > 1000 — the correct clause. WHERE filters rows, HAVING filters groups, and that one sentence answers most questions in this chapter.
  • ORDER BY Rev DESC — legal, because ORDER BY is the last step and the alias exists by then. That inconsistency is not a quirk to memorise; it falls straight out of the evaluation order.

Say it in one sentence at interview: WHERE filters rows before grouping, HAVING filters groups after.

Joins

🧒 Simple

Two lists: children, and lunchboxes. Each lunchbox has a child’s name on it.

  • INNER JOIN — only children who brought a lunchbox.
  • LEFT JOIN — every child; those without a lunchbox get an empty space next to their name.
  • RIGHT JOIN — every lunchbox, even the mysterious one belonging to nobody.
  • FULL JOIN — everybody and everything, gaps included.
  • CROSS JOIN — every child paired with every lunchbox. Thirty children and thirty boxes gives you nine hundred rows of nonsense.
all five, on one schema
-- customers who have placed at least one order
SELECT c.Name, o.Total
FROM   dbo.Customers c
INNER JOIN dbo.Orders o ON o.CustomerId = c.Id;

-- ALL customers; Total is NULL for those with no orders
SELECT c.Name, o.Total
FROM   dbo.Customers c
LEFT JOIN dbo.Orders o ON o.CustomerId = c.Id;

-- the classic anti-join: customers who have NEVER ordered
SELECT c.Name
FROM   dbo.Customers c
LEFT JOIN dbo.Orders o ON o.CustomerId = c.Id
WHERE  o.Id IS NULL;                -- ← the "no match" marker
Line by line
  • FROM dbo.Customers c — c is a table alias. Qualifying every column with one is what keeps a multi-table query readable and unambiguous.
  • INNER JOIN ... ON o.CustomerId = c.Id — keeps rows that match on both sides. A customer with no orders disappears entirely.
  • LEFT JOIN — keeps every row from the left table and fills the right-hand columns with NULL where there is no match. That is why o.Total can be null here but not above.
  • WHERE o.Id IS NULL — the anti-join, and it is a genuinely clever idiom: after a LEFT JOIN, a null in a non-nullable right-hand column can only mean "no match was found".
  • Test on the primary key, as here with o.Id. Testing a column that is genuinely nullable would also match rows that did join but happened to hold null.
  • The trap: putting a condition on the right-hand table in WHERE rather than in ON turns a LEFT JOIN back into an inner one, because WHERE runs after the join and discards the null rows.
⚠ The LEFT JOIN that silently becomes an INNER JOIN
-- ✗ the WHERE runs AFTER the join and discards the NULL rows,
--    turning this into an INNER JOIN without telling you
FROM Customers c LEFT JOIN Orders o ON o.CustomerId = c.Id
WHERE o.Status = 3;

-- ✓ put the condition in the ON clause instead
FROM Customers c LEFT JOIN Orders o ON o.CustomerId = c.Id AND o.Status = 3;
Line by line
  • WHERE o.Status = 3 — the bug, and it is a clause in the wrong place. WHERE runs after the join, so it sees the null-filled rows the LEFT JOIN produced for customers with no matching order.
  • NULL = 3 is unknown, not true, so WHERE discards those rows — and every customer without a matching order vanishes. The LEFT JOIN has silently become an INNER JOIN.
  • ON o.CustomerId = c.Id AND o.Status = 3 — the fix. Conditions in ON decide which rows join; conditions in WHERE decide which rows survive. For the outer side of an outer join those are completely different questions.
  • The rule to carry: filter the outer table in WHERE, filter the inner table in ON. Reversing it is the most common outer-join mistake there is.
  • The one deliberate exception is WHERE o.Id IS NULL from the previous block, which wants to act after the join — it is testing for the absence of a match.

ON filters the join; WHERE filters the result. For an outer join they are completely different questions, and this is a favourite interview trap.

Aggregation and grouping

a realistic reporting query
SELECT
    c.Id,
    c.Name,
    COUNT(o.Id)                       AS OrderCount,
    ISNULL(SUM(o.Total), 0)          AS Revenue,
    MAX(o.CreatedAtUtc)              AS LastOrderUtc
FROM       dbo.Customers c
LEFT JOIN  dbo.Orders    o ON o.CustomerId = c.Id
                            AND o.CreatedAtUtc >= @from
GROUP BY   c.Id, c.Name        -- every non-aggregated column must be here
HAVING     COUNT(o.Id) > 0
ORDER BY   Revenue DESC;
Line by line
  • COUNT(o.Id) — counts non-null values, so a customer with no orders scores 0. COUNT(*) would count the row produced by the LEFT JOIN and give 1 — a classic off-by-one in reports.
  • ISNULL(SUM(o.Total), 0) — SUM over no rows returns NULL, not zero. Without this the revenue column is null for new customers, which then poisons any arithmetic downstream.
  • AND o.CreatedAtUtc >= @from inside the ON — deliberate. In ON it restricts which rows join, preserving every customer. Moved to WHERE it would eliminate customers with no recent orders, silently converting this to an inner join.
  • GROUP BY c.Id, c.Name — every non-aggregated column in SELECT must appear here. Unlike MySQL, SQL Server enforces it, which is a kindness: it refuses to invent a row.
  • HAVING COUNT(o.Id) > 0 — filters the groups after aggregation.
  • ORDER BY Revenue DESC — using the alias, legal because ORDER BY is last.
⚠ COUNT(*) vs COUNT(column)

COUNT(*) counts rows. COUNT(o.Id) counts rows where o.Id is not NULL. After a LEFT JOIN that difference is exactly "customers with no orders": COUNT(*) gives them 1, COUNT(o.Id) correctly gives them 0. Using the wrong one is a very common bug in reports.

Subqueries and CTEs

A CTE (Common Table Expression) is a named subquery written before the main statement. It does not make anything faster — it makes it readable, and it enables recursion.

the same query, unreadable then readable
-- ✗ nested subqueries: you must read inside-out
SELECT * FROM (
    SELECT CustomerId, SUM(Total) AS Rev
    FROM dbo.Orders WHERE CreatedAtUtc >= @from
    GROUP BY CustomerId
) x WHERE x.Rev > 1000;

-- ✓ a CTE: reads top to bottom, like a sentence
WITH Revenue AS
(
    SELECT   CustomerId, SUM(Total) AS Rev
    FROM     dbo.Orders
    WHERE    CreatedAtUtc >= @from
    GROUP BY CustomerId
)
SELECT c.Name, r.Rev
FROM   Revenue r
JOIN   dbo.Customers c ON c.Id = r.CustomerId
WHERE  r.Rev > 1000;
Line by line
  • SELECT * FROM ( ... ) x — a derived table. The x is a required alias, and the whole thing has to be read inside-out.
  • WITH Revenue AS ( ... ) — a common table expression. Same result, read top to bottom: define the intermediate set, then use it by name.
  • A CTE is not a temp table. Nothing is materialised; it is a named subquery the optimiser inlines, so referencing it twice generally executes it twice.
  • JOIN dbo.Customers c ON c.Id = r.CustomerId — a CTE joins exactly like a table. JOIN with no qualifier means INNER JOIN.
  • Why this matters beyond neatness: a query built from three named steps can be read, reviewed and modified by someone else. Three levels of nested subquery, in practice, cannot.
a recursive CTE — an organisation chart
WITH Chain AS
(
    -- anchor: where the recursion starts
    SELECT Id, Name, ManagerId, 0 AS Depth
    FROM   dbo.Employees WHERE ManagerId IS NULL

    UNION ALL

    -- recursive member: joins back to the CTE itself
    SELECT e.Id, e.Name, e.ManagerId, ch.Depth + 1
    FROM   dbo.Employees e
    JOIN   Chain ch ON e.ManagerId = ch.Id
)
SELECT * FROM Chain ORDER BY Depth
OPTION (MAXRECURSION 100);   -- a cycle in the data would loop for ever
Line by line
  • A recursive CTE has exactly two parts joined by UNION ALL: an anchor that runs once, and a recursive member that refers back to the CTE by name.
  • WHERE ManagerId IS NULL — the anchor: the top of the tree, the people with no manager.
  • 0 AS Depth — a literal seeding the level counter.
  • UNION ALL — required, and UNION is not permitted here. ALL means "do not de-duplicate", which is both faster and necessary for the recursion to terminate correctly.
  • JOIN Chain ch ON e.ManagerId = ch.Id — the CTE joining to itself. Each pass finds the direct reports of everyone found in the previous pass.
  • ch.Depth + 1 — each level counts one deeper, which is what makes the result orderable by hierarchy.
  • OPTION (MAXRECURSION 100) — a safety limit. The default is 100 already; 0 means unlimited, which is how a cycle in the data becomes a query that never returns. Employee hierarchies acquire cycles more often than anyone expects.

Window functions

The most impressive thing you can know at this level, because they solve problems that otherwise need a cursor or a round trip to C#.

🧒 Simple

GROUP BY is a blender: ten rows go in, one row comes out and you cannot see the originals any more.

A window function is a pair of glasses. Every row stays exactly where it is — but each one can now see its neighbours, so it can say "I am the 3rd biggest" or "the running total up to me is 450".

the three you will actually use
SELECT
    o.Id,
    o.CustomerId,
    o.Total,

    -- position within each customer, biggest order first
    ROW_NUMBER() OVER (PARTITION BY o.CustomerId ORDER BY o.Total DESC) AS rn,

    -- running total, in date order
    SUM(o.Total) OVER (PARTITION BY o.CustomerId
                       ORDER BY o.CreatedAtUtc
                       ROWS UNBOUNDED PRECEDING)                AS RunningTotal,

    -- the customer's overall total, repeated on every one of their rows
    SUM(o.Total) OVER (PARTITION BY o.CustomerId)                AS CustomerTotal
FROM dbo.Orders o;
Line by line
  • OVER (...) — the marker of a window function. Unlike GROUP BY, it aggregates without collapsing rows: every original row survives and gains a column.
  • PARTITION BY o.CustomerId — restart the calculation per customer. It is GROUP BY's idea applied inside a window instead of to the result set.
  • ROW_NUMBER() OVER (... ORDER BY o.Total DESC) — numbers rows 1, 2, 3 within each partition. The ORDER BY inside OVER is unrelated to the query's own ORDER BY.
  • ROW_NUMBER versus RANK versus DENSE_RANK — on a tie: ROW_NUMBER picks arbitrarily (1,2,3), RANK ties then skips (1,1,3), DENSE_RANK ties without skipping (1,1,2). Choosing the wrong one is a subtle reporting bug.
  • SUM(...) OVER (PARTITION BY ... ORDER BY ... ROWS UNBOUNDED PRECEDING) — a running total. Adding ORDER BY inside OVER turns the aggregate into a cumulative one.
  • ROWS UNBOUNDED PRECEDING — the frame: from the first row of the partition to the current one. Worth writing explicitly, because the default is RANGE, which treats tied values as one group and gives a different answer.
  • SUM(o.Total) OVER (PARTITION BY o.CustomerId) — no ORDER BY, so the frame is the whole partition: the customer's grand total, repeated on every one of their rows. Getting that beside the detail is what would otherwise need a self-join.
the classic question: the latest row per group
-- "the most recent order for each customer" — asked constantly
WITH Ranked AS
(
    SELECT o.*,
           ROW_NUMBER() OVER (PARTITION BY o.CustomerId
                              ORDER BY o.CreatedAtUtc DESC) AS rn
    FROM dbo.Orders o
)
SELECT * FROM Ranked WHERE rn = 1;
Line by line
  • "The most recent per customer" is asked constantly, in interviews and in real reporting work. This is the standard answer.
  • SELECT o.* inside the CTE — keep every column, then add the ranking one. Acceptable inside a CTE; still worth naming columns in production code.
  • ROW_NUMBER() OVER (PARTITION BY o.CustomerId ORDER BY o.CreatedAtUtc DESC) — DESC puts the newest first, so it becomes number 1.
  • WHERE rn = 1 — and it must be outside the CTE. A window function cannot appear in WHERE, because WHERE runs before SELECT computes it. The CTE exists precisely to give the column a name that a later WHERE can see.
  • Ties are silently resolved by ROW_NUMBER. Two orders with the same timestamp means one is chosen arbitrarily; add a tie-breaker such as , o.Id DESC if that matters.
  • The obvious alternative — a correlated subquery with MAX(CreatedAtUtc) — is usually slower and breaks entirely when two orders share a timestamp.
FunctionOn a tie (100, 100, 90)
ROW_NUMBER()1, 2, 3 — always distinct, tie broken arbitrarily
RANK()1, 1, 3 — ties share, then a gap
DENSE_RANK()1, 1, 2 — ties share, no gap
LAG() / LEAD()The previous / next row’s value — ideal for "change since last month"

Paging, and writing data

paging — always with a deterministic ORDER BY
SELECT   o.Id, o.Total
FROM     dbo.Orders o
ORDER BY o.CreatedAtUtc DESC, o.Id DESC   -- Id breaks ties: without it,
OFFSET   @skip ROWS                       -- rows can repeat or vanish across pages
FETCH NEXT @take ROWS ONLY;
Line by line
  • OFFSET @skip ROWS FETCH NEXT @take ROWS ONLY — the ANSI paging syntax, and it requires ORDER BY. SQL Server rejects it otherwise, which is unusually helpful.
  • ORDER BY o.CreatedAtUtc DESC, o.Id DESC — the second column is the entire point. Without a tie-breaker the order among equal timestamps is undefined and may differ between executions, so a row can appear on page 2 and again on page 3 while another is never shown at all.
  • The ordering must be deterministic, not merely present. This is the bug that reaches production because it never reproduces on a small test dataset.
  • @skip and @take — parameters, so the plan is reused rather than recompiled per page.
  • It gets slower as the offset grows, because the server still produces and discards the skipped rows. Page 5000 is genuinely expensive; keyset paging — WHERE (CreatedAtUtc, Id) < (@lastDate, @lastId) — is the fix when it matters.
insert, update, delete — and OUTPUT
INSERT INTO dbo.Orders (OrderNumber, CustomerId, Total)
OUTPUT inserted.Id                       -- returns the new key, no second round trip
VALUES (@number, @customerId, @total);

UPDATE dbo.Orders
SET    Status = 3
WHERE  Id = @id AND Status = 2;         -- guard: only from the expected state

DELETE FROM dbo.Orders WHERE Id = @id;
Line by line
  • INSERT INTO ... (columns) VALUES (...) — always name the columns. An INSERT without a column list breaks the day someone adds one.
  • OUTPUT inserted.Id — returns the generated key as part of the same statement. No second round trip, and unlike SCOPE_IDENTITY() it works for multi-row inserts.
  • inserted — a pseudo-table available in OUTPUT, alongside deleted. An UPDATE has both, which makes writing an audit trail a one-liner.
  • WHERE Id = @id AND Status = 2 — the guard, and the whole lesson of this block. It updates only from the expected state, so two concurrent submissions cannot both succeed. Check @@ROWCOUNT afterwards: zero means someone else got there first.
  • Compare-and-set in one statement beats SELECT then UPDATE, which has a gap between the two where another session can act.
  • DELETE FROM ... WHERE Id = @id — and note what is absent: run any DELETE or UPDATE as a SELECT first. A missing WHERE is instant and total.
⚠ Write the WHERE clause first

An UPDATE or DELETE without a WHERE hits every row in the table, and it is committed the instant you press F5. The professional habit: type the WHERE before the SET, run it as a SELECT first to see what you are about to touch, and on production wrap it in an explicit transaction you can ROLLBACK.

⚠ MERGE — the upsert that looks perfect

Sooner or later somebody suggests MERGE for "insert it if it is not there, otherwise update it". It reads beautifully and it has a long, well-documented history of correctness problems. The one that still bites on a current version is concurrency: 

-- Two sessions run this at the same moment. Both check, both find nothing,
-- both insert. One of them gets a primary key violation — because MERGE does
-- NOT take a range lock by default.
MERGE dbo.Stock AS t
USING (SELECT @sku AS Sku) AS s ON t.Sku = s.Sku
WHEN MATCHED THEN UPDATE SET t.Qty = t.Qty + @qty
WHEN NOT MATCHED THEN INSERT (Sku, Qty) VALUES (@sku, @qty);
Line by line
  • MERGE — upsert in one statement: update when the row exists, insert when it does not. It reads beautifully and it is a trap.
  • USING (SELECT @sku AS Sku) AS s ON t.Sku = s.Sku — a one-row source joined to the target on the key.
  • It does not take a range lock by default. Two sessions can both evaluate NOT MATCHED, both proceed to insert, and one receives a primary key violation.
  • Under low concurrency it passes every test. This is the shape of bug that survives review and code coverage and appears the first busy afternoon.
  • MERGE has a long list of correctness bugs beyond this one, which is why a good deal of production advice is simply not to use it. The next block is the boring, correct alternative.

Making it safe means WITH (HOLDLOCK) on the target — which people forget, because nothing in the syntax suggests it is needed. The plainer form below is longer, has no surprises, and is what most teams settle on: 

BEGIN TRANSACTION;

UPDATE dbo.Stock WITH (UPDLOCK, HOLDLOCK)
SET    Qty = Qty + @qty
WHERE  Sku = @sku;

IF @@ROWCOUNT = 0
    INSERT INTO dbo.Stock (Sku, Qty) VALUES (@sku, @qty);

COMMIT;
Line by line
  • BEGIN TRANSACTION ... COMMIT — both statements succeed or neither does. Necessary, because the update and the insert must be one indivisible decision.
  • WITH (UPDLOCK, HOLDLOCK) — a table hint, and the reason this version is correct. UPDLOCK takes an update lock immediately rather than a shared one; HOLDLOCK keeps it, and the key range, until the transaction ends. A second session must wait rather than concluding the row is absent.
  • Update first, insert second — and it matters. The update establishes the lock on the key range before anyone decides whether to insert.
  • IF @@ROWCOUNT = 0 — @@ROWCOUNT holds the rows affected by the immediately preceding statement. Read it at once: any statement in between, even an IF, resets it.
  • It is longer and less elegant than MERGE, and it is correct. That trade is the whole point of the pair.

Worth being able to say in an interview: "I know MERGE, and I avoid it for upserts because it needs HOLDLOCK to be concurrency-safe and that is easy to forget." Knowing a feature and choosing not to use it is a stronger answer than not knowing it.

Parameters and stored procedures

✗ string concatenation — SQL injection
// Never. If name is:  '; DROP TABLE Orders; --
var sql = $"SELECT * FROM Customers WHERE Name = '{name}'";
Line by line
  • $"...{name}..." — C# string interpolation building SQL by concatenation. The value becomes part of the statement text.
  • '; DROP TABLE Orders; -- — read what it does to the finished string. The ' closes the literal, the ; ends the statement, a new one begins, and -- comments out whatever was left.
  • The database is not at fault. It receives a syntactically valid batch of two statements and executes exactly what it was sent. There is no flaw to patch.
  • Escaping quotes is not the fix. Numeric contexts need no quotes at all, and Unicode has several characters that normalise to an apostrophe. Every hand-rolled escaper has eventually been defeated.
  • Note this is not only about attackers: the Italian surname D'Angelo breaks this query by accident, today.
✓ parameters — data can never become code
// ADO.NET
using var cmd = new SqlCommand(
    "SELECT Id, Total FROM dbo.Orders WHERE CustomerId = @customerId", conn);
cmd.Parameters.Add("@customerId", SqlDbType.Int).Value = customerId;

// EF Core raw SQL — interpolation here IS parameterised, deliberately
var rows = await db.Orders
    .FromSqlInterpolated($"SELECT * FROM dbo.Orders WHERE CustomerId = {customerId}")
    .ToListAsync(ct);
Line by line
  • "... WHERE CustomerId = @customerId" — the SQL contains a placeholder, not a value. The statement text is fixed before any user input exists.
  • cmd.Parameters.Add("@customerId", SqlDbType.Int).Value = customerId; — the value travels separately, in the protocol, and is never parsed as SQL. That is the actual mechanism: not escaping, but separation.
  • SqlDbType.Int — stating the type explicitly. Letting ADO.NET infer it can produce a type mismatch that forces an implicit conversion and quietly prevents an index seek.
  • using var cmd = ... — the command holds unmanaged resources; dispose it, per chapter 08.
  • FromSqlInterpolated($"... {customerId}") — looks exactly like the vulnerable version and is safe. EF Core takes the interpolated string as an FormattableString, pulls the holes out and converts them to parameters.
  • The dangerous sibling is FromSqlRaw with a string you built yourself. The names are chosen deliberately: Raw means you are responsible.
  • A second reason, beyond security: parameterised statements are reused from the plan cache. Concatenated SQL produces a new plan per distinct value and can flood the cache on its own.

Parameters are not only about security. A parameterised query is cached by the engine as a single plan; a thousand concatenated variants produce a thousand plans and evict everything else from the cache.

a stored procedure — you will meet plenty of these
CREATE OR ALTER PROCEDURE dbo.usp_GetCustomerOrders
    @CustomerId INT,
    @From       DATETIME2(3) = NULL
AS
BEGIN
    SET NOCOUNT ON;                  -- suppress "n rows affected" chatter

    SELECT   o.Id, o.OrderNumber, o.Total, o.CreatedAtUtc
    FROM     dbo.Orders o
    WHERE    o.CustomerId = @CustomerId
      AND    (@From IS NULL OR o.CreatedAtUtc >= @From)
    ORDER BY o.CreatedAtUtc DESC;
END;
Line by line
  • CREATE OR ALTER PROCEDURE — creates it or replaces the body, preserving permissions. Better than DROP plus CREATE, which loses them, and it makes the script re-runnable.
  • @CustomerId INT — a required parameter. @From DATETIME2(3) = NULL has a default, so it is optional.
  • AS BEGIN ... END — the body. BEGIN/END is optional for a procedure and universally written anyway.
  • SET NOCOUNT ON — suppresses the "n rows affected" messages. Not cosmetic: those extra network packets measurably slow a chatty procedure, and some client libraries mistake them for result sets.
  • (@From IS NULL OR o.CreatedAtUtc >= @From) — the optional-parameter idiom: when the parameter is not supplied the condition is always true.
  • The cost of that idiom is parameter sniffing. SQL Server caches a plan built for the first set of values it sees, and one plan may suit @From null and be terrible when it is supplied. OPTION (RECOMPILE) is the usual remedy, and chapter 11 covers why.
  • ORDER BY o.CreatedAtUtc DESC — ordering inside the procedure, so callers do not each re-sort.
Try it yourself

Five exercises against the schema from chapter 09, in increasing difficulty:

  1. Every customer with their order count — including those with zero.
  2. The top 5 customers by revenue in the last 90 days.
  3. Each customer’s most recent order, one row each. (ROW_NUMBER.)
  4. Month-by-month revenue with the change versus the previous month. (LAG.)
  5. Customers who ordered in 2025 but not in 2026. (NOT EXISTS — and think about why NOT IN is dangerous here.)

Number 1 is the one people get wrong: an INNER JOIN silently drops the zeros, and COUNT(*) turns them into ones.

Golden rules

  1. Logical order is FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Almost every beginner error follows from it.
  2. WHERE filters rows, HAVING filters groups.
  3. ON filters the join; WHERE filters the result. On an outer join these differ, and putting the condition in WHERE silently makes it an inner join.
  4. LEFT JOIN … WHERE right.Id IS NULL is the anti-join: "things with no match".
  5. COUNT(*) counts rows; COUNT(col) ignores NULL. After an outer join, that is the whole answer.
  6. CTEs for readability and recursion, not for speed.
  7. Window functions keep every row and still let it see its neighbours. ROW_NUMBER() OVER (PARTITION BY … ORDER BY …) then WHERE rn = 1 is the "latest per group" idiom — learn it by heart.
  8. Paging needs a deterministic ORDER BY, tie-broken by a unique column.
  9. Always parameterise. It prevents injection and keeps the plan cache sane.
  10. Write the WHERE before the SET. Run it as a SELECT first.

Interview questions

"Difference between WHERE and HAVING?"

WHERE filters rows before grouping; HAVING filters groups afterwards, which is why only HAVING may reference an aggregate.

"Difference between INNER and LEFT JOIN?"

Inner keeps only matched rows; left keeps every row from the left side, filling the right with NULL. Then volunteer the trap — a condition on the right table in WHERE turns it back into an inner join.

"Write me the most recent order per customer."

ROW_NUMBER() OVER (PARTITION BY CustomerId ORDER BY CreatedAtUtc DESC) in a CTE, then WHERE rn = 1. Mention the correlated-subquery alternative and say the window function usually plans better — it shows you know there is more than one answer.

"UNION or UNION ALL?"

UNION removes duplicates, which costs a sort or hash. UNION ALL just concatenates. Default to UNION ALL unless you actually need de-duplication.

"How do you prevent SQL injection?"

Parameterised queries — never string concatenation, and note that dynamic SQL inside a stored procedure is just as vulnerable. Add least-privilege database accounts as defence in depth, and mention the plan-cache benefit to show you understand the second reason.
