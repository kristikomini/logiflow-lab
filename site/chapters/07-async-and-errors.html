Async, await and exceptions

Every Web API method you will write is async. Most developers use the keyword for years without being able to say what it does — and then hit a deadlock in production and have nowhere to start. This chapter is the mental model, plus the failure handling that belongs next to it.

From the advert

"Ottima conoscenza del linguaggio C#" plus "sviluppo di Web API". Async is where those two meet: it is the single biggest determinant of how many requests a server can handle.

Why async exists at all

🧒 Simple

A waiter takes your order and walks it to the kitchen. Now — should he stand at the kitchen door and stare at your pasta until it is ready?

Of course not. He goes and serves four other tables, and comes back when the bell rings. One waiter, five tables. That is async.

The important detail: waiting faster is not the goal. Your pasta takes exactly as long either way. What changes is how many other people get served while it cooks.

🎓 Professional

A thread costs about 1 MB of stack and is a scarce, OS-scheduled resource. During an I/O operation — a database round trip, an HTTP call, a file read — a synchronous thread is blocked: consuming memory, contributing nothing.

await on an I/O operation releases the thread back to the thread pool. The operation continues at the hardware/OS level with no thread at all, and when it completes a continuation is scheduled onto some available thread. The result is throughput, not latency: the same hardware serves far more concurrent requests. An individual request is not faster — very slightly slower, in fact.

⚠ Async is not "another thread"

The most common misconception. await httpClient.GetAsync(...) does not start a thread — it frees one. Only Task.Run moves work to a pool thread, and that is for CPU-bound work. Wrapping an I/O call in Task.Run makes things strictly worse: you now occupy a thread and pay for the switch.

What await actually compiles to

🎓 Professional

The compiler rewrites an async method into a state machine: a generated type with a field per local variable and an integer recording which await you stopped at. Calling the method runs it synchronously until the first await of an incomplete task; at that point it registers a continuation and returns a Task to the caller. When the awaited operation finishes, the continuation resumes the method at the recorded state.

Two consequences worth stating in an interview: the code after an await may run on a different thread, and if the awaited task is already complete there is no suspension at all — it just carries on, which is why a well-written async method has almost no overhead on the fast path.

the shape you write, every day
public async Task<OrderDto?> GetAsync(int id, CancellationToken ct)
{
    // runs synchronously up to here
    var order = await _db.Orders
        .AsNoTracking()
        .FirstOrDefaultAsync(o => o.Id == id, ct);   // ← thread released

    // resumes here, possibly on a different thread
    if (order is null) return null;

    return new OrderDto(order.Id, order.Total, order.Status);
}
Line by line
  • public async Task<OrderDto?> GetAsync(...) — async is an implementation detail, not part of the signature's contract. It permits await inside and makes the compiler rewrite the body into a state machine. A caller cannot tell, which is why interfaces never declare it.
  • Task<OrderDto?> — a promise of a value, later. The ? belongs to OrderDto: the eventual result may be null.
  • The body runs synchronously to the first await. Calling an async method does not hand anything to a thread pool; it just starts running on the caller's thread.
  • .AsNoTracking() — tells EF Core not to keep a change-tracking snapshot. Correct for a read-only query and measurably cheaper; wrong the moment you intend to modify what comes back.
  • await — the release point. If the operation has not completed, the method returns to its caller and the thread goes back to the pool to serve other requests. It does not block and it does not create a thread.
  • , ct) — the token passed to the database call. Without it the query keeps running after the caller has given up.
  • Execution resumes on a different thread in ASP.NET Core, because there is no synchronization context to capture. Anything thread-affine — a ThreadLocal, a UI control — is therefore unsafe across an await.
  • return new OrderDto(...) — a plain value. The compiler wraps it in the Task the signature promised; you never write that yourself.

⚠ async void — the one that takes the process down

An async void method returns nothing, so there is no Task to await and nothing to carry an exception back to the caller. An exception thrown inside it is raised on the synchronization context and crashes the process. It also cannot be awaited, so callers cannot know when it finished. The only legitimate use is an event handler, whose signature you do not control.

The deadlock: .Result and .Wait()

🧒 Simple

You send your little brother upstairs to fetch a book, and you stand in the doorway to wait. He comes back down — but the doorway is completely blocked by you, waiting for him. He cannot get through, so he never finishes, so you never stop waiting. Both of you are stuck there for ever.

🎓 Professional

In a context with a single-threaded SynchronizationContext — classic ASP.NET, WinForms, WPF — the continuation after an await is posted back to that context. If the calling thread is blocked in .Result, the context is occupied and the continuation can never run. The task never completes; the block never releases. A classic deadlock, and one that typically appears only under load.

ASP.NET Core has no synchronization context, so this specific deadlock is far less likely there — but blocking still burns a thread pool thread, and under load causes thread pool starvation, which looks identical from the outside.

the rule with no exceptions
// ✗ never
var order = GetOrderAsync(id).Result;
GetOrderAsync(id).Wait();
var x = GetOrderAsync(id).GetAwaiter().GetResult();

// ✓ async all the way up — the caller becomes async too, and so does its caller,
//   until you reach the framework, which is async already.
var order = await GetOrderAsync(id);
Line by line
  • .Result and .Wait() — both block the current thread until the task finishes. That undoes the entire point: a thread that could have served another request is parked doing nothing.
  • The deadlock. Where a synchronization context exists — WinForms, WPF, old ASP.NET — the continuation after await must run on the captured context. If that context's one thread is the thread now blocked in .Result, the continuation can never run, and the thread can never unblock. Permanent, and it looks like a hang rather than a crash.
  • .GetAwaiter().GetResult() — the same block, chosen because it throws the original exception instead of an AggregateException wrapper. It fixes the error message and not the deadlock.
  • It is worse under load. It usually passes in development, where there is one user, and deadlocks in production when the pool is saturated — the hardest failure to reproduce.
  • await GetOrderAsync(id) — the fix, and it is contagious on purpose. The caller becomes async, and its caller, up to the framework, which was async already. "Async all the way" is a description of the only shape that works.

"Async all the way" is not a stylistic preference. There is no safe way to block on async code in a general library, which is why the guidance is absolute.

ConfigureAwait(false)

In library code, await something.ConfigureAwait(false) says "resume anywhere; I do not need the original context." It avoids the deadlock above and is slightly faster. In an ASP.NET Core application it is unnecessary (there is no context to capture) and most teams omit it. Knowing why the answer differs is the point of the question.

CancellationToken

When a user closes the browser tab, ASP.NET Core cancels the request token. If you passed it down, the database query is abandoned and the work stops. If you did not, your server keeps computing an answer nobody will ever read.

pass it down, always
[HttpGet("{id:int}")]
public async Task<IActionResult> Get(int id, CancellationToken ct)
{                                     // ↑ ASP.NET Core supplies this automatically
    var dto = await _service.GetAsync(id, ct);
    return dto is null ? NotFound() : Ok(dto);
}

// In a long loop, check it yourself:
foreach (var batch in batches)
{
    ct.ThrowIfCancellationRequested();
    await ProcessAsync(batch, ct);
}
Line by line
  • [HttpGet("{id:int}")] — the route, with :int as a constraint, so a non-numeric id never reaches the method.
  • CancellationToken ct — ASP.NET Core supplies this automatically. You declare the parameter and the framework binds it; it is triggered when the client disconnects.
  • A token is a signal, not a power. Nothing is forcibly stopped. It carries a flag that cooperating code chooses to observe, which is why passing it down every call is the entire mechanism.
  • ct.ThrowIfCancellationRequested() — for loops that do your own work, where there is no library call to hand the token to. It throws OperationCanceledException when the flag is set.
  • That exception is not an error. ASP.NET Core translates it to a 499-style abort and does not log it as a failure. Catching it and returning a normal result turns a cancelled request into a fabricated answer.
  • await ProcessAsync(batch, ct) — the token continues downward. A token that stops being passed on is the commonest reason cancellation "does not work".

Running things at the same time

sequential vs parallel
// Sequential — 300 ms, and only if the second genuinely needs the first
var customer = await GetCustomerAsync(id, ct);      // 100 ms
var orders   = await GetOrdersAsync(id, ct);        // 200 ms

// Concurrent — 200 ms. Start both, then await both.
var customerTask = GetCustomerAsync(id, ct);
var ordersTask   = GetOrdersAsync(id, ct);
await Task.WhenAll(customerTask, ordersTask);

var c = await customerTask;
var o = await ordersTask;
Line by line
  • var customer = await GetCustomerAsync(...) then var orders = await GetOrdersAsync(...) — the second call does not start until the first has finished, because await is a suspension point. 100 ms + 200 ms = 300 ms, and the two operations were independent.
  • var customerTask = GetCustomerAsync(id, ct); — no await. Calling an async method starts it and hands back a Task immediately, so by the next line both are in flight.
  • await Task.WhenAll(customerTask, ordersTask) — completes when the slowest completes. Total is 200 ms, not 300. Do not confuse it with Task.WaitAll, which blocks.
  • Exceptions change shape here. If both fail, await Task.WhenAll rethrows only the first. To see them all, inspect Task.Exception on the WhenAll task itself.
  • await customerTask afterwards — already complete, so this simply unwraps the value at no cost. It is also how you rethrow that task's exception if it had one.
  • Do not do this with a DbContext. It is not thread-safe, and two concurrent queries on one context throw. Parallelism here means two independent services, not two queries on one connection.
⚠ Not with a DbContext

DbContext is not thread-safe and permits exactly one operation at a time. Two EF Core queries in a Task.WhenAll on the same context throws "A second operation was started on this context". Concurrency there requires separate contexts, usually via IDbContextFactory.

Exceptions

🧒 Simple

An exception is a fire alarm. When something goes badly wrong, you do not quietly carry on cooking — you stop, and the alarm sounds all the way up the building until somebody whose job it is comes to deal with it.

The worst possible thing is to hear the alarm, switch it off, and say nothing. The building is still on fire; now nobody knows.

🎓 Professional

Exceptions are for the exceptional: conditions the current method cannot handle meaningfully. They are expensive (stack capture and unwinding), so they must never be used for ordinary control flow — "user not found" on a lookup endpoint is a result, not an exception. Catch only where you can do something useful: retry, enrich, translate to an HTTP status, or log and rethrow.

the shapes that matter
try
{
    await _payments.ChargeAsync(order, ct);
}
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.TooManyRequests)
{
    // exception filter: only enters the catch if the condition holds,
    // and — importantly — does NOT unwind the stack to decide
    await Task.Delay(1000, ct);
    await _payments.ChargeAsync(order, ct);
}
catch (PaymentDeclinedException)
{
    throw;          // ✓ rethrow — keeps the original stack trace
    // throw ex;   ✗ resets the stack trace to this line. Never do this.
}
finally
{
    // runs whether or not it threw — cleanup belongs here
    _metrics.RecordAttempt(order.Id);
}
Line by line
  • catch (HttpRequestException ex) when (...) — when is an exception filter. It is evaluated before the stack unwinds, so when it is false the exception carries on with its original stack intact. Catching and rethrowing to achieve the same test destroys that information.
  • ex.StatusCode == HttpStatusCode.TooManyRequests — catching a type is too coarse here; the filter narrows it to the one case that is worth retrying. A 400 is not.
  • await Task.Delay(1000, ct) — asynchronous waiting. Thread.Sleep would block a pool thread for a second. Passing ct means a cancelled request stops waiting at once.
  • throw; — bare, no operand. Rethrows the current exception and preserves the original stack trace.
  • throw ex; — the same variable, and it resets the stack trace to this line. The log then points at your catch block instead of where the failure happened. One character apart, and this is a favourite interview question.
  • finally — runs whether or not an exception was thrown, and whether or not it was caught. Cleanup belongs here, never after the try, because after is skipped on the failing path.
  • Catch what you can act on. A retry, a fallback, a translation to a status code are actions. A catch that logs and swallows converts a loud failure into a corrupted result.

using and IDisposable

The GC reclaims memory. It does not close files, sockets or database connections — those are unmanaged resources, and releasing them is your job.

deterministic cleanup
// using declaration — disposed at the end of the enclosing scope
using var connection = new SqlConnection(cs);
await connection.OpenAsync(ct);

// the async form, when the type implements IAsyncDisposable
await using var stream = file.OpenRead();

// It is exactly this, and the finally runs even if you throw:
// try { ... } finally { connection.Dispose(); }
Line by line
  • using var connection = ... — a using declaration: no braces, no extra nesting. Dispose() is called at the end of the enclosing scope, in a compiler-generated finally.
  • It is exactly a try/finally. Disposal happens even if the block throws, which is the whole reason the construct exists — a connection released only on the happy path is a connection leak under errors, and the pool exhausts.
  • await connection.OpenAsync(ct) — opening a connection is I/O and has an async form. Prefer it over Open().
  • await using — for types implementing IAsyncDisposable. It awaits DisposeAsync(), so flushing a stream does not block a thread. Using plain using on such a type compiles and silently takes the synchronous path.
  • Disposal order is reverse of declaration, like nested blocks, which is what you want when a reader wraps a stream that wraps a file.
  • Do not using something you did not create — an injected HttpClient or DbContext is owned by the container, and disposing it early breaks every later user in the same request.
Try it yourself

Watch the thread actually change. Run this in a console app and note the two ids — then explain why a WinForms app would print the same id twice. 

Console.WriteLine($"before: thread {Environment.CurrentManagedThreadId}");
await Task.Delay(100);
Console.WriteLine($"after:  thread {Environment.CurrentManagedThreadId}");

// Then break it on purpose — from a WinForms button handler, call:
//     var r = SomethingAsync().Result;
// and watch the UI freeze permanently. That is the deadlock, live.
Line by line
  • Environment.CurrentManagedThreadId — the CLR's own thread id, not the OS one. Printing it either side of an await makes the invisible visible.
  • await Task.Delay(100) — a timer, not a sleep. No thread is held for those 100 ms; a continuation is scheduled when the timer fires.
  • The two numbers usually differ in a console app or ASP.NET Core, because there is no synchronization context to resume on and the continuation runs on whichever pool thread is free.
  • Sometimes they match, and that is not a refutation. If the task completed before the await was reached, execution continues synchronously on the same thread — an optimisation, not a guarantee. Never write code that depends on either outcome.
  • SomethingAsync().Result from a WinForms handler — the deadlock, on purpose. The UI has a single-threaded context; the handler blocks it; the continuation needs it. The window stops repainting and never recovers.
  • Do run this one. Ten seconds of a frozen form teaches the rule better than the paragraph above it, and you will never write .Result again.

Golden rules

  1. Async buys throughput, not speed. One request is marginally slower; the server handles far more of them.
  2. await on I/O releases a thread. It does not start one.
  3. Task.Run is for CPU-bound work. Wrapping I/O in it is strictly worse.
  4. Never .Result, .Wait() or .GetAwaiter().GetResult(). Async all the way up.
  5. async void only for event handlers. Elsewhere its exceptions kill the process.
  6. Accept and forward a CancellationToken in every async method that does real work.
  7. Task.WhenAll for independent work — but never two queries on one DbContext.
  8. ConfigureAwait(false) in libraries; unnecessary in ASP.NET Core applications.
  9. throw; preserves the stack trace. throw ex; destroys it.
  10. Expected outcomes are results, not exceptions. Exceptions are expensive and mean exceptional.
  11. Never swallow an exception silently. If you cannot handle it, let it travel.
  12. using for anything holding an unmanaged resource. The GC will not close your connections.

Interview questions

"What does await do?"

It suspends the method, returns a Task to the caller and releases the thread; when the operation completes, a continuation resumes the method at the point it stopped, possibly on a different thread. Add that the compiler implements this as a state machine — it shows you know it is not magic.

"Why does .Result deadlock?"

Because the continuation wants the synchronization context that the blocking call is already occupying. Then show range: it is far less likely in ASP.NET Core, which has no such context, but blocking there still causes thread pool starvation — so the rule stands either way.

"Does async make my application faster?"

No — it makes it scale. A single request is slightly slower because of the state machine; the server handles far more concurrent requests because threads are not sleeping through I/O. Candidates who say "faster" are usually repeating something they read.

"When would you catch Exception?"

At a process boundary where the alternative is a crash: a background service loop, a message consumer, or global exception middleware — and only to log with full context and then either translate it into a response or rethrow. Anywhere else, catch the specific type.

"What is a CancellationToken for?"

Cooperative cancellation. ASP.NET Core signals it when the client disconnects; passing it to EF Core and HttpClient means abandoned work actually stops instead of finishing an answer that nobody will read.
