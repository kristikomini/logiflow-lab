Talking to systems you do not own

Chapter 14 built an API other people call. This one is the other direction: calling somebody else's, receiving their webhooks, and reading the CSV their old system drops on an SFTP server at two in the morning. It is the part of the job with the most tickets and the least teaching.

From the adverts

"Integrazione tra sistemi web e piattaforme esterne" appears as a duty in one advert and "integrazioni web" again in its nice-to-haves. Another lists "realizzare le relative integrazioni di sistema" as a core responsibility. When a requirement is repeated in both halves of an advert, it is not aspiration — it is most of the sprint.

The shape of the problem

🧒 Simple

Everything so far has been about your own house. You decide where the furniture goes and when the lights turn off.

An integration is a phone call to a neighbour. They might not pick up. They might pick up and take four minutes. They might say "yes, done" and have done nothing. They might change their phone number without telling you. You cannot fix any of that — you can only decide what your house does when it happens.

🎓 Professional

Every rule in this chapter follows from one fact: you control one side of the boundary. Inside your service a method call either returns or throws. Across a network to a system you do not own there is a third outcome — you do not know — and the timeout is exactly the case where the work may well have succeeded.

That is the same three-outcome problem chapter 22 introduced for message queues. Integration is distributed systems with a smaller vocabulary.

Typed clients, and the two bugs everyone ships first

✗ both of these are wrong, in opposite directions
// ✗ 1. A new client per call. HttpClient is disposable, so this looks correct
//      and is the single most common .NET networking bug: each disposal leaves
//      a socket in TIME_WAIT for minutes. Under load you exhaust the ports and
//      the exception says "address in use" — which sounds like a server problem.
using var client = new HttpClient();
var res = await client.GetAsync(url);

// ✗ 2. One static client forever. Fixes the sockets, and now the connection
//      never notices that DNS changed — so a failover the other side performed
//      is invisible to you until a restart.
private static readonly HttpClient Shared = new();
✓ a typed client, registered once
// Program.cs — IHttpClientFactory pools the handlers and rotates them
// (two minutes by default), which solves both problems at once.
builder.Services.AddHttpClient<ICarrierApi, CarrierApi>(c =>
{
    c.BaseAddress = new Uri(options.BaseUrl);
    c.Timeout     = TimeSpan.FromSeconds(10);   // ALWAYS. The default is 100s,
                                                 // which is forever under load.
});

// …and the client itself takes HttpClient in its constructor. Nothing else
// in the application knows that this dependency is HTTP at all.
public sealed class CarrierApi(HttpClient http) : ICarrierApi
{
    public async Task<TrackingResult> TrackAsync(string code, CancellationToken ct)
    {
        using var res = await http.GetAsync($"v2/parcels/{code}", ct);
        if (res.StatusCode == HttpStatusCode.NotFound) return TrackingResult.Unknown;
        res.EnsureSuccessStatusCode();
        return Map(await res.Content.ReadFromJsonAsync<CarrierParcelDto>(ct));
    }
}
⚠ Injecting HttpClient is not injecting a singleton

The HttpClient you receive is cheap and short-lived; the expensive HttpMessageHandler underneath it is the thing being pooled. That is why a typed client should be registered transient (the default) and why capturing the injected HttpClient in a static field puts you straight back into bug 2. Chapter 10's captive-dependency rule, wearing a different hat.

Authenticating outbound

An API key in a header is the easy case — put it in configuration, never in the repository, and read chapter 15 again. The one worth learning properly is OAuth2 client credentials, because it is what every serious platform uses for server-to-server calls.

a DelegatingHandler — middleware for outgoing requests
public sealed class BearerTokenHandler(ITokenProvider tokens) : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage req, CancellationToken ct)
    {
        var token = await tokens.GetAsync(ct);      // cached; refreshes itself
        req.Headers.Authorization = new("Bearer", token);

        var res = await base.SendAsync(req, ct);

        // One retry on 401 — their token lifetime and your clock will disagree
        // eventually, and this is the difference between a nightly blip and a
        // 3am phone call. Exactly once: a loop here is an outage.
        if (res.StatusCode == HttpStatusCode.Unauthorized)
        {
            res.Dispose();
            req.Headers.Authorization = new("Bearer", await tokens.RefreshAsync(ct));
            res = await base.SendAsync(req, ct);
        }
        return res;
    }
}

// Program.cs
builder.Services.AddTransient<BearerTokenHandler>();
builder.Services.AddHttpClient<ICarrierApi, CarrierApi>()
       .AddHttpMessageHandler<BearerTokenHandler>();
⚠ The token stampede

Cache the token, but make the refresh single-flight — one SemaphoreSlim, or a shared Task everyone awaits. Otherwise the moment it expires, fifty concurrent requests all discover this at once and fire fifty token requests, and the identity provider rate-limits you. Refresh at 80% of the lifetime rather than at expiry, and the problem mostly stops existing.

Resilience: timeout, retry, circuit breaker

the standard handler does all four
// package: Microsoft.Extensions.Http.Resilience  (Polly v8 underneath)
builder.Services.AddHttpClient<ICarrierApi, CarrierApi>()
       .AddStandardResilienceHandler();

// …or spelled out, when you need to say why each number is what it is:
       .AddResilienceHandler("carrier", b => b
           .AddTimeout(TimeSpan.FromSeconds(5))          // per attempt
           .AddRetry(new()
           {
               MaxRetryAttempts = 3,
               BackoffType      = DelayBackoffType.Exponential,
               UseJitter        = true    // ← not optional. See below.
           })
           .AddCircuitBreaker(new() { FailureRatio = 0.5, MinimumThroughput = 10 })
           .AddTimeout(TimeSpan.FromSeconds(30)));       // total, across all attempts
🎓 Why each piece is there
  • Timeout — both kinds. A per-attempt timeout stops one slow call; a total timeout stops three retries of a slow call adding up to ninety seconds while your caller waits.
  • Jitter — without it, every instance that failed during the same one-second outage retries at exactly the same moment, twice, and finishes the job the outage started. Randomising the delay is what makes retry safe at scale.
  • Circuit breaker — after enough failures, stop calling and fail immediately for a while, then let one request through to test the water. It protects them from your retries and you from queueing every thread against a dead dependency.
⚠ A retry without idempotency is a duplicate order

Retrying GET is free. Retrying POST /orders after a timeout is how a customer is charged twice — because a timeout does not mean it failed, it means you do not know. Either the operation is idempotent, or you must not retry it blindly. 

// The standard answer: a key YOU generate, stable across retries, that
// they use to recognise a repeat. Most serious APIs support this header;
// if theirs does not, ask what does — there is usually something.
req.Headers.Add("Idempotency-Key", order.Id.ToString());

Chapter 22 makes the general argument. This is the same rule pointing outwards.

Never let their model into yours

This is the rule that decides whether the integration is a contained annoyance or a slow leak through the whole codebase.

✗ their shape, spreading
// Their DTO, deserialised and passed straight into the domain. Now their
// nullable string status, their date format and their spelling of "cancelled"
// are load-bearing in YOUR entities — and their next version breaks you
// in twenty places.
public class CarrierParcelDto
{
    public string? parcel_status { get; set; }     // "IN_TRANSIT", "DELIVERED", "CANC"
    public string? eta { get; set; }               // "2026-03-04 14:00" — no zone. Whose?
}
✓ one translation, in one place
// The DTO stays internal to the Infrastructure project and is mapped at the
// boundary. Chapter 23's dependency rule, applied to a third party:
// the domain must not know this system exists.
private static TrackingResult Map(CarrierParcelDto d) => new(
    Status: d.parcel_status switch
    {
        "IN_TRANSIT" => TrackingStatus.InTransit,
        "DELIVERED"  => TrackingStatus.Delivered,
        "CANC"       => TrackingStatus.Cancelled,
        // The important arm. An unknown value is THEIR new feature, and
        // guessing is worse than admitting it.
        _            => TrackingStatus.Unknown
    },
    Eta: DateTime.TryParse(d.eta, CultureInfo.InvariantCulture,
                          DateTimeStyles.AssumeUniversal, out var t)
         ? t : null);
Read that date parse again

InvariantCulture, explicitly, and an assumption about the time zone stated in code rather than inherited from the server's locale. An integration is exactly where chapter 23's culture rules stop being theoretical: their "03/04/2026" is the fourth of March or the third of April depending on who wrote it, and nobody will tell you which.

Receiving: webhooks

The other half of integration is an endpoint they call. It is a public, unauthenticated URL that causes writes in your database, which makes it the most security-sensitive endpoint you will write.

the four rules, in one endpoint
app.MapPost("/webhooks/carrier", async (
    HttpRequest req, IWebhookQueue queue, IOptions<CarrierOptions> opt,
    CancellationToken ct) =>
{
    // 1. Read the RAW body. Deserialising and re-serialising changes the bytes
    //    — whitespace, key order, number formatting — and the signature will
    //    never match again. This is the bug that costs a whole day.
    req.EnableBuffering();
    using var reader = new StreamReader(req.Body, leaveOpen: true);
    var raw = await reader.ReadToEndAsync(ct);

    // 2. Verify the signature in constant time. SequenceEqual leaks timing;
    //    CryptographicOperations.FixedTimeEquals does not.
    var expected = HMACSHA256.HashData(opt.Value.SecretBytes, Encoding.UTF8.GetBytes(raw));
    var given    = Convert.FromHexString(req.Headers["X-Signature"]!);
    if (!CryptographicOperations.FixedTimeEquals(expected, given))
        return Results.Unauthorized();

    // 3. Reject anything old, so a captured request cannot be replayed forever.
    if (DateTimeOffset.UtcNow - Timestamp(req) > TimeSpan.FromMinutes(5))
        return Results.Unauthorized();

    // 4. Queue and return FAST. They will time out and redeliver if you do the
    //    work inline — which is how one event becomes four.
    await queue.EnqueueAsync(raw, ct);
    return Results.Accepted();
});
⚠ You will receive the same event twice

Every webhook provider is at-least-once. A network hiccup on their side after you committed means they retry, and the second delivery is identical. Store the provider's event id and ignore one you have already processed — the same idempotency table chapter 22 uses for messages. Assume duplicates rather than hoping.

The integration nobody puts on a slide: files

In a manufacturing or logistics company in this region, a large share of "integrazione" is a fixed-width or CSV file on an SFTP server, produced by a system older than you are. It is unglamorous and it is on the ticket.

⚠ The four things that actually go wrong
  1. Encoding. The file is Windows-1252, not UTF-8, and "Società" arrives as "Societ?" — or worse, arrives fine on your machine and broken on the Linux container. State the encoding explicitly; never take the default. On .NET you need Encoding.RegisterProvider(CodePagesEncodingProvider.Instance) before you can even ask for 1252.
  2. Culture. Their 1.234,56 is Italian for one thousand two hundred and thirty-four point five six. Parse it with InvariantCulture and you get either an exception or, far worse, 1.23456. This is chapter 23's demo, arriving as a production incident.
  3. Half-written files. You will read a file while it is still uploading. The convention that fixes it: the sender writes orders.tmp and renames it to orders.csv, because rename is atomic. If they will not, wait for the size to stop changing.
  4. Reprocessing. Move each file to processed/ or failed/ when you are done. A folder you only read from will eventually be read twice.

Testing an integration without the third party

a stub handler — no package, no network, works in any test
public sealed class StubHandler(HttpStatusCode code, string body) : HttpMessageHandler
{
    public List<HttpRequestMessage> Seen { get; } = [];

    protected override Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage req, CancellationToken ct)
    {
        Seen.Add(req);
        return Task.FromResult(new HttpResponseMessage(code)
        {
            Content = new StringContent(body, Encoding.UTF8, "application/json")
        });
    }
}

// The tests that actually matter are the unhappy ones:
[Fact] public async Task Unknown_status_does_not_throw() { … }        // their new enum value
[Fact] public async Task Timeout_is_not_treated_as_failure() { … }
[Fact] public async Task Retries_stop_after_three() { … }
[Fact] public async Task Malformed_json_is_reported_not_swallowed() { … }

For anything larger, WireMock.Net gives you a real HTTP server in the test process that you can program with responses, delays and failures — which is the only practical way to test a circuit breaker. And keep one recorded real response per endpoint as a fixture: when they change their payload silently, that file is the evidence.

Try it yourself
  1. Register a typed client against any free public API with a 2-second timeout. Point it at a URL that never responds and watch the timeout fire. Then remove the timeout and wait a hundred seconds, once, so the default stops being abstract.
  2. Add AddStandardResilienceHandler(), point it at a URL returning 500, and log each attempt. Count the retries and measure the gaps.
  3. Turn jitter off and run ten clients at once. Watch the attempts line up.
  4. Write the webhook endpoint above. Sign a request correctly with a small script, then change one space in the JSON and watch the signature fail. That is the raw-body lesson, learned cheaply.
  5. Save an Italian CSV with 1.234,56 in it from Excel. Read it with InvariantCulture and then with it-IT. Note that one of the wrong answers does not throw.

Golden rules

  1. Across a boundary there are three outcomes, not two. Success, failure, and unknown — and the timeout is the interesting one.
  2. Never new HttpClient() per call, never one static forever. Register a typed client and let IHttpClientFactory rotate the handler.
  3. Set an explicit timeout on every outbound client. The 100-second default is not a timeout, it is a hang.
  4. Retry only what is safe to repeat. A retried POST without an idempotency key is a duplicate order.
  5. Always jitter the backoff. Synchronised retries turn their blip into their outage.
  6. A circuit breaker protects both sides. Fail fast rather than queueing every thread against a dead dependency.
  7. Honour Retry-After over your own schedule. They know when they will be ready; you are guessing.
  8. Map their DTO to your model at the boundary, in one place — and give the unknown value an explicit arm.
  9. Parse their dates and numbers with an explicit culture. The default is the server's locale, and it will differ from your laptop's.
  10. Verify a webhook against the raw body, in constant time, reject stale timestamps, queue the work and answer immediately.
  11. Assume every event and every file arrives twice. Deduplicate on their id; move files once processed.
  12. Test the failures, not the happy path. The happy path was never the problem.

Interview questions

"Why should you not create a new HttpClient for every request?"

Disposing it leaves the underlying socket in TIME_WAIT for minutes, so under load you exhaust the ephemeral ports and start seeing "address in use" — which looks like a server fault, not a client bug. But then give the second half, or the answer is incomplete: a single static client fixes the sockets and never picks up DNS changes. IHttpClientFactory solves both by pooling handlers and rotating them, which is why a typed client is the right default.

"Your call to a partner API times out. Do you retry?"

It depends on whether the operation is idempotent, because a timeout means unknown, not failed — the work may have completed. For a GET, retry freely. For a POST that creates something, either send an idempotency key that lets them recognise the repeat, or query first to see whether it landed. Retrying blindly is how a customer gets charged twice.

"What is a circuit breaker, and why not just retry?"

After a threshold of failures it opens and fails immediately for a cooling-off period, then lets a trial request through. Retrying alone makes an overloaded dependency worse — you add traffic exactly when it cannot cope — and meanwhile every one of your threads is parked waiting, so their outage becomes yours. The breaker protects both sides. Pair it with jittered backoff so your instances do not all retry in unison.

"How do you secure a webhook endpoint?"

Verify an HMAC signature computed over the raw request body — deserialising and re-serialising changes the bytes and the signature will never match — compare it in constant time with FixedTimeEquals, and reject requests whose timestamp is old so a captured call cannot be replayed. Then acknowledge quickly and do the work on a queue, because if you process inline they will time out and redeliver. And deduplicate on their event id, since every provider is at-least-once.

"They return a status value your code has never seen. What happens?"

It should map to an explicit unknown rather than throw or silently pick a default, because their new enum value is a normal event and it must not take your service down. That is the argument for translating their DTO into your own model at the boundary: the unknown value is handled once, in one place, instead of leaking through every layer that touched their type.

"How would you test code that calls an external API?"

Inject the client behind an interface, and test the mapping and the failure handling with a stub HttpMessageHandler — no network, no flakiness. Use WireMock.Net when the behaviour under test is HTTP-level, like retries or a circuit breaker, since you need real responses and delays. Keep one recorded real payload as a fixture so a silent change on their side shows up as a failing test rather than a production surprise. And test the unhappy paths; the happy one was never the risk.
