AWS, for someone who knows Azure

This is the shortest chapter here, deliberately. AWS appears in these adverts as skill facoltativa and as "gradita esperienza o familiarità" — never as a requirement. The goal is not competence, it is credibility: enough to say what you would use, deploy something small, and answer the follow-up without bluffing.

From the adverts

"Utilizzo di ambienti cloud Azure e/o AWS per deployment e supporto applicativo" in one advert's duties, and "gradita esperienza o familiarità con Azure e AWS" in its requirements. Another lists AWS alone under skill facoltative.

The e/o is doing the work. They have one of the two and would like you to not be frightened of the other. Chapter 29 covered Azure properly; this is the translation.

🎓 The two differences that actually change how you work
  • There is no resource group. Azure gives you a container you can delete to remove everything; AWS does not. Grouping is by tags, and isolation is by account — separate accounts for dev, staging and production is the normal pattern, not an enterprise luxury. Deleting an environment is a real task rather than one click, which is why infrastructure-as-code matters more here.
  • IAM is stricter and more explicit. Nothing can talk to anything until a policy says so. Coming from Azure this feels like friction for the first week and like a safety rail afterwards.

IAM, in one page

🧒 Simple

A user is a person with their own keys to the building. They keep those keys forever, and if they lose them, whoever finds them can walk in.

A role is a badge kept at reception. You borrow it, it works for an hour, and then it stops. If someone steals it, it has already expired.

Give machines badges, never keys.

what that means concretely

RDS for SQL Server: the differences that catch people

⚠ You are not sysadmin, and BACKUP DATABASE does not work

RDS is a managed instance, so Amazon keeps the highest privileges. The three things that surprise a .NET developer on day one:

  • Native backup and restore are replaced. BACKUP DATABASE … TO DISK fails; you call the stored procedures msdb.dbo.rds_backup_database and rds_restore_database, which move .bak files to and from an S3 bucket. Restoring the production database onto your machine is therefore a different procedure from the one you know.
  • No xp_cmdshell, no filesystem, no OS access. Anything a legacy procedure did by shelling out has to move into the application.
  • Multi-AZ failover changes the connection, not the name. The endpoint stays the same and DNS repoints — which is exactly the situation where a long-lived pooled connection or a cached DNS entry bites you. Enable connection resiliency (EnableRetryOnFailure) and mean it.

Lambda with .NET, briefly

Lambda runs a function on an event — a queue message, an HTTP request through API Gateway, a file landing in S3. There are managed .NET runtimes for the current LTS versions, and Amazon.Lambda.AspNetCoreServer will host a whole ASP.NET Core application inside one if you want the familiar model.

🎓 The cold start, and why it is a .NET question

A function that has not run recently must start a process, load the runtime and JIT your code before it can answer — the cold start. It hits .NET harder than interpreted languages, and the mitigations are all things you already know from chapter 22 of the course: ReadyToRun, trimming, and Native AOT, which removes the JIT from the path entirely and is the single biggest lever. AWS also offers SnapStart for .NET, which restores a pre-initialised snapshot rather than starting cold.

The judgement, which matters more than the trivia: a steadily-loaded API is usually cheaper and simpler on ECS Fargate than on Lambda. Lambda earns its place with spiky or event-driven work — a file arrives, a queue drains, a webhook fires.

Try it yourself

An afternoon inside the free tier is enough to stop this being theoretical.

  1. Create an account, set a billing alarm first, and pick eu-south-1 (Milan) as your region — the same data-residency reasoning an Italian company applies.
  2. Put a file in S3 from a console app with new AmazonS3Client() and a local profile. Note that there is no key in your code.
  3. Containerise the API from chapter 28 and run it on App Runner. That is a deployment you can legitimately describe in an interview.
  4. Move a setting into Parameter Store and read it at start-up.
  5. Deliberately remove the permission from the role and read the AccessDenied. Learning to read an IAM denial is most of learning AWS.

Golden rules

  1. Roles, never access keys. A role gives temporary credentials; a leaked long-lived key is the classic AWS incident.
  2. The SDK finds credentials itself. The same code runs on your laptop and in production with no credential in the application.
  3. There is no resource group. Group with tags, isolate with separate accounts per environment.
  4. Nothing may talk to anything until IAM says so. Assume a permissions problem before a code problem.
  5. On RDS you are not sysadmin — backup and restore go through stored procedures and S3, and xp_cmdshell is gone.
  6. Multi-AZ failover repoints DNS behind the same endpoint. Turn on connection retry.
  7. Cold starts hit .NET hardest. Native AOT is the biggest lever; SnapStart is the other.
  8. Steady load belongs on containers; spiky and event-driven work belongs on Lambda.
  9. Set a billing alarm before your first resource. The free tier is generous and the cliff is real.
  10. Say what you have actually done. "I deployed a containerised .NET API to App Runner and read secrets from Parameter Store" is worth more than a list of service names.

Interview questions

"Do you have AWS experience?"

Answer precisely and small. Something like: "I have deployed a containerised .NET API to App Runner, used S3 from the SDK and read configuration from Parameter Store, with an IAM role rather than access keys. I know the Azure equivalents better." That is honest, specific and checkable — and for an optional skill it is entirely sufficient. A vague claim to "experience with AWS" invites the follow-up you cannot answer.

"How does your application authenticate to AWS?"

Through an IAM role attached to the compute — a task role on ECS, an instance profile on EC2 — which the SDK picks up automatically through the default credential provider chain. That means no credentials in the application at all, and the same code runs locally against my own profile. Long-lived access keys are the thing to avoid; they do not expire, so a leaked one stays valid until somebody notices.

"What is the AWS equivalent of a managed identity?"

An IAM role. The concept is the same — an identity attached to the compute that yields short-lived credentials, so nothing has to hold a secret. The difference in feel is that AWS requires an explicit policy for every action, where Azure leans more on role assignments at a scope.

"Anything to watch out for running SQL Server on RDS?"

You do not get sysadmin, so native BACKUP and RESTORE are replaced by RDS stored procedures that move .bak files through S3, and xp_cmdshell and filesystem access are gone — which matters if a legacy procedure relied on them. And Multi-AZ failover keeps the endpoint but repoints DNS, so connection resiliency and retry-on-failure need to be switched on rather than assumed.

"Lambda or a container?"

Containers on ECS Fargate for a steadily-loaded API — simpler, usually cheaper, and no cold-start problem. Lambda for spiky or event-driven work: a file lands in S3, a queue needs draining, a webhook arrives. If it does have to be Lambda on .NET, cold start is the thing to manage, and Native AOT or SnapStart is how.
