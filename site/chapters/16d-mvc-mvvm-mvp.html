MVC, MVVM and MVP

Three acronyms that get treated as rivals in interviews and confused in practice. They are the same idea — keep the screen separate from the logic — solved three ways, for three kinds of UI. The real question each one answers is quiet but decisive: who updates the screen? Get that, and you can say which pattern a given .NET technology is, and why.

Why this is worth its own chapter

Chapter 16 is MVC in ASP.NET Core. This one steps back to place it beside its siblings, because a Modena gestionale shop typically runs all three at once: MVC or Razor Pages for new web screens, MVVM in the WPF or Blazor client, and MVP hiding in the WinForms app nobody has rewritten yet. You will be asked to tell them apart.

The one idea behind all three

🧒 Simple

Every one of them splits an app into three jobs:

  • The Model — the real stuff (data and rules). Same in all three.
  • The View — what you see on screen. Same idea in all three.
  • The middle piece — the glue between them. This is the only thing that changes: what it is called, which way the arrows point, and who tells the screen to redraw.
🎓 Professional

All three are separated presentation: keep domain logic out of UI code so it can be tested and reused, and keep UI concerns out of the domain. They differ on the coupling and the update mechanism — whether the mediator holds a reference to the view, whether the view holds a reference to the mediator, and whether updates are pushed manually or carried by data binding. Those three switches produce MVC, MVP and MVVM.

MVC — Model-View-Controller

A controller receives a request, works with the model, and picks a view to render. The flow is a one-way trip: request in, HTML out, and the server forgets you until the next request. This statelessness is why MVC fits the web so naturally.

the controller is the mediator — see chapter 16 for the full version
public class CarriersController(CarrierService service) : Controller
{
    public async Task<IActionResult> Index(CancellationToken ct)
    {
        var vm = await service.ListAsync(ct);   // work with the model
        return View(vm);                       // choose a view, render, forget
    }
}
What makes it MVC
  • The controller is the entry point. The request arrives at it, unlike MVP and MVVM where the view exists first and the mediator hangs off it.
  • The view is stateless and disposable. It is built for this response and discarded. There is no live object watching the model — the next update is simply the next request.
  • "Who updates the view?" — a new request does. This is the defining trait and the reason MVC suits HTTP: the server holds no per-user screen state between calls.
  • The word "ViewModel" you saw in chapter 16 is not MVVM. In MVC it just means "a class shaped for one view". Same word, different pattern — a classic interview trap.

In .NET: ASP.NET Core MVC, and its close cousin Razor Pages (a page-centric take on the same request/response model). This is the pattern of the server-rendered web.

MVP — Model-View-Presenter

MVP grew up in stateful, event-driven desktop UIs — WinForms, classic Web Forms — where the screen is a long-lived object raising events (button clicked, text changed). The presenter holds all the UI logic and talks to the view through an interface, so the presenter can be tested with no real window on screen.

the presenter talks to an interface, not a window
public interface ICarrierView          // the form implements this
{
    string Name { get; }
    string Code { get; }
    void ShowError(string message);
    event EventHandler SaveClicked;
}

public class CarrierPresenter
{
    private readonly ICarrierView _view;
    private readonly CarrierService _service;

    public CarrierPresenter(ICarrierView view, CarrierService service)
    {
        _view = view;
        _service = service;
        _view.SaveClicked += OnSave;      // react to the view's event
    }

    private async void OnSave(object? sender, EventArgs e)
    {
        try   { await _service.CreateAsync(new(_view.Name, _view.Code), default); }
        catch (ConflictException ex) { _view.ShowError(ex.Message); }   // push to the view
    }
}
What makes it MVP
  • The view is passive. It exposes properties and events through ICarrierView and does nothing clever. The Form class implements the interface; the presenter never touches a TextBox.
  • The presenter pushes updates. _view.ShowError(...) — the presenter explicitly tells the view what to display. There is no automatic binding; every update is a line of code. That is the cost, and the control.
  • The interface is the whole point. Because the presenter depends on ICarrierView and not a window, you can unit-test it with a fake view — the thing WinForms otherwise makes almost impossible.
  • "Who updates the view?" — the presenter does, by hand. One-to-one with the view, holding a reference to it. That direct reference is the difference from MVVM.

In .NET: the pattern you retrofit onto WinForms and classic Web Forms to make them testable — exactly the legacy app you may be hired to keep alive. Greenfield desktop work uses MVVM instead.

MVVM — Model-View-ViewModel

MVVM appeared with data-binding frameworks (WPF), where the platform can wire a control's value to a property and keep them in sync automatically. The ViewModel exposes bindable state and commands and has no reference to the view at all — the binding engine connects them. Change a property, raise a notification, and the screen redraws itself.

a WPF/MAUI view model — notifies, and the screen follows
public class CarrierViewModel : INotifyPropertyChanged
{
    private string _name = "";
    public string Name
    {
        get => _name;
        set { _name = value; OnChanged(); }      // raising this redraws the bound control
    }

    public ICommand Save { get; }             // a button binds to this, not to a click handler

    public event PropertyChangedEventHandler? PropertyChanged;
    private void OnChanged([CallerMemberName] string? p = null) =>
        PropertyChanged?.Invoke(this, new(p));
}
What makes it MVVM
  • The view model has no reference to the view. No IView, no control, nothing. It could not call the screen if it wanted to — it only raises PropertyChanged and lets the binder react.
  • INotifyPropertyChanged is the engine. Setting Name raises the event; the data-binding framework hears it and updates the bound TextBox. That is the automatic update MVP did by hand.
  • ICommand Save — even the button is bound. Instead of a SaveClicked event handler, the view binds its button to a command object. This is what lets the whole view model be tested with no UI: you set Name and invoke Save directly.
  • "Who updates the view?" — the binding does, on notification. The view model changes state and announces it; it never touches the screen. That decoupling, plus commands, is the entire pattern.
  • In XAML this is wired with {Binding Name}; in Blazor the component is the view model, binding with @bind and re-rendering on state change — the same idea with a different syntax.

In .NET: WPF, .NET MAUI, Avalonia and Uno — anywhere with a real data-binding engine. Blazor is MVVM-flavoured rather than textbook, since the component holds both markup and state. It is the pattern greenfield desktop and rich-client work reaches for, and the migration target for this region's WinForms estate.

⚠ The three traps in the naming

One: the "view model" in ASP.NET Core MVC is not the MVVM ViewModel — MVC's is a per-screen data class with no binding or notification. Two: MVVM is not "MVC with a rename"; the defining difference is that the ViewModel has no reference to the view, which a controller and a presenter both do in their own way. Three: the pattern is chosen by the platform, not by taste — you use MVVM in WPF because WPF has binding, and MVC on the web because HTTP is stateless. Naming the driver (binding vs request vs events) is what turns a memorised list into an answer.

You rarely choose a pattern in isolation; the technology chooses it for you. The useful skill is reading a codebase and naming what it already is.

Line by line
  • dotnet new mvc — open Controllers/HomeController.cs and a view; trace a request in and HTML out. Notice there is no object holding screen state between requests.
  • dotnet new wpf — add a view model with INotifyPropertyChanged, bind a TextBox to a property with {Binding}, and watch the label update with no code in the click handler. That single experience is what makes MVVM click.
  • Then write the same "rename a carrier" screen in both and feel where the code goes: into an action in one, into a bindable property and a command in the other.
  1. In the MVC app, find where a screen's state lives between two requests. (It does not — that is the lesson.)
  2. In the WPF app, bind a property two-way and change it from code; watch the UI follow with no manual update.
  3. Sketch the MVP version of the WPF screen: an IView interface and a presenter that pushes. Notice how many _view.SetX(...) calls binding removed.

Golden rules

  1. All three separate the model (data + rules) from the view (the screen); only the middle piece and the update mechanism change.
  2. The distinguishing question is "who updates the view?" — a new request (MVC), the presenter by hand (MVP), or data binding on notification (MVVM).
  3. MVC: controller is the entry point, the view is stateless and disposable. ASP.NET Core MVC and Razor Pages.
  4. MVP: passive view behind an IView interface, presenter holds the logic and a reference to the view. WinForms/Web Forms made testable.
  5. MVVM: the ViewModel has no reference to the view; binding and commands connect them. WPF, MAUI, Blazor, Avalonia.
  6. The ASP.NET Core "view model" is a per-screen data class, not the MVVM ViewModel — same words, different pattern.
  7. The platform picks the pattern: binding ⇒ MVVM, stateless request ⇒ MVC, event-driven stateful form ⇒ MVP.
  8. In every one of them the view stays logic-free and the domain stays UI-free — that is the goal the acronyms are three routes to.

Interview questions

"What's the difference between MVC, MVP and MVVM?"

Same goal — separate the screen from the logic — different mediator and different update mechanism. MVC's controller is the request entry point and re-renders a stateless view. MVP's presenter holds a reference to a passive view through an interface and pushes updates by hand. MVVM's view model has no reference to the view and relies on data binding to sync automatically. Answer with "who updates the view?" and you've said the thing that matters.

"Is the ViewModel in ASP.NET Core MVC the same as MVVM?"

No — and it's a deliberate trap. In MVC it's just a class shaped for one view, with no binding and no INotifyPropertyChanged. MVVM's ViewModel is a live, bindable object with commands and change notification. Same two words, different pattern.

"Why does WPF use MVVM and the web use MVC?"

Because WPF has a data-binding engine, so a view model can just raise PropertyChanged and let the framework update the screen. The web is stateless request/response, so there's no live object to bind to — the next update is the next request, which is exactly what a controller handles. The pattern follows the platform's update model.

"Where does MVP still show up?"

In WinForms and classic Web Forms code you're maintaining. Those give you an event-driven, stateful view with no binding, and MVP is how you pull the logic into a testable presenter behind an IView interface. New desktop work uses MVVM instead, so MVP is mostly a legacy-maintenance pattern now.

"Is Blazor MVVM?"

MVVM-flavoured rather than textbook. A component holds both its markup and its state and binds with @bind, re-rendering when state changes — the binding-driven update is MVVM's idea. But the view and view model aren't separate objects the way WPF splits XAML from a view model class, so purists call it component-based. Saying both halves is the strong answer.
