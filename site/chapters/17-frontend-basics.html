HTML, JavaScript and TypeScript

The advert says conoscenza base, and it means it. Nobody expects a React specialist. What they expect is a back-end developer who can open the browser dev tools, see why their own API call failed, and fix the page that consumes it.

From the advert

"Conoscenza base di tecnologie frontend (HTML, JavaScript, TypeScript)." Optional, and honestly scoped. The goal is to be useful at the boundary, not to be a front-end developer.

HTML — structure, not appearance

🧒 Simple

HTML is the skeleton of a page: this is a heading, this is a paragraph, this is a button. CSS is the clothes: what colour, how big, where. JavaScript is the muscles: what happens when you press the button.

Skeleton, clothes, muscles. Three separate jobs, and mixing them up is what makes a page hard to change.

a form, written properly
<!doctype html>
<html lang="it">          <!-- lang matters: screen readers, spell check, hyphenation -->
<head>
  <meta charset="utf-8">   <!-- without this, "Modenaàèì" arrives as mojibake -->
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Nuovo ordine</title>
</head>
<body>
  <main>
    <h1>Nuovo ordine</h1>

    <form id="order-form">
      <!-- label + for/id: clicking the label focuses the input -->
      <label for="customer">Cliente</label>
      <input id="customer" name="customerId" type="number" required>

      <label for="notes">Note</label>
      <textarea id="notes" name="notes" maxlength="500"></textarea>

      <button type="submit">Salva</button>
    </form>

    <p id="status" role="status"></p>
  </main>
  <script src="app.js" type="module"></script>
</body>
</html>
Line by line
  • <!doctype html> — not decoration. Its absence puts the browser into quirks mode, where box sizing and layout follow 1990s rules and your CSS behaves inexplicably.
  • lang="it" — screen readers choose a voice from it, browsers pick a spell checker and hyphenation rules, and search engines read it. One attribute, and it is the most commonly omitted accessibility feature there is.
  • <meta charset="utf-8"> — and it must be in the first 1024 bytes. Without it the browser guesses, and in Italy the guess turns Modenaàèì into mojibake.
  • <meta name="viewport" ...> — without it a phone renders the page at 980px wide and scales it down, so every "why is my site tiny on mobile" question is this line missing.
  • <main> — a semantic element. It tells assistive technology where the content is, so a screen reader user can skip the navigation. A <div> conveys nothing.
  • <h1> — one per page, and headings must not skip levels. Screen reader users navigate by heading the way sighted users skim, so the hierarchy is the navigation.
  • <label for="customer"> with <input id="customer"> — the for matches the id, which makes clicking the label focus the input and lets a screen reader announce the field's name. It is the single highest-value accessibility habit in a form.
  • name versus id — id is for the label and CSS; name is what gets submitted. A field with no name is silently absent from the POST.
🎓 Why semantic elements are worth the two seconds

<header>, <nav>, <main>, <button> carry meaning that a <div> does not. Screen readers navigate by them, search engines read them, and browsers give you keyboard behaviour for free — a real <button> is focusable and responds to Enter and Space; a <div onclick> does neither, and you would have to reimplement both badly. In Italy, public-sector and public-facing work is also subject to accessibility obligations under the Legge Stanca, so this is occasionally a contractual matter, not only a good habit.

The DOM

🧒 Simple

The HTML file is a recipe written on paper. The DOM is the cake once it has been baked — the real thing, sitting in the browser’s memory. JavaScript cannot change the recipe, but it can walk up to the cake and add another candle.

app.js — find, listen, change
// find
const form   = document.querySelector('#order-form');
const status = document.querySelector('#status');

// listen
form.addEventListener('submit', async (event) => {
  event.preventDefault();          // stop the browser doing its own full-page POST

  // change
  status.textContent = 'Salvataggio…';   // textContent, not innerHTML — see below
});
Line by line
  • document.querySelector('#order-form') — takes a CSS selector, so # means id and . means class. It returns the first match or null, never an error, which is why a typo silently produces null.
  • const — block-scoped and not reassignable. Default to it; use let when you must reassign, and never var, which is function-scoped and hoisted.
  • addEventListener('submit', handler) — listens for the form's submit event, not the button's click. That is deliberate: it also fires when the user presses Enter in a text field.
  • async (event) => { ... } — an async arrow function as the handler. JavaScript's arrow is the same idea as C#'s lambda, with the same =>.
  • event.preventDefault() — stops the browser doing its own full-page POST and reload. Forget it and the page navigates away mid-request, which looks like your JavaScript never ran.
  • status.textContent = '...' — textContent, not innerHTML. textContent sets text; innerHTML parses markup, so any user-supplied string in it is a cross-site scripting hole. This is the JavaScript equivalent of @Html.Raw.
⚠ innerHTML and XSS

element.innerHTML = userInput parses that string as HTML, so <img src=x onerror="…"> executes. Use textContent for text. This is the browser-side twin of the SQL injection rule from chapter 10: never let data become code. It is also why Razor encodes by default (chapter 16).

Calling your own API

fetch — the part a back-end developer actually needs
async function createOrder(payload) {
  const response = await fetch('/api/v1/orders', {
    method:  'POST',
    headers: { 'Content-Type': 'application/json' },
    body:    JSON.stringify(payload)
  });

  // ⚠ fetch does NOT throw on 404 or 500. It only rejects on network failure.
  //   Forgetting this is the single most common fetch bug.
  if (!response.ok) {
    const problem = await response.json();   // the ProblemDetails from ch. 11
    throw new Error(problem.title ?? `HTTP ${response.status}`);
  }

  return response.json();
}

form.addEventListener('submit', async (e) => {
  e.preventDefault();
  try {
    const data = new FormData(form);
    const order = await createOrder({
      customerId: Number(data.get('customerId')),
      notes:      data.get('notes')
    });
    status.textContent = `Ordine ${order.orderNumber} creato.`;
  } catch (err) {
    status.textContent = err.message;
  }
});
Line by line
  • fetch(url, { ... }) — returns a Promise, JavaScript's Task. await works the same way it does in C#.
  • headers: { 'Content-Type': 'application/json' } — required. Without it the server may not bind the body at all, and ASP.NET Core returns 415 Unsupported Media Type.
  • JSON.stringify(payload) — the body must be a string. Passing the object directly sends [object Object], which is a genuinely confusing five minutes.
  • fetch does NOT throw on 404 or 500. It rejects only on network failure — DNS, connection refused, CORS. A 500 is a perfectly successful fetch of an error page, and forgetting this is the single most common fetch bug.
  • if (!response.ok) — the check that has to be written every time. ok is true for any 2xx status.
  • await response.json() — the Problem Details body from chapter 13. Reading the error body is what turns "request failed" into a message a user can act on.
  • problem.title ?? `HTTP ${response.status}` — ?? is null-coalescing, the same operator as C#'s. The backticks are a template literal, JavaScript's string interpolation, with ${...} instead of {...}.
⚠ CORS — the error you will meet on day one

A page served from http://localhost:5173 calling an API on https://localhost:7001 is a cross-origin request, and the browser blocks the response unless the API opts in. The error appears in the browser console, which is why back-end developers often think their API is broken when it is answering perfectly. 

// Program.cs — allow the specific front-end origin, never AllowAnyOrigin in production
builder.Services.AddCors(o => o.AddPolicy("spa", p => p
    .WithOrigins("http://localhost:5173")
    .AllowAnyHeader()
    .AllowAnyMethod()));

app.UseCors("spa");   // before MapControllers (ch. 11 — order is behaviour)
Line by line
  • CORS is a browser rule, not a server one. The request usually reaches your API and is answered; the browser then refuses to hand the response to the script. That is why the network tab shows a 200 while the console shows a CORS error.
  • AddCors(o => o.AddPolicy("spa", ...)) — a named policy, defined once.
  • .WithOrigins("http://localhost:5173") — an exact origin: scheme, host and port, with no trailing slash. A different port is a different origin, which is why the SPA dev server needs naming explicitly.
  • Never AllowAnyOrigin in production. Combined with credentials it is forbidden outright by the specification, and alone it makes your API readable by script on any site a user visits.
  • app.UseCors("spa") — and the placement is the point: before the endpoints, after routing. Order is behaviour, exactly as in chapter 14, and CORS registered too late adds headers to a response nobody is allowed to read.
  • A non-simple request — PUT, or a custom header — triggers a preflight OPTIONS call first. If that is blocked by authentication or a proxy, the real request never happens.

JavaScript oddities worth knowing

ThingWhat to know
=== vs ==Always ===. == coerces types, so '' == 0 is true.
const / letUse these. Never var — it is function-scoped and hoisted.
null vs undefinedTwo kinds of nothing: deliberately empty, and never set.
Falsy values0, '', null, undefined, NaN, false. Note 0 — if (count) is a bug when zero is valid.
?. and ??Exactly the C# operators from chapter 02.
Promises / asyncA Promise is JavaScript’s Task; async/await works the same way.
NumbersOne numeric type, IEEE-754 double. 0.1 + 0.2 !== 0.3, and integers above 2⁵³ lose precision — so a C# long id should be serialised as a string.

TypeScript

🧒 Simple

JavaScript lets you put a shoe in the fridge. It will not complain, and you will find out three days later.

TypeScript is a friend who reads over your shoulder and says "that is a shoe" the instant you pick it up — before the fridge is ever opened.

🎓 Professional

TypeScript is JavaScript with a static type system, compiled (technically erased) to plain JavaScript. Nothing survives to run time: the types exist only to let the compiler and the editor catch mistakes and offer completion. That is precisely the same bargain as nullable reference types in C# — compile-time guarantees, no runtime enforcement — and it carries the same caveat: data arriving from an API is not validated by its type annotation. Declaring response.json() as Order is a promise, not a check.

api.ts — the same call, typed
// A contract. Mirror your C# DTO here — camelCase, because System.Text.Json
// uses camelCase by default.
export interface OrderDto {
  id: number;
  orderNumber: string;
  total: number;
  status: 'Draft' | 'Submitted' | 'Shipped';   // union type — a closed set
  notes?: string;                                // ? = may be absent
}

export interface CreateOrderRequest {
  customerId: number;
  notes?: string;
}

export async function createOrder(
  payload: CreateOrderRequest
): Promise<OrderDto> {
  const res = await fetch('/api/v1/orders', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload)
  });

  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json() as Promise<OrderDto>;
}
Line by line
  • export interface OrderDto — a compile-time only declaration. TypeScript interfaces vanish entirely in the emitted JavaScript; nothing is checked at run time.
  • camelCase, deliberately. System.Text.Json serialises C#'s PascalCase to camelCase by default, so this mirrors what actually arrives on the wire rather than what the C# looks like.
  • 'Draft' | 'Submitted' | 'Shipped' — a union of string literals: a closed set, so a typo is a compile error and an editor can autocomplete it. It is TypeScript's nearest thing to an enum, and closer to the wire than a real enum.
  • notes?: string — the ? means the property may be absent, giving string | undefined. That is not the same as string | null, and an API that returns JSON null needs the latter — a distinction that catches everyone once.
  • Promise<OrderDto> — the return type of the async function, matching C#'s Task<T>.
  • This file is a hand-written copy of a C# contract, and hand-written copies drift. Generating it from the OpenAPI document is the standard fix, and chapter 18 covers it.
Generate the types, do not type them twice

Your API already publishes an OpenAPI document (chapter 14). Tools such as NSwag or openapi-typescript turn it into TypeScript interfaces automatically, so a renamed C# property becomes a compile error in the front end rather than an undefined in production. Suggesting this in an interview is a strong, concrete, back-end-flavoured answer to a front-end question.

C#TypeScript
int, decimal, doublenumber (only one)
stringstring
boolboolean
List<T>T[]
string?string | null or notes?: string
enumA union of string literals is usually better
interfaceinterface — structural, not nominal
Task<T>Promise<T>

One real difference: C# interfaces are nominal (a type implements one by declaring it); TypeScript interfaces are structural (any object with the right shape fits). It is why TypeScript feels looser even though it is strict.

Try it yourself

Take the Web API from chapter 14 and put a single HTML page in front of it. No framework, no build step — that is the point.

  1. Add app.UseStaticFiles() and put an index.html in wwwroot.
  2. Fetch /api/v1/orders and render the rows into a table.
  3. Open dev tools → Network. Look at the request, the response headers and the JSON. This tab is where you will spend your front-end time.
  4. Stop the API and reload. Notice fetch throws only on the network failure, and that a 500 would not have thrown.
  5. Now serve the page from a different port and watch CORS block it.

Golden rules

  1. HTML is structure, CSS is appearance, JavaScript is behaviour. Keep them apart.
  2. Semantic elements and real <label>s: accessibility and keyboard support come free.
  3. textContent for text; innerHTML with user data is XSS.
  4. fetch does not throw on 4xx or 5xx. Check response.ok yourself.
  5. CORS is the browser refusing, not your API failing. Read the console before the logs.
  6. Always ===; never var.
  7. JavaScript has one number type. Large long ids should cross the wire as strings.
  8. TypeScript types vanish at run time. An annotation on API data is a promise, not validation.
  9. Generate front-end types from your OpenAPI document instead of maintaining them twice.
  10. Client-side validation is for the user’s convenience. The server is the only control.

Interview questions

"How comfortable are you with front-end work?"

Be honest and specific. "I am a back-end developer. I can write the HTML and vanilla JS to consume my own API, debug in dev tools, and read a React or Angular component well enough to see where it calls the server — but I would not call myself a front-end developer." That answer is credible; "yes, full stack" invites a question you will not enjoy.

"What is CORS?"

A browser security mechanism: script on origin A may not read a response from origin B unless B sends headers permitting it. It is enforced by the browser, not the server — which is why the same request from Postman works fine.

"Why TypeScript over JavaScript?"

Errors at compile time instead of run time, real editor completion, and types as documentation that cannot go stale. Then the caveat that shows depth: types are erased, so data crossing the network boundary still needs validating.

"What is the DOM?"

The browser’s in-memory object tree built from the HTML. JavaScript manipulates that tree, not the source file.

"How do you prevent XSS?"

Encode on output — which Razor does by default and textContent does in the DOM. Never build HTML from user input; add a Content-Security-Policy header as defence in depth. Same principle as parameterised SQL: data must never become code.
