The event loop — the question you will be asked

If a JavaScript interview asks you one conceptual question, it is this one. It is also the topic that makes the language make sense, so it goes first.

🧒 Simple

A shop with exactly one shopkeeper. They serve one customer at a time, start to finish. There is no second shopkeeper, ever.

Two queues form. One is people waiting at the door — the ordinary queue. The other is a small counter beside the till for people who only need a signature; the shopkeeper clears everyone at that counter before letting the next person in from the door.

That side counter is the microtask queue, and it is why a promise callback always runs before a setTimeout that was scheduled first.

the ordering puzzle — predict the output before you read on
console.log('1');

setTimeout(() => console.log('2'), 0);          // macrotask

Promise.resolve().then(() => console.log('3'));   // microtask

console.log('4');
Line by line
  • console.log('1') — runs immediately, synchronously. Nothing surprising yet.
  • setTimeout(fn, 0) — zero does not mean now. It queues the callback as a macrotask, to run after the current script and after all microtasks.
  • Promise.resolve().then(fn) — queues a microtask. Already-resolved, so the only reason it does not run instantly is the queue.
  • JavaScript is single-threaded. Nothing queued can run until the currently executing code returns to the event loop, which is why both callbacks wait for '4'.
  • Microtasks drain completely before the next macrotask. That one rule decides the whole output, and it is why a promise chain always beats a setTimeout(0).
1
4
3
2
Line by line
  • 1 then 4 — the synchronous script runs to completion first. Nothing else can interleave.
  • 3 — the microtask queue drains next, before the browser does anything else.
  • 2 — the macrotask last, despite its zero delay and despite being written first.
  • Why this matters beyond a puzzle: it is the model behind every "why did my state update not apply yet" question in React, and behind await's ordering. await is microtask scheduling with nicer syntax.

1 and 4 are synchronous, so they run first, in order. Then the stack is empty and the engine drains the whole microtask queue — that is 3. Only then does it take one macrotask — 2. The setTimeout delay of zero does not mean "now"; it means "after the current work and every microtask waiting behind it".

🎓 Professional — and this is chapter 07 again

await in JavaScript does exactly what await in C# does: it returns control to the scheduler and registers the rest of the method as a continuation. It does not create a thread. In C# that continuation goes to the thread pool; in JavaScript it goes to the microtask queue, and there is only ever one thread to come back to.

So the C# rule and the JavaScript rule are the same rule: never block. In C# blocking starves the pool (chapter 07); in JavaScript there is no pool to starve, so a synchronous loop over 100,000 items freezes the entire page — no clicks, no animation, no rendering — until it finishes.

this, and why arrow functions exist

In C#, this is the instance. It is decided at compile time and it is never a surprise. In JavaScript this is decided by how the function is called, not where it was written — and that is the source of most "undefined is not a function" bugs.

the same function, four values of this
const order = {
  number: 'ORD-1',
  show() { console.log(this.number); }
};

order.show();                       // 'ORD-1'  — called as a method

const f = order.show;
f();                                // undefined — the function was detached from the object

setTimeout(order.show, 0);          // undefined — same detachment, and this is
                                    //             how it actually happens in real code

setTimeout(() => order.show(), 0);   // 'ORD-1'  — the call site is preserved
setTimeout(order.show.bind(order), 0);// 'ORD-1'  — bound explicitly
Line by line
  • show() { ... } — method shorthand in an object literal. It is an ordinary function, and that is the trouble.
  • order.show() prints 'ORD-1' — this is decided by how a function is CALLED, not where it is defined. Called with order. in front, this is order.
  • const f = order.show; f(); — undefined. The function was detached from the object; there is no dot at the call site, so there is no receiver.
  • setTimeout(order.show, 0) — the same detachment, and this is how it actually happens. Passing a method as a callback is routine, and it silently loses this every time.
  • The fixes: order.show.bind(order), or wrap it in an arrow — () => order.show() — which keeps the call site's dot.
  • C# has no equivalent problem. A delegate created from an instance method captures the instance permanently, which is why this catches C# developers specifically.
🎓 Professional

An arrow function has no this of its own. It captures the this of the scope it was written in, permanently, and bind cannot change it. That single fact gives you both rules:

  • Use an arrow for a callback. It keeps the surrounding this, which is what you almost always meant.
  • Never use an arrow as an object method. There is no surrounding instance to capture, so this will be the module or undefined — not the object you wrote it inside.
const bad = {
  number: 'ORD-1',
  show: () => console.log(this.number)   // ✗ undefined, always
};
Line by line
  • show: () => ... — an arrow function as an object property, and it is always wrong here.
  • Arrows have no this of their own. They inherit it lexically, from the scope where they were written — and an object literal is not a scope.
  • So this is whatever it was outside the object: undefined in a module, window in a classic script. Never the object.
  • The rule that resolves the confusion: use an arrow when you want the surrounding this — a callback inside a method — and a normal function when you want the receiver, which is what a method is.
  • It is the exact inverse of the previous block, which is why the two are shown together: one breaks by losing the receiver, the other by never having one.

Closures, and the loop bug you have already met

You learned this in chapter 04, in C#. Here it is again, in JavaScript, with a different fix — and interviewers on both sides of the stack ask it.

✗ prints 3, 3, 3
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// var is function-scoped: there is ONE i. By the time the callbacks run —
// after the loop, because setTimeout is a macrotask — that one i is 3.
Line by line
  • var i — function-scoped, not block-scoped. There is exactly one i for the whole loop.
  • All three closures capture the same variable, not its value — the same mechanism as the C# for-loop trap in chapter 04.
  • setTimeout makes it visible: the callbacks are macrotasks, so they run after the loop has finished and i is already 3.
  • Output is 3 3 3. Every time, in every browser — this is not a race.
  • var is also hoisted: the declaration moves to the top of the function, so reading it before the line that declares it gives undefined rather than an error. Two reasons never to use it.
✓ prints 0, 1, 2
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// let is block-scoped, and a for loop creates a NEW binding each iteration.
// Each closure captures its own.
Line by line
  • let i — block-scoped, and a for loop creates a new binding each iteration. That second part is special-cased in the specification precisely because of the previous block.
  • Each closure therefore captures its own i, and the output is 0 1 2.
  • C# made the identical change for foreach in C# 5, for the same reason, and deliberately left for alone — where i genuinely is one counter. JavaScript went the other way and fixed for.
  • let is also in the temporal dead zone before its declaration: reading it early is a ReferenceError rather than undefined. An error beats a wrong answer.
  • Use const by default and let when reassigning. var has no remaining use case.
The same law, twice

A closure captures the variable, not the value. That sentence is true in C# and true in JavaScript, and every version of this bug in either language follows from it. The languages differ only in the escape hatch: C# gave foreach a per-iteration variable in C# 5 (a plain for still shares one), and JavaScript gave you let.

Which is also the real reason never to write var: it is function-scoped and hoisted, so it does not mean what a C# developer's eyes think it means.

⚠ Three differences that catch C# developers
  1. They are eager, not deferred. arr.filter(…).map(…) builds a complete intermediate array and then a second one. LINQ would stream it in one pass (chapter 06). On ten items nobody cares; the habit matters when it is ten thousand.
  2. sort() mutates the array and sorts as text by default. 
    [10, 9, 1].sort()                  // [1, 10, 9]  — string comparison!
[10, 9, 1].sort((a, b) => a - b)    // [1, 9, 10]  — what you meant
    Line by line
    • [10, 9, 1].sort() gives [1, 10, 9] — because the default comparator converts every element to a string and compares lexicographically. "10" sorts before "9".
    • It is not a bug, it is the specification, and it is the most reliably surprising line in the language.
    • (a, b) => a - b — the comparator contract: negative if a comes first, zero if equal, positive if b does. The same convention as C#'s CompareTo.
    • Subtraction works only for numbers. For strings use a.localeCompare(b), which also gets Italian accents right — < compares code units and puts Z before à.
    • sort mutates the array in place and returns it. Use toSorted(), or [...arr].sort(), when the original must survive — unlike LINQ's OrderBy, which never mutates.
    OrderBy returns a new sequence; sort reorders the one you passed it, which surprises people who kept a reference to it.
  3. forEach ignores async. It does not await the callback, so the loop finishes instantly and everything runs unordered and unwaited. Use for…of when you need sequence, or Promise.all(items.map(…)) when you want them concurrent.

The syntax you cannot read a modern file without

destructuring, spread, template literals, default parameters
// Destructuring — pull fields out by name. Like C# deconstruction, but by name
// rather than by position, and it works on anything.
const { id, total, customer: { name } } = order;
const [first, second] = list;

// …including in a parameter list, which is how React components are written
function render({ id, total = 0 }) { … }

// Spread — copy and extend. The idiom for "change one field immutably",
// exactly like a C# record's `with` expression.
const shipped = { ...order, status: 'Shipped' };
const all     = [...a, ...b];

// Rest — the params keyword
function log(level, ...args) { … }

// Template literals — string interpolation. Backticks, ${} instead of $"{}"
const msg = `Order ${order.number} totals ${total.toFixed(2)} EUR`;

// Optional chaining and nullish coalescing — identical to C#,
// including the trap: ?? and || are NOT the same.
const city  = order?.customer?.address?.city;
const count = order.count ?? 10;   // 0 stays 0
const wrong = order.count || 10;   // 0 becomes 10 — a real bug
Line by line
  • const { id, total } = order — destructuring by name, not by position. C#'s deconstruction is positional; this matches property names, and it works on any object.
  • customer: { name } — nested destructuring. It pulls order.customer.name into a variable called name. Note the colon here means "look inside", not "rename".
  • const [first, second] = list — array destructuring, which is positional. Same syntax family, different brackets.
  • function render({ id, total = 0 }) — destructuring in a parameter list, with a default. This is how every React component receives its props, so it stops being exotic quickly.
  • Spread — { ...order, total: 10 } copies then overrides. It is the idiom for changing one field immutably, and the direct counterpart of C#'s with expression.
  • It is a shallow copy. Nested objects are shared with the original, which is the same caveat as with in C# and the source of many "why did both change" bugs.

Promises and async/await

A Promise is a Task, with two differences worth knowing before you rely on the analogy.

C#JavaScript
Starts whenUsually when the method is calledImmediately, at construction — there is no cold promise
Run all, need every resultTask.WhenAllPromise.all
On first failureWaits for all, then throwsRejects immediately; the others keep running, unobserved
Want every outcomeInspect each taskPromise.allSettled
CancellationCancellationTokenAbortController — and only where supported
the three shapes, and the bug in the middle one
// Sequential — three round trips, one after another. Usually not what you want.
const a = await getOrder(1);
const b = await getOrder(2);

// Concurrent, fail fast. If getOrder(2) rejects, this throws at once —
// and getOrder(1) is still running with nobody listening.
const [x, y] = await Promise.all([getOrder(1), getOrder(2)]);

// Concurrent, collect everything. The right choice when a partial result
// is still useful — a dashboard with one broken tile.
const results = await Promise.allSettled([getOrder(1), getOrder(2)]);
// [{ status: 'fulfilled', value }, { status: 'rejected', reason }]
Line by line
  • const a = await ...; const b = await ...; — sequential. The second request does not start until the first finishes, because await is a suspension point. Identical to the C# case in chapter 07.
  • Promise.all([...]) — starts both, waits for both. Fail fast: if either rejects, the whole thing rejects at once.
  • And the other request keeps running with nobody listening. There is no cancellation token here, so a rejected Promise.all leaves work in flight — a real difference from C#, where the token propagates.
  • const [x, y] = await ... — array destructuring on the results, which arrive in the order the promises were passed, not the order they completed.
  • Promise.allSettled — the alternative: waits for all and never rejects, returning a status per entry. The right choice when a partial result is still useful, such as four independent dashboard panels.
⚠ The unhandled rejection
// No await, no .catch(). The error has nowhere to go.
saveOrder(order);            // ✗ fire and forget

// In a browser this fires window.onunhandledrejection and is otherwise
// silent — the user sees nothing happen and you get no stack trace.
// In Node it terminates the process.

await saveOrder(order);      // ✓
saveOrder(order).catch(reportError);   // ✓ deliberate fire-and-forget
Line by line
  • saveOrder(order); with no await — a floating promise. The call starts and the caller moves on immediately.
  • The error has nowhere to go. If it rejects, there is no await to throw at and no .catch to handle it.
  • In a browser it is silent. It raises window.onunhandledrejection, which nothing listens to by default, so the user sees nothing happen and you get no stack trace. In Node it terminates the process instead — two very different failures from one mistake.
  • await saveOrder(order) — the fix in almost every case.
  • saveOrder(order).catch(reportError) — deliberate fire-and-forget. Attaching a handler is what makes the intent visible and the failure reportable; the point is that not-awaiting must be a decision, not an omission.
  • C#'s equivalent is an un-awaited Task, which is at least usually a compiler warning. JavaScript gives you nothing, which is why the ESLint rule no-floating-promises is worth turning on.

This is the JavaScript twin of an unawaited Task in C#: the compiler warns you there, and nothing warns you here. It is the most common cause of "the save button does nothing and there is no error".

DOM events: bubbling, and the one pattern to know

A click on a button does not only fire on the button. It travels down from the document to the target (capture), fires on the target, then travels back up through every ancestor (bubble). Almost all handlers listen on the way up.

✗ the version that breaks the moment a row is added
document.querySelectorAll('.delete-btn').forEach(b =>
  b.addEventListener('click', onDelete));
// 500 listeners. And any row rendered AFTER this line has none —
// which is why "it works until you use the search filter".
Line by line
  • querySelectorAll('.delete-btn') — returns a static NodeList of the buttons that exist at this instant.
  • .forEach(b => b.addEventListener(...)) — 500 separate listeners for 500 rows. Each is a closure held in memory for as long as its element lives.
  • The real defect is the snapshot. Any row rendered after this line has no listener at all, so the delete button silently does nothing.
  • "It works until you use the search filter" is the exact symptom, and it is baffling until you see that filtering re-renders the rows.
  • Re-running the wiring after every render is the naive fix, and it double-binds anything that survived — so the handler fires twice.
✓ event delegation — one listener, works for rows that do not exist yet
document.querySelector('#orders').addEventListener('click', (e) => {
  const btn = e.target.closest('.delete-btn');   // the click may land on an
                                                 // icon INSIDE the button
  if (!btn) return;
  onDelete(btn.dataset.orderId);
});
Line by line
  • One listener, on the container. Events bubble up the DOM, so a click on any descendant reaches #orders.
  • It works for rows that do not exist yet, which is the whole point. Re-render freely; the listener is on the parent and never moves.
  • e.target — the innermost element clicked. That may well be an icon or a <span> inside the button, not the button itself, which is why testing e.target.classList directly fails intermittently.
  • .closest('.delete-btn') — walks up from the target looking for a match, returning it or null. It is what makes the handler robust regardless of the markup inside the button.
  • if (!btn) return; — the click landed somewhere else in the container. Required, and easy to forget.
  • btn.dataset.orderId — reads the data-order-id attribute. The dashes become camelCase, which is a small rule worth knowing before it wastes ten minutes.
🎓 preventDefault is not stopPropagation
  • e.preventDefault() — do not do the browser's default thing (submit the form, follow the link). The event still bubbles.
  • e.stopPropagation() — do not let ancestors see this event. The default action still happens.

Reaching for stopPropagation to fix a bug usually breaks somebody else's delegated handler three months later. Prefer to fix the condition.

Modules: the two systems

ESM — the modern one, and what the browser understands
// orders.js
export function total(order) { … }
export default class OrderClient { … }

// app.js
import OrderClient, { total } from './orders.js';
Line by line
  • export function total(...) — a named export. A module may have many, and the names are part of its contract.
  • export default class OrderClient — the default export, at most one per module. The importer chooses its own name for it, which is both convenient and a reason teams often ban it.
  • import OrderClient, { total } from './orders.js' — default first, named in braces. The asymmetry of the syntax is exactly the asymmetry of the two export kinds.
  • './orders.js' — the relative path with its extension. In a browser the extension is required; bundlers let you omit it, which is a common source of "works in dev, breaks in production".
  • Modules are static. Imports are resolved before execution, which is what makes tree-shaking possible and why import cannot be called conditionally — import(), the function form, exists for that.
  • Modules are also strict mode by default and have their own scope, so a top-level const is not global — unlike a classic <script>.
CommonJS — older Node code, and much of what is on disk
const { total } = require('./orders');
module.exports = { total };
Line by line
  • require('./orders') — CommonJS, Node's original module system. Predates ES modules and is still everywhere in the ecosystem.
  • It is synchronous and dynamic. require is an ordinary function call, so it can sit inside an if — which is why it cannot be tree-shaken and ES modules can.
  • module.exports = { total } — assigning an object. { total } is shorthand for { total: total }.
  • Why you need to recognise it: mixing the two is the source of the errors that dominate a first week in Node — "Cannot use import statement outside a module" and "require is not defined in ES module scope".
  • The switch is "type": "module" in package.json, or the .mjs and .cjs extensions to be explicit per file.
  • Write ES modules in new code. This block is here so that an old file does not stop you.

import is static — declarations are resolved before any code runs, which is what lets a bundler remove unused exports. require is a function call that happens at run time. In Node, "type": "module" in package.json decides which one a .js file is; in a browser you need <script type="module">, which is also deferred and always strict mode. Mixing the two systems in one project is the source of most "cannot use import statement outside a module" errors.

Golden rules

  1. One thread, one stack. Microtasks drain completely; then exactly one macrotask; then the browser may paint.
  2. setTimeout(fn, 0) does not mean now. It means after everything currently queued, promises included.
  3. A long synchronous loop freezes the page. There is no other thread to keep it alive.
  4. await yields; it does not create a thread. Same as C#, with a smaller machine underneath.
  5. this is decided by the call, not the definition. Detach a method and you lose it.
  6. Arrow functions capture this lexically and cannot be rebound. Perfect as callbacks, wrong as object methods.
  7. A closure captures the variable, not the value — the same law as C#. Use let, never var.
  8. Array methods are eager. Each link in the chain builds a whole new array.
  9. sort() mutates, and compares as strings unless you pass a comparator.
  10. forEach does not await. Use for…of for order, Promise.all for concurrency.
  11. Promise.all rejects on the first failure; allSettled waits for every outcome. Not the same as Task.WhenAll.
  12. An unhandled rejection is silent in the browser and fatal in Node. Always await or .catch().
  13. Delegate events to a container — one listener, and it works for elements that do not exist yet.
  14. ?? is not ||. 0 and '' are falsy but not nullish, and that difference is a real bug.

Interview questions

"Explain the event loop."

JavaScript has one thread and one call stack. When the stack empties, the engine drains the entire microtask queue — promise callbacks and await continuations — then takes exactly one macrotask such as a timer, an I/O completion or a UI event, then lets the browser render. That is why a promise callback beats a setTimeout(…, 0) queued before it, and why a long synchronous loop freezes the page: rendering only happens between turns. If you know C#, add that await is the same cooperative yielding, minus the thread pool.

"What does this print, and why?"

console.log(1); setTimeout(()=>console.log(2),0); Promise.resolve().then(()=>console.log(3)); console.log(4); → 1, 4, 3, 2. Synchronous code first, then the microtask, then the macrotask. Saying the two queue names is what separates a memorised answer from an understood one.

"What is the difference between var and let?"

var is function-scoped and hoisted; let is block-scoped and in the temporal dead zone until declared. The consequence worth demonstrating is the loop: with var every callback closes over the same single variable and prints the final value, while a for loop with let creates a fresh binding per iteration. Mention that a closure captures the variable and not the value — the identical rule to C#.

"Why is this undefined in my callback?"

Because this comes from the call site. Passing obj.method somewhere detaches it from obj, so it is called with no receiver. Fix with an arrow wrapper that preserves the call, or bind. Then the second half: an arrow function has no this of its own, which makes it right for a callback and wrong for an object method.

"Promise.all or Promise.allSettled?"

all when you need every result and any failure makes the whole operation meaningless — it rejects on the first failure, and the others keep running unobserved. allSettled when a partial answer is still useful, like a dashboard where one tile is broken. Worth flagging that this differs from Task.WhenAll, which waits for everything before it throws.

"There are 500 rows and each has a delete button. How do you wire them up?"

One listener on the container, using bubbling, with e.target.closest('.delete-btn') to identify the button — because the click may land on an icon inside it. That is one listener instead of 500, and it keeps working for rows added after page load, which is the bug the per-element version always eventually has.

"You inherit a page written in jQuery. What do you do?"

Read it, work in it, and leave it alone unless the ticket says otherwise. I know the modern equivalents — querySelector, addEventListener, fetch — and I would write new pages without it, but ripping jQuery out of a page that works is a rewrite with regression risk and no business value. Same argument as migrating a legacy application incrementally rather than in one go.
