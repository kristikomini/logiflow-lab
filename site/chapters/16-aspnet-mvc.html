ASP.NET Core MVC

The same framework as chapter 14, with one difference: the response is HTML rendered on the server instead of JSON. In the gestionale and ERP world this advert comes from, this is how most internal screens are still built — and it is genuinely the right tool for them.

From the advert

"Conoscenza di ASP.NET Core MVC." Its presence alongside Web API tells you the system has both: an API for integrations and a mobile or SPA client, and server-rendered admin screens for internal users.

The pattern

🧒 Simple

A restaurant again, but look at who does what.

  • The Model is the food and the recipes — the real substance.
  • The View is the plate: how it is arranged so it looks good. The plate never decides what goes on it.
  • The Controller is the waiter: takes the order, tells the kitchen, brings back the plate. The waiter does not cook, and does not decide the garnish.

When the waiter starts cooking, everything goes wrong. That is the mistake called a fat controller.

🎓 Professional

MVC separates responsibilities so each can change independently: the model holds data and business rules, the view is a template with no logic beyond presentation, and the controller coordinates — it binds input, invokes the application layer, and selects a result.

The practical consequence is that a controller action should be readable in about ten lines. If it contains business rules, they belong in a service; if it contains queries, they belong in a repository; if it contains formatting, it belongs in the view.

The controller

OrdersController.cs — the MVC version
public class OrdersController(IOrderService service) : Controller   // Controller, not ControllerBase
{
    // GET /Orders  → Views/Orders/Index.cshtml
    public async Task<IActionResult> Index(OrderFilter filter, CancellationToken ct)
    {
        var vm = await service.SearchAsync(filter, ct);
        return View(vm);
    }

    // GET /Orders/Edit/42
    public async Task<IActionResult> Edit(int id, CancellationToken ct)
    {
        var vm = await service.GetForEditAsync(id, ct);
        return vm is null ? NotFound() : View(vm);
    }

    // POST /Orders/Edit/42
    [HttpPost, ValidateAntiForgeryToken]
    public async Task<IActionResult> Edit(int id, EditOrderViewModel vm, CancellationToken ct)
    {
        if (!ModelState.IsValid)
            return View(vm);          // redisplay the form WITH the errors and the input

        await service.UpdateAsync(id, vm, ct);

        TempData["Success"] = "Ordine aggiornato.";
        return RedirectToAction(nameof(Index));   // ← Post/Redirect/Get
    }
}
⚠ Post/Redirect/Get, and why it exists

After a successful POST, always RedirectToAction rather than returning a view. If you return the view directly, the browser’s address bar still shows the POST — so pressing F5 re-submits the form and creates a second order, and the browser shows a "confirm resubmission" dialog that no user understands. The redirect turns the final state into a clean GET.

Razor escapes HTML for you

@someString is HTML-encoded automatically, which means Razor is safe against cross-site scripting by default. The escape hatch is @Html.Raw(...) — and every use of it is a potential XSS hole, so it needs a reason and a review.

Tag helpers and forms

Tag helpers look like HTML attributes but are generated server-side. They produce correct names, ids, validation attributes and the antiforgery token — which is why hand-writing form HTML in MVC is a mistake.

Views/Orders/Edit.cshtml
@model EditOrderViewModel

<form asp-action="Edit" asp-route-id="@Model.Id" method="post">
    @* <form> injects the antiforgery hidden field automatically *@

    <div asp-validation-summary="ModelOnly" class="text-danger"></div>

    <div class="mb-3">
        <label asp-for="Notes" class="form-label"></label>
        <input asp-for="Notes" class="form-control" />
        <span asp-validation-for="Notes" class="text-danger"></span>
    </div>

    <div class="mb-3">
        <label asp-for="Status"></label>
        <select asp-for="Status" asp-items="Model.StatusOptions" class="form-select"></select>
    </div>

    <button type="submit" class="btn btn-primary">Salva</button>
    <a asp-action="Index" class="btn btn-link">Annulla</a>
</form>

asp-for reads the property, so the label text, the input name, the id, the value and the client-side validation attributes all come from one source. Rename the property and everything follows.

View models — the same rule as DTOs

shaped for the screen, not for the database
public class EditOrderViewModel
{
    public int Id { get; init; }

    [Display(Name = "Note")]
    [StringLength(500, ErrorMessage = "Massimo 500 caratteri.")]
    public string? Notes { get; set; }

    [Display(Name = "Stato")]
    [Required(ErrorMessage = "Lo stato è obbligatorio.")]
    public OrderStatus Status { get; set; }

    // data the VIEW needs that the entity has no reason to carry
    public IEnumerable<SelectListItem> StatusOptions { get; init; } = [];
}
⚠ Over-posting / mass assignment

Binding directly to an entity lets an attacker POST fields you never put on the form. Add &IsAdmin=true or &Total=0 to the request body and the binder will happily set them. A view model containing only the editable fields makes the attack impossible rather than merely unlikely — which is the same argument as DTOs in chapter 14, with a sharper security edge.

Antiforgery and the CSRF attack

🧒 Simple

You are logged into your bank in one browser tab. In another tab you open a page a stranger sent you. That page quietly tells your browser: "send a transfer request to the bank." Your browser obediently attaches your bank cookie, because it always does — and the bank sees a perfectly valid request from you.

The defence is a secret word printed on the real form. The stranger’s page cannot know it, so their forged request has no word, and the bank refuses it.

🎓 Professional

Cross-Site Request Forgery exploits ambient cookie authentication. ASP.NET Core defends with a synchroniser token: the <form> tag helper emits a hidden field, a matching cookie is set, and [ValidateAntiForgeryToken] requires both to agree.

Note the scope: this matters for cookie-authenticated MVC forms. A Web API using bearer tokens is not vulnerable in the same way, because the token is not sent automatically by the browser. Knowing why the two differ is the interesting half of the answer.

Golden rules

  1. Controllers stay thin: bind, delegate, choose a result. Business logic lives below them.
  2. Views display; they never decide. No queries and no rules in a .cshtml.
  3. Always a view model. Never bind a form directly to an EF entity — that is mass assignment.
  4. Post/Redirect/Get after every successful POST.
  5. Redisplay the view with ModelState when validation fails, so the user does not lose their input.
  6. Validate on the server. Client-side validation is a courtesy to the user, not a security control.
  7. [ValidateAntiForgeryToken] on every state-changing POST in a cookie-authenticated app.
  8. Razor encodes output by default. @Html.Raw needs a reason and a reviewer.
  9. Tag helpers over hand-written HTML: names, ids and validation attributes stay in sync with the model.
  10. TempData for a message across one redirect; the model for everything else.

Interview questions

"Explain MVC."

Model holds data and rules, view renders, controller coordinates. Then make it concrete: the controller should be about ten lines, and anything longer is logic that belongs in a service.

"What is the difference between MVC and Web API in ASP.NET Core?"

They are the same framework — same routing, binding, DI and middleware. MVC returns a rendered view; a Web API controller derives from ControllerBase and returns serialised data. [ApiController] adds automatic 400s and binding inference.

"ViewBag, ViewData or TempData?"

ViewData is a dictionary and ViewBag is its dynamic wrapper — both last one request. TempData survives a redirect and is consumed on read, which makes it right for a flash message after PRG. For everything real, use a typed model.

"What is CSRF and how does ASP.NET Core prevent it?"

A forged state-changing request from another site, riding on the browser’s automatically sent auth cookie. Prevented by an antiforgery token that the attacker cannot read. Add the nuance: it is a cookie-auth problem, so a bearer-token API is not exposed the same way.

"Why not bind the form straight to your entity?"

Over-posting. The model binder sets any property present in the request, so an attacker can submit fields that were never on the form. A view model with only the editable fields removes the attack surface entirely.
