The screening test

Before anyone reads your code, talks to you, or looks at your project, a large consultancy will send you a link to a timed automated test. It is scored by hidden test cases with no human in the loop. This is the round that filters most candidates out, and the only one you can prepare for mechanically.

Why this chapter exists

Chapter 38 tells you how to behave during live coding with a person watching. This is the other thing: sixty to ninety minutes, two or three problems, no interviewer, no partial credit for good intentions. Product companies and small software houses often skip it; NTT Data, Accenture, Reply, Engineering and their peers generally do not.

What it looks like

🧒 Simple

It is a driving theory test, not a driving lesson. Nobody is sitting next to you being impressed by how carefully you check the mirrors. A machine ticks boxes.

Which is annoying — but it also means it is the fairest round, because you can practise it and get straightforwardly better. Nobody can practise being liked.

🎓 Professional
  • 60–90 minutes, in the browser, timer visible, often with the tab monitored.
  • Two or three coding problems, sometimes preceded by multiple-choice questions on C#, SQL and OOP — that part is chapters 02 to 12 and you have already done it.
  • Scored by hidden tests, usually including large inputs designed specifically to fail an O(n²) solution.
  • Partial credit is normal. A solution passing 7 of 10 cases scores far better than an empty editor. Never leave a problem blank.
  • Frequently there is a SQL problem too, which for a .NET role is often the easiest marks in the whole test — chapter 10 covers more than it will ask.

Complexity, the amount you actually need

🧒 Simple

You are looking for a friend's name in the school register. One way: read every name from the top until you find it. The other: the names are alphabetical, so you open the middle, see whether you have gone too far, and throw away half. Then half again.

With 1 000 names the first way takes up to 1 000 looks. The second takes about 10. That gap is what all this notation is describing — not how fast your computer is, but how much worse it gets when the list grows.

🎓 Professional

Big-O describes how work grows with input size, ignoring constants. You need five of them:

Look at the last row. This is why the test has a large hidden input: it is not testing whether you can write the answer, it is testing whether you noticed the nested loop. And you have met this before — it is the same argument as a table scan versus an index seek in chapter 11, and the N+1 query in chapter 12. Three different chapters, one idea.

The shapes that keep coming back

Junior tests draw from a small pool. Recognising the shape in the first minute is most of the battle — and this is a .NET test, so LINQ is allowed and expected.

1 · frequency count with a dictionary
// "Find the first non-repeating character" / "most common word" / "any duplicates?"
var counts = new Dictionary<char, int>();
foreach (char c in input)
    counts[c] = counts.GetValueOrDefault(c) + 1;

foreach (char c in input)
    if (counts[c] == 1) return c;
return '\0';                          // two passes, O(n). Not nested loops.
2 · lookup instead of a second loop
// "Two numbers that sum to the target" — the classic O(n²) trap.
var seen = new HashSet<int>();
foreach (int n in numbers)
{
    if (seen.Contains(target - n)) return true;
    seen.Add(n);
}
return false;
3 · group, aggregate, rank — the one .NET tests love
// "Top 3 customers by total" — LINQ is the expected answer here.
var top = orders
    .GroupBy(o => o.CustomerId)
    .Select(g => new { Id = g.Key, Total = g.Sum(o => o.Total) })
    .OrderByDescending(x => x.Total)
    .ThenBy(x => x.Id)            // tie-break — hidden tests check this
    .Take(3)
    .ToList();
4 · running window over a sequence
// "Largest sum of k consecutive values" — slide, do not recompute.
int sum = numbers.Take(k).Sum(), best = sum;
for (int i = k; i < numbers.Length; i++)
{
    sum += numbers[i] - numbers[i - k];   // add one, drop one: O(n) not O(n×k)
    best = Math.Max(best, sum);
}
5 · strings, and the trap inside them
// ✗ Building a string in a loop is O(n²): strings are immutable,
//   so every += copies everything so far.
string result = "";
foreach (var w in words) result += w + " ";

// ✓
var sb = new StringBuilder();
foreach (var w in words) sb.Append(w).Append(' ');
// or simply: string.Join(" ", words)
6 · recursion, kept shallow
// Tree or nested-structure walks. Always ask: what is the base case?
static int Depth(Node? node) =>
    node is null ? 0 : 1 + Math.Max(Depth(node.Left), Depth(node.Right));
// If the input could be 100 000 deep, rewrite it with an explicit Stack<T>
// — StackOverflowException cannot be caught and kills the process.

Spending the ninety minutes

  1. Read every problem first (3 min). Do the easiest one first. Marks are marks, and confidence is real.
  2. Write the brute-force version and make it pass (15 min). A working O(n²) scores; an elegant half-finished solution scores nothing. Optimise only after something works.
  3. Then look for the nested loop and replace it with a dictionary or a set.
  4. Spend five minutes on edge cases before submitting. This is where the hidden tests live: empty input, one element, all elements equal, negative numbers, duplicates, null, and values above int.MaxValue — sums overflow silently in C#, so use long when totalling.
  5. Never leave a problem empty. Even a partial solution that handles the simple case earns points.
⚠ The five that actually cost people the round
  • list.Contains(x) inside a loop. Looks innocent, is O(n²). HashSet.Contains is O(1).
  • Building a string with += in a loop. Same trap, different clothes.
  • Ignoring the output format. Returning a list when it wanted a comma-separated string fails every test while the logic is perfect.
  • int.Parse on input that might be malformed. TryParse costs nothing and prevents a crash that scores zero.
  • Optimising first. The most common way to run out of time with an empty editor.
Try it yourself

Do not grind hundreds of puzzles. Do six, one per shape above, under a real timer — 30 minutes each, no pausing, no looking things up. Then do the honest part: 

For each one, write down:
  what shape was it?
  did I spot it in the first two minutes?
  which edge case did I miss?

The list of edge cases you personally forget is short and stable — most people have two or three — and once it is written down you stop losing marks to it. That list is worth more than another fifty solved problems. Then set up a dotnet new console project you can open in thirty seconds, because fumbling with tooling during a timed test is a real and avoidable loss.

Golden rules

  1. Never leave a problem blank. Partial credit is real.
  2. Read all the problems first, then do the easiest one.
  3. Make it work, then make it fast. Never the other way round.
  4. A loop inside a loop over the same data is the thing the large input is testing for.
  5. Dictionary and HashSet turn "search again" into "ask once". That is the whole trick.
  6. Never Contains on a List inside a loop.
  7. Never build a string with += in a loop. StringBuilder or string.Join.
  8. Sum into a long. int overflow is silent by default.
  9. TryParse, never Parse, on input you did not create.
  10. Check the output format as carefully as the logic.
  11. Edge cases: empty, one, all-equal, negative, duplicates, null.
  12. LINQ is expected in a .NET test. Readable LINQ beats a clever loop.
  13. Keep your own list of the edge cases you forget. It is short and it is fixable.

Interview questions

There is nobody to answer in this round — but the same material comes back in the technical interview afterwards, phrased like this:

"What is the complexity of your solution?"

State it and justify it in one breath: "O(n), because it is a single pass and each dictionary lookup is O(1) on average." The word average matters — hashing degrades to O(n) with bad collisions, and knowing that is a genuine signal. Then say what you traded: extra memory proportional to n.

"How would you make this faster?"

Find the nested loop and remove it by indexing one side into a dictionary or set. Then be honest about the trade — memory for time — and add the sentence that shows judgement: with a hundred items it does not matter, and you would only pay that memory if the input can actually get large.

"When is a List the wrong collection?"

When you are searching it by value rather than reading it by index — List.Contains is O(n), so calling it in a loop is O(n²). HashSet<T> for membership, Dictionary<K,V> for lookup by key. This is chapter 06 asked as an algorithms question, and the two are the same thing.

"You did not finish the test. What happened?"

Answer factually and without defensiveness: which problem, what you had, what you would do differently with the time again. Everyone respects "I spent too long optimising the second one before it worked, so I would write the brute force first next time." Nobody respects blaming the platform.
