The eight properties of data

Chapter 00b told you which types to use and chapter 02 told you how the language is put together. This one turns the camera round and looks at a single value — the number 5, the text "MI-0042", one order object — and asks what is actually true about it. Eight things are, and every one of them can be got wrong on its own.

Why this chapter exists

Beginner bugs look like eight unrelated mysteries: why 5 / 2 is 2, why a string "will not change", why two identical orders are not equal, why a bool came back false when nobody set it, why one list changed when a different variable was edited. They are not eight mysteries. They are eight properties, and each mystery is one of them being assumed rather than known. Name the eight and the mysteries stop arriving as a surprise — you learn to ask which property the bug is about.

The eight questions you can ask about a value

🧒 Simple

Imagine somebody hands you a sealed box. Before you can use what is inside, there are eight reasonable questions: what kind of thing is it, how big can it get, where is it kept, what was in it before anyone filled it, can I change it or must I swap the whole box, is it allowed to be empty, when are two boxes "the same", and when does somebody take it away.

A computer asks exactly those eight questions, and C# answers all eight before your program runs. Most of the time the answers are sensible and you never think about it. The bugs are the handful of places where the answer is sensible to the computer and surprising to you.

👔 Professional

This is not an academic taxonomy — it is a debugging checklist. When something is wrong with a value and you cannot see why, walk the eight in order. In practice the answer is almost always property 3 (you copied a reference and thought you copied the thing), property 4 (nobody assigned it and default looked like a real answer), or property 7 (you compared with the wrong kind of "same"). Interviewers ask about exactly those three, in exactly those words: value vs reference, default values, equality.

1 · Type — what fits, and what you may do to it

A type is two promises at once, and beginners usually only hear the first. Promise one: only certain values may go in. Promise two — the more useful one — only certain operations exist on it. The second promise is where most of your errors come from, and all of them arrive at compile time, which is the cheapest possible place to be wrong. 

int boxes = 12;
string code  = "MI-0042";

int more = boxes + 1;          // + means ADD here
string longer = code + 1;      // + means GLUE here → "MI-00421"

int wrong = code;               // error CS0029: cannot convert string to int
int alsoWrong = boxes.Trim();   // error CS1061: int has no Trim
Line by line
  • boxes + 1 — the operator is chosen by the types either side, not by the symbol. Two ints means integer addition.
  • code + 1 — the same symbol, a different operation: concatenation. The 1 is converted to "1" and glued on. This compiles, produces no warning, and is the single most common source of "why is my total 121 instead of 13".
  • int wrong = code; — promise one being kept. A string is not a number even when it looks like one, and there is no silent conversion in this direction.
  • boxes.Trim() — promise two being kept. Trim exists on string and nowhere else, so the type of the thing before the dot decides the entire list of things you are allowed to write after it. This is also why your editor can offer that list: it knows the type.
⚠️ + is the one operator that lies about what it does

Anywhere a string is on either side of +, the whole expression becomes text. That is why "Total: " + 2 + 3 is "Total: 23" and not "Total: 5": + goes left to right, the first one made text, so the second one glued too. Put the arithmetic in brackets, or use interpolation and stop thinking about it: $"Total: {2 + 3}".

2 · Range — the edge every number silently falls off

A type is a fixed number of bits, so it is also a fixed number of possible values. Go past the last one and C# does not stop — by default it wraps round to the first one, the way a car odometer does. This has cost real money in real systems, and it is the second half of the reason money is a decimal. 

int max = int.MaxValue;         // 2147483647
int oops = max + 1;             // −2147483648 — no error at all

int loud = checked(max + 1);    // throws OverflowException

byte b = 200;
b += 100;                        // 44 — a byte only holds 0..255

long ms  = 1000L * 60 * 60 * 24 * 365;  // fine: the L makes the whole sum long
long bad = 1000 * 60 * 60 * 24 * 365;   // overflows as int FIRST, then widens
Line by line
  • int.MaxValue — a constant on the type itself. Every numeric type has MaxValue and MinValue; you never have to remember the digits.
  • max + 1 — unchecked arithmetic, which is the default in C# for speed. The bits wrap and the sign flips. Nothing is logged.
  • checked(...) — an expression-level opt-in that turns the wrap into an OverflowException. There is a checked { } block form too, and a project-wide switch in the .csproj.
  • b += 100 — the same wrap on a smaller ring. byte holds 0–255, so 300 becomes 300 − 256 = 44.
  • 1000 * 60 * 60 * 24 * 365 — the trap of the group. Every literal here is an int, so the whole multiplication is done in int and has already overflowed before the result is widened into the long variable. Declaring the destination long saves nothing. The L suffix on the first number is what fixes it, because it makes every later step long too.
👔 Professional

Two habits cover this in practice. Use long for anything counting time, bytes or rows — int runs out at 2.1 billion and databases do not. And when a calculation mixes literals, put the widening suffix on the first operand, not on the variable you are assigning to. The compiler evaluates left to right and never looks ahead at where the answer is going.

3 · Location — the thing itself, or a note saying where it is

This is the property that causes the most confusion and the most interview questions, and the whole of it fits in one sentence: a value type variable holds the thing, and a reference type variable holds a note saying where the thing is. Everything else — why copies behave differently, why two variables can change together, why null is possible for one group and not the other — follows from that sentence. 

int a = 5;
int b = a;                    // copies the 5
b++;                          // a is still 5

var x = new Order { Quantity = 3 };
var y = x;                    // copies the address, not the order
y.Quantity = 9;              // x.Quantity is now 9 as well

y = new Order { Quantity = 1 };  // y now points elsewhere; x is untouched at 9
Line by line
  • int b = a; — a value copy. The bits of a are duplicated into b. From here the two have nothing to do with each other.
  • var y = x; — still a copy, but of the reference: the address. Both variables now name the same object. This is aliasing.
  • y.Quantity = 9; — mutating through the reference. There was never a second order to protect, so x sees it too. This is the bug people describe as "my object changed by itself".
  • y = new Order { … }; — reassignment, not mutation. You overwrote y's note with a different address. x still holds the old one. This is the distinction that makes the next property, mutability, read properly.
⚠️ "Value types live on the stack" is the half-true version

It is the sentence everyone repeats, and it is close enough for an interview but wrong often enough to bite: an int that is a field of a class lives on the heap, inside that object. A value type captured by a lambda lives on the heap too. The reliable statement is the one about copying: value types are copied by value, reference types by reference. That is true everywhere, and it is what the behaviour actually follows from.

👔 Professional

Which are which, without memorising a list: struct, enum and all the built-in numeric types plus bool, char and DateTime are value types. class, interface, delegate, arrays and every collection are reference types. string is the one that reads as a value type and is technically a reference type — it behaves like a value only because of property 5, which is two sections below.

4 · Default — what a value says before anyone answers

Every type has a default: the value it holds when nobody supplied one. C# is strict about locals — it refuses to read one you never assigned — but fields, array elements and properties are filled with the default silently, and the danger is that the default is usually a plausible answer rather than an obviously missing one.

TypeDefaultWhy it is dangerous
int, long, decimal, double 0 Zero is a real quantity. A price nobody set reads as free, not as unknown.
boolfalse Reads as a decision that was made. "Not approved" and "nobody has looked yet" are the same bit.
DateTime0001-01-01 Not null, not now — a real date in the year one, which sorts first and looks like corrupt data.
enum0 Whichever member happens to be first. Name the zero member Unknown on purpose.
stringnull Not "". Calling .Length on it throws.
any class, array, List<T>null An uninitialised list is not an empty list, and the difference is an exception.
int? and friendsnull The safe one: "nobody answered" is representable, so it cannot masquerade as zero.
 
class Order
{
    public int Quantity { get; set; }        // 0
    public bool IsApproved { get; set; }     // false
    public DateTime Placed { get; set; }     // 0001-01-01 00:00:00
    public string Code { get; set; }        // null ← warns under nullable context
    public DateTime? Shipped { get; set; }   // null, and honestly so
}

var o = new Order();
Console.WriteLine(o.IsApproved);            // False — but nobody decided that
Console.WriteLine(o.Code.Length);           // NullReferenceException
Console.WriteLine(default(int));            // 0 — the default, said out loud
Line by line
  • public int Quantity { get; set; } — an auto-property. It is never "unassigned" the way a local is; the object's memory is zeroed when it is created, so it starts at 0 and the compiler has nothing to complain about.
  • DateTime Placed — the default is DateTime.MinValue, which prints as year 0001. It is the giveaway in a report: a row dated 01/01/0001 is a row where nobody set the date.
  • string Code — null, because string is a reference type. Under nullable reference types (on by default in new projects) this line produces warning CS8618, which is the compiler asking you to decide: make it string?, or give it a value in a constructor.
  • DateTime? Shipped — the honest version. "Not shipped yet" is null, which cannot be mistaken for a date, and the compiler makes you check before you use it.
  • default(int) — the default operator. Useful in generic code where you cannot write the literal, and readable as a statement of intent: return default; says "the nothing-value of whatever I return".
⚠️ The default is why "0" and "unknown" get confused in a database

A nullable column read into a non-nullable property arrives as 0, and now the report says a hundred orders have a quantity of zero when in truth nobody recorded one. The fix is to make the C# type match the column: nullable column, nullable property. Making the property non-nullable does not make the data non-null — it just deletes the evidence.

5 · Mutability — edit in place, or swap the whole thing

Some values can be changed where they sit. Others cannot, and every "change" is secretly the creation of a new value that you then point at. string is the second kind, which is why it is the most misunderstood type in the language. 

string name = "mario";
name.ToUpper();                       // legal, useless — the answer is thrown away
name = name.ToUpper();                // "MARIO"

var list = new List<string> { "a" };
list.Add("b");                       // mutates in place, returns nothing

var sb = new StringBuilder();
for (int i = 0; i < 10_000; i++) sb.Append(i);  // one buffer, grown
string once = sb.ToString();          // one string, at the end
Line by line
  • name.ToUpper(); — a pure method: it reads its input and returns a result without touching anything. Discarding the result means the line had no effect at all. Your editor greys it out; the compiler does not consider it an error.
  • name = name.ToUpper(); — the same call with the answer assigned back. Note what actually changed: not the text, but which text name points at.
  • list.Add("b"); — the contrast. List<T> is mutable, so Add changes the existing list and returns void. A method returning void is a strong hint that it mutates something; a method returning a value is a hint that it does not.
  • StringBuilder — a mutable buffer for text. The same loop written with result += i would allocate ten thousand strings, each a copy of the last; this allocates one growing buffer and one string. Immutability is the reason the naive loop is slow, and StringBuilder is the escape hatch.
👔 Professional

Immutability is not a limitation, it is the reason a string is safe to pass anywhere. Hand a List<T> to a method and it may come back changed; hand it a string and it cannot. That property is worth building deliberately, which is what a record gives you: with produces a modified copy and the original is untouched. Chapter 02 has the syntax.

6 · Nullability — is "no value" one of the allowed answers

Every type answers a question. Nullability asks whether "the question does not apply" or "nobody has answered yet" are legal replies. Getting this wrong in either direction is expensive: allow null where it is meaningless and you check for it forever; forbid it where it is real and you invent a fake value — 0, "", 1900-01-01 — that something downstream will one day treat as data. 

DateTime? shipped = null;
bool isShipped = shipped.HasValue;          // false — ask, never assume

DateTime when = shipped ?? DateTime.MaxValue;  // supply a fallback, explicitly
int? year = shipped?.Year;                  // null in, null out — no exception

string? note = null;
int len = note?.Length ?? 0;              // the two operators together

DateTime boom = shipped.Value;              // InvalidOperationException when null
Line by line
  • DateTime? — shorthand for Nullable<DateTime>, a struct wrapping a value plus a flag. On a value type the question mark genuinely changes the type. On a reference type (string?) it changes nothing at runtime and is purely a message to the compiler.
  • .HasValue — the flag. Equivalent to shipped != null; use whichever reads better in the sentence you are writing.
  • ?? — the null-coalescing operator: "the left, unless it is null, in which case the right". It is the only way to turn a nullable into a non-nullable without risking an exception.
  • ?. — the null-conditional operator: "call this, unless the thing is null, in which case the whole expression is null". Note the consequence in the types: shipped?.Year is int?, not int, even though Year is an int.
  • .Value — the assertion. It means "I know there is one", and it throws if you were wrong. That is a feature: a loud failure beats a silent zero.
⚠️ bool? has three states and one of them defeats if

if (flag) does not compile when flag is a bool?, and the reason is worth understanding rather than working around: there is no sensible branch for null. Writing if (flag == true) compiles and silently treats "unknown" as "no". Sometimes that is right. Decide it deliberately, because flag == false and !(flag == true) are different questions once a third state exists. This is the same three-valued logic SQL's NULL has, which is why chapter 10 spends a section on it.

7 · Equality — four different meanings of "the same"

"Are these two the same?" is four questions in a trench coat, and C# will happily answer a different one from the one you asked. The four are: the same object, the same contents, the same after normalising (case, culture, whitespace), and the same key — which is equality plus a hash code, and is what a Dictionary actually uses. 

var a = new Order { Code = "MI-42" };
var b = new Order { Code = "MI-42" };
Console.WriteLine(a == b);                     // False — different objects

record Line(string Code, int Qty);
Console.WriteLine(new Line("MI-42", 1) == new Line("MI-42", 1));  // True

Console.WriteLine("mario" == "MARIO");           // False
Console.WriteLine("mario".Equals("MARIO",
    StringComparison.OrdinalIgnoreCase));       // True

object x = 5, y = 5;
Console.WriteLine(x == y);                     // False — two boxes
Console.WriteLine(x.Equals(y));                // True  — same contents
Line by line
  • a == b on a class — reference equality. The default == for a class compares addresses, so two objects with identical contents are not equal. This is the correct default: two different orders are two orders.
  • record — a class whose == is generated to compare every field. That is the whole reason records exist, and it is why DTOs and value objects should be records.
  • "mario" == "MARIO" — string is the exception among reference types: it overloads == to compare contents, character by character. Which is why case matters and nothing else does.
  • StringComparison.OrdinalIgnoreCase — the normalising comparison. Prefer Ordinal and OrdinalIgnoreCase for codes, identifiers, file names and anything a machine produced; the culture-aware ones are for text a human will read and sort, and they can genuinely disagree between machines.
  • object x = 5; — boxing. The int is wrapped in an object on the heap so it can be held in an object variable. == on two objects is reference equality, so two separately boxed fives are not == — and .Equals still says they match, because it asks the contents. One of the neatest ways to see that the operator and the method are not the same question.
👔 Professional

The rule that keeps you out of trouble: if you override Equals, override GetHashCode too. Two objects that are equal must return the same hash, or a Dictionary will look in the wrong bucket and report that your key is not there — while == keeps insisting it is. That bug takes a day and a half. Use a record, which generates both correctly, and only hand-roll when you must.

8 · Lifetime — when it stops existing, and who decides

In C you decide when memory goes away and are punished for getting it wrong. In C# the garbage collector decides: an object stays alive exactly as long as something can still reach it, and is collected some time after nothing can. You almost never think about this — except in the places where the thing being held is not memory. 

using (var conn = new SqlConnection(cs))     // a handle, not just memory
{
    await conn.OpenAsync();
}                                             // Dispose() runs here, guaranteed

using var file = File.OpenRead(path);        // same thing, disposed at end of scope

publisher.Changed += OnChanged;               // publisher now holds a path to THIS object
publisher.Changed -= OnChanged;               // the line people forget — that path is the leak
Line by line
  • using (…) — the deterministic half of lifetime. Memory is the collector's business, but a database connection, a file handle and a socket are somebody else's scarce resource, and "eventually" is not good enough. using calls Dispose() at the closing brace, including when an exception is thrown.
  • using var file = …; — the declaration form, disposed at the end of the enclosing block. Same guarantee, one less level of indentation.
  • publisher.Changed += OnChanged; — subscription creates a reference, and it points from the publisher to you. A long-lived publisher therefore keeps every short-lived subscriber alive forever, which is the classic .NET managed leak.
  • -= OnChanged; — the removal. The symmetry is the whole rule: whoever subscribes, unsubscribes. Chapter 08 has the full treatment, including why Dispose is where that line usually belongs.

Exercises, with the reasoning shown

Each of these is a few lines long and has one surprising answer. Read the code, commit to a prediction out loud, and only then read the explanation — a prediction you did not commit to is one you will agree with afterwards no matter what it said.

Exercise 1 — which property is this?

var a = new List<int> { 1, 2, 3 };
var b = a;
b.Add(4);
Console.WriteLine(a.Count);
Line by line
  • var b = a; — a reference copy. List<T> is a class, so this duplicates the address, and property 3 says there is still one list.
  • b.Add(4); — mutation through the alias. Property 5 says a list can be changed in place, and it just was.
  • a.Count — reads the same object. It prints 4.
  • The properties involved are 3 (location) and 5 (mutability). Swap List<int> for a struct and the answer becomes 3; make the list immutable and Add would not compile. Both properties have to line up for the surprise to happen, which is exactly why it is surprising.

Exercise 2 — the assignment that changes nothing

string s = "  MI-42  ";
s.Trim();
Console.WriteLine($"[{s}]");
Console.WriteLine($"[{s.Trim()}]");
Line by line
  • s.Trim(); — returns a new string and nobody keeps it. Property 5: strings are immutable, so no method can alter s.
  • $"[{s}]" — prints [ MI-42 ], spaces intact.
  • $"[{s.Trim()}]" — prints [MI-42], because here the result is used.
  • The tell for this bug in someone else's code is a statement that is nothing but a method call on a string. If a line reads x.Replace(…); with no = in front, it is dead code. Nothing warns you at compile time.

Exercise 3 — two fives that are not equal

object a = 5;
object b = 5;
Console.WriteLine(a == b);
Console.WriteLine(a.Equals(b));
Line by line
  • object a = 5; — boxing. Property 3 in motion: the value 5 is copied into a small object on the heap, and a holds its address. The second line makes a second, separate box.
  • a == b — the compiler sees two objects, so it picks reference equality. Two boxes, two addresses: False.
  • a.Equals(b) — a virtual call, so the runtime uses Int32's override, which compares the numbers: True.
  • Property 7 in one screen: the operator was chosen at compile time from the declared types, the method at run time from the actual ones. Change object to int and both print True, because a different == is selected.

Exercise 4 — the total that is short by ninety-seven cents

int unitPrice = 1999;        // cents
int quantity  = 3;
double euros = unitPrice * quantity / 100;
Console.WriteLine(euros);
Line by line
  • unitPrice * quantity — 5997, an int.
  • / 100 — int divided by int is integer division, so the fraction is discarded before anything else happens: 59. Property 1: the operator was chosen by the operands, and neither was a double.
  • double euros = … — the widening happens after the damage. It prints 59, not 59.97. The declared type of the destination never reaches back into the expression.
  • The tempting fix is the wrong one: / 100.0 gives 59.97 as a double. The right fix is / 100m into a decimal variable, because this is money — see chapter 00b.

Exercise 5 — the flag nobody set

class Shipment { public bool Checked { get; set; } }

var s = new Shipment();
if (!s.Checked) Console.WriteLine("needs inspection");
else            Console.WriteLine("cleared");
Line by line
  • new Shipment() — property 4. Every field is zeroed, so Checked is false without anyone deciding anything.
  • if (!s.Checked) — prints needs inspection, which happens to be correct here, and that is the danger: the default agreed with you by luck.
  • Rename the property to Cleared and the identical code now says an uninspected shipment is not cleared — still right. Rename it to Blocked and a record nobody has looked at is reported as not blocked, which is wrong and will ship.
  • The lesson is about naming, not about bool: the default must be the safe answer. When it cannot be, use bool? and make "nobody looked" a state you can see. Property 6 exists for precisely this.
Try it yourself

Make a console project and write a class Box { public int Size; } and a struct Crate { public int Size; } with nothing else in them. Put one of each in a List, pull an item out into a variable, change its Size, and print the list. One of them changes and one does not. Then make the struct's field readonly and watch which line stops compiling. You will have demonstrated properties 3, 5 and 4 in about fifteen lines, and you will not need to look them up again.

Golden rules

  1. Value types copy the value; reference types copy the address. Every surprise in this chapter follows from that one sentence, and it is true everywhere — unlike "stack versus heap", which is false for an int field of a class.
  2. A cast on the outside cannot fix arithmetic on the inside. Widen an operand, not the result: (long)big + big, never (long)(big + big).
  3. int overflow is silent by default. Use long for anything counting time, bytes or rows, and checked where a wrap would be money.
  4. The default is an answer, not a blank. 0, false and 0001-01-01 all read as data somebody chose. If "nobody answered" is a real state of the domain, the type must be nullable — and it must match the database column.
  5. Name a bool so that false is the safe answer. When it cannot be, use bool?.
  6. Strings are immutable. A statement that is nothing but a method call on a string is dead code. Concatenating in a loop allocates one string per iteration — that is what StringBuilder is for.
  7. Decide which "same" you mean. == on a class compares references; on a string or a record it compares contents. Two boxed ints are Equals and are not ==.
  8. Override Equals, override GetHashCode. Equal objects that hash differently break every Dictionary and HashSet while == keeps insisting they match. Prefer a record, which generates both.
  9. Ordinal and OrdinalIgnoreCase for codes, identifiers and file names. Culture-aware comparison is only for text a human reads, and it can disagree between machines.
  10. Alive means reachable, not "in use". Whoever subscribes to an event, unsubscribes — that reference points from the publisher to you, and it is what a managed leak is made of.
  11. using for anything that is not memory — connections, files, sockets. The collector handles memory; "eventually" is not good enough for somebody else's scarce handle.

Interview questions

"What is the difference between a value type and a reference type?"

A value type variable holds the value itself, so assigning it copies the value and the two copies are independent afterwards. A reference type variable holds the address of an object, so assigning it copies the address and both names then refer to one object — change it through either and both see the change. I would avoid making "stack versus heap" the headline answer, because an int field of a class lives on the heap inside that object; the copying rule is the one that is true everywhere.

"Why is string a reference type that behaves like a value type?"

Because it is immutable and because it overloads ==. No method can change an existing string — they all return new ones — so aliasing is harmless, and == is defined to compare contents rather than addresses. Between the two, a string is impossible to misuse in the way an aliased List is. The cost is allocation: concatenating in a loop makes one string per iteration, which is what StringBuilder exists for.

"Two objects are equal but the dictionary cannot find one. What happened?"

Equals was overridden and GetHashCode was not. A dictionary uses the hash to choose a bucket and only then compares with Equals, so if two equal objects hash differently it looks in the wrong bucket and reports a miss — while a direct comparison in the debugger keeps saying they are equal. The fix is to override both from the same set of fields, or to use a record, which generates both.

"Quando useresti int? invece di int?"

Quando "nessun valore" è uno stato reale del dominio e non un errore. Se la colonna nel database è nullable, la proprietà deve essere nullable: altrimenti il null arriva come 0 e da quel momento non si distingue più da un dato vero. Il costo è che il compilatore mi obbliga a gestire il caso, ed è esattamente quello che voglio — il valore finto, tipo 0 o 0001-01-01, non me lo ricorda nessuno.
