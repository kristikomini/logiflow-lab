.NET and .NET Core

C# is a language. .NET is everything that makes the language run: a compiler, a runtime that turns compiled code into machine instructions, a garbage collector, a class library, and a package system. Most confusion about "which .NET" is really confusion about which of those five things is being discussed.

From the advert

"Buona esperienza nello sviluppo con framework .NET / .NET Core." — the slash means both, which means migration.

What .NET actually is

🧒 Simple

You write a letter in English. The person receiving it only reads Japanese. So you need a translator. But this translator is clever: instead of translating the whole letter in advance, they translate each sentence the moment it is read out loud — and they remember their translation, so if the same sentence comes up again it is instant.

Your C# is the English. The computer’s own language is the Japanese. .NET is the clever translator — plus a tidy assistant who quietly throws away the pages nobody is reading any more.

🎓 Professional

.NET is a managed execution environment. The C# compiler (Roslyn) does not produce machine code; it produces IL (Intermediate Language) packaged into an assembly — a .dll or .exe that also carries metadata describing every type inside it. At run time the CLR (Common Language Runtime) loads that assembly and the JIT compiler translates each method into native code for the actual CPU, the first time that method is called, caching the result.

"Managed" means the runtime owns memory: the garbage collector reclaims objects you stop referencing, so there is no free(). The same metadata that makes JIT possible is what makes reflection, serialisation and dependency injection possible.

.NET Framework vs .NET Core vs .NET 5+

This is the single most common interview question on this topic, and the naming history is genuinely confusing, so learn it as a story rather than a table.

  • .NET Framework (2002–2019, ends at 4.8). Windows only. Installed into Windows, one shared copy for every application on the machine. Still fully supported, still runs an enormous amount of Italian enterprise software, but it receives no new features — only security fixes.
  • .NET Core (2016–2019, 1.0–3.1). A rewrite. Cross-platform, open source, and shipped with the application instead of being installed into the OS. Much faster.
  • .NET 5 and later (2020→). The two were unified and the word "Core" was dropped — and version 4 was skipped so nobody would confuse ".NET 4" with ".NET Framework 4.x". This is just ".NET" now: net8.0, net10.0.

⚠ The trap

Saying ".NET Core is the new .NET Framework". It is not an upgrade, it is a re-implementation — and some things did not come with it. WebForms, WCF server-side, .NET Remoting and AppDomains do not exist in modern .NET. A migration is therefore never just a re-target; the honest answer to "can we move this to .NET 10?" always starts with "what does it use?"

Release cadence — worth knowing by heart

A new major version ships every November. Even-numbered releases are LTS (Long Term Support, three years); odd-numbered ones are STS (eighteen months). So .NET 8 and .NET 10 are LTS — and that is why enterprises sit on them. When an interviewer asks "which version would you target for a new internal service?", the answer they want is "the current LTS, unless there is a specific reason not to."

SDK vs runtime

🧒 Simple

The runtime is an oven. It is all you need to bake a cake somebody else prepared. The SDK is the whole kitchen — oven included, plus the bowls, scales and recipe books you need to make the cake. Your laptop needs the kitchen. The server only needs the oven.

🎓 Professional

The runtime executes IL: the CLR, the GC and the base class library. The SDK contains the runtime plus the compilers, MSBuild, the templates and the dotnet CLI. Developer machines and build agents need the SDK; servers need only the runtime — or nothing at all, if you publish self-contained and ship the runtime inside the output folder.

terminal — what is installed on this machine
# which SDK will be used here (respects global.json)
dotnet --version

# everything installed, SDKs and runtimes separately
dotnet --info
dotnet --list-sdks
dotnet --list-runtimes
Line by line
  • dotnet --version — prints the SDK that would be used in this folder, not the newest one installed. Run it somewhere else and the answer can differ, because a global.json higher up the tree can pin it.
  • dotnet --info — everything at once: the SDK in effect, the runtimes, the architecture and the install paths. This is the output to paste into a bug report.
  • dotnet --list-sdks and --list-runtimes — two lists, because they are two different things. You can have many SDKs and many runtimes side by side; an application built against .NET 8 keeps running on the .NET 8 runtime even with .NET 10 installed.
  • # — a shell comment, not C#. Nothing on these lines is a language construct: this is the terminal.

A global.json in the repository root pins the SDK, so every developer and every build agent compiles with the same one. This repository has one:

global.json
{
  "sdk": {
    "version": "10.0.300",
    "rollForward": "latestFeature",
    "allowPrerelease": false
  }
}
Line by line
  • This is JSON, not C#. global.json sits at the repository root and is read by the dotnet tool before it does anything else.
  • "sdk" — the object naming which SDK this repository expects. It constrains the build, never what the finished application runs on.
  • "version": "10.0.300" — the requested SDK. Without this file, whoever has the newest SDK installed builds with a different compiler from everyone else, and the difference shows up as a build that fails only in CI.
  • "rollForward": "latestFeature" — what to do when that exact version is absent. latestFeature accepts a newer feature band of the same major version; disable would demand the exact number and fail otherwise.
  • "allowPrerelease": false — never silently select a release candidate. A developer who installed a preview for something else does not get a surprise compiler.
  • JSON has no comments and no trailing commas, which is why the reasoning for a file like this lives in the repository's documentation rather than beside it.

The project file

Modern .csproj files are short because they are subtractive: everything is included by default, so the file only records what is unusual.

LogiFlow.Api.csproj
<Project Sdk="Microsoft.NET.Sdk.Web">

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>

  <ItemGroup>
    <!-- a NuGet package -->
    <PackageReference Include="Microsoft.EntityFrameworkCore.SqlServer" />
    <!-- another project in the same solution -->
    <ProjectReference Include="..\LogiFlow.Application\LogiFlow.Application.csproj" />
  </ItemGroup>

</Project>
Line by line
  • A .csproj is XML, and it is an MSBuild file rather than a manifest. The angle brackets are elements, and Include="..." is an attribute.
  • Sdk="Microsoft.NET.Sdk.Web" — selects the project SDK, which imports a large set of default build rules. .Web adds the ASP.NET Core framework reference and the static-file conventions; plain Microsoft.NET.Sdk would be a class library or console app.
  • <PropertyGroup> — holds single-valued settings. <ItemGroup> below holds lists. That is the whole distinction, and it is why references never go in a PropertyGroup.
  • <TargetFramework>net10.0</TargetFramework> — which framework to compile against. It decides which APIs exist at all, and therefore which runtime can execute the result.
  • <Nullable>enable</Nullable> — switches on nullable reference types, so string means "never null" and string? means "may be null". It is compile-time analysis only — nothing is checked at run time, and data arriving from JSON or a database can still be null.
  • <ImplicitUsings>enable</ImplicitUsings> — the compiler adds the common using directives for you. This is why a modern file can call Console.WriteLine with no using System; at the top.
  • <TreatWarningsAsErrors>true</TreatWarningsAsErrors> — a warning now fails the build. Deliberate: warnings that nobody has to fix accumulate until they hide the one that mattered.
  • <PackageReference Include="..." /> — a NuGet package, downloaded from a feed. Note there is no Version attribute: this repository uses central package management, so every version lives in one Directory.Packages.props and cannot drift between projects.
  • <ProjectReference Include="..\..." /> — another project in the same solution, compiled from source. This is the wire that decides which project is allowed to mention which, and it is how the layering in chapter 23 is enforced by the compiler rather than by good intentions.
  • <!-- ... --> — an XML comment. Unlike JSON, XML has them.

Four things to be able to explain:

  • Sdk="…" — which build rules apply. Microsoft.NET.Sdk for a library, .Web for ASP.NET Core, .Worker for a background service.
  • TargetFramework — the TFM. net10.0 is portable; net10.0-windows unlocks Windows-only APIs and gives up Linux.
  • Nullable — nullable reference types (chapter 02). Turning this on is the cheapest bug reduction available in C#.
  • ImplicitUsings — the compiler adds the obvious using lines (System, System.Linq…) for you.
Central Package Management

Notice the PackageReference above has no Version. That is because this repository uses Directory.Packages.props, where every version is declared once for the whole solution. It is how you stop project A using Newtonsoft 12 and project B using 13 — a genuinely good thing to mention in an interview.

The CLI you will actually use

terminal — the daily commands
dotnet new webapi -o LogiFlow.Api   # create from a template
dotnet restore                      # download NuGet packages
dotnet build                        # compile to IL
dotnet run                          # build, then start
dotnet watch                        # rebuild and restart on every save
dotnet test                         # run the test projects
dotnet publish -c Release -o out    # everything needed to deploy

dotnet add package Serilog          # add a dependency
dotnet list package --outdated      # what has moved on without you
Line by line
  • dotnet new webapi -o LogiFlow.Api — creates a project from a template. -o is the output folder.
  • dotnet restore — resolves and downloads NuGet packages. You will rarely type it: build, run, test and publish all restore first unless told not to.
  • dotnet build — compiles to IL in a .dll under bin/. Not machine code — that translation happens later, at run time.
  • dotnet run — builds and then starts the application. It is a developer convenience and not how anything is started in production, where you run the published .dll directly.
  • dotnet watch — rebuilds and restarts on every save. For a web project it also does hot reload, applying many edits without a restart at all.
  • dotnet publish -c Release -o out — produces a folder containing everything needed to deploy. -c Release is the configuration: optimisations on, no debug-only checks. Publishing a Debug build is a small, common and entirely avoidable production mistake.
  • dotnet add package Serilog — adds a <PackageReference> to the .csproj. It edits the file you saw above; there is no hidden state anywhere else.
  • dotnet list package --outdated — what has moved on without you. Worth running before an interview about a codebase you claim to maintain.
⚠ Debug vs Release

dotnet run defaults to Debug, which disables most JIT optimisations so that the debugger can map machine code back to your source. Any performance number measured in Debug is meaningless. Benchmark with -c Release — and if an interviewer mentions a timing they took in Debug, saying so politely is a very good sign.

Assemblies, NuGet and where code comes from

🧒 Simple

A NuGet package is a box of Lego that someone else designed and put on a shelf for everyone. You do not build a wheel yourself — you take the wheel box down, check it says which version it is, and click it onto your model.

🎓 Professional

An assembly is the unit of deployment and of versioning: one .dll, containing IL, metadata and a manifest. NuGet is the package manager that fetches assemblies (and the transitive graph they depend on) into ~/.nuget/packages, and obj/project.assets.json records exactly what was resolved. If you have ever seen a build succeed locally and fail on the agent, that file — or a missing global.json — is very often the reason.

Try it yourself

Prove IL exists rather than taking it on trust. Two minutes:

dotnet new console -o IlDemo
cd IlDemo
dotnet build

# The output is not machine code. Open it and look:
# bin/Debug/net10.0/IlDemo.dll
# Paste it into https://sharplab.io and switch the output to "IL"
Line by line
  • dotnet new console -o IlDemo then cd IlDemo — a throwaway project, because the point is to look at the output rather than to keep it.
  • dotnet build — produces bin/Debug/net10.0/IlDemo.dll. The extension says DLL and the file is not a native library: it is an assembly, holding IL plus metadata describing every type inside it.
  • IL — Intermediate Language. The C# compiler stops here. Turning IL into instructions your processor understands is the JIT's job, and it happens the first time each method actually runs.
  • Why this matters rather than being trivia. It is why the same .dll runs on x64 and on ARM; why a decompiler can reconstruct readable C# from a shipped binary; and why the first request to a freshly started service is measurably slower than the second.
  • sharplab.io — paste C# in, choose IL or "C#" as the output, and watch what the compiler generates. Switching the output to C# is the fastest way to see what async, foreach, records and lambdas actually expand into.

SharpLab is the fastest way to answer "what does this C# actually compile to?" — it is also how you win arguments about whether foreach allocates.

Golden rules

  1. C# compiles to IL, not machine code. The JIT does the second compilation, per method, at run time.
  2. "Managed" means the runtime owns memory. The GC is not optional and not a leak-proof guarantee — it collects what is unreachable, not what you are finished with.
  3. .NET Framework is Windows-only and feature-frozen at 4.8. Modern .NET is cross-platform and ships every November.
  4. Version 4 was skipped to avoid collision with .NET Framework 4.x. Say this and you sound like you were there.
  5. SDK to build, runtime to run. Pin the SDK with global.json.
  6. The TFM (net10.0) decides which APIs exist. Adding -windows buys Windows APIs and costs you Linux.
  7. Prefer the current LTS (even-numbered) for anything a business depends on.
  8. Never quote a performance measurement taken in a Debug build.
  9. A .NET Framework → .NET migration is blocked by what the app uses — WebForms, WCF hosting, AppDomains — not by the target framework line.

Interview questions

"What is the difference between .NET Framework and .NET Core?"

Give the story, not a list: Framework is the original Windows-only runtime installed into the OS, frozen at 4.8; Core was a cross-platform rewrite shipped with the application; from .NET 5 the two lines merged and the name became just ".NET". Then add the sentence that shows experience: "which matters mostly when you have to migrate, and the blockers are usually WebForms or WCF hosting rather than the language."

"What happens between pressing F5 and your code running?"

Roslyn compiles C# to IL inside an assembly with metadata; the host starts the CLR; the CLR loads the assembly; the JIT compiles each method to native code on first call and caches it; the GC manages the heap throughout.

"Do I need the SDK on the production server?"

No — the runtime is enough, and not even that if you publish self-contained. The SDK belongs on developer machines and build agents.

"What is IL, and why bother with it?"

A CPU-independent instruction set. It buys portability (one build, many platforms), the metadata that reflection and DI depend on, and a JIT that can optimise for the exact processor it finds at run time — something an ahead-of-time compiler cannot do.
