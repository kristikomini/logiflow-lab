REST principles

REST is not a technology and not a library. It is a set of constraints on how to use HTTP, and the whole point of them is that a caller who has never seen your API can guess how it works. This chapter is the theory; the next one is the C#.

From the advert

"Comprensione dei principi REST e sviluppo di Web API." The word principi is doing real work: they will ask why a verb, why a status code — not just whether you can write a controller.

The idea

🧒 Simple

Think of a library where every book has its own address, like shelf 3, row 2, book 7. Once you know the addressing system you can find anything, because it always works the same way. Nobody has to give you a special map for each book.

And there are only four things you ever do at an address: look at the book, put a new one there, change the one that is there, or take it away. Four verbs, infinite addresses. That is REST.

🎓 Professional

REST (Representational State Transfer) was described by Roy Fielding in 2000 as an architectural style defined by constraints, of which these matter in practice:

  • Resources with identifiers. Nouns, addressed by URI. The thing at /orders/42 is an order; what you receive is a representation of it (JSON, usually), not the thing itself.
  • Uniform interface. The same small set of verbs everywhere, with the same meanings. This is what makes an API guessable.
  • Statelessness. Every request carries everything needed to serve it. The server keeps no per-client conversation state between requests.
  • Cacheability. Responses say whether and for how long they may be cached.
  • Layered system. The client cannot tell whether it is talking to the server, a load balancer, a gateway or a cache — which is what allows all three to exist.

The anatomy of a request

The verbs

VerbMeaningSafeIdempotentTypical success
GETRead a resource✓✓200, or 404
POSTCreate, or "do something"✗✗201 + Location
PUTReplace entirely✗✓200 or 204
PATCHModify partially✗✗ (usually)200 or 204
DELETERemove✗✓204
🧒 Simple — safe and idempotent

Safe means "looking does not change anything". You can read the same page a hundred times and the book is unchanged.

Idempotent means "doing it twice is the same as doing it once". Setting a light switch to off is idempotent — press it five times, the light is still off. Flipping the switch is not: five presses leaves it on.

This matters because the internet loses messages. If your phone sends a request and the reply never arrives, it does not know whether the thing happened. If the request was idempotent, it can safely just send it again.

🎓 Professional

Safe = no observable state change, so it can be prefetched, cached and retried freely. Idempotent = N identical requests have the same effect as one, so a client, proxy or retry policy may repeat it after a timeout without risk.

POST is neither, which is why "did my payment go through?" is a genuinely hard problem. The standard solution is an idempotency key: the client sends a unique header, the server records it with the result, and a repeat of the same key returns the original response instead of charging twice. Mentioning this unprompted is a strong signal.

⚠ PUT replaces; PATCH modifies

A PUT with only {"status": "Sent"} means "the order is now only this" — a strict implementation clears every field you omitted. If you want to change one field, use PATCH. Getting this wrong quietly wipes data.

Designing the URLs

✗ Not REST✓ RESTWhy
GET /getOrdersGET /ordersThe verb is the HTTP method, not part of the path.
POST /createOrderPOST /ordersSame reason.
GET /orders/delete/42DELETE /orders/42Never mutate through GET. A crawler will find it.
GET /orderGET /ordersCollections are plural, consistently.
GET /orders/42/lines/7/product/nameGET /order-lines/7Nest one level at most; deeper is unusable.
GET /orders?action=submitPOST /orders/42/submitAn action that is not CRUD is a sub-resource, and it is a POST.

GET /api/v1/orders?customerId=42&status=submitted&page=2&pageSize=20&sort=-createdAt

# the path identifies WHICH resources; the query says how to slice them
Line by line
  • /api/v1/orders — the path identifies the resource, and it is a plural noun. Not /getOrders: the verb is GET, supplied by HTTP, so putting one in the path says it twice.
  • v1 — the version. In the path is the crudest of the three options (header and media type are the others) and by far the easiest to read in a log or curl.
  • ? — separates path from query string. The path says which resources; the query says how to slice them. That division is the single most useful rule for designing a URL.
  • & — separates parameters. In HTML it must be written &amp;, which is why a copied URL sometimes arrives broken.
  • status=submitted — a filter. Note it is the lower-case wire name, not the C# enum's Submitted or its underlying number; the API's vocabulary is its own contract.
  • page=2&pageSize=20 — paging is not optional. A collection endpoint with no limit is one that returns a million rows the day the table grows, so cap pageSize server-side regardless of what is asked for.
  • sort=-createdAt — the leading minus means descending, a widespread convention. Whatever you choose, whitelist the sortable fields: passing this straight into an ORDER BY is an injection hole.

Status codes that matter

CodeNameUse it when
200OKSuccess with a body.
201CreatedYou created something. Include a Location header.
204No ContentSuccess, nothing to return — a delete or an update.
400Bad RequestThe request is malformed or fails validation. Their fault.
401UnauthorizedActually means unauthenticated — who are you?
403ForbiddenWe know who you are, and you may not do this.
404Not FoundNo such resource. Also used to hide existence from unauthorised callers.
409ConflictValid request, wrong state — duplicate key, concurrency conflict, submitting a submitted order.
422UnprocessableSyntactically fine, semantically invalid. Some teams prefer this to 400.
429Too Many RequestsRate limited. Send Retry-After.
500Server ErrorYour fault. Never leak a stack trace with it.
503UnavailableTemporarily down — a dependency is unreachable.
⚠ 200 OK { "success": false }

The single most common REST mistake. It forces every client to parse the body to discover whether it worked, and it defeats every intermediary — proxies, monitoring, retry policies, browser caches — all of which understand status codes and none of which understand your JSON. The status code is the answer; the body is the detail.

Errors: use the standard shape

RFC 9457 Problem Details is what ASP.NET Core produces by default. Use it rather than inventing your own error object — clients and tooling already understand it.

400 Bad Request
{
  "type":     "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title":    "One or more validation errors occurred.",
  "status":   400,
  "traceId":  "00-8f2b…-01",
  "errors": {
    "CustomerId": ["CustomerId must be greater than 0."],
    "Lines":      ["An order must have at least one line."]
  }
}
Line by line
  • This is RFC 9457 Problem Details, the standard error shape for HTTP APIs, and ASP.NET Core produces it for you. Inventing your own means every client writes a special case for you.
  • "type" — a URI identifying the kind of problem. It is an identifier rather than a link to fetch; it need not resolve, though pointing it at your own documentation is a kindness.
  • "title" — a short, stable summary of the problem type. It should not vary per occurrence, which is what lets a client group errors by it.
  • "status" — the HTTP status code, repeated in the body. Redundant on purpose: it survives logging and proxies that lose the response line.
  • "traceId" — the W3C trace context id for this request. It is the single most valuable field here: a user can quote it and you can find the exact request in the logs. It links directly to chapter 25.
  • "errors" — the validation extension: field name to list of messages. Note it is a list per field, because one field can fail two rules.
  • What is deliberately absent is a stack trace or an exception type. Those are for your logs, not for the caller, and shipping them is how internals leak into a public contract.

Statelessness

🧒 Simple

Imagine a shop where the assistant forgets you completely the moment you turn around. Annoying? No — brilliant. It means any assistant can serve you, so the shop can hire twenty of them and you never have to queue for "your" one.

You just have to bring your loyalty card every time. That card is the token.

🎓 Professional

No server-side session between requests. Each request carries its own authentication, usually a bearer token. The payoff is horizontal scale: any instance can serve any request, so you can add instances behind a load balancer without sticky sessions, and a restarting instance loses nothing.

Note what statelessness does not mean: the database is still state. The constraint is about conversation state, not application state.

The Richardson maturity model

Useful for one honest sentence in an interview about how RESTful things really are.

LevelWhat it means
0One URI, one verb. RPC tunnelled through HTTP (classic SOAP).
1Resources have their own URIs — but everything is still POST.
2Proper verbs and proper status codes. Almost every real API lives here, including good ones.
3HATEOAS — responses include links to the next available actions. Rare in practice.

Saying "we target level 2, and level 3 is rarely worth the cost outside public hypermedia APIs" is a more credible answer than claiming full REST compliance.

Versioning

You will change the API. Decide how before you have callers. The common options are URL (/api/v1/orders — visible and simple, and what most teams pick), a header (api-version: 1 — cleaner URIs, harder to test by hand), or a media type. Any is defensible; none is not.

Try it yourself

Design the endpoints for a small warehouse system. Write the verb, path and success code for:

  1. List all orders for customer 42, page 2
  2. Fetch order 1001
  3. Create an order
  4. Change only the delivery address of order 1001
  5. Submit order 1001 (a state transition, not a field edit)
  6. Cancel order 1001
  7. Submit an order that is already submitted

Answers: GET /customers/42/orders?page=2 200 · GET /orders/1001 200 · POST /orders 201 + Location · PATCH /orders/1001 200 · POST /orders/1001/submit 200 · POST /orders/1001/cancel 200 (or DELETE if it truly disappears) · and the last one is 409 Conflict — the request was fine, the state was not. Number 7 is the one that separates candidates.

Golden rules

  1. URLs are nouns; HTTP methods are the verbs. /getOrders is a bug in the design.
  2. Collections plural, one level of nesting at most.
  3. GET never changes state. Ever.
  4. Idempotent: GET, PUT, DELETE. Not idempotent: POST, usually PATCH.
  5. For "create and retry safely", use an idempotency key.
  6. PUT replaces the whole resource; PATCH changes part of it.
  7. The status code carries the outcome. Never 200 OK with an error inside.
  8. 401 is "who are you"; 403 is "not you"; 409 is "not now".
  9. Return Problem Details for errors, with a trace id.
  10. Stateless: every request stands alone. That is what makes horizontal scale possible.
  11. Version from day one, and pick one scheme.
  12. Non-CRUD actions become sub-resources: POST /orders/1001/submit.

Interview questions

"What makes an API RESTful?"

Resources identified by URI, a uniform interface using HTTP verbs with their standard meanings, statelessness, and honest use of status codes. Then be candid: most APIs, including good ones, sit at Richardson level 2 rather than doing full HATEOAS.

"What does idempotent mean, and which verbs are?"

N identical requests have the same effect as one. GET, PUT, DELETE are; POST is not. Then give the reason it matters: a client that times out cannot know whether the request succeeded, and idempotency is what makes a retry safe.

"PUT or PATCH?"

PUT replaces the entire resource, so omitted fields should be cleared; PATCH applies a partial change. Sending a partial body with PUT is a common and destructive mistake.

"401 or 403?"

401 means unauthenticated — the credentials are missing or invalid, despite the name "Unauthorized". 403 means authenticated but not permitted. And sometimes 404 is the right answer to a 403 situation, when confirming that a resource exists is itself a leak.

"A client submits the same order twice because of a timeout. What do you do?"

Accept an idempotency key header, store it against the result of the first request, and return that stored response for a repeat. Alternatively make the operation naturally idempotent with a client-generated id and a unique constraint. This question is asked far more often than people expect, and it is where REST theory becomes practical.
