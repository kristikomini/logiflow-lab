Disposal, memory and shared state

C# does two enormous favours for you: it manages memory, and single-threaded code behaves the way you read it. This chapter is about the three places where each favour stops — unmanaged resources, leaks the collector cannot help with, and a second thread. All three are standard interview questions, and all three are where real production bugs come from.

Why this chapter exists

"Mi spiega IDisposable?", "che cosa fa il garbage collector?" and "come rendi questo codice thread-safe?" are three of the most reliably asked junior questions in .NET, and none of the other fifty-six chapters answers them directly. They also happen to be the material behind the two worst kinds of production bug: the process that slowly eats memory, and the one that gives a different answer under load.

What the garbage collector does, and does not

🧒 Simple

Imagine your bedroom is tidied for you by someone who follows one rule: if nothing is holding it, it goes. A toy on the floor with nobody playing with it — gone. A toy your little brother is clutching — stays, even if he has forgotten he is holding it.

So the tidying is automatic, but it cannot help with two things. It will not close the tap you left running, because a tap is not a toy. And it will not take a toy off your brother, however long he holds it.

🎓 Professional

The GC frees managed memory that is no longer reachable from a root (a local, a static, a live thread). Two consequences that matter more than the algorithm:

  • It is non-deterministic. You do not know when. So it is useless for anything that must be released promptly — a file lock, a socket, a database connection.
  • It only frees memory. A file handle, a socket, a window handle, a native library allocation are unmanaged resources, and the runtime knows nothing about them.

Generations are worth one sentence: objects start in gen 0, which is collected very often and very cheaply; survivors are promoted to gen 1, then gen 2, which is collected rarely and expensively. The design bets that most objects die young, which for a web request is exactly right. Objects over 85 KB go straight to the Large Object Heap, which is not compacted by default — a good reason not to allocate huge arrays in a loop.

IDisposable and using

🎓 Professional

IDisposable is how you say "this holds something the GC cannot clean up, and here is how to release it deterministically". One method, Dispose(), and one keyword that guarantees it is called: 

// The using STATEMENT — the classic form.
using (var conn = new SqlConnection(cs))
{
    ...
}   // Dispose() runs here — even if the body threw.

// The using DECLARATION (C# 8+) — same thing, less nesting.
using var conn = new SqlConnection(cs);
...     // Dispose() runs at the end of the enclosing scope.

// What the compiler actually emits — this is the whole trick:
var conn = new SqlConnection(cs);
try     { ... }
finally { conn?.Dispose(); }
Line by line
  • using (var conn = ...) { } — the using statement. The braces are the lifetime: Dispose() runs when control leaves them, by any route including an exception.
  • using var conn = ...; — the using declaration (C# 8). No braces, no extra nesting; disposal happens at the end of the enclosing scope. Prefer it, unless you deliberately want a shorter lifetime than the whole method.
  • try { ... } finally { conn?.Dispose(); } — this is what both compile to. There is no runtime feature called "using"; it is syntax for a try/finally.
  • ?. in the generated finally — guards the case where the constructor itself threw and conn is still null.
  • Why finally and not "after the block": code after the block is skipped when an exception unwinds. A connection released only on the happy path is a leak that appears exclusively under errors — the load pattern where you can least afford it.
  • IDisposable exists because the GC does not manage anything but memory. File handles, sockets and database connections are OS resources the collector knows nothing about, so releasing them is your job, deterministically.

using is try/finally. That is the answer to "what does using compile to", and it explains why an exception cannot leak the resource.

For anything doing I/O on release — flushing a stream, closing a connection — there is IAsyncDisposable and await using, so the release does not block a thread. Prefer it when both are offered.

⚠ The exception: do not dispose HttpClient per call
// ✗ Looks correct. Exhausts sockets under load.
using var http = new HttpClient();
var r = await http.GetAsync(url);
Line by line
  • using var http = new HttpClient(); — correct-looking and wrong. It follows the rule from the previous block and still breaks under load.
  • Disposing an HttpClient does not release its socket immediately. The underlying TCP connection goes into the OS TIME_WAIT state for up to four minutes. Create one per request and a busy service exhausts the ephemeral port range and starts throwing SocketException.
  • The opposite extreme is also wrong. One static HttpClient forever caches DNS, so it keeps calling an IP address that has been decommissioned — invisible until a failover.
  • The answer is IHttpClientFactory: services.AddHttpClient<IPricingClient, PricingClient>(). It pools handlers, rotates them on a schedule to pick up DNS changes, and is where retry policies attach.
  • The general lesson. "Implements IDisposable" does not imply "wrap it in using". Injected services — HttpClient, DbContext — are owned by the container, and disposing one early breaks every later user in the same request.

Disposing an HttpClient does not immediately free its socket — the connection sits in TIME_WAIT for a while. In a loop or a busy endpoint you run out of ports and start getting SocketException from a machine that looks idle. The answer is IHttpClientFactory, which pools and rotates handlers for you. This is a favourite interview question because it is the one case where the obvious application of the rule is wrong.

Boxing, the allocation you did not write

🧒 Simple

A number is small and light — you can carry it in your hand. But some boxes will only accept parcels. So to post a number you have to put it in a little cardboard box first.

One parcel is nothing. A million parcels, made and thrown away one after another, is a lorry full of cardboard nobody needed.

🎓 Professional

Boxing is wrapping a value type in an object on the heap so it can be treated as a reference type; unboxing is the cast back. It allocates, and allocation is the thing you are usually trying to avoid. 

int n = 42;
object boxed = n;              // boxing: a heap allocation
int back = (int)boxed;        // unboxing: a checked cast

// Where it happens without you noticing:
ArrayList list = [1, 2, 3];       // three boxes — use List<int>
string s = "total: " + 42;      // historically boxed; use interpolation
IComparable c = 42;             // a struct assigned to an interface
Line by line
  • object boxed = n; — boxing. int is a value type and object is a reference type, so the CLR allocates a wrapper on the heap and copies the value in. One implicit conversion, one allocation, no syntax.
  • (int)boxed — unboxing: a checked cast that copies the value back out. It throws InvalidCastException unless the boxed type matches exactly — unboxing an int as a long fails.
  • It is a copy, which is its own trap. Mutating a value type through an object reference modifies the box, not the original.
  • ArrayList list = [1, 2, 3]; — three boxes, because it stores object. List<int> stores actual integers in one array and allocates none.
  • IComparable c = 42; — assigning a struct to an interface boxes it. Interfaces are reference types, so this is the boxing people genuinely do not see.
  • Why care. One box is nothing. A box per element in a hot loop is millions of small short-lived objects, which is gen-0 pressure and GC pauses — and it is invisible in the source, which is what makes it worth recognising.

This is the third benefit of generics and the one candidates forget: List<int> stores the ints inline; ArrayList boxes every single one.

Leaking memory in a language that manages memory

"Managed" does not mean "leak-proof". It means you cannot leak by forgetting to free — you leak by accidentally still holding on. Four ways, in the order you will meet them:

  1. Event handlers never unsubscribed. The publisher holds the subscriber. This is number one by a distance — see chapter 04.
  2. A static collection used as a cache. A static field is a GC root, so nothing in it is ever collected. Use IMemoryCache with a size limit and an expiry, or chapter 20.
  3. Timers and background loops holding a captured object alive forever.
  4. Undisposed connections, streams and readers, which exhaust a pool rather than memory — and then look like a hang, not a leak.

How to find one rather than guess: take two memory snapshots ten minutes apart under load in the Visual Studio diagnostic tools (chapter 27) or dotMemory, and compare instance counts. A type whose count only ever rises is your answer, and the tool will show you what is holding it.

Shared state, and why count++ is not one thing

🧒 Simple

You and your sister are both counting sweets in a jar and writing the total on the same piece of paper. You read "10", she reads "10". You add one and write 11. She adds one and writes 11.

Two sweets went in. The paper says one. Nobody made a mistake — you just both looked before either of you wrote.

🎓 Professional

count++ is three operations: read, add, write. Two threads can interleave between any of them, and one increment vanishes. That is a race condition: correctness depending on timing.

four fixes, from heaviest to best
// 1. lock — mutual exclusion. Lock on a PRIVATE, READONLY object you own.
private readonly object _gate = new();
lock (_gate) { _count++; }
//    ✗ never lock(this), lock(typeof(X)) or lock on a string — anyone else
//      can lock the same object and deadlock you from outside your class.

// 2. Interlocked — atomic, lock-free, far cheaper for a single value.
Interlocked.Increment(ref _count);

// 3. A concurrent collection — do not wrap Dictionary in a lock yourself.
private readonly ConcurrentDictionary<int, Order> _cache = new();
_cache.GetOrAdd(id, Load);
//    ⚠ the factory may run more than once under contention — it is
//      thread-safe, not run-once. Make it cheap and side-effect free.

// 4. Do not share mutable state at all. Immutability needs no synchronisation,
//    which is why records and read-only collections are the real answer.
Line by line
  • private readonly object _gate = new(); — the lock object. Private so nothing outside can lock it, readonly so it cannot be reassigned mid-flight, and its own object so it has no other purpose.
  • lock (_gate) { _count++; } — mutual exclusion: one thread inside at a time. It compiles to Monitor.Enter/Exit in a try/finally, so the lock is released even if the body throws.
  • _count++ — needs the lock because it is read, add, write: three steps, and another thread can land between them.
  • lock(this), lock(typeof(X)), locking a string — all wrong, for one reason: the object is reachable from outside. Anyone can lock the same instance, so your class can be deadlocked by code you have never seen. Interned string literals are the worst case, since unrelated assemblies share them.
  • Interlocked.Increment(ref _count) — a single atomic CPU instruction, no lock at all. Far cheaper, and available only for simple operations on one value.
  • ref — passes the variable itself, not a copy, so the method can modify it in place. Required here: the increment must happen at the original location.
  • ConcurrentDictionary — built for concurrent access. Wrapping an ordinary Dictionary in your own lock is slower and easier to get wrong.
  • _cache.GetOrAdd(id, Load) — the factory may run more than once under contention. Only one result is stored, but Load can be called twice, so it must be cheap and free of side effects. "Thread-safe" is not "run-once".
  • Option four beats all three: do not share mutable state. Immutable data needs no synchronisation, which is why records and pure functions scale so much better than careful locking.
⚠ You cannot await inside a lock
lock (_gate)
{
    await LoadAsync();      // does not compile — and that is a kindness
}
Line by line
  • await inside lock — a compile error, and deliberately so.
  • Why the language forbids it. A lock is owned by a thread. await can resume on a different thread, which would then try to release a lock it never took — corrupting the lock, not just failing.
  • It would also be a bad idea even if it worked, because holding a lock across an unbounded wait serialises every caller behind the slowest network call.
  • The error message names the real fix rather than a workaround: you need an asynchronous primitive, which is the next block.

A lock is owned by a thread, and after an await the continuation may run on a different one, so releasing it would be meaningless. Use SemaphoreSlim, which is thread-agnostic, and release it in a finally: 

private readonly SemaphoreSlim _gate = new(1, 1);

await _gate.WaitAsync(ct);
try     { await LoadAsync(ct); }
finally { _gate.Release(); }        // or the lock is held forever
Line by line
  • new SemaphoreSlim(1, 1) — initial count 1, maximum 1. A semaphore permitting a single holder behaves as a mutex you can await.
  • await _gate.WaitAsync(ct) — takes the slot, asynchronously. If it is taken, the method suspends and the thread is released rather than blocked. Passing ct means a cancelled request stops waiting.
  • try immediately after acquiring, never before. Putting WaitAsync inside the try would release a slot that was never taken if the wait itself threw.
  • finally { _gate.Release(); } — the whole reason this shape exists. A semaphore has no scope-based release, so an exception on a path without finally holds the slot forever and every later caller hangs.
  • It is not re-entrant. Unlike lock, the same execution path entering twice deadlocks against itself.
  • The counting form — new SemaphoreSlim(4, 4) — is the standard way to cap concurrency, for example four simultaneous calls to a rate-limited API.
⚠ The one that catches web developers

In ASP.NET Core every request runs concurrently on the thread pool, so anything you register as a singleton is shared by all of them and must be thread-safe. A singleton holding a plain Dictionary, or a singleton holding a DbContext (which is explicitly not thread-safe), gives you corruption under load and nothing at all in testing. That is the captive-dependency trap from chapter 14, seen from the memory side.

Try it yourself

Make the race happen on purpose. It takes four lines and it is genuinely convincing:

int count = 0;
Parallel.For(0, 1_000_000, _ => count++);
Console.WriteLine(count);          // 862417. Or 91355. Never 1000000.
Line by line
  • Parallel.For(0, 1_000_000, ...) — runs the body across many threads at once. The underscores are digit separators, ignored by the compiler.
  • _ as the parameter — a discard: the index is supplied but deliberately unused.
  • count++ — the bug, and it is one character wide. It is three operations: read count, add one, write it back. Two threads can read the same value, both add one, and both write the same result — two increments, one effect.
  • The output is different every run, and always short. There is no exception, no warning and no crash: just a number that is quietly wrong, which is what makes race conditions the worst class of bug to inherit.
  • It gets worse on better hardware. More cores means more contention, so code that passed on a laptop fails on the production server.
int count = 0;
Parallel.For(0, 1_000_000, _ => Interlocked.Increment(ref count));
Console.WriteLine(count);          // 1000000, every time
Line by line
  • Interlocked.Increment(ref count) — the three steps become one atomic instruction the CPU guarantees cannot be interleaved.
  • ref count — passes the storage location itself. Interlocked must operate on the original variable, not a copy, so ref is not optional.
  • 1000000, every time. Not usually, not almost — the guarantee is absolute.
  • Why not just lock: it would also be correct and roughly an order of magnitude slower here. Interlocked is the right tool when the shared state is a single number; a lock is right when several fields must change together.
  • What this pair really teaches is that "it worked when I tested it" is not evidence about concurrent code. The broken version works most of the time, which is precisely the problem.

Run the first one five times and note that the number is different each time and never right. That irreproducibility is the lesson — it is why these bugs survive testing and get closed as "cannot reproduce". Then, for disposal: open a StreamWriter without using, write to it, and read the file back immediately. It is empty, because nothing flushed. Add using and it appears.

Golden rules

  1. The GC frees unreachable managed memory, non-deterministically. Nothing else.
  2. Anything holding an unmanaged resource implements IDisposable. Wrap it in using.
  3. using compiles to try/finally. That is why an exception cannot leak the resource.
  4. Prefer await using and IAsyncDisposable when release does I/O.
  5. Never dispose HttpClient per call. Use IHttpClientFactory.
  6. You rarely need a finalizer. If you write one, you have probably taken on a native handle.
  7. Boxing is a hidden allocation. Generic collections exist partly to avoid it.
  8. Managed languages leak by holding on: events, statics, timers, undisposed pools.
  9. Find leaks with two snapshots and a rising instance count, not by guessing.
  10. count++ is read-modify-write, not one operation.
  11. Lock on a private readonly object. Never this, a type, or a string.
  12. No await inside a lock — use SemaphoreSlim, released in a finally.
  13. Every singleton in a web app is shared by every concurrent request.
  14. The cheapest thread-safety is not sharing mutable state at all.

Interview questions

"Mi spiega IDisposable e using?"

IDisposable releases unmanaged resources deterministically, because the GC handles memory only and does not tell you when. using guarantees Dispose() runs by compiling to try/finally. Then add the modern half — using declarations and await using for IAsyncDisposable — so the answer sounds current rather than learned from a 2012 article.

"What does the garbage collector do?"

Reclaims managed memory that is no longer reachable from a root, using generations because most objects die young. Then volunteer the two limits, which is where the marks are: it is non-deterministic, so it cannot manage a file handle or a connection, and it will not help you if something is still holding a reference — which is how you leak in a managed language.

"What is boxing?"

Wrapping a value type in an object on the heap so it can be used as a reference type — a hidden allocation. Give a place it happens silently, such as putting ints in an ArrayList or assigning a struct to an interface, and connect it to generics: avoiding boxing is one of the three reasons List<int> beats ArrayList.

"This counter is wrong under load. Why, and how do you fix it?"

count++ is read-modify-write, so two threads can interleave and lose an increment. Rank the fixes rather than naming one: Interlocked.Increment for a single value, lock on a private readonly object for a larger critical section, a concurrent collection instead of locking a dictionary yourself — and best of all, not sharing mutable state.

"Can you await inside a lock?"

No, and it does not compile. A monitor is owned by a thread, and the continuation after an await may resume on another, so the release would be meaningless. SemaphoreSlim with WaitAsync is the async equivalent — and it must be released in a finally, or one exception holds the gate shut for the life of the process.
