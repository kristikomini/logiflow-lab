Dynamics 365 Business Central and AL

Every company in the region runs a gestionale — the ERP that holds customers, orders, stock, invoices and the accounts. A large share of them run Microsoft's, and somebody has to extend it. That somebody writes AL, works in VS Code, uses Git, and is much harder to find than another generic backend developer.

Why this chapter exists

Business Central roles are open in Reggio Emilia and Bologna, with around 85 Dynamics NAV / Business Central listings live across Italy, and established partners recruiting juniors directly. It is a parallel .NET-adjacent career with a fraction of the competition for a generic .NET developer post. This chapter is not enough to get the job — it is enough to decide whether you want it, and to not be lost in the first interview.

What it is, and what NAV has to do with it

🧒 Simple

Imagine a huge board game that comes with all the rules already written: how to sell things, how to count what is in the warehouse, how to send a bill. Thousands of companies play it.

Your job is not to write the game. Your job is to add the one extra rule this company needs — without tearing a page out of the rulebook, because next year the makers will send everyone an updated rulebook and yours has to still work.

🎓 Professional

Business Central is Microsoft's ERP for small and mid-sized companies, descended directly from Dynamics NAV (and before that, Navision — you will hear all three names in the same conversation, often from the same person).

The lineage matters because of one change. Old NAV was customised by editing the base application in C/AL: your changes and Microsoft's lived in the same objects, and every upgrade was a code-merge project measured in weeks. Modern Business Central forbids that. You write extensions in AL: separate, versioned packages that hang off the standard application and are re-applied cleanly when Microsoft ships.

Two flavours: Business Central Online (SaaS, Microsoft-hosted, updated on Microsoft's cadence — two major waves a year plus monthly minor updates) and on-premises, which many Italian manufacturers still run, often because it has to sit next to a machine or an MES from chapter 32.

AL, for a C# developer

🧒 Simple

In C# you build things out of classes, and a class can be a copy of another class with a bit changed. AL does not work like that. Instead there is a fixed set of box types — a box for data, a box for a screen, a box for code — and you pick the right box.

And there is a special kind of box that means "the same as that existing one, plus my bit". That is how you add your field to Microsoft's customer screen without ever opening it.

🎓 Professional

AL is strongly typed, object-based and event-driven — but it is not C#, and the differences are the part that trips people up. There are no classes and no inheritance. There is no async. Instead there are object types, each a numbered, named thing in a shared application:

  • table — data. It is the schema; there is no separate migration step.
  • page — a screen (list, card, document). Bound to a table.
  • codeunit — reusable procedures. The nearest thing to a class, without state or inheritance.
  • report — printed or exported output, and also batch processing.
  • query, xmlport, enum, interface, permissionset.
  • tableextension / pageextension / codeunitextension / enumextension — the four that make an extension possible: add a field, add a control, add behaviour, without touching the original.
a complete, realistic extension in about 40 lines
// 1. Add a field to the standard Customer table.
tableextension 50100 "LOGI Customer Ext" extends Customer
{
    fields
    {
        field(50100; "LOGI Delivery Window"; Text[30])
        {
            Caption = 'Finestra di consegna';
            DataClassification = CustomerContent;   // GDPR classification: required
        }
    }
}

// 2. Show it on the standard Customer Card.
pageextension 50100 "LOGI Customer Card Ext" extends "Customer Card"
{
    layout
    {
        addlast(General)
        {
            field("LOGI Delivery Window"; Rec."LOGI Delivery Window")
            {
                ApplicationArea = All;              // omit it and the field is invisible
                ToolTip = 'Orario in cui il cliente accetta consegne.';
            }
        }
    }
}

// 3. React to standard behaviour — do NOT override it.
codeunit 50100 "LOGI Sales Subscribers"
{
    [EventSubscriber(ObjectType::Codeunit, Codeunit::"Sales-Post",
                     'OnBeforePostSalesDoc', '', false, false)]
    local procedure BlockPostingWithoutWindow(var SalesHeader: Record "Sales Header")
    var
        Customer: Record Customer;
    begin
        if not Customer.Get(SalesHeader."Sell-to Customer No.") then
            exit;
        if Customer."LOGI Delivery Window" = '' then
            Error('Il cliente %1 non ha una finestra di consegna.', Customer."No.");
    end;
}

Read the third object again, because it is the entire philosophy. Microsoft's posting routine publishes an event; you subscribe. You never edit Sales-Post. When Microsoft ships a new version, either the event is still there and your code runs, or the publisher changed and your extension fails to compile — early, in your pipeline, not silently in production.

Where it meets your .NET

This is the part that makes the track appealing rather than a total career change: Business Central speaks HTTP, and everything in Part 3 applies.

  • API pages — you write a page of type API and get a REST/OData v4 endpoint over your data, with standard paging and filtering.
  • OData and SOAP web services — expose an existing page or codeunit for integration. SOAP is still very much alive in this world.
  • Outbound — AL can call HTTP itself, so BC can consume your ASP.NET Core API, which is a common shape: BC owns the commercial documents, your service owns something it was never designed for.
  • Not available in the cloud: .NET interop. On-premises AL could declare DotNet variables and call framework types; Business Central Online cannot. Any "we'll just call a .NET library" plan has to become a web service instead. Knowing this is a good sign in an interview.
⚠ Four things that catch newcomers
  • Object ID ranges and the affix. Objects are numbered, ranges are assigned, and every field and object name in an AppSource app needs a registered prefix or suffix (LOGI above). Ignore this and you collide with another partner's extension on the same tenant.
  • Deleting a field is a breaking change. The data belongs to the customer. You mark fields obsolete with ObsoleteState and remove them a version later, after a data upgrade codeunit has moved anything that mattered.
  • Two major releases a year, monthly minors. Your extension must keep compiling against a base application that moves without asking you. Automated build against the next version is not optional at any serious partner.
  • ApplicationArea. Forget it on a control and the field simply does not appear, with no error. Everyone loses an afternoon to this exactly once.
Try it yourself

You need no licence and no customer. Get a free Business Central sandbox from a Microsoft 365 developer tenant, then: 

# VS Code → Extensions → install "AL Language" (Microsoft)
# Ctrl+Shift+P → "AL: Go!" → pick Microsoft cloud sandbox
# it scaffolds app.json + launch.json + a HelloWorld pageextension
# F5 → downloads symbols, compiles, publishes, opens the browser

Then do the thing that teaches the model: take the tableextension and pageextension above, change the ids to your assigned range, and press F5. A new field appears on the standard Customer Card of a full ERP you did not write and cannot break. Now add the event subscriber and try to post a sales order for a customer without a delivery window. Watching your own validation stop Microsoft's posting routine — from outside it — is the moment the whole extension model makes sense.

Golden rules

  1. Never modify the base application. In the cloud you cannot; on-premises you should not.
  2. Subscribe to events; do not override behaviour.
  3. Use your assigned object ID range and your registered affix on every object and field.
  4. Deleting or renaming a field is a breaking change. Obsolete it, then remove it later.
  5. Ship a data upgrade codeunit whenever the shape of stored data changes.
  6. ApplicationArea on every control, or the user never sees it.
  7. DataClassification on every field — it is a GDPR obligation, not paperwork.
  8. Extensions are versioned packages with dependencies. Treat app.json like a .csproj.
  9. Build against the next major version before it ships, in CI.
  10. No async: long-running work belongs in a job queue entry.
  11. No .NET interop in the cloud. Integrations go over HTTP.
  12. Learn the standard application's data model. Knowing where the ledger entries live is worth more than knowing the language.

Interview questions

"Why extensions instead of modifying the base app?"

Upgradeability. In C/AL your code and Microsoft's lived in the same objects, so every upgrade was a manual merge and companies skipped versions for years. Extensions are separate versioned packages re-applied on top, so an upgrade either works or fails loudly at compile time. Mention that in Business Central Online modifying the base app is not even possible.

"How do you change standard behaviour you disagree with?"

You subscribe to a published event — OnBefore… to block or adjust, OnAfter… to react. If no suitable event exists, you request one from Microsoft rather than forking. Then be honest about the constraint that follows: you can only extend where an event was published, and that genuinely limits what is possible.

"A customer wants a field removed. What do you do?"

Not delete it. Mark it ObsoleteState = Pending with a reason and a version, ship that, then remove it in a later release once a data upgrade codeunit has handled anything stored in it. Frame it as the point they are testing: the data is the customer's, and an extension must never destroy it on install.

"You come from C#. Is that a problem?"

Turn it into the answer they want to hear. The tooling is identical — VS Code, Git, JSON project files, CI, semantic versioning — and the REST integration work is the same skill. What is genuinely different is the mindset: no inheritance, the schema is the code, and the base application is a large existing system you extend rather than a blank page. Then say what you have actually built in a sandbox.

"How would you integrate Business Central with an external system?"

Outward: an API page giving a REST/OData endpoint, or a published web service. Inward: AL calling HTTP directly, or a middleware service. Add the constraint that shows you know the platform — no .NET interop in the cloud, so anything that would have been a library reference becomes a service call, and integrations need to be idempotent because retries happen.

Is this track for you?

Honest summary. For: far less competition, strong regional demand, established partners who hire and train juniors, and the tooling transfers directly. Against: you specialise — AL experience does not read as generic .NET experience on a CV, most of the work is consultancy for customers rather than product engineering, and you must learn a very large standard application, not just a language. If Blazor and the Web API track appeal more, that is a perfectly good answer too — but it is worth making the choice deliberately rather than never having heard of the alternative.
