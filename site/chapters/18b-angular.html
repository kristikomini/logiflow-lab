Angular, concretely

Chapter 18 explained what a single-page app is and why a team would want one. It stopped short of the framework itself, on purpose. This chapter is the other half: enough real Angular to open somebody's project, find the file that draws the screen, follow the data back to your own endpoint, and change something without breaking it.

Why this chapter exists

Adverts in this region almost always write the front-end line as a plus, and almost always as "Angular o Blazor". Chapter 19 already answers the Blazor half properly, so the Angular half was the one soft gap in the course. The bar is not "front-end developer". The bar is: you are the backend developer on a full-stack team, and when the screen your API feeds shows undefined, you are the one who finds out why.

There is a second reason, and it is the better one. Angular is the framework whose design decisions a .NET developer already agrees with — dependency injection, a typed HTTP client, a real router, one opinionated way to do each thing. You are not learning a foreign philosophy. You are learning your own, spelled in TypeScript.

The shape of an Angular project

🧒 Simple

Think of a screen as a set of Lego bricks. Each brick knows how to draw a small piece — one row of a table, one search box, one button — and bricks can hold other bricks inside them. The whole page is one big brick made of smaller ones.

Every brick comes in two parts that live together: the picture of what it looks like, and the brain that decides what goes in the picture. Angular's job is to keep the picture matching the brain, automatically, so you never have to write "now go and change that label".

🎓 Professional

An Angular application is a tree of components. A component is a TypeScript class decorated with @Component, carrying a selector (the tag you write to place it), a template (the HTML) and styles. The class holds the state and the methods; the template binds to them. Angular's change detection re-renders the parts of the DOM whose bound values changed.

Around that tree sit three things you already have C# names for. Services are injectable singletons holding logic and data access — the same role as a class you register in Program.cs. The router maps URL paths to components, the same way attribute routing maps them to actions. HttpClient is the typed client that calls your Web API, and it is injected, not newed.

The one word without a C# equivalent is RxJS. Angular's asynchronous values are Observables rather than promises: a stream you subscribe to, which may emit more than once and which you can cancel. It is the part that costs a junior the most time, and the part this chapter refuses to skip.

A generated project has a predictable layout, and knowing it is most of "I can find my way around". src/app/ holds your components and services. src/main.ts is the entry point — the Program.cs of the front end, where the application is bootstrapped and the global providers are registered. angular.json is the build configuration, package.json lists the dependencies, and src/environments/ holds the per-environment settings, which is where the API base URL belongs and where you will find it hardcoded to localhost in somebody's repository at least once.

A component, in full

This is a real one, small enough to read in a single pass. It is the screen that lists shipments for a customer, and it calls the same kind of API the rest of this course builds. 

// src/app/shipments/shipment-list.component.ts
import { Component, inject, signal } from '@angular/core';
import { ShipmentService } from './shipment.service';
import { Shipment } from './shipment.model';

@Component({
  selector: 'app-shipment-list',
  standalone: true,
  template: `
    <h2>Shipments for {{ customerName() }}</h2>

    @if (loading()) {
      <p>Loading…</p>
    } @else if (error()) {
      <p class="error">{{ error() }}</p>
    } @else {
      <table>
        @for (s of shipments(); track s.id) {
          <tr>
            <td>{{ s.reference }}</td>
            <td>{{ s.dispatchedAt | date:'dd/MM/yyyy' }}</td>
            <td><button (click)="select(s)">Open</button></td>
          </tr>
        } @empty {
          <tr><td colspan="3">No shipments yet.</td></tr>
        }
      </table>
    }
  `,
})
export class ShipmentListComponent {
  private readonly service = inject(ShipmentService);

  readonly shipments    = signal<Shipment[]>([]);
  readonly loading      = signal(true);
  readonly error        = signal<string | null>(null);
  readonly customerName = signal('');

  ngOnInit(): void {
    this.service.forCustomer(this.customerId).subscribe({
      next:  list => { this.shipments.set(list); this.loading.set(false); },
      error: ()   => { this.error.set('Could not load shipments.'); this.loading.set(false); },
    });
  }

  select(s: Shipment): void { /* … */ }
}
Line by line
  • @Component — an attribute, in C# terms. selector is the tag other templates write to place this component: <app-shipment-list>.
  • standalone: true — this is a standalone component, the modern default. Older projects instead list every component inside an NgModule, and if you open a codebase written before Angular 15 that is what you will find. Knowing both words is the whole point of mentioning it.
  • inject(ShipmentService) — dependency injection, identical in spirit to constructor injection in ASP.NET Core. The older, equally valid form is a constructor parameter: constructor(private service: ShipmentService) {}.
  • signal(...) — a container holding a value that the template watches. You read it by calling it: shipments(). Change it with .set() and every binding that reads it re-renders, and nothing else does.
  • {{ s.reference }} — interpolation: the template's Razor @Model.Reference.
  • (click)="select(s)" — event binding. Round brackets mean "data flowing out of the template into the class". Square brackets, [value]="x", mean the opposite direction.
  • | date:'dd/MM/yyyy' — a pipe, which is a display-time formatter. Exactly what ToString("dd/MM/yyyy") does, moved into the template.
  • track s.id — how Angular tells one row from another when the list changes. Get this wrong and the framework rebuilds rows instead of moving them: lost focus, lost scroll position, and a table that flickers. The same idea as @key in Blazor.
  • @empty — the branch for "the list came back and it has nothing in it", which is a different state from "still loading" and must look different on screen.
The three-state trap

The component above tracks loading, error and empty as three separate states, and that is not ceremony. The default junior version binds straight to the array, which starts empty — so for the first 300 ms the user reads "No shipments yet" about a customer who has forty, and if the request fails they read it forever.

This is worth rehearsing because it is the same bug as the one in chapter 19: null means "not loaded", an empty list means "none", and a screen that renders them identically is lying to the user. Interviewers who have maintained a front end recognise the answer instantly.

Services, DI and HttpClient

The component above is deliberately thin: it holds screen state and nothing else. The call lives in a service, for the same reason you do not put a SqlConnection in a controller. 

// src/app/shipments/shipment.service.ts
import { Injectable, inject } from '@angular/core';
import { HttpClient, HttpParams } from '@angular/common/http';
import { Observable, retry, shareReplay } from 'rxjs';
import { environment } from '../../environments/environment';
import { Shipment, CreateShipment } from './shipment.model';

@Injectable({ providedIn: 'root' })
export class ShipmentService {
  private readonly http = inject(HttpClient);
  private readonly base = `${environment.apiUrl}/api/shipments`;

  forCustomer(customerId: number): Observable<Shipment[]> {
    const params = new HttpParams().set('customerId', customerId);
    return this.http.get<Shipment[]>(this.base, { params }).pipe(
      retry({ count: 2, delay: 500 }),
      shareReplay({ bufferSize: 1, refCount: true }),
    );
  }

  create(dto: CreateShipment): Observable<Shipment> {
    return this.http.post<Shipment>(this.base, dto);
  }
}
Line by line
  • @Injectable({ providedIn: 'root' }) — registers the service as an application-wide singleton. It is services.AddSingleton<ShipmentService>(), written on the class instead of in a startup file.
  • HttpClient is injected. Angular's is not .NET's, and the one piece of .NET HttpClient lore you carry over — never new it up — happens to be true here too, for entirely different reasons.
  • get<Shipment[]> — the type argument is a promise you are making to the compiler, not a check. Nothing at runtime verifies that the JSON matches Shipment. This is the single most important sentence in the chapter, and the next section is about it.
  • HttpParams builds the query string with proper encoding. Concatenating one by hand is how a customer reference containing & breaks the screen.
  • .pipe(...) — operators applied to the stream, read top to bottom. retry re-issues the request on failure; shareReplay stops two subscribers from causing two HTTP calls.
  • The method returns the Observable and does not subscribe. The caller subscribes. A service that subscribes internally has no way to be cancelled and no way to report failure to the screen.
Observables, for someone who knows Task

A Task<T> has already started, produces one value, and cannot be called off. An Observable<T> is cold: nothing happens until somebody subscribes, it may emit many values, and unsubscribing cancels the underlying request. So IAsyncEnumerable<T> plus a CancellationToken is the closer analogy, and "an Observable is a Task" is the wrong sentence to say out loud in an interview.

Two practical consequences. Calling forCustomer() and ignoring the result sends no request at all — the commonest "my POST never fires" bug. And a subscription in a component that is destroyed keeps running unless you unsubscribe, which is the commonest memory leak in Angular. The modern fix for both is the async pipe or takeUntilDestroyed(), which unsubscribe for you.

Where it breaks: the contract with your API

You will spend more time on this boundary than on anything else in Angular, so it deserves the precision. There are four failures, they are all yours to find, and none of them produces a stack trace.

One: the casing. ASP.NET Core serialises ShipmentReference as shipmentReference by default — camelCase, via JsonNamingPolicy.CamelCase. A TypeScript interface written from the C# class, reading ShipmentReference, compiles perfectly and is undefined at runtime. TypeScript believes the interface you wrote, because believing you is all an interface does.

Two: the rename. You rename a DTO property in C#. Nothing anywhere fails. The front-end build is green, the tests are green, and a column on a screen you have never opened is now blank. This is the failure that chapter 18 tells you to fix by generating the TypeScript client from the OpenAPI document in CI — and now that you have seen the interface it replaces, you know exactly what is being generated and why it stops being optional the moment two people are working on the two halves.

Three: dates. JSON has no date type. A DateTime arrives as the string "2026-03-14T09:30:00", and typeof s.dispatchedAt is "string" even though your interface says Date. The date pipe copes; s.dispatchedAt.getFullYear() throws. Worse, a DateTime carrying no offset is interpreted in the browser's local zone, so the same shipment reads an hour earlier in summer. Serve DateTimeOffset, or UTC with a trailing Z, and the ambiguity disappears.

Four: decimals. A C# decimal becomes a JavaScript number, which is a double. Money that round-trips through the front end and back can come home a hundredth of a cent short. Where exactness matters, send the value as a string, or do not accept it back at all — have the API recompute it.

CORS is not the bug you think it is

The browser blocks the response, the console says "No 'Access-Control-Allow-Origin' header", and the reflex is to add AllowAnyOrigin() in Program.cs. Do not. In development, proxy /api through the Angular dev server (proxy.conf.json, then ng serve --proxy-config) so the browser sees a single origin and the problem does not exist. In production, allow the exact origin your app is served from, and nothing else.

And know the sentence underneath, because it is what the question is really testing: CORS is a rule browsers apply about who may read a response. It is not a server-side protection. Your API is still reachable by anything that is not a browser, which is why authorisation lives in the API and never in the front end.

Routing, forms and interceptors

Three more pieces come up often enough that not recognising them looks worse than not having used them.

Routing. Paths map to components in a routes array, with lazy loading for feature areas and route guards — the [Authorize] of the front end — that decide whether a route may be entered. Remember the deployment consequence from chapter 18: refreshing on /orders/42 asks the web server for a document that does not exist, so the host must be configured to fall back to index.html. When somebody says "it works until you press F5", this is always what it is.

Reactive forms. A FormGroup of FormControls, declared in the class, with validators attached. The alternative, template-driven forms, puts the rules in the HTML with ngModel; reactive is what enterprise projects use, because the form is then a testable object rather than markup. Either way, front-end validation is a courtesy to the user and never a guarantee — the API validates again, because the API is reachable without the form.

Interceptors. An HTTP interceptor is a function every outgoing request passes through: where the bearer token is attached (chapter 15), where a 401 triggers a refresh, where a correlation id is added so a front-end click can be traced to a server log (chapter 25). It is middleware, facing the other way, and saying that out loud is a compact way of showing you understand both halves.

What to claim, and what not to

The honest sentence

"I am a backend developer. I have built an Angular front end against my own API — components, services, HttpClient, routing, reactive forms — and I know where the contract between the two breaks, because I have fixed it. I am not a front-end specialist and I would not design your component architecture."

That is a stronger answer than an overclaim, and far stronger than a shrug. It is also exactly what an apprendistato advert listing Angular as a plus is asking for: not a second specialist, but somebody who will not be blocked by the other half of the repository.

Do not claim RxJS depth you do not have. "I use HttpClient with the async pipe, and I know what a subscription leak is" is defensible; a confident story about switchMap versus mergeMap is a question you will then be asked. And if the shop is a Blazor shop, say so plainly — the two answer the same need, and chapter 19 is the one that pays there.

Interview questions

"Cosa sono i componenti in Angular?"

A class plus a template: the class holds the state and the methods, the template binds to them, and Angular re-renders what changed. Then add the composition point — components nest into a tree, and a screen is the root of one — because that is the sentence that shows you have built one rather than read about one.

"What is dependency injection in Angular, and how does it differ from ASP.NET Core?"

The idea is identical: a class declares what it needs and the framework supplies it. The differences worth naming are that the registration is usually on the class (@Injectable({ providedIn: 'root' })) rather than in a startup file, and that the lifetimes are hierarchical — root-provided is a singleton, but a service provided on a component is created per instance of that component, which is the nearest thing to scoped.

"Observable or Promise?"

An Observable is lazy, can emit many values, and is cancellable; a Promise is eager, emits one, and is not. Angular's HttpClient returns Observables, which is why nothing is sent until something subscribes. Resist the urge to say "an Observable is a Task" — IAsyncEnumerable with a CancellationToken is the honest comparison.

"A field on the screen shows undefined. Walk me through it."

Network tab first: did the request go, what status came back, and is the field in the response body? If it is absent, it is the API's problem. If it is present under a different casing, the TypeScript interface is wrong and nothing warned you, because an interface is a compile-time promise and not a runtime check. Then give the fix that prevents the next one: generate the client from the OpenAPI document in CI.

"Your table flickers and loses focus when the list refreshes. Why?"

The loop has no stable identity, so Angular destroys and rebuilds rows instead of moving them. track s.id on the @for — or trackBy on the older *ngFor. It is the same failure as a missing @key in Blazor, or a list index used as a React key, and saying that shows the knowledge is structural rather than memorised.

"Angular o Blazor, per questo progetto?"

Answer with the team, not the technology. Angular if there is front-end skill in the building or the UI is the product; Blazor if the team is C# and a JavaScript toolchain is a cost nobody will maintain. Then name the shared constraint: either way the API enforces the rules and the front end only decides what to show, so the choice is about who maintains it, not about what is possible.
