Views, functions and stored procedures

Chapter 10 taught you to write a query. This one is about the three ways a team saves a query inside the database — what each is for, which one is a performance trap that looks helpful, and how to call them from C# without fighting EF Core.

From the advert

"Nozioni base di stored procedure, viste o funzioni SQL." A requirements bullet that names all three by name. That phrasing tells you something: on this team, logic lives in the database as well as in C#, and somebody expects you to open SSMS and read it.

Chapter 00 read the same signal from a different advert — T-SQL named before any ORM means people here write SQL by hand.

Three objects, three jobs

🧒 Simple

You have a recipe book. There are three kinds of entry in it.

  • A view is a labelled shortcut: "the good ingredients" means the four things on the top shelf. Saying the label is exactly the same as listing all four — it saves your breath, not your time.
  • A function answers one small question and hands back the answer: "how much does this weigh?" You use it inside other recipes.
  • A stored procedure is a whole recipe: do this, then that, then if it went wrong put it back. It does things, rather than just answering.

The line that decides between them: a function answers, a procedure acts. If it needs a transaction, it is a procedure. If it belongs inside a WHERE clause, it is a function or a view.

Views — a saved SELECT, not a saved result

a view over the schema from chapter 09
CREATE OR ALTER VIEW dbo.vw_OrderSummary
AS
SELECT   o.Id,
         o.OrderNumber,
         o.CreatedAtUtc,
         c.Id           AS CustomerId,
         c.Name         AS CustomerName,
         SUM(l.Quantity * l.UnitPrice) AS Total
FROM     dbo.Orders o
JOIN     dbo.Customers c ON c.Id = o.CustomerId
JOIN     dbo.OrderLines l ON l.OrderId = o.Id
GROUP BY o.Id, o.OrderNumber, o.CreatedAtUtc, c.Id, c.Name;
GO

-- and now it behaves like a table
SELECT * FROM dbo.vw_OrderSummary WHERE Total > 1000;
Line by line
  • CREATE OR ALTER VIEW — a view is a saved SELECT, nothing more. It stores no data and costs no disk; the query runs when you select from it.
  • AS then the query — the whole definition. A view has no parameters, which is the single biggest limitation and the reason inline table-valued functions exist.
  • SUM(l.Quantity * l.UnitPrice) AS Total — the computation lives in one place now, so four reports cannot each get it subtly wrong.
  • GROUP BY o.Id, o.OrderNumber, o.CreatedAtUtc, c.Id, c.Name — every non-aggregated column, as always.
  • GO — not T-SQL. It is a batch separator understood by the client tool, and it is required here because CREATE VIEW must be the first statement in its batch.
  • SELECT * FROM dbo.vw_OrderSummary WHERE Total > 1000 — it behaves like a table. The optimiser inlines the definition and produces one plan, so this is not two queries.
  • The trap is nesting. A view over a view over a view still inlines, and the resulting plan can be enormous while the SQL looks like three lines.
⚠ A view does not make anything faster

This is the misconception the question is designed to catch. A normal view stores no data. At execution the engine expands the definition into your query and optimises the whole thing as one statement — so SELECT * FROM vw_OrderSummary WHERE Total > 1000 costs exactly what the full query costs. You have saved typing, not work.

Worse, views nest. A view over a view over a view produces a query touching twelve tables to return two columns, and nobody notices because each layer looks reasonable. If a query is mysteriously slow, expand every view in it before you look anywhere else.

🎓 Professional

What a view is good for — three real reasons, all about contracts:

  • A stable interface over an unstable schema. Ten reports select from vw_OrderSummary. You split Orders into two tables and fix the view. The reports never notice.
  • A security boundary. Grant SELECT on the view and not on the base table, and a user can see order totals without seeing the customer's payment columns. This is real, enforced by the engine, and a good interview answer.
  • Naming a join everybody gets wrong. If four people have written the same five-table join and two of them wrote it as an inner join by accident, put it in a view once.

Updatable views, and WITH CHECK OPTION

You can sometimes INSERT or UPDATE through a view, but only when the engine can map each row back to exactly one row of one base table — so no aggregates, no GROUP BY, no DISTINCT, no UNION, and the write must touch columns from a single table. vw_OrderSummary above fails on every count.

the surprise WITH CHECK OPTION prevents
CREATE OR ALTER VIEW dbo.vw_ActiveCustomers
AS
SELECT Id, Name, IsActive FROM dbo.Customers WHERE IsActive = 1
WITH CHECK OPTION;   -- without this line, the UPDATE below succeeds
GO

-- Without CHECK OPTION: this works, and the row silently vanishes from the
-- view you just updated it through. With it: the UPDATE is rejected.
UPDATE dbo.vw_ActiveCustomers SET IsActive = 0 WHERE Id = 42;
Line by line
  • A simple view is updatable. If it touches one table with no aggregate, UPDATE and INSERT pass straight through to that table — which surprises people who expect a view to be read-only.
  • WHERE IsActive = 1 — the view's own filter, and the source of the problem.
  • UPDATE dbo.vw_ActiveCustomers SET IsActive = 0 — without CHECK OPTION this succeeds, and the row disappears from the very view you updated it through. It is now invisible to anyone using that view, including whoever tries to undo it.
  • WITH CHECK OPTION — rejects any modification that would push a row outside the view's WHERE. The UPDATE fails loudly instead.
  • The general principle: a filtered view is a promise about what is inside it, and without CHECK OPTION that promise is not enforced for writers.

Indexed views — the one that does store data

Add WITH SCHEMABINDING and a unique clustered index and the view stops being a shortcut and becomes real, persisted, automatically-maintained data. This is SQL Server's materialised view.

a materialised aggregate
CREATE OR ALTER VIEW dbo.vw_CustomerTotals
WITH SCHEMABINDING            -- required, and note the two-part dbo. names below
AS
SELECT   o.CustomerId,
         SUM(o.Total)   AS Total,
         COUNT_BIG(*)   AS OrderCount   -- COUNT_BIG, not COUNT. Required.
FROM     dbo.Orders o
GROUP BY o.CustomerId;
GO

CREATE UNIQUE CLUSTERED INDEX IX_vw_CustomerTotals
    ON dbo.vw_CustomerTotals(CustomerId);   -- this is what materialises it
Line by line
  • WITH SCHEMABINDING — required before a view can be indexed. It locks the underlying tables: nobody can drop or alter a referenced column while the view exists, which is exactly the guarantee a materialised copy needs.
  • Two-part names are mandatory under schemabinding — dbo.Orders and never bare Orders. That is why the qualification here is not just style.
  • COUNT_BIG(*) and not COUNT(*) — required, and the error message is unhelpful when you forget. COUNT_BIG returns BIGINT; the engine insists on it for an indexed view with an aggregate.
  • CREATE UNIQUE CLUSTERED INDEX ... ON dbo.vw_CustomerTotals(CustomerId) — this line is what materialises the view. Until it exists the view is just a saved query; afterwards the results are stored and maintained on disk.
  • The first index on an indexed view must be unique and clustered, which is why the grouping key is the natural choice.
  • What it costs. Every INSERT or UPDATE to Orders now also updates this structure, synchronously, inside the same transaction. You have traded write speed for read speed — excellent for a dashboard over a table written once a minute, disastrous for one written a thousand times a second.
⚠ What it costs
  • Every write to Orders now also maintains this index, inside the same transaction. You have moved cost from reads to writes. On a table written far more often than the aggregate is read, that is a bad trade.
  • SCHEMABINDING locks the base tables. You cannot drop or alter a column the view references until you drop the view. That is a feature for correctness and a genuine friction at deployment time — your migration has to drop and recreate it.
  • The rules are strict: no outer joins, no subqueries, no DISTINCT, deterministic expressions only, and COUNT_BIG(*) whenever you aggregate.
  • Automatic matching is an Enterprise feature. On other editions the optimiser will not silently substitute the indexed view into a query against the base tables — you must reference the view and add WITH (NOEXPAND).

Stored procedures, properly

Chapter 10 showed you one. Here is the version with everything a real one has, and every line is there for a reason.

dbo.usp_PlaceOrder — a procedure that acts
CREATE OR ALTER PROCEDURE dbo.usp_PlaceOrder
    @CustomerId  INT,
    @OrderNumber NVARCHAR(32),
    @OrderId     INT OUTPUT          -- give the caller back the new id
AS
BEGIN
    SET NOCOUNT ON;      -- stop "(1 row affected)" chatter on every statement.
                          -- Not cosmetic: those messages are network round-trips,
                          -- and some clients mistake them for result sets.
    SET XACT_ABORT ON;   -- on any error, kill the transaction. Without it a
                          -- statement can fail and leave the transaction OPEN,
                          -- holding locks, until the connection is reset.

    BEGIN TRY
        BEGIN TRANSACTION;

        IF NOT EXISTS (SELECT 1 FROM dbo.Customers WHERE Id = @CustomerId)
            THROW 50001, 'Customer does not exist.', 1;

        INSERT INTO dbo.Orders (CustomerId, OrderNumber, CreatedAtUtc, Total)
        VALUES (@CustomerId, @OrderNumber, SYSUTCDATETIME(), 0);

        SET @OrderId = SCOPE_IDENTITY();   -- SCOPE_IDENTITY, never @@IDENTITY:
                                          -- @@IDENTITY crosses into triggers.

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        -- XACT_STATE() = -1 means uncommittable: rollback is the only option.
        IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;
        THROW;   -- re-raise with the ORIGINAL error and line number.
                 -- RAISERROR here would lose both.
    END CATCH
END;
Line by line
  • @OrderId INT OUTPUT — an output parameter: a second way to return data, alongside result sets. The caller must also mark it as output, or the value silently never comes back.
  • SET NOCOUNT ON — suppresses the "(1 row affected)" messages. Not cosmetic: each is a network round trip, and some client libraries mistake them for empty result sets.
  • SET XACT_ABORT ON — the important one. Without it, some errors abort only the current statement and leave the transaction open, holding locks until the connection is reset. With it, any error rolls the whole thing back.
  • Both SETs belong at the top of every procedure that writes. They are two lines that prevent two entire categories of production incident.
  • BEGIN / END — the procedure body. Optional to the parser and always written.
🎓 Professional

THROW versus RAISERROR. THROW with no arguments inside a CATCH re-raises the original error unchanged — message, number, line. RAISERROR cannot do that; it always produces a new error, so the stack trace effectively stops at your CATCH. Same idea as throw; versus throw ex; in C# (chapter 07), and interviewers who know T-SQL like the parallel.

Return value versus OUTPUT. RETURN in a procedure can only return an INT, and by convention it means a status code, not data. Anything that is data goes in an OUTPUT parameter or a result set. Using RETURN for a row count is a classic legacy habit that confuses every new reader.

Parameter sniffing — "it was fast yesterday"

🧒 Simple

A courier learns the route to your street the first time they deliver to it, and then uses that same route for every delivery in the city. It was a great route — for your street.

🎓 Professional

SQL Server compiles a procedure's plan on first execution, using the parameter values it was given that time, then caches and reuses it. If the first call was @CustomerId = 7 (three orders) the plan will use an index seek and a nested loop. The same plan applied to the customer with 400,000 orders is catastrophic — and nothing changed in your code, which is why the report says "it was fast yesterday".

The fixes, roughly in the order you should reach for them:

  1. Fix the indexes first. Sniffing hurts most when both plans are bad.
  2. OPTION (RECOMPILE) on the offending statement — a fresh plan every time. Correct plan, small CPU cost per call. Usually the right answer for a procedure called occasionally with wildly varying selectivity.
  3. OPTIMIZE FOR UNKNOWN — ignore the actual value and use average statistics. Deliberately mediocre for everyone, which is sometimes exactly what you want.
  4. Split into two procedures when there are genuinely two shapes of query.

Worth knowing: SQL Server 2022 added Parameter Sensitive Plan optimisation, which keeps several plans for a sensitive predicate. It reduces the problem; it does not remove the interview question.

Functions — one of these three is a trap

Scalar functions: the one that quietly destroys performance

✗ looks tidy, behaves terribly
CREATE OR ALTER FUNCTION dbo.fn_OrderTotal(@OrderId INT)
RETURNS DECIMAL(18,2)
AS
BEGIN
    RETURN (SELECT SUM(Quantity * UnitPrice)
            FROM dbo.OrderLines WHERE OrderId = @OrderId);
END;
GO

-- One million orders. This calls the function ONE MILLION TIMES,
-- once per row, each one its own little query.
SELECT Id, dbo.fn_OrderTotal(Id) FROM dbo.Orders;
Line by line
  • RETURNS DECIMAL(18,2) — a scalar function: one value back. It reads like a C# method, and that intuition is what makes it dangerous.
  • BEGIN ... END around the body — this is the marker of a multi-statement function, and it is what defeats the optimiser.
  • SELECT Id, dbo.fn_OrderTotal(Id) FROM dbo.Orders — the function is called once per row. A million orders means a million separate little queries, each with its own overhead.
  • It is worse than slow, it is invisible. Before SQL Server 2019 the execution plan showed almost no cost for the function, so the plan looked fine while the query took minutes.
  • It also forces the whole query serial. A scalar UDF historically prevented parallelism for the entire statement, not just its own part.
  • SQL Server 2019's scalar UDF inlining fixes many cases automatically — but only some, only on a recent compatibility level, and silently not at all if the function does anything it cannot inline. Do not rely on it.
⚠ Why it is worse than it looks
  • Row-by-row execution. The function is invoked per row rather than folded into the set operation the engine is good at.
  • The optimiser cannot see inside it. It costs the call at roughly nothing, so the execution plan looks cheap while the query takes four minutes. The plan lies to you — which is why this is so hard to find.
  • Historically it forced the whole query to run single-threaded, removing parallelism from an otherwise parallel plan.
  • In a WHERE clause it also kills SARGability (chapter 11): no index seek is possible on WHERE dbo.fn_Something(Col) = 5.

SQL Server 2019 added scalar UDF inlining, which rewrites many of these into the surrounding query automatically. It needs compatibility level 150, it does not apply to every function, and plenty of production databases run lower. Know that it exists; do not rely on it.

Inline table-valued functions: the good one

A single RETURN (SELECT …), no BEGIN, no variables. The optimiser expands it into the calling query exactly like a view — so it is, in effect, a view that takes parameters, and it is the right default whenever you were reaching for a function.

✓ the same idea, done correctly
CREATE OR ALTER FUNCTION dbo.fn_OrdersForCustomer(@CustomerId INT)
RETURNS TABLE          -- no BEGIN/END. That is what makes it inline.
AS
RETURN
(
    SELECT o.Id, o.OrderNumber, o.Total
    FROM   dbo.Orders o
    WHERE  o.CustomerId = @CustomerId
);
GO

-- composable, and the optimiser sees straight through it
SELECT * FROM dbo.fn_OrdersForCustomer(42) WHERE Total > 100;

-- and it joins, per row, with APPLY — still one set-based plan
SELECT c.Name, o.OrderNumber
FROM   dbo.Customers c
CROSS APPLY dbo.fn_OrdersForCustomer(c.Id) o;
Line by line
  • RETURNS TABLE with no BEGIN/END — that absence is the whole thing. It makes this an inline table-valued function: a parameterised view, not a procedure.
  • RETURN ( SELECT ... ) — a single query in parentheses. If you need more than one statement it is no longer inline, and the performance argument evaporates.
  • The optimiser sees straight through it. The definition is expanded into the calling query and optimised as one statement, so there is no per-row cost at all — the exact opposite of the scalar UDF above.
  • SELECT * FROM dbo.fn_OrdersForCustomer(42) WHERE Total > 100 — composable. The outer WHERE is pushed inside during optimisation, so it does not fetch everything and then filter.
  • CROSS APPLY — the join operator for a function that needs a value from the left row: run it for each customer with that customer's id. It is still one set-based plan, not a loop you wrote.
  • CROSS APPLY drops rows where the function returns nothing; OUTER APPLY keeps them with nulls, which makes it the LEFT JOIN of the pair.
  • This is the one to reach for. A view with parameters, no per-row penalty, and it composes — everything the scalar function promised and did not deliver.

Multi-statement table-valued functions: the middle child

If it declares RETURNS @t TABLE (…) and has a BEGIN, it builds the whole result into a table variable first. The optimiser cannot see through it and historically guessed a fixed row count — one row, then a hundred — which produces exactly the wrong join strategy when the real answer is a million. Interleaved execution improved this in SQL Server 2017. If you can rewrite it as an inline TVF, do.

Triggers — the fourth object, deliberately left out

A trigger runs automatically when a table is written to. This repository has none, and being able to say why is more useful than being able to write one.

what one looks like, so you can read it in a legacy schema
CREATE OR ALTER TRIGGER dbo.trg_Orders_Audit
ON dbo.Orders AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    -- `inserted` and `deleted` are the new and old rows. Note they are TABLES:
    -- a trigger fires ONCE PER STATEMENT, not once per row. Code written as
    -- though it were per-row is the classic trigger bug — it silently handles
    -- only the first row of a multi-row UPDATE.
    INSERT INTO dbo.OrderAudit (OrderId, OldStatus, NewStatus, ChangedAtUtc)
    SELECT i.Id, d.Status, i.Status, SYSUTCDATETIME()
    FROM inserted i JOIN deleted d ON d.Id = i.Id
    WHERE i.Status <> d.Status;
END;
Line by line
  • AFTER UPDATE — fires once the statement has completed, inside its transaction. A trigger that throws rolls the original statement back.
  • inserted and deleted — pseudo-tables holding the new and old rows. An UPDATE populates both; an INSERT only inserted.
  • They are TABLES, and a trigger fires once per STATEMENT. One UPDATE touching 500 rows fires the trigger once with 500 rows in inserted.
  • That is the classic trigger bug. Code written as though it were per-row — SELECT @id = Id FROM inserted — compiles, runs, and silently handles only one arbitrary row of the 500. It passes every single-row test.
  • INSERT INTO ... SELECT ... FROM inserted i JOIN deleted d ON d.Id = i.Id — the correct, set-based shape: join the two pseudo-tables on the key and write all changed rows at once.
  • WHERE i.Status <> d.Status — only audit genuine changes. Note this misses rows where the status became NULL or came from NULL, since <> against null is unknown.
  • The real objection to triggers is not performance but surprise: they run invisibly, do not appear in the calling code, and make a simple UPDATE a multi-table write that nobody reading the application can see.
⚠ Why this codebase has none
  • Action at a distance. An UPDATE that also writes two other tables, and nothing at the call site says so. The next reader debugs the C# for an hour before thinking to look in the schema.
  • It is inside your transaction. A slow trigger makes every write slow and widens every lock; a failing trigger rolls back a statement the caller believed was simple.
  • It breaks EF Core's fast path. EF uses an OUTPUT clause to read back generated values, and SQL Server forbids that on a table with triggers — so saving throws until you declare .ToTable(t => t.HasTrigger("trg_…")), which switches EF to a slower, less batched strategy for that table. A trigger added by a DBA can therefore break an application nobody touched.
🎓 When a trigger is still the right answer

When you do not control every writer. If rows arrive from an integration job, a nightly import and someone in SSMS as well as from your API, then auditing in the application only audits the polite callers. The database is the one place all of them pass through — the same argument chapter 20 makes about cache invalidation for a write path you do not own.

Say that, and then say the alternative you would prefer: temporal tables (SYSTEM_VERSIONING) give you full row history maintained by the engine with no procedural code to get wrong, and they are the modern answer to "who changed this and when".

Calling them from C#

This is the half that most SQL tutorials skip and every real ticket needs.

ADO.NET — a procedure with an OUTPUT parameter
await using var conn = new SqlConnection(connectionString);
await using var cmd  = new SqlCommand("dbo.usp_PlaceOrder", conn)
{
    CommandType = CommandType.StoredProcedure   // forget this and it tries to run
                                              // the NAME as a SQL statement
};

cmd.Parameters.Add("@CustomerId",  SqlDbType.Int).Value          = customerId;
cmd.Parameters.Add("@OrderNumber", SqlDbType.NVarChar, 32).Value = orderNumber;

var idParam = cmd.Parameters.Add("@OrderId", SqlDbType.Int);
idParam.Direction = ParameterDirection.Output;

await conn.OpenAsync(ct);
await cmd.ExecuteNonQueryAsync(ct);

var newId = (int)idParam.Value;   // only populated AFTER execution
Line by line
  • await using — asynchronous disposal for both the connection and the command, per chapter 08.
  • CommandType = CommandType.StoredProcedure — forget this and the procedure name is executed as a SQL statement, producing a baffling syntax error. It is the most common mistake in this block.
  • { ... } after the constructor — an object initialiser, setting the property as part of construction.
  • SqlDbType.NVarChar, 32 — type and length. Omitting the length lets ADO.NET infer one from the value, so different callers produce different plans for the same procedure — a cache-bloating problem that is genuinely hard to diagnose.
  • idParam.Direction = ParameterDirection.Output — marks the parameter as returning a value. Both sides must agree, and the C# side is the one usually forgotten.
  • An output parameter is only populated after the command completes — and for a procedure that also returns rows, only after the reader is closed. Reading it too early gives null.
  • ExecuteNonQueryAsync — for a command that returns no result set. Its return value is the rows-affected count, not your data.
EF Core — the three shapes
// 1. Procedure returning rows that match an entity.
//    Interpolation here is parameterised, deliberately (chapter 10).
var orders = await db.Orders
    .FromSqlInterpolated($"EXEC dbo.usp_GetCustomerOrders {customerId}")
    .ToListAsync(ct);

// 2. Procedure returning a shape that is not an entity.
//    Declare a keyless type — see the model configuration below.
var rows = await db.OrderSummaries
    .FromSqlInterpolated($"EXEC dbo.usp_Summary {from}")
    .ToListAsync(ct);

// 3. Procedure that just does something.
await db.Database.ExecuteSqlInterpolatedAsync(
    $"EXEC dbo.usp_ArchiveOrders {cutoffUtc}", ct);
Line by line
  • FromSqlInterpolated($"EXEC dbo.usp_GetCustomerOrders {customerId}") — despite the $, the hole becomes a parameter. Deliberate, and the reason this method exists rather than plain string building.
  • The result columns must match the entity — every mapped property, by name. A missing column is a run-time error, not a compile-time one.
  • db.OrderSummaries — a DbSet for a shape that is not an entity. It needs a keyless type, configured in the model as shown below.
  • db.Database.ExecuteSqlInterpolatedAsync(...) — for a procedure that returns nothing. It sits on Database, not on a DbSet, because there is no entity involved.
  • It returns the rows-affected count, and it bypasses the change tracker entirely — so entities already loaded in memory are now stale.
⚠ You cannot compose LINQ on top of a procedure
// ✗ throws. EF cannot wrap EXEC in a subquery, so there is nothing to add
//   a WHERE or an ORDER BY to.
db.Orders.FromSqlInterpolated($"EXEC dbo.usp_GetOrders {id}")
         .Where(o => o.Total > 100)
         .OrderBy(o => o.CreatedAtUtc);

// ✓ either filter inside the procedure, or materialise first and accept
//   that the filtering now happens in your process (chapter 06's rule).
        .AsEnumerable().Where(o => o.Total > 100);
Line by line
  • .Where(...) after FromSqlInterpolated on an EXEC — throws. EF composes by wrapping your SQL in a subquery, and SQL Server cannot put EXEC inside one.
  • It works for a plain SELECT, which is what makes the failure confusing: the same method call succeeds or fails depending on the SQL inside it.
  • .AsEnumerable() — the escape hatch, and it is chapter 06's rule arriving in a new costume. From that call onwards LINQ runs in your process, on rows already fetched.
  • So the filtering is real but the saving is not. Every row the procedure returns crosses the network first. Acceptable for a procedure returning twenty rows, not for one returning a million.
  • The better fix is a parameter on the procedure. Filtering belongs where the data is, and adding @MinTotal is usually less work than arguing with the ORM.

A view or an inline TVF composes perfectly — which is a concrete reason to prefer them when the thing is a query rather than an action.

mapping a view and a function in the model
protected override void OnModelCreating(ModelBuilder b)
{
    // A view: read-only, no key, no migration generated for it —
    // you create the view yourself with migrationBuilder.Sql(...).
    b.Entity<OrderSummary>()
        .HasNoKey()
        .ToView("vw_OrderSummary");

    // An inline TVF, callable INSIDE a LINQ query. This is the one that
    // makes database logic composable from C#.
    b.HasDbFunction(() => OrdersForCustomer(default))
     .HasName("fn_OrdersForCustomer");
}

public IQueryable<Order> OrdersForCustomer(int customerId)
    => FromExpression(() => OrdersForCustomer(customerId));

// …and now this translates to SQL, filter and all:
var big = await db.OrdersForCustomer(42)
                 .Where(o => o.Total > 100)
                 .ToListAsync(ct);
Line by line
  • b.Entity<OrderSummary>().HasNoKey() — a keyless entity type. Without a key EF cannot track changes, so it is read-only by construction — which is correct for a view.
  • .ToView("vw_OrderSummary") — maps the type to the view and, importantly, tells EF not to generate a migration creating a table for it.
  • You create the view yourself with migrationBuilder.Sql(...) in a migration. EF manages tables; views, procedures and functions are yours to script.
  • b.HasDbFunction(() => OrdersForCustomer(default)) — registers a CLR method as a stand-in for a database function. The lambda is never executed; it exists only so the compiler can hand EF the MethodInfo, which is why default as the argument is fine.
  • FromExpression(() => OrdersForCustomer(customerId)) — the body of the C# method. It never runs as C# either: it produces an IQueryable that EF translates into a call to the TVF.
  • This is the payoff of the whole chapter. An inline TVF registered this way is callable inside a LINQ query and composes with Where and OrderBy, so database logic stays in the database without giving up the C# query surface.
When Dapper is the better tool

If a procedure returns three result sets, or a shape that changes by parameter, EF Core will fight you. Dapper reads a procedure into a POCO in one line and handles multiple result sets natively. Chapter 12 makes the general argument; this is the specific case where a team that otherwise uses EF Core keeps Dapper around, and saying so shows judgement rather than tool loyalty.

So where should the logic live?

You will be asked this, and there is no correct answer — there is a considered one. Argue both sides:

Logic in the databaseLogic in C#
One place, whoever calls it — the API, the nightly job, the report tool, the person in SSMS. One language, one repository, one review process.
Set-based work stays next to the data. Updating a million rows should not travel over a network. Testable without a database. Debuggable with a debugger.
Can be fixed in production without a deployment. Versioned with the code that calls it; a migration is reviewable and repeatable.
…which is also the problem: changed without review, invisible to source control. …which is also the problem: a row-by-row loop in C# where one UPDATE would do.

The defensible position, and the one this repository takes: business rules in the domain, set-based data work in the database. An invariant like "an order cannot ship twice" belongs in C# where it is tested (chapter 23). Archiving two million rows belongs in a procedure, because pulling them into memory to send them back is absurd. And whatever a team already does, consistency beats your preference — say that too.

Try it yourself

Against the schema from chapter 09:

  1. Write vw_CustomerOrderCounts including customers with zero orders. Then try to UPDATE a customer name through it and explain the result.
  2. Write fn_CustomerTotal as a scalar function and select it over every customer. Note the elapsed time and look at the plan — note how cheap it claims to be.
  3. Rewrite it as an inline TVF used with CROSS APPLY. Compare both plans. This contrast is the whole lesson.
  4. Write usp_ArchiveOrders with TRY/CATCH, XACT_ABORT and an OUTPUT row count. Force an error halfway and prove nothing was committed.
  5. Call it from a small console app with CommandType.StoredProcedure and read the OUTPUT parameter back.
  6. Add WITH SCHEMABINDING to a view, then try to drop a column it references. Read the error — that is the deployment friction, felt once.

Golden rules

  1. A view is a saved query, not saved data. It makes nothing faster; it makes things nameable.
  2. A view is a contract and a permission boundary. That is the real reason to create one.
  3. Nested views are how a two-column query ends up touching twelve tables. Expand them before blaming the optimiser.
  4. An indexed view is real data — needs SCHEMABINDING, a unique clustered index and COUNT_BIG(*), and moves cost from reads onto every write.
  5. Scalar UDFs run per row and lie in the execution plan. The plan looks cheap while the query is not.
  6. Inline TVFs are views with parameters. Make them the default; RETURNS TABLE with no BEGIN.
  7. A function answers, a procedure acts. If it needs a transaction, it is a procedure.
  8. SET NOCOUNT ON and SET XACT_ABORT ON at the top of every procedure. One saves chatter, the other prevents an abandoned open transaction holding locks.
  9. Bare THROW in a CATCH preserves the original error; RAISERROR loses it. Same rule as throw; versus throw ex;.
  10. SCOPE_IDENTITY(), never @@IDENTITY — the latter reaches into triggers.
  11. Parameter sniffing means the plan was compiled for somebody else's parameter. Indexes first, then OPTION (RECOMPILE).
  12. You cannot compose LINQ over EXEC. Views and inline TVFs compose; procedures do not.
  13. A trigger fires once per statement, not once per row — inserted and deleted are tables. Prefer temporal tables for history, and reach for a trigger only when you do not control every writer.
  14. Business rules in the domain, set-based work in the database — and consistency with the existing team beats both.

Interview questions

"What is a view, and does it improve performance?"

A named SELECT that stores no data; at execution its definition is expanded into the calling query, so on its own it changes nothing about cost. It is for a stable contract over a changing schema, for granting access to some columns and not others, and for naming a join people keep getting wrong. The exception is an indexed view, which is materialised and genuinely is stored — at the price of maintaining it on every write to the base tables.

"Difference between a stored procedure and a function?"

A function answers a question and can be used inside a SELECT or a WHERE; it cannot modify data. A procedure performs an action, can manage transactions and control flow, can return multiple result sets, and cannot be called from inside a query. The practical rule: if it needs a transaction it is a procedure; if it belongs in a WHERE clause it is a function.

"Why are scalar functions considered a performance problem?"

They execute once per row instead of as part of the set operation, the optimiser cannot see inside them so it costs them at nearly nothing — meaning the execution plan looks cheap while the query is slow — and historically they removed parallelism from the whole plan. In a WHERE clause they also prevent an index seek. Prefer an inline table-valued function, which the optimiser expands like a view. Mention 2019 scalar UDF inlining as a mitigation that requires compatibility level 150 and does not cover every function.

"A stored procedure that was fast for months is suddenly slow. Nothing changed."

Parameter sniffing. The cached plan was compiled for whatever parameters were passed the first time after the last recompile, and a plan that suits a customer with three orders is disastrous for one with 400,000. Confirm by running the statement with OPTION (RECOMPILE) and comparing. Fix the indexes first, then RECOMPILE on the offending statement or OPTIMIZE FOR UNKNOWN. Bonus: SQL Server 2022's Parameter Sensitive Plan optimisation.

"How do you call a stored procedure from EF Core?"

FromSqlInterpolated($"EXEC …") when it returns rows matching an entity or a keyless type configured with HasNoKey(), and Database.ExecuteSqlInterpolatedAsync when it just does something. Then the caveat that shows you have actually done it: you cannot compose LINQ on top of a procedure call — no Where or OrderBy afterwards — because EF cannot wrap EXEC in a subquery. Views and inline TVFs compose; procedures do not. And for multiple result sets, Dapper is the better tool.

"What does SET NOCOUNT ON do, and why is it in every procedure?"

It suppresses the "n rows affected" message each statement sends back. It is not cosmetic: those are extra network round-trips inside a loop, and some client libraries mistake them for result sets. Pair it with SET XACT_ABORT ON, which guarantees a failing statement aborts the transaction instead of leaving it open and holding locks.

"Should business logic live in the database?"

Argue both sides and then commit. In the database it is shared by every caller and keeps set-based work next to the data; in C# it is testable, debuggable, versioned with the code and reviewed. My default is business rules in the domain and bulk set-based work in the database — but the strongest part of the answer is that consistency with what the team already does beats my preference, because a codebase with logic in both places and a rule in neither is the worst outcome.
