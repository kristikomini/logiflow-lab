ASP.NET Core Web API

The framework that turns chapter 13’s principles into running code. Three things carry most of it: the middleware pipeline, dependency injection, and the discipline of never letting a database entity reach the wire.

From the advert

"Comprensione dei principi REST e sviluppo di Web API." This is the day job. If one chapter is going to come up in a live-coding round, it is this one.

Program.cs — the whole application in one file

Program.cs
var builder = WebApplication.CreateBuilder(args);

// ─── 1. REGISTER services: what the application can use ────────────────
builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

builder.Services.AddDbContext<LogiFlowDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddHttpClient<IPricingClient, PricingClient>();
builder.Services.AddHealthChecks().AddDbContextCheck<LogiFlowDbContext>();

var app = builder.Build();

// ─── 2. BUILD the pipeline: ORDER IS THE BEHAVIOUR ─────────────────────
app.UseExceptionHandler();      // outermost: catches everything below
if (!app.Environment.IsDevelopment()) app.UseHsts();
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();        // who are you?   ← must come before…
app.UseAuthorization();         // may you?       ← …this. Always.
app.MapControllers();
app.MapHealthChecks("/health");

app.Run();

The middleware pipeline

🧒 Simple

Getting into a football stadium, you pass through a line of people: someone checks your ticket, someone searches your bag, someone points you to your seat. Each one can either wave you through to the next person, or stop you and send you straight back out.

On the way out you pass all of them again, in reverse.

The order is not a detail — it is the whole design. Searching bags after people are already in their seats would be pointless.

🎓 Professional

Middleware components form a chain of delegates. Each receives the HttpContext and a reference to the next component, and decides whether to call it. Because control returns after the await, every component sees the request on the way in and the response on the way out — which is what allows one component to both log a request and record its duration.

A component that does not call next short-circuits the pipeline: that is exactly how authorisation returns 403 without the controller ever running.

a custom middleware — the shape
public class RequestTimingMiddleware(RequestDelegate next, ILogger<RequestTimingMiddleware> log)
{
    public async Task InvokeAsync(HttpContext ctx)
    {
        var sw = Stopwatch.StartNew();     // before

        await next(ctx);                    // ← everything further in

        log.LogInformation("{Method} {Path} → {Status} in {Ms}ms",  // after
            ctx.Request.Method, ctx.Request.Path, ctx.Response.StatusCode,
            sw.ElapsedMilliseconds);
    }
}

Dependency injection

🧒 Simple

Instead of a chef going out to buy their own ingredients halfway through cooking, the ingredients are handed to them at the door. The chef says what they need; someone else decides where it comes from.

Now, on a day when you want to test the recipe, you can hand them plastic vegetables and the chef neither knows nor cares.

🎓 Professional

ASP.NET Core has a built-in IoC container. A class declares its dependencies as constructor parameters typed as interfaces; the container supplies concrete implementations from the registrations in Program.cs. That is the Dependency Inversion principle from chapter 03, made operational: it is what allows a test to substitute a fake repository without touching production code.

LifetimeOne instance perUse for
AddSingletonThe whole applicationStateless, thread-safe services; caches; configuration.
AddScopedHTTP requestThe default choice. DbContext, repositories, services.

⚠ The captive dependency

Injecting a scoped service into a singleton captures the first request’s instance for the lifetime of the application. With a DbContext that means one context shared across every request and every thread — leaking memory and throwing concurrency errors under load.

ASP.NET Core detects this at startup in the Development environment and refuses to start. If a singleton genuinely needs a scoped service, inject IServiceScopeFactory and create a scope per unit of work — the standard pattern inside a BackgroundService.

Controllers, routing and binding

OrdersController.cs
[ApiController]                       // automatic 400 on invalid model, binding inference
[Route("api/v1/[controller]")]         // → /api/v1/orders
public class OrdersController(IOrderService service) : ControllerBase
{
    [HttpGet("{id:int}")]                                 // GET /api/v1/orders/42
    [ProducesResponseType<OrderDto>(StatusCodes.Status200OK)]
    [ProducesResponseType(StatusCodes.Status404NotFound)]
    public async Task<ActionResult<OrderDto>> Get(int id, CancellationToken ct)
    {
        var dto = await service.GetAsync(id, ct);
        return dto is null ? NotFound() : Ok(dto);
    }

    [HttpGet]                                            // GET /api/v1/orders?page=2
    public async Task<ActionResult<PagedResult<OrderDto>>> List(
        [FromQuery] OrderQuery query, CancellationToken ct)
        => Ok(await service.SearchAsync(query, ct));

    [HttpPost]                                           // POST /api/v1/orders
    public async Task<ActionResult<OrderDto>> Create(
        [FromBody] CreateOrderRequest request, CancellationToken ct)
    {
        var created = await service.CreateAsync(request, ct);

        // 201 + Location: /api/v1/orders/1001 — exactly what chapter 13 asked for
        return CreatedAtAction(nameof(Get), new { id = created.Id }, created);
    }

    [HttpPost("{id:int}/submit")]                        // a state transition, not a field edit
    public async Task<IActionResult> Submit(int id, CancellationToken ct)
    {
        var result = await service.SubmitAsync(id, ct);
        return result switch
        {
            SubmitResult.Ok           => NoContent(),                     // 204
            SubmitResult.NotFound     => NotFound(),                      // 404
            SubmitResult.AlreadySent  => Conflict("Already submitted."),  // 409
            _                          => throw new UnreachableException()
        };
    }
}

Where binding gets its values

AttributeSource
[FromRoute]The URL path — {id}. Inferred for simple types matching a route token.
[FromQuery]The query string. Inferred for other simple types.
[FromBody]The JSON body. Inferred for complex types with [ApiController]. Only one per action.
[FromHeader]A request header.
[FromServices]The DI container.

Route constraints like {id:int} are worth using: a request to /orders/abc then fails to match the route and returns 404 before your code runs, rather than producing a confusing binding error.

DTOs — never return an entity

⚠ Why this rule is absolute

Returning an EF Core entity directly from a controller causes four separate problems:

  1. Over-exposure. Add an internal CostPrice column and it is published to every client the same afternoon. This is how data leaks happen.
  2. Coupling. Your public API contract silently becomes your database schema. Renaming a column becomes a breaking API change.
  3. Serialisation cycles. Order.Customer.Orders.Customer…
  4. Over-fetching. Twenty columns serialised where the client uses three.
request and response models
// Inbound: exactly what a caller may send. Note there is no Id and no Status —
// the client does not get to choose those.
public record CreateOrderRequest(
    [property: Required]              int CustomerId,
    [property: MinLength(1)]           IReadOnlyList<CreateOrderLine> Lines,
    [property: StringLength(500)]     string? Notes);

// Outbound: exactly what you are willing to publish.
public record OrderDto(int Id, string OrderNumber, decimal Total, string Status);

// Map in the query — one SQL statement, only the needed columns (ch. 09)
var dto = await db.Orders
    .Where(o => o.Id == id)
    .Select(o => new OrderDto(o.Id, o.OrderNumber, o.Total, o.Status.ToString()))
    .FirstOrDefaultAsync(ct);

Validation and error handling

With [ApiController], a failed DataAnnotations check automatically returns 400 with a Problem Details body — you write no code for it. For rules that need more than an attribute, FluentValidation is the common choice.

one place for every unhandled exception
public sealed class GlobalExceptionHandler(ILogger<GlobalExceptionHandler> log)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext ctx, Exception ex, CancellationToken ct)
    {
        log.LogError(ex, "Unhandled on {Path}", ctx.Request.Path);

        var (status, title) = ex switch
        {
            NotFoundException              => (404, "Not found"),
            DbUpdateConcurrencyException   => (409, "The record was modified by someone else"),
            ValidationException            => (400, "Validation failed"),
            _                              => (500, "An unexpected error occurred")
            // ↑ never echo ex.Message to the client on a 500
        };

        await Results.Problem(
            title: title, statusCode: status,
            extensions: new Dictionary<string, object?>
            {
                ["traceId"] = Activity.Current?.Id ?? ctx.TraceIdentifier
            })
            .ExecuteAsync(ctx);

        return true;
    }
}

// Program.cs
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
builder.Services.AddProblemDetails();
app.UseExceptionHandler();

Returning a traceId is a small thing that makes support enormously easier: a user reports the id, and you find the exact request in your logs.

Configuration and secrets

strongly-typed options
public class PricingOptions
{
    public const string Section = "Pricing";

    [Required, Url]  public string BaseUrl { get; init; } = "";
    [Range(1, 60)]    public int    TimeoutSeconds { get; init; } = 10;
}

builder.Services
    .AddOptions<PricingOptions>()
    .Bind(builder.Configuration.GetSection(PricingOptions.Section))
    .ValidateDataAnnotations()
    .ValidateOnStart();          // fail at boot, not at 3am on the first call

Configuration sources are layered, each overriding the last: appsettings.json → appsettings.{Environment}.json → user secrets (development) → environment variables → command line. Connection strings and API keys never go into appsettings.json — use dotnet user-secrets locally and Key Vault or pipeline variables in production.

OpenAPI, and minimal APIs

AddSwaggerGen() plus the [ProducesResponseType] attributes above give you a browsable, testable contract at /swagger. It is also the deliverable a front-end colleague will ask you for — which is why the attributes matter.

the same endpoint as a minimal API
app.MapGet("/api/v1/orders/{id:int}",
    async (int id, IOrderService service, CancellationToken ct) =>
    {
        var dto = await service.GetAsync(id, ct);
        return dto is null ? Results.NotFound() : Results.Ok(dto);
    })
    .WithName("GetOrder")
    .Produces<OrderDto>()
    .Produces(StatusCodes.Status404NotFound);

Minimal APIs are leaner and marginally faster; controllers scale better organisationally with filters, conventions and shared base classes. Most enterprise codebases — and almost certainly the one behind this advert — use controllers. Know both, and have an opinion.

Golden rules

  1. Middleware order is behaviour. Exception handler outermost; UseAuthentication before UseAuthorization; both before MapControllers.
  2. Scoped is the default lifetime. DbContext is always scoped.
  3. Never inject a scoped service into a singleton. Use IServiceScopeFactory.
  4. Never return an entity. DTO in, DTO out, always.
  5. Project into the DTO inside the query, so the SQL fetches only what you send.
  6. Thin controllers: bind, delegate, translate the result into a status code. Business rules live below.
  7. Accept a CancellationToken in every action and pass it down.
  8. Handle exceptions in one place with IExceptionHandler, return Problem Details, and include a trace id. Never leak ex.Message on a 500.
  9. Bind configuration to typed options and ValidateOnStart().
  10. Secrets never live in appsettings.json.
  11. Annotate responses with [ProducesResponseType] — the OpenAPI document is a deliverable for your colleagues.
  12. Return the right status code. 201 with Location on create, 204 on a contentless success, 409 on a state conflict.

Interview questions

"What is middleware, and why does order matter?"

A chain of components each deciding whether to call the next; because control returns after the await, each sees both request and response. Order is nesting order, so authorisation registered after endpoint mapping never runs. Offer that example — it proves you have hit it.

"Explain the DI lifetimes."

Singleton per application, scoped per request, transient per injection. Then the captive dependency problem: a scoped service inside a singleton is captured for the process lifetime, which with a DbContext means shared state across threads.

"Why not return your EF entities from a controller?"

Over-exposure of columns you never meant to publish, coupling of the API contract to the database schema, serialisation cycles through navigation properties, and over-fetching. A DTO is a contract you control deliberately.

"Where do you handle exceptions?"

Centrally, in an IExceptionHandler registered with UseExceptionHandler, mapping known exception types to status codes and returning Problem Details with a trace id. Try/catch in controllers only when there is a genuine local recovery.

"Minimal APIs or controllers?"

Minimal APIs for small services and lower overhead; controllers for larger codebases, where filters, conventions and grouping pay off. Then say which the team’s existing code uses, because consistency beats preference.
