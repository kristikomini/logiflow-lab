Databases and SQL Server

Your C# objects live for the length of one request. The database is the only thing in the system that is genuinely permanent — which is why a mistake in a table design outlives every mistake you will make in C#, and why this advert names T-SQL before it names any ORM.

From the advert

"Buona conoscenza di T-SQL e dei principali RDBMS (in particolare SQL Server)." Listed before Entity Framework, which appears only in the optional section. That ordering is deliberate and it tells you people here write SQL by hand.

What a relational database is

🧒 Simple

Imagine a huge filing cabinet in a school office. One drawer holds a card for every student. Another holds a card for every class. A third holds small slips saying "student 42 is in class 7".

Why keep them in separate drawers? Because if a student changes their surname, you want to change one card — not hunt through six hundred slips hoping you found them all.

Every card has a number nobody else has. That number is how the slips point at the right card. That is the whole idea: store each fact once, and point at it.

🎓 Professional

A relational database stores data as relations (tables) of tuples (rows) with typed attributes (columns). Its real value is not storage — it is the guarantees around storage:

  • Declarative constraints — primary keys, foreign keys, uniqueness, checks — enforced by the engine, so invalid data cannot exist regardless of which application wrote it.
  • ACID transactions — atomicity, consistency, isolation, durability (chapter 11).
  • A declarative query language. You state what you want; the query optimiser decides how, and can change its mind as the data grows.

That third point is why SQL survives: the same query gets faster when someone adds an index, without a line of it changing.

Tables, keys and constraints

T-SQL — a table with every constraint labelled
CREATE TABLE dbo.Orders
(
    -- surrogate primary key: meaningless, stable, generated by the engine
    Id            INT            NOT NULL IDENTITY(1,1),

    -- a natural key: meaningful to humans, and unique
    OrderNumber   NVARCHAR(20)   NOT NULL,

    -- points at a row in another table
    CustomerId    INT            NOT NULL,

    Total         DECIMAL(18,2)  NOT NULL,
    Status        TINYINT        NOT NULL CONSTRAINT DF_Orders_Status DEFAULT 0,
    CreatedAtUtc  DATETIME2(3)   NOT NULL CONSTRAINT DF_Orders_Created DEFAULT SYSUTCDATETIME(),
    Notes         NVARCHAR(MAX)  NULL,

    CONSTRAINT PK_Orders          PRIMARY KEY (Id),
    CONSTRAINT UQ_Orders_Number   UNIQUE (OrderNumber),
    CONSTRAINT FK_Orders_Customer FOREIGN KEY (CustomerId)
        REFERENCES dbo.Customers (Id),
    CONSTRAINT CK_Orders_Total    CHECK (Total >= 0)
);
ConstraintGuarantees
PRIMARY KEYEvery row is uniquely identifiable, and never NULL. One per table.
FOREIGN KEYThis value exists in the referenced table. Prevents orphan rows.
UNIQUENo duplicates — but unlike a PK, allows one NULL in SQL Server.
CHECKAn arbitrary rule the engine enforces on every write.
DEFAULTA value used when the insert omits the column.
NOT NULLThis fact is always known. Cheap, and enormously underused.
🎓 Surrogate or natural key?

A surrogate key (IDENTITY, or a GUID) has no business meaning, so it never needs to change. A natural key (OrderNumber, a VAT number) is meaningful, but business meanings change — and updating a key cascades everywhere it is referenced.

The standard answer: surrogate primary key, plus a unique constraint on the natural key. You get stability and you still get the guarantee. On GUID specifically: as a clustered primary key it causes page splits and index fragmentation because the values are random — use NEWSEQUENTIALID(), or keep an INT clustered key and a non-clustered unique GUID.

⚠ IDENTITY leaves gaps, and one Italian requirement cares

An IDENTITY column guarantees uniqueness, not continuity. A rolled-back transaction consumes its number and never gives it back, and a service restart can jump the counter by a thousand because values are cached in blocks. Gaps are normal behaviour, not corruption — so 1, 2, 3, 7, 1004 is a working table, not a broken one.

That matters here more than it does elsewhere, because Italian invoice numbering (numerazione progressiva delle fatture) is legally required to be sequential and without holes. Never use IDENTITY for a document number the business or the tax authority will read. Keep IDENTITY as the meaningless internal key, and generate the invoice number separately — inside the transaction, from a counter row you update and read, per year and per series.

🎓 SEQUENCE, the third option

A sequence is a counter that belongs to the schema rather than to a column, which buys two things IDENTITY cannot: 

CREATE SEQUENCE dbo.OrderNumbers AS INT START WITH 1000 INCREMENT BY 1;

-- 1. You get the number BEFORE the insert, so you can build the row,
--    log it, or hand it to another system first.
DECLARE @id INT = NEXT VALUE FOR dbo.OrderNumbers;

-- 2. Several tables can share one series — useful when Orders and Quotes
--    must draw from the same run of document numbers.

A sequence gaps too, for the same reasons. It is a better tool, not a gapless one.

Data types — where money and dates go wrong

UseTypeWhy
Money, quantitiesDECIMAL(18,2) Exact base-10. Never FLOAT — it cannot represent 0.1, and invoices stop adding up.
TextNVARCHAR(n) Unicode. VARCHAR loses characters outside its code page — and Italian data has accents.
A moment in timeDATETIME2(3) Wider range and better precision than DATETIME, which is legacy and rounds to ~3.33 ms.

A date aloneDATE A birthday has no time. Storing one invites time-zone bugs.

A small enumTINYINT0–255, one byte. Map to a C# enum.
⚠ Three traps, all of which have shipped
  • FLOAT for money. Binary floating point cannot represent 0.1 exactly. Ten line items of €0.10 do not total €1.00. Use DECIMAL → C# decimal.
  • Local time in the database. Store UTC and convert at the edge. Italy switches to ora legale twice a year, and on one night in October the hour 02:30 happens twice.
  • VARCHAR for names. The moment a customer is called Nicolò or Öztürk, you are corrupting data.

Relationships

NULL, and why it breaks your intuition

🧒 Simple

NULL does not mean zero, and it does not mean empty. It means "nobody has told me".

Two people are standing in front of you with their ages written on cards, face down. Are they the same age? You cannot say yes. You cannot say no either. The honest answer is "I do not know" — and that is exactly what SQL says.

🎓 Professional

SQL uses three-valued logic: TRUE, FALSE, UNKNOWN. Any comparison involving NULL yields UNKNOWN, and WHERE keeps only rows evaluating to TRUE. Hence NULL = NULL is not true, and WHERE Notes <> 'x' silently drops every row where Notes is NULL.

the four results that surprise people
SELECT * FROM dbo.Orders WHERE Notes = NULL;      -- 0 rows, always
SELECT * FROM dbo.Orders WHERE Notes IS NULL;     -- ✓ the correct form

-- Aggregates skip NULLs — COUNT(*) and COUNT(col) are different questions:
SELECT COUNT(*), COUNT(Notes) FROM dbo.Orders;     -- 1000, 240

-- NULL poisons arithmetic and concatenation:
SELECT Total + Discount FROM dbo.Orders;             -- NULL if Discount is NULL
SELECT Total + ISNULL(Discount, 0) FROM dbo.Orders;  -- ✓
⚠ NOT IN with a nullable column

WHERE Id NOT IN (SELECT CustomerId FROM Blocked) returns zero rows if any CustomerId in that subquery is NULL — because Id <> NULL is UNKNOWN, so the NOT IN can never be TRUE. Use NOT EXISTS instead, which handles it correctly. This is one of the most-asked senior SQL questions in existence.

Normalisation, in plain terms

🧒 Simple

Do not write your friend's phone number on twenty different pages. Write it on one page, and everywhere else write "see page 14". Then when they change their number, you change one page instead of finding nineteen out of twenty and being wrong for ever after.

🎓 Professional

Normalisation removes redundancy so that each fact is stored exactly once, which eliminates update anomalies. Three forms cover practically everything you will do:

  • 1NF — atomic values, no repeating groups. No Phone1, Phone2, Phone3 columns and no comma-separated lists in a cell.
  • 2NF — no partial dependency on part of a composite key.
  • 3NF — no column depends on another non-key column. If Orders holds CustomerName, that is a 3NF violation: the name depends on CustomerId, not on the order.

Then know when to stop. Deliberate denormalisation — storing the unit price on the order line rather than joining to Products — is often correct, because the price at the time of sale is a genuinely different fact from today’s price. Being able to argue that distinction is worth more than reciting the normal forms.

SQL Server specifics

  • Schemas. dbo.Orders — always qualify. It is faster (better plan caching) and unambiguous.
  • SSMS / Azure Data Studio. The tools you will live in. Expect a screen share.
  • Collation decides sorting and comparison. The default SQL_Latin1_General_CP1_CI_AS is CI (case-insensitive) and AS (accent-sensitive) — so 'ROSSI' = 'rossi' is true in SQL Server and false in C#. That mismatch is a real bug source.
  • IDENTITY for auto-numbering; SEQUENCE when the number must be shared across tables.
  • Editions. Developer edition is free and functionally identical to Enterprise. Express is free with limits. LocalDB is the developer-machine default.

Golden rules

  1. The database outlives the application. Schema mistakes are the expensive kind.
  2. Constraints belong in the database, not only in C#. Applications are not the only thing that writes to a table.
  3. Surrogate primary key plus a unique constraint on the natural key.
  4. Money is DECIMAL. FLOAT for money is a bug, always.
  5. Text is NVARCHAR. Italian names have accents.
  6. Store UTC. Convert at the edge, where you know the user.
  7. NULL means unknown. Use IS NULL, and never NOT IN against a nullable column — use NOT EXISTS.
  8. NOT NULL wherever the fact is always known. It is free correctness and it helps the optimiser.
  9. Normalise to 3NF by default; denormalise deliberately, and be able to say why.
  10. SQL Server’s default collation is case-insensitive; C# string comparison is not. Know which side you are on.

Interview questions

"What is the difference between a primary key and a unique constraint?"

A table has one primary key, it cannot be NULL, and it is clustered by default in SQL Server. You can have many unique constraints, and each permits a single NULL.

"Why not FLOAT for a price?"

Binary floating point cannot represent decimal fractions like 0.1 exactly, so sums drift and equality comparisons fail. DECIMAL is exact base-10, and maps to C# decimal.

"What does NULL mean, and what does NULL = NULL return?"

Unknown — and the comparison returns UNKNOWN, not TRUE, because SQL uses three-valued logic. Follow up with the NOT IN trap; it demonstrates you have been bitten rather than briefed.

"Explain normalisation. Would you always normalise?"

Store each fact once to avoid update anomalies; 3NF covers most designs. And no — an order line stores the price at the time of sale, because that is a different fact from the current price. Denormalisation for reporting or read-heavy paths is a legitimate, deliberate decision.

"When would you use a GUID as a primary key?"

When ids must be generated outside the database — offline clients, distributed systems, or merging data from several sources. The cost is a wide, random clustered key causing page splits, so either use NEWSEQUENTIALID() or keep the GUID non-clustered.
