Design patterns worth knowing

Chapter 05 teaches Strategy and Decorator in depth and then names the rest without showing them. This chapter is the rest: the six patterns you meet by name in a .NET codebase and in an interview — what problem each one actually solves, the smallest code that is really it, where it earns its place, and the way each one is misused. A pattern is a name for a shape, not a thing to install; the value is that "it's a Factory" ends an argument that "there's a method that news up the right class" would drag out.

Why this chapter exists

Interviewers ask "which design patterns have you used?" and the wrong answer is a memorised list of all twenty-three. The right answer is three or four you can explain in terms of a problem you had. Every pattern here is a solution to a specific pain: a new you cannot get rid of, a class you cannot test because it reaches out to the world, a notification that hard-wires the sender to the receiver. Learn the pain first and the pattern is obvious; learn the pattern first and you will apply it where there is no pain, which is where patterns get their bad name.

A pattern is a name for a shape

🧒 Simple

A design pattern is like a knot in scouting. Nobody invented the bowline for you; it is just the knot that has proved best for "make a loop that will not slip". When you meet the same problem, you tie the known knot instead of improvising a tangle. The names matter because they let two people agree in three words — "use a bowline" — on something that would take a paragraph to describe from scratch.

The catalogue below is grouped the classic way. Creational patterns are about making objects (Factory, Builder, Singleton). Structural patterns are about fitting objects together (Adapter, and Decorator from chapter 05). Behavioural patterns are about how objects talk (Observer, Mediator, and Strategy from chapter 05). You do not need the taxonomy in an interview; you need to recognise the shape when it turns up.

Factory: hide the new behind a decision

🧒 Simple

A factory is the person at the counter you ask for "a coffee". You do not reach behind the counter and assemble the machine yourself; you say what you want and they hand back the right thing. If the café changes machines, you still just ask for a coffee.

the problem, then the factory
// ✗ the decision is copied into every caller, and every caller must change when a format is added
IExporter exporter = format switch
{
    "csv"  => new CsvExporter(),
    "xlsx" => new ExcelExporter(),
    _      => throw new NotSupportedException(format)
};

// ✓ the decision lives in ONE place behind an interface
public interface IExporterFactory
{
    IExporter Create(string format);
}

public sealed class ExporterFactory : IExporterFactory
{
    public IExporter Create(string format) => format switch
    {
        "csv"  => new CsvExporter(),
        "xlsx" => new ExcelExporter(),
        _      => throw new NotSupportedException($"No exporter for '{format}'.")
    };
}
Line by line
  • The pain is a new that depends on a runtime value. Left alone, the switch that picks the type gets copied to every place that needs an exporter, and adding a third format means finding all of them.
  • IExporterFactory.Create — callers now depend on the interface and ask for what they want by name. They never see CsvExporter, so a new format is a one-line change in one class.
  • The return type is the abstraction, not the concrete class. That is the whole point: the caller is decoupled from which implementation it gets, exactly like chapter 03c's seam.
  • Use it when object creation involves a choice, a bit of setup, or a dependency the caller should not know about. A plain constructor is better when there is no choice — a factory that only ever calls one constructor is ceremony.
  • The trap is a factory that grows a parameter for every option until it is harder to call than the constructors it hides. When that happens the answer is usually dependency injection: let the container build the graph and inject the one you need.
In .NET this is often just the DI container

The framework's own factory is IServiceProvider. You register services.AddScoped<IExporter, CsvExporter>() and ask for an IExporter in a constructor; the container is the factory. Write your own only when the choice is made at runtime from data (the format string above), which the container cannot do for you. IHttpClientFactory is the same idea shipped in the box, solving a specific lifetime problem. See chapter 14.

Builder: assemble a complicated object one call at a time

a fluent builder, and the framework you already use is one
// step by step, readable, and the half-built object is never handed out
var report = new ReportBuilder()
    .ForCustomer(customerId)
    .Between(start, end)
    .IncludingTax()
    .GroupedBy(Grouping.Month)
    .Build();

// the shape of the builder
public sealed class ReportBuilder
{
    private int _customerId;
    private bool _withTax;
    // ...
    public ReportBuilder ForCustomer(int id) { _customerId = id; return this; }
    public ReportBuilder IncludingTax()      { _withTax = true; return this; }
    public Report Build() => _customerId == 0
        ? throw new InvalidOperationException("A customer is required.")
        : new Report(_customerId, _withTax /* ... */);
}
Line by line
  • The pain is a constructor with eight parameters, half of them optional, where the call site is an unreadable row of true, false, null, null. A builder names each decision at the point you make it.
  • return this in every step is what makes it fluent — each call hands the builder back so the next call chains onto it.
  • Build() is the single place validation runs, so a half-configured ReportBuilder can exist but a half-configured Report cannot — the same "constructor is the one chance to be valid" rule from chapter 03b, moved one step out.
  • Use it when construction has many optional pieces or an order to it. For a handful of values, required and init properties with an object initialiser are simpler and need no builder at all.
  • You already use builders: StringBuilder, WebApplication.CreateBuilder(args), and EF Core's ModelBuilder are all this pattern. Recognising it is more useful than writing one.

Singleton: one instance, and why you rarely write one

🧒 Simple

A singleton is the idea that there should be exactly one of something — one scoreboard for the whole game, not one per player. The trouble is the same as the shared whiteboard from chapter 03b: if everyone writes on the one board at once you get a mess, and if it is bolted to the wall you cannot swap it out to practise.

the hand-written one, and the one you should reach for
// ✗ the classic hand-rolled singleton: global, hard to test, easy to get wrong under threads
public sealed class Config
{
    private static readonly Config _instance = new();
    public static Config Instance => _instance;   // callers do Config.Instance everywhere
    private Config() { }
}

// ✓ let the container own the single instance — one lifetime, still injectable, still fakeable
builder.Services.AddSingleton<IConfigStore, ConfigStore>();

public sealed class PricingService(IConfigStore config)   // asks for it; does not fetch it
{
    public decimal Quote(Order o) => o.Total * config.TaxRate;
}
Line by line
  • The pattern is "exactly one instance, reachable from anywhere". The second half of that sentence is the problem: a global reached through Config.Instance is a hidden dependency that no signature admits to and no test can replace.
  • private Config() and static Instance — the mechanics of the hand-rolled version. It also has thread-safety and lazy-initialisation pitfalls that Lazy<T> exists to solve, which is already a sign you are doing the container's job by hand.
  • AddSingleton<IConfigStore, ConfigStore>() — this is the singleton pattern, done properly. The container guarantees one instance for the process, and because you depend on IConfigStore, a test injects a fake instead.
  • A singleton must be thread-safe and should be immutable or internally synchronised — one instance means every request shares it, the shared-state trap from chapter 08.
  • The trap is a mutable singleton used as a convenient place to stash state. That is global mutable state with a nicer name, and it makes tests depend on each other's order.

Observer: tell whoever is interested, without knowing who they are

C# has this built in as events
public sealed class Order
{
    public event EventHandler<OrderStatus>? StatusChanged;   // the subject exposes a subscription

    public void Dispatch()
    {
        // ... change state ...
        StatusChanged?.Invoke(this, OrderStatus.Dispatched);   // notify all observers
    }
}

// observers subscribe; the Order never learns their names
order.StatusChanged += (_, status) => _email.Send(status);
order.StatusChanged += (_, status) => _audit.Record(status);
Line by line
  • The pain is coupling. Without this, Dispatch would call _email.Send and _audit.Record directly, so the Order would depend on email and auditing and grow a new dependency every time someone wants to react to a dispatch.
  • event EventHandler<OrderStatus> — the language's native Observer. The subject offers a subscription; anyone can += a handler; the subject broadcasts with no idea who is listening.
  • StatusChanged?.Invoke(...) — the ?. matters: with no subscribers the event is null, and invoking it directly would throw. It is also a snapshot, which avoids a race if a handler unsubscribes mid-notification.
  • The trap is the subscription leak. A handler holds a reference to the subscriber, so an observer that never does -= is kept alive by the subject — a memory leak in a language that manages memory (chapter 08). Long-lived publisher, short-lived subscriber, no unsubscribe: that is the shape.
  • Reactive Extensions (IObservable<T>) is Observer for streams — the same pattern when the events form a sequence you want to filter, throttle and combine.

Adapter: make a thing that does not fit, fit

🧒 Simple

An adapter is the travel plug you carry abroad. The wall socket and your charger were built to different shapes; the adapter sits between them so neither has to change. In code it is a small class that speaks your interface on one side and the awkward foreign one on the other.

your code depends on your interface, not the vendor's
// what your application wants to depend on
public interface ISmsSender
{
    Task SendAsync(string toNumber, string message, CancellationToken ct);
}

// the vendor's SDK, whose shape you do not control
//   twilio.Messages.Create(new(from, to, body));  // sync, different names, no token

public sealed class TwilioSmsAdapter(TwilioClient twilio) : ISmsSender
{
    public Task SendAsync(string toNumber, string message, CancellationToken ct) =>
        twilio.Messages.CreateAsync(new(from: _from, to: toNumber, body: message), ct);
}
Line by line
  • The pain is a dependency you do not own bleeding into your code. Call the Twilio SDK directly from twenty places and your application is welded to Twilio; the day you switch provider, all twenty change.
  • ISmsSender — the interface you wish existed, written for your needs: async, cancellable, named the way your domain talks.
  • TwilioSmsAdapter : ISmsSender — the adapter is the only class that mentions Twilio. It translates your call into the vendor's, and nothing else in the codebase imports the SDK.
  • Use it at the edges — payment gateways, SMS, storage, any third-party or legacy API. It is the practical form of Dependency Inversion from chapter 05: depend on an abstraction you own, adapt the concrete thing behind it.
  • The bonus is testing. Your services depend on ISmsSender, so a test uses a fake and never touches the network — the adapter is the seam that makes the rest of the code testable.

Repository and Unit of Work: the pattern EF Core already is

the shape, and the nuance interviewers are listening for
// Repository: a collection-like abstraction over storage
public interface IOrderRepository
{
    Task<Order?> GetAsync(int id, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
}

// Unit of Work: many changes, committed together as one transaction
await using var tx = await db.Database.BeginTransactionAsync(ct);
repo.Add(order);
inventory.Reserve(order.Lines);
await db.SaveChangesAsync(ct);        // all of it, or none of it
await tx.CommitAsync(ct);
Line by line
  • A repository is a collection you can query that happens to be backed by a database. Callers say GetAsync/AddAsync and never see SQL, so the data layer can be swapped or faked.
  • A unit of work batches changes and commits them atomically — several writes succeed together or roll back together, so a half-applied change cannot be left behind.
  • The interview point: DbContext is already both. DbSet<T> is a repository and SaveChanges is a unit of work. Wrapping EF Core in your own IRepository often just hides a good API behind a worse one, and blocks LINQ, includes and projections.
  • Use your own repository when you want the domain to depend on an interface rather than on EF Core, or to pin down exactly which queries exist. Skip it when it is a thin, leaky pass-through — the commonest over-engineering in .NET code.
  • The trap is the generic IRepository<T> with fifteen methods, twelve of which no caller uses. That is Interface Segregation (chapter 05) ignored, and it makes faking painful for no benefit.
And the one behind MediatR: Mediator

Mediator puts a middleman between senders and receivers so they do not reference each other: a controller sends a CreateOrderCommand to a mediator, which finds the one handler that deals with it. The popular library is MediatR, and it is how many .NET codebases wire up CQRS — commands and queries as messages with handlers. It genuinely decouples, and it is genuinely overused: for a small application it adds a layer of indirection over a plain method call. The full treatment, including when it pays and when it does not, is chapter 23.

Exercises, with the reasoning shown

Exercise 1 — the pattern that was not needed

public interface ICustomerFactory { Customer Create(string name); }
public sealed class CustomerFactory : ICustomerFactory
{
    public Customer Create(string name) => new Customer(name);
}
This factory adds a name, an interface and a file, and hides nothing.
  • There is one implementation, no choice, and no setup — Create just calls the constructor. A pattern with no pain to solve is pure indirection: the reader now has to open two files to learn that a Customer is made from a name. Delete it and write new Customer(name). Reach for the factory the day a second kind of customer, or a real decision, appears.

Exercise 2 — the singleton that broke the tests

public sealed class Clock
{
    public static Clock Instance { get; } = new();
    public DateTime Now => DateTime.UtcNow;
}
// used deep inside the code as Clock.Instance.Now
A test cannot make it be midnight, and two tests cannot disagree about the time.
  • The singleton is reachable globally and returns real time, so any logic that depends on "now" is untestable and non-deterministic. Replace it with an injected IClock registered as a singleton in the container; production gets the real clock, a test injects one that returns a fixed instant. Same single instance, but a seam instead of a global — the chapter 03c lesson again.
Try it yourself

Take the exporter switch from the top of the chapter and give it a third format, twice: once with the decision copied inline at two different call sites, and once behind IExporterFactory. Notice that the inline version makes you edit both call sites and the factory version makes you edit one class — and that the callers of the factory did not change at all. Then register the exporters in the DI container instead and see the factory shrink to the part that genuinely needs the runtime format string. 

public interface IExporter { string Write(Report r); }

public sealed class CsvExporter  : IExporter { public string Write(Report r) => "csv"; }
public sealed class ExcelExporter : IExporter { public string Write(Report r) => "xlsx"; }

public sealed class ExporterFactory : IExporterFactory
{
    public IExporter Create(string format) => format switch
    {
        "csv"  => new CsvExporter(),
        "xlsx" => new ExcelExporter(),
        _      => throw new NotSupportedException($"No exporter for '{format}'.")
    };
}
Line by line
  • Each exporter is a Strategy behind the shared IExporter interface; the factory is the one place that maps a string to a strategy.
  • Add JsonExporter and the only edits are a new class and one arm of the switch — the callers, which depend on IExporterFactory, are untouched.
  • Registered in DI, the exporters are constructed by the container; the factory keeps only the runtime decision the container cannot make, which is the honest minimum.

Golden rules

  1. Name the pain before the pattern. A pattern applied where there is no problem is indirection that makes the code harder to read, which is how patterns earn their bad reputation.
  2. A Factory hides a new that depends on a decision. If there is no choice and no setup, a plain constructor is better.
  3. A Builder is for many optional parts. For a few, required and init properties are simpler.
  4. Prefer the container's Singleton to a hand-written one, and keep any singleton immutable or synchronised — one instance is shared by every request.
  5. Observer decouples the sender from the receiver. C# events are it; always -= what you +=, or you leak the subscriber.
  6. Adapter keeps a foreign API in one class. Depend on an interface you own; let the adapter be the only file that imports the SDK.
  7. EF Core's DbContext is already a Repository and a Unit of Work. Wrap it only for a real reason, and never behind a generic interface with methods no caller uses.
  8. You can name a pattern with the framework feature that is it — IHttpClientFactory, StringBuilder, AddSingleton, middleware. That is the answer that shows you have used them, not memorised them.

Interview questions

"Which design patterns have you actually used?"

I would name three I can tie to a problem rather than reciting the catalogue. Strategy, to swap a pricing rule at runtime behind an interface. Adapter, to keep a payment provider's SDK in one class so the rest of the code depended on an interface I owned and the tests never hit the network. And Factory, but usually in the form the framework gives me — the DI container and IHttpClientFactory — writing my own only when the choice was made from runtime data the container could not see. The point I would make is that patterns are names for shapes I already needed, not things I set out to add.

"Is Singleton an anti-pattern?"

The goal — one instance for the process — is fine and common. The classic implementation, a static Instance reached from anywhere, is the problem: it is a global, it hides a dependency no signature declares, and it makes code non-deterministic and hard to test. In .NET I get the same single instance from the container with AddSingleton and inject it through an interface, which keeps the one-instance guarantee and restores the seam. I also keep it immutable or synchronised, because a singleton is shared by every concurrent request.

"Should you always put a Repository over EF Core?"

No, and this is where a lot of .NET code over-engineers. DbContext is already a Unit of Work and DbSet<T> is already a Repository, so wrapping them frequently hides a rich API — LINQ, includes, projections, async streaming — behind a thinner, leakier one. I add my own repository when I want the domain layer to depend on an interface rather than on EF Core, or to constrain exactly which queries exist. I avoid the generic IRepository<T> with fifteen methods, because most callers need three and faking the other twelve is pure cost.

"How do C# events relate to the Observer pattern?"

An event is the Observer pattern built into the language. The subject exposes the event, observers subscribe with +=, and the subject raises it without knowing who is listening, which is exactly the decoupling Observer is for. The thing I watch for is the subscription leak: a handler keeps a reference to the subscriber, so a long-lived publisher and a short-lived subscriber that never unsubscribes is a memory leak. For streams of events I would reach for IObservable<T>, which is the same pattern with operators to filter and combine.

"Quando useresti un Adapter?"

Quando devo dipendere da qualcosa che non controllo — l'SDK di un fornitore di pagamenti, un servizio SMS, una libreria legacy. Definisco l'interfaccia che vorrei avere, scritta per il mio dominio, e poi scrivo una piccola classe adapter che la implementa chiamando l'API esterna. Così l'unico file che conosce il fornitore è l'adapter: se cambio provider, cambia una classe sola, e nei test uso un fake senza toccare la rete. È la forma pratica della Dependency Inversion del capitolo 05: dipendere da un'astrazione che possiedo io.
